## 1. 목적과 원칙

객관식 판단은 결정 모델이 맡고, 추론 모델은 주관식이 필요할 때만 부른다.

| 판단 | 담당 |
|---|---|
| 이번 턴에 어떤 자료가 필요한가, 어느 시점(과거·현재·계획·가정) 얘기인가, 답 유형은 무엇인가 | 결정 모델 |
| 브라우저에서 다음에 무엇을 누를까, 페이지 상태는 어떤가, 목표에 도달했나 | 결정 모델 |
| 계획이 완료·취소됐다는 보고인가, 가정 분기를 어디서 시작하나 | 결정 모델 |
| 답변 문장, 시뮬레이션 서술, 검색어·입력 문장, 버튼을 누른 뒤 기대 효과(postcondition) | 추론 모델(Codex/Claude) |

- 결정 모델: OpenAI Decisions API(`POST /v1/decisions`, `gpt-6-luna` 전용). predicate·choice·score만 반환하고 문장·인자를 만들지 않는다.
- 확률은 실행 권한이 아니다. 실행 가능 여부는 기존 `classifyAction`·URL 정책·카드 권한·revision 검사가 정한다.
- 결정 호출이 실패하면 지금 방식(추론 모델이 직접 도구 호출)으로 돌아간다.
- 키·크레딧(2026-11 기준): ChatGPT Pro($100/$200/$500)·Business 좌석의 API 크레딧이 연결한 API 조직의 project key에 적용된다. Plus는 대상 아님. API 키로 쓰는 Codex는 크레딧 대상 아님.

### 구독 연결 시 판정과 추론의 비용 경로

**제품 규칙:** Decisions는 허용한 API 프로젝트에서 처리하고, 답·요약·새 교훈처럼 텍스트를 생성하는 추론은 선택한 Codex/Claude **구독 사용량**만 쓴다. 구독의 해당 요금제·연결 조직에 실제 적용되는 API 크레딧이 있을 수 있지만, 키 보유만으로 크레딧이나 무상 이용이 보장되지는 않는다. 구독에 문제가 생겨도 판정용 키·호스트의 생성 API 키·다른 사람의 로그인을 사용하지 않는다. 외부 처리 동의와 비용 주체 확인도 별개다.

**현행 차이:** 아래 Board 일회 질문의 선택형 서술 초안은 별도의 OpenAI Responses API 경로다(기본 꺼짐). 구독으로 생성하는 기능이 아니므로 구독 전용 사용의 대체 경로로 쓰지 않는다. 구독 모드에 이 구분을 전 구간 강제하는 것은 구현 과제다. 소유자의 비공개 일반 구독 대화로 연결해 문제를 해결해서도 안 된다.

## 3. 흐름

### 3.1 턴 전 컨텍스트 세팅
1. 후보 수집(코드): 이번 요청의 권한과 채널에 맞는 선택 자료, Board 자료, 온톨로지 시간선 항목 등을 열거한다. 기본 경로에서 최근 발언의 유무나 자동으로 찾은 기억 행은 외부 후보로 만들지 않는다. 명시적으로 선택한 기억 행도 일반 제목만 쓰며 줄 본문은 보내지 않는다. 별도 허용을 받은 세션 주제 이력은 아래의 전용 입력이다. 현재 메시지와 각 후보의 설명이 외부 판정 입력이 될 수 있다.
2. 결정 요청은 `answer_type`·`time_intent`와 후보의 `rel_i`를 묻는다. 발언 재사용에 별도로 동의한 일반 DM에서는 현재 메시지의 구간별 의미 문항도 한도 안에서 함께 구성한다. 보기 밖의 근거를 만들어내지 않는다.
3. 선택(코드): 필수·메시지에 이름이 나온 자료는 점수와 무관하게 포함. 나머지는 임계값 이상. 현재 시점 질문에서 계획·가정 자료는 더 높은 기준(0.8). 거절은 불명.
4. 원문 로드 → 자료마다 `[item id=… kind=… time=… status=… source=…]` 머리말 → `extraContext.egdesk_decision_context` 문자열.
5. 추론 턴: 자료로 답하고 모자랄 때만 도구 사용.

### 같은 세션에서 어느 대화를 이어가는가 (태화 Jev 원안과 로컬 구현의 대응)

**원출처.** 태화트랜스 Codex 대화 「jev 문서인가 skill인가 설치해줘. 전역으로」, 스레드 `01a0c300-c2c1-7b60-83de-34d730e68544` (2026-09-21 시작, 이하 KST). 9/24 00:10 사용자는 대화쌍을 늘려 ‘이어지는가’를 묻는 초기안을 냈다. 9/26 20:50에는 세부 문제 해결에 필요한 결정과 작업 분할의 **수직 구조**가 있어야 큰 목적을 놓치지 않는다고 했다. 10/1 09:54에는 그 구조로 실제 과거 대화를 복원하는 단계가 **문서 본문 판정보다 먼저**라고 바로잡았다. 10/2 22:10·22:24에는 단위를 스레드·턴·토픽·서브토픽·자료로 나누고, “T sub n 이 들어올때마다 그 T sub n 이 배정되는 토픽을 그냥 찾는거잖아”라고 정리했다. 저장소의 [Jev 브레인스토밍](../../../ideas/brainstorming/JEV_INTEGRATION_SUGGESTIONS.md)은 별도 문서다.

**원문의 예시.** 10/5 21:20에 당시 어시스턴트가 설명한 **기대 배정**이다. `T31`에서 대화가 온톨로지 리더 Hook으로 문서 탐색 시간을 줄이자는 목적으로 시작했다. `T70–71`은 장비 Hook 문제와 확인, `T72–74`는 그 과정에서 검사할 계정 범위를 정정한 대화다. `T75`에서 사용자가 “jev hook 흐름 정리해줘봐”라고 하면 마지막 계정 이야기의 연장도, 별개 새 토픽도 아니다. `T31`의 토픽으로 돌아가되 `T70–74`의 결정 경위를 함께 쓴다. 두 끝점만 남기면 설명에 왜 검사 범위가 바뀌었는지가 빠진다. 다른 형제 토픽까지 일괄 첨부하는 것도 아니다.

**당시 어디까지 됐나.** 9/27의 과거 재생에 대해 당시 어시스턴트는 72쌍 중 54쌍을 골랐고 부모 관계도 저장했다고 보고했다. 10/1 10:16에 같은 어시스턴트는 그 관계로 누락된 하위 대화를 되살리지는 않았다고 명시했다. 10/5 설명은 이를 보완하는 이상안이다. 54는 정답 수나 정확도가 아니며 재생은 실사용 자동 Hook 또는 EG-Desk 시험이 아니다.

**EG-Desk에 가져올 순서**

1. **토픽 배정.** 호스트가 현재 사용자 원문 `Tn`(답변은 아직 없음), 같은 스레드의 허용된 이전 턴(사용자 원문 + 당시 최종 답변), 시간순서·시작 턴·토픽 소속·부모 관계를 준비한다. 판정자는 호출 간 기억에 기대지 않는다. 예문을 먼저 읽고서 미리 정답 보기를 만드는 대신, 저장된 실제 후보마다 ‘이 토픽에 배정’ 또는 ‘이 토픽 아래 분리’, 그리고 ‘별개 새 토픽 / 판별 불가’를 호스트가 구성한다. 복귀는 오래된 기존 토픽에 다시 배정하는 경우다. 직전 것 하나가 그럴듯하다고 후보 검색을 끝내지 않는다. 모델은 제목이나 ID를 쓰지 않고, 채택할 수 있을 때만 호스트가 소속과 관계를 기록한다.
2. **원문 경로 복원.** 어느 토픽인가와 어느 근거가 필요한가는 별개다. 이번 턴에 연결된 상위 목적, 하위 문제·정정·결정, 복귀 요청을 원문 순서로 묶고, 연결되지 않은 곁가지만 뺀다. ‘정정할까요?’와 ‘그렇지, 고쳐’처럼 혼자서는 뜻이 달라지는 턴은 함께 다룬다. 무관한 형제를 모두 넣지도, 문서와 단어가 다르다는 이유로 필요한 중간 턴을 두 번째로 잘라내지도 않는다. 입력을 나누면 근거 참조로 다시 엮고, 문맥이 부족하거나 판정이 충돌하면 미해결로 남긴다.
3. **그 뒤 자료 판정.** 복원한 흐름과 현재 요청을 기준으로 허용한 자료의 실제 조각에 대해 ‘이 작업에 필요한가’를 판정한다. 같은 스레드·같은 압축 구간에서 같은 버전·범위가 이미 전달됐고 아직 사용 가능한 조각만 **판정 전** 중복으로 제외한다. 바뀐 조각, 지난번 무관했던 조각, 압축 뒤 잔존을 모르는 조각은 다시 후보가 될 수 있다. ‘이미 있음’, ‘무관’, ‘권한 없음/미해결’, ‘선택했지만 미전달’은 다른 결과다. 선택 판정은 전달·읽음·사실 증명이 아니다.

**판정 입력 예시(설계, 허용된 수신자에 한함).** `input`에는 T75 원문과 후보 토픽의 시작·소속 턴 원문쌍 및 부모 관계를 넣는다. `choice(route)`의 보기는 예컨대 ‘T31 리더에 배정 / T70 장비에 배정 / T72 검사 범위에 배정 / 각 후보 아래 분리 / 별개 / 미상’이다. ‘각 후보 아래 분리’는 실제 요청에서 부모마다 다른 보기다. 이미 지시·정정 대상으로 명시된 연결은 그대로 보존한다. 새로 의미 판단이 필요한 연결도 코드가 시간순서나 단어 일치로 확정하지 않는다. 예컨대 ‘T72~74의 범위 결정은 T75에 설명할 절차를 바꾸는가?’를 후보별로 물어 원문을 볼 수 있는 판정자에게 선택하게 하거나, 답변 Agent가 근거 턴을 지목한다. 호스트가 참조·범위·수신자 권한을 검증한 뒤에만 필요한 연결로 사용한다. 고정 후보로 명확한 배정과 근거를 고를 수 있으면 한 호출에 묶고, 보기가 없거나 맥락을 줄 수 없으면 ‘미상’이다.

**EG-Desk 고유의 경계.** 기본 선별이나 최근 발언 허용은 과거 원문을 외부로 보낼 권한이 아니다. 별도로 허용한 기존 Codex Agent DM에서만 아래 증분 경로가 작동한다. 위 1·2의 토픽 배정·근거 복원은 연결됐다. 3의 토픽별 문서 재검색, 전송 영수증에 따른 중복 조각 제거, 자동 후속 판정은 범용 기능으로 구현되지 않았다. **검증 범위.** [오프라인 인수 예제](../scripts/egdesk-session-context-tree.acceptance.test.mjs)는 일반화한 합성 발언과 미리 준 배정·종속관계로 실제 토픽 트리와 턴 경로를 만든다. 비연속 복귀, 필요한 하위 결정 보존, 무관한 형제 제외, 분리·새 토픽·유보, 다른 스레드·철회·누락·순환 시 보류, 자료 판정 순서와 원래 이력 불변을 검사한다. 런타임 import가 없고 의미 판정 정확도나 속도·비용을 재지 않는다.

#### 일반 Codex Agent DM: 어느 원문을 보내고 언제 연결을 확정하는가

**API가 받을 수 있는 것과 앱이 보내는 것은 다르다.** 2026-11-20에 확인한 [OpenAI Decisions 가이드](https://developers.openai.com/api/docs/guides/decisions)의 ‘Evaluate a conversation’은 이전 user 메시지와 assistant 출력, 현재 user 메시지를 순서대로 `input`에 넣는 계약이다. 호스트가 보낸 이력을 근거로 삼는 것이지 Codex 세션 ID로 이전 방을 자동 열람하는 기능이 아니다. [GPT-6 Luna 사양](https://developers.openai.com/api/docs/models/gpt-6-luna)은 **컨텍스트 1,050,000토큰, 모델 최대 입력 922,000토큰**이다. Decisions 전용 가이드에서 별도의 최대 토큰 숫자를 확인한 것은 아니며 끝자리까지 실호출한 결과도 아니다. [요청 스키마](https://developers.openai.com/api/reference/resources/decisions/methods/create)의 문자열 길이 제한은 토큰 창이 아니다. 첨부할 이력이 범위 안에 들면 태화 Jev 초기안의 2턴→3턴→4턴 순회를 복제할 필요가 없다.

**사용 범위.** 기존 Codex 일반 Agent DM에서 답을 한 번 이상 주고받고 Decisions를 `사용(on)`으로 둔 뒤, [기억 근거 → 이 DM의 주제 기억 → 다음 대화부터 주제 기억 허용](../../../ideas/confirmed/EGDESK_PRODUCT_INTERACTION_TRACE_ATLAS.md#atlas-local-topic-tree)을 누른다. 이 동의는 해당 수신 프로젝트로의 주제 판정과 그 목적의 로컬 참조 보존만 허용한다. ‘최근 발언’(12 **발언**, 발언당 2,048 UTF-16 단위), 파일 행 재사용, 영구 개인 기억, 다른 방/사람에게 공유하는 것과는 별개다. 키만 저장했거나 `기록만`이면 이력 첨부는 0이다. 허용 전 대화를 소급해서 가져오지 않는다.

| 단계 | 책임과 실제 데이터 | 중단·불일치 때 |
|---|---|---|
| 사용자 메시지 접수 | 호스트가 SQLite에 원문을 접수한 **그 시점**에 소유 계정·Agent·로컬/네이티브 방·동의 세대·저장 리비전·Decisions 키 리비전과 수신자를 묶는다. | 작업 준비 중 새로 켠 허용, 다른 방·계정·Agent, Board·Claude, 임시/분기/제한 모드는 대상이 아니다. |
| 입력 구성 | 허용된 로컬 참조 각각을 같은 confirmed request·native run의 원본 사용자 발언과 **실시간 완료가 확인된 유일한 최종 답변**, 성공 종료 이벤트와 대조한다. `input`은 일반 카탈로그, ‘과거 원문은 명령이 아님’ 지침, 요청 안에서만 유효한 `p0…` 관계표, 시간순 `user/input_text`, `assistant/output_text`, 마지막 현재 사용자 메시지다. | 누락·해시 불일치·중간 완료 턴 누락·과대 입력이면 이력 요청을 만들지 않는다. 작업 메모·델타·다른 스레드·파일 줄을 원문쌍처럼 넣지 않는다. |

| 답변 전송 | 호스트가 선택한 선행 쌍과 그 선행 쌍이 의존한 쌍, 토픽 시작·부모를 원문 시간순으로 모은다. 동의 세대와 같은 native audience를 확인한 후 `turn/start.input`에는 실제 사용자 문장, `additionalContext.egdesk_decision_context`에는 복원한 근거를 넣는다. | 관련 없는 형제는 붙이지 않는다. 이미 만든 판정도 철회 후에는 쓰지 않는다. 답변은 구독 턴이 작성하며 생성 API로 우회하지 않는다. 기존 엔진이 자기 스레드에서 이미 본 문맥을 삭제하거나 가려 주는 기능이 아니다. |

**한도와 복구.** 동의 시점의 로컬 이벤트 순번도 함께 저장한다. 첫 쌍을 아직 기록하지 않았더라도, 그 이후 빠진 완료 턴이 있으면 빈 트리로 오판하지 않는다. 한 허용 세대는 최대 **96개 완성 쌍**이다. 가득 차면 그 구간의 주제 선별·추가 저장을 멈추며 오래된 가지를 자동으로 지우지 않는다. 현재 제품은 토픽용 이력 입력 전체의 직렬화 크기 **96 KiB**, 직접 필요 연결 **24개**, 답변용 토픽 근거 **24 KiB**를 넘기지 않는다. 이는 현재 메시지·일반 후보·문항까지 포함한 공급자 요청 전체의 한도나 모델의 토큰 창이 아니다. 로컬 원문이 불완전하거나 중간 정정을 검증할 수 없는 동안에는 옛 트리를 완전한 것처럼 쓰지 않는다. 필요한 결정을 메시지에 직접 적어 일반 대화를 계속할 수 있고, 과거 연결 없이 새로 시작하려면 주제 기억을 철회·삭제한 뒤 다시 허용한다. 키 또는 대상이 바뀌어도 자동으로 권한을 옮기지 않는다. 철회는 일반 채팅 원문을 지우거나 이미 전달된 공급자 입력을 회수하지 않는다.

**비용과 권한.** 기본 대기 예산은 800ms이지 실측 왕복 시간이 아니다. 모델 사양이 1M급이어도 매번 전체 세션을 보내지 않는다. 허용된 후보를 한 요청에서 읽을 수 있는 것과 이미 확정된 주제 트리를 다시 쓰는 일은 다르다. 토픽을 먼저 골라야 문서 후보가 생기는 경우는 별도 허용·조회와 후속 문항이 필요한 **후속 설계**다. 이 구현은 새 native 도구나 구형 스레드 manifest의 변경을 요구하지 않는다. 파일·메모리 판정 권한을 주제 권한으로 확대하지 않는다. 기록된 질문과 답에 사람이 실제로 적거나 인용한 내용도 **발언 원문**으로 전송될 수 있으므로 전송을 원하지 않으면 이 허용을 켜지 않는다.

**확인한 것과 아직 모르는 것.** [실제 일반 DM 런타임 통합 시험](../helper/egdesk-memory-evidence-wiring.test.mjs)의 `production topics`는 가짜 판정기가 실제 요청만 읽게 하고, 실제 채팅 런타임과 재개한 SQLite에서 두 갈래를 거친 같은 대여 질문을 보낸다. 앞선 ‘서가 1 / 서가 2만’ 정정만 바꾸면 선택된 근거와 구독 입력이 바뀌어 합성 답변이 각각 **8권 / 21권**이다. 같은 부모의 전시 주제는 제외되고, 다음 재질문은 저장된 종속 연결을 따라간다. 별도 사례에서는 초기 결정·정정을 남긴 다음 무관한 안건 8개를 거쳐 재시작해도 최근 12발언 밖의 근거만 정확히 복원했다. 외부 허용·응답·native 송신 사이의 철회, 키 교체, 누락한 판정, 중단된 답도 분리해 검사한다. 이전 `opt-in prototype`의 17건/43건은 장부 선택을 실험한 **시험 전용** 경로다. [판정기](../helper/egdesk-session-topic.mjs)와 [저장소](../helper/egdesk-memory-evidence.mjs)는 제품 코드지만, 실모델의 한국어 의미 정확도, 응답 시간·비용, 대규모 세션 성능, 출시 또는 라이브 계정 동작은 이 결과로 검증되지 않는다. 독립 라벨과 동일 native 이력의 on/off 대조가 필요하다.

<a id="temporal-refinement"></a>
### 자연어 시간을 해석한 뒤 달력을 계산하기 (제안·일반 DM 미구현)

1. **맥락부터.** ‘11월 2일 회의에서 “다다음 주에 납품하자”고 했잖아. 그게 언제야?’라면, 먼저 무엇을 묻는지(납품 **예정** 기간)와 어느 발언이 기준인지(11월 2일 회의)를 사용자 원문·허용된 대화에서 판별한다. ‘다다음 주’ 문자열이나 질문 시각만으로 코드는 이 관계를 정할 수 없다.
2. **의미가 정해진 뒤 산술.** 2026년 11월 2일 발언 + 2주 뒤 + 주 단위 + 서울·월요일 시작이라면 호스트가 11월 16~22일로 계산한다. 발언의 기준일을 특정할 수 없으면 오늘을 대입하지 않는다. 작성일·계획 대상일·질문일은 별개이며 실제 납품을 증명하지 않는다.
3. **닫힌 문항은 선택적으로.** 권한 있는 실제 기준 사건·역할 후보가 있을 때만 보기를 묻는다. 보기가 표현하지 못하는 관계는 허용된 구독 추론이 원문에서 해석하거나 미상으로 남긴다. 독립 문항은 묶을 수 있으나 ‘기타’라는 이유로 월→일→시를 순차 호출하지 않는다. 앞선 배정으로 구별할 새 근거가 생길 때만 제한된 후속 판정을 한다. 일반 Chat의 기본 800ms는 후보 수집·선별 **대기 한도**이지 공급자 평균 속도가 아니다. 아래 가정 분기 도우미는 같은 세션의 토픽 트리나 날짜 검색 구현이 아니다.

<a id="time-selects-evidence"></a>
#### 기준 시점이 결정하는 것은 날짜뿐 아니라 **조회할 기록**이다 (제안·미연결)

예를 들어 ‘주간 사용량이 72%입니다’를 인용하며 ‘혹시 ultrafast 쓴 건 아니겠지?’라고 물었다. `ultrafast`는 질문자가 사용한 표기다. 제품이 그 이름의 실행 모드나 완전한 사용량 장부를 제공한다고 가정하지 않는다. 질문은 그 보고와 관련된 실행을 묻는다. 오늘 실행 중인 작업자가 무엇인지를 묻는 것이 아니다.

1. **조회 전에 대상을 고른다.** 인용을 원 발언/보고에 연결하고, 그 보고가 관찰한 기준 시각·집계 구간/시간대, 대상 계정·해당 작업이나 세션을 가능한 범위에서 식별한다. 질문 수신 시각, 인용 발언 시각, 보고가 가리킨 기간, 지금 기록을 읽는 시각은 다를 수 있다. 초기화 예정일만으로 기간 시작·정확한 보고 시각·시간대를 역산하지 않는다. 특정 작업을 지목한 질문을 계정 전체 주간 감사로 몰래 확대하지 않는다.
2. **맞는 자료로 보낸다.** ‘그때’에는 허용된 원 세션의 실행 기록과 귀속이 확인된 하위 실행·모드 변경을 해당 기간까지 읽는다. 이미 종료·취소된 실행도 대상일 수 있다. 현재 살아 있는 실행이라도 **당시 구간의 기록**만 당시 사실에 쓸 수 있다. 가동 중 목록, 현재 기본값이나 지금 새로 시작한 작업은 과거 근거가 아니다. 지금 띄운 조회 작업자가 과거 원본을 읽는 것은 가능하다. 과거 세션 접근·외부 모델 전송은 별도 범위이며, 접근할 수 없다면 현재 목록으로 대체하지 않는다.
3. **증명할 수 있는 만큼만 말한다.** 당시 요청한 모드, 실제 적용된 모드(중도 변경 포함), 공급자가 계량한 사용량은 별도다. 한 실행에 적용 기록이 있으면 그 실행에서 사용했다는 것은 말할 수 있다. 전체 기간에 안 썼다고 하려면 관련 기록과 모드 항목이 빠짐없이 확인되어야 한다. 72%라는 합계만으로 모드의 사용 여부나 기여분을 단정하지 않는다. 기록 누락이면 ‘확인한 실행에서는 없고, 나머지는 확인 불가’처럼 범위를 밝힌다.
4. **현재 요청의 진행 표시도 같은 대상을 따른다.** 과거 보고를 조사할 때는 ‘인용한 보고 당시의 실행 기록 확인 중’이라고 표시한다. 일반적인 PR 소통 가능 여부를 묻는 새 질문에 무관한 다른 작업의 완료·진행을 붙이지 않는다. 나란히 표시된 UI 문구는 배정 오류를 의심할 단서이지, 실제 도구 호출 증거는 아니다. 요청·인용·세션·실행의 대응을 확인해야 한다.

**가상 인수 사례 (미실행):** 과거가 빠른 모드·현재가 일반인 경우와 그 반대에서 과거 답은 각각 뒤집혀야 하고, 현재 목록만 바꾸면 뒤집히지 않아야 한다. 같은 날이어도 보고 이후에 시작한 실행은 제외한다. 권한 없는 다른 방에만 기록이 있거나 당시 **요청 설정만** 남은 경우는 실제 적용 미확인이다. ‘그때와 지금이 달라?’에는 과거 기록과 현재 관찰을 따로 조회·표기한다. 범위 밖 작업자의 완료 통지는 이 질문의 진행이나 답이 되지 않는다.

**현재 경계:** [시간 분류 도우미](../helper/egdesk-context-setup.mjs)의 `time_intent`는 과거·현재·계획·가정·비교 등을 구별하는 분류이지 어떤 과거 세션을 열라는 조회가 아니다. [계정 사용량 표시](../helper/codex-account-usage.mjs)는 관찰한 사용 한도를 표시할 수 있으나 어느 실행이 몇 %를 썼는지 기록하는 장부가 아니다. 현재의 [같은 DM 주제 기억](#membrain-turn-wire)은 다른 세션을 열 권한도, 당시 실행 모드를 증명할 근거도 아니다. [기술 계약](../../../ideas/confirmed/EGDESK_INTERACTION_AND_ORCHESTRATION_CONTRACT.md#tech-temporal-evidence) · [사용자 예시](../../../ideas/confirmed/EGDESK_PRODUCT_INTERACTION_TRACE_ATLAS.md#atlas-quoted-usage-time)

### 3.2 가정 분기와 시간선 전이 (도우미 설계·시험, 사용자 흐름 미연결)
- 분기: 기준 상태 choice → (의존) 그 기준에 속한 사실 predicate → 기준·사실·가정(사용자 원문)을 묶어 추론 1회.
- 전이: 열린 계획 항목 choice + 전이 종류 choice. 완료·취소는 고정 문구로 확인 제안(추론 없음), 변경은 추론 필요.

### 3.3 브라우저 반사 (`egdesk_browser_reflex`)
- 추론 모델이 자기 run 안에서 한 번 부르는 추가 도구. 매 단계는 기존 `egdesk_browser_*` 도구를 그대로 거쳐 카드 권한·행동 분류·같은 사이트 정책·revision·receipt가 모두 적용된다. run 밖 helper 단독 루프는 카드 binding이 없어 지원하지 않는다.
- 스스로 하는 것: 같은 사이트 링크 이동(url postcondition), 스크롤, 받은 값으로 입력(target-value postcondition), 로딩 대기, 목표 도달 시 종료.
- 돌려주는 것: `needs_free_text`(쓸 문장 필요), `escalated`(버튼·탭은 기대 효과를 모델이 정해야 함, 불확실, 차단), `handoff`(로그인·2단계·봇 검사), `fallback`(결정 모델 불가).
- 결제·권한·삭제·제출 요소는 후보에 들어가지 않는다. 비밀번호 역할 입력칸과 민감 라벨 입력칸도 제외.

## Board의 일회 질문은 일반 채팅과 다르다

Board 소유자가 활성 Agent 버전, 공개 발췌, 공개할 답변 작성 지침을 따로 지정한다. 상대는 Profile 파일이나 로그인 세션을 받지 않는다. 요청 파일은 질문 코드를 담을 때 반드시 암호화한다. 파일을 열면 내용을 볼 뿐 코드나 모델 사용량을 소모하지 않는다. 현재 Board에서 소유자가 공개 범위를 확인하고 실행해야 질문 코드를 소비한다. 초안은 파일에 자동으로 쓰거나 전송하지 않는다.

- **로컬 발췌**: 허용된 문장에서만 질문과 관련 있는 발췌를 고른다. 적절한 발췌가 없으면 빈 답으로 남긴다. 외부 호출은 기본값이 아니다.
- **외부 선별**: 소유자가 이번 요청에 별도로 동의하면 Decisions에 질문과 화면에 표시한 후보 발췌만 보낼 수 있다. 비공개 Agent 지침, 요청자 파일의 부가 설명, 실제 Board/사용자 ID는 보내지 않는다. `advisory`에서는 외부 판단이 로컬 선택을 바꾸지 않는다.
- **서술형 초안**: 요청마다 별도 승인한다. 전용 OpenAI Responses 경로에 질문, 선택된 발췌, 공개 작성 지침, 제한된 말투만 보낸다. 개인 대화·파일·도구·이전 응답은 연결하지 않는다. 조건에 맞는 발췌나 전용 설정이 없으면 일반 Chat이나 구독 계정으로 대체하지 않는다. 특정 엔진/계정에 연결된 Agent도 다른 비용 주체로 바꾸지 않는다.

초안 서비스는 기본 꺼짐이다. 운영자가 명시적으로 사용하기로 한 경우에만 `<앱 데이터 디렉터리>/settings/board-agent-draft-service.json`에 `version`(숫자 `1`), `provider`(`openai`), `apiKey`(별도 발급), `model`(허용된 정확한 모델 ID) 네 필드를 설정한다. 본 경로에서 허용한 모델은 `gpt-4.1-mini-2025-04-14`, `gpt-4.1-nano-2025-04-14`다. POSIX에서는 본인 소유의 `0700` 설정 폴더와 `0600` 파일을 사용한다. Windows에서는 같은 사용자와 시스템/관리자 외의 주체가 접근할 수 없도록 기존 보안 정책을 적용한다. 키는 환경변수·대화·Board·검토 파일에 넣지 않는다. 설정이 유효해 보인다는 표시는 실제 계정의 모델 사용권, 결제 주체 또는 연결 성공을 검증한 것이 아니다.

## 장부 행에서 원본까지: 일반 Agent DM의 선택 근거

`MemoryEvidenceStore`는 선택한 **장부 한 줄**을 같은 대화에서 캡처한 원본의 정확한 버전과 줄에 연결한다. `counted`는 ‘실사로 연결한 기록’이라는 뜻이지 시스템이 현물을 직접 보았다는 보증이 아니다. `posted`(처리 완료)와 `scheduled`(예정)는 다른 관계다. `copied`는 독립된 관측이 아니다. `present`는 질문의 현재 범위에 해당한다는 뜻이며 실측 여부와 독립적이다.

**신뢰된 로컬 호출자용 API.** `scope`는 실제 대상 계정·Agent·DM을 확인하고, 소유자가 해당 범위의 원본 재사용을 허용한 뒤 만드는 `{ownerKey, agentId, clientThreadId}`다. HTTP/body/문서 안의 필드에서 만들면 안 된다. 일반 Agent DM의 **기억 근거** 화면은 인증된 `/memory-evidence/` 관리 경로를 사용한다. 열린 파일 전체를 검색하거나 다른 대화의 캡처를 가져오지 않는다. `dataDir`는 앱 전용 디렉터리이고, `captures`는 기존 `ImmutableContextStore` 인스턴스다.

```js
const evidence = new MemoryEvidenceStore({ dataDir, captures })
const line = (capture, n) => ({ sourceId: capture.sourceId, revision: capture.revision, startLine: n, endLine: n })
const id = await evidence.bind(scope, {
  ledger: line(ledgerCapture, 4),
  sources: [{ relation: 'counted', ...line(stocktakeCapture, 12) },
            { relation: 'posted', ...line(dispatchCapture, 2) },
            { relation: 'coverage', ...line(movementWindowCapture, 1) }],
  discovery: { label: 'A창고 재고', terms: ['재고', '몇 개'] }, // 생략하면 자동 조회하지 않는다.
  expiresAt, // 생략하면 명시적으로 해제할 때까지. 날짜를 모른다는 뜻이 아니다.
})
// 기존 selectedSources에 { id, kind: 'memory-evidence', label: '장부 행' }로 명시 선택한다.
const trace = await evidence.read(scope, id) // 같은 권한으로 원본 줄·sourceId·revision을 확인. 불가하면 null.
evidence.revoke(scope, id)                  // 영속 철회. 다시 동의할 땐 별도 bind로 새 ID를 발행한다.
evidence.close()
```

선택은 권한이 아니다. `on`인 확인된 일반 DM에서만 원문을 늦게 로드한다. 판정 모델에는 일반 제목만 주고, 답변 모델에는 허용한 줄과 관계만 준다. 패킷이 잘리거나 원본이 없거나 철회됐다면 일부만 붙이지 않는다. 네이티브 턴에 넘기기 직전에도 권한을 검사한다. 파일명이 같은 새 캡처로 대체하지 않는다. Board나 과거 채널을 확인할 수 없는 대화에는 붙이지 않는다. 철회는 **향후 원본 읽기·새 전달**을 막는다. 이미 상대 엔진에 보낸 값이나 공개한 답변을 소급 지우지는 않는다. 기존 네이티브 대화의 히스토리는 이 원본 연결 권한과 별개다. 비공개 근거를 전달할 때 기존 DM의 네이티브 대화를 계정·Agent·로컬 대화에 영속 귀속한다. 다른 Agent·Board·검증되지 않은 세션 재개·분기로 같은 과거 입력을 상속하지 않는다. 이전 버전에서 이미 전달된 입력을 소급 봉인하지는 않는다.

**제품에서 사용하기.** 한 번 이상 답변을 주고받아 Agent와 계정이 확인된 일반 DM에서 자료를 먼저 캡처한다. ‘기억 근거’를 열고 장부 한 줄, 실사 등 원본 줄, 관계, 이름과 호출할 표현을 골라 동의한다. 컨텍스트 설정이 `on`일 때 다음 메시지부터 별도 선택 없이 조회한다. 동점이면 어느 장부도 선택하지 않고, ‘왜?’ 같은 짧은 후속 질문은 같은 대화에서 바로 앞에 공개된 답변의 실행 ID에 연결된 활성 원본만 사용한다. 후속 조회 기록은 입력을 보냈다는 표시이지 모델이 이를 읽거나 사용했다는 증명이 아니다. 모호한 수량만으로 출처를 찾지 않으며, 작업 노트나 전체 파일을 숨은 근거로 가져오지 않는다. 관리 화면에서 ‘직전 답에 전달된 근거’를 누르면 같은 이름이나 수량으로 찾아내지 않고, 그 실행에 실제 전달한 원본을 연다. 유일한 활성 연결이 없으면 버튼을 표시하지 않는다. 원본 보기와 철회는 채팅 발언을 만들지 않는다. 이전 버전의 수동 연결은 마이그레이션 후에도 자동 등록되지 않는다.

### 질문의 시각과 검증의 경계

“장부에 몇 개라고 적혀 있어?”는 해당 행으로 답할 수 있다. “지금 몇 개야?”는 실사 시각부터 질문 시각까지 **완료된 변동과 그 기록이 덮는 기간**도 봐야 한다. 예를 들어 9시 실사 30개, 이후 출고 완료 2개, 10시까지 다른 변동이 없다는 근거가 있으면 “지금 28개예요.”라고 답한다. 예정 출고는 빼지 않는다. 그 기간의 기록이 빠졌다면 마지막으로 확인된 값과 지금 값을 구분한다. 이유를 물었을 때만 계산 근거를 풀어서 설명한다.

호스트가 확인한 것은 **허용한 캡처 버전의 해당 줄이 일치한다는 것**이다. 답변 모델에는 실사 보고·장부 기재·추론·복사·예정을 구분해 전달한다. 캡처 시각을 실사 시각으로 대체하지 않는다. ‘과거지만 정확한 날짜는 모름’, ‘현재 유효하고 종료 기한은 정하지 않음’, ‘언제의 일인지 모름’도 서로 다르다. 이는 모델에 전달하는 해석 기준이지, 모든 발언을 자동 분류하거나 현물을 독립 검증한다는 뜻이 아니다.

새 격리 Firefox의 실제 DM과 Board 화면, 채팅 런타임·저장소에서 등록, 자동 조회, 직전 답에 전달된 원본, 철회와 브리지 재시작, Board 미전달을 확인했다. 이때 답변 공급자와 판정 모델은 합성이었다. 검증 대상은 **어느 원본이 누구에게 전달되는가**와 그 결과가 화면에 표시되는 경로다. 실제 모델이 항상 같은 수량을 계산하는지, 운영 자료가 실제 재고와 일치하는지는 이 검증으로 알 수 없다.

**이름:** `MemBrain`은 작업명이다. `Membrain`이라는 영업 CRM이 이미 있어 공개 제품명으로는 혼동 소지가 있다. 상표권은 조사하지 않았다.

## MemBrain에 파일과 기억 조각을 넣는 규약

**파일은 판단의 원본이고, 기억 조각은 다음 판단에 재사용할 주장·교훈 하나다.** 업로드, 의미 해석, 저장 허용, 사용 허용은 서로 다른 일이다. 아래 공통 규약은 설계 계약이다. 모든 단계를 제공하는 범용 HTTP/MCP 쓰기 도구가 이미 있다는 뜻이 아니다.

1. **원본 접수.** 파일은 허용된 파일/캡처의 `sourceId + revision + startLine/endLine`으로, 발언은 해당 대화에서 호스트가 실제 접수한 사용자 메시지나 완료된 Agent 최종 발언의 ID·이벤트 순번·원문 해시·문자 범위로 고정한다. 파일 경로·이름·검색어·다른 문서의 요약은 원본 ID가 아니다. 원본 없이 사람이 직접 알려준 것도 ‘그 사람이 그렇게 말했다’는 발언을 원본으로 삼을 수 있다. 출처 없는 주장을 관측 사실로 등록하지 않는다.
2. **조각 제안.** 사람 또는 허용된 Agent가 한 조각에 한 주장·결정·교훈과 근거 참조를 제안한다. 발언자와 그 발언에서 인용한 사람은 분리한다. 관측 **보고**, 전언, 기록, 계산·추론을 구분하고, 예정·조건·질문을 완료 사실과 구분한다. 혼합 문장을 믿을 만하게 나눌 수 없으면 해당 축을 미상으로 남긴다. 디지털 기록 확인은 현물 확인이 아니다.
3. **시점·권한 검사.** 접수·캡처 시각, 발언 시각, 사건·계획의 시점 또는 유효 기간은 별도 값이다. ‘금요일’은 원래 발언 시각·당시 시차와 연결하고, 정확한 시각이 없으면 만들지 않는다. 재사용 시 ‘현재’의 범위는 질문자가 정한다. 호스트가 계정·Agent·방·동의·원본 버전·범위를 확인한다. 모델은 분류할 수 있지만 자신의 쓰기/공유 권한을 발급하지 못한다.
4. **등록 또는 보류.** 제안된 범용 쓰기 계약에서는 `operationId + 대상 범위 + 입력 지문`이 같은 재시도는 기존 `fragmentId/revision` 영수증을 돌려준다. 같은 요청 ID에 다른 내용은 충돌이다. 허용되지 않은 원본은 거부한다. 사실 여부가 미확인이어도 발언을 전언으로 보존할 수 있다. 새로 확인되거나 정정된 내용은 별도 리비전/조각으로 추가하고 `supports`, `contradicts`, `supersedes` 또는 `refines`로 잇는다. 같은 원본의 복사본은 독립 근거로 세지 않는다. 접수 영수증은 저장 결과이지 내용이 참이라는 증명이 아니다.
5. **승격은 별개.** 같은 방의 최근 발언이 개인 장기 기억이나 Board 공개 기억이 되는 건 아니다. 경험에서 교훈을 뽑는다면 원래 사건에 대한 인용이 아니라 별도의 **추론**, 적용 조건·예외·근거 링크를 갖는 제안이다. 장기 보존이나 다른 수신자에게의 공유는 별도 허용을 받으며, 재사용 직전에도 권한을 다시 확인한다. 철회는 이후의 읽기·전달을 막지만 이미 보낸 답변을 지우지는 않는다.

**예시:** 회의록 7행에 “금요일 출고 예정”이 있으면 조각 A는 ‘예정’이다. 나중에 전표 2행에 출고 처리가 기록되면 B는 ‘처리 기록’이고 A의 계획과 연결된다. 전표를 인용한 메일을 또 넣어도 현물 관측이 하나 더 생기지 않는다. 약속이나 전표만으로 수취 완료까지 주장할 수 없다.

### 현재 제품에서 넣는 방법

- **파일:** 인증된 로컬 `POST /context/captures`로 원본 버전을 고정한다. 일반 Agent DM에서 `기억 근거`를 열어 장부 한 줄과 근거 1~6개의 줄·관계를 미리 확인하고 허용하면 `POST /memory-evidence/bind`가 `memrow:…`를 반환한다. `read`·`revoke`는 같은 권한을 요구한다. **현재의 `bind`는 호출마다 새 ID를 만들며 범용 중복방지 영수증이 아니다.** 임의 파일 업로드나 일반 텍스트를 장기 기억으로 승격하는 API도 아니다.
- **일반 대화:** 컨텍스트 설정이 `on`인 검증된 Agent DM에서 `기억 근거 → 이 DM의 다음 발언부터 허용`을 선택한다. `/memory-evidence/speech-enable`과 `/speech-disable`(같은 `/memory-evidence` 경로 아래)은 현재 Agent·방을 확인하고 동의를 열고 닫는다. 이전 대화는 소급하지 않는다. 파일 행의 동의로는 켜지지 않는다. 현재 메시지만 기존 판정 호출에서 문장별 의미를 제안받는다. 비공개 동의 저장소에는 원문 대신 로컬 메시지 ID·검증용 해시·발언 시각과 시차·해석 범위가 있는 최근 12개 참조만 유지한다. Agent 자신의 답변은 ‘이 Agent가 이렇게 말했다’일 뿐 독립 증인이 아니다.
- **다음 턴:** 선별 모델에는 과거 발언의 본문·발췌가 없는 목록만 준다. 이전 대화가 필요하다고 선택된 경우에만 실제 답변 Agent가 같은 DM의 원본과 확인된 인용 범위를 받는다. 이 발췌는 해당 기간에 일어난 모든 사건의 완전한 기록이 아니다. 작업 메모·가져온 대화·다른 Agent·Board는 대상이 아니다. 발언 동의를 철회한 뒤 재허용하면 새 동의이며 예전 참조는 되살리지 않는다. 판정 모드만 바꾸는 것과 다르다. 이 경로는 기존 네이티브 대화 이력을 지우지 않는다. 시스템이 확인하는 것은 발언 원문과 그 수신 범위이지 그 사람이 말한 사건의 진위가 아니다.
- **아직 설계:** 파일·발언을 임의의 의미 조각으로 **범용 등록**하는 API, 교훈 자동 승격, 공통 중복방지 영수증과 정정 관계 그래프. 위 필드는 제안 규격이지 현재 HTTP 요청에 임의로 넣어도 된다는 뜻이 아니다.

### 읽기/쓰기가 아니라 선택/생성이 모델의 경계다

- **호출:** 호스트가 허용된 근거 후보를 열거하고 판정 모델은 관련 후보, 시점, 응답 유형 또는 ‘해당 없음’을 고른다. 이미 있는 근거를 고르는 데 별도 생성 작업자는 필요 없다. 후보 목록이 비었는데 모델이 새로운 원본을 만들어낼 수는 없다. 새 자료 찾기나 최종 자연어 답변은 후보 선택과 다른 일이다.
- **입력:** 원본 캡처·버전 고정, 정형 행의 필드 매핑은 코드만으로도 된다. 원문에서 고정된 구간을 선택하고 `예정/관측 보고/추론` 등 등록 스키마의 항목을 고르는 작업은 입력이어도 객관식이다. 사용자가 완성된 조각과 근거를 제시했다면 생성 작업자를 거칠 이유도 없다. 보기가 모자라면 억지로 분류하지 않는다.
- **새 조각 제안(설계):** 원문에 그대로 있지 않은 명제·적용 조건·재사용할 교훈을 여러 자료에서 작성해야 할 때만 생성형 추론 작업자가 필요하다. 대화 응답을 늦추지 않도록 허용된 범위에서 비동기로 초안을 만들 수 있다. 백그라운드라는 것은 실행 시점이지 저장 권한이 아니다. 작업자는 근거 참조와 함께 제안할 뿐이며, 호스트만 최신 동의·원본 버전·범위 및 중복을 검사하고 저장/보류한다. Decision Model의 동의·높은 점수는 사실 증명이나 쓰기 권한이 아니다. 현재 제품에는 이 범용 백그라운드 작업자/큐가 없다.

## Board 배치와 발표 구성을 닫힌 선택으로 다루기 (설계, 라이브 연결 전)

명확한 UI 명령은 로컬에서 처리한다. 예: 두 장 선택 → **나란히 비교**. 반대로 “인계하기 좋게 보여줘”에는 적절한 구성을 **고르는** 판단이 필요하다. 기존 `GET /decision/mode`의 `off / advisory / on`을 재사용할 수 있다. `/decision/mode`나 Board의 발췌·답변 작성 경로가 이미 배치를 바꾼다는 뜻은 아니다. [실행 가능한 문항 계약](../helper/egdesk-board-presentation-plan.mjs)은 네트워크나 Firefox 상태 변경 없이 시험한다.

1. **문항 작성자는 Desk 호스트다.** 사용자가 선택한 보드·카드, 현재 권한, 고정 여부, 사용 가능한 안전 폭을 대조한다. `현재 배치 유지`는 항상 후보. 지정 초점이 있어야 `한 장 집중`, 정확히 두 장을 이동할 수 있고 필요한 폭이 나와야 `두 장 비교`가 생긴다. 자료 전체 보기/한 장 집중은 카메라 작업이고 나란히 놓기는 구성 작업이다. Desk의 줌에 따른 `detail/outline/marker`는 이와 별개의 자동 표현이다. 보드 전체 발표 모드나 다른 사람 시점 따라오기를 기존 선택지로 지어내지 않는다.
2. **외부 전송은 옵션과 별개다.** 모델에는 이번에 전송까지 승인한 목적 문구 그대로와 허용된 선택 카드의 종류·임시 기호만 준다. 보드 참여/카드 열람은 외부 전송 허가가 아니다. 수신처·비용·목적 문구·실제 후보 요약을 확인하고 요청에 묶어야 한다. 목적 문구가 민감하면 사람이 고쳐 승인하거나 로컬 목록을 쓴다. 제목·파일 경로·본문·URL·로그인·사적 DM·실제 ID·다른 멤버·비공개 카드 수를 기본 입력에 넣지 않는다. 후보를 얻기 위해 숨은 원본을 추측하지 않는다.
3. **구체 요청 예**(표시한 문구 승인, A=업무 전표 B=메모, A를 초점으로 지정, 두 장 폭 가능). 기존 `client.decide({input,questions})`가 읽는 구조다. 유형과 설명만 모델에 보내고 기호→실제 view ID, 좌표, 원상복구 상태는 로컬에 둔다.

```json
{
  "input":[{"role":"user","content":[
    {"type":"input_text","text":"담당자에게 배송을 인계하기 좋게 보여줘"},
    {"type":"input_json","data":{"selected":[{"slot":"A","kind":"업무 전표","designatedFocus":true},{"slot":"B","kind":"메모","designatedFocus":false}],"availableWidth":"두 장 폭"}}
  ]}],
  "questions":[{"type":"choice","name":"board_view","instructions":"목적에 맞는 내 화면 구성 하나를 고르세요. 근거가 없으면 현재 배치 유지입니다.","choices":[{"value":"현재 배치 유지"},{"value":"선택 자료 전체 보기"},{"value":"지정 자료 한 장에 집중"},{"value":"선택한 두 장 나란히 비교"}]}]
}
```

4. **답은 보기 하나다.** 호환되는 구성 전체를 하나의 보기로 보내므로 레이아웃/초점/밀도를 독립적으로 찍어 불가능한 조합을 만들 필요가 없다. 발표를 확장한다면 읽기 순서 `(A→B)`와 `(B→A)`, 한 화면/한 장씩 등 호스트가 실제 렌더 가능한 제한된 조합만 후보로 추가한다. A/B의 업무 의미를 알아야 하면 승인된 설명이 있을 때만 붙인다. 정보가 없으면 모델이 추론해 업무 순서를 만들어선 안 된다. 순서별 카드 이동, 설명문 창작, 슬라이드 생성은 현재 계약에 없다.
5. **모드 차이:** `off`는 호출 0. `advisory`는 선택 품질을 참고용으로만 보고 실제 배치/활성 미리보기를 바꾸지 않는다. `on`은 유효한 보기만 내 화면의 미리보기로 넘길 수 있다. 확신도·상위 후보 간 차이 검사는 기존 기본 기준(0.75/0.20)을 출발점으로 쓴다. 보정된 정확도 수치가 아니다. 거절·선택지 밖의 값·불확실·타임아웃·예산 초과면 현재 배치와 수동 선택을 남긴다. 객관식 배치 때문에 reasoning model로 재시도하지 않는다.
6. **적용 권한:** 어떤 모드에서도 결과는 좌표, 코드, 클릭, 결제, 공개 또는 실행 명령이 아니다. 응답 뒤 보드/계정/대상 카드/원문·배치·권한/시점 버전을 재확인한다. 사용자가 옮겼거나 창 폭이 달라졌으면 폐기한다. 승인 전에는 영속 배치를 건드리지 않는다. **내 화면에 적용 → 되돌리기**, **공용 배치로 제안 → 대상 확인**을 구별한다. 발표자를 따라보는 일은 청중 각자의 별도 선택이어야 한다.

**검증/미구현:** [합성 테스트](../helper/egdesk-board-presentation-plan.test.mjs)로 입력 축소·좁은 폭·고정 카드·미승인/바뀐 문구·모드·늦거나 불확실한 답을 검사했다. Board 화면에서 실제 Decisions 호출, 결제·권한 승인 UI, 배치 미리보기·적용/되돌리기, 발표 순서 렌더러는 아직 미연결이다. 기존 [카메라/배치 계약](./VIEWPORT_LAYOUT_INTERACTION_MODEL.md)과 현재 사람 협업 [런타임](./JOINT_BOARD_RUNTIME.md)은 그대로다.
