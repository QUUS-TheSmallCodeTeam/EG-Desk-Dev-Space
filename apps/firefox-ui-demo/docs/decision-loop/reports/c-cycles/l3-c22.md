## 1. 계약 하나로 통합 (Main 결정: L2의 이름과 런타임 API)

**제거한 것 (내 중복 구현):**
- 플래그 `conversationFlow.inRunMessages` / `EGDESK_IN_RUN_MESSAGES`
- 표시 `inRunMessage: true`
- `acceptInRunMessage`, `workingRunFor`
- 내 steer/interrupt 코드
- flow 단위 메시지 목록

이제 L2의 받기 → 큐 → 처리(settle) → 다음 턴으로 넘기기(carry) 경로 하나만 남았다.

**heartbeat 쪽 동작 (L2의 API만 쓴다):**
- **질문:** beat는 `pendingInRunMessages(run)` 가운데 아직 판정하지 않은 가장 오래된 메시지 하나를 인용해 묻는다. 질문은 `person_status` / `person_change` / `person_stop`이다.
- **결정:** 코드가 하고, `settleInRunMessage`로 처리한다.

| 판정 | 처리 |
|-|-|
| stop | `'interrupt'` |
| change, 그 밖의 경우, 판정 실패 | `'steer'` (안전한 기본값) |
| status만 | 검사를 거친 진행 답 하나를 게시한 뒤 `'reply'`. 게시하지 못하면 `'steer'` |

- **끝나지 않은 라운드:** 그 메시지는 다음 beat에서 steer한다.
- **settle 실패:** 메시지는 pending으로 남고, L2가 다음 턴으로 넘긴다.

**테스트:**
- 내 테스트를 통합 경로(`inRunMessageTo`, `decisionContext.inRunMessages`)로 옮겼다. 단언하는 동작은 같다.
  - "왜 멈췄니?" → 진행 답 1개, 처리 `reply`, 큐가 빔
  - "B부터" → steer
  - 중지 → interrupt
  - 판정 실패 → steer
  - 플래그 꺼짐 → L2의 409 `INRUN_MESSAGE_UNAVAILABLE`, 저장 없음
- 변이 3건이 모두 잡혔다: 처리 누락, stop→steer, 큐 무시.
- L2의 `scripts/egdesk-chat-completed-messages.test.mjs`는 고치지 않았고 통과한다.

**L2 파일 변경 (모두 mock, 내 경로가 들어와서 생긴 것):**

## 3. conversation-scenarios-002 실측 실패 2건 (Main 전달, 9/11)

본문을 읽어 보니 두 건 모두 원인은 **내 라벨링 질문의 문구**였다. 제품의 판단은 맞았다.

**(a) triage_recall "오전 6시에 작업 중지 예약 걸었지?" — tn_recall .13**
- 직전 Assistant는 "06:00 강제 중지 알림은 그대로 둡니다"라고 했다.
- 이 턴은 대상(06:00 중지)을 이름으로 밝히고, 그 한 가지가 되었는지 확인한다.
- tn_recall의 정의는 "한 가지 새 사실이나 좁은 세부가 아니라, 다시 불러오기·요약을 요청"이다. 그러니 .13은 정확하다. 제품은 tn_need .99로 맞게 다뤘다.
- 틀린 것은 이 예시를 recall로 고른 라벨이었다. c19 문구 "point back to something earlier instead of naming it"이 "이전 일에 관한 것"으로 읽혀 referential .99가 나왔다.
- **수정:** "가리키기만 해서('그거', '위에', '방금 말한') 이전 대화를 봐야만 뜻을 알 수 있는가. 대상을 이름으로 말하는 턴은 아니다." (R4)

**(b) context_reask_v2 "아니 앱화면 말고 그냥 태화 프로젝트에 공모전 대화 인수인계 받으라고" — answer_type 미결 (.51)**
- 이 턴은 지시를 다시 하면서 고치는 것이다. 이해하지 못한 것을 다시 묻는 게 아니다.
- c19 문구 "explanation was unclear or missing and ask again"이 "다시 요청한다"로 읽혀 re-ask .92가 나왔다.
- 제품의 answer_type은 answer .63 / action_only .22로 갈렸고, 기준 미달이라 미결로 처리됐다. 미결이 정상 동작이다.
- **수정:** "Assistant가 말하거나 보여 준 것을 이해하지 못했거나 보지 못했다고 말하고, 다시 설명하거나 보여 달라고 하는가."
- 참고: 이런 다시 하는 지시에서 turn context가 answer와 action_only 사이에서 갈리는 것은 그 질문 소유 레인(L7)에 알릴 사항이다. 내가 그 질문을 바꾸지는 않았다.
