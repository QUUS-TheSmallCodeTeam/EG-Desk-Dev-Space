## 3. 설계 가이드 결정 루프

옵션은 묻기 전에 전부 데이터로 존재한다.
- **part**(코드가 자료에서 열거): `supersedes`/`superseded_by` 링크 쌍 → compare, 날짜 있는 자료 2개 이상 → sequence, 기록 status가 `plan`인 자료 → open_items, 어디에도 안 들어간 자료 → single.
- **part별 옵션**: 그 trait에 맞고 요건을 채우는 카탈로그 컴포넌트 + (자료 1개이고 이미 카드가 있으면) `reuse_T#` + `none_fits` + `bubble_enough`.
- **재사용 우선은 구조로 강제**: 이미 카드가 있는 자료에는 `result_text`가 옵션에 아예 없다. 그래서 "불필요한 새 컴포넌트 0"은 모델 판단이 아니라 코드 규칙이다.
- 회수(접기) 제안은 이전과 같은 규칙: 이 에이전트가 이전 답변용으로 만들었고 대체된, 아직 보이는 카드에만 옵션이 생긴다.

| 단계 | Decision 요청 | 내용 |
|-|-|-|
| (a) place | 1 | bubble vs board. 확신 없으면 bubble |
| (b) parts | 1 (part별 질문을 한 요청에) | 컴포넌트 / 기존 카드 재사용 / none_fits / bubble_enough, 회수 제안 |
| (c) order | 선택된 part 수 − 1 | "남은 것 중 다음은?" 마지막은 질문 없음 |
| (d) repair | 0–2 | 코드가 실제 크기로 배치 계산 → 닫힌 검사 항목(overflow, overlap, spread, too_many_steps, unreadable_order) → 걸린 항목만 재선택(trim/own_step/drop/time_order/keep) |
| fill 후 검사 | 1 | step 설명이 가리키는 카드와 맞는지 (빈/불일치 슬롯과 넘침은 코드가 판정) |
| rechoose | 0–2 (+재검사 0–2) | 걸린 컴포넌트만: 다른 옵션 / (비교면) 있는 버전 카드 재사용 / 다시 쓰기(1회, 데이터가 없으면 제외) / 빼기 |

**요청 수와 상한의 근거** (warm 0.25–0.6초/회 기준, 이번에 측정한 값이 아니라 주어진 수치):
- 대표 시나리오 5회 → 1.25–3.0초. 단일 버전 6회 → 1.5–3.6초.
- 최장 경로 1+1+5+2+1+4 = 14회 → 3.5–8.4초. 상한 `maxRequests: 14`.
- 판단 대기 누적 40초를 넘으면 중단(`judgeMs`). 비공개 turn 총 100초 + 40초 + 마지막 요청 4초 < chrome 대기 150초.
- 지연의 대부분은 주관 모델 turn(턴당 최대 30초)이다. 새 순서는 그 turn을 **1회**로 줄인다(이전 순서는 설계 1회 + 새 카드마다 1회).

확신이 부족한 답의 기본값은 코드가 정한다: place → bubble, part → 선택 안 함, 회수 → 유지, order → 코드 순서, repair → 문제를 없애는 쪽(유지 아님), rechoose → 빼기.

## 4. Fill과 검증

주관 모델이 받는 것은 **가이드와 자료뿐**이다(`kind, guide, materials`). 답변 본문, 보드 좌표, id는 프롬프트에 없다(테스트 고정). 대표 시나리오 프롬프트는 3,593자, 구획은 Design guide / Materials / Rules / JSON shape. 전문은 `journey-sim.txt` 끝에 있다.

돌아온 JSON은 슬롯 스키마로 검증한다.
- 가이드에 없는 item·필드·슬롯이 있으면 답 전체 거부(`extra-item`/`extra-field`/`extra-slot`) → 1회 재시도 → 그래도 안 되면 채팅 답변 유지.
- 채울 수 없는 슬롯은 `unfillable`로 보고하게 했고, 보고되거나 빠진 슬롯은 그 item의 문제로만 기록된다. 코드가 값을 지어내지 않는다.
- 행 수 min/max, 길이, "이 part의 자료만 인용" 규칙을 어기면 mismatch.

## 6. L7 자료와의 연결

L7(c14, 아직 미병합)이 `chat.memoryMaterialsFor(run)`을 만들고 있고 행 형태를 받아 맞췄다. `normalizeMaterials`가 그 행을 그대로 읽는다: `alias, title, excerpt, time.at, status, statusPending, links[{type, toAlias}]`. L7이 정정해 준 닫힌 어휘를 반영했다(버전 관계 = `supersedes`/`superseded_by`, 미완료 = status `plan`만).

`briefingDeps.materialsFor`는 그 메서드가 있으면 부르고 없으면 빈 배열이다. **즉 L7 c14가 병합되기 전의 실제 bridge에서는 새 순서가 항상 `no-materials`로 끝난다.** 테스트는 L7 형태의 고정 배열을 그 자리에 넣어 모델링했다.

## 7. Egress

한 개의 공유 gate를 쓴다. 사용자 요청문은 `draft_text`(run), 자료는 `memory_page`, 카드 라벨은 `canvas_text`. run이 없으면 아무것도 묻지 않고, memory가 없으면 자료가 없고, canvas가 없으면 기존 카드가 목록에 안 나온다(테스트). memory 클래스는 "그 run의 accessor가 행을 돌려줬을 때만" 켠다. 이건 내가 정한 연결이니 L5/L7 확인이 필요하다.

## 8. 한계

1. 표·체크리스트는 진짜 컴포넌트가 아니라 줄 템플릿이다.
2. 레이아웃 좌표는 검사용 계획이다(제품의 크기표와 `placeCanvasView` 사용). 새 카드가 실제로 어디에 열리는지는 확인하지 않았다.
3. "기존 카드가 이 자료를 보여준다"는 제목 일치로 판정한다. 거칠다.
4. fill 프롬프트에는 가이드와 자료만 있지만, 비공개 turn은 답변 대화의 fork이므로 모델 컨텍스트에는 대화가 있을 수 있다(c11부터 미검증인 부분).
5. advisory 기록 경로는 여전히 이전 순서의 판단(placement + reuse)을 기록한다. 새 순서로 바꾸려면 advisory 요청에 run id가 필요하다.
6. 요청문은 chrome이 보낸다(그 답변 바로 앞의 사용자 메시지). `on` 경로는 이제 답변이 카드 2장을 언급하지 않아도 요청문이 있으면 bridge에 묻는다.
7. 결과 3건 발행 후 제안이 실패하면 발행된 결과가 남는 문제(c11 이월)는 그대로다.
8. 기준값(.75/.2/.7)은 보정 전 임시값이다.

## 9. 승인 요청

- **새 기능 이름·라벨: 없음.** 새 고정 문구도 없다.
- 사용자 눈에 보이게 되는 코드 생성 서식(승인 필요): 비교 카드 줄의 화살표 `→`, 줄 앞 굵은 라벨. 카드 제목과 step 문장은 주관 모델이 자료의 언어로 쓴다.
- 이전 사이클에서 대기 중인 문구는 변동 없음(접기 안내, "오래된 결과 접기", "내 화면에 적용", 채팅 fallback 문구).
- 내부 식별자(비노출): env `EGDESK_BRIEFING_ORDER`, 라우트 `/decision/briefing-skeleton`, 컴포넌트 id 4개.

## 10. 결정이 필요한 것

1. 표·체크리스트 **실제 렌더러**를 만들 것인가. 카탈로그는 받을 준비가 되어 있다.
2. advisory 기록도 새 순서로 바꿀 것인가.
3. 비교를 위해 이전 순서 코드를 언제까지 둘 것인가.
