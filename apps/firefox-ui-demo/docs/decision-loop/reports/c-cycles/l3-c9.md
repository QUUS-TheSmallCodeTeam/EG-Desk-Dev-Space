# L3 cycle 9: 완성된 메시지만 보이는 답변 보류, 사람 같은 중간 메시지

브랜치 `lane/c9-held-answers`(`int/c8` = `90a7d56` 기준). 커밋 `fc742a0`. 증거 `evidence/l3-c9/held-flow.tap`(시뮬 진단), 게이트 `evidence/gate-l3c9/full.tap`.
**합성 결과**: 가짜 엔진(가짜 app-server)·가짜 Decisions, 가상 시계·타이머, 네트워크·Codex 바이너리 없음. **실제 엔진·설치 앱·화면은 검증하지 않았다.** 제품 동작은 플래그 두 개 모두 기본 OFF.

## 사용자 결정 반영
스트리밍 없음, 완성된 메시지만, 일하는 동안 기존 작업 표시. "추론1→추론2→중간 답→추론…→최종 답"의 대화 흐름. Decision 모델은 다른 모델과 같은 데이터 공유 설정을 따르며 별도 동의 없음: 이번 기능도 기존 `decisionContext`의 모드(advisory/on)와 저장된 키를 그대로 게이트로 쓰고 새 동의 화면·설정은 만들지 않았다.

## 1. 보류된 완성 답변 (on 모드, 플래그 `decisionContext.draftCheck.mode() === 'on'`)
- **작업 표시는 기존 것**: 채팅 끝의 `[···] Agent 작업 중` 말풍선(`EGDeskChatState.agentWorkingView` → 서피스 `codexAgentWorkingRow`, `data-testid chat-agent-working`, 점 세 개 `egd-codex-typing-dots`). 실행이 진행 중인 동안(`isRunBusy`) 항상 보이므로 새 라벨을 만들지 않았다. 보류 중 실행 상태는 `inProgress`로 남아 이 말풍선이 유지되는 것을 시험으로 확인(보류 항목은 `run.messages`에 없음).
- 구현 위치: 기존 주제 답변 가드(`startTopicAnswerGuard`/`holdTopicAnswer`/`settleTopicAnswer`)에 `kind: 'draft'`를 추가했다(`codex-chat-runtime.mjs` +302 중 일부). 차이점:
  - 델타·시작·부분 텍스트는 어디에도 나가지 않고(`enqueue`/`messageDelta`), 완성된 최종 항목만 메모리에 보류.
  - 만료는 실행 시작이 아니라 **첫 최종 항목 이후 20 s**(`DRAFT_HOLD_RELEASE_MS`): 긴 실행은 정상이므로. 턴이 끝나지 않으면 **원문 게시**. 주제 가드의 거절 안내(`EG-Desk가 답변을 표시하지 않았습니다`)는 draft 가드에 쓰지 않고 모순 검사도 적용하지 않는다.
  - 항목 수·크기 초과(16개, 256 KiB), 연결 끊김, 잘림은 **보류 해제 후 원문 게시**(`releaseDraftOriginal`).
  - 턴이 끝나면 `finish`의 기존 순서대로 `settleTopicAnswer`가 `run.status` 변경 **이전에** 호출되어, 검사·수정 동안 작업 표시가 유지된다.
- 해제 흐름(`settleDraftAnswer`): 보류 → `checkHeldDraft`(c7의 `checkDraft`, mode on, 근거는 이번 턴 패킷과 도구 참조) → 발견 사항이 있으면 **비공개 포크에서 수정 1회**(`reviseOnFork`) → 재검사 → 완성된 메시지 1개로 게시. 시간·예산 상한은 c7과 같고(첫 검사 1.5 s, 재검사 1.2 s, 총 `holdMs` 45 s), 실패·시간 초과·판정 불가는 **원문 게시**. 게시 직전에 Decision 모드·키·설정 세대를 다시 읽어 바뀌었으면 검사 결과를 쓰지 않고 원문(c4 규칙). 같은 문장이 이미 보낸 중간 메시지와 글자 그대로 중복이면 최종에서 뺀다(남는 문장이 있을 때만).
- 비공개 포크(`codex-internal-turn.mjs`): `thread/fork`로 임시 포크를 만들어 한 턴만 돌리고 최종 텍스트만 읽고 폐기. 포크의 알림은 `handleNotification` 맨 앞에서 가로채 실행·메시지·활동으로 처리되지 않으며, 포크의 도구·승인 요청은 모두 거절한다.
- 시험(`egdesk-held-answers-flow.test.mjs`): 빠른 답(3 s) 한 번에 한 메시지·델타 조각 없음, 보류 중 어떤 텍스트도 이벤트에 없음, 수정 포함 보류(`현재 운영 중입니다`→`아직 계획 단계입니다`, 원문은 이벤트·저장소 어디에도 없음), 포크 실패·불가 시 원문 게시, 플래그 off면 오늘 동작.

## 2. 사람 같은 중간 메시지 (플래그 `decisionContext.conversationFlow.mode() === 'on'`, 보류 모드가 on일 때만)
- 매 5 s 틱(`FLOW_LIMITS.tickMs`)마다 실제 실행 사실로 **선택지를 런타임에 열거**(`egdesk-conversation-flow.mjs`): 사용자 메시지 이후 경과, 도구 단계 완료/진행 수, 마지막 중간 메시지 이후 경과·단계 수, 에이전트가 작업 메모에서 낸 질문(마지막 메모가 `?`로 끝남, 같은 메모로 두 번 묻지 않음), 승인·입력 대기(대기 중이면 없음). 열거 규칙: `none`은 항상; `ask_missing`은 질문 신호가 있고 아직 안 물었을 때; `explain_wait`은 10 s 이상 지났고 아직 설명 안 했을 때; `milestone`은 앞선 메시지 뒤 2단계 이상 진행했을 때. **`none`만 가능하면 Decision 요청 자체가 없다.**
- Decision 요청 1회(선택 4지 중 가능한 것만): 입력은 숫자와 닫힌 라벨뿐이고 **작업 메모 본문·추론·도구 명령은 보내지 않는다**(시험: 작성 모델 프롬프트에도 도구 명령 미포함). 선택은 기존 기준(신뢰도 0.75, 마진 0.2) 미달이면 `none`.
- 작성: 주관 모델이 비공개 포크에서 한두 문장(280자 이하)을 쓴다(추론·결과·목록·코드 금지, 이전 메시지 반복 금지). 그 메시지도 **초안 검사**를 받고 수정 없이 통과해야만 게시(실패하면 게시하지 않음). 게시는 완성된 어시스턴트 메시지(`phase` 없음, `completionConfirmed`)로 일반 경로(`applyItem`)를 통해 저장·표시되고 실행은 계속된다. 최종 답변이 보류에 들어가거나 검사가 시작되면 흐름을 닫고, 그 뒤에는 중간 메시지를 게시하지 않는다.
- **빈도 상한과 근거**: 첫 메시지는 10 s 이후(Nielsen: 약 10 s가 사용자 주의가 유지되는 한계, 그 전은 곧 올 답을 끊음), 이후 최소 30 s 간격(분당 두 번을 넘으면 소음), 실행당 최대 3개(대기 설명·질문·진행 1회씩; 그 이상은 보고), 질문은 실행당 1개이고 미답이면 다시 묻지 않음, 설명은 1회. Decision 요청은 10 s에 1회·실행당 6회 이하(`maxEvals`), 3 s짜리 실행은 틱이 한 번도 돌지 않아 요청 0.
- **사용자 답변을 같은 실행으로**: 질문이 열려 있는 동안 같은 DM에서 보낸 메시지는 `send` 맨 앞에서 가로채 **검증된 `turn/steer` 계약**(Board 동료 입력과 같은 증명, `boardPeerContract`)으로 같은 네이티브 턴에 넣고, 로컬 사용자 메시지로 저장·표시한다. 계약이 없거나 steer가 실패하면 아무것도 바꾸지 않고 `INRUN_REPLY_UNAVAILABLE`(409). 질문당 답변은 1회.

## 4. 한계와 아직 안 한 것 (정직하게)
- **작성/수정 포크는 실제 app-server 미검증**: `thread/fork`가 부모의 완료된 턴을 복사하는지, `ephemeral` 옵션, 포크의 도구·승인 거절만으로 충분한지 확인 필요. 포크는 부모의 **진행 중인** 턴 내용을 모르므로 중간 메시지는 사실(경과 시간·단계 수)과 에이전트가 메모에 적은 질문 한 줄(로컬에서 같은 공급자로 전달)만 쓴다.
- **사용자 답변 UI**: 서피스 작성창은 실행 중(`threadBusy`)이면 전송을 막는다(`eg-desk-surface.uc.js` `sendMessage`). 런타임은 질문이 열린 실행에서 같은 경로(`/chat/send`)의 답을 받도록 되어 있지만, **작성창이 그 상태에서 전송을 허용하려면 서피스 변경이 필요**하고 이번에는 하지 않았다(다음 사이클). 그전에는 UI에서 이 답변 경로에 닿을 수 없다.
- 중간 메시지는 네이티브 기록에 없고 로컬 저장소에만 있다. 대화 복원 때 네이티브 기록으로 턴을 재구성하는 경로에서 이 메시지가 보존되는지는 확인하지 못했다(저장소 체크포인트 경로는 `completionConfirmed`로 보호).
- 기존 동작 관찰(이번 변경 아님): 실행 중 같은 DM에 일반 `send`를 하면 사용자 메시지가 저장소에 먼저 기록된 뒤 409가 날 수 있다(시험 중 확인). UI는 막으므로 도달하지 않는다.
- 작업 메모에서 질문을 알아내는 신호는 "마지막 메모가 물음표로 끝남"이라는 단순 규칙이다. 오탐·미탐은 보정 기록(`conversation_flow` 항목)으로 모은 뒤 판단해야 한다.
- 게이트 1회 불안정: `egdesk-chat-choice.test.mjs`의 "timeout reason tells a started POST…"(수정하지 않은 시간 의존 시험)가 부하 상태에서 한 번 실패, 단독 3회·게이트 재실행 2회는 통과. 내 변경과 무관한 불안정 시험으로 판단하나 원인 미분석.

## 5. 사용자 문구 (승인 필요)
이번 사이클에 **새 고정 문구 없음**. 작업 표시는 기존 `Agent 작업 중`. 중간 메시지는 모델이 쓰며 고정 문구가 아니다(작성 지침은 내부 영문). c7의 `DRAFT_CHECK_COPY` 두 문장은 검사가 일부만 게시하거나 되물을 때 그대로 쓰이며 승인 대기 상태 그대로다.

## 7. 철학 점검
