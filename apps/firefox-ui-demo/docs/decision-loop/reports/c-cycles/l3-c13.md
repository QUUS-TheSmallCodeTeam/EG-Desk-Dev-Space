## 1. 무엇이 바뀌었나

### 1.1 하트비트 수명이 run 이 아니라 대화 세션을 따른다 (간극 a)

이전에는 run 이 끝나면 하트비트가 멈췄다. 이제 대화마다 하트비트 하나가 run 을 넘어 유지된다.

| 상태 | 박자 | 시작 | 끝 |
|-|-|-|-|
| active | 5 s | 메시지 접수 (`hb.activate`) | run 종료·취소 (`hb.settle`) |
| idle | 20 s | run 종료 | 아래 정지 조건 |

정지 조건 (정지 이유는 닫힌 값):

| 조건 | 기준 | 이유 값 |
|-|-|-|
| 대기 중인 것이 없고 사람이 조용함 | 5분 (`lingerMs`) | `idle` |
| 대기 중인 것이 있어도 사람이 없음 (하드 스톱) | 15분 (`idleStopMs`) | `idle` |
| 대화 닫힘 | `chat.closeSession(key)` | `closed` |
| 연결 끊김 / 프로세스 종료 | 기존과 동일 | `disconnect` / `restart` |
| 첫 메시지의 턴 시작 실패 | 기존과 동일 | `start_failed` |

- "대기 중인 것" = 열린 질문, 사람을 기다리는 단계(`waiting_user`), provider 의 attention 사실. 이것이 있으면 5분을 넘겨도 유지되고 15분에서 끊는다.
- 같은 대화에 새 메시지가 오면 **같은 하트비트**가 다시 active 가 된다. 박자 격자는 그 메시지 시점부터 다시 시작한다. provider 등록(배치, 명령 등)은 그대로 남는다.
- run 단위 사실(단계 수, 승인 대기, 추론 중 여부)은 run 이 끝나면 비워지고 다음 run 이 들어올 때 교체된다.
- 살아 있는 하트비트 상한(64)에 닿으면, 가장 오래 idle 인 세션이 새 세션에 자리를 내준다. 일하는 세션은 밀려나지 않는다.

박자 근거:
- **idle 20 s**: 아무도 초 단위로 기다리지 않는 구간이다. L4 배치 대기열 유효 시간 30 s 보다 짧아야 해서 20 s 로 잡았다.
- **nudge**: provider 가 `hb.nudge()` 를 부르면 다음 박자가 0.5 s 안에 온다 (5 s 에 한 번). 격자는 바뀌지 않는다.
- **5분 / 15분**: 측정값이 아니라 판단값이다. 실제 사용에서 조정이 필요하다.

### 1.2 세션 창(window)별 공유 한도

창 = run 하나, 또는 run 뒤 idle 구간 하나. `activate` 와 `settle` 마다 새 창이 열린다.

| 한도 | 값 |
|-|-|
| 창당 판단 요청 | 최대 6 |
| 박자당 요청 | 최대 1 (모든 provider 질문을 한 요청에) |
| 요청당 질문 | 최대 6 |
| "없음" 뒤 간격 | 10 → 20 → 40 → 80 s |
| 한 라운드 상한 | 60 s |
| 창당 박자 | 최대 720 |
| 창당 포인터 메시지 | 최대 2, 사실 하나당 1 |
| 메시지 사이 간격 | 30 s (기존) |

- idle 박자는 사실만 읽는다. provider 가 실제 질문을 내놓지 않으면 **요청 0** 이다. idle 구간 최악의 경우는 박자 45회, 요청 6회다.
- idle 에서 메시지 질문이 나오는 경우는 하나뿐이다: attention 사실이 있고, 보낼 수 있는 대화가 있고, 아직 알리지 않았을 때.

### 1.3 닫힌 사실 요약 (간극 b)

메시지 판단과 작성 모델은 provider 사실을 **닫힌 라벨**로만 받는다. 페이지·터미널 글자는 들어가지 않는다.

| 라벨 | 읽는 사실 |
|-|-|
| `command_waiting_input` | `terminal: 'waiting'` (+ `quietMs`) |
| `command_running` | `terminal: 'running'` (+ `runningMs`) |
| `browser_task_waiting_person` | `task: need_context / cannot_proceed` |
| `browser_task_running` | `task: 'running'` |
| `placement_pending` | `placementsPending > 0` |
| `objective_step` | 단계 `objective_step` |
| `tool_running` | 실행 중인 도구 단계 (다른 라벨이 없을 때) |

- 판단 요청에는 `waiting_on: command_running`, `waiting_on_seconds: 9` 같은 줄이 들어간다.
- 작성 모델에는 고정 문구("a command is still running (about 9 seconds so far)")가 들어가고, 문장은 작성 모델이 쓴다.
- provider 가 `waitingOn: <라벨>` 로 직접 말할 수도 있다. 표에 없는 라벨은 버린다.

### 1.4 포인터 메시지 (간극 c)

provider 의 attention 사실을 소비한다. 닫힌 필드 셋:

| 필드 | 값 |
|-|-|
| who | `owner` / `requester` |
| where | `in_view` / `left` / `right` / `above` / `below` / `none` |
| kind | `result` / `approval` / `question` |

- L4 의 현재 필드명(`pointerPending / pointerFor / pointerWhere / pointerDistance / pointerNeeds`)을 그대로 읽는다. `pointerNeeds: 'owner_action'` 은 approval, 나머지는 result 로 읽는다. L4 모듈은 고치지 않았다.
- 일반형(`attention / attentionFor / attentionWhere / attentionDistance`)도 받는다. `question` 은 일반형으로만 온다.
- **어디에 보낼지는 코드가 정한다** (`pointerRoute`). 모델은 "지금 알릴지"만 판단한다.
  1. 그 사람이 작업 대화에 참여하고, 참여자가 요청자·소유자뿐이면 그 대화
  2. 아니면 참여자가 그 사람뿐인 다른 살아 있는 대화 (본인 대화)
  3. 그 사람이 자리에 없거나 그런 대화가 없으면 보내지 않음. 요청도 하지 않음
- 게시 직전에 경로와 run 상태를 다시 읽는다.
- 카드와 카메라는 건드리지 않는다. 작성 지시문에 "아무것도 옮기지 않았다"가 들어간다.
- 게시되면 provider 에 알린다: `hb.acknowledge(provider, 'attention')`, 그리고 브리지의 `attentionPosted` 가 `workPlacement.acknowledgePointer(key)` 를 부른다.

### 1.5 run 이 끝난 뒤의 게시

- 중간 메시지와 **같은 경로**다: 비공개 fork 에서 작성 → 같은 초안 검사(증거 없이) → `applyItem` → `message.started/delta/completed` 이벤트와 저장소. 새 말풍선 종류는 없다.
- 대화가 idle 이면 마지막 run 에 붙는다. 그 사이 새 run 이 시작됐으면 그 run 의 흐름에 들어간다 (그 run 의 메시지로 집계).
- 말할 수 있는 조건은 그대로다: 답변 보류 모드(`EGDESK_DRAFT_CHECK=on`)이거나 그 run 이 opt-in 했을 때만.

### 1.6 L8 (간극 d)

`runtime.allowIntermediateMessages(conversationKey)` 는 이름·인자·의미가 그대로다. opt-in 은 그 run 에만 유효하고 run 이 끝나면 지워진다. 첫 메시지에서 브라우저 루프가 run 보다 먼저 도는 문제는 L8 구조 변경 전까지 그대로다.

## 4. 다른 레인에 필요한 것

- **L4**
  - run 이 끝난 뒤에도 `chat.heartbeatFor(key).state === 'running'` 이다 (`tempo: 'idle'`). 세션이 끝난 뒤(5분/15분)에는 다시 `no-heartbeat` 가 나온다.
  - `submit` 과 포인터 설정 시점에 `heartbeat.nudge?.()` 를 부르면 박자가 최대 20 s 가 아니라 0.5 s 안에 온다. 지금은 부르지 않는다.
  - 포인터 사실은 현재 필드명 그대로 소비된다. 게시되면 `acknowledgePointer(key)` 가 불린다.
- **L5**: `engine_commands` 행의 `terminal`, `runningMs`, `quietMs` 를 읽는다. 행 모양은 그대로 두면 된다. 123행 테스트는 하트비트 시작 시 `audience`, `message` 가 등록된다는 점만 반영하면 된다.
- **L2**: run 종료 뒤 포인터 메시지는 **이미 completed 인 run 의 runId** 로 `message.*` 이벤트가 `run.completed` 뒤에 온다. 화면이 이를 그리는지는 확인하지 않았다 (L2 영역).
- **L8**: `allowIntermediateMessages` 그대로. `browser_task` 행의 `task` 라벨을 읽는다.

## 5. 남은 것과 한계

- **대화 닫힘 신호가 없다.** `chat.closeSession(key)` 는 만들고 테스트했지만 부르는 곳이 없다. 브리지에 "대화가 닫혔다"는 신호가 없어서다. 그때까지는 5분/15분 한도로만 끝난다.
- **소유자 본인 대화가 살아 있지 않으면 포인터는 가지 않는다.** 대신 보내는 다른 통로는 없다. L4 쪽 사실은 120 s 뒤 철회된다.
- 사람의 활동은 그 대화에 보낸 메시지로만 센다. L1 의 presence 는 포인터 경로의 부재 판단에만 쓴다.
- 포인터 메시지 하나는 주 모델의 fork 턴 하나를 쓴다 (중간 메시지와 같다).
- 검사 요청 횟수: 시뮬레이션의 포인터·대기 메시지는 검사할 주장이 없어 검사 요청이 0회였다 (c12 와 같은 동작). 구체적 주장이 든 포인터가 증거 없이 걸러지는 경우는 이번에 따로 시뮬레이션하지 않았다. 경로는 c12 의 제한 run 과 같다.
- 실제 엔진에서의 측정(추론 delta 간격, 20 s 정지 기준, 판단 지연)은 여전히 열려 있다.

## 6. 승인이 필요한 문구

이번 사이클에 새로 생긴 사용자 노출 고정 문구는 없다. 라벨 문구와 포인터 지시문은 작성 모델에 주는 영어 지시이고 화면에 나오지 않는다. 이전 사이클의 대기 건은 그대로다: `FLOW_COPY.stalled`, c7 `DRAFT_CHECK_COPY` 2건, c3 설정 검증 문구, c2 `spend_limit_reached` 설정 문구.
