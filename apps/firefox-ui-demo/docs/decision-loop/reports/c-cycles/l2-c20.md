## 1. 계획 v7에 더한 것

v6의 모든 기대(66개, 문구·인자·예측까지)는 글자 그대로 둡니다(테스트로 확인). 새 기대 22개:

**(a) 변경 nudge, 단계 `s4c-change-nudge`** (s4n 바로 뒤, 같은 명령이 도는 중. 새 단계, `since 7`)
- 사람이 "그거 말고 B부터 해줘"를 run에 이름 붙여 보냅니다. 상태 nudge가 판단된 뒤 하트비트의 판단 간격(10초)이 지나도록 5.5초 기다린 다음 보냅니다(아래 3절 관찰).
- Decision 쪽은 **실제 모델의 답**으로 잽니다 (계산 기록의 닫힌 단어 `beat_person_change`, `beat_person_stop`의 확률).
- 엔진 쪽은 **코드로** 판정합니다 (가짜 엔진이 받은 것).

**(b) s3b**: 사람이 보는 답이 물은 것에 대한 것이다
- `s3b.on-topic` (필수 L3): 사람이 본 답(Agent 자신의 것이거나 점검 뒤 고친 것)이 PostgreSQL을 말한다.
- `s3b.not-off-topic` (필수 L3): 다른 일(A사 견적)로 넘어가지 않는다.
- `s3b.answer-kept` (선택 L3): 점검이 Agent 자신의 답을 그대로 통과시킨다(맞는 recall을 걸지 않는다). **실제 모델이 c28처럼 .86을 주면 실패로 예측**합니다. 점검의 판단을 재는 것이라 선택입니다.
- **정해진 고침 문장을 없앴습니다.** 이전 계획에서는 하네스가 점검에 걸린 초안을 고정 문장("앞에서 확인한 내용 기준으로, A사 견적은…")으로 바꿨습니다. v7의 세계(`world.wording: "faithful"`)는 고침 프롬프트가 모델에게 요구하는 대로 합니다: 나열되지 않은 문장은 그대로 두고, 나열된 문장은 "기록에 따르면 …"으로 그 문장을 남깁니다. 주제가 바뀔 수 없고, 사람이 보는 글은 제품 사슬(점검 → 고침 → 게시)로 만들어집니다. 다만 **고침 문장 자체는 여전히 스크립트**입니다(실제 작성 모델이 쓴 글이 아님).
- 이 기대들은 점검의 **실제 답**에 기대지만 문장은 스크립트이므로, 실제 모델의 고침 품질은 여전히 측정되지 않습니다.

**(c) nudge 답 프롬프트의 경과 시간**
- 작성기 프롬프트의 "has taken about N seconds so far"(대기 메모)와 "is still going (about N seconds so far, …)"(진행 답)의 숫자를 파싱해서, 가짜 시계로 잰 run의 실제 나이와 비교합니다(2초 이내). 멈춤 줄("Nothing has come from the work for about N seconds")과 대기 줄 안의 "(about N seconds so far)"는 일부러 대상이 아닙니다(L3와 합의).
- `s4.elapsed-true` (필수 L3, 대기 메모): 통과 예측(c28에서 10초 대 10초).
- `s4n.elapsed-true` (필수 L3, 진행 답): **L3 c24가 합쳐지기 전까지 실패 예측**(c28에서 "1초"). L3 설명: 원인은 nudge가 `mark('user')`를 불러 `sinceUserMs`가 다시 시작하는 것이었고, 수정은 숫자를 작업의 나이 `workMs`로 바꾸는 것입니다. 표기는 그대로입니다.

## 3. 이번에 보인 것과 알려야 할 것

1. **메시지를 연달아 보내면 두 번째 판단이 늦습니다** (L3, 하트비트 한도 `askGapMs` = 10초, nudge는 5초에 한 번). 상태 nudge가 판단된 지 5초 뒤에 변경 메시지를 보냈더니 **다음 10초 동안 판단 요청이 하나도 없었고**, 다음 단계(명령 종료 이벤트가 온 뒤)에서야 판단됐습니다(`debug-beats.mjs`: 가짜 시계 24초에 보내고 34초까지 heartbeat 요청 0건). 이것은 코드 순서이고 모델 결과가 아닙니다.
   - 급한 것은 중지입니다. 직전에 다른 메시지가 판단된 직후라면 "그만해"도 10–15초 기다립니다.
   - v7의 s4c는 이 간격을 일부러 기다린 뒤 보냅니다(이 단계가 재는 것은 판단과 엔진 쪽이므로). 지연 자체를 재는 기대는 만들지 않았습니다. 정할 것: 중지 후보 메시지는 간격에서 제외할지 (owner/L3).
2. **L3 c24는 그 밖에 점검의 시간 질문도 고쳤습니다** ("Draft check tense: decisions and plans are not 'done'…", 커밋 `83e1f26`). v6 s3b의 .86 오탐이 이 수정 대상입니다. 합쳐지면 점검 요청의 본문이 바뀌므로 `s3b.answer-kept`의 결과가 달라질 수 있습니다. 합친 드라이런(대본 judge)에서는 통과했지만 실제 판정은 보내 봐야 압니다.
3. L3 c24가 합쳐지면 nudge가 있는 요청에 "The work began N seconds ago (the person wrote again into the running work M seconds ago)." 줄이 더해집니다(L3 설명). 그러면 이 줄이 있는 요청의 본문 바이트가 v6와 달라지므로, `--rerun`의 재생에서는 그 요청들이 `recorded_changed_body`로 표시됩니다. 오류가 아니라 예상된 변화입니다.
4. 이번 계획은 **s4c 한 단계에 전부 달아 둔** 하네스 가정이 있습니다: 변경 메시지가 steer되어도 가짜 엔진은 그것을 따르지 않고 원래 스크립트대로 s6의 답("테스트가 모두 통과했습니다.")을 합니다. 그래서 실제 실행에서 변경 메시지가 s6 점검의 근거(대화)에 들어가 s6 `sup_0`가 달라질 수 있습니다. 어느 기대가 흔들리면 그 때문인지 먼저 의심해야 합니다.
5. 측정하지 못하는 것: 실제 작성 모델이 쓴 진행 답·고침 글(스크립트), 실제 엔진이 steer를 받은 뒤의 행동(가짜 엔진), steer·interrupt가 실제 Codex에서 받아들여지는지(Main이 실엔진으로 확인한 interrupt 사실만 근거).
