## 1. 공용 실행기
**사용법**
```
node scripts/egdesk-decision-real-measure.mjs <plan.json>                               # 드라이런: 검증하고 표만 출력, 아무것도 보내지 않음
OPENAI_API_KEY=... node scripts/egdesk-decision-real-measure.mjs <plan.json> --send --out results.json   # 승인 후 실제 전송
```
종료 코드: 0 완료, 2 계획 거부(전송 0), 3 키 없음(전송 0), 4 실행 중단(실패 또는 토큰 상한). 드라이런에서도 상한 초과면 4.

**지키는 규칙 (L7 실행기와 동일, 각각 시험 있음)**
| 규칙 | 구현 |
|---|---|
| 기본 드라이런 | `--send` 없으면 환경에 키가 있어도 fetch 호출 0, 결과 파일도 안 만듦 |
| 키 | `--send`일 때만 `OPENAI_API_KEY`에서 읽고 Authorization 헤더에만 사용. 출력, 결과 파일, 오류 어디에도 없음(상위 오류 문구는 저장하지 않고 코드만) |
| 엔드포인트 | 코드에 고정된 공식 주소. 인자가 아님(`--endpoint` 같은 모르는 플래그는 종료 2). `redirect: 'error'` |
| 본문 = 파일의 정확한 바이트 | 재직렬화하지 않음. 계획 로드 때 한 번, 보내기 직전에 한 번 더 해시. 하나라도 다르면 전체 0건 전송 |
| 재시도 없음 | 첫 비-200, 네트워크 오류, 시간 초과에서 멈춤. 뒤 요청은 `not_sent` |
| 토큰 상한 | 선언 추정치 합이 `tokenCeiling`을 넘으면 시작 거부. 실행 중 실제 보고된 입력 토큰 누계가 넘어도 멈춤 |
| 결과 파일 | 0600(기존 파일도 0600으로). 답, 지연, `openai-processing-ms`, usage, 채점표 |

**계획 형식에 대해 다른 lane이 알아야 할 것 (형식은 지시된 그대로, 아래는 로드 때 거부되는 경우)**
- `file`은 계획 파일 기준 상대 경로이고 계획 디렉터리 안의 일반 파일이어야 한다(밖을 가리키는 심볼릭 링크 거부).
- 본문은 `model: "gpt-6-luna"`여야 하고 필드는 `model, input, questions, prompt_cache_key, safety_identifier`만 허용. 제품 클라이언트의 요청 검증(문항 이름 중복 등)을 그대로 통과해야 한다.
- `expect`의 `name`은 본문에 있는 문항이어야 하고 종류가 맞아야 한다. choice의 `equals`/`oneOf` 값은 그 문항의 선택지여야 한다(오타로 돈을 쓰기 전에 걸러냄). predicate는 `min`/`max` 중 하나 이상, choice는 `equals`/`oneOf` 중 정확히 하나.
- 채점: 경계 포함(p >= min, p <= max). 거절/누락/형식 오류 답은 그 검사의 실패. 요청은 실패한 hard 검사가 없으면 통과. 각 검사의 관측값(확률 또는 선택값, 보고된 confidence, top, 2위, margin, 선택지 수)을 결과에 남겨 나중 문턱 분석에 쓸 수 있다.
- 표에 `independentEst`(L7의 실측 적합식으로 따로 계산한 토큰 추정)를 같이 보여 주고, 선언 추정이 그 2/3에 못 미치면 경고한다. 상한 판정 자체는 선언값으로 한다.
- 점수형(score) 문항은 본문에 있어도 되지만 기대값 형식에는 없다(지시된 형식대로).

## 3. 이 자료로 뒷받침할 수 없는 것 [해석]
1. **보정(calibration).** "confidence 0.8이면 80% 맞는다"를 볼 수 없다. 오답이 거의 없고(선택형 55개 중 오답 4개는 전부 한 요청의 메시지 전체 축), 행들이 독립이 아니다.
2. **독립 표본 수.** scan 174개는 메시지 3개, triage 72개는 메시지 6개, 3지 상태는 메시지 1개에서 나왔다. 행 수가 아니라 이 숫자가 실제 표본 크기에 가깝다.
3. **일반화.** 전부 공개 합성 한국어이고 정답이 분명하도록 설계됐다. 실제 사용자 글, 애매한 문장, 다른 언어에 대한 근거는 없다.
4. **문턱 변경의 안전성.** 발화 축 0.70 등 후보에서 틀린 설치 0은 관찰이지 보증이 아니다(상한 18 ~ 39%).
5. **N이 큰 선택형.** 9지선다는 2개, 7지선다는 11개뿐이다.
6. **지연 꼬리.** 3,000 토큰 초과는 11건, 7,000 초과는 1건이다. 첫 요청의 1초 안팎이 어디서 생기는지도 모른다.
7. **등록 자체의 한계.** 격리 세트의 time_0은 두 값을 모두 허용하도록 등록됐다. 한 값만 허용했다면 오답 1(설치는 어느 문턱에서도 안 됨)이다.
