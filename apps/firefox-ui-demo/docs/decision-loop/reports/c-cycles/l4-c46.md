## 무엇을 만들었나

기록된 실제 입력 (check-29br/29bh/25br의 요청 `LOOP_SAY`, 열두 ledger 재료, check-29br의 한 문장 답, check-25br의 표 답, 엔진이 쓴 기록된 채움)으로 제품 흐름(`runSkeletonFlow`)을 엔진 없이 오프라인으로 돌려, **제품이 실제로 보내는 요청 바이트**를 계획으로 굳혔다.

- 계획 `proofs/decision-real-measure/briefing-layer-replay/` (세트 `l4-briefing-layer-replay`), 요청 3개, 34 질문, 적합 추정 **14,039 토큰 / 천장 15,000** (러너의 `estimateBodyTokens`로 선언; 러너는 x1.1 여유가 천장을 넘을 수 있다고 경고만 낸다).
  1. `layer-place` (16): check-29br의 한 문장 답을 인용한 placement. `combines`, 열두 재료 각각의 `about_M#`, 제목이 겹치는 세 쌍의 `same_`. 재료 관련성 층이다.
  2. `layer-fit` (12): 열두 항목 각각의 `happened_M#`. 카드 종류(순서 카드 = result_lines)를 정하는 층이다.
  3. `layer-coverage` (6): check-25br 표 답의 첫 여섯 사실(`onboard_F1..F6`)을 기록된 실제 보드에 대해. 사실마다 코드가 만든 기대값: 보드에 그 항목의 핵심 수치가 있으면 hard 예, 없으면(알려진 밀집 줄 손실) 아니오를 기록만.
- 토큰 천장 때문에 이 계획에 넣지 않은 단계(order 1.9k, fill_check 5.4k, 나머지 coverage 4.4k, 25br place 8.6k)는 **같은 도구로 따로 만들 수 있고**(요청 바이트는 이미 오프라인 흐름에서 나온다), 재생에서는 check-29br 흐름이 기록한 값으로 대체한다(`defaulted`로 목록 표시: slot .98, step .95, 부분 순서 .09 = 측정 흐름 먼저).
- `replayLayers({ results })` (`helper/egdesk-briefing-layer-replay.mjs`): 러너의 결과 파일을 받아 같은 입력으로 제품 흐름을 다시 돌리되 place/fit 질문은 **실제 Decision 답을 이름으로** 넣는다. 제품 규칙(c41 linked, c44 voted, 묶음, 카드 종류, 부분 순서, 커버리지)을 다시 구현하지 않고 제품 코드를 그대로 쓴다.
- 코드가 기록에서 만든 기대값(hard): 열두 항목 모두 유지(`relevance.kept` 12, 누락 0), 주제 둘이 한 파트씩(파일 이름의 주제어 integration / measure로 만든 M1/M2/M4/M5/M7/M10 대 M3/M6/M8/M9/M11/M12), 각 파트가 날짜순 result_lines 순서 카드, 열두 사실(`9aeed73`, `5752건`, ... `1,812`, ...)이 카드에 있음, 상태 presented. soft: 모든 질문이 답을 받았는가(받지 못한 이름 목록), 부분 순서(기록만).
- 시간: 러너가 요청별 `elapsedMs`를 기록하고, 보고에는 check-29br 흐름이 같은 단계에 잰 시간(place 506, fit 303, coverage 662 ms)과 나란히 나온다.
- 확인: check-29br이 기록한 실제 Decision 답(`about_M12` .26, `about_M11` .65 포함)을 `replayLayers`에 넣으면 열두 항목 유지(M11은 linked, M12는 voted), 두 순서 카드, 열두 사실 모두 통과. 한 로그 전체를 아니오로 바꾸면 hard 실패(6개 빠짐), 답이 없으면 통과가 아니다.
