# L5 / C2 — 전송 인지 타임아웃 + 턴 시작 컨텍스트 cold 루프

브랜치 `lane/c2-timeout-dispatch` (기준 `int/c1` = 1dc3a84). 모든 수치는 루프백 모의 서버(합성 키)의 결과이며, 실제 OpenAI·실제 앱으로 검증한 것은 없다. 증거: `evidence/l5-c2/` (`sim2.mjs`, `ctx-{1409,1800,2229}.json`, `full.tap`).

## 1. 전송 인지 타임아웃

### 문제 (패치 전, 코드 근거)
- `codex-chat-runtime.mjs:4344`의 `expired` 타이머는 POST가 시작됐는지와 무관하게 `chatChoiceManual('timeout')`을 낸다. `egdesk-chat-choice.mjs`도 마찬가지(`authorized && deadline 경과 → 'timeout'`, 키 조회가 멈추면 이유 없는 `manual`).
- 키 조회/어댑터가 멈춰 POST가 한 번도 나가지 않은 경우에도 DM은 "추천이 도착하지 않았습니다"(= 보냈다는 뜻)로 보였고, 기존 테스트 주석도 "Nothing was sent ... told it timed out"이라고 이 불일치를 인정하고 있었다(`egdesk-chat-choice-runtime.test.mjs:162`).
- 반대로 보냈는데 답이 없는 경우(비용 청구 가능)에도 문구는 "다시 시도할 수 있습니다"뿐이어서, 재시도가 요청을 한 번 더 보낸다는 사실을 말하지 않았다.

### 설계
데이터 없는 닫힌 신호 하나: "클라이언트가 POST를 시작했는가"(fetch 호출 직전에 true). 질문·보기·키·제공자 문구는 어디에도 실리지 않는다.
- 클라이언트: `decide({ onDispatch })` 콜백이 `fetchImpl` 호출 직전에 정확히 한 번 호출됨(관찰자가 던져도 요청 불변). `DecisionError.dispatched`(true/false/null)를 `timeout`·`unreachable`에 기록.
- `runChatChoice`: `onDispatch`로 `sent` 기록. 데드라인 경과 시 `sent ? 'timeout' : 'timeout_unsent'`. 클라이언트가 던진 `timeout`도 `!sent`면 `timeout_unsent`.
- 런타임: 래퍼가 실제 클라이언트의 `onDispatch`를 받아 `posted`를 기록, `expired` 타이머가 `posted ? 'timeout' : 'timeout_unsent'`. (래퍼의 기존 `dispatched`는 키 조회 전에 true가 되므로 쓰지 않음.)
- `CHOICE_MANUAL_REASONS`에 `timeout_unsent` 추가(닫힌 enum 유지). 브리지 응답 키는 여전히 `status`, `reason`뿐.
- 로컬 예산 코드는 건드리지 않음(L3 영역). "보냈고 사용량 모름" 집계는 `DecisionError.dispatched`를 읽으면 되도록 신호만 남김.
- `dispatched`는 "fetch를 호출했다"이지 "서버가 받았다"가 아니다. cold 연결 중 타임아웃은 서버에 닿기 전일 수도 있지만 닿았는지 알 수 없으므로 "비용이 청구될 수 있다"가 안전한 쪽이다.

### DM 문구 (승인 대기 카피)
기존 어휘 재사용: "요청을 보내지 않았습니다"(`budget_exceeded`, `overlay/JS/eg-desk-surface.uc.js:12727`)와 같은 어휘.
| 이유 | 문구 | 상태 |
|---|---|---|
| `timeout` | 제한 시간 안에 추천이 도착하지 않았습니다. 요청은 이미 보냈으므로 비용이 청구될 수 있고, 다시 시도하면 요청을 한 번 더 보냅니다. | **변경 카피, 승인 대기** |
| `timeout_unsent` | 제한 시간 안에 요청을 보내지 못해 아무것도 전송하지 않았습니다. 비용은 없습니다. 다시 시도할 수 있습니다. | **신규 카피, 승인 대기** |
둘 다 `retry: true`, 재시도 버튼은 이전처럼 검토 화면으로만 돌아가며 자동 전송하지 않는다.

### Board 사진 적용
Board 경로(`egdesk-board-presentation-http.mjs`)는 타임아웃을 화면에 드러내지 않는다. 모든 실패가 이유 없는 `{ status: 'manual' }`이고 UI도 이유 문구가 없다. 따라서 "타임아웃을 표시하는 경우"에 해당하지 않아 **변경하지 않았다**(이유 필드를 추가하면 소비처 없는 데이터가 되고 기존 `manual` 동등성 테스트에 영향). 필요하면 같은 `onDispatch`를 `client.decide`에 넘기면 되고 Board 문구는 별도 승인이 필요하다.

### 테스트
- 신규: 클라이언트 `onDispatch`/`dispatched` 단위 테스트, chooser sent vs unsent 타임아웃, 결과 매트릭스(`egdesk-chat-choice-outcomes.test.mjs`)에 `timeout_unsent`(키 조회 정지, POST 0건) 추가 및 두 문구 단언.
- 의도적 기대값 변경 2건: 키 조회 정지 시 이전 `manual`/`timeout` → `timeout_unsent`(`egdesk-chat-choice.test.mjs`, `egdesk-chat-choice-runtime.test.mjs`).

## 2. 턴 시작 컨텍스트 cold 루프: abort vs detach vs 예산

방법: `sim2.mjs`가 실제 `prepareTurnContext`와 클라이언트를 사용. 턴1 → 턴1이 끝난 뒤 gap → 턴2. "detach"는 800 ms에 기다리기를 멈추되 요청은 최대 3000 ms까지 살려 둔다(결과 폐기). 서버: 유휴 5 s 후 소켓 종료, Keep-Alive 힌트 없음(undici 4 s 기본). cold = 1409/1800/2229 ms. 표는 `턴1 / 턴2` 결과(ms).

| 방식 | cold | gap 1 s | gap 3 s | gap 6 s | gap 12 s |
|---|---|---|---|---|---|
| **abort@800 (현행)** | 전부 | 폴백 / 폴백 | 폴백 / 폴백 | 폴백 / 폴백 | 폴백 / 폴백 |
| **detach@800** | 1409 | 폴백 / **ready 306** | 폴백 / **ready 304** | 폴백 / 폴백 | 폴백 / 폴백 |
| | 1800 | 폴백 / 폴백(겹침) | 폴백 / **ready 304** | 폴백 / 폴백 | 폴백 / 폴백 |
| | 2229 | 폴백 / 폴백(겹침) | 폴백 / **ready 302** | 폴백 / 폴백 | 폴백 / 폴백 |
| 예산 1500 | 1409 | ready 1411 / 305 | ready 1413 / 303 | ready 1411 / 1411 | ready 1411 / 1412 |
| | 1800, 2229 | 폴백 / 폴백 | 폴백 / 폴백 | 폴백 / 폴백 | 폴백 / 폴백 |
| 예산 2500 | 1409 | ready 1412 / 304 | ready / 303 | ready 1411 / 1411 | ready / 1411 |
| | 1800 | ready 1804 / 303 | ready / 303 | ready 1803 / 1802 | ready / 1803 |
| | 2229 | ready 2231 / 303 | ready / 303 | ready 2230 / 2232 | ready / 2230 |

판단:
- detach는 **턴1을 구하지 못하고**(항상 폴백), 턴2도 소켓이 데워져 있고 4 s 유휴 한도 안인 좁은 창(대략 gap 1~3 s, cold가 짧을 때만)에서만 warm이다. gap 6 s 이상(= 실제 DM 턴 간격 대부분, 분 단위)에서는 효과 없음. gap 1 s에서 cold가 길면 두 번째 요청이 첫 요청과 겹쳐 두 번째 cold 소켓을 하나 더 연다(전송 횟수는 턴당 1건으로 동일하지만 동시 in-flight 2건).
- 비용: 요청은 이미 전송되므로 전송 횟수·요청 내용은 동일(서버 수신은 턴당 1건). 차이는 서버 쪽 결과가 `client_aborted` 대신 `answered`로 끝나는 것뿐. 로컬 집계는 기존처럼 폐기된 응답을 기록하지 않음(L3 영역).
- **구현하지 않음**: "명확히 도움"이 아니고(좁은 창, 턴1 구제 없음), 소켓 수명을 늘리려 요청을 background로 살려 두는 복잡도(신호 구조 변경, 턴 취소 시 즉시 abort 필요)가 있다.

### 사용자 결정 선택지 (수치는 위 표 기준)
| 선택지 | 효과 | 비용 | 동의 측면 |
|---|---|---|---|
| (a) DM 입력 시작 시 pre-connect | cold가 TCP/TLS 비용이라면 숨길 수 있어 턴 시작은 warm 300 ms대 가능. cold가 서버 측 첫 요청 비용이면 효과 없음(원인 미규명, 실제 앱 측정 필요). 입력이 4 s 이상 걸리면 undici 기본 유휴 4 s로 소켓이 먼저 닫혀 이득이 사라질 수 있음 | 연결 1회/입력 시작 | **명시적 사용자 행동 없이 api.openai.com에 접속**: Decisions 켬 상태에서 입력 시작이 "호출 동의"를 함의하는지 사용자 결정 필요(연결만으로 데이터는 안 나가지만 사실상 새 아웃바운드). 제안 전용, 구현 안 함 |
| (b) 턴 시작 예산 확대(예: 2500 ms) | cold 1.4–2.2 s에서도 폴백 0건(위 표), 단 **cold 턴마다 턴 시작이 1.4–2.2 s 늦어짐**(warm 턴은 ~300 ms로 영향 없음). 6 s 이상 간격이면 매번 cold이므로 사실상 대부분의 턴이 그 지연을 겪음. 예산 1500은 cold 1.8 s 이상에서 효과 없음 | 턴당 최대 +1.4–2.2 s | 새 동의 없음. 800 ms 캐논(`DECISION_MODEL_CONTEXT_SETUP.md` 96행: 대기 한도)과 충돌하므로 캐논 수정 필요 |
| (c) 폴백 수용(현행) | 지연 0 추가, cold 턴은 항상 현행 방식으로 진행. 실제 사용에서 컨텍스트 결정은 명시 호출로 소켓이 데워진 직후(수 초 이내)에만 발동 | 없음 | §1 "실패하면 지금 방식으로" 그대로 |
권고: 근거 수치만으로는 (c) 유지가 안전하고, 실제 앱에서 cold 원인(TCP/TLS vs 서버 첫 요청)을 먼저 측정한 뒤 (a)/(b)를 결정하는 것이 맞다. (b)는 지연을 사용자 체감 비용으로 바꾸므로 단독으로 권하지 않는다.

## 4. 철학 점검
P2 "결정 호출이 실패하면 지금 방식으로 돌아간다": 폴백 경로·재시도 없음·`off`=0 호출 모두 불변. 새 표시는 *진실한 설명*만 더한다: 보내지 않았으면 "비용 없음", 보냈으면 "비용이 청구될 수 있고 재시도는 한 번 더 보낸다". 이는 "모델 제안 ≠ 승인된 실행"에서 사용자가 재시도(=또 한 번의 전송)를 알고 결정하게 한다. P3: 새 연결·pre-connect·detach 모두 구현하지 않음.
