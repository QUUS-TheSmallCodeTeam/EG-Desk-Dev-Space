## 사용자 방향 반영
하트비트의 판단에 "어느 작업이 어느 활성 사용자의 어느 화면으로 가는가"까지 들어가야 한다. → 하트비트를 **다른 기능이 내 모듈을 고치지 않고** 사실과 질문을 얹을 수 있는 공용 판단 지점으로 만들고, 메시지 판단 자체도 "누가 기다리는가"를 본다.

## 1. 다른 레인을 위한 API (계약은 `egdesk-heartbeat.mjs` 머리말에 문서화)
- **사실**: `hb.register(name, () => facts)` 또는 `{ facts() }`. 숫자·불리언·닫힌 라벨만 남는다. 매 비트 `facts.sources[name]`으로 모든 구독자에게 보인다.
- **질문 제안**: `hb.register(name, { facts?, propose(beat), onVerdict({ beat, verdicts }) })`. `propose`는 이 비트에 실제 선택이 있을 때만 `{ name, instructions, options: [{ value, description }], none?, facts?, kinds? }`를 낸다.
  - 닫힌 어휘 강제: 질문 이름·선택지 값은 닫힌 라벨(제공자 자신의 어휘), 선택지 2~8개 중 하나는 "아무것도 안 함"(`none`). `instructions`/`description`은 고정 영어 프롬프트(출력 가능한 ASCII, 300자 이하)만 통과한다. 제목·이름 같은 내용을 넣은 질문은 **그 질문만** 거절된다(시험: 한글 제목, 대문자 값, 긴 문장, 중복, `none` 없음 등). 질문의 `facts`도 숫자·닫힌 라벨만.
  - `kinds`: 실행 사실 외에 필요한 egress 종류. 이 실행의 모델이 받을 수 없는 종류면 **그 질문만** 빠지고 나머지는 묻는다.
- **비트당 요청 1개**: 그 비트에 제안된 모든 질문(메시지 필요 여부 + 제공자 질문들)이 **하나의 Decision 요청**에 독립 질문으로 실린다(`egdesk-heartbeat-judge.mjs`, 신규; egress 등록 `run_facts`). 세션 줄(경과 시간·단계·phase)은 공유하고 질문별 사실은 `Question <제공자>__<이름>:` 블록에 둔다.
- **자기 판정만 수신**: `onVerdict`는 자기 질문의 판정 `{ name, value, accepted, failed, skipped, confidence, margin }`만 받는다. `subscribe` 구독자는 사실만 받고 판정은 받지 않는다. 한 일을 닫힌 라벨로 돌려주면 내용 없는 기록에 남는다.
- **공유 상한(기존 값 유지, 하트비트로 이동)**: 비트당 요청 최대 1, 한 번에 한 라운드(모든 `onVerdict`가 끝나거나 60 s), 요청당 질문 6개, 요청 간 10 s(모두 `none`이면 20→40→80 s), 한 번도 제안된 적 없는 선택지는 즉시 물을 수 있음, 하트비트당 요청 6회. 예산·기한·egress는 소유자(런타임)의 판정기가 지고, 제공자는 Decision을 직접 부르지 않는다.
- 메시지 판단은 이제 이 API의 **제공자 하나(`message`)**다. c9/c11 시나리오 16건은 구조 변경 뒤에도 그대로 통과(시험 하네스의 질문 이름·캐시 키만 새 요청 형식에 맞춤).
- 계약 시험 `egdesk-heartbeat-contract.test.mjs`(가짜 제공자, 5건): 한 요청에 3질문·각자 판정만 수신, 내용이 든 질문 거절, 상한(간격·배증·새 선택지·6회·6질문), 한 번에 한 라운드, 실패의 국소성(판정기 오류, 던지는 제공자, 허용 안 된 종류, 라운드 중 정지).
- 런타임 시뮬: `placement` 제공자를 `runtime.heartbeatFor(key).register(…)`로 붙이면 10 s 비트에 **요청 1개**에 `message__need`+`placement__surface`가 실리고, `canvas_text`를 선언한 질문은 이 실행에 보낼 카드가 없어 혼자 빠진다(제안 3 → 전송 2). 실행이 생기기 전(턴 이전 객관 루프)에도 제공자 질문은 대화의 게이트로 판정된다.
- 보정 기록: 항목에 `questions` 수와 판정별 `provider`(닫힌 집합: message, placement, attention, presence, browser_task, terminal_loop; **새 제공자는 `egdesk-decision-calibration-log.mjs`에 이름을 추가**해야 기록에 남는다) 추가.

**다른 레인이 알아야 할 것**: (a) 요청 6회·질문 6개는 하트비트의 **모든 제공자가 나눠 쓴다**. 매 비트 제안하는 제공자는 메시지 판단의 몫을 줄인다(상한은 런타임이 `limits`로 정함; 늘릴지는 Main 결정). (b) 판정에 텍스트 근거를 보낼 수 없다(숫자·닫힌 라벨만). 텍스트가 필요한 판단은 하트비트 밖에서 자기 요청으로 해야 한다. (c) 제공자는 최대 8개(런타임이 `audience`, `message`, 때로 `browser_task`를 씀).

## 2. 다중 사용자 인식
- 규칙(순수 함수 `audienceFacts`, `egdesk-conversation-flow.mjs`): 과업의 `audience { requester, owner, participants }`와 presence 스냅샷 행 `{ member, self, active, viewport, focusCard, lastInputAgeMs }`에서
  - `waiting`: 요청자가 있으면 `requester`, 요청자가 없고 소유자가 있으면 `owner`, 아니면 `nobody`.
  - `postable`: 기다리는 사람이 **이 대화의 참여자**이고, 대화의 모든 참여자가 **요청자 또는 소유자**일 때만.
- 메시지 판단: `postable`이 아니면 선택지가 `none`뿐이라 **요청도 하지 않는다**. 게시 직전에 다시 읽어, 판정과 게시 사이에 사람이 떠나면 쓰인 메시지도 게시하지 않는다. 판정 사실에 `waiting_person`, `waiting_person_present`, `waiting_person_idle_seconds`가 들어간다. **구성원 id는 요청·비트·기록 어디에도 나가지 않는다**(닫힌 라벨과 숫자만; 시험으로 확인).
- 다른 제공자용 사실: `facts.sources.audience { waiting, addressee, addresseePresent, addresseeInConversation, postable, reasoningOpen }`. 예: 소유자가 다른 곳에 있으면 `addressee: owner, addresseeInConversation: false`로 보여 주므로 L4가 주의 환기·배치를 판단할 수 있다(런타임은 다른 대화에 메시지를 넣지 않는다).
- 연결: `decisionContext.conversationFlow.presence.snapshot()`와 `conversationFlow.audience({ run })`(선택). 없으면 오늘과 같다: 로컬 사용자가 자기 DM에서 물었고 presence는 `unknown`.
- 시뮬(스텁): 초대된 요청자 있음 → 게시 1; 요청자 없음·소유자 참여 → 게시 1(`waiting_person: owner`); 아무도 없음 → 요청 0·게시 0; 제3자가 참여한 대화 → 요청 0; 소유자가 이 대화에 없음 → 요청 0(사실로만 노출); 판정 뒤 떠남 → 작성은 됐으나 게시 0.
- 한계: `viewport`, `focusCard`는 아직 규칙에 쓰지 않는다(`active`와 입력 경과만). `audience`를 주는 실제 공급자가 없고, 지금 말할 수 있는 실행은 직접 DM뿐이라 **다중 사용자 경로는 스텁으로만 검증**했다. 아무도 없을 때는 이른 질문도 하지 않는다(돌아왔을 때 최종 답이 있다).

## 3. 멈춤과 긴 추론의 구분
- 확인한 것:
  - 공개 문서(https://developers.openai.com/codex/app-server): 항목 델타로 `item/reasoning/summaryTextDelta`, `item/reasoning/summaryPartAdded`, `item/reasoning/textDelta`("모델이 지원할 때")가 있다. `thread/tokenUsage/updated`는 토큰 집계 이벤트에서 나온다(openai/codex 커밋 401f94c, app-server `bespoke_event_handling.rs`).
  - 저장소: `cleanNotification`은 이 중 `summaryTextDelta`와 `tokenUsage`만 통과시켰고 나머지는 버렸다. c11의 "마지막 엔진 이벤트"는 통과한 이벤트만 셌다.
- 수정: **스레드에 온 모든 알림·서버 요청**(런타임이 쓰지 않는 것 포함)이 도착 즉시 하트비트의 엔진 표시를 옮긴다(`markEngineActivity`; 종류는 닫힌 라벨 reasoning/output/tool/usage/turn/other로 `lastEngineKind`에 남음). 시작했지만 끝나지 않은 reasoning 항목을 기억한다.
- 멈춤 규칙: `stalled`는 **엔진 차례(phase가 thinking)일 때만**. 진짜 침묵 20 s 유지. reasoning 항목이 열려 있으면 60 s(추론을 스트리밍하지 않는 모델은 끝날 때까지 아무것도 보내지 않을 수 있으므로; 판단값). **도구가 조용히 오래 도는 것은 멈춤이 아니라 기다림 설명 대상**으로 바꿨다(c11에서는 23 s 조용한 도구에도 `stalled`가 제안됐다).
- 시뮬: 60 s 추론 중 4 s마다 위 네 가지 알림 → 침묵 4 s 이하, `stalled` 제안 0; reasoning 항목만 열리고 무소식 → 55 s까지 제안 없음, 65 s 비트에 제안; 항목이 닫힌 뒤 22 s 침묵 → 제안; 58 s 조용한 도구 → 기다림 메시지 1, `stalled` 제안 0.
- **확인하지 못한 것**: (1) 실제 모델이 긴 추론 중 델타를 얼마나 자주 보내는지, 요약/원문 추론이 꺼진 모델이 중간에 무엇이라도 보내는지. (2) reasoning 항목의 `item/started`가 추론 시작 때 오는지 끝난 뒤 한꺼번에 오는지. (3) `thread/tokenUsage/updated`가 추론 도중에도 오는지(문서상 모델 응답 단위로 보임). (1)(2)가 불리하면 추론을 숨기는 모델의 20 s 넘는 추론에 `stalled`가 제안될 수 있다. 기록의 `sinceEngineS`로 실측 보정이 필요하다.

## 4. 제한(bounded) 실행의 말하기
- 결정: **허용한다, 실행 단위 opt-in으로.** `runtime.allowIntermediateMessages(conversationKey)`를 부른 대화의 실행만 중간 메시지를 낼 수 있다. 조건·성질: 초안 검사가 켜져 있어야 함(같은 검사), 완성된 메시지만 같은 경로로 게시, **최종 답변의 보류 여부(hold-eligibility)는 바뀌지 않음**(그 실행의 최종 답은 오늘처럼 스트리밍), 최종 답변이 시작되면 더는 말하지 않음, 다른 제한 실행은 영향 없음.
- 검사: 제한 실행은 턴의 근거를 쓸 수 없으므로 **근거 없이** 검사한다(구체적 사실을 말하는 메시지는 실패해 게시되지 않음). 같은 규칙을 보호된 근거가 있는 보류 실행에도 적용했다(c9는 그 경우 검사 없이 게시했다: 더 엄격해짐).
- 시뮬(readOnlyQa 제한 실행 2개): opt-in한 실행은 12 s에 완성 메시지 1, 다른 실행은 요청 0·메시지 0; opt-in 실행의 최종 답은 델타로 스트리밍되고 그 뒤 40 s 동안 추가 메시지 없음; 초안 검사가 꺼져 있으면 opt-in해도 요청 0.
- **L8에 남는 것(중요)**: (a) `runBrowserEntryOn`에서 opt-in을 부르는 한 줄은 넣지 않았다(L8이 재배치 중인 코드). (b) 브라우저 작업 루프는 **네이티브 실행이 생기기 전**에 돈다. 그 구간에는 메시지를 실을 실행이 없어, opt-in을 해도 런타임이 **루프 도중에는 게시할 수 없다**(실행이 생긴 뒤부터 가능). 루프 중에 말하려면 루프를 실행 안에서 돌리거나(예: 실행 중 도구 호출 경로) 실행을 먼저 만들어야 한다. 그 전에도 제공자 질문은 판정되므로(위 1) L8이 자기 표면에 표시하는 것은 가능하다.
