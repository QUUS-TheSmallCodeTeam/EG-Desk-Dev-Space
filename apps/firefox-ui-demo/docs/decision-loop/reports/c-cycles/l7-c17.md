## 2. s9: 대상과 상태가 정해졌는데 읽기가 없었던 이유

| 단계 | 값 |
|-|-|
| 대상 (`tw_target`) | P7 = `ontology:db/pg-plan`, 0.99 |
| 상태 (`tw_status`) | done 0.94 |
| 시점 라벨 | past_unspecified 0.77, 확신 0.73. 0.85 선 미만이라 설치 안 됨 |
| 제안 | `update_status`, `time.slice: 'unknown'` |
| 쓰기 | `writer.apply` → `{ status: 'invalid' }` (이유 없이) |

- **원인**: 시점 라벨이 설치되지 않아 제안의 slice 가 `unknown` 이 됐다. 그러자 writer 가 제안 전체를 무효로 거부했다.
- **아닌 것**: choice 경로 자체, 동의, writer 미설정 (writer 있음, mode on, 실행 completed) 은 원인이 아니다. 두 설계 모두 같은 줄을 쓴다.
- **수정**: `readingSlice` 를 추가했다. 설치된 시점 라벨이 있으면 그것을 쓰고, 없으면 정해진 상태에서 코드로 정한다 (done → past, plan → planned). writer 의 거부에는 이제 이유가 붙는다 (`provenance`, `time_slice`).
- **테스트**: 런타임 on 리그로 실제 s9 라벨 값을 넣었다. `choice`, `about` 둘 다 대기 읽기 `done` 이 남고 상태는 바뀌지 않는다. 수정을 빼면 실패한다.

## 3. 정직성: 답이 하지 않은 기록을 말하지 않게

- **선택**: 답변 모델에 "기록하겠다고 말하지 말라" 고 알리는 쪽을 골랐다.
- **이유**: 쓰기 판정은 답이 끝난 뒤에 돈다. 답을 내는 시점에는 확인할 쓰기가 아직 없으니, 주장을 실제 쓰기와 대조하는 방식은 순서상 불가능하다. s9 가 그 사례다 ("네, 기록해 두겠습니다." 를 말했는데 아무것도 기록되지 않음).
- **`RECORDING_RULE`** (모델용 지시, 사용자에게 보이지 않음): "EG-Desk 가 답 뒤에 기록 여부를 정하고, 기록은 사용자가 확인할 때까지 미확정이다. 기록했다거나 기록하겠다고 말하지 말라. 기록된 것이 있으면 다음 턴에 알려 준다."
  - 기록이 따라올 수 있는 턴에만 붙는다: 묶음이 붙은 첫 턴(기록 판정이 아직 도는 중), 그리고 분류가 "기록할 가치 있음" 으로 정한 중간 턴.
  - 묶음이 거부·차단되거나 꺼진 턴에는 붙지 않는다.
  - 실제로 기록된 것은 다음 턴의 확인 메모(`confirmInConversation`)로 전달된다.
- **초안 점검 쪽**: L3 와는 근거 항목으로만 맞춘다. 같은 턴들에 `record-state` 항목(kind memory, source system)을 넘긴다. 내용은 "답 중에는 아무것도 기록되지 않는다, 기록은 답 뒤에 생기고 확인 전까지 미확정" 과, 이 세션에서 기록됐고 확인을 기다리는 읽기 목록이다. "기록해 두겠습니다" 를 이 근거로 판정할지는 L3 가 정한다.
- **아직 모르는 것**: 실제 답변 모델이 이 지시를 따르는지는 측정하지 않았다. 다음 여정에서 s9 의 답 문장으로 보면 된다.

## 4. 브라우저 작업 기록은 시스템 결과다 (s11.record)

- **실제 값**: s10, s11 의 쓰기 판정은 시스템 메모에 대해 target new 0.20 / 0.18 대 none 0.41 이었고, 발언 라벨 form 은 unknown 0.30 이었다. 그래서 아무것도 쓰이지 않았다.
- **결정 (R3)**: 쓰기 판정을 거치지 않는다. 작업의 id, 사이트, 단계, 결과는 코드가 안다. 예전 코드도 판정 결과와 상관없이 항상 새 페이지로 바꿔 쓰고 있었으니, 판정이 보탤 것이 없었다.
- **변경**: `createOutcomeToOntology` 가 코드 규칙으로 쓴다. 새 페이지, provenance agent_note, time past, 상태 done(완료) 또는 unknown(중단), 링크 없음. 같은 operation id, 같은 egress 조건(browser_task_record + memory_page).
- **L8 영향**: 시그니처는 그대로다 (`client` 는 받고 무시). 호출부 변경은 없고 import 하나만 빠졌다. L8 에 알렸다. Decision 요청이 작업당 1건 줄어든다.
- **테스트 갱신**: L8 의 C10 은 쓰기 판정 요청 없음, 저장된 페이지는 그대로 단언한다. egress 테스트는 허가가 있으면 저장되고 요청 없음, 없으면 저장 안 됨. L2 여정의 b2 는 memory_write 없음.
- **이번 실행의 s11 에는 해당 안 될 수 있다**: s11 은 작업 자체가 끝나지 않았다 (L8 의 s11.download). 중단 코드가 기록 대상 목록에 있을 때만 페이지가 생긴다.

## 5. 브리핑 자료의 날짜·상태·버전 링크

- **원인**: 온톨로지 노드의 기록된 상태는 스냅숏에 속한 노드만 넘어왔고, 날짜는 `pagesFromCandidates` 가 버렸다.
  - 실제 동봉 그래프(`overlay/resources/ontology/graph.json`, 노드 102개)에는 날짜 필드가 아예 없다.
  - 상태가 있는 노드는 스냅숏에 속한 2개뿐이다 (planned/observed).
- **수정**:
  - `candidatesFromOntologyGraph`: 스냅숏 밖 노드가 자기 `status` 를 기록하고 있으면 그것을 쓴다. 노드가 ISO 날짜 `at` 을 기록하고 있으면 넘긴다. 본문에서 날짜를 읽지는 않는다.
  - `pagesFromCandidates`: `time.at` 을 유지한다.
  - 버전 링크는 기존 관계 매핑(supersed/replac/obsolet → supersedes)으로 이미 넘어오고 있었다.
- **L2 하네스**: 그래프가 합성 페이지에 기록된 날짜와 상태를 노드에 싣게 했다.
- **제품 경로 테스트** (`scripts/egdesk-memory-materials-briefing.test.mjs`):
  - A사 질문 뒤 `memoryMaterialsFor` 행에 2026-11-06 같은 기록된 날짜, v2 계획의 status plan, v2→v1 supersedes 가 있다.
  - L4 의 `enumerateSkeleton` 이 sequence, open_items, compare 를 모두 낸다.
  - 날짜나 노드 상태 전달을 빼면 테스트가 실패한다.
  - L4 코드는 건드리지 않았다.
- **한계**: 실제 사용자 온톨로지에 날짜·상태가 기록돼 있지 않으면 여전히 규칙이 돌지 않는다. 그 데이터를 어디서 받을지는 소유자 결정이다.
