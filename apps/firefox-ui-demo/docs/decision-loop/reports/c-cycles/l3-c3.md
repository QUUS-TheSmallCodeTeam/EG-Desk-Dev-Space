# L3 cycle 3: 키 저장 분기, 키 교체 안전, 전송 후 무응답 요청의 로컬 집계

브랜치 `lane/c1-budget-durability`, c2(`1b81a1a`) 위 신규 커밋은 최종 답변에 기재. 증거 `evidence/l3-c3/`: `before-key.log`, `after-key.log`, `before-tally.log`, `after-tally.log`, `regression-after.tap`, `simkey.mjs`, `simtally.mjs`.
**합성 하네스 관찰**: 실제 `createDecisionHttpHandler` + 실제 자격증명/예산 저장소 + 실제 `createDecisionClient`(loopback mock 제공자, Authorization 헤더로 OLD/NEW 키 구분) + 실제 `EGDeskAccountSettingsView.sys.mjs`(문구 함수 호출). **실제 설치 앱·Firefox 화면 검증은 하지 않았다.** 포커스·입력창 동작은 `eg-desk-surface.uc.js` 코드 읽기로만 확인했으며 이 하네스로 실행해 보지 못했다.

## 1. 키 저장 분기 (원본, `before-key.log`; 신규 키 / 기존 키 없음 기준, 괄호는 교체 시)
| 분기 | HTTP | 키 저장 | 화면 문구(원본) | 모드 |
|---|---|---|---|---|
| verified | 200 | 저장(교체) | 확인됨 | 불변 |
| not_verified (확률 0.3) | 422 | 안 함 | **"OpenAI에 연결하지 못했습니다"**(오표시) | 불변 |
| invalid_key | 422 | 안 함 | 키가 올바르지 않습니다 | 불변 |
| no_credit | 200 | 저장 | 크레딧 없음 · 저장했습니다 | 불변 |
| spend_limit_reached | 200 | 저장 | 지출·사용 한도 · 저장했습니다 | 불변 |
| rate_limited | 200 | 저장 | 요청 한도 · 저장했습니다. 잠시 뒤 다시 시도 | 불변 |
| timeout (5초 대기) | 422 | 안 함 | 제때 답하지 않았습니다 | 불변 |
| unreachable | 422 | 안 함 | 연결하지 못했습니다 | 불변 |
| server_error | 422 | 안 함 | **"연결하지 못했습니다"**(오표시) | 불변 |
| model_unavailable | 422 | 안 함 | 이 키로는 결정 모델을 쓸 수 없습니다 | 불변 |
| bad_response | 422 | 안 함 | **"연결하지 못했습니다"**(오표시) | 불변 |
| budget_exceeded(로컬 상한 도달, 추가 점검) | 422 | 안 함 | **"연결하지 못했습니다"**(오표시), 제공자 호출 0회 | 불변 |

문제 A: `DECISION_VERIFICATION_TEXT`(`EGDeskAccountSettingsView.sys.mjs`)에 not_verified·server_error·bad_response·budget_exceeded가 없어 `unreachable` 문구로 떨어짐. 재시도 안내는 rate_limited만 있고, 서버 오류(재시도 의미 있음)에는 없었음.
**코드로만 확인(실행 미검증)**: `eg-desk-surface.uc.js:22313-22317` `saveDecisionKey`는 POST 전에 `input.value = ''`로 비우므로 **모든 분기에서 입력창이 비워진다**(실패해도 다시 붙여넣어야 함). 저장 중에는 탭 전체를 다시 그려(`renderAccountTab`) 입력창이 새로 만들어져 **포커스가 명시적으로 이동하지 않는다**(문서 body로 빠질 가능성). 비밀번호 필드를 실패 시에도 비우는 것은 키를 DOM에 남기지 않는 안전한 쪽이라 바꾸지 않았다. 포커스 복원은 실제 앱에서 확인해야 해서 패치하지 않고 다음 sim 후보로 둔다.

## 2. 키 교체 안전 (`before-key.log`, OLD 키 저장+모드 on+월 합계 510)
- 원본 문제 B: 새 키가 **no_credit / spend_limit_reached / rate_limited**이면 `SAVE_ON` 때문에 **동작 중인 OLD 키가 NEW로 교체**됨(`OLD->NEW`), 이후 결정이 모두 크레딧 없음·한도로 멈춤. 근거 문서(https://developers.openai.com/api/docs/guides/error-codes): 이 오류들은 재시도로 풀리지 않으므로 교체는 되돌리기 어려운 회귀다. 키가 없을 때 저장하는 이유(나중에 크레딧을 받아 다시 입력하지 않으려는 것)는 교체에는 해당하지 않는다.
- 그 외 실패(invalid, not_verified, timeout, unreachable, server_error, model_unavailable, bad_response, budget_exceeded): OLD 유지, 모드 저장 호출 0회, 남는 임시 파일 없음(settings 디렉터리에 credential/budget 파일만), 원본부터 정상.
- verified 교체: OLD 사라짐(grep OLD = 없음, NEW는 `settings/egdesk-decision-credential.json`에만), 월 합계 510 유지(+검증 호출 10 = 520).
- 교체 중 진행 중인 DM 추천(OLD 키로 600ms 지연): 요청은 OLD로 이미 전송됨(제공자가 AAAA 확인), 교체는 즉시 성공, 진행 중 결과는 `{status:'manual'}`로 버려짐(설정 세대 변경, `onSettingsChanged`), 다음 요청은 NEW(BBBB) 사용, OLD 잔존 없음, 합계 30(진행 중 요청 10 포함). 설계대로라 변경 없음.

**수정**: `egdesk-decision-http.mjs`: 이미 저장된 키가 있고 새 키가 `verified`가 아니며 같은 키가 아니면 422 `DECISION_KEY_NOT_REPLACED`(검증 상태 포함)로 거절하고 OLD 유지. 같은 키 재입력은 기존처럼 갱신. 키가 없을 때의 저장 동작은 그대로. 화면: 이 코드에 `새 키에 크레딧이 없습니다 · 새 키로 바꾸지 않았습니다. 지금 쓰는 키는 그대로입니다. 기존 키를 지운 뒤에는 이 키도 저장할 수 있습니다.`(spend/rate 변형 포함)를 표시해 다음 행동을 알림. 서피스는 `code`와 `verification`을 이미 전달하므로 **서피스 수정 없음**.
추가 문구(Main 정리용, 모두 설정 화면 키 검증 영역): not_verified `OpenAI가 키 확인 질문에 통과시키지 않았습니다`, server_error `OpenAI 서버 오류입니다. 잠시 뒤 다시 시도하세요`, bad_response `OpenAI의 답을 해석하지 못했습니다`, budget_exceeded `이번 달 로컬 사용 한도에 도달해 확인하지 못했습니다`, NOT_REPLACED 문구 3종. DM 결과 문구는 건드리지 않음.
이후(`after-key.log`): 교체 시나리오 12개 모두 OLD 유지 또는 verified일 때만 NEW, 모드 불변, 합계 불변(검증 호출 분 제외), 임시 파일 없음.

## 3. 전송 후 무응답 요청의 로컬 집계 (L2 관찰 평가)
**측정(`before-tally.log`)**: mock 제공자가 요청을 받은 뒤 429, 500, 응답 없음(timeout), 헤더만 보내고 본문 정지, 호출자 취소(abort) 각 1회 → 제공자 수신 4~6회에 비해 로컬 합계는 정상 응답 400만 증가, 나머지 0. 관찰 확인.
**조사(1차 출처 우선)**
- OpenAI 오류 코드 문서: 한도·크레딧 429는 접근을 막은 것이고 재시도로 풀리지 않는다. 429/500의 과금 여부는 명시되지 않음.
- OpenAI 지원 답변(커뮤니티 공식 계정, https://community.openai.com/t/cancelling-stream-does-not-show-usage/1377768): 스트림이 취소·중단돼도 "Billing/usage is still recorded on our backend", 최종 사용량 이벤트만 전달되지 않을 수 있음. 스트리밍 응답에 대한 답이며 일반 비스트리밍 요청의 명시적 규칙은 아님.
- 2차 자료: 비스트리밍은 전체 생성 과금, 취소해도 컨텍스트(입력)는 과금(커뮤니티 답변), "OpenAI는 중단된 스트림·타임아웃의 과금 규칙을 문서에서 밝히지 않았다"(https://infro.io/blog/do-providers-bill-cancelled-or-failed-streams-what-to-forecast).
- 결론: 타임아웃·취소 후 과금 여부는 **공식 문서로 확정되지 않았으나 입력이 과금될 가능성이 크다.** 기본 응답 대기가 1.5초(`DEFAULT_DECISION_TIMEOUT_MS`)라 지연이 큰 환경에서는 실제 지출이 로컬 합계보다 크게 누락될 수 있다.
**결정**: 문서화만 하지 않고 **보수적 추정치를 별도 필드로** 집계. (1) 전송 직전 표시(`dispatched`)를 세우고, 타임아웃(헤더 후 본문 정지 포함) 또는 전송 후 취소일 때만 추정 기록. 429/5xx(제공자가 오류로 거절, 사용량 없음), 전송 전 취소·미연결(`unreachable`)은 집계하지 않음. (2) 추정 = 본문 UTF-8 바이트/3(한글 1글자≈3바이트≈1토큰이라 높게 잡힘) + 인라인 이미지는 base64 크기 대신 detail 기준(low 85, 그 외 765). (3) 측정값 `inputTokens`와 섞지 않고 `estimatedInputTokens`와 `unmeteredRequests`(건수)로 분리, 상한 판단(`canSpend`)만 합산. (4) 설정 화면 집계 줄에 `+ 응답 없이 보낸 요청 N건 추정 M`으로 표시, 상한 도달 문구도 합산 기준. (5) 필드는 `unmeteredRequests > 0`일 때만 스냅샷·파일에 나타나 기존 소비자(status, 파일, 기존 시험)의 모양은 변하지 않음. 상한 기본값은 여전히 없음(상한 미지정이면 집계만).
**이후(`after-tally.log`, 상한 5000)**: ok 400, 429·500 추정 0, timeout +367(1건), 본문 정지 +734(2건), abort +1101(3건), 합계 400은 그대로. 추정이 상한에 합산되어 `canSpend`가 바뀜(상한 1000 시험에서 헤더 정지 후 `budget_exceeded`).
한계: 추정은 청구액이 아니다(실제 토큰화와 다를 수 있고, 제공자가 실제로 처리하지 않은 요청까지 센다). 월 경계에서 진행 중이던 요청의 귀속은 미검증.

## 6. 철학 점검
원칙: **사용자의 선택(저장한 키와 모드)을 사용자가 정하기 전에는 바꾸지 않는다 / 지출 통제는 정직하게 센다.** 동작하는 키를 쓸 수 없는 키로 조용히 바꾸지 않고(교체는 검증된 키만, 아니면 이유와 다음 행동을 알림), 보냈지만 결과를 모르는 요청을 "0"으로 숨기지 않고 추정이라고 표시해 소유자의 상한이 실제 위험에 더 가깝게 작동한다. 상한은 여전히 소유자가 정하기 전에는 없다.
