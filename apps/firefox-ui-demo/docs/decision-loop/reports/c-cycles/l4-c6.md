브랜치 `lane/c6-briefing-flow` (기준 `int/c5` 1cf9261). 커밋 `01c754a`(시험), `1ce477f`(구현). 합성 하네스 결과이며 설치된 앱 검증이 아니다.

## 1. 기존 코드와 오늘의 동작 (`evidence/l4-c6/before-today.txt`)
- 상태/표시: `overlay/resources/EGDeskBriefingState.sys.mjs`(단계·target·강조·이동·댓글 상태, `validBriefing`, 브리핑 요청 제안 `briefingRequestOffer`), 서피스에 534곳 연결.
- 제안 경로: Agent가 도구 `egdesk_publish_briefing` / `_multi`(단계마다 target 1–6개, `emphasis`, `fallback`) / `_regions`를 호출하면 `helper/egdesk-context-runtime.mjs` `publish()`가 target(sourceId/artifactId/canvasRect/annotationSet)의 존재·권한을 검증해 `presentationStatus:'proposed'`로 저장하고 `briefing.published` 이벤트를 낸다. 카메라·실행·새 턴 없음.
- 말풍선 vs 보드의 결정은 **오늘 Decision이 아니라 Agent의 도구 선택**이다(`egdesk_publish_output`: "about 30 lines or more… not for short answers"). 브리핑 코드 경로의 Decision 호출은 0건이다. 사용자 경로로는 답변 아래 '브리핑 요청'이 초안만 입력칸에 넣는다.
- canon: 계약 §8(순서 있는 step, 단계별 target set, focus/camera, 짧은 사용자용 설명, 대상 없음/stale/권한 없음의 fallback; System이 모든 target의 존재·권한·freshness를 검증), Atlas §0.5/AI-05/OBJ-038..040, JEV §9.4 JEV-BRIEF-01 "Briefing 설명과 대상 일치"(단계 설명이 가리키는 target과 맞는지 판정, 시스템이 후보 ID를 열거하고 자유 생성 문장을 인용으로 쓰지 않음).

## 2. 구현 (`helper/egdesk-briefing-flow.mjs` 신규, 핸들러에 판정 경로 2개)
(a) **말풍선 vs 보드**: `enumerateBriefingFacts`가 실제 후보(바인딩된 자료+열린 캔버스 뷰: id, ref, 종류, 라벨, 요약, `onBoard`, `maySend`, rect)에서 사실을 만든다. 보고서가 라벨로 가리키는 target 수, 그중 보드 위에 실제로 있는 수, 길이·줄·목록·제목·표 행 수. **보내도 되는 카드만 후보**(아닌 카드는 개수에도 안 잡음). 보드 선택지는 가리킨 보드 항목이 2개 이상일 때만 존재한다(없으면 요청 자체를 안 보내고 말풍선). 있으면 choice `placement`(bubble/board, 막대 0.75·여유 0.2, 불확실하면 bubble). 요청에는 숫자 7개뿐이고 원문·라벨이 없다. 경로 `/decision/briefing-placement/*`.
(b) **설계 요청**: 주관 모델에 `{kind:'briefing_design', facts, targets:[{alias,kind,label,gist,referenced}](보드 위 항목만), limits, reply}`. `resolveDesign`이 별칭을 실제 ref로 풀고 기존 구조에 맞는지 검증: 단계 1–8, 설명 ≤240자, `fallback` 필수, 단계당 target 1–6개 중복 없음, 보드 위 target만, `emphasis`는 기존 값만, `validBriefing` 통과. 결과 `publishArgs`는 **기존 `egdesk_publish_briefing_multi` 입력 스키마에 그대로 맞는다**(시험이 도구 스키마 대조). 발행은 호스트가 기존 도구로 한다(이 모듈은 쓰지 않음).
(c) **단계별 흐름 점검**(`/decision/briefing-check/*`): 런타임이 설계에서 항목을 열거한다. 단계마다 `step_unclear`, `explanation_mismatch`(target 요약이 있을 때), 전역 `uncovered_target`(보고서가 가리킨 보드 항목이 어느 단계에도 없음), `step_order`(관계의 앞뒤와 단계 순서 불일치), 단계별 `targets_far`(한 시야에서 함께 읽을 수 없음: 뷰 대비 축소율 < 0.5), `targets_overlap`. 기하 항목은 c5 점검의 같은 규칙을 단계 target에 적용한 것이다(배치는 항목 중 하나일 뿐). 한 요청: predicate `understandable`, 항목별 predicate `issue_<항목>_<S#>`, choice `where`(단계·target 별칭 + none). 판정 규칙은 c5와 같다(문제 있음 ≤0.3 그리고 적용 항목 ≥0.7이면 findings, 이해됨 ≥0.8이고 적용 항목 없으면 ok, 나머지 inconclusive, 쓸 수 없는 답은 manual).
(d) **제한된 재설계 루프** `runBriefingFlow`: 최대 재설계 2회(설계 1+재설계 ≤2, 판정 요청은 placement 1 + check ≤3). findings → `briefing_redesign`(항목명, 범위 S#, 별칭, 확률, where, 직전 설계, 남은 횟수), inconclusive → `briefing_redesign_inconclusive`(더 구체적으로 하라는 고정 안내), 해석 불가 설계 → `invalid` 사유로 재요청. 통과하면 `presented`(publishArgs), 한도 안에 못 통과하면 `fallback-chat`(사유: check-not-passed / check-inconclusive / design-invalid / judge-unavailable), 말풍선이면 `bubble`. off=판정 요청 없음(말풍선), advisory=placement 1회 기록만(`advisory-only`, 설계 시작 안 함), on=전체 흐름. 인증·예산·4초 전경 마감·티켓·중단 시 추정 예산·응답 시점 재확인은 기존 Board 핸들러 경로를 그대로 쓴다.
- 핸들러: c5의 단일 'check' 배관을 `JUDGES` 테이블(캔버스 점검, 말풍선/보드, 브리핑 흐름)로 일반화했다(`egdesk-board-presentation-http.mjs` +23/-16). 기존 `/decision/canvas-check` 동작은 불변(기존 시험 통과).
- 보정 로그: 기존 API만. placement는 `choice`(top/second, 0.75/0.2), 흐름 점검은 c5와 같은 `goal_met`/`relevance`/`choice` 행. **누락 필드**: 로그의 `feature`가 닫힌 어휘(`board_arrangement` 등)라 배치 점검·말풍선 판정·브리핑 흐름 점검을 구분하는 필드가 없다(질문 행 모양으로만 구분 가능). 어휘 변경은 L7 소유라 하지 않았다.

## 3. 시뮬레이션 (`scripts/egdesk-briefing-flow.test.mjs`, 12 시험; 보드 사실은 support world의 실제 컨트롤러 기하에서)

- **B. 짧은 답**("Done. The total is 42." / 보드 항목 1개만 언급): 말풍선, **판정 요청 0건, 설계 요청 0건**. B2: 보드 항목을 여럿 가리켜도 판정이 bubble(0.92)이면 말풍선, 불확실(0.55)이면 말풍선, 설계 요청 없음.

## 4. 사용자 노출 문구 (승인 대기; 새 기능 이름 없음, Answer Briefing은 canon의 임시 정본명)
- 이번 변경이 **화면에 새로 그리는 문구는 없다.** 호스트 연결(아래 §5)이 없어 사용자 화면 경로는 아직 이 흐름을 부르지 않는다.
- 호스트가 `fallback-chat`일 때 말풍선 답변에 붙일 안내가 필요하다(미구현, 제안 문구 후보): `보드 브리핑을 만들지 못해 대화로 답합니다.` — 승인 전.
- 모델이 보는 문장(전송 전 검토 패킷에 보이는 모델 대면 문구, 사용자 카피 아님): placement/흐름 점검의 질문 지시문과 주관 모델 요청의 `reply`/`note` 문장(영어, 코드 내).

## 5. 열린 점·결정 요청
- **전송 동의 정책**: placement는 숫자만이라 mode on의 상시 동의(기존 turn-start 판정과 같은 패턴)로 충분해 보이나, 흐름 점검은 **단계 설명·target 라벨·요약이 외부로 나간다**. 상시 동의로 둘지, 실행마다 패킷 검토를 요구할지는 사용자 결정이 필요하다. 코드는 `allow(kind, preview)` 콜백으로 둘 다 지원한다.
- **호스트 연결(미구현)**: 최종 보고 시점에 후보 목록을 `egdesk_list_context`의 바인딩과 열린 캔버스 뷰에서 만드는 어댑터, 주관 모델(Codex/Claude) 호출 경로, 통과한 `publishArgs`를 기존 `egdesk_publish_briefing_multi`로 발행하는 연결, 실패 시 말풍선 안내 표시.
- 보정 로그 어휘: `feature`가 닫혀 있어 새 판정 종류 구분 불가, `outcome.next` 라벨 배선(L7 반영 후).
- c5의 캔버스 배치 점검(`/decision/canvas-check`)은 별도로 남는다(배치는 이 흐름에서는 항목의 하나로 재사용). 기존 4개 프리셋 경로 결정은 c5 보고서의 사용자 결정 요청 그대로다.
- 한계: target 요약(gist)·라벨 일치 판정은 호스트가 준 짧은 요약에 의존한다. 한국어 정확도는 이 프로젝트에서 실증하지 않았다(JEV 문서 §9.2).

## 7. 철학 점검
Decision은 시스템이 열거한 옵션(숫자, 단계, target, 닫힌 문제 종류) 안에서만 판정하고, 설계는 주관 모델이, 최종 제시 여부는 규칙(통과/한도/모드)이 정한다. 통과하지 못하면 아무것도 새로 띄우지 않고 기존 대화 답변이 그대로 남으며, 모든 외부 전송은 닫힌 DTO와 예산·마감·모드 재확인을 거친다.
