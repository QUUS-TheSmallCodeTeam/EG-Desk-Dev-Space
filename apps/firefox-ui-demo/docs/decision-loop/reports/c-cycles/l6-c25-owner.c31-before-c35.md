# 지금 무엇을 켤 수 있고, 얼마나 빨라지고, 무엇이 모자란가 (owner 용 한 장, L6 c31 갱신판 — 층 기준)

**방향** (U13 + 정정): 결정 모델은 대화 아래의 정의된 층(**기억**, **행동**)을 먼저 확정하고, 대화는 그 위에 얹힌다. 그래서 아래는 기억 → 행동 → 대화 순서다. 모든 플래그는 지금 꺼져 있고 켤지는 당신이 정합니다.
**읽는 법**: 초 = 오늘 실제 엔진 기록(메시지부터 엔진 턴 끝까지). 비용 = 결정 모델 입력 토큰(턴당). "맞음" = 그 실행의 코드 기대 통과. 대화 3~16개짜리 측정이라 비율이 아니라 "있었다/없었다"로 읽으세요. 새 문구·요소는 전부 **승인 필요**, 제안만.

**한 줄 결론**: 켤 수 있음 **1개**(미리 읽기). 요소 하나 정하면 켤 수 있음 **1개**(명령 빠르게: 25.1→3.5초). 측정이 아직 없는 것 **2개**. 감시는 **고쳐야** 켤 수 있음(실제 180초 정지를 못 잡음). 초안 검사는 이번 재실행으로 "아무것도 안 남음"이 **7/12 → 1/12**.

## 기억 층
**M1. 읽을 파일을 미리 읽기 (`TURN_MEMORY_PREFETCH=files`) — 켤 수 있음**
- 사람이 느끼는 것: "예산이 얼마야?" 같은 폴더 질문에 엔진이 파일을 읽으러 다니는 시간이 사라집니다. 실측 3쌍: 16.7→7.8, 13.2→9.5, 11.7→6.9초 (평균 **−5.8초**), 엔진 도구 호출 1→0, 답은 둘 다 맞음.
- 비용: 턴당 결정 호출 +1(0.3~0.45초), +1.2k~1.4k 토큰. 위험: 고른 파일이 틀리면 엔진이 지금처럼 직접 읽는다(추가 손해는 결정 호출 0.4초). 결정 모델은 파일 **이름·크기·날짜**만 보고 내용은 엔진에게만 갑니다(결정 모델도 엔진과 같은 허용을 따른다는 규칙 안).
- 모자란 것: 큰 폴더·무관한 요청에서의 측정 한 번(지금은 합성 폴더 3개).

**M2. 기록을 엔진보다 먼저 확정 (`TURN_MEMORY_WRITE_FIRST`, c38) — 측정 없음**
- 사람이 느끼는 것: 엔진이 "확정됐군요"라고 말하는데 기록은 아직 확인 전인 어긋남이 사라집니다. 오늘 기록(check-27mw): 기억 층 자체는 맞았습니다(확인 전 → 사람이 "응 맞아" → 기록 `확정`). 어긋남은 한 번 보였습니다(own-confirm 2번째 턴).
- 비용: 같은 판단을 앞당길 뿐 호출 수 변화 없음(대기 최대 2.5초). 모자란 것: **실엔진 실행 0회.**

## 행동 층
**A1. 명령을 결정 모델이 고르고 코드가 실행 (`DECISION_FIRST`, c32) — 요소 하나만 정하면 켤 수 있음**
- 사람이 느끼는 것: "테스트 돌려줘"에 엔진이 폴더를 둘러보다 4번 도구를 쓰던 것(**24.3초**)이, 결정 모델이 `npm test`를 고르고 EG-Desk 가 바로 돌리는 것(**3.0초**, 엔진 턴 0)으로 바뀝니다. 실패하는 프로젝트는 결과를 엔진에게 주고 설명만 시킵니다(10.9초, 답 "5개 중 4개 통과, 1개 실패").
- 비용: 요청당 결정 호출 1(0.33~0.41초, 0.2k 토큰). 위험: 낮음(안전한 스크립트 이름만 후보, 승인·위험 규칙 그대로, 3/3 기대 통과, 바깥 파일 안 건드림).
- 모자란 것: **새 요소 승인.** 성공하면 엔진의 말이 없어 터미널 카드만 남습니다("끝났는데 말이 없다"로 보일 수 있음). 제안: 터미널 카드 아래 한 줄 요약 칩("성공 · 5/5"), 설정 토글(이름·설명, 폴더에서 만든 고정 설명이 결정 모델로 간다는 안내 포함). 빌드·git 상태·"실행하지 마" 같은 거절 사례의 실측도 아직 없음.

**A2. 열린 항목·승인을 빠르게 (L1 c32) — 측정 없음**
- 사람이 느끼는 것: "그냥 해" / "아니 잠깐"을 엔진이 새로 해석하는 시간이 줄어듭니다. 지금(check-27aw): 승인 질문 9.8~11.4초, "그냥 해" 8.5초, "아니 잠깐" 3.3초.
- 모자란 것: **실행 0회**(필요한 점검 스크립트가 아직 통합본에 없어 오늘 시작되지 않음). 새 문구는 없다는 것이 L1 보고.

**A3. 엔진이 멈췄을 때 감시 (`ENGINE_STALL_FIRST_EVENT_MS`, c33) — 지금 켜도 효과 없음, 고쳐야 함**
- 오늘 사실: 주 대화 168턴 중 **4턴이 180초 정지**(2.4%, 턴당 평균 약 4.3초). 4건 모두 엔진이 사용자 메시지만 받아 적고 그 뒤 아무 진행이 없었습니다. 감시를 45초로 켠 실행(check-29st)에서도 정지가 났는데 **감시가 못 잡았습니다**: 사용자 메시지 이벤트가 2ms 에 와서 "정상"으로 봤기 때문입니다.
- 고치는 법(내부 규칙, 새 문구 없음): "첫 이벤트"가 아니라 **첫 진행**(사용자 메시지 뒤의 추론·답·도구)을 기다리게. 값은 정상 턴의 첫 진행 시간을 먼저 재야 합니다(지금 기록에 없음).
- 내부 고쳐 쓰기용 fork 에는 이미 비슷한 안전장치(11초 뒤 새 스레드에서 같이 시작)를 넣었고 효과가 보였습니다(아래 C1).

**A4. 브라우저 루프 (`BROWSER_ENTRY` 계열) — 켜기 직전**

## 대화 층
**C1. 초안 검사 + 고쳐 쓰기 (`DRAFT_CHECK`) — 아무것도 안 남는 문제가 크게 줄었으나 결정은 당신 몫(P1)**
- 사람이 느끼는 것: 기록과 어긋나는 문장("아직 안 했는데 배포 완료")을 올리기 전에 고칩니다. 심은 거짓 12개를 **12/12 찾았고**, 맞는 문장은 한 번도 안 건드렸습니다(0/4). 거짓은 사람에게 **0/12** 도달.
- 이번 재실행(고친 뒤): 고쳐 쓴 문장이 게시된 것 **5/12 → 10/12**, **아무것도 안 남은 것 7/12 → 1/12**. 이전에 침묵하던 원인은 "고쳐 쓰기를 못 해서"가 아니라 엔진이 가끔 응답을 안 해서(7건 모두 25초 마감)였고, 11초 뒤 새 스레드로 같이 시작하게 하니 정지한 6건 중 5건이 19.7~24.0초에 올바른 문장으로 구해졌습니다(정상 fork 는 6.1~7.1초에 끝남; 나머지 1건은 새 스레드가 느려서 마감 0.2초 전에 끊김).
- 남은 결정: 그래도 아무것도 안 남을 때(1/12) **침묵(A)인가, 글 없는 표시(D)인가.** 새 문구 없음. 모자란 것: 새 입력(다른 말투·페이지)에서의 확인, 정지 에피소드(약 4분간 6/6)가 길면 구하기에 여유가 얇음(가장 느린 구해진 건 24.0초/25초 마감: hedge 를 9초로 당기는 내부 값 조정 제안).

**C2. 안내 문장 (`CONVERSATION_FLOW`)**: 변동 없음. 고정 문장 승인(P2) 대기. **C3. `WORK_PLACEMENT`, `PRESENCE`**: 변동 없음, 켜도 됨.
