# L8 / C11 브라우저 `on` 경로: 완성 메시지 왕복, 진행 사실, 진입 결정 비용, 안전 재확인

브랜치 `lane/c11-browser-on-e2e` (base int/c10 f57b0cd), 커밋 `409eca0`. 합성 검증만(실제 `CodexChatRuntime.send` + 실제 provider/Browser service/reflex + 채팅 저장소, UI 대역, mock Decisions fetch, 각본으로 움직이는 주관 엔진). 실제 Firefox·네트워크·codex 없음. 어떤 flag도 켜지 않았다(모두 기본 off).

## 1. 객관 루프 <-> 챗 왕복 (완성 메시지만)
### 발견한 문제
`on` 경로의 턴은 제한된(bounded) 브라우저 턴이고, L3의 보류(held) 답변은 `!bounded` 턴에만 적용된다(`codex-chat-runtime.mjs` `context.draftHold = !bounded && …`). 그래서 D1 모드(draftCheck `on`)를 켜도 **브라우저 작업의 질문/최종 보고는 스트리밍으로 나갔다**(R3 대조: 턴이 끝나기 전에 조각이 보임).

### 수정 (두 번째 장치를 만들지 않음)
- `runBrowserEntryOn`이 닫힌 노트를 돌려준 턴에 한해, L3의 보류 가드를 그대로 켠다(`context.draftHold = pending.draftHold = true`). 조건은 L3와 같은 flag(`draftCheck.mode() === 'on'`, 결정 모델 사용 가능). 같은 가드·같은 정산 지점(`settleDraftAnswer`)·같은 게시(`applyItem`)를 쓴다.
- 초안 검사 자체는 제한된 턴에 대해 L3 규칙대로 부적격(`ineligible`)이므로, 주관 모델이 쓴 문장이 **수정 없이 한 번에** 게시된다.
- 브라우저 작업 턴에는 중간 메시지 작업(conversation flow)을 시작하지 않는다(`startConversationFlow`에 조건 1개). 이유: 그 턴은 노트를 문장으로 옮길 뿐이고, 중간 질문에 대한 답이 턴 안으로 steer되면(`answerEarlyQuestion`) 일시정지된 브라우저 작업이 재개되지 않는다.

### 내부 턴(private fork) 작성 경로를 쓰지 않은 이유
객관 루프는 네이티브 턴이 생기기 **전에** 돈다(c9). 그 시점에는 메시지를 붙일 run이 없고, 질문을 쓰는 주체가 곧 그 턴의 주관 모델이다. 그래서 "턴의 최종 답 = 질문/보고"를 L3의 보류 경로로 완성 메시지 한 건으로 만드는 것이 기존 장치만 쓰는 방법이다. 질문 때마다 턴이 끝나므로 이 경로는 L2의 composer 잠금 해제에 의존하지 않는다.

### 검증 (codex-chat-browser-task-roundtrip.test.mjs R1~R4, 채팅 저장소의 기록 순서)
| 케이스 | 결과 |
|---|---|
| R1 need-context | 기록 순서: user(요청) -> assistant(질문) -> user("두 번째 사업자로") -> assistant(최종 보고). 턴이 끝나기 전 assistant 이벤트 0건, delta는 메시지당 1건(전체 문장), 완성 메시지 2건. 답은 같은 작업을 재개(같은 task id). 답 전 동작 0, 이후 navigate 2. Decisions: 진입 1, 단계 4, 재개 판단 1, 이미지 0. 각 객관 구간이 그 턴의 `turn/start`보다 먼저 끝남. fork·steer 호출 0 |
| R2 cannot-proceed (2FA) | 완성 메시지 1건으로 사람에게 요청 -> "했어" -> 같은 작업 재개 -> 완성 보고 1건. 사람 조치 전 동작 0 |
| R3 대조(보류 모드 off) | 같은 턴이 조각으로 스트리밍됨 |
| R4 보류 모드 on, 브라우저 작업 아님 | 변경 없음: 일반 제한된 턴은 여전히 스트리밍(L3의 기존 규칙) |

### 남은 한계
- **턴 전 구간에는 run이 없다.** 객관 루프가 도는 동안 `send`가 아직 반환되지 않아 run 기반 작업 표시가 없다. 호출 수로 본 추정 대기(요청당 0.25~0.45 s 가정): 첫 턴 2건 ≈ 0.5~0.9 s, 재개 턴 4건 ≈ 1.0~1.8 s + 페이지 로드. 실측 아님. heartbeat가 이 구간을 덮으려면 run 이전에 시작해야 한다(아래 사실 API는 `clientThreadId` 기준이라 가능).
- 브라우저 작업이 아닌 제한된 턴은 D1 아래서도 스트리밍된다(L3의 `!bounded` 규칙, 이 사이클 범위 밖).
- 질문을 쓰는 턴의 주관 모델은 여전히 브라우저 도구를 갖고 있어 묻는 대신 직접 조작할 수 있다(모델 행동, mock으로 검증 불가; 전역 게이트 정책은 Owner 결정 그대로).
- 질문 문장은 초안 검사를 거치지 않는다(제한된 턴 부적격).

## 2. heartbeat용 읽기 전용 진행 사실
- `chat.browserTaskFacts(clientThreadId)` -> `null | { taskId, status, active, phase: 'objective_step'|'waiting_user'|null, stepsDone, stepsRemaining, waitingOnUser, waitingKind, waitingCode, actions:{fill,navigate,scroll}, lastActionAgeMs, ageMs, idleMs }` (동결 객체, 숫자와 닫힌 단어만; 목표·라벨·호스트·URL 없음). `active/phase/waitingOnUser/stepsDone/stepsRemaining`은 L3 heartbeat의 사실 이름과 맞췄다.
- 루프 중에도 갱신: `runBrowserReflex({ onStep })` 관찰자(읽기 전용, 던져도 무시) -> `store.progress`. 관찰자가 있든 없든 결과와 도구 호출이 같음을 테스트로 확인. beat는 구현하지 않았다.
- L3의 작업 중인 provider(`observeBrowserTaskStore`, 미커밋, 읽기만 함)는 내 저장소를 감싸며 `progress`/`facts`가 없지만 선택 호출이라 깨지지 않는다(그 경우 구간 단위로만 갱신).
- R1 측정: 대기 중 `paused/waiting_user/need_context/choice_needed, stepsDone 1`, 루프 중 `running/objective_step`이며 stepsDone 증가, 완료 후 `done, stepsDone 4, navigate 2`.

## 3. 비용: 진입 결정을 턴 시작 triage 요청에 얹기
- 구현(기본 없음): `triageTurn({ extraQuestions })`(L7 파일, 추가만; triage 질문 뒤에 붙고 `tn_` 이름 불가, 답은 `extra`로 그대로 반환), `entry.handle({ entryAnswers })`, 런타임 훅 `browserEntry.entryAnswers({ body, context, question, client })`. 답이 쓸 수 없으면 단독 요청으로 돌아가고, 불확실한 답은 작업을 시작하지 않는다(C4).
- triage 답 불변(C3, mock 판정자): 세 메시지에서 courtesy/need/record/recall 판독 동일, evidence 바이트 동일, triage 질문 순서·문구 동일. **실제 모델에서 질문 간 독립성은 검증하지 못했다.**
- 하네스 측정(와이어 바이트): 단독 진입 요청 913 B, triage 1379 B, triage+진입 1904 B -> 얹는 추가분 525 B, 순 절감 388 B와 왕복 1회.
- 실제 수치로 환산(추정, 약 4 B/토큰): 얹는 추가분 ≈ 130 토큰(1.3~1.6k 토큰 triage 요청 대비 +8~10%), 단독 요청 ≈ 230 토큰 -> **요청 1건, 왕복 0.25~0.45 s, 약 100 토큰 절감**. 토큰은 추정이고 provider 실측이 아니다.
- 추가 효과(C2): 얹은 답이 "브라우저 작업 아님"이면 기억 fetch를 통째로 건너뛴다(얹지 않으면 fetch가 먼저 실행됨, c10 측정 2건).
- **지금 배선에서는 이득이 없다.** 제한된 브라우저 턴에는 턴 시작 triage가 없다(L7의 turn memory는 `!bounded` 턴에서, dispatch 뒤 advisory로만 돈다). triage를 얹기 위해서만 보내면 오히려 손해(1904 B 대 913 B). 그래서 브리지에는 훅을 연결하지 않았다. L7이 제한된 턴의 시작 시점에 triage를 돌리게 되면 훅 한 줄로 켤 수 있다.
- 얹는 경우 진입 결정은 기억 packet을 보지 못한다(c8 설계와의 차이, 객관 루프는 여전히 packet을 받음).

- c4 측정 스크립트를 int/c10 코드로 재실행(`measure-int-c10.json`): href 놓침 0/50, 라벨 놓침 0/36, 라벨 거짓 제외 0/31, href 거짓 제외 13/50(c4와 동일).
- 새 케이스:
  - provider 경로(매트릭스): 세션 종료·계정 폐쇄·주문·권한 허용·계약 해지 어휘 20개(라벨 12, 무해한 라벨 뒤 위험 경로 8) -> 후보 0, 확신도 0.99로 골라도 요청 0. 같은 페이지의 일반 링크는 정상 이동(대조).
  - 런타임 `on` 경로(S1): 위험 요소만 있는 페이지에서 8가지 선택 모두 동작 0, 노트는 `cannot_proceed`(`blocked`이면 `human_step`), 노트에 해당 라벨 없음.
  - S2: 제출 버튼·구독 해지 링크 요청 0, fill 0(직접 진입은 값을 공급하지 않으므로 입력 자체가 없음; "값은 소속 페이지에서만"은 reflex 도구 경로의 journey 테스트가 계속 확인).
  - S3: 런타임을 통한 페이지 변경 override: 기억이 가리킨 선택이 없으면 모델이 `[L1]`을 0.95로 골라도 동작 0으로 질문, 그대로 있으면 질문 없이 완료.
- egress(D2): 훅에 넘기는 클라이언트를 run의 권한으로 감쌌다(진입 질문 = `page_text`, 기억 fetch = `memory_page`, 결과 기록은 `browser_task_record`+`memory_page` 확인). 별도 동의 없음, 새 Decisions 호출 지점 없음(등록 테스트 통과).

## 7. 철학 점검
확률은 실행 권한이 아니다: 위험 어휘·제출은 후보가 되지 않고, 기억이 가리킨 선택이 사라지면 확신도와 무관하게 사람에게 묻는다. 결정 모델은 사용자에게 말하지 않는다: 사용자에게 가는 문장은 주관 모델이 닫힌 노트로 쓴 완성 메시지뿐이다.
