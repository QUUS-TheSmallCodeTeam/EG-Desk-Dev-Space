## 2. 문제 (패치 전, COLD=1800 기준; 다른 COLD 값은 증거 파일)
| 단계 | 결과 | 경과 | 사용자가 보는 것 | 서버 수신 |
|---|---|---|---|---|
| a | `manual` | 1502 ms | 수동 안내(오류성 화면) | 1 |
| c | `manual` | 1500 ms | 수동 안내 | 1 (또 cold) |
| c2 | `manual` | 1500 ms | 수동 안내 | 1 (cold) |
| b | `manual` | 1501 ms | 수동 안내 | 1 (cold) |
| d1 | `fallback:timeout` | 800 ms | 조용한 폴백 | 1 (client_aborted) |
| d2 | `fallback:timeout` | 801 ms | 조용한 폴백 | 1 (cold, aborted) |
| d3 | `ready` | 303 ms | 컨텍스트 사용 | 재사용 소켓 |

| f | `verified` | 1803 ms | 확인됨 (5 s 한도) | 1 |

관찰:
1. **자기 강화 실패 루프.** 시작 후 첫 호출이 cold ≥ ~1.5 s이면 1.5 s 데드라인이 요청을 abort하고 소켓도 파괴한다. 따라서 그 뒤 후속 호출(1.5 s 뒤, +1 s 뒤)도 계속 cold가 되어 계속 timeout이다. COLD=1800과 2229에서는 4번 연속 4/4 `manual`. 사용자가 실제로 "warm 230–600 ms"를 보는 경우는 데드라인 안에 cold가 끝날 때(COLD=1409에서만 a가 1419 ms로 81 ms 차이 통과)뿐이다. 관련 코드: `egdesk-chat-choice.mjs:83`(데드라인), `codex-chat-runtime.mjs:4310-4312`(`min(DEFAULT, choiceBudgetMs)`), `egdesk-decision-client.mjs:38`·`:287`(기본 1500, Board 경로는 timeoutMs를 안 넘겨 이 기본값을 그대로 사용 — `egdesk-board-presentation-http.mjs:132`).
2. 1500 ms는 "응답 대기"가 아니라 "연결 수립 + 추론 + 본문"을 모두 덮는데, 기록된 cold 호출 1.4–2.2 s는 이를 넘는다. 이 값은 git 이력이 한 개의 스쿼시 커밋(`30cf73b`)뿐이라 선택 근거를 이력에서 찾지 못했다(`git log -S` 확인). `docs/DECISION_MODEL_CONTEXT_SETUP.md:96`은 800 ms를 "대기 한도이지 공급자 평균 속도가 아니다"라고 명시한다.
3. 키 확인(f)은 이미 5000 ms(`egdesk-decision-client.mjs` verifyKey `options.timeoutMs ?? 5000`)라 cold 2.2 s를 통과한다. 변경 불필요.
4. 부수 관찰(원인 미규명): abort 뒤 모의 서버에 요청 없이 TCP 연결이 하나 더 열려 있었다(`conns`가 호출당 2씩 증가: 1→2→4→6→8). undici가 abort 뒤 재연결하는 동작으로 보이나 확인하지 못했다. 실제 TLS에서의 영향은 실제 앱 필요.
5. 중복 전송 없음: 모든 호출에서 서버 수신 요청은 호출당 정확히 1건.
6. 키 확인을 제외한 cold 호출은 5 s 유휴(undici 기본 `keepAliveTimeout` 4 s) 이후 항상 cold로 돌아간다: 패치 후에도 c2/b는 cold 시간 그대로 걸린다.

## 3. 개선 근거
- NN/g 응답 시간 한도 (https://www.nngroup.com/articles/response-times-3-important-limits/): 1 s는 흐름 유지, 10 s는 주의 유지 한계이고 1 s 초과 시 작업 중임을 알려야 한다. 사용자가 직접 확인 버튼을 누르고 기다리는 경로는 1–10 s 사이에서 진행 표시가 있으면 허용된다. DM 패널은 이미 `pending` 상태 "추천을 기다리는 중…"(`overlay/JS/eg-desk-surface.uc.js:12915-12916`)을 보여 주므로 UI 변경 없이 4 s까지 늘릴 수 있다. → **4 s 결정에 이 출처가 영향.** (cold 최대 2.23 s의 약 1.8배, 10 s의 절반 미만.)
- 반대로 턴 시작 컨텍스트는 사용자가 기다리는 요청이 아니라 턴 지연을 키운다(NN/g 1 s 한도). 800 ms 유지(`DECISION_MODEL_CONTEXT_SETUP.md:96`, §1 폴백). → **800 ms는 변경하지 않음.**
- undici Client 문서 (https://raw.githubusercontent.com/nodejs/undici/main/docs/docs/api/Client.md): `keepAliveTimeout` 기본 4 s, 서버 힌트로만 늘어나며(`keepAliveTimeoutThreshold` 2 s 차감) 최대 600 s. Agent 문서(…/Agent.md)는 기본 dispatcher가 origin별 Pool을 재사용한다고 한다. Node http Agent 문서(https://nodejs.org/api/http.html)는 서버가 유휴 연결을 닫을 수 있으며 그 경우 새 연결을 만든다고 한다. → 전용 dispatcher로 keepAlive를 늘리는 이득은 4 s 창 → 서버 한도 사이에 한정되고, 서버 한도는 알 수 없다. 오래된 소켓 재사용 경쟁(재전송 금지 규칙과 충돌, 실패 시 `unreachable`)의 위험이 있다. 또 이 앱은 `undici`를 의존성에 두지 않아(`package.json` 의존성 확인) dispatcher를 만들려면 새 의존성이나 `node:https` 어댑터가 필요하다. → **전용 dispatcher는 이번 패치에서 제외, 제안으로 둠.**
- 캐논: `DECISION_MODEL_CONTEXT_SETUP.md` §1 "결정 호출이 실패하면 지금 방식으로 돌아간다" 유지. 실패 시 manual/fallback 동작과 `off` = 0 호출은 불변.
- 데드라인 의미 정리:
  - 사용자 명시 대기(chooser, Board 사진 적용): **연결 수립 포함 4000 ms**. fetch API는 연결 단계와 응답 단계를 분리해 주지 않아 분리 데드라인은 불가하고, 연결을 포함해 넉넉히 두는 것이 abort-and-cold 루프를 끊는다.
  - 키 확인: 5000 ms 유지(이미 연결 포함).
  - 턴 시작 컨텍스트: 800 ms, 연결 포함, 초과 시 조용한 폴백(현행).

## 6. 철학 점검
원칙: **"결정 호출이 실패하면 지금 방식으로 돌아간다"**와 **모델 제안 ≠ 승인된 실행**. 변경은 사용자가 확인 버튼으로 이미 승인한 요청의 대기 시간만 늘리며, 새 호출·재시도·아웃바운드를 추가하지 않는다. 실패·초과 시 여전히 manual/fallback으로 돌아가고 추천은 "실행하지 않음"으로만 표시된다. 턴 시작 컨텍스트(대기하지 않는 설정)는 800 ms를 유지해 턴 지연을 키우지 않는다. 사용자는 4 s 동안 "추천을 기다리는 중…"을 보므로 화면에서 발견·완료 가능하다.

## 7. 한계와 제안 (패치에 넣지 않음)
- **합성 관찰만.** 실제 cold 지연의 원인(TCP/TLS인지 서버 측 첫 호출 비용인지)은 하네스로 구분할 수 없다. 실제 앱·실제 네트워크 필요.
- **턴 컨텍스트 cold 루프(d1→d2)는 남아 있다.** 800 ms abort가 cold 소켓을 파괴하므로 사용자가 이전에 명시 호출을 한 적이 없으면 컨텍스트 결정은 계속 폴백한다. 제안 A: 예산 만료 시 호출자는 폴백으로 진행하되 이미 전송된 요청의 전송 계층만 짧은 유예(예: 2.5 s) 동안 유지해 소켓을 데움(결과는 버림, 사용량은 기록). 새 연결이 아니라 이미 동의된 동일 요청이지만, 턴 취소 시 즉시 abort 해야 하고 `prepareTurnContext` 신호 구조를 건드리므로 별도 레인에서 설계 필요. 제안 B: 시작 시 pre-connect/keep-alive 핑은 **사용자 동의 없는 아웃바운드**라 규칙상 제안만 한다(동의 UI 필요).
- 전용 keep-alive dispatcher: `undici` 의존성 추가 또는 `node:https` 어댑터가 필요하고 이득 구간이 4 s → 미상(서버 한도)이라 실측 후 결정.
