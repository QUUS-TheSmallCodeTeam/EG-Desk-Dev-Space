# L6 / C7: 작업 기억 게이트를 int/c12 위로 옮기고, 명령 출력 경로 확인, 만료 코드와 활동 기록 행 추가

브랜치 `lane/c7-memory-gate-on-c12` (base int/c12 2ad24e5). 커밋 3개: `d091b4e` (c6 abef52f를 옮김, 충돌 해소), `317762d` (만료 코드), `24b8061` (활동 기록 행 + 인계 도우미 + 시험). 증거: `evidence/l6-c7/` (`gate.out`, `simulation.json`, `handoff-compare.json`, `handoff-raw-*.txt`, `handoff-gate-*.txt`).

## 0. 결론
1. c6를 int/c12 위로 옮겼다. 충돌 2곳은 지시대로 해소: 보정 로그 어휘는 합집합(L3의 `questions` 필드 + 내 `wm` 묶음), 런타임은 양쪽 유지(L5의 명령 판정 메서드 + 내 게이트 메서드, import 둘 다).
2. **엔진 명령 출력은 EG-Desk를 거쳐 주관 모델에 가지 않는다** (L5 c8 이후에도). 그리고 EG-Desk가 통제하는 경로 중 **명령 출력을 모델에 싣는 것은 지금 하나도 없다.** 그래서 바꿔 끼울 인계 지점이 없다. 대신 나중에 인계가 실제로 연결될 때 쓸 도우미를 만들고, 지금 기록되는 "원시 블록" 방식과 수치로 비교했다.
3. 만료된 포인터에 닫힌 공개 코드 `SPILL_EXPIRED` + 고정 문장 추가.
4. 게이트가 실제로 결과를 바꾼 답변에는 활동 기록에 내용 없는 행 1개(건수만). 문구는 승인 대기.
5. 광범위 게이트: 292 파일, 6278 tests, 6235 pass, 33 skipped, **10 fail = int/c12의 알려진 10건과 정확히 동일** (L2 9건, L5 1건). 내 변경으로 생긴 실패 0.

## 1. 명령 출력 경로 확인
**엔진 명령 출력이 가는 곳 [코드]**
- 엔진이 자기 명령을 실행하면 브리지는 알림(`item/commandExecution/outputDelta`, `item/completed`)으로 출력을 받아 run별 메모리 저장소에 넣는다 (`codex-chat-runtime.mjs` `keepRunOutput` :5731, 저장소 `codex-run-outputs.mjs`: 명령당 앞 8 KiB + 뒤 64 KiB, run당 24개, 메모리 전용, 읽을 때 가림).
- 그 저장소를 읽는 곳은 정확히 두 군데다.
  1. 화면의 명령 출력 보기: `GET /chat/command-output` (`codex-bridge-http.mjs:188` -> `commandOutput` :5805). 사람에게만 간다.
  2. L5의 명령 상태 판정 (`egdesk-engine-command-watch.mjs`, `readOutput` 연결 `codex-chat-runtime.mjs:826`): 꼬리 일부가 **Decision 모델**로 간다(권한 종류 `command_output`). 결과는 기록뿐이다(`acted: false`, "Nothing is typed, interrupted, injected or shown").
- 주관 모델은 이 출력을 엔진 내부에서 직접 받는다. EG-Desk 코드는 그 전달에 끼지 않는다. c5의 지도와 같다.

**"오류 로그 블록 인계"는 어디까지 가나 [코드]**
| 위치 | 하는 일 | 주관 모델에 닿나 |
|---|---|---|
| 엔진 명령 판정 (`egdesk-engine-command-watch.mjs:132-138`) | 실패로 판정되면 런타임이 나눈 블록 중 무엇을 강조할지 고르고 **블록 번호만 기록** | 아니오 |

| 객관 루프 `runObjectiveLoop` (`egdesk-terminal-judge.mjs`) | 고른 블록 글을 `deps.subjective(...)`에 넘기도록 짜여 있음 | **연결되면 닿는다. 지금은 호출처가 없다** (`runTerminalLoopWithHeartbeat`도 시험에서만 호출) |
| 하트비트/대화 흐름 | 명령 사실을 숫자와 닫힌 라벨로만 전달 | 글은 가지 않음 |

[해석] 따라서 "그 인계를 내 장치로 바꾸라"의 조건(모델에 닿는 경로가 큰 명령 출력을 싣는가)은 지금 **거짓**이다. L5 파일은 건드리지 않았다.

**미리 준비한 것: `commandOutputHandoff` (`egdesk-working-memory-wiring.mjs`)**
수리 인계가 실제로 연결될 때 원시 블록 대신 쓸 함수다. 코드 규칙만 쓰고 Decision 호출이 없다. 앵커(명령 줄, 오류 줄과 앞뒤, 수정 경로, 요약)는 원문, 생략은 줄 범위가 적힌 고정 문구, 저장소가 실제로 있을 때만 다시 읽기 포인터.

지금 기록되는 원시 블록 방식(실패 표지 블록 + 마지막 블록, 블록당 700자, 최대 4개)과의 비교 [측정, 합성 출력]:
| 출력 | 원시 블록 | 게이트 인계 |
|---|---|---|
| 빌드 로그 300줄, 오류 1건 (4,767 토큰) | 103 토큰, 필수 줄 3/3, 무엇을 뺐는지 표시 없음 | 166 토큰, 3/3, 286줄 생략을 2개 범위로 명시 |

원시 블록은 이미 작게 묶여 있어 "큰 출력" 문제는 없다. 차이는 정확성 쪽이다: 멀리 떨어진 여러 실패에서 사유 줄을 놓칠 수 있고, 생략 사실이 드러나지 않는다. 연결 시점에 L5와 함께 교체를 권한다.

## 2. 결정 반영
**(a) 보통 run에 스필 읽기 도구를 주지 않음 [소유자 결정 사항으로 보고]**
코드 변경 없음. 지금 동작: 읽기 권한(자료 첨부 + 읽기 허용)이 있는 run에서만 스필 선택지가 존재하고, 없는 run에서는 검색 결과와 페이지 글은 그대로, 과정 출력만 포인터 없이 접힌다. 바꾸려면 새 스레드의 도구 목록에 읽기 도구를 넣는 결정이 필요하다(기존 스레드는 시작 때의 도구 목록이 고정).

**(b) 만료된 포인터의 공개 코드 `SPILL_EXPIRED` (커밋 317762d)**
- 그 run이 스스로 스필한 id가 보존 상한을 넘겨 사라졌을 때만 낸다. 브리지 재시작 뒤에도 같은 답이 나온다(복원 때 만료 id를 기억). 그 밖의 id는 예전처럼 `CONTEXT_FORBIDDEN`.
- 모델에게 가는 글은 고정 한 문장: "The spilled tool result this pointer names is no longer kept. Run the tool again if you still need those lines." 내부 오류 문구, 경로, 도구 이름, 내용은 실리지 않는다. 문맥 provider 밖에서는 이 코드가 나갈 수 없다(시험).
- 화면의 "자료 읽기 실패" 줄에는 코드만 간다.

**(c) 활동 기록의 내용 없는 행 (커밋 24b8061, 문구 승인 대기)**
- 플래그 on에서 게이트가 결과를 실제로 바꾼 답변에만, 답변당 1행. 같은 답변에서 또 바뀌면 같은 행의 숫자만 갱신한다. advisory는 아무것도 바꾸지 않으므로 행도 없다.
- 제안 문구: `도구 결과 정리 · 2건 · 1,912줄 생략 · 다시 읽기 가능 1건` (다시 읽기 가능 건이 없으면 마지막 부분 생략).
- 담는 값: 결과 건수, 생략 줄 수, 다시 읽기 가능 건수. 도구 이름, 줄 내용, 경로 없음(시험).
- 기존 호스트 행 종류(`decisionContext`)를 써서 다른 lane이 관리하는 "호스트 자체 행" 목록 5곳을 건드리지 않았다. 화면은 이 종류를 제목으로만 그린다(상세 필드를 읽는 코드 없음을 확인). 실제 화면에서 본 것은 아니다.
