브랜치 `lane/c5-working-memory-gate` (base int/c10 f57b0cd), 커밋 `9736f33`. 증거: `evidence/l6-c5/` (`simulate.mjs`, `simulation.json`, `simulation.out`, `before-*.txt` / `after-*.txt`, `gate.out`).

## 0. 결론 먼저
1. **지금 제품에서 큰 툴 출력은 EG-Desk 코드를 거치지 않는다.** 엔진 내장 셸, 엔진이 직접 붙는 MCP, 엔진 하위 Agent, Claude 내장 도구의 결과는 엔진 안에서 바로 모델 문맥으로 들어가고 브리지는 알림만 본다. EG-Desk가 실제로 통제하는 출력(Browser 도구, 문맥 읽기, 턴 전 문맥 패킷)은 이미 코드로 상한이 걸려 있다. 따라서 이 게이트는 **출력을 돌려주는 런타임(예: EG-Desk 터미널 도구, MCP 중계)이 먼저 있어야** 큰 효과가 난다. 사용자 원칙("선택지를 만드는 런타임부터")과 같은 결론이다.
2. 프로토타입 모듈과 시험은 만들었다 (연결하지 않음, 기본 꺼짐). 블록 분할, 앵커 규칙, 블록별 선택(전체 주입 / 고정 문구로 접기 / 스크래치로 내보내기 + 포인터), 고정 문구, 비공개 스필 저장소, 장기 세션용 블록 역할 분류.
3. 합성 시뮬레이션 [측정]: 반복적인 출력(빌드 로그, grep, 상품 목록 페이지)은 **코드 규칙만으로 94.7~99%** 줄고 앵커는 전부 남는다. Decision을 써도 같은 결과에 요청 비용만 더 든다. 반복이 없는 글(도움말 본문)은 규칙으로는 0%, 판단이 있어야만 줄일 수 있다 (모의 판정으로 80%).
4. 권장 기준: 추정 2,000 토큰 미만은 손대지 않는다. 그 이상에서 반복 출력은 코드 규칙만, 반복 없는 글만 Decision 호출. 근거는 4절.
5. 광범위 게이트: 275 파일, 6101 tests, 6068 pass, 33 skipped, **0 fail**.

## 2. 프로토타입 (`helper/egdesk-working-memory-gate.mjs`, 491줄, 시험 16개)
- **블록 분할 (코드만):** 빈 줄, grep 형식의 파일 바뀜, 실패 표지, 40줄 상한으로 자르고 12블록을 넘으면 이웃끼리 합친다. 모든 줄이 정확히 한 블록에 속한다.
- **앵커 (코드 규칙, 판정과 무관하게 원문 유지):** 첫 줄, 마지막 3줄(요약/종료 줄), 최종 수정 경로가 든 줄, 목표에서 패턴으로 뽑은 식별자(파일 경로, camelCase, snake_case, 따옴표 구간)가 든 줄, 오류 줄과 앞뒤 1줄("0 errors"는 제외), 반복 출력 속의 드문 모양 줄(숫자를 지운 모양이 2번 이하인 줄).
- **런타임 선택지:** 4줄 이하이거나 절반 이상이 앵커인 블록은 "전체 주입"만 가능(질문 안 함). 나머지는 주입 / 접기, 스필 저장소가 있을 때만 스필 추가.
- **Decision 요청:** 출력 하나당 요청 1번, 열린 블록마다 choice 1개. 선택지 설명은 입력에 한 번만 싣는다(문항마다 반복하면 요청이 커짐). 블록 미리보기는 위치로만 고른 개요(첫 2줄, 뒤 문단들의 첫 줄 3개, 마지막 줄)이고 비밀값은 가린다.
- **송신 권한:** 공용 게이트를 그대로 따른다. build/terminal/search는 `terminal_output`, page는 `page_text`. 허용되지 않으면 키 조회 전에 요청 0건. 하위 Agent 출력과 일반 도구 출력은 맞는 권한 종류가 없어 **보내지 않는다** (결정 필요 항목 참조). `EGRESS_SITES`에 등록함.
- **고정 문구:** `[System: 320 lines of build log omitted (lines 5-324). Exit code: 0.]`, 스필은 `... spilled (lines a-b). Re-read: egdesk_read_source {"snapshotId":"<id>","intent":"re-read spilled tool output","range":{"startLine":a,"endLine":b}}]`. 숫자는 런타임 값, 낱말은 닫힌 목록. 원안의 "Output verified"는 런타임이 보증할 수 없는 말이라 넣지 않았다.
- **스필 저장소:** 지정한 비공개 디렉터리 0700, 파일 0600, 한 번만 쓰기, 무작위 UUID, 읽을 때마다 SHA-256 검사, 개수/총량/파일 크기 상한(기본 32개, 16 MiB, 4 MiB)에서 오래된 것부터 삭제, 심볼릭 링크와 경로 탈출 거부. 읽기는 기존 읽기 도구와 같은 줄 범위(최대 500줄).
- **모드:** off = 그대로, 요청 0. advisory = 묻고 기록만(보정 로그에 `working_memory` 항목, 내용 없음). on = `enabled` 플래그가 켜져 있을 때만 적용, 기본 꺼짐. 실패, 시간 초과, 낮은 확신은 지금 방식(전체 주입).
- **결과 검사:** 적용 후 모든 앵커 줄이 순서대로 남아 있는지 코드로 확인하고, 아니거나 10% 미만 절감이면 원문을 그대로 돌려준다. 실패한 도구 결과, 여러 항목 결과, JSON 결과는 손대지 않는다(JSON은 호출자가 글 배열 하나를 지정했을 때 그 배열만).
- **장기 세션 변형:** 첫 사용자 메시지는 `user_goal`, 최신 턴은 `current_active_task`로 런타임이 고정. 나머지만 5개 역할 중 블록별로 허용된 것에서 고르게 한다(정상 종료 출력은 "해결된 오류"가 될 수 없음). 접기는 `stale_intermediate_log`와 `error_trace_resolved`만, 사용자 글은 절대 접지 않고, 해결된 오류는 첫 오류 줄을 원문으로 남긴다. 이력 글은 `topic_history` 권한을 따른다.
- 공유 파일 수정: `egdesk-decision-calibration-log.mjs` 허용 목록에 feature 1개, 질문 2개, 값 8개 추가(+5/-3줄), `egdesk-decision-egress.mjs` 등록 2줄.

- 다시 읽기: 결과에 적힌 포인터 전부(2 + 6 + 2 + 3 = 13개)를 **적힌 그대로** 읽어 원문 줄과 일치함을 확인. 같은 글을 실제 `ImmutableContextStore`에 넣고 `inspect`의 줄 범위(241-280)로 읽어도 일치 (단, 툴 출력용 캡처 종류가 없어 board 선택으로 대신 넣은 시험용 확인이다).

시뮬레이션이 잡아낸 설계 결함 3건 (모두 수정, 시험 추가):
1. 500줄 넘는 스필 구간의 포인터는 읽기 도구의 범위 한도에 걸려 그대로는 못 읽었다 -> 포인터를 400줄 단위로 끊음.
2. 블록 미리보기가 첫 2줄과 끝 1줄뿐이라 합쳐진 블록 안쪽의 소제목이 보이지 않았다 -> 문단 첫 줄 개요를 추가.
3. 반복 목록 한가운데의 중요한 줄(환불 기한 2줄)이 미리보기에 안 보여 접힐 뻔했다 -> 드문 모양 줄을 앵커 규칙으로 추가.
남은 한계: 반복 없는 글에서 문단 **중간**에만 있는 중요한 문장은 판정자가 볼 수 없다. 그래서 내용 종류(검색 결과, 페이지 글)는 "접기"가 아니라 항상 "스필"로 두어 한 번 더 읽으면 복구되게 했다.

## 4. 어디서 쓸 만한가 (실측 지연: 따뜻할 때 0.25~0.6초, 긴 유휴 뒤 1.3~1.6초)

[해석]
- **반복 출력은 크기와 무관하게 코드 규칙으로 충분.** 판정이 더해 주는 절감은 약 90 토큰인데 요청은 600~1,500 토큰과 0.25~0.6초를 쓴다.
- **2,000 토큰 미만은 건드리지 않는다.** 이 구간에서는 최선의 경우에도 절감이 요청의 2배를 못 넘고, 툴 결과 전달이 0.25~0.6초 늦어진다.
- **Decision이 값을 하는 곳은 반복 없는 큰 글뿐.** 약 2,750 토큰(80줄)부터 절감이 요청의 3배 이상이다. 줄어든 글은 같은 턴의 이후 모델 단계마다 다시 읽히지 않으므로 단계가 많을수록 이득이 커진다.
- 긴 유휴 뒤 1.3~1.6초는 게이트 마감 1,500 ms에 걸릴 수 있다. 그 경우 그 출력은 그대로 주입된다(안전한 쪽). 툴 호출은 턴 중에 몰려 오므로 보통은 따뜻한 연결이다.
- 측정하지 못한 것: 두 모델의 토큰 단가 비율, 주관 모델이 입력 토큰당 얼마나 느려지는지, 잘못 스필했을 때 다시 읽는 한 단계의 실제 시간. 위 기준은 토큰 수와 Decision 지연만으로 세운 것이다.

## 6. 사용자/Main 결정이 필요한 것
1. **무엇을 먼저 만들 것인가.** 게이트의 실제 대상이 되려면 큰 출력이 EG-Desk를 거쳐야 한다. 후보: (a) 이미 있는 터미널 판정 루프(`runObjectiveLoop`)를 런타임에 연결하고 그 출력에 게이트 적용, (b) Claude용 MCP의 10,000 토큰 초과 오류를 "스필 + 포인터"로 바꾸기(가장 작은 실사용 지점), (c) `dispatchToolProvider`에 연결(지금은 Browser observe 글 60조각이 최대라 효과 작음).
2. **하위 Agent/일반 도구 출력을 Decision에 보낼 권한 종류.** 지금 표에는 맞는 종류가 없어 보내지 않게 했다. 새 종류를 만들지, 코드 규칙만 쓸지.
3. **스필을 `egdesk_read_source`로 실제로 읽게 하려면** 문맥 저장소에 툴 출력용 캡처 종류와 실행 중 바인딩 추가가 필요하다(`pinOutput`, `egdesk-context-runtime.mjs:851-869`과 같은 방식). 이번에는 저장소 API 수준의 왕복만 확인했다.
4. **코드 규칙 정책(`rules` 플래그)을 Decision과 별개로 먼저 켤지.** 합성 자료에서는 규칙만으로 대부분의 절감이 나오고 요청도 지연도 없다.

## 7. 철학 점검
"확률은 실행 권한이 아니다"와 "실패하면 지금 방식으로": 판정이 무엇을 답하든 앵커는 코드가 지키고(모델이 전부 접으라고 답해도 오류 줄과 요약은 남는다는 시험 포함), 판정 실패는 전체 주입이다. "선택지는 런타임에 존재해야 한다": 스필 선택지는 저장소가 실제로 있을 때만 제시되고, 저장이 거부되면 그 블록은 조용히 버려지지 않고 주입된다. 기존 제품의 "몰래 자르지 않는다"(Claude MCP 한도) 원칙도 유지했다: 생략은 항상 줄 범위가 적힌 한 줄로 드러난다.
