# L2 / c2 — 같은 DM에서 반복·동시 의도 (retry/확인 더블클릭, 진행 중 재오픈, 방 전환)

브랜치 `lane/c1-chooser-outcomes`, e40c6f0 위에 커밋 `2eeefde`.
증거: `$L/evidence/l2-c2/` (`table-before.json`, `table-after.json`, `inflight-before.tap`, `inflight-after.tap`, `baseline-after.tap`, `baseline-plus-sims-after.tap`).

## 0. 범위와 한계
- 합성 하네스 관찰. 체인: mock Decisions fetch → 실제 `createDecisionClient`(실제 `createDecisionBudget`, cap 1,000,000, 응답마다 `usage.input_tokens=10`) → 실제 `CodexChatRuntime.chatChoice` → 실제 `/chat/choice` 핸들러 → 실제 Surface chooser(가짜 DOM). UI가 fetch를 abort하면 응답에 `close`를 내보내 실제 loopback 소켓 종료를 모사.
- 가짜 DOM의 "포커스"는 `focus()` 호출 추적 + `panel.contains(activeElement)`로 판정(실제 Firefox 포커스 아님). 설치 앱 검증 아님: 실제 DOM에서 `section[tabindex=-1]` 포커스 링 모양, 스크린리더 낭독, 연속 클릭 타이밍은 설치 앱에서 확인 필요.
- 타임아웃 의미론(L5), 429 분류(L3), 예산 로직은 읽기/측정만 했고 수정하지 않음. 신규 버튼 라벨 없음.

## 2. 측정 결과 (패치 전, 원 출력 `inflight-before.tap`)
| 항목 | 결과 |
|---|---|
| 확인 더블클릭 | POST 1, provider 1, 예산 10, 결과 포커스 `이유 묻기`. **중복 없음** (`confirm()`이 `phase` 가드로 첫 클릭에서 `checkingConfirm`으로 전이) |
| retry 더블클릭 | 재시도 단독으로는 POST 0 추가(review 화면으로만 복귀). 이후 확인 더블클릭 → 총 POST 2, provider 2, requestId 2종(`choice-<ts>-<uuid>` 각각 새로 생성). 예산은 응답이 온 요청만 10 |
| 요청 ID 중복 제거 | 있음: runtime이 `requestId`+fingerprint를 기억(`codex-chat-runtime.mjs` `choiceRequests`, 같은 ID 재전송은 `manual`), 같은 방 동시 요청은 `activeChoices`로 거절. UI는 의도당 ID 1개 |
| 진행 중 `[보기 추천]` | 트리거가 숨겨지고 핸들러도 `entry` 가드 → POST 1, provider 1, 에디터 0개. **중복 없음** |
| 방 전환 후 복귀 | 첫 요청은 abort로 runtime `activeChoices`가 풀려 새 요청이 정상 처리(provider 2, 추천 표시). 늦은 첫 응답(다른 보기)은 화면에 영향 없음(`current(item)` 실패로 폐기, 화면 텍스트 동일). 복귀 후 보기는 비어 있음(L1 영역 외, 기존 정책) |
| 로컬 예산 | 응답이 파싱된 요청만 `record`. abort·429·500·timeout으로 끝난 요청은 provider가 처리했더라도 0으로 집계 → **보낸 요청 수보다 로컬 집계가 낮을 수 있음**(예: 방 전환으로 abort된 첫 요청, 늦은 응답 도착 시에도 0). 측정만, L3에 전달할 관찰 |
| **포커스** | **재현된 실제 문제**: retry 클릭 직후 review로 가는 `checking` 구간, 진행 중(`pending`)/확인 중 구간에서 포커스가 `body(lost)`. (confirm/retry 버튼이 패널 재구성으로 제거되며 포커스 유실; 이후 `checking`→`review` 완료 시 confirm으로 복귀하지만, 대기·`statusUnavailable`·`setup` 구간엔 복귀 처리 없음) |

실패 테스트(전): C2-2 ×2 (`focus must not be lost (body(lost))`), C2-3 (`focus must not be lost while waiting`). C2-1, C2-4는 통과 → 중복 유료 요청, 늦은 응답 덮어쓰기는 **재현되지 않음**(수정 대상 아님).

## 3. 패치 (`2eeefde`, `eg-desk-surface.uc.js` +9/-1, 신규 sim +228)
- `paint()`를 얇게 감쌈: 재구성 전 포커스가 패널 안에 있었는데 재구성 후 어디에도 없으면, chooser가 남아 있으면 패널(`tabindex=-1`)로, 사라졌으면 `[보기 추천]` 트리거로 포커스를 돌려줌. 기존의 명시적 포커스(confirm/explain/retry/edit 등)는 그대로 우선(그 뒤에 실행되므로 덮이지 않음).
- 근거: VA.gov focus-management(https://design.va.gov/accessibility/focus-management — "Restore focus to a logical location when content is removed", "Don't move focus when content is loading; use ARIA to announce"). 대기 중 상태 문구는 이미 `role=status`라서 포커스를 로딩 표시로 옮기지 않고 컨테이너에 유지하는 쪽을 택함(→ **출처가 "대기 구간 포커스를 새 버튼으로 옮기지 않고 컨테이너에 둔다"는 결정을 바꿈**). WCAG 2.4.3 Focus Order(https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html)도 같은 방향.
- 일부러 바꾸지 않은 것: 중복 방지 로직(이미 의도당 1 POST), 예산, 타임아웃, 429 분류, 버튼 라벨.

## 6. 철학 점검
원칙: **화면 안에서 발견·완결 가능(키보드 사용자가 자리를 잃지 않음) + 한 의도 = 한 명시적 행동.** 반복 클릭이 새 유료 요청을 만들지 않는다는 점을 실측으로 확인했고(retry는 review로만, 확인 1회 = POST 1회·ID 1개), 패치는 그 흐름을 건드리지 않고 포커스 유실만 고쳐, 확인 대기 중에도 사용자가 chooser 안에 머문다.

## 7. 한계/전달 사항 (수정하지 않음)
- 로컬 예산(L3): abort/실패한 요청은 provider에서 과금될 수 있으나 `budget.record`가 호출되지 않아 집계가 과소. 사용자 문구 "이미 보낸 요청은 회수되지 않습니다"와 상충하지 않지만, 월 한도 판단에는 낙관적.
- 방 전환 후 복귀 시 입력 보기는 복원되지 않음(`leaveForList`/L1 경로 외 일반 전환; 기존 동작).
- 다음 sim 제안: 설치 앱(또는 JS DOM 환경)에서 실제 `:focus-visible`/스크린리더로 panel 포커스 확인, 그리고 retry 후 `statusUnavailable`(설정 조회 실패)과 `setup`(키 삭제) 분기에서의 포커스·복구.

## 8. 추가(Main 요청): `spend_limit_reached` 결과
- L3의 닫힌 코드 `spend_limit_reached`(비재시도)를 `CHOICE_MANUAL_REASONS`에 추가, DM 결과 추가: **재시도 없음, `[계정 설정 열기]` 없음, `[질문·보기 수정]`·`[닫기]` 유지**. 포커스는 `[질문·보기 수정]`.
- **승인 대기 카피(사용자 승인 전 제안 문구)**: `OpenAI의 지출·사용 한도에 도달해 추천을 받지 못했습니다. OpenAI에서 한도를 올리거나 다음 달 초기화 뒤에 쓸 수 있습니다.` (L3 설정 문구 재사용). 공통 하단 안내문은 c1과 동일.
- 한계: L3 코드가 이 브랜치에 없어 실제 client는 이 코드를 만들지 못함(알 수 없는 코드는 `bad_response`로 접힘). 따라서 sim 행은 client를 같은 모양의 `DecisionError`(name `DecisionError`, code `spend_limit_reached`)를 던지는 stub으로 대체해 측정(provider 요청 0건). 통합 후 실제 429(organization/project spend, organization usage limit) → 이 행으로 이어지는지는 int 브랜치에서 재확인 필요. 
- 결과: outcomes sim 16/16(신규 행 포함), 기준 회귀 254 (253 pass, 1 skip, 0 fail), 기준 + 두 sim 275.
