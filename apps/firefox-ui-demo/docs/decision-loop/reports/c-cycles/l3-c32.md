# L3 사이클 32 — 승인 결정 모델 우선(U13 R-A)과 대기 노트 문구의 취약성

- 브랜치 `lane/c32-approvals-fast` (int/c14 `6c4a861` 위). 증거 `evidence/l3-c32/`.

## 1. V1 `s4.wait`: 대기 노트 질문이 사람의 말에 취약한가
- 같은 사실 위에서 요청 문장만 바뀌었는데 `message__note` 가 .83 → .75 (bar .8). 질문은 "사려 깊은 동료라면 지금 짧은 진행 노트를 보내겠는가"라는 열린 기준이라, 요청 문장의 인상(결과를 알려 달라는 말투 등)이 .8 선 근처에서 판정을 흔들 수 있다. 같은 사실에서 말만 바뀌면 안 되는 질문이라는 점에서 취약하다고 본다.
- 측정 계획 `evidence/l3-c32/remeasure-note/plan.json`(dry run 통과, **6요청 2,509토큰**, ceiling 3,137, 전송 안 함): s4 beat의 제품 본문(9초째 명령, 아무 말도 안 함)에서 요청 문장만 바꾼 세 가지(원래, V1, 세 번째 표현) × 현재 문구(비교, soft)와 **후보 문구**("사람이 기다리는데 아무 말도 못 들었고 일은 아직 돌고 있는가": 조건 하나씩, c22-c23의 교훈) — 후보는 세 표현 모두 .8 이상이어야 하고(hard), 3초 시점 가드는 .2 이하여야 한다(hard). 통과하지 않으면 문구는 바꾸지 않는다. bar는 그대로다.
- 코드는 바꾸지 않았다(측정 전 문구 변경 금지).

## 2. 승인 결정 모델 우선 (U13 R-A, 소유자 정정 반영)
정정: 승인 **상태**는 action 층, **말**은 대화 층. 그래서 코드가 질문이나 답 문장을 게시하지 않는다.
- 플래그 `EGDESK_DECISION_FIRST_APPROVALS=on` (`EGDESK_DECISION_FIRST=on` 과 함께; 기본 꺼짐; 브리지·own-tools 배선·체크 등록).
- 질문은 지금처럼 엔진이 쓴다(게이트가 needs_person을 돌려주면 엔진이 문장을 만든다).
- **답**: 장부가 기다리는 그 한 명령(`broker.pendingAsk`)에 대해 기존 승인 판정(`reply_runs_command` / `reply_declines_command`)이 읽고, 코드가 **바로** 행동한다: 승인이면 그 명령을 한 번 실행기로 실행(8.1초 대신 약 1초), 거절이면 취소(브로커가 분명한 거절을 `declined`로 알린다). 그다음 엔진은 **한 번만** 이어서 돌고, 명령이 어떻게 됐는지를 컨텍스트로 받는다(도구 호출 불필요, "다시 호출하지 마라"). 승인도 거절도 아니면 지금과 같다(질문은 닫힌다, 한 홉).
- 새 문구 없음. 사람에게 보이는 말은 전부 엔진이 쓴다.
- 테스트 6건(엔진의 질문 턴 → "그냥 해"/"아니 잠깐"/애매한 답/기본값 유지, 브로커의 `declined`), 변이 12건이 잡혔다.
- 비교 스크립트 `real-engine-approvals-fast-v1`(Main이 실행): 질문 턴은 오늘과 같고, 답 턴에 `decisionFirst {reason: approval_ran | approval_declined, engineTurns: 1}`, `noToolCalls`, `commandsRan`을 요구한다. `scripts/egdesk-approvals-fast-compare.mjs <approval-words 출력> <approvals-fast 출력>`이 두 기록의 턴별 latencyMs·엔진 턴·실행 명령을 나란히 보여 준다. 가짜 app-server에서 두 대화 모두 통과한다.

## 한계
- 거절이 엔진을 기다리지 않게 만든 것은 "엔진이 한 번 이어 도는 일에 도구 호출이 필요 없다"는 가정이다. 실제 엔진이 결과 컨텍스트를 받고도 멈추면(그 180초 정체가 엔진 쪽이었다면) 이 경로로도 그 정체는 남을 수 있다. 진단 필드(c31)로 구분된다.
- 질문 12.5초는 대화 층(엔진)이라 그대로다.
