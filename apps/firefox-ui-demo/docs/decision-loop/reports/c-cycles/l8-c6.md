# L8 / C6 챗 직접 진입 -> 객관 브라우저 작업 보고

브랜치 `lane/c6-chat-direct-browser` (base int/c4 ef82022), 커밋 `0029b72`. 합성 검증만(실제 provider/Browser service/runBrowserReflex, UI 대역, mock Decisions, 주관 모델은 mock 엔진). 실제 Firefox·네트워크·codex 없음.

## 1. 오늘의 진입 경로 (매핑)
- 사용자 DM -> `codex-chat-runtime.mjs` send. 제한된 브라우저 턴(bounded)은 턴 시작 Decisions를 건너뛴다(`:2277` `bounded ? null : await this.prepareDecisionContext`). 브라우저는 선택된 카드의 interact 허용으로만 열린다(`codex-browser-tool-provider.mjs` prepare/bindRun).
- reflex는 provider specs에 추가되는 도구(`specs()`)이고, **Codex가 스스로 목표를 만들어 `egdesk_browser_reflex`를 불러야만** 시작된다(주관 모델이 하위 목표를 발명). 반사 결과는 `max_steps/escalated/...`이고 작업 id·상태가 없다. 사용자 답 이후의 재개는 새 도구 호출이라 `attemptedRefs`·대기 값이 초기화된다(아래 대조 테스트: 같은 값을 같은 페이지에 다시 입력).
- "여러 항목 중 어느 것" 같은 상황에 맞는 고정 옵션이 없어 `uncertain`으로만 끝났다.

## 2. 설계와 구현 (패러다임: 시스템 판정자, 사용자에게 추천을 보이지 않음)
새 모듈 `helper/egdesk-browser-task.mjs`(+231), `egdesk-browser-reflex.mjs`(+37/-?), `codex-browser-tool-provider.mjs`(+35/-?):
1. **진입 결정(시스템 결정)**: `entryQuestion(cards)`는 코드가 열거한 옵션(`[C1] <host>` = 사용자가 이 챗에 허용한 interact 카드들) + 고정 옵션 `not_browser_task`, `ask_user`로 된 choice 질문 1개. 임계값은 기존 choice 0.75/margin 0.2. `readBrowserEntry`가 모호/거부/목록 밖이면 `uncertain`으로 읽고 이때 작업을 시작하지 않는다(불확실하면 보통의 주관 턴). 질문 1개이므로 이미 턴 시작 Decisions 요청이 있으면 `questions`에 추가해 같은 요청에 얹을 수 있고(`readBrowserEntry(answers, ...)`), 단독이면 `decideBrowserEntry`(4 s foreground 마감, authorizeDispatch 포함)가 요청 1건을 쓴다.
2. **사용자 메시지가 곧 목표**: 하위 목표 단계 없이 메시지(500자 이내)가 `runBrowserReflex`의 goal.
3. **고정 옵션**: 모든 객관 단계에 `scroll_more / goal_met / needs_free_text / blocked`에 더해 신규 `needs_user_context`(여러 요소가 맞는데 목표가 어느 것인지 모름, 또는 사용자만 아는 세부) 추가. `blocked` 설명은 "Cannot proceed"로. `needs_user_context` 선택 -> `outcome: needs_user_context` + `candidates`(그럴듯한 요소 라벨).
4. **상태가 있는 작업**: `createBrowserTaskStore`(메모리 전용, 대화당 활성 1개, 30분 TTL): task id, 카드, 목표, 총 단계 수(최대 24, 구간 6), 이미 한 동작 수, 사용자 맥락, 일시정지 사유, reflex `state`(남은 값·고정 필드 바인딩·시도한 필드·history). `runBrowserReflex`가 `resumeState`/`userContext`를 받고 결과에 `state`를 돌려준다(모델용 텍스트에는 포함 안 됨).
5. **일시정지 후 재개**: 다음 사용자 메시지에 일시정지된 작업이 있으면 Decisions 질문 `task_resume`(`resume_task/cancel_task/unrelated`)으로 판단. resume이면 메시지가 사용자 맥락으로 추가되어 같은 작업이 계속된다. cancel이면 작업 취소, unrelated면 일시정지 유지, 불확실이면 보통 주관 턴.
6. **주관 모델에 가는 텍스트**(`subjectiveNote`): 한 줄 JSON, 닫힌 어휘 + 숫자만. `{"egdesk_browser_task":{id,status:need_context|cannot_proceed|done,code,candidates?(최대 3개, 60자),detail?(BROWSER_* 코드만),stepsDone,actions:{fill,navigate,scroll},next:ask_user_in_chat|tell_user_and_ask_in_chat|report_to_user}}`. URL·페이지 본문·입력값 없음. 코드: need_context=`choice_needed|detail_needed`; cannot_proceed=`login_required|two_factor_required|bot_check|sensitive_flow|access_denied|error_page|modal_blocking|blocked|uncertain|press_needs_expected_effect|tool_failed|observe_failed|step_rejected|step_limit|human_step`. `human_step`은 후보에서 제외된 요소(제출·결제·권한·삭제·구독 해지 등)만 남았을 때(제외 개수>0, `blocked`).
7. **게이트·예산·마감**: 진입은 provider의 같은 게이트(`directEntryEnabled` = 키 + mode on)로만 호출한다. off이면 Decisions 0건(S5). 예산/4 s foreground 마감은 기존 client·FOREGROUND_DECISION_TIMEOUT_MS를 그대로 사용한다. 마감이 지나면 `fallback:timeout`으로 보통 주관 턴(canon: 결정 호출이 실패하면 지금 방식).
8. **실행 범위 불변**(canon §5.2): 후보 필터, 분류기, URL 정책, revision 검사는 그대로. 확률이 실행 권한이 아니다.
9. **calibration 기록**: 진입 결정을 기존 `feature: 'browser_reflex'`, `q: 'choice'` 어휘의 내용 없는 기록으로 남긴다(`normalizeEntry`를 통과하며 메시지·호스트·URL 없음; S8).

## 4. 사용자 승인이 필요한 항목
- **사용자에게 보이는 문구는 코드에 추가하지 않았다.** 주관 모델이 노트를 읽고 자기 문장으로 말한다. mock 엔진의 문장("사업자가 둘입니다. 어느 쪽으로 받을까요?" 등)은 테스트 전용이며 제품 문구가 아니다. 기능 이름도 만들지 않았다(`egdesk_browser_task`는 모델 입력 JSON의 내부 키).
- **데이터 결정(승인 요청)**: `need_context` 노트에 페이지 요소 라벨 최대 3개(60자)가 들어간다(예: 사업자 번호). 주관 모델이 질문을 구체적으로 하려면 필요하지만 페이지 텍스트다. 기존 reflex의 `ranked`/`suggestion`도 같은 종류의 라벨을 이미 돌려주므로 카드 grant 안이지만, 빼려면 `subjectiveNote`의 `candidates`만 제거하면 되고 그 경우 주관 모델이 observe로 직접 읽는다.
- **Decisions로 가는 사용자 텍스트**: 진입/재개 판단에 사용자 메시지(500자 이내)가 간다(턴 시작 context setup과 같은 종류). 재개 후 단계 판단에는 사용자 맥락(최대 4줄, 400자)이 `Context the user gave in the chat (not page text)`로 들어간다.

## 5. 아직 안 한 것 (정직한 한계)
- **채팅 런타임 연결은 하지 않았다.** `codex-chat-runtime.mjs` send 경로에서 (a) 제한된 브라우저 턴의 `bounded ? null` 건너뜀(`:2277`), (b) 노트를 주관 모델 입력에 싣는 위치(`additionalContext`, `:2525` 부근), (c) 대화당 `createBrowserTaskStore`/`createDirectBrowserEntry` 보유가 필요하다. 5384줄 런타임을 다른 레인과 병행 수정하는 위험 때문에 별도 단계로 남긴다. 이번 결과는 모듈 + provider 수준 계약이다.
- 진입 결정을 턴 시작 요청에 합치는 것은 `entryQuestion/readBrowserEntry`로 가능하게만 했고 실제 합치기는 위 연결에서 한다.
- 팝업은 기존대로 `modal_blocking` -> cannot_proceed다. 다중 카드 선택 중 `ask_user`는 보통 주관 턴(`reason: ask_user`)이다.
- 실제 Firefox·네트워크 검증 없음.
