# L1 c27: 실제 엔진 점검에서 협업 (소유자와 초대된 사람, 한 방)

브랜치 `lane/c27-collab-real-engine` (base `int/c14` `4051509`, c26 병합 확인). 전부 mock과 가짜 app-server. Codex 바이너리는 실행하지 않았고 아무것도 보내지 않았다. 새 문구 없음. 제품 플래그 기본값은 그대로(꺼짐).

## 1. 협업 훅 (`helper/egdesk-real-engine-collab-hook.mjs`, 자기 모듈)
`helper/egdesk-real-engine-hooks.mjs`에 한 줄 등록(`CHECK_HOOKS = [briefingHook, collabHook]`). 창 없이, 브리지의 진짜 요청자/프레즌스 경로로 한 방에 두 사람이 있다.
- 두 사람(합성): 소유자(로컬 사람, `self` 행)와 초대된 구성원(피드 별칭 `m-` + 16 hex, 초대된 Board uuid, 자기 시야).
- 프레즌스: 브리지의 `createPresenceMirrorHttpHandler` (`POST /presence/snapshot`)로 올리고, 창이 하듯 3초마다 다시 올린다 (`dispose`로 멈춤).
- 누가 보내는가: 스크립트 턴의 `from: 'owner' | 'invited'`. 초대된 사람의 턴 앞에서 브리지의 `createRunRequesterHttpHandler` (`POST /presence/requester`)로 요청자를 알리고(레지스트리는 프레즌스 스냅샷에 그 별칭이 있을 때만 받음, 브리지와 같은 규칙), 소유자의 턴은 지운다.
- 대화 흐름: 점검의 `conversationFlow`에 브리지가 `EGDESK_PRESENCE=on`일 때 넘기는 키 그대로(`presence`, `audience`, `attentionPosted`)를 훅이 만들어 준다. 흐름이 같은 레지스트리에서 요청자를 읽고, 무엇을 물었는지 기록한다.
- 관심 장면: `expect.collab.attention`이 있는 턴만, 답이 올라온 뒤 제품의 작업 배치 런타임(`createWorkPlacement`)에 자기 경로(`POST /decision/work-placement/request`)로 끝난 결과의 장면을 보낸다. 장면은 코드로 만든 합성이다(캔버스가 없음): 소유자는 왼쪽에서 작업, 초대된 사람은 오른쪽, 좌표 없음. 소유자 질문(`owner_action`)은 Decision 모델이 받고, 방의 라이브 하트비트에서 판단된다.

## 2. 스크립트와 검사 (`real-engine-collab-v1`, 빌더와 같음)
`helper/egdesk-collab-real-engine-script.mjs`(빌더), `scripts/egdesk-collab-real-engine-script.mjs`(`--write`/비교), `scripts/real-engine/scripts/real-engine-collab-v1.json`. 4턴: (1) 소유자: 폴더에 무엇이 있나 (방의 세션을 시작), (2) 초대된 사람: 견적서 v1/v2 비교와 필요한 승인, (3) 초대된 사람: 납기만, (4) 소유자: 한 줄 요약. 멀티유저 v4의 창 없이 되는 hard 검사를 기록 수준에서 같게 한다 (기대는 코드, `expect.collab`):

|---|---|---|
| K1 요청이 초대된 사람의 것 | `requester: 'invited'` | 브리지의 audience가 그 별칭, 레지스트리가 `held`, 흐름이 물을 때마다 같은 답 (소유자 턴은 `cleared`와 null) |

| R3 소유자 분기, 포인터 | `attention {branch:'owner', kind:'point', pointer:'posted'}` | 배치 런타임이 소유자 분기를 정하고 포인터를 올리고, 대화 흐름이 소유자 방에 정확히 1개 메시지를 올림(`flowMessages` 1) |

## 5. 실제 엔진에서 알아 둘 점 (정직하게)
- **포인터는 방의 세션을 이어받는다.** 점검의 일회용 스레드는 제품의 DM이 아니다(`channelKind`, `stateless`): 답을 붙잡는 초안 점검 보류가 적용되지 않고 대화 흐름은 말할 수 없다. 훅은 `chat.allowIntermediateMessages(clientThreadId)`(제품이 한정된 실행에 쓰는 같은 입구)로 세션을 흐름의 메시지에 옵트인시키는데, 이는 그 세션의 다음 실행부터 효력이 있다. 그래서 스크립트의 첫 턴은 소유자의 짧은 턴이고, 포인터가 기대되는 턴은 두 번째부터다. (훅이 `draftCheck.eligible`로 방을 DM이라 선언하는 방법은 해 봤고 답이 사라져서 접었다.)
- **포인터를 쓰는 모델은 비공개 포크 턴이다.** 실제 0.171에서 일회용(ephemeral) 스레드는 포크가 거절되므로 포인터 메시지가 쓰이려면 `--persisted-with-cleanup`이 필요하다. 아니면 `pointer: 'posted'`는 'raised'에서 멈추고 검사는 실패하며 그 사유가 상세에 남는다 (`flowMessages` 0).
- **시간.** 포인터는 방의 하트비트의 유휴 박자(20초)에서 쓰인다. 훅은 장면 판단을 25초, 포인터 게시를 30초까지 기다린다. 가짜 엔진에서는 전체가 약 27초.
- **흐름이 요청자를 물었는가.** 짧은 가짜 턴에서는 턴 안에 박자가 거의 없어 `flowAudience`가 비어 있고, 대신 전체 실행 동안은 흐름이 물은 것이 기록된다(`flowAudienceTotal` > 0). 실제 엔진의 긴 턴에서는 턴 안의 질문도 기록된다.
- 소유자 필요 기대(2번 턴)는 실제 모델이 답에서 소유자의 승인을 말하는지에 달려 있다. 아니면 소유자 질문 판단과 분기 검사가 정직하게 실패하고 상세에 이유가 남는다. 요청자 분기(3번 턴)도 마찬가지로 모델의 판단이다.
- 모두 가짜 엔진 관측이다. 설치된 앱과 실제 Codex 0.171에서의 동작은 확인하지 않았다.

## 6. int/c14 병합과 L5의 확장 API로 옮김 (후속)
int/c14(`ec7b4cc`, 이어서 `15b0df9`)를 이 브랜치에 병합했다. L5가 핵심 줄 수정을 확장 API(`helper/egdesk-real-engine-extensions.mjs`, 레인별 절은 `helper/egdesk-real-engine-registrations.mjs`)로 바꿔서, 충돌 난 세 파일(`check`, `hooks`, `script`)은 int/c14 쪽을 그대로 가져오고 내 것을 API로 다시 붙였다. 내 직접 편집은 `hooks.mjs`와 `script.mjs`의 키/`from` 목록에서 모두 사라졌다.
- **내 레인의 등록(slot L1)**: `registerTurnFields({ from })`, `registerExpectKeys({ collab })` (검증기: 프레즌스/작업 배치/대화 흐름 플래그, 포인터엔 초안 점검), `registerTurnHooks('collab', createCollabTurnHook)`, `registerFlags({ reproduced: [EGDESK_PRESENCE, EGDESK_WORK_PLACEMENT], decisionDependent: [EGDESK_WORK_PLACEMENT] })`. 훅은 이제 `CHECK_HOOKS`가 아니라 등록된 턴 훅이다 (`createCollabTurnHook(conversation)`): 대화의 플래그에 `EGDESK_PRESENCE=on`이 없으면 아무것도 하지 않는다. 기록은 턴 기록의 `collab` 아래, 검사는 훅이 반환하는 expectations로 합쳐진다.
- **API에 더한 것 (작고 테스트됨, 다른 레인도 쓸 수 있음)** (`egdesk-real-engine-extensions.test.mjs` +3 테스트):
  - `registerTurnFields({ <field>: { schema, validate(value, { conv, turn, path, bad }) } })`: 턴 자신의 필드 (스키마에 들어가고, 모르는 턴 키는 여전히 거절).
  - `registerFlags({ reproduced, decisionDependent })`: 한 레인의 기능이 재현하는 제품 플래그와 Decision 모델이 필요한 플래그 (점검의 `BRIDGE_COMPOSITION.flags`, `DECISION_DEPENDENT_FLAGS`에 합쳐짐; 형식 오류와 중복 거절).
  - 턴 훅의 새 선택 멤버 (런타임이 만들어진 뒤가 필요한 훅용): `flowOptions({ FLAG, conversation })`, `attach(deps)`, `beforeSend(ctx)`, `afterTurn(ctx) → { record?, expectations? }`, `dispose()`. `ctx.state()`는 `conversationId`도 알려 준다.
- **핵심에 더한 호출 지점 (각 한 줄)**: 대화 흐름 옵션에 `turnHooks.flowOptions`, 런타임 구성 후 `turnHooks.attach`, 메시지 보내기 전 `await turnHooks.beforeSend`, 답이 올라온 뒤 `await turnHooks.afterTurn`(기록과 expectations를 합침), 끝에서 `turnHooks.dispose()`.
- 단언은 모두 유지했다. 바뀐 테스트는 위치만 옮겼다: 협업 훅 테스트의 `turn.hooks.collab`은 `turn.collab`, 등록 단언은 API 기준 (`registeredTurnHookNames`, `registeredExpectKeys`, `registeredTurnFields`, `registeredFlags`), 확장 API 테스트의 등록 목록에 `collab`/`from`을 더했다 (순서는 등록 파일 순서). L4의 등록 단언은 int/c14의 원래 줄로 되돌렸다.
