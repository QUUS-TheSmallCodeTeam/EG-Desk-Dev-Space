# L1 cycle 4: advisory 보정 기록 + 질문 코드 수명

브랜치 `lane/c4-board-reply-advisory` (base `int/c2` 256c816), 커밋 `4c72998`. 모든 관찰은 **synthetic harness**(임시 desk/보정 로그 파일, 실제 service/selector/Decisions client + mock fetch). 설치 앱, 실제 OpenAI는 쓰지 않았다.

## 1. advisory/on 보정 기록
**사용한 기존 API만:** `openCalibrationLog().record(entry)` / `complete(id, {run})`. L7 모듈은 변경하지 않았다.
- 항목: `feature:'turn_context'`, `mode`, 후보별 `{q:'relevance', p, threshold:0.6, kind:'board', would:'attach'|'skip'}` (p 내림차순, id 없음), `candidates`, `judgedTotal`, 실패 시 `fallback`(no_credit / rate_limited / timeout 등 닫힌 어휘), `attached`(= on이면서 외부 선별 결과가 실제 답에 적용됐는지, advisory는 항상 false).
- 라벨: 실행 종료 시 `complete(id, {run:'completed'|'failed'|'cancelled'})`.
- 구현: selector에 선택적 `observe` 콜백(확률 배열, 기준 0.6, 후보 수, 실패 코드)을 추가했고 선택 로직은 불변. 서비스가 `screeningEntry()`로 화이트리스트 필드만 만들어 기록한다. 기록 실패는 무시된다. 브리지 `codex-bridge-server.mjs`가 기존 `decisionCalibrationLog`를 서비스에 넘긴다. off는 기록 0.
- 확인(sim 20개): 모드 off/advisory/on x 확신/저확신/기권/429 no_credit/429 spend limit/timeout. 로그 파일에 질문, 발췌문, Board/Agent id, Agent 이름, 키, 상대 이름, 질문 코드가 없다. advisory의 답은 로컬 선택 그대로. 로그가 던져도 결과 동일.

**기존 API에 없어 못 한 것(의미를 바꾸지 않고 보고):**
1. 요청한 라벨 "소유자가 실제로 보낸 발췌 수 vs 모델 would-pick(유지/삭제 개수)": `complete()`의 outcome은 `run`, `toolActivities`만 받는다. 유지/삭제 개수 필드가 없다. 또 소유자가 답을 내보내는 시점(포털 review export)에 이 기록 id를 이어 줄 훅도 없다. 필요한 최소 확장: outcome에 `ownerKept`, `ownerRemoved`(0-8 정수)와 export 시 requestId로 기록을 찾는 경로.
2. 전용 feature 이름 없음: `FEATURES`에 board reply가 없어 `turn_context` + `kind:'board'`로 구분한다. turn_context 임계값 분석 시 `kind:'board'` 행을 제외해야 한다(Board는 0.6, turn_context 기준과 다름).
3. `top`/`second`/`minMargin`은 이 선별이 쓰지 않아 기록하지 않는다.
- 보정 로그 필드 확장은 L7 모듈의 의미를 바꾸는 일이라 하지 않았다.

## 2. 질문 코드: 실패한 실행
Sim(`L1c4 code lifecycle`): 
- 외부 선별 실패(429 no_credit, spend limit, timeout): **실행은 실패가 아니다.** 로컬 선택으로 답이 나오고(`screening:'fallback'`, c3 이후 소유자에게 표시), 코드는 정상 소비, 같은 티켓 재실행은 `STALE`, 같은 코드로 `prepare`하면 `CODE_INVALID`.
- draft 공급자 500: `RUN_FAILED` 502, 답 없음, 코드 소비됨, 같은 코드 재사용 거부.
- 승인 후 철회/교체: `STALE`(c3).
**결정: 코드 소비 로직은 바꾸지 않는다.**
- 근거(canon): Contract 2730행 "한 번 승인한 경우에만 처리", "정책 변경·회수·코드 만료 시 이전 승인을 재사용하지 않는다". 승인 1회 = 처리 1회이고 실패 후 코드를 되살린다는 문구는 없다. 코드 소비는 Desk store CAS이고 코드 소유자가 요청 파일을 재사용하지 못하게 하는 장치다. 되살리면 이미 외부로 나갔을지 모르는 질문의 재전송 길이 열린다(UI 코드 주석 "a timeout or failed response does not prove nothing ran"과 충돌). 외부 선별 실패는 이미 답을 내므로 되살릴 필요가 없다.
- 막힌 상태는 없다: 코드가 소진돼도 소유자는 같은 요청 파일로 **직접 회신**을 쓸 수 있고(prepare의 CODE_INVALID 문구도 그렇게 안내), 새 시도는 새 코드를 받아 한다.
- **실제 문제(문구):** 실행 실패 후 소유자가 보던 문구는 "실행 결과를 확인하지 못했습니다. 자동으로 다시 실행하지 않습니다."뿐이라 코드가 사용되었을 수 있다는 점과 직접 회신이 남아 있다는 점이 없었다. 패치: 같은 문구 뒤에 "이 질문 코드는 이미 사용되었을 수 있습니다. 직접 회신을 쓰거나 새 질문 코드를 받아 다시 시도해 주세요."(`EGDeskBoardAgentAsk.sys.mjs`, 1줄). 사용자에게 가는 카피이므로 승인 대기.

## 4. 철학 점검
"보내진 것은 쓰이거나 배운다": advisory가 비용만 들던 구조를 content-free 숫자 기록으로 바꿔 보정에 쓸 수 있게 했다. 승인 1회=처리 1회 원칙은 유지하고, 실패한 경우에도 사용자가 다음에 할 일(직접 회신, 새 코드)을 화면에서 알게 했다.
