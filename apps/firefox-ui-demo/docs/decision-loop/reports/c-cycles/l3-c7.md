# L3 cycle 7: 게시 전 초안 검사 (시스템 판정자, 추천기 아님)

브랜치 `lane/c7-draft-check`(`int/c4` = `ef82022` 기준). 커밋 `5293a28`(검사 모듈), `a076429`(int/c4에서 발견한 게이트 회귀 수정). 증거 `evidence/l3-c7/`: `after-draft.log`(시뮬 전/후와 지연표, 보정 기록), 게이트 `evidence/gate-l3c7/full.tap`.
**합성 결과이며 설치 앱/실제 엔진 검증 아님.** 판정자·주관 모델은 모두 결정론적 가짜(`egdesk-draft-check.fixture.mjs`)라서 **오케스트레이션**(분절, 선택지, 한 번의 요청, 한 번의 수정, 대체 경로)을 검증하며 실제 모델의 판단 정확도는 측정하지 않았다. **런타임에는 연결하지 않았다**(이유는 §1·§6).

## 사용자 방향 반영
Decision 모델은 주관 모델의 초안을 게시 전에 검사해 **발견 사항을 주관 모델에 돌려주고**, 사용자에게는 별도 UI로 보이지 않는다. 선택지는 런타임에 존재: 분절은 코드가 고정(생성 없음), 용어 후보는 코드가 수집, 근거 선택지는 이번 턴에 실제로 모델에게 준 자료(시점·출처 태그 포함). 수정은 1회, 그래도 실패하면 확실한 부분만 게시하거나 사용자에게 묻는다.

## 1. 최종 답변이 만들어져 게시되는 경로와 검사 위치 (코드 읽기)
- 생성: Codex `agentMessage`(`phase: final_answer`)가 `item/completed`로 도착 → `applyItem`(`codex-chat-runtime.mjs:4936-5013`).
- 노출: 같은 함수가 `message.started`/`message.delta`를 내보내 **스트리밍으로 UI에 보이고**, 완료 시 `message.completed`(:5013)를 내보낸다. 영속은 `emit`에서 `message.completed`(assistant, `localMessageId`)가 durable일 때(:1317-1320) 저장소에 쓴다. 즉 현재는 **초안이 곧 게시본**이며 사용자가 델타로 먼저 본다.
- 이미 있는 보류 장치: 주제 기억 답변 가드(`topicAnswerGuards`)는 최종 답변 항목을 **보류**(시작·델타 미보존, `messageDelta`가 가드 중 반환: :4866-4900, :4905 근방), 턴이 끝나면 `settleTopicAnswer`가 모순 검사(`topicAnswerContradiction`) 뒤 승인 플래그로 `applyItem(..., approved=true)`을 호출하거나 `rejectTopicAnswer`(안내 활동 `host:topic-answer-grounding`)로 폐기한다.
- **검사가 들어갈 곳**: `settleTopicAnswer`와 같은 자리, 즉 **보류된 최종 답변이 `applyItem`으로 풀리기 직전**(저장·UI 이전). 같은 보류 메커니즘을 모드가 on이고 일반 DM인 턴의 최종 답변에도 확장하면 초안이 사용자에게 노출되지 않는다.
- 연결하지 않은 이유(범위·위험): (1) 보류를 일반 DM 전체로 넓히면 최종 답변 스트리밍이 사라진다(제품 체감 변화, 소유자 결정 필요). (2) **수정 1회는 같은 네이티브 스레드의 추가 턴(또는 steer)**이어서 지금 mock 엔진/바이너리 금지 조건에서 실제 경로를 검증할 수 없다. (3) 근거 목록에는 패킷뿐 아니라 이 턴의 **도구 출력**도 들어가야 한다(`run.activities`). 빠지면 도구로 확인한 사실이 "근거 없음"으로 오판된다. 모듈은 이 모두를 주입(`evidence`, `revise`, `mode`, `budget`)받게 해 두었다.

## 2. 런타임 선택지 (코드가 고정, `helper/egdesk-draft-check.mjs`)
- `segmentDraft`: 문장 구간(시작·끝 오프셋 고정; `v1.2` 같은 숫자 점은 자르지 않음; 코드 블록·질문은 판정 대상 아님; 최대 12문장). 시험으로 오프셋이 원문과 일치함을 확인.
- `collectTerms`: 백틱 이름, snake_case, camelCase, SCREAMING_SNAKE, 호스트가 주는 `internalVocabulary`(Agent 지침·제품 코드명 중 사용자에게 안 보인 것)를 **고정 부분문자열**로 수집. 각 용어에 **노출 근거**를 코드가 붙인다: `user_said`(사용자가 쓴 말), `in_evidence`(사용자가 준 자료에 있음), `internal_only`. **근거가 있는 용어는 판정자에게 묻지 않는다**(사용자가 쓴 말은 내부 용어가 아님).
- `evidenceFromPacket`: 결정 컨텍스트 패킷의 `[item id kind time status source]` 머리말과 본문을 읽어 시점·출처가 붙은 선택지로 만든다.
## 3. 결정 단계(요청 1회)
문장마다 선택(`supported / contradicted / not_mentioned / insufficient`), 문장마다 술어("계획·과거 기록·전달 보고를 현재 사실처럼 말하는가?"), 용어마다 술어("독자가 근거 없는 내부 용어인가?"). 문항 상한 400 안(최대 12+12+8). 판독은 기존 `readChoice/readPredicate`(선택은 신뢰도 0.75/마진 0.2, 술어 발견 기준 0.7: `DRAFT_CHECK_THRESHOLDS.finding`, 보정 전 임시값). 발견 사항 종류: `contradicted`, `present_tense`(근거 항목의 시점 태그 포함), `unverified`(구체적 문장이면서 근거에 없음), `internal_term`. 판정이 불확실하면 발견 사항을 만들지 않는다.
- 수정: `revisionNote`가 주관 모델용 지시를 만든다(영문, 문장 인용과 종류만, "이 검사를 언급하지 말 것"). **발견 사항은 답변 텍스트에 복사되지 않는다**(시험으로 확인).
- 재검사 1회(`recheckMs`), 두 번째 수정 없음. 그래도 실패하면 `certain_part`(플래그된 문장을 뺀 나머지 + 고정 문구) 또는 남은 확실한 문장이 없으면 `ask_user`.

## 4. 시뮬레이션 (`after-draft.log`; "전"은 검사가 없던 지금 동작=초안 그대로 게시)
| 사례 | 전(게시) | 후(on) | 호출 |
|---|---|---|---|
| (a) 깨끗한 답 | 초안 | 초안 그대로, `passed` | 1 |
| (b) "PostgreSQL 마이그레이션은 현재 운영 중입니다."(근거: planned 페이지) | 현재 사실로 게시 | "…아직 계획 단계입니다." `revised`, 수정 지시 종류 `present_tense` 1건 | 2 |
| (c) `동의 세대`가 바뀌면…(내부 용어) | 내부 용어 노출 | "허용 상태가 바뀌면…" `revised` | 2 |
| (d) 근거 없음, 구체 문장+일반 문장 | 사실처럼 게시 | 일반 문장만 + 고정 문구, `certain_part` | 0 |
| (d2) 근거 없음, 구체 문장뿐 | 사실처럼 게시 | 고정 질문 문구, `ask_user` | 0 |
- 모드: **off**는 호출 0·초안 그대로(5/5); **advisory**는 판정하고 보정 기록만 남기며 초안을 바꾸지 않고 수정도 요청하지 않음(b·c에서 발견 사항 기록, 게시 불변); **on**만 수정·대체. 
- 예산: `budget.canSpend()`가 거짓이면 호출 없이 초안 게시(`budget_exceeded` 대체 기록). 제공자 오류·시간 초과도 **현재처럼 초안 게시**(fail-open, 검사 장애가 답을 막지 않음; 검사 장애는 "검증 실패"와 구별).
- 호출 절감: 검사할 구체 문장이 없고 용어 후보도 없으면 호출 0(`nothing_checkable`). 근거가 아예 없을 때 구체 문장은 판정자 없이 코드가 `unverified`로 분류(호출 0).

### 지연 상한과 근거
실측(소유자 제공): 따뜻한 호출 0.3-0.6 s, 장기 휴지 뒤 첫 호출 1.3-1.4 s.
- 첫 검사 한도 `firstCheckMs = 1500`: 첫 호출(cold 1.4 s)까지 포함하고 그보다 늦으면 **검사 없이 게시**. 깨끗한 답(다수)의 추가 대기는 따뜻할 때 0.3-0.6 s, 최악 1.5 s.
- 재검사 한도 `recheckMs = 1200`: 첫 호출로 연결이 따뜻해진 뒤이므로 0.6 s의 2배.
- 전체 보류 상한 `holdMs = 45000`(수정 모델 시간 포함, 주제 답변 가드의 `until`과 같은 개념으로 맞출 것).
- 시뮬(`after-draft.log` 지연표): 따뜻한 0.45 s → 검사 2회로 추가 대기 약 0.9 s(수정 시간 제외), 0.6 s → 1.2 s, cold(1.35 s)→warm(0.45 s) → 1.8 s, 2.0 s 느린 응답 → 1.5 s에서 `timeout`으로 초안 게시.
- 완화: 기존 `/decision/preconnect`(`warmDecisionConnection`)를 턴 시작 때 호출하면 최종 답이 나올 즈음 연결이 따뜻해 cold 1.4 s를 대부분 피한다(턴이 수 초 이상 걸리므로). 이 시뮬은 연결 재사용을 모형화하지 않았다.
