## 1. 작업 배치 재설계 (R3: 계산되는 것은 코드, 모델은 내용 판단만)

### 지금: 누가 무엇을 정하나
| 결정 | 주체 | 규칙 |
|-|-|-|
| 같은 자원이 이미 열려 있음 | 코드 | 항상 재사용, 질문 없음 (`same_resource`) |
| 같은 작업의 다른 화면이 있음 | 코드 | 그 옆 (`same_task`) |
| 요청자가 기다리고 idle(20초 무입력) | 코드 | 요청자 뷰 안의 빈 자리, 없으면 바로 옆 (`requester_idle`) |
| 요청자가 기다리고 작업 중 | 코드 | 요청자 뷰 바로 바깥 (`requester_working`) |
| 아무도 기다리지 않음 | 코드 | 모든 활성 뷰에서 떨어진 조용한 자리 (`nobody_waiting`) |
| 요청자를 모름(presence에 없음) | 코드 | 보수적 구역: 이 Desk 뷰 옆의 빈 작업 영역, **소유자 뷰를 포함한 모든 뷰 보호** (`unknown_presence`) |
| 근처 카드와 같은 건인가 | Decision 술어 | `same_matter_R#` 예 → 그 카드 옆. 아니면 규칙 자리 |
| 끝난 결과가 소유자의 행동을 필요로 하나 | Decision 술어 | `owner_action` 예 → 소유자에게 포인터. 아니면 요청자 쪽 결과 |
| 아직 실행 중 / 소유자 결정 대기(`waiting_owner`) | 코드 | 아무 일 없음 / 소유자에게, 질문 없음 |

- 모든 자리는 묻기 전에 하드 규칙을 통과한 실제 사각형이고, bridge가 닫힌 단어로 다시 검사한다(남의 활성 뷰 침범, idle 아닌데 뷰 안, 같은 자원이 아닌데 재사용, 사용자 카드 이동, 소유자 쪽 이동 → 통째로 거절).
- 질문은 R2/R4대로: 예/아니오 술어만, 항목마다 따로 인용한 블록, 공유 자료는 요청문 한 번. 코드가 결합한다(가까운 순서의 첫 "예").
- 판단 기준 0.8(`PLACEMENT_PREDICATE_YES`, heartbeat와 같은 엄격한 쪽). 아래면 코드 규칙 그대로.
- 개수 상한: 배치당 관련 카드 3개(=술어 3개), 주의 1개, heartbeat당 요청 12건, 대기열 8, 30초 지난 장면 폐기. 인용 길이: 요청 600자, 답 1200자, 카드 제목 120자, 발췌 400자.
- **advisory / on(`live`) 의미는 L4 c14 그대로**: 포인터 사실은 `live`일 때만, advisory는 "가리켰을 것"만 기록.

### 데이터 권한 (같은 허용 설정, 별도 동의 없음)
- "같은 건인가"는 run 자신의 요청문(`run_text`) + 카드 제목·발췌(`canvas_text`, **호스트가 maySend로 표시한 카드만**). 표면에서는 게시된 결과 카드만 maySend(브리핑 호스트와 같은 규칙). 메모·파일 카드는 글자가 나가지 않는다.
- "소유자 행동이 필요한가"는 run 자신의 요청문과 게시된 답(`run_text`).
- 둘 다 그 run의 게이트를 쓴다: 새 읽기 전용 접근자 `CodexChatRuntime.placementContextFor(key, { canvasMaySend })` → `{ request, answer, egress }` (`decisionEgressFor(run)`). 허용 안 되면 0건 전송, 코드 결과 유지.
- egress 등록: `egdesk-work-placement.mjs: ['run_text', 'canvas_text']`. 닫힌 단어 전용 종류 `placement_facts`는 보내는 곳이 없어져 삭제했다.
- **행동 변화(알림)**: 이전 배치 요청은 별칭과 닫힌 단어뿐이었다. 이제 run 요청문·답과 maySend 카드의 제목·발췌가 Decision model로 간다(D2 범위 안, run의 다른 모델이 받는 것과 같은 것).

## 4. Board 회신과 시점

**제품 코드가 확인한 사실**: 승인 발췌문은 소유자가 입력한 문자열뿐이다(`validateExcerpts`: 최대 8개, 1,500바이트; 저장은 문자열 JSON 배열). 날짜·버전·"대체됨" 링크가 없다. 그래서 "최신 같은 건 우선, 옛것은 dated 표시"라는 코드 규칙은 **계산할 재료가 없어 해당 없음**이고, 본문이 말해 주는 경우만 남는다.

- 발췌문마다 술어 하나 추가, 따로 인용: `cN_now` = "Judging only from this excerpt's own text and date (excerpt cN), is what it says still in effect on <today>?" (`today` = 물은 날의 로컬 날짜).
- 코드 결합: 관련(≥0.6) **그리고** 유효(≥0.5)만 제공. 관련인데 유효 아님 = dated: **현재 답으로 절대 제공 안 함**(근거에서 제외).
- 유효 답이 없거나 잘못됐으면 "유효"로 보지 않는다. 응답 전체를 못 쓰는 것으로 처리하고 기존 단어 일치가 선다(다른 잘못된 응답과 같음).
- 상한: 질문 수 = 2 × 발췌문(≤ 16).
- 요청 형식도 R4로 바꿨다: JSON 덩어리 대신 질문 블록 + 발췌문마다 따로 인용한 블록.
- dated 발췌문을 "이전 정보"로 보여 주는 것은 **새 문구가 필요해서 하지 않았다**. 지금은 빠지기만 한다. 관련 발췌문이 전부 dated면 답이 비고, 기존 문구 "관련 공개 발췌문을 찾지 못했습니다"가 나온다. 사실과 조금 어긋나므로 결정 항목에 올렸다.
- 테스트: `helper/egdesk-board-reply-time.test.mjs`(실제 서비스·선별기·client). 기존 Board 테스트의 provider mock은 새 질문(`_now`)에도 답하도록만 고쳤다(screening journey, calibration, context, crosslane, quota acceptance, draft-host acceptance). 판정 단언은 약해지지 않았다.

## 8. 한계
- 창은 두 모드 모두 표면을 오늘 자리에 연다. 코드 규칙 자리에 실제로 열려면 그 표면의 reveal(카메라 이동)과 activate(포커스)도 함께 막아야 한다(`revealPlacedCanvasCard`, `spawnFileCard`의 `activate`). 이번에 하지 않았다.
- 실행 파일 뷰어는 항상 새 카드로 열린다(`openMode: 'new'`). 같은 자원 재사용 규칙은 런타임에 있지만, 표면이 파일 카드에 자원 키를 주지 않아 실제 앱에서는 결과 카드(기존 출처 재사용)에만 해당한다.
- 주의 장면을 보내는 창 쪽 트리거는 여전히 없다(L4 c14와 같음). 왕복은 bridge 수준에서만 성립한다.
- 단어 일치 경로(extract, Decisions 꺼짐·실패)는 시점을 모른다.
- 실제 모델 답은 모른다. 두 계획의 기대는 가설이다.
