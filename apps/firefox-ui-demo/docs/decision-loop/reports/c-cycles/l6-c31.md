## 0. 기준 (먼저)
1. 한 기능 = 한 플래그(또는 한 경로). 실제 엔진 기록이 있는 것만 "초"와 "맞음"을 쓴다. 기록이 없으면 "측정 없음"이라고 쓰고 기대값은 추정이라고 표시한다.
2. 초는 기록의 서브턴 `latencyMs`(사람 메시지부터 엔진 턴 끝까지), 결정 호출 `ms`·`inputTokens`, 도구 호출 수, 항목 수. 비용은 결정 모델 입력 토큰(턴당).
3. 맞음은 그 실행의 코드 기대(`expect.*`)와 답의 사실 일치. 같은 입력의 되풀이는 증거로 세지 않는다(c23).
4. "켤 수 있음" = (a) 해당 경로의 실엔진 기록에서 안전·정답 기대가 통과, (b) 사람이 보는 새 문구·요소가 없거나 이미 승인, (c) 알려진 결함이 없거나 켜도 안전하게 실패. 하나라도 비면 무엇이 비었는지 적는다.
5. 새 문구·요소는 제안만, '승인 필요'. (U13)
6. 표본이 작으면(대부분 n=1~4) 비율을 일반화하지 않고 "있었다/없었다"로만 쓴다.

## 2. 엔진 정지: 감시가 못 잡은 이유 [측정]
- 오늘 기록 전체: 주 대화 서브턴 168개 중 **180초 시간 초과 4개**(check-22mw hedged t3, 24un approval-wait-no t2, 27mw own-confirm t4, 29st watchdog-armed t2). 4개 모두 항목이 `userMessage` 하나뿐: **엔진이 사용자 메시지만 받아 적고 그 뒤로 아무 진행(추론·답·도구)이 없다**.
- 29st watchdog-armed t2: 감시를 45초로 켠 상태였고 `firstEventMs = 2`ms 였다. c33 의 감시는 "그 턴의 이벤트가 하나라도 오면 정상"으로 보는데, 사용자 메시지 항목 이벤트가 2ms 에 와서 정상으로 판정했다. 그래서 180초를 그대로 기다렸다. ("실제 정지가 아직 안 잡힘"의 원인.)
- 같은 서명이 내부 고쳐 쓰기 fork 7/12 에도 있었을 가능성이 높다(기록에 이벤트가 없어 확정은 못 함; c30 이 이제 이벤트를 남긴다).
- 평균 영향 [해석]: 4/168 × 180초 = 턴당 평균 약 **4.3초**. 이 표본에서 정지가 한 턴에 더하는 평균이 prefetch 가 아끼는 평균(−5.8초, 파일 질문 턴 한정)에 가깝다. 표본이 작고 합성 시나리오라 일반화하지 않는다.
- 제안(L5, 승인 불필요한 내부 규칙): "첫 이벤트"를 **첫 진행 이벤트**(사용자 메시지 항목을 뺀 첫 항목·추론·답·도구)로 바꾼다. 재시도 안전 조건(그 턴에서 아무것도 실행되지 않음)은 `userMessage` 만 본 상태에서도 그대로 성립한다. 값 N 은 정상 턴의 첫 진행 시간 측정이 먼저다 — 지금 기록에는 그 값이 없다(이벤트 종류별 시간이 없음). 필요한 측정: 정상 턴 `firstProgressMs` 를 기록에 추가.

## 3. P1 증거: 심은 거짓 문장 재실행 (check-25pl → check-30pl)
같은 16대화(4사례 × 4)를 c30 수정 전(25pl)과 후(30pl)로 비교 (`evidence/l6-c31/planted-compare.mjs`, 같은 점수 도구):

| | 25pl (수정 전) | 30pl (c30 hedge 후) |
|---|---|---|
| 심은 거짓 12개를 검사가 찾음 | 12/12 | **12/12** |
| 오탐 대조(tense, 맞는 문장) | 0/4 발견, 4/4 그대로 게시 | **0/4, 4/4** |
| 고쳐 쓰기 실행 | 12/12 | 12/12 |
| **빈 응답 (아무것도 안 남음)** | **7/12** (coding 3, number 2, s13 2) | **1/12** (s13 1) |
| 재검사 통과해 게시(revised) | 5/12 | **10/12** (+ 확실한 부분만 1: coding) |
| 심은 거짓 문장이 사람에게 도달 | 0/12 | 0/12 |
| 금지 구절·허용 안 된 숫자 게시 | 1 (측정 도구 오탐) | 0 |
| 결정 토큰 | 54,655 | 59,601 (상한 60,000 이내, 선언한 추정 59,200) |

- 첫 읽기(fork) 정지: 25pl 7/12 → 30pl **6/12** (fork 가 25초 마감까지가 아니라 11초에 hedge 시작). 정지한 fork 6개의 기록(c30 이 남긴 trace): 모두 **첫 이벤트 51~116ms → 사용자 메시지 항목(약 2.5초) → 이후 이벤트 없음**. 주 대화 턴의 정지 4건(2절)과 같은 서명이다: 엔진이 메시지를 받아 적고 진행하지 않음. 정상 fork 는 6.1~7.1초에 끝났다(6/6).
- hedge 결과: 정지한 fork 6개 중 **5개를 새 스레드가 구했다**(통틀어 19.7~24.0초에 글; fresh 가 hedge 뒤 8.7~13.0초). 1개(s13-4)는 새 스레드가 **정지가 아니라 느렸다**: 사용자 메시지 항목 13.4초, 추론이 끝나고 답이 나오기 시작한 것이 24.8초(hedge 로부터 13.8초)로 25초 마감 0.2초 전이었고 마감이 그 답을 끊었다. 즉 이 1건은 hedge 가 늦어서(마감 여유 부족) 놓친 것이다.
- 가장 느린 구해진 건이 23.1~24.0초로 25초 마감에서 1~2초 남았다: 11초 hedge + 13초 fresh. hedge 를 9초 정도로 당기면 마진이 2초 늘어난다(끝난 fork 는 25pl 5.8~8.3초, 30pl 5.8~7.1초). 내부 값 조정이라 새 문구·요소 없음, 제안만(L3/L6).
- 사람이 보는 것: 25pl 에서는 12개 중 7개에서 아무 글도 못 봤다. 30pl 에서는 11개에서 옳은 문장을 봤고(대부분 6~7초 또는 20~24초), 1개에서 아무것도 못 봤다. **P1 에 대한 해석** [해석]: "모든 문장이 걸려서 아무것도 안 남는다"의 주된 원인은 고쳐 쓰기가 못 쓰는 것이 아니라 엔진 정지였다. 정지를 hedge 로 줄이니 "nothing remains" 가 7/12 → 1/12 로 줄었다. 남은 1/12 는 fork 와 fresh 가 둘 다 마감까지 못 끝난 경우다. 그래서 P1 의 선택지에서 B(보이지 않게 한 번 더)는 이미 hedge 가 하는 일이고, 남는 질문은 "그래도 아무것도 안 남을 때 침묵(A)인가, 글 없는 표시(D)인가"뿐이다(1/12, n 작음).
- 정지가 줄어든 것이 아니라 **정지의 처리**가 바뀐 것이다(fork 정지 7/12 → 6/12). **정지는 시간 에피소드로 온다**: 30pl 실행 순서(KST) 18:25:10~18:26:40 의 fork 4개는 모두 정상(6.1~7.1초), **18:27:01~18:31:16 의 연속 6개(coding-2, number-2, s13-3, coding-3, number-3, s13-4)는 6/6 정지**, 18:31:54 이후 2개는 다시 정상. 25pl 의 F F F F F S S S S S F F 와 같은 모양이다(정지 구간 약 4분). **그 구간에서도 새 스레드는 5/6 이 완료**했다(나머지 1개는 느림). 즉 에피소드 동안 영속 방의 fork 는 막히고 새 임시 스레드는 돌았다. 정지 에피소드의 원인(fork 가 영속 방의 롤아웃/MCP 시작과 겹치는지)은 기록에 없어 확정하지 못한다; 주 대화 턴의 정지 4건(2절)은 fork 가 아니므로 같은 원인인지도 모른다.

- 결정 호출 ms 가 기록에 없는 경로(브라우저 루프의 입장·다음 단계)는 엔진 시간만 적었다.
- 병렬 도구 호출이 있는 턴(브리핑 26개 호출 34초)은 도구 라운드 시간이 라운드당 3초라는 c29 추정의 반례다(한 라운드에 여러 호출). R-B 계열 기대값은 직렬 읽기 기준이다.
- 정지 비율(4/168)은 시나리오 설계의 영향을 받는다(승인·명령 시나리오가 많음).
