## 1. B4: 계획과 작업 그래프 (`97c8e7f`)
계획은 이제 그 계획을 제안한 방의 계정에 속한다 (소유자 결정 3: "작업별 계정은 재개할 때 확인").
- `plan.owner`는 이미 해시된 계정 키이므로, 제안 때 방의 slot 계정 키를 쓰면 저장 필드를 바꾸지 않고도 계정이 기록된다. 계획의 slot은 저장하지 않고 원본 대화(`origin.conversationId`)에서 매번 구한다 (채팅 저장소가 대화마다 프로필 하나를 고정하므로). 방이 다른 계정으로 옮겨가면 옛 계정의 계획은 그 방에서 더 이상 보이지 않는다 (`PLAN_NOT_FOUND`).
- `createTaskPlanService`: `getOwnerKey(slot)`, `slotOf`, `roomKeyed`. `propose`/`owned`(보기, 승인, 거절)/`resolveTaskInput`/`list`가 계획 slot의 계정으로 확인한다. 기본 로그인이 로그아웃이거나 남의 계정이어도 프로필 방의 계획은 제안, 목록, 보기, 승인, 실행이 된다.
- 작업 원문(`egdesk-task-sources`): `getOwnerKey(boardId)`. 계획의 Board는 그 방의 계정으로 등록/해결된다. 제안 중에는 계획이 아직 저장 전이라 `proposing` 맵이 slot을 잠깐 들고 있다.
- 위임 범위(`egdesk-workflow-runtime` `captureScope`): 계획 그래프는 방 계정의 `ownerKey`로 잡고, 프로필 slot의 `generation`은 기본 로그인 변화에 따라 움직이지 않는다 (그 계정 자체가 바뀌면 `ownerKey`가 달라져 끝난다).
- HTTP(`/tasks/plans*`): 보기/승인/거절은 `ensureAuth(hints)`로 계획의 방(대화 쌍)을 인증한다. 목록은 플래그 on이면 기본이 로그아웃이어도 프로필 방의 계획을 보여준다. 기본 계획은 이전과 같다.
- 브리지: `openWorkflowRuntime`에 `ownerKeyFor`(c24의 `browserOwnerKeyFor`), `roomSlotOf`(플래그 off면 `undefined`), `roomKeyed`.
- 테스트 `helper/egdesk-plan-room-account.test.mjs` 7개: 기본 로그아웃/남의 계정, 기본 변경은 무관, 프로필 계정 변경은 종료, 방 이동 시 미발견, 기본 방 불변, 플래그 off 불변, 보내는 도중 기본 계정 변경에도 위임 유지.
- 기존 핀 2개의 마커 문자열만 새 배선에 맞췄다 (`egdesk-portable-http.test.mjs`, `egdesk-workflow-runtime.test.mjs`).

## 2. B5: 가져오기/내보내기 첨부 (`97c8e7f`)
프로필 방의 캡처는 그 계정 아래 저장되므로 기본 로그인 하나로는 내보내기에 잡히지 않았다. `createContextAttachmentProvider({ ownerKeys })`: 플래그 on이면 기본 로그인과 상주 프로필 서버들의 계정 키를 모두 조회하고 (`residentIds()` 신규), 각 캡처는 자기 계정 키로 읽는다. 기본이 로그아웃이어도 프로필 방의 캡처는 내보낸다. 키 중복은 한 번만. 가져오기는 기본 로그인 그대로. 테스트 `helper/egdesk-portable-room-account.test.mjs` 3개.

## 3. 창의 Browser 카드 정체성 (`7aa6d53`, `3ec4b9a`)
c24의 브리지 쪽과 짝이다. 창이 카드 정체성을 기본 로그인과 비교하던 곳을 방의 계정으로 바꿨다 (플래그 on, 프로필 방).
- `browserToolBinding(roomKey)`, `browserToolRoomKeyFor(clientThreadId)`, 창이 만든 바인딩 객체만 방을 기억하는 `WeakMap`(`browserToolBindingRooms`, 브리지가 준 객체는 들어가지 않음), `browserToolRoomKeyOf(binding)`.
- 방 키를 쓰는 곳: 선택 등록(`registerBrowserToolSelection`: 프로필 방은 붙일 때의 기본 계정 사실 대신 방의 계정을 받는다), 선택 새로고침, 보낼 때 선택 확인, 스탠딩 grant 확인, 바인딩 요청, 이후 모든 `assertBrowserToolBinding`, 액션 lease 확인, 에이전트가 연 카드. 기본 방과 플래그 off는 같은 값이라 달라지지 않는다.
- 일부러 남긴 0인자 `toolBinding()` 호출: 카드 세대(`cardEpoch`)만 보는 두 곳, 붙일 때의 카드 사실 수집, QA 픽스처 신원. 테스트가 이 목록을 고정한다.
- 테스트 `scripts/egdesk-browser-room-card.test.mjs` 6개 (창 함수는 실제 소스에서 추출): 기본 로그아웃/남의 계정, 기본 변경은 무관, 프로필 계정 변경은 선택과 grant 종료, 기본 방 불변, 플래그 off 불변.
- 기존 하네스(`egdesk-browser-tool-transport`, `egdesk-surface-state`, `egdesk-annotation-memo`)는 새 자유 식별자 때문에 파라미터와 경계 문자열을 추가했다. 단언은 건드리지 않았다. `egdesk-room-keyed-checks`의 "기본에 남은 곳" 목록의 해당 줄만 새 문장으로 바꿨다.
- 관찰: 로그아웃 계정의 선택 등록은 이전에도 가능했고(식별자만 null), 막는 것은 바인딩 요청의 `knownCodexAccountKey`다. 그 동작을 그대로 유지했다.

## 4. 프로필 서버의 쿼터/권한 실패 (`9d2303b`)
공유 추적기(SUB-14)는 공유 서버의 알림만 보고 기본 계정의 `accessFailure`에 쓴다. 프로필 서버의 거절은 안 보였다 (그리고 다른 계정이 상속하지 않는 규칙 때문에 거기에 쓸 수도 없다).
- `helper/egdesk-profile-access.mjs`: 프로필마다 진짜 SUB-14 추적기 하나를 그 프로필의 auth 스냅샷 위에 둔다. 알림(`error`, `turn/completed`, `turn/started`, `account/login/completed`)과 `turn/start` RPC 거절을 기록하고, 실패는 그 계정 정체성과 함께 저장되어 프로필에 다른 계정이 로그인하면 상속되지 않는다. 완료된 턴이 지운다. 기본 계정과 다른 프로필의 실패는 건드리지 않는다.
- 상태 데이터만: 엔진 상태의 프로필 행에 `accessFailure: { kind, cause, at }` (식별자 없음, 허용 목록)를 플래그 on일 때 실패가 있을 때만 붙인다. 문구 없음.
- 테스트 `helper/egdesk-profile-access.test.mjs` 5개.

## 남은 것 / 결정 필요
1. **plan의 newThread 단계 계정**: 채팅 `send` 본문은 `engineProfileId`를 받지 않아서, 프로필 방에서 만든 계획의 `newThread` 단계는 (Agent 저장 계정 또는 기본) 새 방에서 돈다. `sameThread` 단계는 방의 고정 계정으로 돈다. 계획의 권한은 방 계정 기준이지만 `newThread` 단계의 실행 계정은 다르다. 선택지: (a) `newThread`도 방의 계정으로 새 대화를 열기 위해 신뢰된 내부 경로만 `engineProfileId`를 받게 한다 (새 API 표면 아님), (b) 프로필 방 계획은 단계를 모두 `sameThread`로 강제. 소유자 결정이 필요하다 (이번에는 만들지 않음).
2. `/tasks/*` (그래프 상태, 취소, 게이트 계속)와 `/task-sources` HTTP는 아직 `ensureAuth()`(기본 로그인)다. 계획 HTTP만 방 기준으로 바꿨다.
3. 프로필 서버의 사용량(rate limit)과 상속 MCP는 여전히 표시되지 않는다 (B7). 접근 실패만 이번에 추가했다.
4. 모두 합성(mock) 관측이다. 설치 앱에서 프로필 서버의 실제 실패 알림 형태는 확인하지 않았다.
