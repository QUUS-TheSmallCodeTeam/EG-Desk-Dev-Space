## 4. 본문 크기 probe 계획 (보내지 않음)

`proofs/decision-real-measure/turn-context-warmup-size/{S1-small,S2-large}/plan.json`, 빌더 `buildSizePlan` / `analyzeSize`, CLI `node scripts/egdesk-turn-context-latency-plan.mjs --size [--write]`. 등록부(`helper/egdesk-committed-plans.mjs`)에 등록했다.

- 물을 것: c18 설계는 제품 warm-up 본문(고정 요청, 추정 약 159 토큰)이 probe B·C 가 쓴 648 토큰 본문과 똑같이 데워 준다고 **가정**했다. 이 probe 가 그 가정을 직접 시험한다.
- 두 run, 각각 10분 이상 쉰 뒤 시작:
  - **S1-small**: 제품 warm-up 본문 (추정 159 토큰), 1 s 뒤 측정 turn_context (추정 840 토큰)
  - **S2-large**: 648 토큰 warm-up (추정 649), 1 s 뒤 측정 turn_context (추정 836)
- 추정 입력 합계 **2,484 토큰** (한도 3,000), run 상한 합계 2,740, 요청 4개, 제품 transport, 기록만 한다. S1 의 warm-up 은 제품이 보내는 본문과 바이트까지 같다 (`CONTENT_FREE_REQUESTS.warmup`, 테스트로 확인).
- 점 러너가 같은 10분 규칙을 쓴다: `scripts/egdesk-turn-context-warmup-run.mjs --set size --point S1|S2 [--send]`, `--set size --status`, `--set size --analyze`. 결과 파일은 `<HOME>/turn-context-warmup-size-results.json` (0600). 여섯 점이 다 들어오기 전에 돌리면 거부하지 않고 메모(`note2`)로 알린다. 여섯 점의 결과 파일과 이름이 섞이지 않는다.
- 꼬리 유무는 warm-up 요청 자신으로 판단한다 (B1 1,597 ms, C1 1,187 ms 처럼 800 ms 초과면 그 run 에 꼬리가 있었다). A2 가 보였듯 꼬리가 간헐적이라 이 구분이 필요하다.
- 등록한 판독 (측정 요청 800 ms 초과 = 느림):
  1. `inconclusive`: 두 warm-up 이 모두 빠름 (꼬리 없음), 크기에 대해 말할 수 없다
  2. `size does not matter`: 두 warm-up 이 모두 느리고 (꼬리 있음) 두 측정이 모두 빠름
  3. `small body does not warm`: S1 의 warm-up 과 측정이 모두 느리고 S2 의 측정은 빠름 → 더 큰 본문을 보내야 함
  4. `warm-up did not help`: 꼬리가 있었는데 두 측정이 모두 느림 → B·C 와 모순이므로 설계 변경 전에 반복
  5. `one run only`: 꼬리가 한 run 에만 있음 → 그 run 만 읽고 다른 쪽을 반복
  - 위 외에 S2 만 느린 경우 `large body failed while the small one warmed` 로 따로 낸다.
- 테스트: 빌더 파일 일치, 추정 ≤ 3k, 본문이 서로 다름, S1 warm-up 바이트, 판독 7가지, 점 러너 `--set size` 전 과정 (거부 규칙, 결과 파일 분리, 분석, 잘못된 점 이름).
- [한계] 두 run 으로는 "꼬리가 없던" run 이 나올 수 있다 (A2 처럼). 그 경우 판독은 `inconclusive` 또는 `one run only` 가 되고 반복이 필요하다.
