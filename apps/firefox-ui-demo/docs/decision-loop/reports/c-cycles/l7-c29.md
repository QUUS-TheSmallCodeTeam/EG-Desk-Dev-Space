## 2. 기본 켬(default-on)일 때 잘못될 수 있는 것
코드로 확인한 것:
1. **병합은 마지막 순간에, selection이 `on`이고 attached일 때만**입니다 (`onePacketSelection`). advisory이거나 selection이 없거나 늦게 빠지면 지금처럼 키 두 개로 나갑니다. 그 경우의 이득은 없지만 해도 없습니다.
2. **본문이 selection 항목과 글자 그대로 같을 때만** 생략합니다 (`mergeIntoSelection`; 같은 id면 항목 본문과 같아야 하고, 다른 id면 24자 이상). selection이 같은 기록을 다른 모양으로 보여 주면 본문을 한 번 두고 "같은 기록"이라고 표시합니다. 그래서 내용이 사라지지는 않습니다. 그 대신 본문이 잘린 selection 항목(`[…]`)이면 생략이 일어나지 않아 절감이 줄어듭니다.
3. selection이 마지막 순간에 빠지면(예: egdesk 안전 판정 실패로 키가 지워짐) 병합할 대상이 없으므로 메모리는 자기 키(`egdesk_turn_memory`)로 나갑니다 (`onePacketSelection`이 null). 메모리 쪽의 페이지별 권한 확인은 그대로 다시 일어납니다. 즉 한쪽이 다른 쪽을 끌고 내려가지 않습니다.
4. 키를 읽는 쪽: `turnMemoryMayDispatch`/`turnMemoryNoteFor`는 additionalContext에 `egdesk_turn_memory`가 이미 있으면 거절하는데, one packet에서는 그 키를 만들지 않으므로 영향 없음. 영수증은 attached 상태에서 만들어져서 키와 무관. draft check에는 memory 키가 병합 상태에서도 따로 알려집니다 (`memoryPacket` 기준).
확인되지 않은 것 (실행해서 확인해야 할 위험):
5. **모델이 "among the selected items above" 참조를 따라가는가**: 실제 엔진 1턴 한 번(check-4)에서만 확인했습니다 (답에 47일). 참조된 본문이 위에서 멀면(페이지 많고 긴 경우) 더 약해질 수 있음.
6. **한 키가 커집니다** (예: x30에서 selection+메모리 한 키에 약 13~15k 토큰대). 엔진이 additionalContext 한 항목의 크기를 제한하는지, 큰 한 항목이 두 항목보다 잘리기 쉬운지는 확인하지 못했습니다.
7. 지침 문구 두 벌(selection의 시제 지침, 메모리의 judge 설명)이 한 키 안에 이어집니다. 모델이 이를 구분하는지는 실제 측정이 필요합니다.
8. 값은 이 저니의 스크립트 선별 기준입니다. 실제 selection이 더 많은 페이지를 고르면 중복 건수와 절감이 같이 늘고, 덜 고르면 둘 다 줄어듭니다.
