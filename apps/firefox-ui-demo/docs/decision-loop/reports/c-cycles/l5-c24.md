## 1. 포크할 수 없는 대화의 내부 턴 (`helper/codex-internal-turn.mjs`)
Main의 smoke-5(공식 0.171): `thread/fork {threadId, excludeTurns:true, ephemeral:true}`는 **ephemeral 원본에서 -32600 "no rollout found"** 로 실패함(완료된 턴 뒤, 진행 중, lastTurnId 모두). 영속 원본은 된다. 그래서 일회용(ephemeral) 방은 내부 턴을 한 번도 돌릴 수 없었음.
- 규칙: 부모가 ephemeral이면(`run.stateless`) 포크를 시도하지 않고, 부모가 ephemeral이 아니어도 포크가 "no rollout found"로 거절되면(그 한 가지 메시지만) **새 ephemeral 스레드**에서 같은 턴을 돌림. 다른 포크 실패는 전과 같이 호출자에게 전달됨(대체하지 않음). `fresh`를 넘기지 않는 호출은 전과 똑같음.
- 새 스레드: `thread/start { ephemeral:true, sandbox:'read-only', approvalPolicy:'never', cwd: 부모의 엔진 폴더(진짜 폴더가 아님), model: 부모의 모델, config: 순수 엔진 스위치 + 격리(c22/c23의 MCP 이름별 끄기 등), developerInstructions: '…private one-off task…' }`, **도구 없음**(`dynamicTools` 없음). 엔진이 이 스레드를 ephemeral이 아니라고 답하면 쓰지 않고 해제함. 5분 동안 대화별로 오버라이드를 캐시(목록을 다시 읽지 않음). 입력은 `preamble + 호출자 텍스트`, `outputSchema`와 `effort`는 포크 경로와 같은 `turn/start` 파라미터로 그대로 감.
- 새 스레드는 대화를 본 적이 없으므로 각 호출자가 포크의 기록에 기대던 것을 이렇게 채움:

| 호출자 | 필요한 것 | 어디서 옴 |
|-|-|-|
| 하트비트 작성기(`writeChecked`: 중간 메시지, "왜 멈췄지" 답) | 사람의 마지막 메시지; 그 밖에는 프롬프트가 이미 사실(걸린 시간, 단계 수, 기다리는 것, 이전 메시지) | preamble: "Context: the person's last message to you was "…"." (800자 이하) |
| 초안 점검의 수정(`reviseOnFork`) | 사람의 마지막 메시지; 초안과 지시는 프롬프트에 있음 | 같은 preamble |
| 브리핑의 채우기/설계(`internalText`) | 프롬프트가 이미 답, 안내, 자료를 담음(L4) | **preamble 없음**: `internalText(run, prompt, { preamble: false })`(L4 요청, 채우기는 자료만 보도록 일부러 답 텍스트를 뺌) |

- 호출자가 쓰는 `internalText`의 서명은 그대로이고 옵션 `preamble`만 추가됨(기본 true). 모듈 내부는 `{ text, via: 'fork'|'fresh' }`를 돌려줌.
- 테스트(`helper/codex-internal-turn.test.mjs`, 10개): 영속 부모는 이전처럼 포크; ephemeral 부모는 포크 시도 없이 새 스레드(overrides, preamble, outputSchema, effort, 해제); "no rollout found" 대체와 다른 오류의 비대체; `fresh` 없으면 변화 없음; 저장된 스레드/startThread 없음/응답 없음; 선언(declines)과 feed; 런타임 3개 호출자(채우기 경로, 수정, 작성기)가 같은 경로를 타고 진짜 폴더가 와이어에 나가지 않음; preamble:false는 호출자 텍스트만. 그리고 **스키마 검사를 받는 가짜 app-server**(`refuseEphemeralFork: true`, 0.171처럼 ephemeral 원본의 포크를 거절)에 대해 점검 도구로: ephemeral 방은 포크 없이 새 스레드에서 답을 받고(`thread/start`의 파라미터가 프로토콜 스키마를 통과), 영속 방은 포크해서 받음.
- 한계: 진짜 바이너리에서는 Main이 이번 변경으로 why-stopped의 "reply"와 브리핑 채우기를 다시 돌려 봐야 확인됨(가짜는 거절 방식만 같게 만든 것). 새 스레드는 모델에게 대화 맥락이 없으므로, 호출자가 더 많은 맥락을 필요로 하는 경우가 생기면 preamble에 항목을 더하는 한 자리에서 고치면 됨.

## 2. 점검 도구: `--persisted-with-cleanup` (기본은 ephemeral만)
- 영속 원본 스레드로 제품과 같은 포크를 시험함. 영속 스레드는 Codex 홈의 기록에 남으므로 **지울 수 있음이 보장될 때만** 시작함:
  1. 시작 전: 바이너리의 생성 스키마에 `thread/delete`가 있어야 함(`inspectNativeCapabilities().threadDelete`); 없거나 읽을 수 없으면 `cleanup_not_guaranteed`로 아무것도 시작하지 않음(exit 2).
  2. 시작 전: 원장 `<out>/created-threads.jsonl`에 "만들어졌으나 사라졌음이 확인되지 않은" 스레드가 있으면(이전에 죽은 실행) 시작하지 않고 `--cleanup-leftovers`를 안내함.
  3. 엔진이 스레드를 돌려주는 즉시(`thread/start`, `thread/fork`의 결과) 원장에 `created`(0600, 추가만)를 적음. 포크한 내부 스레드는 ephemeral이라 기록만 하고 삭제 대상이 아님(제품이 해제함).
  4. 대화가 끝날 때마다(중단되어도 `finally`에서, 엔진을 종료하기 **전에**) 영속 스레드마다 `thread/delete` 후 `thread/resume`이 "no rollout found"로 실패하는지로 사라졌음을 확인함. 이미 없는 스레드(삭제 오류 + 사라짐 확인)는 정상. 하나라도 지워지지 않았거나 아직 resume되면 그 대화는 실패(`cleanupFailed`), 원장에 남고 요약이 `FAIL`이며 끝에 "CLEANUP FAILED … --cleanup-leftovers --run"을 크게 출력함.
- `--cleanup-leftovers [--run]`: 스크립트 없이 홈과 `--out`만으로, 원장의 남은 스레드를 app-server 하나를 띄워 삭제하고 사라짐을 확인함(기본은 dry: 개수와 id만 출력, 아무것도 시작하지 않음; 원장이 깨끗하면 아무것도 시작하지 않음). `--codex-home`이면 앱서버가 보고한 홈이 같은지 확인.
- 기본 동작은 그대로(원장 없음, `thread/delete` 없음, ephemeral 강제).
- 테스트: 정상(삭제 후 확인, 원장 created/deleted/gone, 0600), 기본 모드 불변, 거부 3종(thread/delete 없음, 스키마 읽기 실패, 이전 실행의 남은 스레드; 아무것도 시작되지 않음), 삭제 실패와 "삭제했다고 하나 계속 resume됨"이 대화를 실패시키고 원장을 더럽힘 → 다음 시작 거부 → `--cleanup-leftovers`가 정리, 깨끗한 원장은 아무것도 시작하지 않음, 인자와 계획 문구. 가짜 app-server에 영속 스레드, `thread/delete`, `thread/resume`, `deleteFails`/`deleteIgnored`를 추가(프로토콜 부분집합에 `thread/delete`, `thread/resume`도).
- 주의: `--person-home`이면 실행 중 영속 스레드가 사람의 Codex 기록에 잠시 보이다 사라짐(계획의 `threads:` 줄에 명시). 완전히 숨기려면 `--codex-home`으로 별도 홈을 쓰면 됨.

## 3. 게시된 링크 (엔진의 빈 폴더 경로 → 진짜 폴더)
- 원인: own-tools에서 엔진은 EG-Desk의 빈 폴더가 작업 폴더라고 알기 때문에 모델이 `…/engine-folders/empty/app.js` 같은 경로를 씀. 파일은 run의 진짜 폴더에 있음.
- 수정(`mapOwnPaths`, `applyItem`의 맨 앞): own-tools run의 assistant 메시지 텍스트에서 **엔진 폴더로 시작하는 경로를 같은 상대 경로의 진짜 폴더 경로로 바꿈**. 저장, 표시, 산출물(artifact) 링크 읽기가 모두 바뀐 텍스트를 봄 → 산출물 검증(`verifyFile`)도 진짜 파일을 열고 `artifact.target.path`가 진짜 파일을 가리킴. 경로 접두 전체만 바꾸고(`<엔진 폴더>-other` 같은 형제 폴더는 안 바꿈), 경로가 아닌 텍스트와 `/etc/hosts` 같은 다른 경로, own-tools가 아닌 run은 그대로. macOS의 실제 경로(`/private/var`) 형태도 같이 처리함.
- 한계: 스트리밍 델타는 조각 단위라 경로가 쪼개지면 바꿀 수 없어서, 메시지가 **완료될 때** 전체 텍스트에서 바꿈(완료 항목은 항상 전체 텍스트를 가짐). 상대 링크(`[app.js](app.js)`)는 이번에 다루지 않음(산출물 링크는 절대 경로만 읽음).
- 테스트: 링크, `<…>` 형태, 하위 경로, 형제 폴더 비변경, `/etc/hosts` 비변경, 산출물이 진짜 파일, own-tools가 아닌 run은 변경 없음.

## 4. 기록
- Decision 호출마다 `inputTokens`(응답의 `usage.input_tokens`, 읽을 수 없으면 null).
- 턴마다 `postedCount`(그 창에서 게시된 메시지 수)와 `finalAnswer`(마지막 게시 텍스트)를 `posted`(전체 텍스트)와 따로 둠.
- 실패한 엔진 호출의 `requests[].message`(300자 이하)가 코드와 함께 남음(예: `-32600`, "no rollout found for thread id …").
- **초안 점검은 대화 자신의 선택(opt-in)**: 스크립트의 `draftCheck: { mode: 'advisory'|'on', design?: 'predicates'|'choice' }`(L7의 `memory`와 같은 자리). **`--decisions`가 켜져 있어도 더 이상 모든 대화에 초안 점검(advisory)이 자동으로 붙지 않음**(Decision 호출을 쓰기 때문). 명시한 `flags.EGDESK_DRAFT_CHECK`는 그대로 우선하며(L3의 why-stopped처럼), `draftCheck.mode`와 모순되면 검증기가 거부. `--decisions` 없이는 사전 점검이 거부. 턴 기록에 `draftCheck.rows`(제품의 점검이 쓰는 보정 행: 모드, 부착 여부, 대체 사유의 닫힌 단어)가 담기고, `expect.draftCheck: { ran: boolean }`으로 점검이 돌았는지를 코드로 검사함.
  - 확인한 것: 가짜 app-server에서 일회용 방(ephemeral)의 메인 답에도 제품의 초안 점검이 돌아 보정 행을 남김(`evidence_unavailable` 대체 사유; 근거 자료가 없어서임). 진짜 바이너리에서 어떤 행이 나오는지는 Main의 실행이 보여 줌.
  - 동작 변화 고지: 기존 스크립트(L4 브리핑, L7 메모리)가 기본 advisory 초안 점검의 Decision 호출 수에 기대고 있었다면 달라질 수 있음. 게이트는 통과함.

## 5. Main이 실행할 명령(int-c14 경로, c24 병합 뒤)
먼저 `--run` 없이(기본 dry) 계획을 확인. 환경에 `EGDESK_REAL_CHECK_DECISION_KEY`가 있어야 `--decisions`가 돎.
```
cd $L/int-c14/apps/firefox-ui-demo
BIN=/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex
export EGDESK_CODEX_MODEL=gpt-6-astra EGDESK_CODEX_EFFORT=low

# (1) 기본(ephemeral): 하트비트 작성기와 브리핑 채우기가 이제 새 스레드로 간다. 이전 check-3의 "reply 없음"과 "채우기 실패"가 사라지는지
node scripts/egdesk-real-engine-check.mjs --codex-bin $BIN --person-home --decisions \
  --script scripts/real-engine/scripts/real-engine-why-stopped-v1.json \
  --script scripts/real-engine/scripts/real-engine-briefing-progress-v2.json \
  --out $L/evidence/main-real/real-engine/check-4 --run

# (2) 영속 원본 + 정리: 제품과 같은 포크. 끝에 모든 스레드가 삭제되고 사라짐이 확인된다
node scripts/egdesk-real-engine-check.mjs --codex-bin $BIN --person-home --decisions --persisted-with-cleanup \
  --script scripts/real-engine/scripts/real-engine-why-stopped-v1.json \
  --out $L/evidence/main-real/real-engine/check-4p --run

# (3) 둘 중 하나가 죽었거나 "CLEANUP FAILED"가 나왔다면, 다른 것을 돌리기 전에
node scripts/egdesk-real-engine-check.mjs --codex-bin $BIN --person-home --out $L/evidence/main-real/real-engine/check-4p --cleanup-leftovers --run
```
- 볼 것: (1)과 (2)의 기록에서 `requests`의 `thread/fork` 오류 유무와 `message`, 하트비트 작성기 메시지의 `postedCount`, `cleanup`(persisted/deleted/verifiedGone/failures), 원장 파일. edit-undo를 다시 돌리면 게시된 답의 링크가 진짜 폴더(`scratch/<id>/app.js`)를 가리키는지 `turns[].posted`에서 볼 수 있음.

## 6. 결정이 필요한 것
1. 초안 점검 기본 off 변경(위 4번)을 그대로 둘지(L3, L4, L7 스크립트가 기본에 기대고 있었는지 확인이 필요하면 알려 주세요).
2. 진짜 방의 직접 DM 답(Agent 프로필과 `replyDestination:'direct'`)은 점검 도구가 만들지 않으므로, 메인 답의 초안 점검 시험은 아직 불가함(보정 행은 일회용 방에서도 남음). 필요하면 점검 도구에 합성 프로필을 하나 추가해야 함.
3. 새 스레드의 preamble이 사람의 마지막 메시지만 담는 것으로 충분한지(작성기와 수정 기준). 진짜 실행에서 모델이 맥락 부족을 보이면 이어서 늘림.
