## 1. 관련성 (c16 지시의 회귀 수정)

메모리 루프의 관련성은 "답하는 모델이 맥락으로 필요한 것"이다. "이 요청에 대해 보드에 올릴 것"보다 넓다. 그래서 자료별 술어를 따로 둔다. 질문에는 요청과 자료 **하나만** 인용한다.

> "The person asked, quoted exactly as a JSON string: "…". Material, quoted as JSON: M6 {…}. Does this material contain information that the person's request asks about?"

- **연결된 묶음당 질문 하나.** 기록이 같은 일로 이어 둔 자료(same_task, follows_from, decided_in, refers_to, supersedes)는 한 묶음으로 보고, 묶음의 첫 자료(메모리 루프의 순서)로 묻는다.
  - 예 → 묶음 전체를 둔다. 나머지는 묻지 않는다(절약 경로).
  - 아니오·미결 → 묶음 전체를 뺀다. 채팅 답에는 그대로 남는다.
  - 아무것과도 연결되지 않은 자료는 따로 묻는다(개별 경로).
  - 두 경로 모두 테스트했다.
- **근거:** 실제 6행(A사 5건 + B사 1건)에서 질문이 6개가 아니라 2개다. 대신 묶음의 첫 자료가 아니라고 답하면 관련 있는 나머지도 빠지는 보수적 위험이 있다. 그래서 계획의 `r-about-each`로 건너뛴 4건을 각각 실측한다. 하나라도 아니오면 "묶음 하나 질문" 규칙을 "각각 질문"으로 바꿔야 한다.
- **요청이 늘지 않는다.** 관련성과 버전 쌍 질문은 place 요청에 같이 들어간다. 빠진 자료는 이후 어떤 요청에도, fill에도 가지 않는다(테스트 고정).
- 남는 것이 없으면 채팅 답으로 끝난다(내부 사유 `not-asked-about`).
- **mount 테스트를 3장으로 되돌렸다.** 주석은 사실대로 적었다: 스크립트된 Decision model이 B사 페이지에 아니오라고 답하는 것이고, 실제 모델의 답은 재측정 plan의 hard 항목이다.

## 2. "같은 것의 다른 버전인가"

**코드가 먼저 판정한다:**
- 버전 링크나 버전 표시가 있으면 버전이다. 표시 없는 제목이 표시 있는 제목의 기본형과 같은 경우도 포함한다("A사 견적서" / "A사 견적서 v2").
- 그 밖의 기록된 링크가 있으면 다른 관계로 기록된 것이므로 버전이 아니다.
- 제목의 회사가 다르면 버전이 아니다.

남은 쌍 중 제목에 두 글자 이상의 같은 말이 있는 것(접두 일치 포함: 견적/견적서)만 묻는다. 공유 단어가 많은 순으로 **최대 3쌍**이다.

> "Are these two materials an earlier and a later version of the same document, offer or plan?"

예면 날짜가 늦은 쪽에 버전 링크를 더하므로 비교 part가 생긴다. 실제 6행에서는 "A사 단가 협의 메모"와 "A사 건 결정 메모" 한 쌍이 걸린다(기대: 아니오).

## 3. todo 문구

"구체적 단계를 말하는가"(c16 실측 .07)를 "According to this material, is something not done yet or still to happen?"로 바꿨다. 조건은 하나이고, 기록된 `plan` 상태는 계속 코드 규칙이다.

## 5. Main의 all-on 실측 s3 (제품 경로, 실제 모델: several .57 / one_sentence .49)

**본문을 정확히 복원했다.** 결과 파일에는 sha만 있다. 그 실행의 커밋(`1f36c00`, 실행 시각 기준)을 내보내 L2의 journey runner를 그대로 돌리고, fetch는 기록된 실제 답을 순서대로 돌려주는 로컬 함수로 바꿨다. 39개 요청 모두 sha가 일치했고 s3 본문은 `715a34ce…`, 1,520 B다(`replay-all-on.mjs`, `s3/s3-11.json`). 보낸 것은 없다.

**place가 미결이 된 이유** (내 계획 본문의 several .93 / one_sentence 0과의 차이):
1. **요청이 "방금 그 내용 정리해줘"뿐이었다.** "그 내용"은 직전 답변("A사 견적은 11월 3일 요청, 11월 6일 v1 발송, v2는 팀장 승인 후 발송 예정")인데, 답변이 요청에 없었다. 판단 대상이 무엇인지 알 수 없는 질문이었다.
2. **붙은 자료가 엉뚱했다.** 메모리 루프가 이 turn에 붙인 것은 PostgreSQL 페이지 두 개("헬스체크 3종 체크리스트", "PostgreSQL 마이그레이션 배포 계획")였고 A사 자료가 아니었다. 이것은 L7/L2 쪽 문제로 보인다.
3. **날짜가 없고 status는 "unknown"이었다.** L2 지적대로 날짜·순서·미완료 코드 규칙이 동작할 수 없었다.

**이번 수정 (`694bae9`):**
- **(a) 답변 인용.** place 요청에 펼칠 답변을 한 번 인용한다(최대 1,200자, 그 run 자신의 글이므로 `draft_text`). 관련성 질문에도 "요청이 위 답변을 가리킬 수 있다"를 붙였다. fit·order·fill check에는 넣지 않는다(테스트 고정). 기존 "답변 글은 Decision model에 가지 않는다" 고정 assertion은 이 정확한 새 규칙으로 바꿨다. 보내는 내용이 늘어난 변경이니 승인이 필요하다(결정 4).
- **(b) 기록에 있는 것만 인용.** 날짜가 없으면 date 필드가 없고, status가 "unknown"이면 status 필드를 넣지 않는다. 결과에는 `recordGaps: { materials, undated, noStatus }`를 남긴다.
  - 날짜·상태·링크가 없으면 순서 part·미완료 part·비교 part가 생기지 않는다. 자료마다 단독 카드만 남는다(테스트 고정, 추측 없음).
  - L7이 날짜·상태를 실어 오면 같은 코드가 그대로 동작한다.
- **(c) s3 입력을 이번 제품 코드로 다시 만들어 계획에 넣었다.** 아래 `r-s3-product`, `r-s3-degraded`.

이번 코드로 s3 입력이면: 두 PostgreSQL 페이지가 관련성 아니오(스크립트 기준)라서 판단 요청 1회로 채팅 답 종료(`not-asked-about`). 그 자료로 보드를 만들지 않는 것이 옳다. "보드에 카드 2장 이상"이라는 s3 기대를 맞추려면 메모리 루프가 A사 자료를 붙여야 한다.
