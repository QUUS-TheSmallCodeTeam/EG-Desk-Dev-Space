**스크립트가 그 위에 더한 것**

단계별로 기록하는 것:

- `seen`: 그 단계 뒤에 사람이 보는 것
  - 두 대화방의 전체 메시지(사람 / Agent / 시스템 흐름 메시지 구분)와 이번 단계의 새 메시지
  - 하트비트가 정하고 게시한 흐름 종류, 활동 행
  - 주관식 모델에게 간 묶음의 키와 페이지 ID
  - 실행 상태와 답장 열림, 엔진 턴 수
  - 보드: 브리핑 결과, 게시된 카드 제목, 구성 부분의 종류와 컴포넌트
  - 작업 배치: 보낸 요청, 카드 위치, 판단 기록, 포인터 사실
  - 브라우저 작업 메모와 동작, 쓰기 저장소, 이번 단계의 보정 기록
- `checks`: 계획의 기대를 위 결과에 대어 본 판정(`pass`, `observed`, 담당 레인, 사전 예측)

## 5. 요청 모양이 바뀌어도 스크립트를 고칠 필요가 없다는 증명

`scripts/egdesk-all-on-live-measure.test.mjs`의 guard 테스트 두 개입니다.

**런타임 검사**
- 모든 본문은 하네스 제공자를 거쳐 전송 직전에 스택을 검사받습니다. 제공자 바로 아래가 `helper/egdesk-decision-client.mjs`여야 합니다.
- 클라이언트 아래 첫 다른 모듈이 스크립트면 거부합니다. 거부되면 실행이 멈추고 아무것도 보내지 않습니다.
- 테스트로 확인한 것:
  - 모의 전송 실행에서 모든 요청의 호출자가 제품 클라이언트입니다.
  - 네트워크 호출 수가 기록된 전송 수와 같습니다. 우회 경로가 없습니다.
  - 테스트가 본문을 만들어 전송기에 직접 넘기면 `hand_built_body:not_from_the_harness_provider`로 거부되고 0건 전송입니다.
  - 테스트가 본문을 만들어 제품 클라이언트의 `decide()`에 넘기면 클라이언트는 보내려 하지만 `hand_built_body:built_by_a_script`로 거부되고 0건 전송입니다.

**정적 검사**
- 스크립트의 import가 허용 목록과 정확히 같아야 합니다. 요청 빌더 모듈은 import하지 않습니다.
- 엔드포인트 문자열, `prompt_cache_key`, `questions: [`, 질문 타입 리터럴, `.decide(`가 없어야 합니다.
- 네트워크 호출은 `runPlan`에 넘기는 어댑터 한 곳뿐이어야 합니다.
- 드라이런에서 제품이 물은 질문 이름(20개 이상)이 스크립트와 계획 어디에도 나오지 않아야 합니다.

따라서 L3(하트비트)나 L1(배치)이 질문을 바꾸거나 없애도 스크립트와 계획은 그대로입니다. 바뀌는 것은 요청 종류 표시(`featureOf`, 하네스)와 드라이런의 대본 답 정책뿐입니다. 표시가 틀려도 실패가 아니라 `other:…`로 나옵니다.

## 6. 모의 네트워크 테스트 (11개, 모두 통과)

- **계획**: 해시 고정, 단계 ID 일치, 기대마다 check, 등급, 담당 레인이 있어야 함.
- **드라이런**: 키가 설정돼 있어도 네트워크 호출 0. 단계 표 11줄 출력. 결과 파일 0600, `sent: 0`. 추정치가 기본 상한 안.
- **`--send`**: 매 호출이 고정 엔드포인트에 `redirect: 'error'`, `credentials: 'omit'`으로 감. 본문마다 한 번씩, 기록된 sha256 순서와 같음.
  - 키는 Authorization 헤더에만 있고 본문, stdout, stderr, 결과 파일 어디에도 없음.
  - 요청마다 종류, 호출자, 해시, 답, 시간, usage가 있음.
  - 대본 답을 네트워크 뒤에 두면 단계별 요청 종류가 드라이런과 같음.
- **상한**
  - 토큰 상한 9,000이면 s2 첫 요청 전에 `token_ceiling`으로 멈추고 이후 단계는 `not_run`.
  - 공급자가 추정의 10배를 보고하면 `token_ceiling_reached`로 멈춤. 그 보고 뒤에는 아무것도 전송되지 않음.
  - 요청 상한 4면 4건 전송.
  - 단계 요청 상한 2면 `step_request_cap`, 단계 토큰 상한 1,000이면 `step_token_cap`.
  - 잘못된 상한 값은 사용법 오류.
- **실패에서 멈춤**
  - 3번째 응답이 429면 `http_429`. 실패 도착 뒤 전송 0, 같은 본문 두 번 없음(재시도 없음).
  - 이미 전송 중이던 요청은 응답까지 기록. 나머지는 `stopped:http_429`로 미전송.
  - 그 단계의 답은 사람에게 그대로 게시됨(P2).
  - 네트워크 오류도 같은 방식으로 멈춤.
- **키 없음**: 키가 없거나, 짧거나, 공백이 있으면 종료 코드 3, 전송 0, 여정도 돌지 않음. 모르는 인자는 거부.

## 7. 만들면서 발견한 것 (고치지 않음)

1. **브리핑에 타임라인과 남은 작업 부분이 나올 수 없습니다 (L4 / L7).**
   - 원인 1: 온톨로지 페이지가 브리핑 자료로 갈 때 날짜가 빠집니다. `pagesFromCandidates`가 `time.slice`만 남깁니다.
   - 원인 2: 스냅샷 밖 노드는 상태가 없습니다. 상태는 `snapshotStatus`에서만 옵니다.
   - 그래서 스켈레톤이 `sequence`와 `open_items` 부분을 만들지 않습니다. 드라이런 구성은 `single, compare, single, single`입니다.
   - 합성 페이지에는 날짜와 상태가 있지만, 제품 매핑이 그것을 실어 나를 자리가 없습니다. Main이 예로 든 "타임라인과 남은 작업 카드"는 지금 구조로는 실제 모델과 무관하게 나오지 않습니다.
2. **창 쪽 코드 중 배치의 attention 요청을 보내는 곳이 없습니다 (L1 / L4).**
   - `attentionRequest`는 있지만 표면은 배치 요청(`advisoryPlacement`)만 보냅니다(surface 9399행).
   - 여정은 창 빌더의 본문을 표면의 배치 요청 모양(`{ clientThreadId, conversationId, dto }`)으로 보내 포인터를 일으킵니다.
3. **컨텍스트 세팅 예산 800ms (L7).** 브리지는 `budgetMs`를 넘기지 않으니 런타임 기본 800ms가 적용됩니다. 실제 지연이 이보다 길면 컨텍스트 세팅 요청은 제품이 포기하고(`abandonedByProduct`로 기록) 선택 묶음 없이 진행됩니다. s1.packet은 턴 기억 묶음으로도 채워지므로 통과할 수 있지만, A3(같은 본문 두 번)는 실측에서 다르게 보일 수 있습니다.
4. **A2는 그대로입니다.** 브라우저 작업은 여전히 별도 대화방에서 돌립니다(s10, s11).

## 8. Main이 실측할 때

1. 먼저 드라이런으로 추정과 상한을 확인합니다: `node scripts/egdesk-all-on-live-measure.mjs`
2. 실측: `OPENAI_API_KEY=… node scripts/egdesk-all-on-live-measure.mjs --send --out $L/evidence/main-real/c16-all-on-journey.json`
3. 판정은 결과 파일의 `checks`와 `scorecard`로 합니다. 각 실패는 `owner` 레인으로 넘기면 됩니다.
