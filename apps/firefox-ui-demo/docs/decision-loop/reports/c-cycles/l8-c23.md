## 0. 등록과 오류 페이지 entry

- **등록.** `plan-stability`와 `plan-settings-error`를 등록부에 넣었습니다. Main은 "rebuilt로"라고 했지만, 이 plan 파일들은 형제 plan(statement, delivery, settings)처럼 정적 바이트이고 시계 의존이 없어서 `handWritten`으로 등록했습니다. `rebuilt`는 코드가 다시 만들어 바이트가 같음을 검사하는 항목이라 사실과 다르게 됩니다.
- **오류 페이지 entry** (실측 v4: 요청 predicate .90, 카드 predicate 0).
  - 원인: 카드가 보여주는 줄이 오류 문구뿐이라서, 모델이 "이 요청을 할 곳"이 아니라고 판단했습니다. 제목이 요청의 서비스를 지명하지 않으면 코드는 identity로 정할 수 없습니다. 실측 v2에서 같은 제목 "알림 설정 | 계정"의 identity만으로도 .19였기 때문에 identity-only predicate를 추가해도 해결되지 않습니다.
  - 수정: 요청이 web 작업으로 결정됐고, 어느 카드도 yes가 아니고, 줄이 알려진 카드가 no일 때만 **후속 요청 한 번**으로 그 카드마다 "이 열린 페이지는 오류 페이지, 로그인 페이지, 또는 내용을 막는 확인 단계인가?"를 묻습니다(그 페이지만 인용, R4). 방해 페이지는 카드를 **거부하지 못합니다**: 카드가 하나이거나, 방해로 결정된 카드가 하나이고 나머지는 모두 no이면 그 카드로 들어가고, step의 `ps_error`가 사람에게 넘깁니다.
  - 첫 entry 요청은 바이트 단위로 그대로입니다. 코드가 카드를 지명한 경우에는 줄이 카드를 거부하지 못합니다(원래 카드 질문을 하지 않음). ride-along 경로도 같은 후속을 씁니다.
  - 동작: 오류 페이지로 entry하면 `error_page`로 인계됩니다. 평범한 페이지인데 맞는 곳이 아니면 여전히 들어가지 않습니다(`not_browser`).

## 1. 브라우저 작업의 in-run 메시지 (`EGDESK_INRUN_MESSAGES`, L2 계약)

- 목적지: held-open run 안에서 objective loop가 돌고 있을 때(`hold.phase === 'working'`)도 `inRunMessageTo`를 받습니다. 사람의 답을 기다리는 동안(`waiting`)은 기존대로 그 메시지가 답입니다. 플래그가 꺼져 있으면 409 `INRUN_MESSAGE_UNAVAILABLE`이고, 요청 바이트도 그대로입니다(I6).
- 메시지는 대기열에 들어가고(`pendingInRunMessages`) heartbeat가 한 번 판정합니다(3개 predicate, 메시지만 인용). 코드가 결정하고 `settleInRunMessage`로 처리합니다.
  - **stop** → `interrupt`. 기존 정지 경로입니다. 진행 중인 페이지 동작은 끝나고, 이후 단계는 막힙니다(I2: 동작 1건 뒤 추가 동작 0, native turn 시작 없음). 이 루프에는 제출 동작이 없으므로 "제출 도중"이라는 지점이 존재하지 않습니다. 안전 지점은 페이지 동작 사이입니다.
  - **change** → `store.changeGoal`: 목표 = 원래 요청 + `/ Update from the person while the task ran: <메시지>`(최근 3개, 500자 이내). 실행 중인 segment는 `AbortSignal`로 다음 안전 지점에서 끝나고, 다음 segment는 새 목표로 계획합니다. segment가 무엇으로 끝났든(done 포함) 옛 목표에 대한 결과로 보고 다시 계획합니다(I8).
    - 같은 recorded-choice 검사를 새 목표로 합니다. 바뀐 요청은 기록된 요청이 아니므로 코드는 기록을 가져오지 않고, 변경 문장이 기록된 선택을 지명하면(예: 사업자번호) 코드가 가져옵니다.
    - 이전 질문에 대한 답(pendingAsk, confirm)은 비웁니다. 노트에 `goalChanges`(횟수)가 들어갑니다.
  - **status** → 근거가 확인된 진행 노트 1건(기존 `reply_status`, c18의 task 줄 포함). 작업은 그대로 진행합니다(I4).
  - **판정되지 않은 메시지**(잡담, 판정 실패, 판정기 없음): 목표를 바꾸지도 멈추지도 않고 대기 상태로 남아 다음 턴으로 이어집니다(I5, 잃지 않음). 기본 `steer`를 브라우저 작업에 그대로 적용하면 잡담이 목표가 되므로, 판정된 change만 목표를 바꿉니다.
- **사람의 단계 중에 온 change** (작업이 답을 기다리는 중): `decideResume`이 같은 요청에 predicate 하나(`resume_change`: 이 메시지가 질문에 답하는 대신 작업을 바꾸는가? 메시지와 질문을 인용)를 더합니다. yes(done 기준 .85)이면 메시지는 목표가 되고 답으로 컨텍스트에 쌓이지 않습니다(I3). 플래그가 꺼져 있으면 c22 요청 그대로입니다(I3b).
- 재현 중 발견한 것: `const confirm = paused.confirm` 다음 줄이 `(`로 시작하면 ASI 때문에 호출식으로 파싱될 수 있어 `void (`로 바꿨습니다.
- 테스트(`codex-chat-browser-task-roundtrip.test.mjs` I1~I8, 제품 경로):
  - I1: 이동 도중의 change
  - I2: 이동 도중의 stop

  - I4: status

- **두 번의 실행이 8개 요청 전부에서 동일합니다**(본문 sha, 답의 두 자리 소수, 입력 토큰). 같은 바이트를 다시 보내면 정보가 늘지 않습니다. 변이가 아니라 본문의 차이를 비교해야 합니다.

  - 조치: 컨트롤 줄과 predicate를 첫 step 요청에서 빼고, **길을 못 찾았을 때만**(미결정, scroll_more, blocked) 후속 요청으로 묻도록 옮겼습니다. 확정된 다음 단계는 후속에 도달하지 않습니다.
