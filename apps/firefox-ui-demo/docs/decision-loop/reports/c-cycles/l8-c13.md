## 2. L3의 순서 문제 해결 (`5cb5782`)
### 왜 "run을 먼저 만들기"를 그대로 하지 않았나
이 런타임에서 run은 네이티브 턴과 같이 생기고, 네이티브 턴은 주관 모델이 말할 것이 있을 때만 의미가 있다. 객관 루프 시작 시점에는 말할 것이 없다. 턴을 먼저 열어 두려면 (a) 모델이 "대기 도구"를 스스로 부르게 하거나(모델 행동에 의존, 새 도구), (b) 버려질 인사말 턴을 돌리거나, (c) 네이티브 스레드 밖에서 호스트가 메시지를 쓰게 해야 한다(다음 턴의 주관 모델이 질문·보고를 모름). 셋 다 택하지 않았다.

### 택한 구조: 첫 넘겨주기부터 run이 계속 살아 있다
```
요청 -> [진입 결정 + 객관 루프 첫 구간: run 없음]
     -> 네이티브 턴 1이 질문을 쓴다(완성 메시지 1건)           ← 여기서 run 생성
     -> run은 끝나지 않고 열려 있다: run.replyOpen = 질문 메시지, heartbeat는 waiting_user
     -> 사용자의 답이 그 run 안으로 들어온다(in-run reply)
     -> 객관 루프가 run 안에서 재개된다(allowIntermediateMessages; heartbeat가 중간에 말할 수 있음)
     -> 같은 스레드의 네이티브 턴 2(입력 = 사용자의 답, 닫힌 노트 동봉)가 보고를 쓴다(완성 메시지 1건)
     -> run 종료
```
- 모든 문장은 주관 모델이 자기 스레드의 턴에서 쓴다(질문 = 턴 1, 답 = 턴 2의 사용자 메시지, 보고 = 턴 2). 네이티브 스레드 내용은 c12와 같고, 달라진 것은 **run 하나가 여러 네이티브 턴에 걸친다**는 점뿐이다.
- 구현:
  - `finish()`에 한 줄: 넘겨주기 턴이 끝났고 작업이 사용자 입력을 기다리면 run을 닫지 않는다(`holdRunForBrowserReply`). 저장소에 "질문이 전달됨"을 표시(`markAsked`) -> provider 행이 `handing_off`에서 `waiting_user`로.
  - 답: `send`의 기존 in-run 경로(`openEarlyQuestion`)에서 이 run이면 네이티브 턴으로 steer하지 않고 작업으로 보낸다(`answerBrowserTaskReply`). 답 저장은 L3/L2의 코드와 같은 한 함수(`recordInRunReply`, 동작 변경 없이 추출).
  - 재개: `resumeBrowserTaskInRun`이 같은 `entry.handle`(재개 판단 `task_resume` -> 루프)을 진짜 run으로 실행한다. 이 구간에는 살아 있는 네이티브 턴이 없어 주관 모델이 동시에 페이지를 조작할 수 없다.
  - 다음 턴: `continueBrowserRunTurn`이 같은 run의 다음 네이티브 턴을 시작하고, 그 턴의 이벤트를 run에 연결한다(`turnAliases`, `enqueue` 입구 한 줄). 답변은 다시 보류되어 한 번에 게시.
  - 두 번째 질문이 나오면 같은 방식으로 다시 열어 둔다. 작업이 답을 받지 않으면(취소·무관) 노트 없이 답만 가진 턴이 돌고 run이 끝난다.
  - 중지: 기다리는 중/루프 중에는 살아 있는 네이티브 턴이 없으므로 run을 여기서 끝낸다(네이티브 interrupt 없음). 턴 2 중이면 그 턴을 interrupt.
  - 기다림 한도: 작업을 재개할 수 있는 시간(30분, 기존 작업 TTL)과 같다. 지나면 run이 정상 종료하고, 이후 메시지는 새 턴에서 같은 작업을 재개한다(c12 경로).
- 적용 조건(모두 개발자 flag, 기본 off): `EGDESK_BROWSER_ENTRY=on` + `EGDESK_DRAFT_CHECK=on` + `EGDESK_CONVERSATION_FLOW=on` + 채팅 저장소. heartbeat가 없으면 c12 동작(질문으로 run 종료, 답은 다음 턴)으로 떨어진다(N5). 브라우저 작업이 아닌 제한된 run의 동작은 그대로다.

## 4. 남은 한계 (결정이 필요한 것 포함)
1. **첫 구간은 여전히 run 이전이다.** 요청 직후부터 첫 질문(또는 질문 없이 끝나는 경우 보고)까지의 객관 루프에는 run이 없어 heartbeat가 말할 수 없다. 이 구간까지 run 안에 넣으려면 위 (a)(b)(c) 중 하나를 골라야 한다. 질문 없이 끝나는 작업은 전체가 이 구간이다.
2. 한 run이 여러 네이티브 턴에 걸치는 것은 이 런타임에서 처음이다. 확인하지 못한 것: 재시작 후 복구(이후 턴 id는 저장소에 기록되지 않음), 실제 화면(L2)의 표시 — `run.replyOpen`과 진행 중 run을 그대로 쓰지만 L2의 화면 테스트 9개는 현재 기준선에서 실패 중이라 화면 쪽은 검증하지 못했다.
3. 기다리는 동안 카드 권한(binding)이 최대 30분 유지된다. 더 짧게 할지는 결정 사항.
4. 루프 중에 중지하면 작업 결과가 `stuck`으로 기억 sink에 기록될 수 있다(사용자 중지와 구분하지 않음).
5. 작업 턴의 문장은 초안 검사를 받지 않는다(제한된 턴 부적격). 질문을 쓰는 턴의 주관 모델은 브라우저 도구를 갖고 있다(모델 행동, mock으로 검증 불가).
6. 다른 레인 영역 수정: `finish()` 한 줄, `enqueue()` 한 줄, `interrupt()` 분기, `answerEarlyQuestion` 첫 줄 + 답 저장 함수 추출(동작 동일), L3 테스트 기대값 3곳(c12에서 변경한 `handing_off`). L2·L3 확인 필요.
7. L7의 c14 안내(`memoryMaterials`)는 아직 int/c12에 없어 반영하지 않았다.

## 6. 철학 점검
결정 모델은 시스템 판정자이고 사용자에게 말하지 않는다: 사용자에게 가는 문장은 전부 주관 모델이 자기 턴에서 쓴 완성 메시지다. 확률은 실행 권한이 아니다: 답이 작업을 재개할지도 닫힌 선택(`resume/cancel/unrelated`)이며, 재개된 루프는 같은 후보 필터·분류기·revision 검사를 거친다.
