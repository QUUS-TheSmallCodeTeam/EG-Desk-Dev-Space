# L1 c33: 열린 항목 해소기를 "라우팅"까지 올리면 사람에게 무엇이 달라지나 (소유자용 결정 자료)

코드 변경 없음. 읽기만 했고 새 문구를 만들지 않았다. **문구가 필요한 곳은 전부 "제안(승인 필요)"로 표시**한다. 코드 줄은 `lane/c32-open-items` `bef3d3c` 기준이며 int/c14에서는 몇 줄 밀릴 수 있다. 오늘 실제 엔진 기록은 `$L/evidence/main-real/real-engine/check-21nj` (진행 중 말), `check-14w` (멈춤 질문), `check-32oi` (해소기 실행, 결과 대기 중이라 이 문서에는 반영하지 않았다).

## 0. 먼저 알아야 할 것: 오늘의 길은 *화면*이 정한다

해소기(`resolveOpenItems`, `codex-chat-runtime.mjs:3230`)는 `send()` 맨 앞(`:1850`)에서 판정하지만, 어느 길로 갈지는 **이미 화면이 정해서 보낸다** (`overlay/JS/eg-desk-surface.uc.js:19356-19381`, 규칙은 `overlay/resources/EGDeskChatState.sys.mjs:1430, 1441`):

| 화면이 보는 상태 | 화면이 보내는 것 | 브리지의 오늘 처리 |
|---|---|---|
| 열린 되묻기가 있음 | `inRunReplyTo: <runId>` | 그 run의 답으로 `turn/steer` (`answerEarlyQuestion :6477`). 되묻기 하나에 답은 한 번 (`flow.question.pending = false`) |
| run이 하나 일하는 중, 되묻기 없음, `EGDESK_INRUN_MESSAGES=on` | `inRunMessageTo: <runId>` | 큐에 넣고 다음 박동에 판정 (`acceptInRunMessage :6522` → `personPredicates :6172`: 멈춰/바꿔/상태 3질문, 어디에도 안 맞으면 **`steer`가 기본값**, `egdesk-conversation-flow.mjs:588`) |
| run이 일하는 중, 플래그 꺼짐 | **아무것도 안 보냄** (입력창이 턴이 끝나길 기다림) | 해당 없음 (보내도 `RUN_IN_PROGRESS`, `:2723`) |
| 일하는 run 없음 | 보통 메시지 | 새 턴 |

그래서 "라우팅"은 브리지만의 일이 아니다. 해소기가 "이 말은 그 항목과 상관없다"고 해도 **화면은 이미 그 말을 '답' 또는 '진행 중 말'로 이름 붙여 보냈다.** 브리지가 다르게 처리하려면 (1) 같은 응답 모양(`inRun: true`, `runId`)을 유지한 채 안에서만 다르게 처리하거나 (2) 화면과 계약을 바꿔야 한다. 아래 옵션은 이 구분을 같이 적는다.

해소기가 오늘 하는 일 (플래그 `EGDESK_OPEN_ITEMS=on`): 판정을 **기록**하고 (`record.today`에 오늘의 길을 같이 남김, `:1854`), 엔진에게 "정리된 것/아무것도 아님"을 닫힌 단어로 알려 주고, **승인 판단과 기억 확인 판단만** 그 항목에 속할 때만 돌게 한다 (`openItemRoute :3253`). 사람이 보는 것은 바뀌지 않는다.

## (a) 열린 되묻기가 있는데 그 답이 아닌 말을 보낼 때

**상황**: 엔진이 일하면서 "어느 폴더로 할까요?"라고 되물었다 (run은 계속 진행 중). 사람이 "그건 그렇고, 지금 폴더에 뭐 있어?"라고 쓴다.

**오늘 사람이 보는 것**: 입력창은 그 말을 되묻기의 답으로 보낸다 (`inRunReplyTo`). 그 말은 말풍선에 사용자 메시지로 뜨고, 엔진 턴 안으로 들어가 (steer) 엔진이 그것을 폴더 질문의 답인 것처럼, 또는 새 질문으로 읽고 이어서 말한다. **되묻기는 닫히고** (한 번만 답할 수 있다), 원래 질문 ("어느 폴더로 할까요?")은 답을 못 받은 채 사라진다. 이 경로의 실제 엔진 기록은 아직 없다 (`확인 안 됨`: 해소기 기록 `today: 'question_route'`가 쌓이면 센다). 코드로 읽은 사실이다.

**라우팅하면** (해소기가 "상관없음"이라 판정한 경우만):

| 옵션 | 사람이 보는 것 | 바뀌는 것 | 새 문구 |
|---|---|---|---|
| A0 오늘 그대로 + 엔진 블록 (지금 켜져 있는 것) | 위와 같음. 엔진은 "이 말은 열린 되묻기를 정리하지 않는다"를 알고 말함 | 없음 | 없음 |
| A1 진행 중 말로 받기 (되묻기는 계속 열림) | 말풍선은 같음. 엔진은 되묻기의 답이 아니라 *진행 중 말*(멈춰/바꿔/상태/그 밖은 steer)로 받는다. 원래 질문은 열려 있어 다음 말로 답할 수 있다 | 브리지 안 처리 (`acceptInRunMessage`). 화면은 `replyPending = true`로 "답했다"고 믿어서 되묻기를 다시 못 보낸다 → **화면 수정 필요** 또는 화면 규칙 변경 | 없음 |
| A2 다음 턴으로 미룸 | 말풍선은 같고 엔진은 지금 안 읽음. run이 끝나면 다음 턴 입력으로 들어감 (`carryInRunMessages :6567`, `carriedInputFor :6575`의 기존 장치) | 말이 *지금* 엔진에 닿지 않음 | 미룬다는 표시를 하려면 필요 (제안: 승인 필요) |
| A3 거절 | 말이 거절됨 (`INRUN_REPLY_UNAVAILABLE`, 오늘도 있는 코드) | 말이 사라질 수 있음, 입력이 지워지는지는 화면 처리에 달림 | 거절 문구 필요 (제안: 승인 필요) |

**Main 권고 초안**: **A0 유지**, 해소기 기록(`today: question_route` 대비 `status: none`)으로 *실제로 얼마나 자주* 답이 아닌 말이 되묻기를 소비하는지 먼저 센다. 잦으면 A1(문구 없음, 화면 한 곳 수정). A3는 권하지 않는다 (사람 말을 막는다).

## (b) 일하는 run이 있는데 새 요청을 보낼 때

**상황**: run이 `sleep 25 && echo build-A-finished`를 돌리는 중에 사람이 "그리고 폴더에 뭐 있어?"를 보낸다 (이것은 멈춤/변경/상태가 아닌 *다른 새 요청*).

**오늘 사람이 보는 것**:
- 플래그(`EGDESK_INRUN_MESSAGES`) 꺼짐: 입력창이 턴이 끝날 때까지 기다린다. 보낼 수 없다.
- 켜짐: 말풍선이 뜨고 다음 박동(보통 몇 초)에 판정된다. 멈춰/바꿔/상태에 안 맞으면 **`steer`**: 지금 도는 턴 안으로 들어가 엔진이 현재 일 도중에 이 말을 읽는다. 실제 기록: `check-21nj` `journey-change` ("그거 말고 B부터 해줘" → steer 1건, 도는 명령 SIGTERM으로 닫힘, 엔진이 "A의 실행 대기는 중단했습니다 … B로 실행할 명령을 알려 주세요", 26.9 s), `journey-stop` (interrupt 1건), `journey-status` (박동 메시지 1건, 엔진 말 아님). **"다른 새 요청"의 기록은 없다** (`확인 안 됨`). 코드상 기본값이 steer이므로 새 요청도 steer로 현재 턴에 들어간다.

**라우팅하면** (해소기가 `run` 항목에 "상관없음"이라 판정한 경우):

| 옵션 | 사람이 보는 것 | 비고 | 새 문구 |
|---|---|---|---|
| B0 오늘 그대로 (steer) | 현재 일에 끼어들어 엔진이 둘을 섞어 처리할 수 있음 | 기록: 해소기 `today: new_turn`이 아니라 in-run 경로라 `record.today`는 이 경로를 구분 못 함 (갭) | 없음 |
| B1 다음 턴으로 미룸 (큐) | 현재 일은 그대로 끝나고 이 말은 그 다음 턴으로 | 기존 `carriedInRun` 장치. **병렬 턴은 불가** (한 대화에 run 하나, `:2723`) | 미뤘다는 표시를 하려면 필요 (제안: 승인 필요) |
| B2 사람에게 묻기 | "지금 하던 일 끝나고 할까요, 바로 바꿀까요?" | 사람의 한 번 더 | **제안 문구, 승인 필요** (내가 만든 문구가 아님, 소유자가 정할 것) |
| B3 거절 | 보낼 수 없음 (플래그 꺼짐과 같은 경험) | | 필요 시 제안 |

**Main 권고 초안**: **멈춰/바꿔/상태는 오늘 그대로** (기존 판단이 이미 정확: `check-21nj` 3건 통과). "상관없는 새 요청"만 B1(미룸)로, 이때도 표시 문구는 승인 전에는 넣지 않는다 (표시 없이 미루면 사람이 말이 무시됐다고 오해할 수 있으므로 **표시 없는 미룸은 권하지 않는다**: 승인 전까지는 B0 유지가 안전). 먼저 측정: 해소기에 `run` 항목이 "상관없음"으로 나오는 빈도와 오늘 steer가 낳는 실제 결과 (새 스크립트가 필요, 이번에는 만들지 않았다).

## (c) 짧은 답이 열린 항목 두 개에 다 맞을 때

**상황**: 엔진의 답 하나가 "일정을 적어 둘게요 (기억 확인 대기)"와 "이 순서대로 실행해도 될까요? (제안)"를 같이 남겼고, 사람이 "응"만 보낸다.

**오늘 사람이 보는 것 (해소기 꺼짐)**: 화면이 보내는 길은 하나지만 (입력창 규칙은 되묻기/진행 중 말/새 턴 중 하나), **브리지 안의 두 판단은 서로 모르고 같은 말을 각자 읽는다**: 기억 확인 (`confirmNotedRecords`, `rc_confirms`)과 대기 승인 (`readGateHookReply`)이 같은 "응"을 둘 다 읽어, 한 말이 기록 확정과 명령 승인을 동시에 할 수 있다. 사람은 두 가지를 승인했다는 것을 말풍선에서 알 수 없다 (코드로 읽은 사실; 이 조합의 실제 기록은 없다).

**해소기 켜짐 (이미 출하된 동작, `egdesk-open-items.mjs:72`)**: 두 항목 모두 0.85 이상, 또는 하나가 0.85 이상이고 다른 하나가 0.5 이상이면 `several_items` → **아무것도 정리하지 않는다**. 두 판단 모두 건너뛴다 (`openItemRoute`가 `skip`을 돌려줌), 엔진은 "이 말은 아무 것도 정리하지 않는다, 항목들은 열려 있다"를 알고 보통 턴으로 말한다. 즉 오늘 사람은 "응"을 보냈는데 아무것도 승인되지 않고, 엔진이 알아서 되묻거나 넘어간다 (엔진이 되묻는지는 모델 몫).

| 옵션 | 사람이 보는 것 | 비고 | 새 문구 |
|---|---|---|---|
| C0 출하된 동작 (아무것도 정리 안 함, 엔진이 말로 처리) | "응"이 아무것도 승인하지 않음. 엔진이 말로 되물을 수도, 무시할 수도 있음 | 안전하지만 "응"이 헛돌 수 있음 | 없음 |
| C1 되묻기: 번호 붙여 어느 것인지 | "어느 것에 대한 답인가요? 1) … 2) …" (코드가 항목 요약으로 조립, 엔진은 안 씀) | 사람이 한 번 더 말해야 함. 요약은 항목의 닫힌 단어 | **제안 문구, 승인 필요** (고정 문구이자 새 UI 요소) |
| C2 코드 규칙으로 하나 고름 (가장 최근, 또는 승인이 우선) | 한 항목만 승인됨. 사람은 어느 것인지 모를 수 있음 | R5(안전 하한선은 규칙) 관점에서 *명령 승인*을 규칙으로 고르는 것은 위험. 기억 확인은 가역적 | 없음, 그러나 **권하지 않음** |
| C3 항목마다 따로 읽기 (두 항목을 각각 yes/no 판정, 둘 다 yes면 둘 다 정리) | 한 "응"이 둘을 다 승인 | 오늘의 암묵적 동작과 같은 결과를 *명시*하는 것. 명령 승인이 섞이는 문제는 그대로 | 없음, **권하지 않음** |

**Main 권고 초안**: **C0 유지** (가역/비가역을 한 말로 같이 승인하지 않는 것이 안전하다). 사람에게 "응이 헛돌았다"는 신호가 필요하다고 판단되면 그때 C1 문구를 소유자가 정한다. 먼저 `check-32oi`와 실사용 기록에서 `several_items`가 실제로 나오는 빈도를 센다 (합성 기록에서는 한 번도 관측되지 않았다, `확인 안 됨`).

## 못 한 것, 확인 안 됨
- (a), (b)의 "관련 없는 말" 실제 엔진 기록이 없다. 위 서술은 코드와 `check-21nj`의 관련 있는 말(바꿔/멈춰/상태) 기록에서 나온 것이다.
- `record.today`는 (b)의 in-run 경로를 구분하지 못한다 (오늘 값은 `question_route` 또는 `new_turn`뿐). (b)의 빈도를 세려면 이 값을 `in_run_message`로 넓혀야 한다 (작은 변경, 이번에는 하지 않음).
- `check-32oi` 결과는 아직 읽지 않았다. 나오면 (c)의 `several_items`와 (a)/(b)의 `none` 빈도를 이 표에 채운다.
- 화면 쪽 동작은 소스에서 읽은 것이고 실제 창에서 확인하지 않았다.
