## 점검 도구와 스크립트
- 삭제 턴(`action: delete`)이 이제 **제품의 라우트 핸들러**(`createChatHttpHandler`, `POST /chat/conversation/forget { clientThreadId }`, 창이 보내는 그대로)로 감(가짜 요청/응답 객체, 엔진 계정 확인 없음 = 로컬 쓰기 라우트). 이전에는 `chat.forgetConversation`을 직접 불렀음.
- 새 스크립트 기능(레지스트리에 L5 구역으로 등록, 코어 줄은 건드리지 않음): 대화 필드 `seededWrites`(합성 위키 쓰기: 쪽 4가지 범위 conversation/other/personal + 포인터, 읽기 pending/accepted와 어느 대화에서 들었는지)와 삭제 턴의 `expect.deleted { routeAccepted, storeRowsGone, engineGone, pendingReadingsWithdrawn, conversationMemoryGone, otherMemoryKept, pointerMarked }`. 메모리는 **시드**(모델이 무엇을 쓸지는 비결정이라, 점검 도구 자체의 격리된 쓰기 저장소에 합성 데이터를 직접 기록): 증명 대상은 쓰기가 아니라 삭제.
- 증명은 삭제 전후에 읽은 사실에서 코드로 판정(`helper/egdesk-real-engine-delete.mjs`): 
  - storeRowsGone: 대화/메시지 0, 목록에 없음, 로컬 메시지 id 0, 라우트가 보고한 삭제 행 수 ≥ 삭제 전 메시지 수, 삭제 전 메시지가 있었음(아무것도 없던 대화는 증명이 못 됨).
  - engineGone: 삭제 뒤 **`thread/resume`이 실패**(점검 도구가 직접 확인; 저장된 스레드가 필요해 `--persisted-with-cleanup` 필수, 사전 점검과 실행이 모두 거부) + 방의 모든 스레드가 `deleted`.
  - pendingReadingsWithdrawn(그 대화에서 들은 pending 읽기가 사라지고 모듈 개수와 일치), conversationMemoryGone(그 대화 범위의 쪽과 거기 붙은 읽기), otherMemoryKept(다른 대화의 쪽과 그 pending 읽기, 개인 쪽과 accepted 읽기는 그대로), pointerMarked(첫 메시지를 가리키던 본문 없는 쪽은 `sourceDeleted`로 남음).
- 스크립트 `real-engine-delete-v1`: 저장된 스레드에서 notes.txt를 읽는 두 턴 → 삭제 턴(`conversationGone` + 위 7개). Decision 모델 불필요.
- 가짜 app-server 검증(`egdesk-real-engine-check.test.mjs` +3, `egdesk-real-engine-delete.test.mjs` +3): 긍정(7개 증명 모두 통과, 삭제 뒤 resume 거부, 정리 실패 0), 부정 각각이 코드로 실패(엔진이 스레드를 남기면 engineGone만, forgetter를 빼면 pendingReadings와 conversationMemory만, 저장소가 행을 남기면 storeRowsGone과 conversationGone만; 나머지는 통과), 사전 점검, 판정 함수의 값별 부정(상태/수/없음 각각).
- 레지스트리 테스트(`egdesk-real-engine-extensions.test.mjs`)는 다른 lane이 키를 더하면 깨지던 정확 일치였음(L2가 `collab`을 더함): 세 키의 상대 순서와 중복 없음으로 바꿈(원래 단정의 의도는 유지, 새 키는 허용; 턴 필드 단정도 유지).
