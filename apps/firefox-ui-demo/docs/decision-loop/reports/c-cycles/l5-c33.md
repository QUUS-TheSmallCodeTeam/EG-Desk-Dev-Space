## 동작 (`CodexChatRuntime.startTurnWatched`, 플래그 없으면 정확히 `engine.startTurn`)
- 턴이 **수락된 뒤**(turn/start 응답) 그 **턴 id의 이벤트**를 기다림. 기다림은 런이 만들어지기 **전**(디스패치 안)에서 일어나므로 이벤트가 하나도 없었다는 것 = **아무것도 실행되지 않았음**(도구 호출·승인·사용자 메시지 외 항목 없음)이 구조적으로 보장됨. 이 보장 위에서만 재시도.
- N초 안에 그 턴의 이벤트가 없으면: `turn/interrupt`(최대 3초 기다림, 실패해도 진행) → **같은 파라미터로 한 번만** 다시 `turn/start`(메시지 id만 `…:retry1`). 둘째도 침묵하면 다시 시도하지 않고 `ENGINE_STALLED`(504, 닫힌 코드)로 요청을 끝냄. 이벤트가 한 번이라도 온 턴은 이후 얼마나 조용해도 이 감시가 **건드리지 않음**(도구 호출 뒤 재시도 없음).
- "첫 이벤트" = 그 턴 id를 단 알림이나 서버 요청(`turn/started`, 사용자 메시지 항목, 추론, 도구 호출 …); 스레드 단위 알림(`thread/status/changed` 등, 턴 id 없음)과 **인터럽트된 이전 턴의 늦은 이벤트는 세지 않음**(재시도 턴을 구해 주지 못함). 응답보다 먼저 온 이벤트는 셈.
- **사실 기록**: `run.engineStall`(재시도로 이어진 런), 대화별 `chat.engineStalls`, 하트비트 사실 `engine_stall { stalled, after_ms, stalls, recovered }`(숫자·불리언만). 다음 턴에 모델에게 주는 문구는 **만들지 않음**(복구된 재시도는 모델이 모르는 새 턴이고, 실패는 요청이 오류로 끝남): 필요하면 제안.
- 점검 도구: 모든 턴 기록에 `firstEventMs`(turn/start 응답부터 그 턴의 첫 이벤트까지, 응답보다 먼저 왔으면 0)와 `latencyMs`. `expect.engineStall { stalled, recovered?, maxFirstEventMs? }`. 가짜 app-server에 `silentTurns: n`(처음 n개의 일반 턴은 수락 후 침묵, 인터럽트 전까지).

## N: 암시된 값 45초(잠정), 확정은 측정 뒤
- **기존 기록에는 첫 이벤트 시간이 없음**(L3의 진단은 메시지 종류별 **개수**; 시간은 없었음; 기록 132개 확인). 그래서 p99를 지금 계산할 수 없고, 이번에 `firstEventMs`를 기록에 넣었음. 임시 N = **45초**: 건강한 엔진의 첫 이벤트는 수락 직후(밀리초~수 초)라는 가정에 큰 여유를 두고도 180초의 4분의 1. 틀리게 침묵으로 잡으면(느린 추론의 첫 이벤트가 45초를 넘는 경우) 멀쩡한 턴을 인터럽트·재시도하므로 **측정이 먼저**. 계산식 제안: `N = max(15 s, ceil((p99 firstEventMs × 3 + 5 s) / 5 s) × 5 s)`.
- 기대 효과: 180초 침묵이 **N + (재시도 턴의 정상 시간)**으로 줄어듦(N=45면 약 45초 + 정상 턴; 재시도도 침묵이면 N×2 = 90초 뒤 `ENGINE_STALLED`).
