# L1 c29: 실제 엔진 협업 점검에서 브리지/엔진 재시작

브랜치 `lane/c29-collab-restart-real` (base `int/c14` `1a9515f`). 가짜 app-server와 mock만. Codex 바이너리 미실행, 아무것도 보내지 않음, 새 문구 없음.

## 1. 점검에 `restart` 턴 (작고 테스트됨, 다른 레인도 쓸 수 있음)
턴 사이에서 브리지와 엔진이 멈췄다가 다시 시작한다. 대화의 저장소, 폴더, 저장된(persisted) 스레드는 그대로다.
- **스크립트 형식** (`egdesk-real-engine-script.mjs`): 턴 `action: 'restart'`. say, approve, afterMs 없음, 핵심 `expect` 키 없음(등록된 키만, 예: `expect.collab`), 첫 턴이나 마지막 턴이 될 수 없고 뒤에 일반 메시지 턴이 와야 한다, 연속 restart와 agentProfile 대화에서는 안 된다. `--persisted-with-cleanup`이 필요하다: 미리 점검(`preflight`)이 알려 주고 `runCheck`는 `restart_needs_persisted`로 거절한다.
- **구현** (`egdesk-real-engine-check.mjs`): `runConversation`이 restart 턴에서 대화를 구간으로 나눠 구간마다 앱서버, 런타임, 훅을 새로 만든다 (이전 브리지의 메모리는 없다). 같은 저장소와 폴더(폴더는 다시 쓰지 않음), 같은 저장된 엔진 스레드를 이어 쓰고, 창이 다시 연결될 때처럼 `chat.resume`으로 방을 이어 받는다. 마지막 구간에서만 저장 스레드를 지우고 확인한다 (중간 구간이 중단되면 그 자리에서 정리). 기록은 하나로 합쳐지고 턴 번호는 스크립트의 것 그대로, restart 턴은 자기 기록을 가진다.
- **확장 API** (`egdesk-real-engine-extensions.mjs`): 턴 훅의 새 선택 멤버 `beforeRestart(ctx) → carried`(예전 훅이 엔진이 사라지기 직전에), `afterRestart(ctx) → { record?, expectations? }`(새 훅이 새 런타임에서, `ctx.carried`로 예전 것을 받음). 단위 테스트 +1.
- **가짜 앱서버** (`scripts/real-engine/fake-app-server.mjs`): 선택 인자 `shared`(저장 스레드, 쓰인 스크립트 턴, id 카운터)로 같은 테스트의 여러 인스턴스가 디스크에 남은 것을 본다 (실제 바이너리가 프로세스를 다시 띄워도 스레드가 디스크에 남는 것과 같다).

## 2. 협업 스크립트 `real-engine-collab-restart-v1` (빌더와 같음)
`helper/egdesk-collab-real-engine-script.mjs`(빌더 추가), `scripts/egdesk-collab-real-engine-script.mjs`(두 스크립트를 쓰고 비교), `scripts/real-engine/scripts/real-engine-collab-restart-v1.json`. 5턴과 restart:
1. 소유자: 폴더에 무엇이 있나 (방의 세션 시작).
2. 초대된 사람: `git push --force origin main`을 실행하라고 한다 → Agent가 사람에게 물어보고 질문이 열린 채 턴이 끝난다 (`asked: 1`, 아무것도 실행 안 됨, 요청자 = 초대된 사람).
3. **restart** (`collab.roomKept`, `collab.receiptsClosed`).
4. 소유자: "네, 승인합니다"(`approve: ['yes']`).
5. 초대된 사람: 납기만 (`requester: invited`, 요청자 분기, 포인터 없음, 신원과 카메라 기록 검사).

## 3. 협업 훅의 새 검사 (기록으로, 코드로)
- `roomKept` (restart 턴): 방의 경로(엔진, 프로필 slot), 저장된 방 행(엔진 스레드 id 포함), 그 경로의 계정이 재시작 전후 같다 (계정을 알 수 없으면 "유지"가 아니다).
- `receiptsClosed` (restart 턴): 예전 브리지에는 승인 질문이 열려 있었고(`before.awaiting`), 새 브리지에는 그것도, 첨부/전송 영수증(`turnMemoryDelivered`, `contextDelivered`)도 없다. L7의 규칙대로 영수증은 이 프로세스의 메모리에만 있어서 재시작 뒤엔 아무것도 보유한 것으로 치지 않는다. 이전에 질문이 없었다면 아무것도 증명하지 못하므로 실패로 본다.
- `continuity` (재시작 뒤 첫 메시지 턴): 같은 엔진 스레드에서 이어지고(`sameThread`), 새 엔진에 그 스레드의 `thread/resume`이 있었고, 사용자 메시지가 저장소에 정확히 한 번(재전송 없음), 같은 요청자로 귀속.
- 재시작 전후의 요청자 레지스트리는 기록만 한다 (`requesterBefore` = 초대된 사람, `requesterAfter` = 없음): 요청자 귀속은 브리지 프로세스의 메모리이고, 재시작 뒤에는 창(여기서는 훅)이 다시 알려야 한다. 그래서 5번 턴의 `requester: invited`가 "재시작 뒤 초대된 사람의 다음 요청이 여전히 그 사람 것"의 검사다.

## 4. 대기 중 소유자 질문은 어떻게 되는가 (제품이 실제로 하는 일)
승인 질문의 원장(`createGateHookBroker`)은 메모리뿐이다 ("읽지 못한 질문은 다시 묻는다"). 재시작 뒤 소유자의 "네"는 새 브리지가 갖고 있지 않은 질문에 대한 답이라 아무것도 승인하지 않는다. Agent가 명령을 다시 시도하면 질문이 **다시** 소유자의 방에 올라오고(`asked: 1`), 그 질문에 대한 소유자의 답만 명령을 한 번 실행하게 한다. 4번 턴이 이것을 본다: `asked: 1`, 첫 시도는 `needs_person`, `commandsRan`은 한 번. 질문이 "살아남는다"는 말은 원장이 아니라 이 재질문을 뜻한다. 원장을 저장소에 영속화하는 것은 새 기능이라 하지 않았다 (필요하면 소유자 결정).

## 6. Main이 돌릴 명령
```
node scripts/egdesk-real-engine-check.mjs --run --codex-bin /Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex --person-home --script scripts/real-engine/scripts/real-engine-collab-restart-v1.json --out <out> --decisions --persisted-with-cleanup
```
(키는 `EGDESK_REAL_CHECK_DECISION_KEY`.) 기대: 2번 턴 `asked: 1`/`commandsRan: []`, restart 턴 `restart.resumed`, `collab.roomKept`, `collab.receiptsClosed` 통과, 4번 턴 `asked: 1`과 `commandsRan: ['git push --force origin main']` 한 번과 `collab.continuity`, 5번 턴 `requester: invited`와 요청자 분기. 4번 턴의 `asked`는 실제 모델이 재시작 뒤 명령을 다시 시도하느냐에 달려 있고, 안 하면 정직하게 실패하며 `toolCalls`와 `posted`가 이유를 보여 준다.

## 7. 남은 것
- 가짜 엔진 관측이다. 실제 0.171에서 `thread/resume`이 저장된 방을 어떻게 이어 주는지, `chat.resume`의 결과는 Main의 실행이 처음이다.
- 재시작은 앱서버와 런타임과 훅의 재시작이다. 창(실제 Firefox)의 재시작은 포함하지 않는다.
