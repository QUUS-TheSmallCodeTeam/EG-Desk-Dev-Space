## 1. 준비 상태를 "이 턴을 돌릴 slot"의 것으로 (U11)

### 무엇이 전역이었나
`browserProvider`, `planProvider`, `annotationProvider`의 `schemaReady`와 런타임의 `qaReady`가 모두 `nativeCapabilities.… && appServerReady`, 즉 **공유 바이너리의 probe와 공유 서버가 떠 있는지**만 봤다. Agent 프로필 계정의 서버에서 도는 턴도 공유 서버가 죽으면 도구를 못 받고, 제한 실행(QA)이 거부됐다. 반대로 프로필 서버가 죽었는데 그 방에 공유 서버의 준비 상태가 그대로 적용됐다.

### 한 일
- 새 모듈 `helper/egdesk-slot-readiness.mjs` (`createSlotReadiness({ shared, profiles })`, `isProfileSlot`):
  - **공유 slot**: 공유 바이너리 probe(`schemaMatch`, `qaReadOnly`)와 공유 서버가 떠 있는지.
  - **프로필 slot**: 그 프로필 **자신의** probe(c22의 `profiles.capabilities(id)`, 로그인·실행 중일 때만 참). 새로 `qaReadOnly`도 바이너리별 probe에 넣었다.
  - 어느 한쪽 서버가 꺼져도 다른 쪽 답은 바뀌지 않는다. 읽기가 던지거나 비어 있으면 "준비 안 됨"이다.
- 런타임:
  - **세 곳의 `qaReady()`가 모두 `qaReady(slot)`**이다(전송 입장, 스레드 시작, 재개). 브리지는 `slot => slotReadiness.qaReady(slot)`.
  - 컨텍스트 외의 모든 도구 provider에게 `specs(route)`와 `prepare(body, route)`로 **이 턴의 slot**(`{ engineId, engineProfileId }`)을 넘긴다. 컨텍스트 provider는 전체 authority를 그대로 받는다.
  - slot은 **run 자신의 경로에서** 온다(`collectToolSpecs(..., { slot })`, 준비 단계는 `context.route`). 처음 구현은 slot을 컨텍스트 authority에서만 읽었는데, 컨텍스트 provider가 없는 런타임에서는 authority가 undefined라 프로필 방도 공유 slot으로 판정됐다. 종단 테스트가 이를 잡아 고쳤다.
- 브라우저, plan, annotation provider가 `schemaReady(route)`를 부른다. 브리지의 네 곳과 컨텍스트(c22)는 같은 모듈을 쓴다.
- 컨텍스트 런타임 하나를 추가로 고쳤다(§3 B8): "붙인 자료가 바뀌었다"는 안내가 방 자신의 계정이 아니라 기본 로그인 키로 찾아져 프로필 방에는 전혀 가지 않았다.

### 테스트
- `helper/egdesk-slot-readiness.test.mjs`(5개):
  1. 모듈: 공유 서버 down + 프로필 up, 프로필 down + 공유 up, 다른 바이너리, 도구 계약은 있으나 QA 계약이 없는 프로필, 읽기 실패. 각 slot은 자기 서버로만 답한다.
  2. **종단(실제 런타임, 실제 plan·annotation provider, 가짜 서버 둘)**: 공유 서버가 죽어 있어도 프로필 방의 `thread/start`는 plan·annotation 도구를 가진다. 공유 방은 도구가 없다. 반대로 프로필 서버가 죽으면 프로필 방만 없다.
  3. 제한 실행 gate: 게이트는 **방의 slot**을 받고, 그 slot의 상태로만 거부한다(`QA_POLICY_UNAVAILABLE`, 거부 시 스레드 0). 공유가 죽어도 프로필 방은 통과하고, 프로필이 죽으면 프로필 방만 거부된다.
  4. 브라우저 provider: slot별 도구 제공과 `prepare`의 `BROWSER_TOOLS_UNAVAILABLE`.
  5. 소스 고정: 브리지가 모듈을 쓰고, `schemaReady: () =>`나 `qaReady: () =>`처럼 slot을 무시하는 콜백이 없고, 런타임의 세 `qaReady(slot)` 호출과 provider 힌트가 있다.
- 기존 c22 테스트 두 개(`capabilities` 객체 기대값)에 `qaReadOnly` 필드를 더하고, `codex-bridge-http.test.mjs`의 `isProfileSlot` 고정을 "모듈이 정의하고 브리지가 가져옴"으로 갱신했다(원래 문구는 같고 위치만 옮겨짐).

## 3. 권장하는 다음 순서
1. **W1**(창의 요청 등록과 울타리를 방의 계정으로): 사용자가 프로필 방에서 가장 자주 만나는 증상이다(기본 로그아웃이면 자료 읽기와 증거 패널이 막힘).
2. **B3**(브라우저 binding의 소유자를 slot별로): 이번 변경으로 도구는 제공되지만 기본 계정 변화에 run이 끝난다.
3. **B2**(slot별 reader): 쿼터와 가용성 결합이라 소유자가 "프로필 방의 읽기가 어느 계정 쿼터를 쓰는가"를 정해야 한다. 추천: 방의 계정.
4. B4는 소유자 결정 (3)의 작업 계정 확인과 함께.
