## 2. 결정과 근거

### 2.1 포인터 (과제 1): 코드가 아는 것은 코드로

`pointerBlocked(facts)` 가 막는 이유를 닫힌 값으로 돌려준다. 하나라도 걸리면 질문이 없다.

| 이유 | 코드가 쓰는 사실 | 비고 |
|-|-|-|
| `no_fact` | provider 의 attention 사실 | |
| `in_view` | 배치 런타임의 기하 (이미 시야 안) | c15 부터 |
| `no_route` | presence 와 참여자 (`pointerRoute`): 그 사람이 자리에 없거나, 본인 대화가 없거나, 다른 사람이 있는 대화뿐 | c13 부터. 이때 사실은 보관된다 |
| `pointed` | 게시한 포인터 기록, 또는 지금 쓰는 중 | 쓰는 중 표시는 이번에 추가 (같은 사실에 작성 턴 두 번 방지) |
| `declined` | 판단기가 이 사실에 "필요 없다"고 이미 답함 | 이번에 추가 |
| `bound` | 창당 2개 | |

**hard 실패한 "아무도 없음"은 제품이 원래 묻지 않는 순간이었다.** c15 의 반사실 요청이었고, 제품은 `no_route` 로 요청 없이 보관한다. 실측 1.0 은 이것을 모델에 맡기면 안 된다는 증거다. c16 계획 테스트가 실제 런타임에서 이 경우 요청 0, 보관 1 을 확인한다. 시야 안도 요청 0 이다.

모델에는 코드가 모르는 것만, 항목 하나씩 따로 인용해 묻는다 (R4).

| 질문 | 인용 | 언제 묻나 |
|-|-|-|
| `message__pointer` | 그 작업의 run 이 게시한 답 ("The message about the finished work") | 종류가 result 이고 답이 있을 때. 결정·질문 종류는 정의상 사람이 필요하므로 묻지 않는다 |
| `message__told_N` (최대 2) | 포인터가 갈 대화에 그 작업 시작 뒤 게시된 메시지 하나씩 | 그런 메시지가 있을 때 |

코드의 조합(`pointerDecision`):
- `told_N` 중 하나라도 예 → 포인터 없음
- result 이고 `pointer` 를 물었으면 → 그 답을 따름
- 결정·질문 종류, 또는 읽을 답이 없으면 → 포인터 (L4 판단기가 이미 가리키기로 정했다)

함께 바뀐 것:
- **질문이 하나도 남지 않으면 요청 없이 바로 게시한다.** 예: 소유자가 결정해야 하고 그에게 그 뒤 게시된 메시지가 없을 때. 기록에는 `flow: 'pointer'`, `questions: 0` 으로 남는다.
- **판단기가 "필요 없다"고 답한 사실은 다시 묻지 않는다** (`declined`). provider 가 사실을 거둘 때 기록도 지운다. 답이 실패하거나 건너뛰어졌으면 아무것도 정하지 않는다. 이 처리 없이는 같은 사실을 60초에 4번 물었다.
- **포인터 질문만 있는 요청에는 run 재료 블록을 붙이지 않는다.** 위치·자리·사람 문장이 요청에서 빠졌다. 계획 테스트가 확인한다.
- "이미 알림" 경우: 코드는 무엇이 게시됐는지는 알지만 그 문장이 위치를 말했는지는 모른다. 그래서 게시된 메시지를 하나씩 인용해 `told_N` 으로 묻는다.

### 2.2 정지 (과제 2): 코드 규칙으로

두 본문을 읽었다.
- 25초 침묵: 도구 없음, 추론 항목 닫힘, 엔진 24초 무소식, 메모 "변경 파일을 확인하는 중" → stalled **.28**, note .88
- 70초 추론: 추론 항목이 열린 채 60초 무소식 → stalled **.78**, note .94

| 근거 | 내용 |
|-|-|
| 숫자를 따라감 | stalled 답은 무소식 초(24 → 60)를 따라 올라갔다 |
| 숫자 아닌 사실은 거꾸로 작용 | "추론 중"(정상적으로 오래 걸림의 근거)이 있는 쪽이 더 높았다 |
| 말할지는 이미 정해짐 | 두 경우 모두 note 가 .88 / .94 로 예였다. stalled 는 문구만 고른다 |
| 출력은 이미 판단됨 | 도는 명령의 출력은 L5 판단기가 실제 tail 을 읽어 상태를 정하고(13/13), 그 상태가 재료 문장에 들어간다. 따로 물을 것이 없다 |

결정: stalled 질문을 없앴다. 코드가 무소식 기준(20초, 추론 중이면 60초)에 닿았다고 보고 note 가 예면 종류는 `stalled` 다. 쓰기 실패 시 고정 문구 대체도 그대로다.

선택형 시절에는 "처음 나온 선택지는 바로 물을 수 있다"는 규칙이 정지 시점에 새 요청을 일으켰다. 그 성질을 지키려고 하트비트 계약에 예/아니오 질문의 `topic`(닫힌 라벨)을 추가했다. 처음 보는 topic 이면 바로 묻는다. note 의 topic 은 지금 대변하는 종류들(`explain_wait_stalled` 등)이라, 정지 기준에 닿는 순간 새 topic 이 되어 바로 묻는다. 새 포인터 사실도 새 topic 이다. 기존 질문은 바뀌지 않는다.

### 2.3 20초 note .62 (과제 3): 하한을 코드로

같은 생각만 하는 재료에서 3초 .35, 12초 .45, 20초 .62 였다. 바뀐 것은 초 숫자뿐이므로 모델은 시계를 읽고 있었다 (R3).

| 규칙 | 값 |
|-|-|
| 대상 | 도구 단계가 없고 엔진이 보이게 활동 중(무소식 20초 미만)인 run |
| 하한 | 첫 진행 알림을 30초부터 (`thinkingNoteMs`) |
| 예외 | 엔진이 20초 이상 무소식이면 20초부터 (정지 경로). 도구 단계가 있으면 10초부터 (그대로) |
| 예 기준 | 0.8 그대로 (낮추지 않음) |

"시간에 민감한 요청이면 예외"는 넣지 않았다. 요청 내용이 같은 시각의 답을 바꾼 사례가 측정에 없고, 넣으면 생각만 하는 run 마다 질문이 하나 는다.

부수 효과: 20~30초 사이에 첫 도구를 시작하는 run 은 첫 요청이 20초 → 25초로 늦춰지고, 두 번째도 40초 → 45초로 밀린다. 그래서 `need-command-40s` 는 `need-command-45s` 로 다시 잰다. 브라우저 다단계 작업은 엔진이 조용하므로 20초에 묻고 40초 일정도 그대로다.

## 6. 남은 것과 한계

- **결정형 포인터는 하트비트 판단 없이 게시된다.** L4 판단기의 "가리킨다" 판단과 코드 전제조건만으로 정한다. 게시 전 초안 검사는 그대로 거친다.
- **보관된 포인터는 원 작업의 답을 소유자 대화의 판단 요청에 인용한다.** 원 run 의 전송 관문(`run_text`)을 따로 확인한다. 작성 지시문에는 여전히 닫힌 문구만 간다.
- **told 후보의 시각 기준은 원 run 의 첫 메시지 시각(벽시계)이다.** 시계가 뒤로 가면 후보가 빠질 수 있다.
- **브라우저 작업 run 은 엔진이 조용해서 하한 예외(무소식 20초)에 걸린다.** 20초에 묻는 것은 c15 와 같다. 의도와 맞는지는 실측 뒤 보아야 한다.
- 승인이 필요한 새 사용자 노출 문구는 없다. 이전 대기 건은 그대로다 (`FLOW_COPY.stalled` 등).
- c14 의 열린 끝은 그대로다: `/chat/session/close` 호출처 없음 (L2), L4 가 `nudge()` 를 부르지 않음.
