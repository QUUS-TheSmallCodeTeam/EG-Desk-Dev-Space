## 1. 왜 [측정]
같은 요청 본문은 같은 답을 낸다 (70/70, c23). 그래서 같은 여정을 한 번 더 돌려도 본문이 같은 요청은 모델의 새 표본이 아니다. "켠 채 전체 실행 두 번 통과" 규칙이 증거가 되려면 **다른 입력**이 필요하다. 변형은 각 단계의 의도와 기대 결과를 그대로 두고 모델이 읽는 것만 바꾼다.

## 5. dry run (V1 이 보낼 계획) [측정]
`--switch action-relevance` 를 켠 채, 전송 없음. 한도 선언: 계획 파일의 `ceiling` (V1 70,000 토큰, 요청 70개). 한도는 **전송에서만** 막는다: `--send` 에서 더 높은 `--token-ceiling` 은 보내기 전에 거부되고 (테스트), dry run 은 한도에서 멈추지 않고 추정치를 선언한 한도와 비교해 출력한다 (`overDeclaredCeiling`).

| 계획 | 한도 | 스크립트 dry run: 요청 / 추정 토큰 | hard (통과 / 실패) | 단계 | v7b 답을 재생한 dry run: 요청 / 추정 | 실제 토큰 예측 |
|-|-|-|-|-|-|-|
| 기반 v7 | - | 55 / 68,992 | 65 / 1 | 16 | 50 / 61,782 | 66,739 (v7b 실제 66,698) |
| **V1** | **70,000 / 70** | 60 / 75,183 | 65 / 1 | 16 | **51 / 64,517** | **69,770** |
| V2 | 76,000 / 75 | 56 / 70,821 | 65 / 1 | 16 | 52 / 65,826 | 71,230 |
| V3 | 76,000 / 75 | 66 / 85,524 | 65 / 1 | 16 | 54 / 66,136 | 71,591 |

- 실패하는 hard 하나는 모든 계획에서 같다: `s4.no-page-for-the-action` (action 규칙은 스크립트 이중이 구현하지 않는다. 실제 실행에서는 모델이 정한다. 기반 v7 의 dry run 도 똑같이 이것 하나가 실패한다).
- soft 미달: 기반 `s2.triage-need`, `s4.no-unrelated-pages`. V1 과 V3 은 `s9.packet` 이 하나 더 있다: 이중이 "배포 끝났다" 류 말에서 글자쌍(bigram) 겹침으로 A사 페이지 (`a-meeting`, `a-decision`) 를 골랐기 때문이다 (soft). 실제 모델의 판단이 아니다.
- **토큰 예측의 방법**: 기반 여정 v7b 의 실제 결과에서 계열별 (보고된 토큰 / 추정) 비율을 구하고 (draft_check 1.11, memory_fetch 1.14, briefing 1.13, heartbeat 1.01 등), v7b 의 답을 재생한 dry run 의 요청마다 곱했다. 기반에 적용하면 66,739 로 실제 66,698 과 같다. V1 은 69,770 이다. 스크립트 dry run 은 메모리 페이지를 실제의 약 두 배로 가져와서 (fetch 20개 대 실제 9개) 추정이 실제보다 크다.
- **V1 의 한도는 빠듯하다**: 예측 69,770 은 70,000 의 0.3% 아래다. 예측의 약 2,000 토큰은 재생이 미끼 페이지 때문에 맞추지 못한 요청 하나 (스크립트가 대신 답함) 에서 나온다. 미끼 없이 재생하면 62,399 추정, 예측 67,428 이다. 실제 실행이 한도를 넘으면 마지막 단계 (s12) 의 일부가 실행되지 않는다 (`stopped`/`not_run`, 한도 거부는 요청 전에 일어난다). 여유가 필요하면 한도를 올려 다시 쓰면 된다 (V2, V3 의 한도 76,000 은 예측 + 약 6%).
- V1 대신 V2/V3 를 보낼지는 owner 가 정한다. Main 이 정한 "70,000 이하" 에는 V1 만 닿는다.

## 6. 검증한 것 (테스트 12개)
- 변형이 유효하다 (검증기가 모든 주장을 확인: 말 11개와 답변 10개 전부 있고 기반과 다르다, 짧은 말 있음, 리네임이 prefix 를 안 바꾸고 주제어를 지킴, 미끼는 기반 페이지가 아님, 순서 제약).
- 세 변형이 기반과 서로 어떤 말도 공유하지 않는다 (사람의 말 11개, 답변 10개 모두 4개 실행에서 서로 다름), 그래프도 서로 다르다.
- 변형 계획 파일 = 생성기 출력 (비교 모드), 로더가 받아들임, 기반 계획의 모든 hard 확인과 같은 id/check/severity/owner/text, args 는 의도한 매핑만 다름 (미끼 id 가 prefix 제외에 더해짐).
- 검증기가 나쁜 변형을 거부한다 (같은 문구, 이스케이프되는 문자, 틀린 kind, 짧은 말 없음, 답변 누락, 주제어 소실, prefix 이동, 중복 리네임, 기반 페이지를 미끼로, 순서 위반 등 18가지).
- 로더가 바뀐 변형, 모르는 변형, 숫자가 아닌 한도, 변형 순서가 아닌 단계 순서를 거부한다.
- `--send` 에서 선언 한도를 넘는 플래그는 키를 읽기 전에 거부된다. 플래그가 없으면 계획의 한도를 쓰고 (70,000 / 70), 낮은 플래그는 받아들인다. 오프라인이라 첫 요청은 가짜 네트워크에서 멈춘다 (테스트가 임시 폴더의 stamp 파일을 쓰도록 했다: 실제 홈을 건드리지 않는다).
- 세 변형의 scripted dry run: 사람이 한 말이 변형의 것이고 기반 말은 하나도 없다, 단계가 변형 순서대로 간다, `answer`/`kept`/`steered` 확인이 변형의 말로 통과하고, 실패하는 hard 는 기반 dry run 과 같은 것뿐이다.

## 7. 한계 [한계]
- **v8**: L2 의 plan v8 (s13 withheld, s14 이후 단계, 한 packet 스위치) 은 int/c14 에 아직 없어서 변형에 없다. v8 이 들어오면 `BASE_PLAN` 을 바꾸고 `--write` 한 다음 `SAYS_KEYS` 에 새 키 (bench, benchFollow) 의 변형 말을 더해야 한다 (테스트 첫 번째가 "기반의 모든 말이 변형에 있다" 를 실패시켜서 알려 준다). 하네스 파일을 L2 도 고쳤으므로 병합 충돌이 날 수 있다 (STEPS 끝 부분, SAYS 근처).
