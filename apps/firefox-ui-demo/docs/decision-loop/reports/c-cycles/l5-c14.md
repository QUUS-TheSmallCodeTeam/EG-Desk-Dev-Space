## 1. 미확인 2가지에 대한 답 (1차 출처)
### (a) 훅이 app-server의 환경 변수를 물려받는가 → **받음(Codex 프로세스 환경의 스냅샷)**
- `codex-rs/hooks/src/registry.rs:84`: `let environment = Arc::new(std::env::vars_os().collect());`. 스레드마다 `Hooks::new`가 Codex 프로세스의 **현재 환경 전체**를 스냅샷으로 떠서 `CommandHookRuntime::new`에 넘김(85-86행).
- `codex-rs/hooks/src/engine/command_runner.rs:490-501`: "Both launchers start with an empty environment. Replay the session snapshot before hook overrides, filtering restricted names from both sources". 스냅샷과 훅 정의의 `env`를 적용하되, `is_non_inheritable_env_var`인 이름만 뺌.
- 빼는 목록 `codex-rs/protocol/src/shell_environment.rs:19-28` `NON_INHERITABLE_ENV_VARS`: `CODEX_EXEC_SERVER_NOISE_AUTH_TOKEN`, `NODE_REPL_AUTH_TOKEN`, `CODEX_GUARDIAN_DECISIONS_API_KEY`, `OPENAI_*` 신원 관련 6개, `SPIFFE`. `EGDESK_*`는 여기에 없음.
- 훅 환경은 `shell_environment_policy`(모델 명령용 필터)를 거치지 **않음**. 위 경로에 그 정책이 없음.
- **결론**: EG-Desk가 app-server를 띄울 때 넣은 `EGDESK_GATE_HOOK_URL`과 `EGDESK_GATE_HOOK_TOKEN`은 그 스레드의 훅에 전달됨. 따라서 과제 2의 재설계 조건("상속되지 않으면")에 해당하지 않음.
- **모델 쪽에서 보이는지(별도 확인)**: 모델이 실행하는 명령은 `populate_env`(`shell_environment.rs`)를 거침. 기본값은 `inherit = All`(`config/src/shell_environment_policy.rs:135`, 123행)이고, **기본 제외**(145-151행)가 이름에 `*KEY*`, `*SECRET*`, `*TOKEN*`이 들어간 변수를 대소문자 구분 없이 뺌. 그래서 `EGDESK_GATE_HOOK_TOKEN`은 **기본 설정에서는** 모델 명령에 보이지 않고, URL은 보임(괜찮음). 이 사실을 상수(`GATE_HOOK_ENV`)와 테스트로 고정함.
- **0600 파일 대안을 평가한 결과(구현하지 않음)**: 공식 권한 문서(https://developers.openai.com/codex/permissions)의 예시 프로필은 "By default, deny read access to all files on disk"를 쓰려면 `":root" = "deny"`를 **직접 설정해야 함**을 보여줌. 즉 기본 `:workspace` 프로필에서는 같은 사용자 소유의 0600 파일도 샌드박스 명령이 읽을 수 있음(샌드박스 문서는 workspace-write를 "can read files, edit within the workspace"로만 설명하고 읽기 제한은 말하지 않음: https://developers.openai.com/codex/concepts/sandboxing. 기본 읽기 범위가 디스크 전체라는 것은 위 권한 예시에서 추론한 것이고, 문서가 직접 쓴 문장은 아님). 따라서 기본 설정에서는 파일 방식이 환경 변수 방식보다 **더 노출됨**. 이를 막으려면 사람의 Codex 설정(deny 규칙)을 고쳐야 하는데, 이는 금지되어 있음.
- **설계 원칙(테스트로 확인)**: 토큰 비밀 유지는 기본 설정에서만 성립하는 방어선임. 그래서 설계는 토큰 비밀에 의존하지 않음.
  - 엔드포인트는 "이 명령이 지금 실행돼도 되는가?"만 답하고 승인을 만들 수 없음.
  - 토큰을 얻은 모델이 check를 위조하면 자기 승인을 소비할 뿐이고, 진짜 훅의 다음 check는 deny됨(fail closed).
  - 위조를 반복해도 stop_asking에 빨리 도달할 뿐임(fail closed).
  - 브로커에는 readReply 외에 승인을 기록하는 메서드가 없음.

### (b) `session_id`는 무엇인가 → **루트 스레드의 id(= EG-Desk가 가진 thread/conversation id)**
- 입력 스키마 `codex-rs/hooks/schema/generated/pre-tool-use.command.input.schema.json`: `session_id`, `turn_id`("Codex extension: expose the active turn id"), `cwd`, `tool_name`, `tool_use_id`, `tool_input`, `transcript_path`, `model`, `permission_mode`가 모두 required이고, `agent_id`와 `agent_type`은 선택.
- 값: `codex-rs/core/src/hook_runtime.rs:222-224` `session_id: sess.session_id().into()`, `turn_id: turn_context.sub_id.clone()`. 이것이 `hooks/src/events/pre_tool_use.rs:184`에서 문자열이 됨.
- `codex-rs/core/src/session/session.rs:675-676`: `session_id()`는 `agent_control.identity()`이고, 주석은 "the identity shared by the root thread and all descendant threads". 1007-1015행 "session_id is equal to the root thread's ID": 새 루트 스레드는 `SessionId::from(thread_id)`, 재개(resume)는 rollout의 SessionMeta 값, 서브에이전트는 부모(루트)의 id. 공식 문서의 "Subagent hooks use the parent session id"와 일치함.
- **결론**: EG-Desk의 대화(루트 스레드)에서 `session_id`는 app-server의 thread id, 즉 EG-Desk의 conversationId와 같음. 서브에이전트의 명령에서는 부모 대화의 id가 됨(EG-Desk에서 그 부모 대화가 맞는 대상임).
- `turn_id`: core의 `turn_context.sub_id`임. app-server의 `turn/start` 응답 `Turn.id`(`app-server/src/request_processors/turn_processor.rs:825`)는 `start_or_steer_turn`이 돌려준 turn_id임. `core/src/codex_thread.rs:446-452`(`current_turn_extension_data(expected_turn_id)`가 `task.turn_context.sub_id != expected_turn_id`로 비교함)는 공개 API 차원에서 turn id와 sub_id를 같은 것으로 다룬다는 점을 보여줌.
- **주의**: `turn/start`가 이미 진행 중인 턴에 steer되면(`turn_processor.rs:792` `Steered`) 기존 turn id가 돌아옴. EG-Desk의 `ensureRun`은 그 id를 그대로 쓰고 `turnStarted`는 같은 id에 대해 멱등이므로 문제 없음.

### 그대로 남는 미확인 (솔직하게)
1. `codex_thread.rs`의 `start_or_steer_turn` → `TurnInputSubmission::Started { turn_id }`가 `TurnContext.sub_id`로 만들어지는 **바로 그 줄**은 추적하지 못했음. 위 비교 코드로 강하게 시사될 뿐임.
2. unix 쪽 실행기: `command_runner.rs:482-488`의 `env_clear()`는 `#[cfg(not(unix))]` 아래에 있음. macOS에서 실제로 빈 환경에서 시작하는지는 `codex_utils_pty`(ProcessMode::NewSession)를 보지 않아 미확인임. 다만 어느 쪽이든 스냅샷은 적용되므로 결론(EG-Desk 변수가 전달됨)은 바뀌지 않음.
3. 이것은 **공개 문서의 약속이 아니라 구현**(a0d5b0a6 시점)임. 훅 문서에는 환경 상속이 명시되어 있지 않고, registry.rs 66-67행의 TODO는 스냅샷 위치가 바뀔 수 있다고 말함.
4. 사람이 `shell_environment_policy.ignore_default_excludes = true`를 쓰거나 `set`이나 `include_only`를 쓰면 토큰이 모델 명령에 보일 수 있음. 위 원칙상 승인은 생기지 않음.
5. macOS에서 샌드박스 안의 명령이 같은 사용자의 다른 프로세스 환경(`ps eww` 등)을 읽을 수 있는지는 미확인임. 영향은 4와 같음.
6. 실제 Codex로 한 번도 돌려보지 않았음(금지됨). 즉 모든 결론은 소스 읽기에 근거함.

## 3. 결정 5 구현: 한 번에 하나, 순서대로 (`helper/egdesk-gate-hook-broker.mjs`)
- 한 턴에서 사람이 필요한 **첫** 명령만 `needs_person`(그 턴의 유일한 질문)임. 그 뒤로 사람이 필요한 다른 명령은 `{"status":"queued","position":n,"next":"ask_after_previous_answer"}`로 거부됨(순서가 위치로 보임).
- 턴이 끝나면 질문한 명령은 다음 메시지가 답할 대상이 됨(한 번만 건너감). 대기열은 순서대로 다음 턴으로 넘어가고, 다음 턴에서는 대기열의 머리만 질문이 될 수 있음.
- 넘어간 명령을 모델이 그 턴에서 다시 시도하지 않으면 버림(한 번만 건너감). 무한정 쌓이지 않음.
- 답은 **질문한 그 명령만** 승인함(예/아니오/불명확 모두 그 명령만 소비).
- 테스트(새 테스트 1개): A, B, C가 차례로 거부되면 A=needs_person, B=queued 2, C=queued 3.
  - yes → A만 승인됨.
  - T2: C=queued 2(B가 앞), B=needs_person(A의 yes가 B를 승인하지 않음), A=allow.
  - yes → B만 승인됨.
  - T3: B=allow, A=queued(만료되어 새 명령이 되었고 C가 앞), C=needs_person.
  - no → 아무것도 승인하지 않음.
  - 시도하지 않은 턴 뒤에는 아무것도 넘어가지 않음.
- c13 테스트 2곳은 새 규칙에 맞춰 바꿈: "턴의 마지막 질문에 답한다"가 "첫 질문에 답하고 나머지는 대기열"이 됨. deny와 allow 단언은 모두 유지했고 약화하지 않음.
