## 0. 무엇을 실제 코드로 돌렸나
- **bridge 쪽(실제)**: `CodexChatRuntime`(보류 답변 + 중간 메시지 플래그 on), 실제 `/chat/send`·`/chat/history`·`/chat/state` HTTP 핸들러, 실제 SQLite 채팅 저장소. 엔진은 스크립트된 mock(L3의 `egdesk-held-answers-flow` 시험과 같은 방식), 가상 시계.
- **화면 쪽(실제)**: `EGDeskChatState`(이벤트 reducer, 실행 투영, 기록 복원)와 Surface 소스의 다음 구간을 vm에서 실행 — `threadBusy`, `syncProtocolRun`, `updateThreadById`/`appendMessageToThread`, `createCodexMessage`, bridge 메서드 `setDraft`/`retryRun`/`sendMessage`, 작성창의 전송 버튼 규칙·제출·keydown 핸들러.
- **마운트하지 못한 것(시험 안의 대역)**: `mountCodexHUD`의 말풍선 DOM 루프(건너뛰는 규칙 한 줄을 소스에서 확인하고 시험에서 그대로 따름), 첫 메시지의 전체 전송 경로(같은 `ChatState` 호출로 접수), 프로필 카탈로그, `normalizeThreads`(busy 두 줄만 따름).
- 합성 하네스 관찰이다. 설치된 앱, 실제 app-server의 `turn/steer`, 실제 화면의 프레임 타이밍은 검증하지 않았다.

## 1. `[보기 추천]` — 사용자 결정 전까지 숨김 (기본 OFF, 삭제하지 않음)
- 플래그: bridge 환경 변수 `EGDESK_CHAT_CHOICE=on`. 켜져 있을 때만 `/v1/state`의 `capabilities.chat`에 `'choice'`가 들어가고 `/chat/choice` 경로가 열린다(`codex-bridge-server.mjs:515, 1001, 1092`). 꺼져 있으면 경로는 404 `CHAT_CHOICE_DISABLED`.
- 화면: HUD가 컨트롤러에 `enabled`를 넘긴다. 꺼져 있으면 컨트롤러가 trigger·panel·hint 노드를 **내주지 않아** footer에 그려지지 않고(`eg-desk-surface.uc.js:12728`), 범위 게이트 `chatChoiceScope`가 맨 앞에서 `null`을 돌려줘 어떤 chooser 요청도 만들 수 없다(`:17411`).
- 시험(양쪽 상태): 꺼짐 — capability 없음/`null`/빈 목록/`'choice'` 없는 목록에서 노드 없음·scope `null`·상태 조회 0·POST 0, 떨어진 노드를 눌러도 열리지 않음, 추천이 떠 있는 중 꺼지면 패널이 사라짐. 켜짐 — 기존 chooser 시험 전부(고정 데이터에 `chatCapabilities: ['choice']`를 넣어 "플래그 on"으로 명시)와 새 on/off 왕복 시험.
- 기능 코드와 L1/L2/L3/L5의 chooser 시험은 그대로 남아 있고 플래그 on에서 통과한다.

## 2. 실행 중 작성창 — 열린 중간 질문에 답하기
### 찾은 것
- L3 런타임은 열린 질문을 **메모리에만**(`flow.question.pending`) 두고 화면에 알리는 이벤트·상태가 없었다. 그래서 화면은 질문이 열렸는지 알 수 없었다.
- canon 확인: `EGDESK_PRODUCT_INTERACTION_TRACE_ATLAS.md:893`(진행 중 업무의 작성창에서 추가 지시를 보내면 같은 Run의 가장 이른 다음 모델 호출에 넣는다, 새 Run 없음. 수신·반영 표시는 `Q-AI-05`, `Q-AGENT-18`로 미정), `EGDESK_INTERACTION_AND_ORCHESTRATION_CONTRACT.md:1204-1208`. canon에는 "대기열"이 없다. canon의 일반 형태(질문이 없어도 실행 중 추가 지시를 같은 Run에 넣기)는 **이번에 만들지 않았다**: 런타임이 받는 것은 열린 질문에 대한 답 1회뿐이고, 수신·반영 표시는 사용자 결정이 남아 있다. 그래서 질문이 없을 때는 오늘의 busy 동작을 그대로 둔다.
### 바꾼 것
- 런타임(`codex-chat-runtime.mjs:4706`): 열린 질문을 실행의 공개 상태로 — `run.replyOpen = { messageId }`와 이벤트 `reply.opened` / `reply.closed`(식별자만). 답을 받거나, 최종 답변 검사가 시작되거나, 실행이 끝나면 닫힌다. 스냅샷(`/chat/state`)에도 실린다.
- 런타임(`:1611`): 화면이 답할 실행을 `inRunReplyTo`로 지목한다. 그 질문이 더는 열려 있지 않으면 **아무것도 저장·시작하기 전에** 409 `INRUN_REPLY_UNAVAILABLE`. (지목이 없는 기존 호출은 그대로.)
- 화면 상태(`EGDeskChatState.sys.mjs:29, 1176, 1326`): `runReplyOpen`, `replyRunForThread`(이 DM의 유일한 실행 중 run이 질문을 열었고, resume·첨부 준비·제출 중 요청이 없을 때만).
- 작성창(`eg-desk-surface.uc.js:14814`): 위 상태면 전송 버튼이 켜진다. 텍스트만 — 첨부나 프로젝트 지정이 있으면 기존 busy 규칙. 조합 중 Enter, Shift+Enter는 기존 핸들러 그대로 전송하지 않는다.
- 전송(`:19019`): 일반 사용자 메시지로 즉시 표시(`보내는 중`) → `/chat/send`(+`inRunReplyTo`) → 런타임이 같은 실행에 steer, 일반 사용자 메시지로 저장. 질문당 답 1회(보내는 즉시 작성창은 busy 규칙으로 복귀). 거절되면 말풍선은 `전송 거절됨`, 문장은 빈 작성창으로 되돌아오고, 연결 실패면 `접수 미확인`으로 남기고 다시 보내지 않는다.
- `다시 시도`(`:18919`): 실행에 들어간 답이 아니라 그 실행의 원래 요청을 다시 보낸다(답 말풍선도 같은 runId를 갖게 되므로 필요).

## 3. 완성된 메시지만 표시 — 재현한 문제와 수정
`trace-before.txt` / `trace-after.txt`는 같은 시나리오(질문 → 답 → 최종 답변)에서 이벤트마다 화면 reducer의 메시지 상태를 찍은 것이다.

| # | 재현(패치 전, 원 출력) | 원인 | 수정 |
|---|---|---|---|
| P1 | 보류 답변·중간 메시지가 한 프레임 동안 **두 번 이어 붙은 글**로 그려짐: `message.delta: drew "이 부분은 시간이 좀 걸립니다. 계속 확인하고 있어요.이 부분은 시간이 좀 걸립니다. 계속 확인하고 있어요."`. 플래그 off(오늘)에서도 시작 이벤트 없이 완성된 채 도착한 답은 같다 | 런타임이 완성된 메시지를 `message.started`(전체 글) + `message.delta`(전체 글)로 보냈고 화면은 둘을 더했다. 화면은 이벤트마다 다시 그린다(`if (run) { syncProtocolRun(run); emit(); }`) | 완성된 채 처음 보이는 메시지의 `message.started`는 글 없이 보낸다(`codex-chat-runtime.mjs:5618`). 글은 한 번만 간다 |
| P2 | 사용자가 실행 중에 보낸 답이 **Agent 말풍선**으로 그려짐: `["assistant","complete","스테이징이요"]` | 화면 reducer가 `message.*` 이벤트를 항상 assistant로 만들었다 | 완성된 `role: 'user'` 이벤트는 사용자 메시지로 두고, 이미 보이는 말풍선(요청 ID 일치)에 합친다. 첫 요청 말풍선을 덮어쓰지 않는다(`EGDeskChatState.sys.mjs:1120, 1501`) |
| P3 | 질문이 열려도 작성창이 꺼져 있음(`false !== true`), 재연결 스냅샷에도 상태 없음 | 2절 | 2절 |
| P4 | (경계) 질문이 이미 닫혔는데 화면이 모르고 보낸 답 | 일반 전송 경로로 떨어지면 메시지가 저장된 뒤 409가 날 수 있음(L3 c9가 적어 둔 기존 동작) | `inRunReplyTo` 거절(2절). 시험: 저장소·`turn/start`·steer 변화 0 |

확인된 것(수정 불필요): 보류 중에는 최종 답변의 어떤 글자도 화면 상태에 없다(엔진이 세 조각으로 스트리밍해도). 작업 표시(`Agent 작업 중`)는 보류 내내 유지되고 답변이 나타난 프레임에서도 아직 떠 있으며 `run.completed`에서 사라진다(답변 전에 표시가 먼저 사라지는 틈 없음). 중간 메시지는 순서대로 일반 완성 말풍선으로 들어간다.

복원: 새 화면이 실제 `/chat/history/threads` + `/chat/history`를 읽어 `normalizeLocalHistoryPage` → `hydrateLocalChatThread`로 복원하면 `user → 질문 → user 답 → 최종`이 실시간과 같은 순서·역할·글로 나온다. 스트리밍 상태 없음, 작업 표시 없음, 답 열림 없음. 재연결 스냅샷(`/chat/state`)도 열린 질문과 답의 역할을 유지한다.

## 5. 손댄 사용자 문구
- **새 라벨·새 문구 없음.**
- 기존 문구를 새 자리에 다시 쓴 것(승인 확인용 목록): 실행 중 답이 거절됐을 때 전송 오류 줄에 `아직 보낼 수 없습니다.`(기존: 작성창 차단 안내), 연결 실패 때 `접수 여부를 확인하지 못했습니다. 자동으로 다시 보내지 않습니다.`(기존 문장의 앞부분). 말풍선 상태 `보내는 중`·`전송 거절됨`·`접수 미확인`, 버튼 제목 `요청을 보내는 중입니다.`·`보내기`, 작업 표시 `Agent 작업 중`은 기존 그대로.
- 수정한 기존 시험 고정 데이터: chooser 시험 7개 파일에 `chatCapabilities: ['choice']` 한 항목씩(플래그 on 명시).

## 6. 철학 점검
- **사용자는 그냥 말한다(D1 패러다임)**: 보기를 채우게 하는 UI는 기본으로 보이지 않는다. Agent가 일하다 묻는 질문에는 평소 작성창에 평소처럼 답하면 되고, 그 답은 같은 실행에 들어간다(새 실행·새 버튼 없음).
- **보이는 것은 완성된 것**: 조각이나 이중으로 붙은 글이 한 프레임도 그려지지 않는다. 기다리는 동안은 기존 작업 표시가 자리를 지킨다.
- **사용자의 말은 사용자의 것**: 답이 Agent 말풍선으로 바뀌거나 첫 요청을 덮지 않고, 받지 못한 답은 조용히 사라지지 않고 작성창으로 돌아온다.

## 7. 한계와 다음
- 말풍선 DOM 루프는 마운트하지 못했다. 완성 직전 한 프레임은 상태가 `streaming`인 채 **전체 글**을 가진다(조각은 아님). 실제 화면에서 점 표시가 겹치는지는 설치 앱에서 봐야 한다.
- 실제 app-server에서의 `turn/steer` 수락·반영은 L3와 마찬가지로 미검증.
- 질문 없이 실행 중에 보내는 추가 지시(canon ATLAS:893의 일반 형태)는 만들지 않았다. 수신·반영 표시(`Q-AI-05`, `Q-AGENT-18`) 결정이 먼저 필요하다.
- 답은 텍스트만, 질문당 1회. 첨부가 걸려 있으면 답 전송이 막힌다(안내는 기존 `요청을 보내는 중입니다.`라 이유가 정확하지 않다 — 문구가 필요하면 승인 대상).
- 실행 중 지목 없는 일반 `send`가 메시지를 저장한 뒤 409를 내는 기존 동작(L3 c9 기록)은 그대로다. 화면에서는 닿지 않는다.
- 다음 시뮬레이션 제안: (1) 답을 보낸 직후 사용자가 `중지`를 누르는 경합, (2) 질문이 열린 채 방을 옮겼다 돌아왔을 때 작성창 상태, (3) 설치 앱에서 완성 직전 프레임과 작업 표시 겹침.
