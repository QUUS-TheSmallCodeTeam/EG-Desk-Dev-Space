# L1 (lane/c1-restored-dm): 복원된 기존 DM에서 `[보기 추천]` 다시 쓸 수 있게 하기

커밋: `6a44f31` (branch `lane/c1-restored-dm`, base `loop-base` 1991d7d)
모든 관찰은 **synthetic harness** 기준이다. 설치된 실제 앱 검증은 하지 않았다.

## 1. Sim 여정 (새 파일 `apps/firefox-ui-demo/scripts/egdesk-chat-choice-restored-dm.test.mjs`)
복원된 방은 제품 자체 함수 쌍 `ChatState.detachNativeThread -> reconcileNativeThread`로 만들었다. Surface 복원 경로(`eg-desk-surface.uc.js` ~15888)와 같은 쌍이다. 권한이나 binding을 임의로 주입하지 않았다. 실제 `/chat/send`, `/chat/resume`, `/chat/choice`는 production HTTP handler + runtime + SQLite로 처리하고, Decisions와 구독 RPC는 mock이다. 런타임 프로세스 재시작은 모사하지 못했다. resume은 같은 store 위에 보냈다.

| 단계 | 상태 | 게이트 결과 (패치 전 = 패치 후, 5단계부터 다름) |
|---|---|---|
| 1 복원 직후, 로그아웃 | `held=true`, `bindingState=awaiting-identity` | scope null, trigger 숨김, 일반 전송 막힘. 안내문: "이 방을 시작한 계정을 확인하지 못해 이어서 보낼 수 없습니다..." |
| 2 같은 계정 재인증(reconcile) | `bindingState=verified`, `conversationId` 복구, **`retainedNativeBinding`은 그대로 남음**(reason은 `awaiting-identity`로 stale) | `nativeBindingHeld=false`, canResume=true, 일반 전송 게이트 열림 |
| 3 `/chat/resume` | 200, conversationId 일치 | - |
| 4 `[보기 추천]` | **패치 전: scope null, trigger 숨김.** 패치 후: scope 있음, trigger 표시 | 숨긴 게이트는 `chatChoiceScope`의 `thread.retainedNativeBinding` 단독 조건 |
| 5 검토→확정 | mock Decisions 1회, `EG-Desk 추천: 일정 공지 · 실행하지 않음` | 구독 turn 0 |

## 2. 문제
- `eg-desk-surface.uc.js:17258` (패치 전): `|| thread.retainedNativeBinding`가 **값이 있기만 하면** 거부한다. 그런데 owner 확인 성공 경로(`EGDeskChatState.sys.mjs:592-605` `reconcileNativeThread`)는 `conversationId`와 `verified`만 복구하고 retained 참조를 지우지 않는다. 그래서 확인과 resume이 모두 성공한 방에서도 `[보기 추천]`이 영구히 숨겨진다. 되살릴 경로가 없다. 같은 방의 일반 전송은 열려 있어서 화면 간에 모순이 생긴다.
- 원래 실패 출력(`$EV/before-patch.tap`): `chatChoiceScope admits the restored, verified, resumed DM` / `expected: true actual: ~`. 대조군 `e: control`도 같은 이유로 실패했다.
- 부가 관찰(수정하지 않음): 재검증 뒤 retained의 `reason`이 `awaiting-identity`로 stale하게 남는다. 숨은 UI에서는 안 보이지만 `chat-retained-binding` 렌더(4879)는 `nativeBindingHeld`일 때만 그린다.
- 이 guard의 기원: `git log -S` 결과 `484ba33`("Route reviewed choices in an existing Codex DM...")에서 chooser와 함께 들어왔다. 주석이나 canon에 retained를 영구 금지한다는 근거는 없다. 같은 커밋이 추가한 Atlas(`ideas/confirmed/EGDESK_PRODUCT_INTERACTION_TRACE_ATLAS.md:305`)는 "기존 대화가 같은 구독 계정에서 **확인된 경우**에 쓸 수 있다"고 쓴다. 코드가 canon보다 엄격했다(복원 시나리오 누락).

## 3. 개선 근거
- 내부: Atlas:305(확인되면 사용 가능), 같은 파일의 일반 전송 게이트 `nativeBindingHeld`(14029, 14662-14667). 코드의 다른 모든 곳(1356, 2014, 4485, 15120, 18017, 18546 등)은 retained 값이 아니라 `nativeBindingHeld(thread)`(= retained && !conversationId)로 "보류"를 판정한다. 이 한 곳만 어긋나 있었다.
- 외부:
  - OWASP Authorization Cheat Sheet (https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet): "deny by default"와 "매 요청 권한 검증" -> 완화는 하되 기본 거부를 유지한다. 허용 조건을 명시적으로 열거한다(owner verified + resumed + 같은 계정 + 쌍 일치). 이 출처가 **쌍 일치 검사를 추가하기로** 결정했다. retained 값을 무조건 신뢰하지 않는다.
  - secdoc "Proving Least Privilege with Denial Tests" / NIST SP 800-53 AC-6 (https://secdoc.tech/proving-least-privilege-with-denial-tests): 승인 identity의 통과(긍정) 테스트와 다른 identity, 부정 입력의 실패(부정) 테스트를 한 묶음으로 쓰라고 한다. 이 출처가 **negative sim 구성**을 결정했다.
  - Microsoft HAX G11 (https://www.microsoft.com/en-us/haxtoolkit/guideline/make-clear-why-the-system-did-what-it-did): 추천이 왜 나왔는지 접근 가능해야 하고 과신 위험도 있다. `[이유 묻기]`는 기존대로 일반 전송 게이트 뒤에 두었다.
- 결정 요약: 추천 권한(Decisions 호출, binding 불필요)과 이유 질문(구독 conversation 사용)을 분리한다. 추천 노출은 "같은 방의 일반 전송이 열릴 조건"과 같게 하고, `[이유 묻기]`->`[보내기]`는 변경하지 않았다.

## 4. 패치 (`eg-desk-surface.uc.js` +6/-1)
`thread.retainedNativeBinding` 단독 거부를 다음으로 대체했다.
1. `ChatState.nativeBindingHeld(thread)`이면 거부(owner 미확인, 계정 불일치, 보류).
2. retained가 있으면 `conversationId`, `clientThreadId`(=`clientThreadBinding`), `accountKey`(=`bindingAccountKey`)가 현재 binding과 모두 일치할 때만 허용.
- 그대로 유지: `stateless/startStateless/executionBounded` 거부, `readiness.ready`, `canResumeNativeThread`, access.state, busy, draft 일치, built-in template Agent 조건 등.
- 새 파일: `scripts/egdesk-chat-choice-restored-dm.test.mjs` (+547, 3 tests; 앞 ~310줄은 roundtrip-v3 harness 복사).

## 6. 철학 점검
"사용자의 선택, 기록, 권한을 보존하고, 모델 제안과 승인된 실행을 분리한다." 사용자는 키를 저장한 뒤 같은 기존 DM에서 추천을 쓰려 한다. 복원 방이 이미 일반 전송을 허용하는데 추천만 숨기면 화면에서 발견하고 끝낼 수 없다. 이번 변경은 그 방을 새 방으로 보내지 않고 같은 DM에서 열되, 허용 조건을 owner verified + resume + 같은 계정 + 쌍 일치로 좁게 열거했다. 추천은 계속 "실행하지 않음"이고 `[이유 묻기]`는 draft만 만들며, 전송은 사용자의 일반 `[보내기]`뿐이다.

## 7. 실제 앱이 필요한 것 / 한계
- 실제 설치 앱의 재시작, 실제 Codex 로그인 이벤트 순서, 실제 `/decision/status`는 검증하지 못했다. HUD 전송 버튼은 같은 술어를 복제해 평가했다(실제 버튼 슬라이스를 장착하지 않음).
- resume은 런타임 재시작 없이 같은 store에 보냈다.
- 이 harness에서 project default는 "none 확인" fixture이며 binding이 바뀌면 다시 키를 맞춰 줘야 했다(reconcile이 binding을 원래 쌍으로 되돌리기 때문). 실제 앱에서 project 읽기가 binding 변경 뒤 재수행되는지는 설치 앱에서 확인해야 한다.

## 8. 다음 sim 제안
복원된 DM에서 키를 **계정 설정에서 저장한 직후**(status가 off, unconfigured에서 on으로 바뀜, `choiceSettingsGeneration` 증가) 열린 패널과 초안이 어떻게 되는지, 그리고 `reconcile` 후 stale `reason: awaiting-identity`가 재복원 때 다시 `detach`되어도 쌍이 보존되는지. 이어서 실제 HUD 전송 버튼 슬라이스를 장착한 end-to-end.
