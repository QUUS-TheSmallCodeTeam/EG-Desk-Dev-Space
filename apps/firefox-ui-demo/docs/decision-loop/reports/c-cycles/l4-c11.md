# L4-c11 보고서: 브리핑 흐름의 주관 모델 엔진 (L3 internal turn 위), 답변·제안 순서, 종료된 실행에서의 발행

브랜치 `lane/c11-briefing-engine` (기준 `int/c10` f57b0cd). 커밋 `753b10c`(시험·지원 모듈), `59b28eb`(구현). 합성 하네스 결과이며 설치된 앱 검증이 아니다.

## 1. 엔진 어댑터 (`helper/egdesk-briefing-engine.mjs`, 신규)
- `createBriefingEngine({ runText, report, limits })` → `engine(request)`. 흐름이 요구하는 세 가지 요청을 처리한다: `briefing_design`, `briefing_redesign`(점검 findings 또는 무효 사유 포함)·`briefing_redesign_inconclusive`, `briefing_component`(새 컴포넌트 본문).
- `runText`는 `CodexChatRuntime.internalText(run, prompt, { timeoutMs })`(신규, L3의 `reviseOnFork`와 같은 방식: `internalTurns.run`으로 그 대화의 **비공개 fork**에서 한 턴, 최종 텍스트만 회수). 즉 **답변을 쓴 바로 그 모델**이 설계한다. fork의 메시지·활동은 채팅에 들어가지 않고(run 아님), fork의 도구·승인 요청은 L3 설비가 거절한다. `canInternalTurn(run)`(신규)은 엔진의 `threadFork` 능력만 본다.
- 구조화 출력: 응답에서 JSON 객체 하나만 읽고(`parseEngineJson`: 코드 펜스·앞뒤 문장 허용) 닫힌 모양으로 줄인다(`shapeDesign`: title, steps[text, targets(문자열 별칭), emphasis, fallback], newComponents[part, title, summary]; 그 외 키·비문자열 target은 버림). **의미 검증은 기존 검증기 그대로**(`resolveDesign`의 재사용 제약·새 컴포넌트 허용 규칙, `completeBriefingArgs`, 발행 시 `publish()`). 파싱 실패는 null → 흐름이 사유와 함께 재요청 → 한도 후 채팅 답변 유지.
- 한도(`BRIEFING_ENGINE_LIMITS`): 턴당 30초, 전체 100초(마지막 턴은 남은 시간만), 최대 6턴(설계 1 + 재설계 ≤2 + 컴포넌트 본문), 응답 16,000자, 컴포넌트 본문 8,000자, 프롬프트에 넣는 답변 20,000자. 한도 초과 요청은 턴을 쓰지 않고 null. `engine.stats()`는 내용 없는 숫자만.
- 프롬프트(모델 대면, 영어): 비공개 준비임, 도구 금지, 사용자에게 말하지 말 것, JSON 객체 하나만, 나열된 별칭만, `reuse`의 모든 별칭 사용, `newAllowed`가 있을 때만 `new:<part>`, 답변의 언어로 작성. 요청 데이터(별칭·종류·라벨·요약·제약)를 그대로 싣는다(id·좌표 없음, 시험이 확인).
- 가정(실제 앱서버 필요): L3 설비의 가정(fork가 부모의 완료 턴을 복사하는지)은 여기서도 확인 못 했다. 그 가정에 기대지 않도록 **프롬프트에 답변 본문을 직접 넣었다**(같은 모델이 쓴 자기 답변).

## 2. 브리지 배선 (기본 OFF)
- `codex-bridge-server.mjs`: `briefing: briefingDeps({ chat, contexts, enabled: process.env.EGDESK_BRIEFING_FLOW === 'on' })`. `briefingDeps`는 엔진 모듈에 있어 시험이 **브리지와 같은 의존성**을 그대로 마운트한다.
- **켜는 조건이 하나 늘었다(보고)**: 기존 플래그는 크롬 pref `egdesk.briefingFlow === "on"`(+ Decisions 모드 on)인데, 브리지는 그 pref를 읽을 수 없다. 다른 레인의 관례(`EGDESK_DRAFT_CHECK`, `EGDESK_CONVERSATION_FLOW`)대로 브리지 쪽에 환경변수 `EGDESK_BRIEFING_FLOW=on`을 두었다. 없으면 엔진이 없고 경로는 `no-engine`으로 아무 요청도 보내지 않는다. 즉 on 경로는 pref on + Decisions on + 환경변수 on + 그 엔진이 fork 가능일 때만 돈다. 환경변수를 빼고 pref만으로 가길 원하면 `enabled: true` 한 줄이다(Main/사용자 결정).
- 핸들러(`egdesk-board-presentation-http.mjs`): `briefing.engineFor(run, { report })`로 실행별 엔진 생성; **완료된 답변만**(`run.status === 'completed'`, 아니면 `run-not-completed`); **답변당 1회**(`already`); 새 컴포넌트는 본문을 모두 받은 뒤에만 게시(일부만 만들어지는 일 없음). egress는 c10 그대로 공용 게이트 하나.
- 크롬 대기 시간: on 경로 응답 대기 60초 → 150초(엔진 100초 + 판정 몇 번). 응답이 늦어도 발행은 브리지에서 끝나고, 늦으면 크롬은 접기 제안만 놓친다.

## 3. 답변과 브리핑 제안의 순서 (D1: 완성 메시지만) — 선택과 근거
**선택: 답변 말풍선이 먼저 완성된 채로 올라오고, 그 뒤 브리핑 제안이 같은 답변에 붙는다(새 말풍선 없음, 답변 본문 불변).** 보드에 속하는 보고라도 답변을 짧은 안내로 바꾸지 않는다.
- canon: 계약 §8 "Agent는 Answer에 속하는 사용자용 material로 briefing을 제안" / "선택적이고 사용자 제어형"; Atlas M7(1684행~) "Answer는 하나이고 표현은 복수일 수 있다"(Chat projection과 Canvas projection → Answer Briefing); AI-05(1050행) "Answer에 연결된 게시 Briefing이 있으면 `[브리핑 보기]`로 연다". 브리핑은 답변의 또 하나의 표현이지 답변의 대체가 아니다.
- D1: 짧은 안내 말풍선으로 바꾸려면 설계·점검이 끝날 때까지(최대 약 2분) 답변을 붙잡아야 하고, 실패 시 원문으로 되돌려야 한다. 지금 방식은 붙잡지 않고, 어떤 실패에도 완성된 답변이 이미 있다.
- 동작: 크롬은 `run.completed`에서만 흐름을 시작하고, 브리지는 완료된 실행만 받는다. held 모드(L3)에서는 답변이 점검 후 한 번에 올라온 뒤 실행이 끝나고, 그 다음에 제안이 온다.
- 시험: 이벤트 순서 `message.completed`(답변) < `run.completed` < `briefing.published`, 그 사이·이후 새 메시지 0건, fork 프롬프트·설계 JSON·거절된 초안 문구가 어떤 채팅 이벤트에도 없음. 크롬의 실제 reducer(`reduceChatEvent` → `projectRunMessages`)에 같은 이벤트를 먹이면 말풍선은 1개 그대로이고 그 답변에 `briefing`(proposed, 2단계)이 붙으며, 기존 '브리핑 요청' 제안은 사라진다(기존 `[브리핑 보기]` 진입).
- 사용자 결정으로 남김: "보드에 속하면 채팅에는 짧은 안내만" 변형을 원하면 답변 보류 시간(최대 약 2분)과 작업 중 표시가 필요하다. 구현하지 않았다.

## 4. 종료된 실행에서의 발행 (c9에서 추론만 했던 것)

## 7. 확인하지 못한 것
- 실제 앱서버에서의 fork 동작(부모 턴 복사, ephemeral, 도구 거절)과 실제 모델의 JSON 준수율·별칭 준수율. 하네스의 fork 응답은 스크립트다.
- Claude 엔진: `threadFork` 능력이 없으면 `no-engine`. 있더라도 Claude 실행은 브리핑 권한(`publishBriefing`)이 없어 `publish-failed`로 채팅에 남는다(기존 정책).
- 흐름이 도는 동안(최대 약 2분) 화면에 진행 표시가 없다. 표시를 넣으려면 문구 승인이 필요하다.
- 비공개 턴의 비용(주관 모델 호출 최대 6회)은 Decisions 예산에 잡히지 않는다.
- 발행이 중간에 실패하면(본문은 다 받았는데 게시·제안이 실패) 이미 게시된 새 결과가 남을 수 있다(창은 좁혔지만 원자적이지 않음).
- `outcome.next`, 보정 로그의 판정 종류 구분, `stale` 신호는 그대로 미구현.

## 9. 철학 점검
판정은 Decision이, 창작은 답변을 쓴 그 모델이 보이지 않는 곳에서 하고, 사용자에게는 완성된 것만 간다: 먼저 완성된 답변, 그 다음 검증을 통과한 제안. 어떤 실패도 답변을 건드리지 않고, 접기는 사용자가 직접 열어 적용할 때만 일어난다.
