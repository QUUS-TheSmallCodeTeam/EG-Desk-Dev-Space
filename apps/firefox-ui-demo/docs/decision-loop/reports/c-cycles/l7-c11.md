### 1.1 pg-mid 스캔이 헬스체크 페이지를 못 고름
실제 답(요청 `pg-mid-2-scan`, 보기 3개): 헬스체크 3종 체크리스트 **0.37**(미결정), 배포 후 후속 체크리스트 **0.80**(경계에서 선택), 전환 벤치마크 0.01. 미결정이라 "두 번째 보기"로 갔고(`pg-mid-3-expand`) 거기서 같은 페이지가 **0.03**("필요 없음")으로 닫혔다. 첫 턴 스캔(`pg-first-2-scan`)에서도 같은 페이지는 0.40이었다. 사전 분류는 이 실행에서 need .86, record 1로 맞았다.
- 설계 쪽 원인(고칠 수 있음):
  1. 스캔 요청의 보유 목록은 **제목·시간·상태만**("content not repeated")이었고, 사전 분류의 보유 페이지는 내용 앞부분도 보여 줬다(c9에서 사전 분류에만 적용). 판정자는 보유한 계획 페이지가 "헬스체크 3종을 통과해야 한다"고 말하는 것은 알 수 없고, 그 **기준**(연결 풀 응답, 지연 50 ms 이하, 복제 지연 없음)이 보유 자료에 없다는 것도 알 수 없었다.
  2. 질문과 규칙의 문구가 "답하는 데 필요한가"("helps answer the message" / "still needs for its next judgment")로 좁았다. "배포 끝났어"에서 답변 모델이 다음에 해야 할 판단은 말이 아니라 **성공을 판정하고 남은 일을 확인하는 것**인데, 판정자는 "인사하고 축하하는 답"에 필요한 것만 필요하다고 읽었다.
- 모델 쪽(고칠 수 없음, 측정으로 확인): 첫 턴·세션 중간에서 이 페이지에 일관되게 0.3–0.4를 줬다(미결정). 사전 등록의 hard(헬스체크 필수 선택)가 사용자가 말한 시나리오("다음 판단에 필요한 헬스체크 기준")와 일치하는 만큼 틀린 기대는 아니지만, 다른 합리적 해석(계획 페이지가 이미 헬스체크를 언급)도 있어 설계 수정 뒤에도 모델이 같은 답을 줄 수 있다. 그 경우는 모델 거동이다.

### 1.2 j-mid 사전 분류가 need를 0.02로 "no"
요청에 보유 페이지 두 개(설계 초안: PreToolUse 훅 설명, 사용자 발언)의 상태와 내용 앞부분이 있었고, 메시지는 "아까 jev hook 흐름 다시 정리해줘". 판정자는 "보유한 초안이 훅을 다루므로 덮였다"고 본 것으로 보인다(추정).
- 설계 쪽 원인: **사전 분류는 보유하지 않은 저장 페이지가 무엇인지 알 수 없다.** 흐름이 적힌 `jev hook 흐름 메모`(보유 아님)는 판정자에게 보이지 않았다. T6/T4x(c9)에서 보유 내용 노출이 통했던 것은 질문이 **좁은 사실 하나**(롤백 조건)여서 보유 내용에 그 사실이 없다는 것이 드러났기 때문이다. "아까 …다시 정리해줘" 같은 **회상·재정리 요청**은 몇 개의 보유 페이지 앞부분만으로는 "다 덮였다/아니다"를 판단할 수 없다. 이것이 T4/T6 패턴과의 차이다: 노출된 보유 내용은 **좁은 질문의 부재**는 드러내지만 **넓은 요청의 불완전성**은 드러내지 못한다.
- 모델 쪽: 입력이 주어진 만큼은 합리적인 판단이다. 모델 거동의 문제로 보기 어렵다.

## 2. 설계 수정 (`egdesk-turn-memory.mjs`, `egdesk-wiki-reconstruction.mjs`)

1. 사전 분류가 보유하지 않은 저장 페이지를 **제목만**(시간·상태 포함) 본다(`Stored pages that are not held (titles only)`, 최대 80개). 읽을 수 있는 페이지만(범위 필터 뒤)이며 본문·보유 페이지는 없다. 80개를 넘으면 "N more stored pages are not listed"를 붙이고 목록은 **불완전**으로 표시한다. 첫 턴 사전 분류(기록 판정 용도)에는 목록을 싣지 않는다(비용).
2. 새 질문 `tn_recall`: "메시지가 앞서 논의·작업한 것을 가리키며(예: '아까', '지난번', '다시') 그것을 상기·요약·재정리해 달라고 하는가, 새로운 사실 하나나 좁은 세부를 묻는 것이 아니라?" `tn_need` 문구는 목록을 가리키도록 바뀐다(목록이 없을 때는 기존 문구 유지).
3. **건너뜀 규칙**(`triageSkipsFetch`, 채점기도 같은 함수로 실제 답에 적용): courtesy가 결정된 yes면 건너뜀. need가 결정된 no여도 건너뛰려면 **보유 내용 노출 ∧ 저장 페이지 목록이 완전 ∧ recall이 결정된 no**가 모두 필요하다. 그 외는 항상 가져온다. 답: "다시 정리해줘" 같은 요청이 need no만으로 건너뛸 수 있는가? — 아니다. recall이 yes거나 미결정이면 가져온다.
4. 가져오기(첫 턴·세션 중간 공통) 규칙 문구: "페이지는 답변 모델이 이 메시지가 요구하는 것을 **결정·검증·실행**하는 데 도움이 될 때 필요하다(말로 답하는 데만이 아니라). 무언가가 끝났다는 보고라면 성공 판정 방법, 남은 일, 실패했을 때 할 일을 포함한다." 문항마다 반복하지 않고 규칙에 한 번만 둔다(문항 31개에 붙이면 첫 턴 스캔이 약 1k 토큰 늘어난다).
5. 세션 중간 스캔·확장 요청의 보유 목록이 사전 분류와 같이 상태와 내용 앞 200자를 보여 준다("the start of each is shown; the rest is not repeated"). 보유 페이지는 여전히 선택지가 아니고 패킷에도 들어가지 않는다.
6. 보정 로그에 `triage_recall` 질문 추가, 런타임 advisory가 기록한다. 영수증·권한·범위는 불변.
- 비용: 세션 중간 사전 분류 요청이 약 0.8k → 약 1.3–1.4k 토큰(목록 약 +0.4k, recall 질문 약 +0.1k). 첫 턴 비용은 거의 그대로(스캔 규칙 문구 약 +60 토큰).
