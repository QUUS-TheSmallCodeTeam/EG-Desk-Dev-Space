## 1. 턴마다 `thread/resume`이 두 번 나가는 문제

### 두 호출 위치 (`helper/codex-chat-runtime.mjs`, send 경로)

| | 위치 | 하는 일 |
|---|---|---|
| ① | `justRestored`일 때 `restoreThread(... qaOverrides)` | 기록을 hydrate하고 그 thread의 옛 cwd를 알아냄 |
| ② | `!loadedThreads.has(cid)`일 때 `restoreThread(... mergeCeilingOverrides(...))` | 저장된 Agent 프로필, 프로필 전환, computer control off가 있으면 thread를 내려놓고(`releaseThread`) ceiling, computer-off, own-tools 설정을 실어 다시 resume. `thread/resume`은 이미 로드된 thread의 설정을 바꿀 수 없기 때문 |

L2 harness(Agent 프로필 DM)에서 호출 순서를 재생해 확인했습니다. 재시작 뒤 첫 턴은 `thread/resume → thread/unsubscribe → thread/resume → turn/start`이었습니다.

### 두 가지가 겹쳐 있었습니다

1. **재시작 뒤 첫 턴의 resume 두 번**: ②가 확정적으로 일어나는데도 ①이 먼저 같은 기록을 hydrate했습니다. ②가 다시 hydrate하므로 ①은 중복입니다.
   - ①이 필요한 이유는 cwd를 알아내기 위해서뿐입니다.
   - 설정을 읽는 쪽(ceiling, computer-off, `config/read`)은 모두 `overrides.cwd`를 먼저 씁니다. 그러니 send가 cwd를 싣고 있으면 ①이 할 일이 없습니다.
2. **Agent 프로필 DM은 매 턴 `thread/unsubscribe + thread/resume`을 합니다.** 로드된 thread도 마찬가지입니다. 이건 **의도된 설계**입니다. 코드 주석대로 저장된 프로필은 ceiling이 바뀌었을 수 있어 매 턴 다시 적용하고, 매 턴 resume 응답으로 `verifyCeilingNativeThread`가 다시 확인합니다 (AGENT-04). 그래서 이쪽은 건드리지 않았습니다.
   - 같은 설정이면 건너뛰는 방법은 있지만, 매 턴 나오는 ceiling 알림과 확인 결과를 같이 캐시해야 해서 정책 변경과 얽힙니다. 이번 범위 밖입니다.

### 수정

- ②가 확정이고(`!bounded`, Codex, 그리고 `profileEnabled`가 지정됨 / `profileRun`이 있음 / `computerOff`) send가 cwd를 싣고 있으면 ①을 건너뜁니다.
- 건너뛴 경우 **active-run 검사를 ② 뒤에 한 번 더** 합니다. 기록 hydrate가 ②에서 일어나기 때문입니다.
- cwd가 없으면 ①이 그대로 남습니다. 새 대화처럼 ②가 없는 경로도 그대로입니다.
- 결과: `thread/resume → turn/start`. 재시작 후 연속성 확인(c25)도 한 번만 돕니다 (이전에는 resume마다 두 번).

### 테스트 (`scripts/egdesk-resume-count.test.mjs`, 5개)

| 상황 | 결과 |
|---|---|
| Agent 프로필 DM, 로드되지 않은 thread | resume 1번, 설정과 cwd 포함 (전: 2번) |
| Agent 프로필 DM, 로드된 thread | `unsubscribe + resume` 그대로 |
| 로드되지 않은 thread, send에 cwd 없음 | resume 2번 (①이 cwd를 알아냄) |
| 로드되지 않은 thread에 끝나지 않은 run | `RUN_IN_PROGRESS`로 거절, `turn/start` 없음 |
| 연속성 확인 | 한 번 |

- 변경을 빼면 "resume 1번"과 "연속성 확인 한 번" 두 테스트가 실패합니다 (`mutation-check.txt`). 나머지 세 개는 보호용입니다.
- 런타임, 브리지 기존 테스트 535개는 모두 통과합니다.

## 2. real-engine check의 메모리 시드

### 구조: 별도 모듈과 최소한의 등록 지점

`helper/egdesk-real-engine-memory.mjs`가 전부를 가집니다. L5의 check 파일에는 `memory hook`이라고 표시한 줄만 넣었습니다.

| 등록 지점 (check 파일) | 줄 |
|---|---|
| import | 1 |
| preflight: 시드된 메모리는 `--decisions` 필요 | 2 |
| 훅 생성, 엔진 요청 관찰 (`turn/start`) | 2 |
| `ontologyStore.readGraph`가 시드한 그래프를 돌려줌 (없으면 빈 그래프, 이전과 같음) | 1 |
| 메모리 모드 설정과 turn memory 적격성 | 2 |
| 턴 시작과 끝 (`beginTurn`, `finishTurn`), 턴 기록에 `memory` | 3 |

validator(`egdesk-real-engine-script.mjs`)에는 conversation의 `memory` 키와 expect의 `memory` 키, 그리고 모듈의 검증 호출을 추가했습니다. 커밋된 JSON schema도 다시 만들었고, 일치 테스트가 있습니다.

### 스크립트 형식

```
"memory": { "mode": "on" | "advisory", "pages": [ { "id", "title", "body", "time", "status", "links": [ { "to", "type" } ] } ] }
turn.expect.memory: { "attached": [id…], "notAttached": [id…], "noResends": true }
```

- 페이지는 check의 **격리된 data 폴더가 읽는 온톨로지 그래프**가 됩니다. 대화가 시작되기 전에 있고, 다른 곳에는 없습니다. turn memory의 wiki와 컨텍스트 선택이 모두 이 그래프에서 만들어집니다.
- 기대값은 모두 **코드로** 판정합니다. 제품이 엔진에 보낸 `turn/start`의 `additionalContext`에서 읽습니다.
  - `attached`: 그 페이지의 **본문**이 이 턴의 컨텍스트에 있음. 선택의 `[item id=…]`와 메모리 packet의 `[page id=…]` 둘 다 본문입니다.
  - `notAttached`: 본문이 없음
  - `noResends`: 앞선 턴에 본문이 나간 페이지가 본문으로 다시 나가지 않음. "already delivered earlier in this thread … content not re-sent" 참조 줄은 본문이 아닙니다.
  - 답 내용은 기존 `answerIncludes`로 확인합니다.
- 턴 기록에 `memory: { attached, referenced, resent, keys, duplicatesInTurn, deliveredBefore }`가 남습니다. `duplicatesInTurn`은 한 턴에 한 페이지가 선택과 메모리 packet 양쪽으로 두 번 나간 경우의 정보용 숫자입니다.

### 발견: check에서는 turn memory가 기본으로 돌지 않습니다

- 제품은 turn memory를 Agent 프로필이 있는 direct DM이면서 일회성(stateless)이 아닌 대화에서만 돌립니다. 그런데 check의 모든 대화는 일회성 ephemeral thread이고 Agent 프로필이 없습니다. 그래서 기본 상태에서는 컨텍스트 선택만 돌고 turn memory는 한 번도 돌지 않습니다 (가짜 엔진 실행에서 `egdesk_turn_memory` 키가 없는 것으로 확인).
- 그러면 "라이브 영수증"이라는 이번 요구를 확인할 수 없습니다. 그래서 `memory.mode: "on"`인 스크립트는 turn memory를 그 대화의 모든 턴에서 켭니다 (훅의 `eligible`, Board 턴 제외). 이것은 제품 기본과 다른 점이라 모듈 머리 주석에 적어 두었습니다. 선택 쪽은 이 옵트인이 필요 없습니다.

### 스크립트 2개 (`scripts/real-engine/scripts/`, 합성 페이지, 둘 다 `--decisions` 필요)

공통 페이지 (made-up 서버 백업 정책): "서버 백업 보관 기간 결정"(11월 5일 회의에서 보관 기간을 **47일**로 정했고, 지나면 **자동 삭제**하고 월 1회 복원 시험), 그리고 관련 없는 "회의실 예약 규칙", "점심 설문 결과".

| 스크립트 | 흐름 | 코드 기대값 |
|---|---|---|
| `real-engine-memory-recall-v1` | 첫 턴: "지난번 점검 회의에서 서버 백업을 며칠 보관하기로 정했는지 알려줘." | 보관 기간 페이지 본문이 컨텍스트에 있음, 관련 없는 두 페이지는 없음, 답에 `47`, 네이티브 도구 없음, 턴 완료 |
| `real-engine-memory-held-v1` | 1턴은 위와 같음. 2턴: "그럼 그 기간이 지나면 어떻게 하기로 했지?" (`EGDESK_TURN_MEMORY_PRUNE_HELD=on`, 복원 절차 페이지가 하나 더 있음) | 2턴에서 `noResends`(이미 받은 페이지를 본문으로 다시 보내지 않음), 관련 없는 페이지 없음, 답에 `자동 삭제`(그 페이지에만 있는 문구) |

- 두 스크립트는 코드(`helper/egdesk-memory-real-engine-scripts.mjs`)로 만들고, 커밋된 JSON과 같은지 테스트합니다.
- 실행 명령 (Main이 실행):

```
node scripts/egdesk-real-engine-check.mjs --codex-bin <bin> --person-home --decisions --out <dir> --run \
  --script scripts/real-engine/scripts/real-engine-memory-recall-v1.json \
  --script scripts/real-engine/scripts/real-engine-memory-held-v1.json
```
(키는 `EGDESK_REAL_CHECK_DECISION_KEY`)

### 테스트 (`helper/egdesk-real-engine-memory.test.mjs`, 10개)

가짜 app-server와 L2의 scripted Decision 모델로 check 전체를 오프라인 실행했습니다. Codex 바이너리는 쓰지 않았습니다.

- 검증: 알 수 없는 키, 잘못된 id, 중복, 없는 페이지를 가리키는 링크, 페이지가 없는 expect
- 그래프를 컨텍스트 선택이 실제로 읽는 후보로 바꿔서 제목, 본문, 시간, 상태, 링크를 확인
- 본문 블록과 참조 줄 구분
- 훅의 판정: 본문이 다시 나가면 `noResends`가 실패하고, 참조 줄은 실패하지 않음
- **recall 스크립트**: 제품이 보관 기간 페이지를 붙이고 관련 없는 페이지는 붙이지 않음 (통과)
- **held 스크립트, 가지치기 플래그 켬**: 1턴에 본문이 한 번, 2턴에 다시 나가지 않음 (통과). 1턴에 turn memory 키가 있음을 확인
- **같은 대화에서 플래그를 뺌**: check가 재전송을 보고 2턴이 실패합니다. 기대값이 실제로 실패할 수 있다는 확인입니다.
- 메모리가 없는 스크립트는 그대로 동작하고 턴 기록에 `memory` 필드가 없음
- 가짜 Decision 모델의 한계: 이 모델은 관련도를 키워드로 판단하고, 실제 엔진이 답을 쓰는 부분은 가짜입니다. 이 테스트는 check의 배선과 판정을 증명할 뿐 실제 모델의 판단은 증명하지 않습니다. 그건 실측으로 봐야 합니다.
