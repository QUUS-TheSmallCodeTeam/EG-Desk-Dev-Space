## 1. 원인

- 실제 본문은 제품 코드로 바이트 단위까지 똑같이 다시 만들었습니다(sha256 `6b1eb94e…`, 631 bytes, `evidence/l8-c21/settings-entry-body.txt`).
- 요청은 "마케팅 알림 꺼줘"였고, 카드는 `"알림 설정 | 계정" at "account.example.test"`로만 인용됐습니다. 이 페이지에 마케팅 알림 토글이 있다는 사실은 근거 어디에도 없었습니다.
- 결과: 요청 predicate는 .90(web 작업), 카드 predicate는 .19였습니다.
- **조합 표는 설계대로 동작했습니다.**
  - "카드 하나 + 요청이 web 작업으로 결정"이면 들어가는 규칙은, 그 카드가 no로 결정되지 **않았을 때만** 적용됩니다.
  - .19는 no 기준(≤ .25) 아래이므로 카드가 명시적으로 no였고, 따라서 "모든 카드 no → 브라우저 작업 아님"이 적용됐습니다.
  - 이 판단은 틀린 것이 아니라 근거가 부족했던 것입니다. 기준은 낮추지 않았습니다.

## 2. 수정 (R1)

- 코드가 카드를 지명하지 않은 경우, entry가 카드마다 한 번 관찰합니다. UI 읽기이고 Decision 요청은 추가되지 않습니다.
- 카드 predicate가 카드가 지금 보여주는 첫 줄들을 인용합니다. 최대 3줄, 줄마다 60자, 각 줄을 따로 인용합니다(R4).
  - 예: `…"알림 설정 | 계정" at "account.example.test", which now shows "알림 설정" / "마케팅 정보 알림: 켜짐" / "보안 알림: 켜짐"?`
- run의 egress가 `page_text`를 허용할 때만 동작하고, 기본은 꺼져 있습니다(`cardTextInEntry`). 런타임은 `pageTextInNote`와 같은 gate로 켭니다.
- 관찰할 수 없는 카드는 지금처럼 제목과 host만 인용합니다.
- 꺼져 있으면 실제 본문과 바이트 단위로 같습니다(테스트로 확인).
- 카드가 둘이어도 grouping lint를 통과합니다.
- 본문은 약 100 bytes 늘어나고 요청 수는 같습니다.
- ride-along 경로(turn-start 요청에 entry 질문을 덧붙이는 비용 옵션, 기본 꺼짐)는 이번에 관찰을 하지 않습니다. 필요하면 다음에 맞춥니다.
