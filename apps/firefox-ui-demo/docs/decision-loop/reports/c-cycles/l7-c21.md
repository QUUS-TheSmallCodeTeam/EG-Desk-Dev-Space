## 1. 진단: predicate별 실제 확률 (c23)

원자료는 `evidence/l7-c21/per-pred.txt`에 있습니다. 표기는 Y ≥ .85, n ≤ .15, ? = 그 사이(undecided)입니다.

### control이 설치를 잃은 이유

전부 같은 이유입니다. 두 번째 predicate가 undecided로 남았고, 규칙("정확히 하나만 yes이고 나머지는 모두 decided no")이 그 경우를 unknown으로 처리했습니다.

| control | 맞는 쪽 | 걸린 predicate |
|---|---|---|
| source c01 "내가 봤어" | own .99 Y | guess **.66** |
| source c02 | other 1.0 Y | own **.23**, guess **.16** (no bar .15를 살짝 넘음) |
| source c10 | record .97 Y | own **.58**, guess **.71** |
| time c01 "어제 오후에 … 봤어" | when 1.0 | before **.56** (방향 자체가 undecided) |
| time c26 "작년 이맘때도 … 멈췄었어" | when .99 | before **.75** |

한 번에 yes가 둘 나온 control은 없습니다.

Main이 대안으로 말한 "exactly-one-yes AND all-others decided no"는 **이미 지금의 split 규칙**입니다. control을 잃게 만든 게 바로 이 조건입니다.

### a16이 설치된 이유

- 문장: "내일 비 오면 오늘 했어야 했나 싶어"
- 답: before .12 n, now **.92 Y**, ongoing 0 n, after .07 n, when **1.0 Y**
- 방향 넷 중 now 하나만 yes이고 나머지는 decided no라서 규칙상 `at_utterance`가 됐습니다. "싶어"(지금의 느낌)를 now 질문의 "an opinion at the moment"로 읽은 것으로 보입니다.
- 그런데 이 문장은 "내일"과 "오늘"이라는 다른 시점을 둘 다 말합니다. 그래서 일부러 모호하게 만든 축입니다.

### 다른 규칙을 같은 21개 답에 적용한 결과 (오프라인, `options.txt`)

- 옛 N-way 답은 60문장 study의 답을 썼습니다. study는 본문 구성이 달라서 이 비교는 참고용입니다. 그래서 §2에서 다시 잽니다.
- hybrid는 "옛 N-way가 .85에서 설치하면 그 라벨, 아니면 split"입니다.

| 규칙 | target (11) | control (6) | 틀린 guard |
|---|---|---|---|
| A. split (보낸 그대로) | 6 | 1 | 1 (a16) |
| D. split + when 규칙 | 6 | 1 | 0 |
| B. hybrid | 6 | 6 | 1 (a16) |
| **C. hybrid + when 규칙 (채택)** | **6** | **6** | **0** |
| R. split, 나머지는 "yes가 아니기만" 하면 됨 (**채택 안 함**: no 쪽 bar를 약하게 만드는 것) | 11 | 4 | 2 (a13, a16) |

- **when 규칙**: now 하나로 읽혔는데 when이 yes(날짜나 시각을 말함)이면 다른 사건을 다른 시점에 둔 문장으로 보고 unknown으로 둡니다. L6 라벨 규칙 L3/L6("두 사건을 다른 시점에 두는 문장은 ambiguous")과 같은 생각입니다.
  - c08 "지금 … 안 돼"는 when이 .26(undecided)이라 그대로 at_utterance로 설치됩니다.
  - ongoing 경로(c07, c37)는 이 규칙의 영향을 받지 않습니다.
- **hybrid**: study에서 옛 N-way는 .85 bar에서 틀린 설치가 0개였고, 대신 이번 target 11개는 하나도 설치하지 못했습니다. 그래서 옛 설계가 설치하는 축은 그 라벨을 그대로 두고, 남긴 축만 split이 채웁니다.
- 한 요청에 옛 질문과 predicate를 같이 넣습니다. 그래서 제품 비용은 문장당 약 2,400 est로, 지금(약 1,250)의 두 배쯤 됩니다. 결과가 좋으면, 옛 질문이 남긴 축만 두 번째 요청으로 묻는 방식도 다음 선택지로 볼 수 있습니다.

### 구현 (`egdesk-speech-grounding.mjs`)

- `splitLabels`에 when 규칙을 넣었습니다. `split-isolated`에도 적용됩니다.
- `SPEECH_HYBRID = 'hybrid-isolated'`를 추가했습니다.
  - `speechHybridQuestions`: isolated axes 질문 3개 + split predicate 9개. 문구는 바꾸지 않았습니다.
  - `speechHybridInterpretations`: 축마다 axes의 `pick()` 결과가 있으면 그것, 없으면 split 결합 결과. form은 axes 결과를 씁니다.
- `WRITE_SPEECH_DESIGNS`에 hybrid를 추가했습니다. 플래그는 `EGDESK_TURN_MEMORY_SPEECH_DESIGN=hybrid`(기본 off)입니다. 기본 `axes-isolated`의 요청은 바뀌지 않습니다.

## 3. 명령 실행 요청: turn memory 쪽 (`memory-action-v1`, `proofs/decision-real-measure/memory-action/`)

- **v4 실측**: selection의 action 규칙은 동작했습니다 (`egdesk_decision_context` 키가 아예 없음). 그런데 turn memory가 PostgreSQL 페이지 4개를 본문으로 보냈습니다. 흐름은 triage need .99 → scan pg_0/pg_1 .87 → 링크 op_P4/P5 1.0이었습니다.
- **수정**: `ACTION_MEMORY_RULE`(`egdesk-wiki-reconstruction.mjs`)을 추가했습니다. selection의 규칙과 같은 내용이고 "item"을 "stored page"로만 바꿨습니다.
  - triage(`TRIAGE_RULES`)와 scan(`JUDGE_RULES` / `NEXT_RULES`) 뒤에 한 줄씩 붙습니다. 질문은 바꾸지 않았습니다.
  - 같은 플래그 `EGDESK_CONTEXT_RELEVANCE=action`으로 켭니다. 런타임이 `prepareTurnMemory({ ruleSet })`로 넘깁니다.
  - 기본 rules는 바이트 단위로 같습니다 (테스트로 확인).
- **플랜**: 3개 요청, **4,150 est**, ≤ 5k. productBars `tn_need`, `pg_#` .8/.2.
  - 모두 all-on journey 안에서 제품이 만든 본문입니다. v4 플래그 + action 규칙, scripted 모델, 오프라인입니다.
  - s4는 실제처럼 triage need .99를 주입해서, 그 뒤에 오는 scan 본문까지 만들었습니다.
  - 요청과 HARD 기대값:
    - `s4-triage`: tn_need ≤ .2. decided no이고 held 페이지가 있으며 목록이 완전하면 fetch를 건너뜁니다 (c18 규칙).
    - `s4-scan`: 모든 pg_ ≤ .2. triage가 여전히 yes를 줘도 scan이 아무것도 고르지 않아야 합니다.
    - `s3b-triage` (대조군, 설계 질문): tn_need ≥ .8 (실제 v4에서 1.0).
  - 미리 정한 기대값: hard 3개 모두 통과.
- **한계**
  - 이 본문들은 scripted journey 안에서 만든 것이라, held 목록이 실제 v4와 똑같지 않습니다. 규칙을 뺀 sha가 v4 기록과 일치하지 않습니다. c20의 s4-action처럼 실제 본문에 규칙 한 줄만 더한 정확한 A/B는 아닙니다.
  - 실제 input 토큰은 est보다 10–15% 많이 나오는 편이라 약 4.6k로 예상합니다.
