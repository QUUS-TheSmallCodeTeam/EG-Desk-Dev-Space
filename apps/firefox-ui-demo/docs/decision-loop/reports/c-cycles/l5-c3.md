# L5 / C3 — Keep-alive 전송 계층 + 내용 없는 pre-connect

브랜치 `lane/c3-keepalive-preconnect` (기준 `int/c2`), 커밋 `3144b54`. 증거 `evidence/l5-c3/`. **모든 수치는 로컬 TLS 모의 서버(합성 키, 지연 프록시)의 결과이며 실제 OpenAI/실제 앱 검증이 아니다.** 사용자 피드백 반영: 1.4–2.2 s는 bridge→OpenAI 인터넷 구간이고 첫 호출 3건만 측정됐으며 idle 후 재연결 비용은 미측정이다. 그래서 아래 모의 서버는 지연을 "연결 수립 비용(CONN)"과 "첫 요청 서버 비용(FIRST)"으로 분리해 모델링했다(원인은 모름).

## 1. 하네스
- `sim3.mjs`: `net` 지연 프록시(연결 후 CONN ms 뒤에 TLS 바이트 전달) → 자체서명 `https` 서버(첫 요청 FIRST ms, 이후 300 ms), 서버 쪽 유휴 종료 5/60/300 s, 소켓 단위 계측(연결 수, 핸드셰이크 수, 복호화된 애플리케이션 바이트, HTTP 요청 수). 실제 `createDecisionClient`를 사용하고 전송만 교체(현행 전역 `fetch` = undici vs 새 transport).
- 모든 실행은 127.0.0.1, 합성 키 `egd-synthetic-not-a-key-0005`. 외부 호출 없음.

## 2. 구현 (커밋 3144b54, +341/−6, 6 파일)
- `helper/egdesk-decision-transport.mjs` (신규, 의존성 없음, `node:http(s)`만): 결정 클라이언트 전용 `fetch` 어댑터.
  - **연결 재사용:** keep-alive Agent(소켓 최대 4, free 2). free 소켓은 idle 상한 55 s 후 닫고, 서버가 `Keep-Alive: timeout=N`을 보내면 `N − 1 s`로 더 줄인다(서버보다 먼저 닫기). 근거: 상한 값은 서버 한도를 모르는 상태의 보수적 추정이며 실제 한도는 §6 실측 후 확정.
  - **자동 재시도 없음.** 재사용 소켓이 실패하면 `reusedSocket: true` 표시와 함께 오류로 올린다. 결정 클라이언트는 이를 `unreachable`, `dispatched: true`(비용 청구 가능)로 보고한다. 근거: RFC 9110 §9.2.2 "A client SHOULD NOT automatically retry a request with a non-idempotent method…" 및 POST 자동 재전송 금지(https://www.rfc-editor.org/rfc/rfc9110.txt). 단일 재연결은 "본문이 쓰이지 않았음"을 증명할 수 없어(서버가 이미 처리했을 수 있음) 구현하지 않았다. 대신 idle 상한을 서버 hint/보수적 값으로 두어 FIN 경합 창을 줄인다.
  - **pre-connect:** `preconnect(endpoint)`는 자격 증명을 인자로 받지 않으며 소켓에 아무것도 쓰지 않는다. TCP(+TLS) 연결 하나만 열어 보관, 다음 실제 요청이 `createConnection`을 통해 그 소켓을 채택(공개 확장점만 사용). idle 기간당 최대 1회(실제 요청이 오면 초기화), 안 쓰이면 15 s 후 닫음. 이미 free/사용 중 소켓이 있으면 건너뜀.
  - 선택적 `trace` 훅: 단계 이름과 시간만(lookup/connect/secureConnect/response, 내용 없음) → 실측에서 원인 분해용.
  - TLS 세션 캐시는 `https.Agent` 기본값(`maxCachedSessions` 기본 100, https://nodejs.org/api/https.html)이라 idle 후 재연결 때 자동 재개 시도; 이 하네스에서는 재개 효과를 **측정하지 않았다**.
  - 한계: HTTP/1.1 전용(전역 fetch는 h2 가능). 프록시 환경변수는 전역 fetch와 동일하게 읽지 않음.
- `codex-bridge-server.mjs`: 결정 클라이언트와 Board 클라이언트가 같은 transport 사용. `/decision/preconnect` 경로 연결.
- `egdesk-decision-http.mjs`: `POST /decision/preconnect`(본문 없음). **mode on/advisory + 저장된 키가 있을 때만** warm-up 호출, off·키 없음이면 접촉 0. 루프백/Origin 가드 동일. 키 값은 읽지 않고 존재 여부만 확인.
- `eg-desk-surface.uc.js`: Codex DM 입력 시 600 ms 디바운스 + 30 s 스로틀, `[보기 추천]` 열 때 호출(실패 무시). 이 호출은 로컬 브리지로만 가며, 바깥 접속 여부는 브리지가 게이트한다. 기존 호출 규약은 그대로.

## 3. warm-up이 아무것도 보내지 않는다는 증명
- TLS 서버 증거(`proof-warmup.json`): warm-up 후 `hs:1`(TLS 핸드셰이크 완료), `appBytes:0`(복호화된 애플리케이션 바이트 0), `requests:0`.
- 단위 테스트(평문 HTTP 서버): 서버가 연결 1개를 보지만 수신 바이트 0, 요청 0; 이어진 실제 요청에서만 `authorization` 헤더가 도착, 연결은 새로 열리지 않고 warm 소켓을 채택. 라우트 테스트: off/키 없음 → warm 0회, advisory/on+키 → 호출, GET 405, 외부 Origin 403.

## 5. 측정: pre-connect 이득 (typing 시작 → 호출까지 lead 시간별)
| 프로파일 | lead 0.5 s | 2 s | 5 s | 20 s |
|---|---|---|---|---|
| P1 연결 지배 (conn 1500 / first 0) | 1834 → **1309** | 1811 → **304** | 1815 → **305** | 1813 → 1804 (warm 15 s 만료, 연결 2개) |
| P2 첫요청 지배 (conn 0 / first 1500) | 1806 → 1803 | 1806 → 1803 | 1812 → 1804 | 1811 → 1808 |
| P3 혼합 (conn 800 / first 800) | 1911 → 1407 | 1910 → **1102** | 1906 → **1102** | 1913 → 1908 |
- pre-connect는 **연결 수립 비용만** 숨긴다. cold의 원인이 서버 첫 요청 비용이면(P2) 이득 0이다. 입력이 15 s 이상 걸리면 warm이 만료되어 헛된 핸드셰이크 1회(내용 없음)만 발생한다.
- 턴 시작 800 ms 예산에는 P1에서만 들어간다(304 ms). P3은 1.1 s라 800 ms를 넘어 폴백.
- 따라서 이득은 원인에 달려 있어 §6 실측의 trace(connect/secureConnect/response 분해)가 결정적이다.

## 6. 실제 호출 측정 계획 (사용자 승인 후 Main이 실행, 나는 실행하지 않음)
스크립트 초안: `evidence/l5-c3/measure-real.mjs.NOT-RUN` (승인 환경변수 없으면 종료, 키는 환경변수로만 전달, 출력·로그에 키 없음). 4건 모두 제품 키 확인과 같은 161토큰 predicate, 사용자 내용 없음. 비용 극소.
| # | 경로 | 시점 | 알아내는 것 |
|---|---|---|---|
| R1 | 전역 fetch(현행) | 프로세스 시작 직후 첫 호출 | cold 기준값(과거 2229/1409 재현) |
| R2 | 전역 fetch | R1 +10 s | undici 4 s 기본 때문에 10 s 간격도 재연결하는지, 서버 Keep-Alive hint 유무 |
| R3 | 새 transport | 첫 호출 (trace 켬) | cold를 lookup/connect/secureConnect/응답 단계로 분해 |
| R4 | 새 transport | R3 +60 s | 서버가 60 s idle 소켓을 살려 두는지(재사용 여부, 오류 여부) |
기록: wall ms, 단계별 ms, 소켓 재사용 여부, 응답 헤더 `keep-alive`/`connection` 값, `openai-processing-ms`(서버 처리 시간)와 존재 여부 헤더(cf-ray/via/server), 상태 코드. 키·본문은 기록 안 함.
판정 규칙:
1. R3에서 (connect + secureConnect)가 wall의 약 60% 이상 → 연결 지배: pre-connect + keep-alive 채택 유지, 800 ms 예산은 warm(≈수백 ms)에 맞음. 미만(`openai-processing-ms`가 지배) → pre-connect는 무의미: 라우트·UI 호출 제거 또는 비활성, 대신 (b) 예산 확대/(c) 폴백 수용을 사용자 결정으로.
2. R2 ≈ warm(<600 ms) 또는 hint 존재 → 현행 undici도 이미 소켓을 유지, transport 이득은 작음(idle 상한만 의미). R2 ≈ R1 → transport 이득 확인.
3. R4 재사용+warm → idle 상한 55 s 유지(필요하면 hint 기준 상향 검토). R4 새 연결 → 서버 idle < 60 s: 상한을 hint/실측 값−여유로 낮춤. R4 오류(`reusedSocketErrors`) → 상한을 즉시 낮추고 재시도 없는 정책 유지.
4. warm 호출 p50이 800 ms 안에 안정적으로 들어오면(예: <500 ms) 턴 시작 예산 800 ms 유지, 아니면 사용자에게 예산 결정 요청.

## 8. 철학 점검
P3 "동의 없는 접속 없음": 사용자 설명대로 mode 사용/기록만 + 저장 키가 동의이며, off는 접촉 0(라우트 테스트로 고정). warm-up은 키·헤더·본문을 쓰지 않고(증명 §3), 입력 시작/패널 열기라는 명시적 사용자 행동에서만 발생하며 idle 기간당 1회. P2 "실패하면 지금 방식으로": 재시도 없음, 실패는 `unreachable`+`dispatched:true`로 정직하게 보고(비용 가능성 숨기지 않음).
