## 0. 먼저 확인할 사실: 제품 바는 .8이 아니라 .7
- `helper/egdesk-briefing-skeleton.mjs`의 `SKELETON_BARS = { yes: .7, no: .3 }`. 즉 .7 이상이면 yes, .3 이하면 decided no, 그 사이는 undecided입니다.
- .8은 `egdesk-decision-questions.mjs`의 `relevantStrict: 0.8`에만 있고, 스켈레톤 판정에는 쓰이지 않습니다.
- 그러므로 c18의 `several` .74는 제품 바에서 **yes**였습니다. c18 계획의 hard 조건(≥.7)도 통과했습니다.
- 이번 규칙 변경으로 `several` 질문은 답이 인용된 경우 아예 묻지 않습니다. 따라서 이 차이가 결과를 바꾸지는 않습니다. 그래도 Main의 전제와 다르므로 기록합니다.

## 1. 보드 규칙 (Main 결정 구현)
- 답이 인용된 경우, place 요청에는 `combines`와 관련성(`about_*`), 버전 쌍(`same_*`)만 들어갑니다. `several`은 빠집니다.
- 보드가 되는 조건은 두 가지입니다. `combines`가 yes(≥.7)이고, 코드가 센 **관련 자료(about-yes)가 2개 이상**이어야 합니다.
  - `combines`가 decided no이면 bubble `judged-bubble`, undecided이면 bubble `placement-undecided`입니다.
  - 관련 자료가 1개이면 bubble `single-material`, 0개이면 `not-asked-about`입니다.
- 답이 없는 경로는 그대로 `several` + `one_sentence`입니다.
- `decidePlace(answers, { relevant })`. 관련 자료 수 세기는 R3(코드가 셀 수 있는 것은 코드), 한 질문에 한 조건은 R4입니다.
- **오프라인 재생**(`replay-c18.json`)은 Main의 c18 실제 답을 질문 이름별로 그대로 넣은 결과입니다. 새 body가 묻는 질문은 모두 실제 답이 있는 것뿐입니다. `several`은 아예 묻지 않습니다.
  - s3: `combines` .98, about .99/.98/.97 → 관련 3개로 place를 통과해 fit, order까지 갑니다. 재생은 place 단계 검증이라 fill 함수를 주지 않았습니다. 그래서 마지막 상태는 fill 단계의 `fallback-chat fill-invalid`이고, 이것은 재생 범위 밖입니다. s3 전체 보드 경로는 2부(모의 fill)에서 `presented`로 확인했습니다.
  - 사실 하나짜리 대조군: `combines` 0 → `bubble judged-bubble`로 place에서 끝납니다(요청 1개).

## 3. 커버리지 판정과 제한된 재설계
- 새 단계 `coverage`, 질문 `covers` 하나입니다. 문구(영문 그대로): "The person asked, quoted exactly as a JSON string: …. The board, its parts quoted in order as JSON: […]. Does this board answer everything the person's request asks about (the request may refer to the assistant's answer quoted above)?"
  - 보드는 파트 순서대로 `{text, shown:[{label, rows|lines|text}]}`의 구조 필드로 인용합니다. 이어 붙인 평문은 거부합니다(`normalizeSkeletonDto` 테스트, R4).
  - 답은 place와 같은 방식으로 user 메시지에 한 번 인용합니다(`draft_text`). fit/order/fill_check에는 여전히 넣지 않습니다(테스트로 고정).
- 판정별 동작:
  - yes 또는 undecided이면 보드를 제안합니다. undecided는 no가 아니고, 값은 `coverage.p`에 기록합니다.
  - decided no(≤.3)이면 **재설계를 한 번만** 합니다. fit에서 undecided였던 카탈로그 파트 하나를 추가하고, 그 파트만 fill(fill 턴 +1) → fill check(요청 +1) → coverage 재질문(요청 +1)을 합니다.
  - fit에서 **no로 판정된 파트는 다시 넣지 않습니다.** 추가할 파트가 없거나, 추가 파트가 검사를 통과하지 못하거나, 두 번째도 no이면 `fallback-chat not-covered`로 대화 답을 유지합니다.
- 요청 수: 기본 경로 place, fit, order, fill_check, coverage = 5개, fill 재작성이 있으면 6개, 재설계까지 하면 최대 8개입니다. `SKELETON_LIMITS.maxRequests`를 6에서 8로 올렸습니다.
- 결과 객체에 `coverage {asked, p, redesign}`를 추가했습니다. `redesign`은 `{part, trait, component, from:'undecided-part'}` 형태입니다.
