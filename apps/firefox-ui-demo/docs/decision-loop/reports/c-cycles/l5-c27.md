## check-10s는 왜 실패했나 (기록으로 확인한 것)
- 3턴 답: "확인된 건 실행 요청이 약 4.9초 후 중단됐다는 점입니다. 명령 자체는 백그라운드에서 계속 실행됐을 수도 있어, … 확인되지 않았습니다. `cleanup-finished` 출력도 받지 못했습니다."
- **블록은 실렸다고 본다**: "4.9초"는 내 블록에만 있는 숫자(1턴은 아무것도 게시하지 않았고, 엔진의 도구 호출 기록에는 소요 시간이 없음). 따라서 알려진 한계(유예 안의 다음 메시지)가 아니라 **모델이 사실을 받고도 얼버무린 것**. 다만 기록에는 turn/start가 실은 컨텍스트 키가 없어 100% 확정은 못 함: 이번에 점검 도구가 `turn/start`마다 additionalContext **키 이름**(본문 아님)을 요청 행과 턴 기록의 `contextKeys`로 남기게 했음. 다음 실행에서 `egdesk_stopped_command`가 있었는지 바로 보임.
- 모델이 얼버무린 이유로 짚은 것(내 문구): "whether it would have succeeded is not known"과 "it has no exit code"가 불확실성을 부추겼고, 엔진 자신의 기록에는 결과 없는 도구 호출이 남아 있어 "백그라운드에서 계속 실행"을 의심하게 함. 문구를 사실만 단정하게 바꿈: "The command `…` was stopped at the person's request after 4.9 s. EG-Desk ended its process with signal SIGTERM: the command did not run to its end and has no exit code, and its process has exited." + 출력(없으면 "It had printed no output before it was stopped.").
- **스크립트 쪽 결함**: 실패한 expectation은 `answerExcludes`였는데 답이 `cleanup-finished`를 "출력도 받지 못했다"며 **부정문으로 인용**했음(맞는 말). 3턴에서는 그 단어 제외를 빼고, 모델이 "알 수 없다"고 하는 표현(`확인할 수 없`, `확인되지 않`, `알 수 없`)만 제외하도록 고침(1턴에서는 계속 제외). 이 스크립트를 다시 돌리면 이번 답은 `확인되지 않았습니다` 때문에 여전히 실패할 것이므로, **문구 변경 후 모델이 실제로 단정하는지**가 이번 재실행에서 확인할 내용.

## 알려진 한계 닫기: 다음 전송이 정지 기록을 기다린다 (Main 승인)
- 실행기에 `stopSettled(room)`: `cancelRun`이 멈추라고 한 명령마다 "기록 완료" 약속을 두고(`onConditions` 직후 또는 실행 실패 시 해제), 방(clientThreadId)별로 대기 목록을 가짐. 런타임 `settlePendingStops(room)`이 turn을 만들기 전(정지 사실을 소비하기 전)에 최대 `STOP_RECORD_WAIT_MS = 2500`ms 기다림(진행 중인 정지가 없으면 즉시, 다른 방은 기다리지 않음, 한정 전송은 기다리지 않음).
- 테스트(가짜, 2): SIGTERM을 무시하는 명령을 인터럽트한 직후(킬 유예 안) 다음 메시지를 보내면 그 전송이 기록을 기다려 블록이 실림, 신호는 SIGTERM→SIGKILL, 끝나면 대기 목록이 비어 있음, 상한 안에 끝남; 기록이 오지 않는 정지는 정확히 상한(≈2.5 s)까지만 붙잡고 블록 없이 전송됨.

## 타이밍에 약했던 테스트
- `whileRunning: a run that ended before afterMs no longer takes the message…`: 가짜 턴이 500 ms 안에 끝난다는 벽시계 가정이 부하에서 깨졌음. 점검 도구에 시험용으로 주입 가능한 `deps.sleep`(기본은 실제 sleep; afterMs 대기와 그 뒤의 "일찍 깨어나지 않기" 루프는 그대로)를 두고, 테스트는 "첫 run이 끝난 뒤에야 끝나는" sleep을 줌: **run이 끝난 뒤에 메시지가 보내진다는 것이 이벤트로 보장됨**. 단정(`INRUN_MESSAGE_UNAVAILABLE`, 같은 detail, 첫 턴 ok, 전체 not ok)은 그대로, 첫 run이 completed였음을 추가로 확인. 6개 병렬 실행(부하)에서 6/6 통과.
