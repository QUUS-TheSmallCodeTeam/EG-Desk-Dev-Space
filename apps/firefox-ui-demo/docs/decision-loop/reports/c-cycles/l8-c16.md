## 1. 기록된 선택을 코드로 비교 (R3)

배경이 된 실측(c15 live): month 2에서 기록이 근거로 주어졌는데도 모델은 기록된 사업자를 .76으로 골랐습니다. 기준(.75)을 0.01 넘긴 값입니다. 페이지가 바뀐 경우에는 needs_user_context를 .26(1·2위 .21/.22)으로 답했고 후보를 하나도 대지 못했습니다.

`recordedChoice(prior, snapshot, options, { goal, userContext })`는 `egdesk-browser-task-memory.mjs`에 있습니다. 기록에서 **이 경로(path)**에 대해 정해진 최신 "어느 것?" 답을, 지금 제시된 라벨들과 비교합니다. 정규화는 NFKC, 대소문자, 공백, `[L1]` 접두어만 합니다.

| 결과 | 코드 동작 |
|---|---|
| `one` (정확히 하나 일치) | "어느 것" 질문 없이 코드가 그 요소를 고릅니다. 요청에는 page-state와 goal 질문만 남습니다. 요소·href 가드는 그대로라서, 같은 라벨이 이제 삭제 주소를 가리키거나 제출 버튼이면 애초에 제시되지 않고 아무것도 실행되지 않습니다. |
| `several` (둘 이상 일치) | 일치한 것들을 후보로 나열하고 `choice_needed`로 멈춥니다. |
| `maybe` (라벨 형태는 다르지만 같은 식별번호, 6자리 이상 숫자열) | 해당 후보마다 predicate를 하나씩 묻습니다. 문장은 `Is this option, "가나상사 (987-65-43210)", the same thing as the recorded choice, "사업자 987-65-43210"?`이고, 한 predicate에 옵션 하나만 인용합니다(R4). 정확히 하나가 decided yes(≥0.85)이고 나머지가 모두 decided no(≤0.15)일 때만 그것을 고르고, 그 밖에는 사람에게 묻습니다. 후보가 4개 이상이면 묻지 않고 `several`로 처리합니다. |
| `none` (일치 없음) | 기록된 라벨과 단어를 공유하는 요소("사업자" 등)를 후보로, 공유하는 요소가 없으면 제시된 모든 요소를 후보로 하여 `choice_needed`로 멈춥니다. "어느 것"은 코드가 정하고, 문장은 주관 모델이 씁니다. 새 고정 문구는 없습니다. |

코드가 기록을 적용하지 않고 예전처럼 모델에게 묻는 경우(현재 요청이 기록보다 우선):
- 이번 작업 안에서 사람이 이미 답했을 때
- 요청이 다른 요소를 지목할 때
- 요청 문장이 기록과 다르고 기록된 선택도 언급하지 않을 때. 예: "이번엔 첫 번째 사업자 걸로"

기록은 한 run 안에서 경로당 한 번만 적용합니다.

이번 사이클에서 발견해 고친 버그 2건:
1. **이월 누락.** 질문 없이 기록으로 고른 month 2의 결과 기록에 `선택:` 줄이 빠져서, month 3에서 다시 물을 상황이었습니다. 이제 코드가 고른 선택을 그날 라벨로 다시 기록합니다(M3b). 고치기 전에는 이 테스트가 `actual: []`로 실패하는 것을 확인했습니다.
2. **사라진 선택이 질문을 강제함.** 바뀐 페이지에서 사람이 답한 뒤에도 "사라진 기록된 선택"이 매번 질문을 다시 강제했습니다. 이제 사람의 답이 있으면 그 답이 결정합니다.

## 2. Main의 s10/s11 (all-on journey 실측의 hard 실패 2건)

- **본문 재현.** 결과 파일에는 sha256만 있어서, L2의 포털 double 페이지(보이는 텍스트는 "합성 포털"뿐)로 c15 형태 step 본문 3개를 제품 코드로 다시 만들었습니다. 모두 바이트 단위로 같았습니다(`evidence/l8-c16/s10-s11-body-reproduction.json`, 2dae289에서 확인).
  - s10 step: `b2f736ed…`
  - s11 step 1: `d5b691b4…`
  - s11 step 2: `f02274cc…`
- 원인은 두 가지입니다.
  - s10: next_step needs_user_context가 .70로 기준 미달이었고, page_state content도 .69로 기준(.7) 미달이었습니다. 결과는 `uncertain`, 후보 없음이었습니다.
  - s11: page_state content가 .65였습니다(loading .18). 9지선다에서 "content"가 나머지를 다 받는 catch-all이라 평범한 페이지에서도 점수가 퍼집니다(R2).
- **page state를 predicate 6개로 분리** (`PAGE_STATE_CHECKS`, 각각 "이 페이지"에 대한 질문 하나):
  - `ps_sign_in` → login_required
  - `ps_code` → two_factor_required
  - `ps_challenge` → bot_check
  - `ps_sensitive` → sensitive_flow
  - `ps_error` → error_page (access denied 포함)
  - `ps_covered` → modal_blocking
- 결합 규칙: decided yes(≥0.7)가 하나라도 있으면 멈춥니다(사람의 단계, 오류). 모두 decided no(≤0.3)여야 진행합니다. 값이 없거나 그 사이면 사람에게 페이지를 보게 하고, 조용히 멈추는 경우는 없습니다. 이때 노트는 `need_context / page_unclear`입니다.
  - `page_unclear`는 **새 closed code**입니다. 사람에게 보이는 문장은 주관 모델이 쓰고, 결과 기록은 남기지 않습니다.
  - loading은 모델에게 묻지 않고 코드가 `snapshot.readyState === 'loading'`으로 판단해, 요청 없이 wait합니다.
  - Main은 4개를 예로 들었는데 6개로 늘린 이유: sensitive_flow와 modal_blocking을 빼면 결제 화면이나 대화상자 아래에서 무해한 링크를 따라갈 수 있게 됩니다. 이는 지금 자동으로 하지 않는 동작이라, 에이전트가 자동으로 하는 범위를 넓히게 됩니다.
- **결정되지 않은 다음 단계** (`sameKindCandidates`): 숫자를 비운 라벨 모양이 같은 요소(예: "사업자 ###-##-#####" 두 개)를 코드가 묶습니다.
  - 미결정의 1위가 고정 질문 옵션(needs_user_context)이거나, 같은 종류 요소가 2개 이상이면 `choice_needed`로 멈추고 그 묶음을 후보로 냅니다.
  - 확정된 needs_user_context일 때도 이 묶음을 후보로 씁니다. 예전에는 확률 상위 3개에서 후보를 뽑았는데, s10 분포라면 L1 하나만 남았을 것입니다.
  - 요소가 하나뿐이고 1위가 그 요소인 미결정은 지금처럼 `uncertain`입니다.
- 실제 답 재생(`egdesk-browser-real-rules.test.mjs`):
  - s10의 .70 분포 → 두 사업자를 후보로 `choice_needed`, 동작 0
  - s11의 다운로드 .99 + predicate 모두 no → 다운로드를 엽니다
  - predicate가 .5 → `page_unclear`, 동작 0

### 비용 (결정 필요)

predicate는 하나당 약 135 토큰입니다(L7 추정식, s10 memory_fetch 실측 2,921 vs 추정 2,660). step 하나가 **약 0.81k에서 약 1.57k 입력 토큰으로 늘어납니다(+약 90%)**.

일부는 줄였습니다. 파싱된 기록이 있으면 그 사실이 이미 코드가 만든 History 줄로 들어가므로, 같은 내용을 담은 일반 memory packet(3,000자)은 그 step에서 빼서 step당 약 300 토큰을 절약합니다(R1). 기록이 없을 때는 packet이 그대로 step 근거로 들어갑니다(테스트로 확인).

## 4. 사람이 결정할 것: Main의 잠정 입장 기록

- **(a)** `card_choice_needed`의 문장은 문구가 승인될 때까지 주관 모델이 씁니다(Main 잠정안). `choice_needed`와 `page_unclear`도 같은 방식입니다.
- **(b)** 푸시 승인형 2FA 페이지는 2FA 라벨 없이 `human_step`으로 처리합니다. 당분간 받아들입니다(Main 잠정안).
  - 측정(`scripts/egdesk-browser-human-step-census.mjs`, `evidence/l8-c16/human-step-census.txt`): 페이지 모양 12종 중 8종이 c15 규칙으로 요청 없이 멈추고, 그중 **3종**(푸시 2FA 두 종, 체크박스 captcha)만 물어봤다면 라벨(`two_factor_required`, `bot_check`)이 붙었을 것입니다.
  - 이것은 페이지 모양 기준의 집계이고 **실사용 빈도가 아닙니다**. 셀 수 있는 브라우징 로그가 없습니다.
  - 라벨 하나를 얻는 비용은 이제 page-state predicate 6개 + goal 요청 1건, 약 **1.25k 토큰**입니다(1,547 bytes).
  - 두 경우 모두 사람에게 넘기고, 라벨은 사람에게 무엇을 말하느냐만 바꿉니다. 그래서 **요청 1건을 쓸 가치가 없다**고 판단합니다. 실사용 로그에서 푸시형이 자주 보이면 다시 검토합니다.
- **(c)** read-only QA 경로는 범위 밖입니다.
- **신규 1**: predicate 분리로 step 비용이 약 +90% 늘어납니다. 6개 대신 4개로 줄이려면 sensitive와 covered를 빼야 하는데, 그러면 자동 동작 범위가 넓어지므로 권하지 않습니다.
- **신규 2**: closed code `page_unclear`를 추가했습니다. 고정 문구는 없습니다.

## 5. 다른 레인 영역에 닿은 것, 그 밖의 발견

- **L2 `scripts/egdesk-all-on.support.mjs`**: 브라우저 double이 page-state predicate에 "평범한 페이지"로 답하도록 한 줄만 추가했습니다. 기존 page_state 답은 그대로 둬서 동작에 영향이 없습니다. 이게 없으면 all-on journey 테스트의 브라우저 단계가 `page_unclear`로 멈춥니다. L2에 알려야 합니다.
- **`egdesk-decision-calibration-log.mjs`**: QUESTIONS 화이트리스트에 `ps_*`가 없어서 page-state predicate가 보정 로그에 남지 않습니다. 파일 소유 레인 확인이 필요해 수정하지 않았습니다.
- **c14 실측 계획** (`egdesk-browser-real-plan.mjs`): 이제 현재 형태로 만들어집니다. c14 당시 바이트는 `evidence/l8-c14`에 남아 있습니다. 바뀐 점:
  - 기대값: page_state "content" → predicate 각 ≤0.3 hard, 2FA → `ps_code` ≥0.7 hard. 그래서 hard 기대값이 20개에서 35개로 늘었습니다.
  - 상한: 9k에서 12k로 올렸습니다(추정 9.9k).
- **테스트 double 수정**: 다른 테스트 파일들의 page_state 응답은 공용 fixture `egdesk-browser-page-state.fixture.mjs`로 바꿨습니다. assertion 값이 바뀐 곳은 세 종류입니다.
  - 질문 이름 목록
  - 미결정 결과가 `uncertain`에서 `page_unclear`로 바뀐 곳. 사람에게 묻는 쪽으로 더 엄격해진 것입니다.
  - 요청 수 집계의 키(`page_state` → `ps_sign_in`). 요청 수 자체는 같습니다.
- **범위 밖 발견**: SSO 버튼 하나만 있는 로그인 페이지("카카오로 로그인")는 분류기가 막지 않아 후보로 제시됩니다. 이제 `ps_sign_in`이 yes면 사람에게 넘기지만, 버튼 자체는 여전히 선택 가능합니다. 분류기 어휘 담당 확인이 필요합니다.

## 6. 철학 점검

- R1: 요청에는 판단에 필요한 내용만 넣었습니다. 기록이 있는 step에서는 packet을 빼고 History 줄만 남겼습니다.
- R2: "content"를 catch-all로 두던 N지선다를 없애고 상태마다 predicate로 바꿨습니다.
- R3: 기록된 라벨 비교, 같은 종류 후보 묶음, loading 판단은 코드가 합니다.
- R4: same-thing predicate에는 옵션 하나와 기록 하나만 인용합니다.
- R5: 사람 전용 상태와 요소 가드는 점수와 무관한 규칙으로 유지했고, 자동 범위는 넓히지 않았습니다.
