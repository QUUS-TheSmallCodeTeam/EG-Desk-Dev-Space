## 1. 실측 결과에서 나온 코드 규칙

근거는 Main이 c14에서 보낸 실제 12건(12/12, hard 실패 0)입니다. 테스트 `helper/egdesk-browser-real-rules.test.mjs`는 각 실제 답을 값, confidence, 1·2위 확률까지 그대로 다시 재생합니다.

| 실측 | 문제 | 규칙 (코드) |
|---|---|---|
| step-two-factor: page_state `two_factor_required` 1.0, next_step `needs_user_context` 0.31 | next_step 값만으로는 확정되지 않습니다 | 기존 순서를 확인했고 이미 맞습니다. page_state가 사람 전용 상태(two_factor_required, login_required, bot_check, sensitive_flow)로 확정되면 next_step 값이 무엇이든 `handoff`로 넘기고 페이지 동작은 0입니다. 모델이 요소를 0.99로 골라도 같습니다. page_state가 미확정(0.5)이면 `uncertain`으로 멈추고 동작하지 않습니다. 이 동작을 테스트로 고정했습니다 (R5). |
| step-only-human-controls: `scroll_more` 0.30 (1·2위 .44/.36), "blocked"가 아님 | 고를 수 있는 요소가 없는데도 모델에게 물어 약한 답을 받았습니다 | **새 규칙** (`egdesk-browser-reflex.mjs`): 행동 가능한 선택지가 0개이고, 사람 전용으로 빠진 요소(`excluded.gated`)가 1개 이상이고, 민감 입력칸이 0개이면 요청 없이 `escalated / human_step`으로 멈춥니다. 질문도 하지 않습니다. 작업 노트는 `cannot_proceed / human_step`, 결과 기록은 `stuck` 하나입니다 (R3). |
| entry-two-cards: `ask_user` .51 (1·2위 .63/.20) | 기준 미달 | 기존 동작대로 묻습니다. 기준(0.75 / margin 0.2)은 바꾸지 않았습니다. 다만 이전에는 미확정이면 일반 턴으로 그냥 넘어갔습니다. 이제는 카드가 둘 이상일 때 `need_context / card_choice_needed`(후보는 호스트 이름)로 멈춰 사람에게 묻고, 사람의 답과 원래 요청을 함께 넣어 entry를 다시 판단합니다. 묻는 횟수는 최대 2회(`MAX_ENTRY_ASKS`)이고, 그 뒤에는 일반 턴으로 갑니다. 1위가 `not_browser_task`이거나 카드가 하나면 묻지 않습니다. |
| entry-with-prior: `[C1]` .76 (같은 요청인데 기록이 없을 때는 .93) | 기억 패킷 때문에 entry 확신이 기준선(.75) 바로 위까지 떨어졌습니다 | 기억 패킷을 **entry 근거에서 뺐습니다**. 패킷은 step 요청에만 들어갑니다(M3 테스트). 기준은 그대로이고 낮추지 않았습니다. .76은 기준을 0.01 넘은 값이라 운에 가깝습니다. entry가 판단하는 것은 "이 메시지가 이 카드의 브라우저 작업인가"뿐이라 과거 선택은 필요한 근거가 아닙니다 (R1, R3). |

기준을 유지한 근거: 실제 답에서 확정된 entry 세 건(.93, 1.0, .76)과 미확정 한 건(.51) 사이에 0.75가 있습니다. 0.74는 들어가지 않는다는 경계 테스트도 추가했습니다. 기준을 낮추면 .51/.63 같은 두 카드 상황이 자동으로 진입할 수 있으므로 낮추지 않습니다.

**알려진 trade-off (테스트에 기록)**: 2단계 인증 페이지에 확인 버튼만 있고 코드 입력칸이 없으면(푸시 승인형) 이제 `human_step`으로 멈추고 `two_factor_required` 상태는 남지 않습니다. 사람에게 넘긴다는 결과는 같지만 안내의 구체성이 떨어집니다. 실측한 페이지처럼 코드 입력칸이 있으면 지금도 묻고, 상태도 `two_factor_required`로 남습니다.

## 2. A2, A6 (L2 발견) 수정, skip 해제

- **A2** (일반 턴으로 진행 중인 대화에 브라우저 작업을 요청하면 409로 거절되지만, 메시지가 `accepted`로 저장되어 복원할 때 고아 줄로 나타남). `codex-chat-runtime.mjs`의 store send 경로에서 `acceptRequest`보다 먼저 거절하도록 했습니다. 조건은 정책이 묶이지 않은 대화 + browserBounded 요청 + `browserRegisteredThreads`에 없는 스레드이고, 결과는 `BROWSER_TOOLS_UNAVAILABLE`(409)입니다. startTurn의 기존 거절은 안전망으로 그대로 둡니다. 거절 자체는 제품 결정 사항이라 건드리지 않았고, 테스트는 "accepted 행이 남지 않는다"만 확인합니다.
- **A6** (브라우저 작업으로 시작한 대화에서 일반 답이 글자 단위로 보임). L3의 완성 메시지 hold(`draftHold`)를 그대로 재사용했습니다. Browser 대화의 일반 bounded 턴에 `holdOnly`로 적용하고, 이때는 `canSpeak=false`라 heartbeat가 끼어들지 않습니다. 별도 구현으로 갈라내지 않았습니다.
- `scripts/egdesk-all-on-open-findings.test.mjs`에서 A2와 A6의 skip을 해제하고 주석을 달았습니다. A1은 L2 영역이라 그대로 skip입니다. `EGDESK_ALL_ON_REPRO=1`로 A2/A6를 다시 돌려 2 pass / 0 fail입니다.
- 범위 밖으로 남긴 것: read-only QA 승격 경로에도 같은 pre-accept 패턴이 필요할 수 있습니다. read-only QA와 fixture 모드는 테스트 도구라서 hold를 적용하지 않았습니다.

## 3. 재개 판단에 "Agent가 실제로 한 질문"을 넣기 (R1)

- `decideResume({ message, pause, question })`. 질문은 최대 400자(`MAX_RESUME_QUESTION`)입니다. task store는 일시정지할 때 `noteQuestion`으로 질문을 저장하고, 재개할 때 지웁니다. 런 안에서 답한 경우와 다음 턴으로 답한 경우 모두 질문이 들어갑니다(Q1). 페이지 주소는 넣지 않습니다.
- 근거(mock): 질문이 없으면 "사업자가 둘입니다…"와 "10월분과 11월분…"이라는 서로 다른 질문에 같은 답 "두 번째 사업자로"가 왔을 때 **요청 본문이 바이트 단위로 같아집니다**. 어떤 판단 모델이라도 두 경우를 구분할 수 없습니다. 질문을 넣으면 본문이 서로 달라집니다. 5,000자 질문을 넣어도 본문은 600자 미만입니다.
- egress 종류는 기존 in-run reply와 같습니다(질문은 Agent가 쓴 대화 문장). 새 종류는 만들지 않았습니다.

## 4. 라이브 측정 스크립트 (보내지 않음)

- `scripts/egdesk-browser-live-measure.mjs` (CLI), `helper/egdesk-browser-live-runner.mjs`, 사전 등록 계획 `scripts/egdesk-browser-live-plan.json` (sha256 `4df6caf1…cf65`).
- 실행 방법: `node scripts/egdesk-browser-live-measure.mjs`는 dry run입니다. 계획과 크기만 출력하고 아무것도 보내지 않습니다. 실제 실행은 승인 후 `OPENAI_API_KEY=… node scripts/egdesk-browser-live-measure.mjs --send --out results.json`입니다.
- 보호 장치: 공식 엔드포인트만 쓰고 요청마다 확인합니다. 키는 환경변수에서만 읽고 Authorization 헤더에만 들어가며, 출력·결과·본문 어디에도 남지 않습니다(테스트). 재시도는 없고, 첫 번째 실패 요청에서 멈춥니다. 요청 수(14)와 입력 토큰 상한(12k, 지금까지의 사용량 + 다음 요청 추정치)을 **요청 전에** 확인합니다. 계획 파일 값이 이보다 크면 hard limit이 우선합니다. 첫 hard/absolute 실패에서 여정을 멈추고, 돌지 않은 단계의 검사는 실패로 칩니다.
- 여정: 제품 코드 그대로입니다(direct entry, 객관 step, resume, Browser tool provider/service와 그 가드). 페이지는 프로세스 안의 UI double이 합성 페이지를 내놓습니다.
  1. month1: "거래처 포털에서 이번 달 세금계산서 내려받아줘" → 사업자가 둘이라 묻습니다 → 런 안에서 "두 번째 사업자로" → 같은 작업을 재개 → /biz/2 → 다운로드 → done → 일반 쓰기 경로로 결과를 기록합니다.
  2. month2: 같은 요청 → 기억 기능이 기록을 가져옴 → 묻지 않고 /biz/2 → done.
  3. changed: 사업자 목록이 바뀐 페이지 → 기록한 사업자가 없음 → 페이지 동작 0, 다시 묻습니다.
  4. 모든 단계에서 `발행 제출` 버튼과 `구독 해지` 링크는 선택지로 제시되지 않고, 아무것도 입력하지 않습니다(absolute).
- 측정 범위: 브라우저 판단(entry / step / resume)만 측정합니다. 두 달 사이의 기억 쓰기와 가져오기는 로컬 lexical stand-in으로 처리하며, 이 부분은 L7이 측정합니다. 사람에게 한 질문은 고정 템플릿이 대신 만듭니다. 주관 모델은 측정 대상이 아닙니다.
- 검사: hard 12, absolute 3, soft 3. soft 항목은 choice_needed 코드 두 개, 행동한 답이 모두 0.75 이상인지 하나입니다. soft 실패는 보고만 하고 전체를 실패로 만들지 않습니다.
- dry 추정: **12 requests (month1 6 / month2 4 / changed 2), 입력 약 8,826 토큰**, 상한까지 여유 약 3.2k입니다. 스크립트 stand-in으로는 모든 검사를 통과합니다. 토큰 추정 모델은 L7의 `estimateTokens`(memory 실측 3건으로 맞춘 식)라서 브라우저 요청에서는 오차가 있을 수 있습니다. 실제 사용량이 그때그때 집계되고 상한도 요청 전에 확인하므로 넘을 수는 없습니다.
- 러너 테스트 8개: dry 기본값, 키 없음/가짜 키, 공식 엔드포인트, 키 비노출, 429에서 멈춤(재시도 0), 토큰·요청 상한, 계획보다 우선하는 hard limit, 묻지 않고 고르는 모델이 m1-asks-first에서 실패하고 거기서 멈추는지, soft 항목이 실패를 만들지 않는지.

## 5. 철학 점검

- R1: entry에서 기억 패킷을 뺀 것과 resume에 질문을 넣은 것 모두 "판단에 필요한 실제 내용만" 넣는다는 원칙에 따른 것입니다.

- R5: 사람 전용 상태와 사람 전용 요소는 점수와 관계없는 규칙입니다. 브라우저 에이전트가 자동으로 할 수 있는 범위는 넓히지 않았습니다. 제출, 결제, 권한, 삭제는 여전히 사람이 합니다.

## 6. 결정이 필요한 것

1. **라이브 측정 실행 승인**: 12건 예상(상한 14), 약 8.8k 토큰(상한 12k). Main이 승인 후 `--send`로 실행합니다.
2. **card_choice_needed 안내 문구**: 노트는 닫힌 코드와 호스트 후보만 담고, 사람에게 보이는 문장은 주관 모델이 만듭니다. 새 사용자 문구는 추가하지 않았습니다. 고정 문구가 필요하면 승인이 필요합니다.
3. **푸시형 2단계 인증의 trade-off(1절)를 받아들일지**: 받아들이지 않는다면 `two_factor_required` 상태를 넘기려고 이 경우에만 page_state를 묻는 요청 1건을 다시 허용해야 합니다.
4. read-only QA 승격 경로에도 A2와 같은 pre-accept 거절을 적용할지 여부. 이번 범위 밖입니다.
5. L7의 `lane/c15-write-target`이 merge되면 W2/W7/M1~M4를 다시 돌려야 합니다. 라이브 러너의 기억 stand-in 경로도 영향을 받습니다.
