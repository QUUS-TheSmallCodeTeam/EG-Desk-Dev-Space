# L4-c5 보고서: 캔버스 디자인 점검 (Decision = 시스템 판정자, 주관 모델 = 재설계자)

브랜치 `lane/c5-canvas-design-check` (기준 `int/c4` ef82022). 커밋 `342c58c`(시험), `2c4342d`(구현). 합성 하네스 결과이며 설치된 앱 검증이 아니다.

## 0. 사용자 정정 반영 방식
Decision은 "프리셋 4개 중 추천"이 아니라 **캔버스 시스템이 런타임에 열거한 점검 항목·위치 후보** 안에서만 판정하고, 그 결과(닫힌 항목명, 별칭, 확률)를 **주관 모델(Codex/Claude)** 에 넘긴다. 재설계는 주관 모델이 하고, 사용자가 자기 화면에서 미리보기·적용·되돌리기(⌘Z)를 한다. 공유 Board 원장은 개인 적용으로 쓰지 않는다. 근거 문서 `JEV_INTEGRATION_SUGGESTIONS.md` §4.3(판단/창작 분리), §9.2("후보 ID를 선택하게 하고 자유 생성 문장을 쓰지 않는다", "raw probability와 execution permission은 다른 값", "불확실하면 정해진 코드 경로·상위 Agent·사용자 선택으로"), §9.5 JEV-CANVAS-01("System이 미리보기·좌표·충돌 회피·revision·undo, 담당 Agent는 grouping 제안, 실패 시 현재 배치 유지").

## 1. 캔버스 점검 런타임 (신규 `overlay/resources/EGDeskCanvasDesignCheck.sys.mjs`)
- `enumerateCanvasChecks(scene)`: 순수 함수. 입력은 실제 캔버스 상태(카드 rect·종류·보내도 되는지·이동 가능·화면 안 여부·중요 표시, 관계 간선, 그룹, 캔버스 능력). 후보는 `maySend` 카드 최대 12장뿐이고, 보낼 수 없는 카드는 개수에도 안 잡힌다. 항목은 위치(별칭 A.., 그룹 G1..)가 있을 때만 나온다.
- 항목 8개(전부 계산 가능, 임계값은 `CHECK_RULES`로 이름 붙임): `reading_order`(관계의 앞뒤가 읽는 순서와 반대), `related_far`(간선 양끝 간격 > 큰 카드 폭의 2배), `overlap`(겹침 > 작은 카드의 14%), `unlabeled_group`, `missing_relation`(카드가 서로 참조하는데 간선 없음), `size_inconsistent`(같은 종류 면적비 > 2.5), `misaligned`(어긋난 정렬 3~32), `offscreen_important`.
- `unlabeled_group`은 **캔버스 그룹에 라벨 필드가 없어** `capabilities.groupLabels === true`일 때만 열거한다(현재는 꺼짐: 고칠 수 없는 항목을 만들지 않음).
- `checkRequestDto()`: 화면 밖으로 나가는 닫힌 객체. 목적 한 줄(≤280), 카드별 별칭·종류(+호스트가 허용한 짧은 라벨만), 그룹 크기, 항목명·별칭·개수. id·좌표·본문 없음. `sceneFromDesk()`는 컨트롤러의 `designScene()`(신규, 제목·본문 없는 장면 복사본)에서 입력을 만든다.

## 2. Decision 단계 (`helper/egdesk-canvas-design-check.mjs` + 기존 Board 핸들러에 `/decision/canvas-check/{prepare,run,cancel}` 추가)
- 한 요청: predicate `understandable`("처음 보는 사람이 이 흐름을 이해할까?"), 항목별 predicate `issue_<item>`("이 문제가 적용되는가?"), choice `where`(런타임 위치 후보 별칭 + `none`).
- 판정 막대(자리표시자, 보정 전): 이해됨 ≥0.8, 문제 있음 ≤0.3, 항목 적용 ≥0.7, where 확신도 ≥0.75·여유 ≥0.2. `findings` = 흐름이 문제 있음 **그리고** 적용되는 항목 ≥1. `ok` = 이해됨 그리고 적용 항목 없음. 그 밖(중간 확률, 모순, 문제 있다지만 위치 근거 없음) = `inconclusive`. 답이 쓸 수 없으면 `manual`. where가 적용 항목 밖 위치를 고르면 이름 붙이지 않는다.
- 모드: off = 요청 없음(`disabled`), advisory = 기록만(응답은 `{status:'advisory-only', verdict}`, findings 반환 안 함), on = findings 반환. 인증·예산·4초 전경 마감(`FOREGROUND_DECISION_TIMEOUT_MS`)·티켓 1회 사용·중단 시 추정 예산·응답 시점 재확인은 기존 Board 핸들러 경로를 그대로 쓴다(같은 파일, 같은 `invalidate()`·`settingsRevision` 에포크, 별도 핸들러를 만들지 않음).
- 보정 기록: 기존 로그 API만(`feature:'board_arrangement'`), `goal_met`(이해됨 p, 막대 0.8, would act/none/hold), 항목별 `relevance`(p, 0.7), `choice`(top/second, 0.75/0.2). 항목명·별칭·목적·라벨 없음(시험이 확인).

## 3. 주관 모델로의 인계 (`overlay/resources/EGDeskCanvasRedesign.sys.mjs`)
- `buildRedesignRequest`: findings → `{kind:'canvas_design_findings', findings:[{item, aliases, p}], where, understandable, cards:[{alias, kind, rect, movable}], bounds, min, reply}`. 원문·제목·id 없음(시험이 확인). inconclusive → `{kind:'canvas_design_inconclusive', note:'… Make no layout change.'}`. 선택하지 않은/보낼 수 없는 카드의 위치는 넘기지 않는다(충돌은 로컬 검증에서 폐기).
- `validateRedesignProposal`: 제안은 나열된 이동 가능 별칭만, 정수화한 rect, 최소 크기, 보이는 영역 안, 서로·그 외 카드·장애물과 비충돌, 변화 없는 제안 거부. 폐쇄 사유(`no-targets, unknown-alias, duplicate, immovable, bad-rect, too-small, out-of-bounds, collision, no-change`).
- `runCanvasDesignCheck({desk, extras, purpose, decide, engine, review})`: 열거 → (항목 없으면 **요청 자체를 안 보냄**) → DTO → prepare → 사용자가 정확한 패킷을 본 뒤 `review` 동의 → run → 분기: ok/advisory-only는 주관 모델에 접촉하지 않음, inconclusive는 주관 모델에 "결론 못 냄" 통지만(제안이 와도 무시), findings만 재설계 요청.
- 적용: 컨트롤러에 `offerRedesign(plan)` 추가(검증된 plan을 **미리보기 선택지 하나**로 올림; 모델 결과처럼 적용 시점에 모드·키·권한·시간창 재확인) → 기존 `applyPlan` → `commit`(history 기록, 개인 pose 저장) → 기존 ⌘Z/Shift+⌘Z. `choose()`로 다른 미리보기를 거쳐 돌아와도 같은 적용 시점 확인이 유지됨. 선택·초점이 바뀌면 제안은 폐기.

## 7. 미해결과 한계
- 트리거·검토 UI·주관 모델 연결(Codex/Claude 어느 경로로 요청을 보낼지)은 미구현이다. 오케스트레이터는 `engine(request) → proposal` 주입 방식이고 시험은 모의 엔진을 쓴다.
- 호스트 추가 입력(중요 카드 표시, 카드 간 참조 `refs`, 허용된 짧은 라벨, 그룹)은 `sceneFromDesk`의 `extras`로 받도록만 했고 서피스에서 채우는 배선은 하지 않았다.
- 재설계는 위치만 지원한다. 그룹 구성 변경/라벨은 캔버스에 그룹 라벨 개념이 없어 이번엔 제외(그룹 구성 변경은 history가 groups 단계를 가지므로 후속 가능).
- 보정 로그에 사용자의 다음 행동 라벨(`outcome.next`)은 L7 반영 후 배선 예정.
- 사진 경로와 달리 이 점검은 사진을 쓰지 않는다(런타임 기하만). 시각적 판단이 필요한 항목은 허용된 비전 처리가 따로 필요하다.

## 9. 철학 점검
Decision은 코드가 열거한 후보 안에서 닫힌 판단만 하고(원시 확률은 권한이 아님: 적용 시점 재확인), 창작은 주관 모델이, 최종 결정은 사용자가 자기 화면에서 미리보고 적용·되돌린다. 불확실하면 아무것도 바꾸지 않고 주관 모델에 "결론 못 냄"만 알린다.
