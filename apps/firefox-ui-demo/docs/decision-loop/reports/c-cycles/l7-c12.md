# L7 / cycle 12 / lane/c12-memory-on 보고서

재측정 결과(6건, 13,404 토큰, hard 실패 0)로 세션 중간 설계가 실데이터에서 통과했다. 이번 사이클: (1) 턴 메모리 `on` 모드, (2) 엔진 압축 신호 연결, (3) 라이브(적응형) 실측 스크립트. 코드 실호출 0회(판정자는 어휘 stand-in, 엔진은 합성). 기본값은 여전히 `off`.

## 1. `on` 모드 (설정 `turnMemory`: off | advisory | on, 기본 off)

### 1.1 동작
- 유효 모드: `turnMemory=on`이어도 판정 모델 모드(`decisionContext`)가 `on`일 때만 붙인다. 판정 모드가 advisory면 advisory로(기록만), off면 아무것도 하지 않는다. 모드의 뜻을 다른 기능과 같게 유지했다.
- **시작 시점**: 메시지가 도착하면(컨텍스트 선별 요청과 스레드 준비보다 먼저) 루프를 백그라운드로 시작한다(`beginTurnMemory`). 턴은 준비를 그대로 진행하고, 턴을 점유하는 동기 검사 직전에 **cap에서 남은 시간만** 기다린다(`awaitTurnMemory`). 스레드 준비에 쓴 시간은 공짜로 겹친다.
- **첫 턴**(네이티브 스레드 없음 / 새 스레드 / 완료된 선행 턴 없음 / 압축됨): 위키에서 재구성한 packet을 턴 입력의 `additionalContext.egdesk_turn_memory`(kind application) 한 키로 붙인다. 기록 여부만 정하는 사전 분류는 packet을 기다리게 하지 않는다(`packetFirst`: 옆에서 돌고, 쓰기 판정이 나중에 그 결과를 기다린다).
- **세션 중간**: 도착 즉시 사전 분류 → 건너뜀이 아니면 다음 판단용 가져오기(links-first). **실제 전달 영수증**(`turnMemoryDelivered`: 스레드별, 리비전+해시만, 메모리 내 최대 50 스레드)으로 라이브 맥락이 가진 페이지를 판정 전에 빼고 packet에도 넣지 않는다. 영수증은 packet이 실제로 붙은 턴이 수락된 뒤에만 커밋한다. advisory의 그림자 영수증과는 분리돼 있다.
- **dispatch 직전 재검사**(`turnMemoryMayDispatch`): 모드가 아직 on인지, packet의 모든 페이지가 지금도 읽기 허용인지, 키 충돌이 없는지. 하나라도 아니면 packet 전체를 붙이지 않는다(부분 전달 없음).
- **쓰기 판정은 답변 뒤**: 런이 `completed`로 끝난 뒤 백그라운드에서 판정하고, 최신 스냅샷을 다시 만들어(판정자가 본 리비전을 지금의 페이지와 대조) 어댑터 쓰기 경로로 적용한다. 저장되는 것: 이 DM이 읽을 수 있는 페이지에 대한 **pending 판독**, 또는 새 발화 페이지(채팅 저장소 참조만, 발언 재사용 동의가 있을 때만; 해당 발화의 발언 기록이 없으면 격리 축 라벨과 함께 남긴다). 실패·중단된 런은 판정하지 않는다. **승격은 여기서 일어나지 않는다**(`promote`는 사용자 본인의 이후 명시적 확인으로만; 호출하는 UI는 아직 없다).
- **송신 게이트**: 루프의 모든 요청(사전 분류·가져오기·쓰기 판정)이 공유 게이트를 지난다. 런이 생기기 전이므로 같은 권한 구조에서 만든 게이트(`turnMemoryEgress`: 메모리 범위, 발언·토픽 동의)를 쓰고, 위키에 발화/대화 쌍 페이지가 있으면 `speech_history`/`topic_history`도 선언한다. 허용되지 않은 종류면 요청 0건(시험).
- **사용자가 볼 수 있는 것**: packet이 붙으면 활동 줄 하나(`기억 자료 N개`, 페이지 제목·시간, 본문·라벨 없음). 기존 `decisionContext` 활동 종류를 재사용했다(다른 레인의 "자체 활동" 집합을 건드리지 않기 위해). **문구는 소유자 승인 대기.**
- **초안 검사와의 관계**: packet이 붙은 턴은 초안 검사에 불투명 참조 하나로 알린다(기존 `extraKeys` 경로).

### 1.2 cap과 그 근거 (실측)
요청당 실측: 웜 0.24–0.72 s(23건 중 22건이 0.24–0.72), 긴 정지 뒤 첫 요청 1.6–2.2 s.
| 위치 | 실제 루프 시간(임계 경로) | cap | 루프 자체 기한 |
|---|---|---|---|
| 첫 턴: 스캔 + 링크 라운드 최대 2 (사전 분류는 병렬) | 웜 1.2–1.6 s (a-first 1.22, j-first 1.58), 콜드 3.1 s (pg-first) | **4.0 s** | 3.8 s |
| 세션 중간: 사전 분류 → links-first 스캔 → 링크 라운드 1 | 웜 0.95–1.27 s (j-mid 0.95, pg-mid 1.05, a-mid 1.27), 콜드 1.9–2.3 s | **2.5 s** | 2.3 s |
- 루프는 cap보다 200 ms 이른 자기 기한에 **가진 것을 반환**한다(스캔 선택만 있고 상태 판독이 없는 partial packet). 기한은 클라이언트의 타임아웃 준수에 기대지 않고 루프가 직접 강제한다(`settleBy`). cap은 최후선이다: 루프가 스스로 끝나지 못하면(예: 위키 원천이 멈춤) cap에서 packet 없이 턴을 시작한다.
- 대기는 "남은 cap"뿐이므로 스레드 준비가 길수록 추가 대기는 줄고, 작은 말(사전 분류 1회, 0.25–0.45 s)과 건너뜀은 그만큼만 기다린다.

### 1.3 세션 중간: 왜 "cap까지 대기"이고 "다음 턴으로 이월"이 아닌가
구현한 것은 **cap까지 대기**다. 세션 중간의 필요는 지금 메시지가 요구하는 판단에서 나온다("그럼 롤백 조건은?"). 이월하면 (a) 이번 답은 그 자료 없이 나가고, (b) 다음 턴에 붙는 자료는 이미 지나간 질문의 것이라 맥락만 채우며, (c) 영수증이 "관련 없던 턴에 전달됨"으로 기록돼 이후 중복 제거 판단을 흐린다. 실측으로 세션 중간 루프는 웜 1.3 s·콜드 2.3 s 안에 끝나 cap 2.5 s가 대부분을 덮고, 대기는 가져오기가 필요한 턴에만 생긴다. cap을 넘기면 아무것도 이월하지 않는다: 영수증이 그대로라 다음 턴의 사전 분류가 여전히 필요하다고 보면 그때 다시 가져온다(상태 없는 재판정이 이월을 대신한다).

### 1.4 기본값·advisory가 이전과 같다는 증명 (`egdesk-turn-memory-on.test.mjs`, 기존 bridge/wiring 시험)
실제 채팅 런타임에서 `turn/start` 매개변수 전체를 직렬화해 비교(생성 ID만 정규화):
- 기능 없음 = off = advisory = (`on` + 판정 모드 advisory) = (advisory + 판정 모드 advisory) = (`on` + 판정 모드 off): **바이트 동일**, packet 키 없음, 메모리 요청은 있어도 모두 `turn/start` 이후, 활동 줄 없음.
- `on`(판정 모드 on): 차이는 `additionalContext.egdesk_turn_memory` **한 키뿐**(그 키를 지우면 기능 없는 브리지와 바이트 동일).
- 기본 브리지: 추가 Decisions 요청 0, 어댑터 생성 0, 위키 파일 없음(c9 시험 유지).

### 1.5 시험 (13개 + 단위 2개)
첫 턴 부착과 한 키 차이 / 기본·advisory 바이트 동일 / 활동 줄(본문·라벨 없음) / 세션 중간(실 영수증으로 보유 페이지 제외, MID 규칙, 작은 말은 사전 분류 1회·부착 없음) / cap 두 경로(요청이 멈춤 → 루프 기한에서 포기, 원천이 멈춤 → cap에서 시작; 전달 없음·영수증 없음·닫힌 fallback 기록) / 기한에 잘린 루프의 partial packet / dispatch 직전 권한 철회·모드 전환 → 부착 없음 / 게이트 거부 → 요청 0 / 쓰기는 답변 완료 뒤·pending만·정책 콜백으로도 승격 안 됨·질문은 기록 안 함·실패 런은 판정 안 함 / writer 없음·모드가 꺼지면 저장 없음 / 실제 배선+어댑터: pending 판독이 0600 파일에 저장, 다음 턴에 상태 옆에 표시, 리비전이 바뀐 페이지는 다시 전달, 사용자 문장 사본 없음 / 압축 신호 2종. 단위: `packetFirst`(packet이 사전 분류를 기다리지 않음), `deadlineMs`(클라이언트와 무관하게 잘림, 표시됨).

### 1.6 시험으로 덮지 못한 경로
- 발언 동의가 있는 DM에서 새 발화 페이지를 참조로 저장하는 런타임 경로(발언 기록 보강 포함)는 구현했지만 런타임 시험이 없다(시험 장치에 발언 동의가 없음). 참조 저장·해석 자체는 c9의 어댑터 시험이 덮는다.
- Codex가 아닌 엔진에서 영수증을 신뢰하지 않는 분기는 런타임 시험이 없다(시험 장치의 엔진은 Codex).
- 실제 Firefox 화면에서 활동 줄이 어떻게 보이는지는 확인하지 않았다.

## 2. 엔진 압축 신호
- 저장소의 helper에는 압축 관련 프로토콜 처리가 **없었다**: 알림 정규화(`cleanNotification`)는 목록에 없는 메서드를 버리고, 아이템 변환(`safeItem`)은 알려진 11개 타입 외에는 버린다. 스키마 프로브(`codex-native-schema-probe.mjs`)가 읽는 스키마 목록에도 압축 타입이 없다. 바이너리는 실행·열람하지 않았다.
- 공개 1차 자료로 확인한 프로토콜: Codex app-server는 맥락을 압축할 때 **`contextCompaction` 아이템**(`item/started` → `item/completed`, `{id}`만)을 내보내고, 예전 `thread/compacted` 알림(`ContextCompactedNotification {threadId, turnId}`)은 폐기 예정이다(https://developers.openai.com/codex/app-server , https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/v2/thread.rs ; 자동 압축에서도 같은 아이템이 나온다는 것은 app-server 시험 `tests/suite/v2/compaction.rs`). 수동 압축 요청은 `thread/compact/start`.
- 연결: `compactionSignal(message)`가 두 신호 모두에서 threadId를 읽고(`handleNotification`에서, 공개 이벤트 필터보다 먼저), `markContextCompacted`가 (a) 그 스레드를 압축됨으로 표시하고 (b) 실제·그림자 영수증을 지운다. 다음 턴은 `first/context_compacted`로 재구성하고, 루프가 끝까지 돈 턴에서 표시가 소모돼 그다음부터 다시 세션 중간이다(잘리거나 실패한 턴은 표시를 남긴다). 표시 집합은 200개로 제한. 시험: 두 신호 각각, 다른 스레드의 신호는 무관, 압축 뒤 재전송, 표시 소모.
- **남은 gap(정확히)**:
  1. 설치된 Codex 빌드가 실제로 이 아이템을 보내는지는 이 환경에서 확인하지 못했다(바이너리 실행 금지). 두 신호를 모두 받도록 했으므로 어느 쪽이든 동작하지만 실기 확인이 필요하다.
  2. **Claude 엔진**: 어댑터의 번역기는 Claude Code 스트림의 압축 경계(system/`compact_boundary`)를 알림으로 내보내지 않는다. 그래서 `on` 모드는 **Codex 스레드에서만 영수증을 신뢰**한다. 그 외 엔진에서는 보유로 치는 페이지가 없어, 이미 가진 페이지를 다시 보낼 수는 있어도(토큰 비용) 잃은 페이지를 안 보내는 일은 없다.
  3. 브리지 재시작: 영수증은 메모리에만 있으므로 재시작 뒤 첫 세션 중간 턴은 보유 없음으로 판정한다(중복 전송 가능, 안전한 쪽).
  4. 압축 뒤 요약에 무엇이 남았는지는 알 수 없다(`contextCompaction`은 `{id}`뿐). 그래서 압축 = 전부 잃음으로 본다.

## 3. 라이브(적응형) 실측 스크립트 (Main이 사용자 승인 후 실행)
`scripts/egdesk-memory-live-measure.mjs` + `helper/egdesk-memory-live-runner.mjs`. 스크립트된 답 없이 **실제 루프**를 `on` 모드와 같은 조건(같은 cap, links-first, packet 먼저, 쓰기 판정은 뒤)으로 공개 합성 위키에 돌린다. 요청은 제품의 Decisions 클라이언트가 보내고(공식 엔드포인트 기본값, 재시도 없음, `redirect: error`), 공유 게이트(`memory_page`)를 지난다.
- 실행: 기본이 **dry run**(계획·상한·추정만 출력, 0건 전송): `node scripts/egdesk-memory-live-measure.mjs`. 실제: `OPENAI_API_KEY=… node scripts/egdesk-memory-live-measure.mjs --send --out results.json`. 키는 그 환경변수에서만 읽고 출력·저장하지 않는다(러너는 아무것도 출력·기록하지 않고, 결과에 키가 없음을 시험이 확인). 키가 없으면 0건 전송·종료 코드 3(직접 확인).
- 6턴: `pg`/`a`/`j` × 첫 턴/세션 중간. 세션 중간의 보유 페이지는 c10과 같은 고정 집합(영수증으로 제공): pg(설계·계획·롤백·SQLite 스키마), a(요청·v1), j(초안·사용자 발언).
- **상한**: 요청 **최대 36건**(턴당 6 = 사전 분류 1 + 루프 4 + 쓰기 1). 입력 토큰 **상한 60,000**(매 요청 전에 "지금까지 실제 사용량 + 이 요청 추정"으로 검사; `--max-tokens`로 낮출 수 있고 80,000을 넘겨 올릴 수는 없다). 둘 중 하나에 닿거나 첫 HTTP 실패·네트워크 오류가 나면 **측정 전체를 중단**한다(재시도 없음, 이후 턴은 시작하지 않고 "실행 안 됨"으로 채점). 루프의 기한이 느린 요청을 끊는 것은 측정 결과이지 중단 사유가 아니다(그 요청은 `aborted_by_deadline`, 추정 토큰을 사용량에 더함).
- 추정(어휘 stand-in으로 잰 크기, 모델 아님): 25건, 입력 약 42.9k 토큰(유형별 모형; 지금까지 실측은 이 모형보다 8–11% 많았으므로 약 46–48k 예상). 턴별: pg-first 5건/12.1k, pg-mid 4/6.1k, a-first 4/9.2k, a-mid 4/3.7k, j-first 4/8.4k, j-mid 4/3.4k.
- **사전 등록(최종 packet 기준, `LIVE_RUNS`)**: 적응형이라 선택 경로는 달라질 수 있으므로 각 턴이 답변 모델에 넘길 최종 packet과 쓰기 제안을 채점한다.

  |---|---|---|---|---|---|

## 6. 철학 점검
"Decision Model의 동의·높은 점수는 사실 증명이나 쓰기 권한이 아니다": `on`에서도 판정은 packet의 선택과 **pending** 판독까지만 만들고, 저장은 호스트 쓰기 경로의 권한·리비전 검사 뒤에만, 승격은 사용자 본인의 이후 확인으로만 일어난다. dispatch 직전에 권한을 다시 확인하고 하나라도 어긋나면 전체를 버린다. "보기가 모자라면 억지로 분류하지 않는다": 시간에 잘린 루프는 판독 없는 partial로 표시되고, 압축·재시작·다른 엔진처럼 보유 여부를 모르는 경우는 "가지고 있지 않다"로 본다. 사용자는 붙은 자료를 활동 줄에서 볼 수 있다.
