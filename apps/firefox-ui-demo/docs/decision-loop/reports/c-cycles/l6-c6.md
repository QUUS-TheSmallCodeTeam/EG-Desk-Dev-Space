# L6 / C6: 작업 기억 게이트를 실제 도구 결과 경계에 연결

브랜치 `lane/c6-memory-gate-wiring` (base int/c11 edbec8b), 커밋 `abef52f`. 증거: `evidence/l6-c6/` (`simulate.mjs`, `simulation.json`, `simulation.out`, `delivered-*.txt`, `gate.out`).
구분: [측정] 로컬 실행 수치, [코드] 저장소 사실(파일:줄), [해석] 내 판단. Decisions는 모의, 네트워크/codex/Firefox 실행 없음.

## 0. 결론
1. 스필이 **진짜 `egdesk_read_source`로 다시 읽힌다.** 문맥 저장소에 `tool-output` 캡처 종류를 추가했고, 스필은 그 run에 묶인 불변 소스가 되어 기존 읽기 경로(바인딩 검사, 입장 심사, 전달 영수증)를 그대로 탄다. c5의 대역(stand-in) 확인은 실제 도구 경로 시험으로 바꿨다.
2. 게이트를 EG-Desk 도구 결과 경계(`dispatchToolProvider`)에 연결했다. 플래그 `EGDESK_WORKING_MEMORY=advisory|on`, 기본 꺼짐. 플래그가 없으면 결과는 **같은 객체, 같은 틱**으로 나간다.
3. advisory는 결과를 바꾸지 않고 내용 없는 기록 1건만 남긴다. on은 **코드 규칙만** 적용한다(Decision 호출이 결과를 정하는 경로 없음). Decision 판정은 규칙이 남겨 둔 반복 없는 글 2,750 토큰 이상에만 묻고, 기다리지 않으며, 기록만 한다.
4. Claude 한도 초과(10,000 토큰): 플래그 on이면 오류 대신 앵커 + 고정 문구로 줄여 한도 안에 넣는다. 그래도 넘으면 손대지 않고 지금의 오류가 그대로 난다.
5. 영수증 해시가 걸린 문맥 읽기 패킷과 엔진 네이티브 이력은 경로상 닿지 않고, 명시적으로도 거부한다 (시험 포함).
6. 광범위 게이트: 285 파일, 6200 tests, 6167 pass, 33 skipped, **0 fail** (1회 실행, L7의 부하성 시험도 통과).

**먼저 알아야 할 한계 2가지 [해석]**
- **포인터는 그 run에 읽기 권한이 있을 때만 존재한다.** `egdesk_read_source`는 사람이 자료를 붙이고 읽기를 허용한 run에만 있는 도구다(스레드의 도구 목록은 시작 때 고정). 그래서 읽기 권한이 없는 보통 턴에서는 스필 선택지가 런타임에 없고, 검색 결과와 페이지 글은 **그대로** 나간다(내용을 복구 수단 없이 버리지 않음). 과정 출력(빌드/명령 로그)만 포인터 없이 접힌다.
- **지금 실제로 선언된 소비자는 Browser 읽기 도구 3개뿐**이다(observe, wait_text, wait의 페이지 글 배열, 최대 60조각). 이 결과는 보통 2,000 토큰 기준에 못 미친다. "EG-Desk 도구가 돌려주는 터미널 읽기 결과"는 제품에 아직 그런 도구가 없어서, 시험과 시뮬레이션은 같은 경계를 지나는 **대역 도구**로 했다. 새 도구는 한 줄 선언으로 소비자가 된다.

## 1. 스필을 실제로 다시 읽게 만들기
- **캡처 종류 [코드]:** `egdesk-context-store.mjs` `captureToolOutput` (:403). 종류 `tool-output`, 범위 `tool-output`(도구 이름 기록), 출처 `egdesk-tool-result`, 완전(잘림 없음), 쓰기 1회, 내용 해시 주소. 화면/HTTP 첨부로는 만들 수 없다(내부 호출만, 위조 시험 포함).
- **run에 묶기:** `bindToolOutput` (:421)이 그 run의 것인지 확인하고 표시가 붙은 바인딩 기록을 쓴다. `ContextRuntime.spillToolOutput` (`egdesk-context-runtime.mjs:832`)이 살아 있는 바인딩의 읽기 허용 목록에 넣는다. 사람에게 보이는 첨부 목록과 모델의 `egdesk_list_context` 목록에는 넣지 않는다.
- **권한:** 읽기는 기존 검사 그대로다. 다른 대화의 run이 같은 포인터를 쓰면 `CONTEXT_FORBIDDEN` (시험). `canSpill` (:820)은 바인딩 + 읽기 허용 + run당 상한(8건) 미만일 때만 참이고, 이것이 스필 선택지의 존재 조건이다.
- **보존 상한:** `pruneToolOutputs` (:434). 24시간, 계정당 64건, 64 MiB, 건당 4 MiB. 오래된 것부터 소스 기록과 색인 기록을 지우고, 같은 바이트를 다른 소스가 쓰고 있으면 바이트는 남긴다(시험). 만료된 포인터로 읽으면 제품의 일반 문맥 실패 응답이 나오고, 브리지 재시작 복원은 만료된 스필을 건너뛴다(시험).
- **포인터 형식 변경:** 스필 구간마다 한 줄. 전체 줄 범위 + **한 번의 읽기에 들어가는 첫 범위**(추정 1,100 토큰, 200줄 이내)를 바로 쓸 수 있는 인자로 적고, 뒤 범위나 문자열 검색(`query`)을 쓰라는 고정 안내를 붙인다. c5의 "400줄 단위 포인터"는 실제 읽기 도구의 입장 심사(사용량 미측정 시 글 약 1,250 토큰)를 넘겨 Reader 경로로 빠질 수 있어서 바꿨다.
- **알아둘 점:** 다시 읽은 줄은 저장소의 기존 자격증명 가림이 적용된 사본이다(줄 수는 불변, 캡처 때 검사). 예: `Authorization: Bearer ...` -> `Authorization: [REDACTED]`. 기존 가림 규칙의 오탐도 그대로 온다(`tsc -p .`의 `-p` 값이 가려짐). 게이트가 문맥에 남기는 앵커 줄은 지금처럼 도구 원문이다.

## 2. 경계 연결
- **위치 [코드]:** `codex-chat-runtime.mjs:1222` (`dispatchToolProvider`), 메서드 `workingMemoryGate` (:5053), 로직 `helper/egdesk-working-memory-wiring.mjs`. 플래그는 `codex-bridge-server.mjs:480-481`.
- **소비자 선언:** provider가 `workingMemory = { 도구이름: { kind, jsonTextArray? } }`를 가진다. Browser provider에 3개 도구를 선언(`codex-browser-tool-provider.mjs:84`): 페이지 글 배열만 대상이고 카드 id, 관찰 id, 요소 ref, 영수증은 바이트 단위로 그대로다. 이미지 항목은 그대로 따라간다.
- **기본 동작 보존:** 플래그가 없거나 off면 `workingMemoryGate`가 null을 돌려 기존 코드가 같은 틱에 같은 객체를 전달한다. 플래그가 켜져 있어도 선언되지 않은 도구(Claude run 제외)는 동기적으로 건너뛴다.
- **advisory:** 결과 동일, 스필 기록 없음, 보정 로그에 `working_memory` 1건(블록 수, 줄 수, 전후 추정 토큰, 종류, 스필 가능 여부; 글 없음). 2,000 토큰 미만과 미선언 도구는 기록도 안 한다.
- **on (코드 규칙만):** 앵커는 원문, 반복 블록은 스필(가능할 때) 또는 접기(과정 출력만), 반복 없는 글은 그대로.
- **Decision 판정(기록 전용):** Decision 모드가 advisory/on이고 키가 있고 그 run의 모델 권한이 그 글 종류를 허용할 때만, 도구 결과 전달과 무관하게 따로 묻는다. 하위 Agent/일반 도구 출력은 권한 종류가 없어 묻지 않는다(결정 (b)).
- **Claude 한도 초과:** 미선언 도구라도 Claude run에서 한도를 넘는 평문 결과는 on일 때 크기 기준 없이 규칙을 적용한다. JSON 결과와 줄여도 넘는 결과는 그대로 두어 지금의 오류가 난다. 이 경로는 연결 모듈 수준에서 실제 `boundedCallToolResult`로 확인했고, Claude 런타임 전체를 띄운 시험은 아니다.

## 3. 손대지 않는 것 (확인)
- 문맥 읽기는 자체 응답 경로라 이 경계를 지나지 않는다. 플래그 on에서 150줄 반복 첨부를 읽혀도 패킷 글은 원문 전체이고 저장소가 보증하는 전달 해시와 일치한다(시험). 런타임 메서드와 연결 모듈 모두 문맥 provider를 거부한다.
- 스필을 다시 읽은 결과도 문맥 읽기이므로 게이트를 다시 타지 않는다.
- 엔진 네이티브 출력과 이력에는 코드가 닿지 않는다. 변경 없음.

## 6. Main/사용자 결정이 필요한 것
1. **읽기 권한 없는 run에서의 스필.** 지금은 선택지가 없다. 보통 턴에도 스필 전용 읽기 도구를 줄지(새 스레드부터만 가능, 도구 목록 변경), 지금처럼 과정 출력만 접을지.
2. **만료된 포인터의 응답.** 지금은 일반 문맥 실패 문구다. 모델이 "만료"를 알 수 있게 공개 코드를 추가할지(오류 공개 목록은 다른 영역이라 건드리지 않았다).
3. **사람에게 보이기.** 스필/접기가 일어난 사실은 지금 화면에 없다(다시 읽기는 기존 "자료 읽기" 줄로 보임). on을 실사용에 켜기 전에 활동 기록 한 줄이 필요하다고 본다.
4. **Browser 결과의 실효.** 60조각 상한 때문에 기준(2,000 토큰)을 넘는 경우가 드물 것이다. advisory로 실제 분포를 먼저 모으길 권한다.

## 7. 철학 점검
"선택지는 런타임에 존재해야 한다": 스필은 그 run이 실제로 다시 읽을 수 있을 때만 제시된다. 읽을 수 없는 run에서는 내용을 버리지 않고 그대로 준다. "확률은 실행 권한이 아니다": on 경로에서 결과를 바꾸는 것은 코드 규칙뿐이고 Decision은 기록만 한다. "실패하면 지금 방식으로": 스필 저장 실패, 한도 재초과, 권한 없음은 모두 원문 전달 또는 기존 오류다. 권한: 다시 읽기는 기존 문맥 권한과 영수증을 그대로 따르며 새 동의 경로를 만들지 않았다.

## 8. 다음 시뮬레이션 제안

2. 실제 모델에게 고정 문구가 든 결과를 주고 포인터 사용률과 다시 읽기 횟수 측정(구독 엔진 실행 승인 필요).
3. EG-Desk 터미널 읽기 도구(또는 판정 루프 연결)가 생기면 같은 선언 한 줄로 붙여 규칙만 정책의 절감과 오판 측정.
