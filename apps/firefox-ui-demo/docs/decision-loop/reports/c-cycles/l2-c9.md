### 충돌과 중복

1. **한 기능에 스위치 둘 이상 (3건).** 프레즌스, 작업 배치, 브리핑은 브리지 환경변수와 창 pref를 둘 다 켜야 합니다. 브리핑은 셋입니다: pref 값이 `decisionContext` 설정 값과 같아야 하고(`want !== mode`면 `skipped: mode`), on 흐름은 환경변수도 필요합니다. 한쪽만 켜면 오류 없이 조용히 건너뜁니다. (하네스에서 확인한 것은 "전부 끔 → `skipped: mode`"뿐이고, 나머지 조합은 코드 읽기 기준입니다.)
2. **값 어휘가 서로 다릅니다.** 브리핑 환경변수는 `on`만, pref는 `advisory|on`. 작업 배치와 명령 판단은 `advisory`만 있습니다.
3. **`advisory`의 뜻이 기능마다 다릅니다.** `EGDESK_WORK_PLACEMENT=advisory`는 "기록만"처럼 읽히지만, 대화 흐름이 켜져 있으면 사용자에게 실제 채팅 메시지(포인터)가 게시됩니다 (여정 c4에서 확인).
4. **터미널 이름 셋이 겹칩니다.** `COMMAND_JUDGE`(엔진 명령), `TERMINAL_JUDGE`(터미널 카드), `TERMINAL_GATE`(승인 게이트). 명령 판단의 보정 기록 이름은 `terminal_state`라 이름만으로는 어느 스위치의 기록인지 구분되지 않습니다.
5. **숨은 의존.** 중간 메시지는 `EGDESK_CONVERSATION_FLOW=on`에 더해 `EGDESK_DRAFT_CHECK=on`이 있어야 합니다(브리지 주석 기준, 이번에 따로 검증하지 않음).
6. **보정 기록 이름 공유.** 브리핑 판단 6건과 작업 배치 1건이 모두 `board_arrangement`로 기록됩니다. Board 배치까지 세 기능이 한 이름을 씁니다. 브라우저 단계는 `browser_reflex`입니다.
7. **`onePacket`은 도달 불가.** 브리지가 이 옵션을 넘기지 않아 환경변수나 설정으로 켤 수 없습니다. 결과는 아래 A3.

## 3. 교차 기능 발견 (고치지 않음, 담당 레인별)

이번에 제 레인이 분명히 소유한 작은 접합 버그는 없었습니다. 아래는 모두 다른 레인 소유이거나 제품 결정이 필요해 고치지 않았고, 테스트에도 단정으로 박지 않았습니다(원장에만 기록).

**A1. 초안 점검 × 턴 기억 (초안 점검 담당 / L7).** 세션 중간 턴에서 새로 붙일 자료가 없으면, Agent가 이미 그 다섯 페이지를 갖고 있어도 초안 점검은 근거가 0건이라고 보고 날짜·숫자가 든 문장을 전부 "미확인"으로 처리합니다. Decision 요청 없이 로컬 규칙으로 결정되고, 답을 다시 쓰게 하는 포크 턴이 1회 듭니다. 사용자는 Agent의 원래 답이 아니라 다시 쓴 답을 받습니다.
- 증거: `journey-ledger.json` → `findings.A1` (`draftCheckRequests: 0`, `rewriteTurns: 1`, `postedAnswerIsTheAgentsDraft: false`).
- 원인 위치: `codex-chat-runtime.mjs` 2760행 근처. `TURN_MEMORY_KEY` 참조는 이번 턴에 묶음이 붙었을 때만 근거 목록에 들어갑니다. `egdesk-draft-check.mjs` 232행의 "근거 없음 → 전부 미확인" 규칙과 만나 생깁니다.
- 첫 턴(a1)은 묶음이 붙어 같은 문장이 통과합니다. 같은 사실인데 턴 위치에 따라 결과가 달라집니다.
- 더 넓은 질문: 턴 기억이 꺼져 있어도, 앞선 답을 되짚는 후속 질문은 같은 이유로 다시 쓰기에 걸릴 가능성이 있습니다(이번에 확인하지 않음).

**A2. 브라우저 작업 × 기존 대화 (L8).** 일반 턴으로 시작한 대화에서는 브라우저 작업을 시작할 수 없습니다(`BROWSER_TOOLS_UNAVAILABLE`, 409). 그래서 시나리오 b는 요청하신 "한 대화 세션" 안에서 돌릴 수 없었고, 같은 하네스 안의 새 대화에서 돌렸습니다.
- 추가로, 거절은 사용자 메시지가 저장된 뒤에 납니다. 저장된 행은 `status: accepted`이고, 다시 불러온 방에 답 없는 사용자 말풍선으로 남습니다. 증거: `findings.A2`, `screen.restored`.
- 결정 필요: 대화 중간에 브라우저 작업을 허용할지, 아니면 새 대화로 안내할지.

**A3. 컨텍스트 세팅 × 턴 기억 (L7).** 둘 다 on이면 같은 페이지 본문이 한 턴 입력에 두 번 들어갑니다(`egdesk_decision_context`와 `egdesk_turn_memory`). 증거: `findings.A3_sameBodyDeliveredTimes: 2`. 이를 합치는 `onePacket` 옵션은 있지만 켤 방법이 없습니다.

**A4. 보정 기록 이름 (L4 / L7).** 위 1절 6번. 브리핑과 작업 배치가 `board_arrangement`로 기록됩니다. 증거: `totals.calibration`.

**A5. `advisory`인데 사용자에게 보이는 효과 (L4 / L3).** 위 1절 3번.

**A6. 브라우저로 시작한 대화 안의 일반 메시지 (L8, 초안 점검 담당).** 그 대화는 계속 `browserBounded` 정책으로 남습니다. 일반 메시지를 보내도 컨텍스트 세팅, 턴 기억, 초안 점검이 전혀 돌지 않고(Decision 요청 0건), 답이 도착하는 중간 글자가 화면에 그려집니다. "완성된 메시지만"이 이 방에서는 지켜지지 않습니다.
- 증거: `journey-ledger-browser-room.json` (`partialTextOnScreen: [["message.delta","A사 견적은 "]]`).
- 참고: 완성본만 그리는 동작은 현재 초안 점검의 붙잡기에 묶여 있어, 초안 점검이 꺼진 기본 상태에서도 마찬가지로 중간 글자가 보입니다.

**관찰 (제 레인 후속 후보).** 기록 불러오기는 100개 이벤트씩 페이지로 읽습니다. 이 여정의 방은 5턴 만에 이벤트가 130개였고, 첫 페이지만 반영된 순간에는 한 실행 안의 메시지 순서가 실제와 달랐습니다(대기 메시지가 답 뒤로). 마지막 페이지까지 읽으면 맞습니다. 제품이 페이지마다 다시 그리므로 긴 방을 열 때 잠깐 잘못된 순서가 보일 수 있습니다. 탐색 중에 본 것이고 증거 파일로는 남기지 않았습니다. c8 리그의 한 페이지 복원은 이벤트 100개 이하에서만 유효합니다.

## 4. 실행 종료 뒤 포인터 메시지 (화면 리듀서)

`run.completed` 뒤에 오는 `message.started / delta / completed`를 제품 리듀서 경로(`canAdmitChatEvent → reduceChatEvent → syncProtocolRun`)에 그대로 넣었습니다.
- 실시간: 세 이벤트 어느 시점에도 덜 그려진 글자가 없고, 말풍선은 정확히 1개 늘어 마지막 답 바로 뒤에 `complete`로 놓입니다. 방은 다시 바쁨 상태가 되지 않고 작업 표시도 뜨지 않습니다.
- 복원: 새 화면이 실제 기록 라우트를 끝 페이지까지 읽은 뒤, 순서와 내용이 실시간과 같습니다(b0의 거절된 메시지 한 줄만 추가로 보임, A2).

## 5. 전부 끈 경로

같은 일반 턴을 (가) 모든 스위치를 끈 런타임과 (나) Decision 기능 자체가 없는 런타임에서 돌려 비교했습니다. 임시 폴더 경로와 무작위 ID만 치환하고 나면 엔진에 보낸 호출, 내보낸 이벤트, 저장된 메시지 행, 실행 스냅샷이 **바이트 단위로 같습니다**. Decision 요청 0건, 포크 턴 0회, 보정 기록 0건, 하트비트 없음, 쓰기 저장소 파일 미생성, 턴 뒤 60초 동안 추가 메시지 없음. 작업 배치 라우트는 `status: off`, 브리핑 라우트는 `skipped: mode`로 답합니다.
