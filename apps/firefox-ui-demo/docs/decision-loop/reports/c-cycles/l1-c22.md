# L1 cycle 22: Agent profile app-server의 capability와 thread/delete 라우팅, 계정을 바꾼 방의 steer/interrupt/delete

- 워크트리 `wt-l1c22`, 브랜치 `lane/c22-profile-servers` (기준 `int/c14` = `218c711`)
- 커밋 `ebb40ce`, `764ef59`, `cb2d770`. 전부 커밋했다.
- 넓은 게이트 `gate.sh wt-l1c22 l1c22`: **388 files / 6989 tests / 6955 pass / 1 fail / 33 skipped**. 그 1건은 알려진 "every committed plan location is registered"(L2/L8의 미등록 plan)다.
- 변이 11/11 검출. M5와 M10은 처음 0이어서 테스트를 보강했다(§5).
- **보내지 않았다.** mock만 썼다. Firefox와 Codex 바이너리는 쓰지 않았다. 새 사용자 문구와 의존성은 없다.
- 제품 동작이 바뀌는 곳: 프로필 서버(`codex-profile-app-servers`)와 `thread/delete` 허용 판단, 컨텍스트의 `schemaReady`. 새 플래그는 없다(분명히 잘못된 결합 제거). 계정 전환에 관한 부분은 c21의 `EGDESK_ROOM_ACCOUNT` 뒤에서만 데이터가 생긴다(저장소 구간 표는 전환 때 처음 만들어진다).

## 1. 지금 있는 것 (찾은 것)
- **thread/delete 라우팅**: 런타임의 삭제 쓸기(`forgetConversation`)는 이미 스레드의 slot으로 엔진을 부른다(`engine.deleteThread(cid, slot)`). 막힌 곳은 **허용 판단**이었다. 브리지의 `getThreadDelete`가 `id == null || id === 기본`일 때만 참이라 프로필 slot은 늘 거부됐다("remains").
- **capability probe가 공유 서버 것을 빌렸다**: 프로필 서버의 steer 증명(`boardPeerContract`)은 `getBoardPeerContract(bin)`으로 만들어졌는데, 이것은 **공유 서버의 probe 결과**(`nativeCapabilities`)를 같은 경로의 바이너리일 때만 돌려주는 것이었다. 즉 바이너리가 같으면 공유의 것을 상속하고, 다르면 null이었다. 프로필 바이너리 자신의 스키마는 한 번도 검사되지 않았다.
- **다이내믹 툴 준비 판단이 공유 서버에 묶여 있었다**: 컨텍스트의 `schemaReady`가 `nativeCapabilities.schemaMatch && appServerReady`(공유 바이너리와 공유 서버가 떠 있음)였다. 프로필 slot에서 도는 run도 공유 서버가 떠 있어야 했다. U11의 결합이다.
- **계정을 바꾼 방(c21)의 옛 네이티브 대화**: 전환 뒤 방 레코드에는 새 계정만 있고, 옛 대화의 slot은 메모리 지도(`threadEngineProfiles`)에만 있었다. 재시작하면 그 지도가 비어 옛 대화가 **공유 서버로 오라우팅**된다. 또 삭제 쓸기는 방의 **현재** 네이티브 대화만 모았다. 옛 구간의 대화는 삭제되지 않았다.

## 2. 한 일

### (b) 프로필 서버마다 자기 바이너리로 probe (공유 것 상속 없음)
- `egdesk-native-capabilities.mjs`: `capabilitiesOf(native)`는 한 바이너리의 `{version, dynamicTools, ephemeral, turnSteer, threadDelete, boardPeerContract}`를 만든다. 값은 그 바이너리의 생성 스키마가 정한다(기존 `inspectNativeCapabilities` 그대로).
  - dynamicTools는 Context 계약이다.
  - ephemeral은 `thread/start`의 `ephemeral`(같은 계약에 들어 있음)이다.
  - turnSteer는 검증된 peer-input 계약(`TurnSteer` 스키마)이다.
  - threadDelete는 `thread/delete` 스키마다.
- `createNativeCapabilityCache`: 바이너리마다 따로 한 번만 probe한다. 키는 경로, 크기, 수정 시각이라 바뀐 바이너리는 다시 검사한다. 실패는 기억하지 않는다.
- `codex-profile-app-servers.mjs`:
  - 실행 파일 선택이 프로필 id를 받는다(`executable(id)`).
  - 새 옵션 `inspectCapabilities`가 있으면 그 바이너리의 probe 결과만 쓴다. **probe가 실패해도 공유 서버의 것으로 되돌아가지 않는다**(아무것도 주장하지 않는다. 처음 구현은 실패 시 공유 훅으로 되돌아갔고, 테스트가 이를 잡아 고쳤다). 옵션이 없으면 예전 동작 그대로다.
  - `capabilities(id)`는 로그인된 준비 상태의 프로필에만 값을 준다. 로그아웃이면 전부 false, 모르는 프로필도 전부 false다.
- 브리지는 `createNativeCapabilityCache()`를 프로필 서버에 연결했고, 공유 probe를 빌려주던 `getBoardPeerContract`는 프로필 서버에서 뺐다.

### (a) 삭제는 그 스레드를 가진 app-server로, 그 바이너리가 가진 경우에만
- 어댑터 `threadDeleteSupported`와 `deleteThread`: 공유 slot은 공유 probe로, 프로필 slot은 `profiles.capabilities(id).threadDelete`(그 프로필 바이너리의 probe)로 판단한다. 삭제 호출은 이미 `profiles.request(id, 'thread/delete', …)`로 그 서버로 간다.
- 어댑터 `slotCapabilities(id)`가 프로필 서버의 자기 capability를 보여 준다.
- 프로필의 바이너리에 `thread/delete`가 없으면 아무것도 보내지 않고(`THREAD_DELETE_UNSUPPORTED`), 삭제 결과는 "remains(unsupported)"다.

### 컨텍스트 `schemaReady`를 slot별로 (U11)
- 프로필 slot의 run은 **그 프로필 서버의** `dynamicTools`로 판단한다. 공유 서버 상태에 의존하지 않는다. 공유 slot과 Claude는 그대로다. L6의 소스 고정 한 곳(`codex-bridge-http.test.mjs`)은 원래 조각을 전부 유지한 채 새 분기를 더해 갱신했다(약화가 아니라 강화).

### 2. `EGDESK_ROOM_ACCOUNT`가 켜진 방: 옛 대화와 새 run의 라우팅
- 저장소: `roomSegments(clientThreadId)`와 `segmentOf(conversationId)`가 방이 **떠난** 네이티브 대화와 그것이 돌던 계정을 돌려준다. 방을 삭제하면 구간 행도 같이 지워진다(데이터베이스에서 직접 확인).
- 런타임:
  - `threadEngineProfile(cid)`는 메모리 지도가 비었을 때(재시작 뒤) 저장소의 구간에서 옛 대화의 계정을 찾는다. 기억하며, 전환 때 갱신한다. 이 값을 steer, interrupt, 늦은 콜백 응답, 삭제가 쓰는 `threadOperationSlot`이 그대로 쓴다.
  - 삭제 쓸기는 방이 떠난 대화들을 모으고 **스레드마다 자기 계정의 서버**로 `thread/delete`를 보낸다(방의 현재 대화는 방의 저장된 계정으로).
- 방의 **현재** 대화는 구간이 아니다. 재시작 직후 아무 것도 살아 있지 않으면 그 계정은 방의 저장된 값이고(삭제가 쓴다), 방이 다시 열릴 때 지도에 올라간다. 이 동작은 전과 같다.

## 3. (c) 프로필 서버와 공유 서버가 지금 받는 "순수 엔진" 설정 (오늘 상태)

| 항목 | 공유 app-server | 프로필 app-server |
|-|-|-|
| 실행 인자의 기반 | `buildCodexAppServerLaunch`(model, effort, memories 끔을 `-c`로) + `--listen ws://…` | **같은 함수** + `--listen stdio://` |
| 추가 인자 | 없음 | `-c cli_auth_credentials_store=file` |
| 환경 | 브리지의 **전체** 환경(기본 `CODEX_HOME`, API 키 환경 포함) | OS 필수 변수만 + **그 프로필의 `CODEX_HOME`**. 키, dotenv, 프록시 없음 |
| 시작 검사(preflight) | 같은 `preflightOwnedAppServer`(model/effort 설정 읽기, memories 끔 확인) | 같은 함수 |
| capability probe | 시작 때 `inspectNativeCapabilities`(자기 바이너리) | **이번에** 자기 바이너리를 같은 함수로 probe(예전엔 없고 공유 것을 빌림) |
| `mcp_servers` 비움 | **없음** | **없음** |
| 스레드별 설정(ownTools 등) | 런타임이 `thread/start` 덮어쓰기로 보냄 | 같은 경로(런타임이 어느 서버든 같은 덮어쓰기를 보냄) |

- 같은 빌더를 쓰므로 L5가 `buildCodexAppServerLaunch`에 순수 엔진 설정(예: MCP 비움)을 더하면 **두 서버 모두**에 들어간다. 테스트가 "프로필 인자 = 공유 인자(listen 제외) + 파일 자격증명 저장소"임을 고정해 이를 보장한다. 반대로 L5가 환경 쪽을 바꾸면 프로필 서버(화이트리스트 환경)에는 영향이 다를 수 있다.
- 실제 엔진에서 사람의 MCP 서버 8개가 시작되는 것은 **`-c mcp_servers={}`가 인자로 들어가도** 일어난다고 Main이 확인했다. 그래서 이 항목은 L5의 몫이다.

## 6. 남은 것 (이 사이클에서 하지 않음, 소유자 결정은 불필요)
- **다른 provider들의 `schemaReady`는 아직 전역이다**: 브라우저, 계획, 주석 도구와 `qaReady`(제한 실행)는 인자 없이 `nativeCapabilities.schemaMatch/qaReadOnly && appServerReady`를 본다. 프로필 slot의 run이 이 도구를 쓸 때도 공유 서버에 묶인다. 판단 시점에 slot을 넘기도록 provider 계약을 넓혀야 한다(툴 provider를 가진 레인).
- **`ephemeral`은 보고만 한다**: 프로필 서버가 `ephemeralThreads`를 늘 광고하는 것은 그대로다(런타임이 시작 뒤 `ephemeral: false`면 거부하므로 안전). 이를 probe로 막으면 계약 버전이 아닌 바이너리(예: 0.171)의 일회성 방이 막힌다. 정책 결정은 L5와 소유자다.
- 프로필 probe는 시작 때 `spawnSync`로 동기 실행한다(공유 서버가 시작 때 하는 것과 같다). 바이너리당 한 번이다.
- 설치 앱 검증이 아니다.
