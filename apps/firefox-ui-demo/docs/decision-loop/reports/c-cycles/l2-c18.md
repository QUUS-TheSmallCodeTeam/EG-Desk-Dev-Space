## 2. 대화 임시 범위 기억 (결정 3)

- 범위 `dm:<clientThreadId>`로 쓰인 페이지와 그 페이지의 읽기를 삭제합니다.
- 다른 범위(Board, Agent, 개인, 조직)의 페이지는 그대로입니다.
- 삭제된 채팅 메시지만을 원본으로 가리키던 **다른 범위** 페이지는, 글 없이 포인터만 남기고 `sourceDeleted: true`로 표시합니다. 내부 상태이고 화면에는 나오지 않습니다(어디서도 풀리지 않음).

- 테스트: DM 범위 페이지 2개(본문형, 참조형)와 읽기가 지워집니다. 다른 방과 Board 페이지는 바이트 그대로입니다. Board의 참조 페이지는 본문 없이 `sourceDeleted`만 붙어 남습니다. 같은 id로 새 대화를 열어도 지워진 기억이 돌아오지 않습니다. 결과의 `modules.conversation_memory`는 4(페이지 2, 읽기 1, 포인터 1)입니다.

## 3. 엔진 기록 (결정 4)

- 공식 Codex 0.171 app-server에는 `thread/delete { threadId }`(응답 `{}`)와 알림 `thread/deleted { threadId }`가 있습니다.
  - Main이 만든 스키마(`$L/evidence/codex-0171-schema/`)의 실제 파일로 확인했습니다. `ClientRequest` 유니온에 들어 있고 params는 `{ threadId: string }` 하나뿐입니다.
- 확인 방식(기존 스키마 탐침과 같은 방식):
  - 탐침에 **선택 계약**을 더했습니다(`threadDeleteSchemaFingerprint`). `ClientRequest` 유니온 항목, `ThreadDeleteParams`(필수는 `threadId` 하나), `ThreadDeleteResponse`가 모두 맞아야 합니다.
  - 실제 0.171 파일로 통과합니다(`verifyThreadDeleteSchema` true, 디렉터리 검사에서 context/QA/board-peer 계약도 그대로 true).
  - 능력 `threadDelete`는 그 바이너리의 지문이 있을 때만 켜집니다.
  - 컨텍스트 계약 버전이 아닌 바이너리(예: 0.171.0)는 컨텍스트·QA·board-peer 계약을 **얻지 않고** 이 항목만 확인합니다. 기존 "알 수 없는 버전은 모양만으로 받아들이지 않는다" 테스트는 그대로 통과합니다.
- 어댑터: `deleteThread`는 `getThreadDelete`가 켜졌을 때만 `thread/delete`를 보냅니다. 아니면 `THREAD_DELETE_UNSUPPORTED`(409)로 거부합니다.
  - 브리지는 **공유 app-server**에서만 켭니다. Agent 프로필의 전용 app-server는 이번에 증명하지 않았으므로 `remains`로 보고합니다.
- 삭제 결과에 `engineHistory: [{ conversationId, engineId, state: 'deleted' | 'remains', reason?: 'unsupported' | 'failed' }]`가 들어갑니다. 엔진 호출이 실패해도 EG-Desk 쪽 삭제는 계속됩니다.
- 테스트(가짜 app-server): 스키마가 있는 세계에서는 `thread/delete`가 `{ threadId }`로 한 번 가고 `thread/deleted` 알림이 와도 저장소는 정상입니다. 없는 세계에서는 호출이 0이고 `remains/unsupported`입니다. 실패하는 세계에서는 `remains/failed`이고 EG-Desk 기록은 지워집니다.
- **Claude**: 어댑터에는 삭제 경로가 없습니다(`releaseThread`뿐). 그래서 `remains/unsupported`로 보고합니다.
  - 일반 대화는 `--session-id` / `--resume`으로 CLI의 세션을 쓰며, `--no-session-persistence`는 한 번짜리 print 경로(`claude-engine-transport.mjs:403`)에만 붙습니다.
  - 따라서 CLI가 자체 설정 폴더(`CLAUDE_CONFIG_DIR` 또는 기본 폴더)의 `projects/` 아래에 세션 기록을 저장할 것으로 보입니다. **이 저장 위치와 삭제 가능 여부는 이번에 확인하지 못했습니다**(Claude 바이너리를 실행하지 않았고 이 저장소에 그 경로를 아는 코드가 없습니다). 지우려면 EG-Desk가 소유하지 않은 폴더의 파일을 지워야 하고 경로도 cwd 인코딩에 의존하므로, owner 결정과 별도 확인이 필요합니다.

## 4. 삭제 뒤에 어디에 무엇이 남는가 (정확히)

**EG-Desk의 채팅 저장소 (삭제됨)**: 방 기록, 메시지, run, 이벤트, 요청, 멤버, 참조. 삭제 후 재시작해도 없음. 파일 바이트에도 없음.
**업그레이드 백업**: 파일은 남고, 이 대화의 행은 지움.
**임시 상태**: 하트비트, 받은 기억·컨텍스트 기록, 확인 대기 메모, 보관된 포인터, 브라우저 작업, 브리핑 바인딩, 요청자, 작업 배치, 이어 보낼 메시지를 지움.
**실행 중이던 run**: 중단하고 이후 아무것도 저장하지 않음.
**기억**: 이 대화에서 들은 pending 읽기를 철회함. 대화 임시 범위의 페이지와 읽기를 지움.

**남는 것**
1. **다른 범위의 기억**(Board, Agent, 개인, 조직)과 온톨로지 페이지, 승격(accepted)·거부된 읽기. 정본상 Memory이고 `[기억]`에서 지웁니다. 페이지 본문에는 사람의 말이 들어 있을 수 있습니다. 삭제된 메시지만 가리키던 페이지는 글 없는 포인터(`sourceDeleted`)로만 남습니다.
2. **동의로 쌓인 발언·주제 기록**(`egdesk-memory-evidence`): 정본상 Memory이므로 남습니다. **이 저장소에는 글이 들어가지 않습니다.** 각 항목은 로컬 메시지 id, 순번, 시각, 문장 구간 라벨, 메시지 글의 sha256 해시만 갖습니다. 채팅 기록이 지워졌으므로 이 참조는 어디에서도 글로 풀리지 않습니다(읽을 때 채팅 저장소에서 확인하다가 실패하면 비워 줍니다). 다만 메시지 id와 해시는 남습니다.
   - **c17 보고서의 "이 기록들에는 사람의 말이 남습니다"는 틀렸습니다.** 이번에 저장 스키마를 읽고 바로잡습니다.
3. **c17 이전에 저장된, 대화가 기록되지 않은 pending 읽기**: 결정 1에 따라 그대로 둡니다.
4. **보정 기록**: 내용이 없고 대화 id도 없습니다(c16에서 33행 확인).
5. **보드에 게시된 카드와 출력**: 정본은 "Board 참조 변경·화면 닫기·업무 기록 삭제는 각각 별도"입니다. 바인딩만 지웠습니다.
6. **엔진이 가진 기록**: Codex는 `thread/delete`를 지원하는 공유 app-server일 때만 삭제됩니다. 그렇지 않으면 남습니다. Agent 프로필 전용 app-server의 스레드는 이번에 삭제하지 않습니다(`remains`). Claude는 위 3절. 어느 쪽이든 결과의 `engineHistory`가 알려 줍니다.
7. **EG-Desk 밖**:
   - OpenAI Decision 모델에 이미 보낸 요청은 이 프로그램이 지울 수 없습니다.
   - 운영체제나 백업 도구(Time Machine, APFS 스냅샷)의 복사본도 EG-Desk가 지울 수 없습니다.
   - SQLite 파일 자체는 `secure_delete`, WAL 비우기, 백업 `VACUUM`으로 글자가 남지 않음을 테스트했지만, 파일시스템 수준의 잔여물은 보증하지 않습니다.

3. **발언·주제 참조의 해시**: 이미 지워진 메시지의 sha256 해시와 메시지 id가 남습니다. 삭제된 메시지의 참조는 `[기억]`에서만 지우게 둘지, 대화 삭제 때 함께 지울지 (owner, L7).

5. L3 c22가 c17 계약으로 통합되면 L3의 4개 테스트가 통과해야 합니다. 그때 `forgetConversation`은 비동기가 되었으므로 호출하는 쪽은 `await`가 필요합니다(HTTP 경로는 이미 `await`).
