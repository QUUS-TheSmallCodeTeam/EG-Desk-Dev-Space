## 1. 점검 도구 `scripts/egdesk-real-engine-check.mjs`

실제 런타임 경로를 구동함. `helper/egdesk-real-engine-check.mjs`가 `codex-bridge-server.mjs`와 같은 생성자로 `CodexChatRuntime`을 조립함(own tools wiring, 대화 저장소, ContextRuntime, Decision client와 egress gate, turn memory, draft check, heartbeat 플래그, terminal gate). 다시 쓴 것이 아니라 같은 모듈을 부름. 단 bridge 서버 파일은 import할 수 없는 단일 스크립트(포트 39218/39219 고정)라서 조립 부분은 도구 쪽에 있음. 그래서 **드리프트 방지 테스트**를 둠: bridge의 `decisionContext` 블록에 새 키나 `process.env.EGDESK_*` 플래그가 생기면, 도구가 재현하거나 `notReproduced`로 이유와 함께 적지 않는 한 테스트가 실패함(실제로 `relevanceRules`를 잡아냈음). 재현하지 않는 것: Browser Card, Desk presence, work placement, briefing, HUD(창이 필요함).

## 5. 순수 엔진 공백: 사람의 홈을 쓸 때 무엇이 샘

방법: 0.171 설정 타입(`core/config.schema.json`, `features/src/lib.rs`)과 Main의 스키마만 읽었고 사람의 설정은 읽지 않음.

**c18의 `pureEngineThreadOverrides()`가 끄는 것**: 엔진의 shell, unified_exec, view_image, web_search, 프로젝트 문서(`project_doc_max_bytes=0`). **끄지 않는 것**(사람의 홈에서 그대로 활성): 사람의 MCP 서버, 플러그인과 그 MCP 서버, apps/connectors, hooks(사람의 hook이 엔진의 모든 이벤트에 걸림), skills(카탈로그와 지침 블록), memories(기능 기본은 off이나 사람의 설정이 켤 수 있음), 하위 에이전트, 전역 AGENTS.md(아래 참고), 모델과 effort(사람의 config.toml 상속).

**Main 실측(MCP 누수)**: 스레드 시작 시 서버 8개에서 `startupStatus` 16회, `-c mcp_servers={}`는 효과 없음. 설정 레이어가 테이블 단위로 합쳐지므로 빈 테이블은 사람의 항목을 지우지 못한다고 읽힘(c19 이전 QA 경로의 0.160.1 메모와 같은 결론). **제품은 시작 인자로 `mcp_servers={}`를 넣어도 얻는 것이 없으므로 넣지 말 것**. `features.memories=false`는 이미 `EGDESK_CODEX_DISABLE_MEMORIES=1`(시작 인자)로 제품에 있음.

**제안(구현함, `EGDESK_OWN_TOOLS=on`과 같은 플래그, 기본 off)**: `helper/egdesk-own-tools-isolation.mjs` → `ownToolsIsolationOverrides`가 own-tools 스레드의 `thread/start` config에 다음을 병합함(`codex-chat-runtime.mjs`, 이름 `loadOwnToolsIsolation`).
1. 사람의 직접 MCP 서버를 **이름별** `mcp_servers.<이름>.enabled=false`. 이름은 `config/read`(레이어)와 `mcpServerStatus/list`에서 읽음(모양만, 명령/URL/env는 복사도 보관도 안 함). 이것은 이미 QA 스레드가 쓰는 방식(`qaThreadOverrides`)임.
2. 플러그인이 제공하는 서버는 `plugins.<id>.enabled=false`(이름 stub은 전송 없는 항목을 만든다는 0.160.1 발견 때문에 쓰지 않음).
3. `features`: `apps`, `hooks`, `plugins`, `remote_plugin`, `multi_agent`, `memories`, `skill_search`, `browser_use`, `browser_use_external`, `computer_use` = false, `code_mode.enabled=false`.
4. `skills.include_instructions=false`, `skills.bundled.enabled=false`, `include_apps_instructions=false`.
5. 목록을 읽지 못하면 던지지 않고 features/skills 스위치만 두고 `mcp: unchecked`로 기록함(P2). off일 때는 목록을 읽지도 않음(테스트로 고정).
6. 후보로 두 가지를 더 구현했으나 기본은 둘 다 꺼짐: `EGDESK_OWN_TOOLS_ENVIRONMENTS=none`이면 `environments: []`를 추가함(0.171 `ThreadStartParams.environments`의 문서: "Empty disables environment access"). MCP 서버가 환경에 묶이는지는 알 수 없음(`mcpServerStatus`에 `environmentId`가 있음). Main이 점검 도구에서 `flags: {EGDESK_OWN_TOOLS_ENVIRONMENTS: "none"}`로 비교해 볼 수 있음.

**점검 도구의 읽기**(`readOwnToolsIsolation`, 첫 턴 뒤): `mcpServerStatus/list`(threadId) 서버 수와 도구가 있는 서버 수, `experimentalFeature/list`(threadId)에서 끄려던 기능 중 꺼지지 않은 것의 이름, `hooks/list`(threadId) hook 수, `ThreadStartResponse.instructionSources`에서 엔진 폴더 밖에서 로드된 지침 파일 수, 모델과 effort. 서버, hook, skill, 파일 이름은 기록에 없고 개수와 Codex의 기능 이름만 남음. 그리고 대화 기록의 `mcpStartup`이 `mcpServer/startupStatus/updated`의 starting/ready/failed 개수를 세어, Main이 본 "16회"가 사라졌는지 바로 비교할 수 있음.

**남는 공백(정직하게)**:
- 전역 `~/.codex/AGENTS.md`: 설정 키에서 끄는 스위치를 찾지 못했음. `project_doc_max_bytes=0`은 프로젝트 문서에 관한 것이고 전역 지침도 막는지는 모름. `instructionSources.outside`가 0이 아니면 샌다는 뜻임. 스위치가 없으면 해법은 EG-Desk 소유의 Codex 홈(Main이 말한 "later")뿐임.
- 모델과 effort는 사람의 config에서 상속됨(Main 실측: effort "ultra"). 소유자 규칙 U11(프로필, 계정, 폴더, 화면이 따로 조합됨)대로라면 EG-Desk가 프로필에서 모델과 effort를 정해 매 턴 `model`/`effort`로 보내야 함. 점검 도구는 `--model`/`--effort`로 이미 그렇게 함(런타임의 `body.model`/`body.effort` 경로). 제품이 own-tools 스레드에서 프로필의 값을 항상 보내도록 하는 일은 프로필 모델이 있어야 해서 이번에 만들지 않았음.
- `mcpServerStatus/list`를 스레드 없이 부르는 것이 서버를 시작시키는지는 확인하지 못했음(스레드 시작 시 시작 알림이 오는 것만 확인됨). 점검 도구의 `mcpStartup`은 스레드 시작 전에 온 알림도 세므로 이 점도 드러남.
- 키가 실제 바이너리에서 지켜지는지는 미확인임. 위 읽기가 그 확인 수단임.

## 9. L3 요청: `whileRunning` (c23 스크립트 4개)

- 형식: 턴의 선택 필드 `whileRunning: { afterMs: 0..120000 }`. 이 턴의 `say`를 **이전 턴이 아직 일하는 중에**, 그 턴이 *시작한 뒤* afterMs 시점에 `chat.send({ clientThreadId, conversationId, inRunMessageTo: <그 실행의 runId> })`로 보냄. 새 턴을 시작하지 않고 두 턴이 모두 끝나기를 기다림.
- 검증기 규칙(스키마 JSON도 갱신): 첫 턴 불가, 다른 whileRunning 바로 뒤 불가, `approve` 불가, 그 대화의 `flags.EGDESK_INRUN_MESSAGES = "on"` 필수, afterMs 정수 범위.
- 기록: 이전 턴의 `expect`는 **두 턴 전체 창**(게시된 모든 메시지, 도구 호출, 명령, 상태)에 적용되어 `turnStatus completed`(명령이 중단되지 않음), `commandsRan`, `answerIncludes`가 그대로 유효함. whileRunning 턴의 `expect`는 **보낸 뒤**에 일어난 것(그 뒤 게시된 메시지, 그 뒤의 도구 호출과 명령)에 적용됨. 이 턴에는 암묵적 검사 `sent_while_running`이 붙음: 실행이 이미 끝나서 런타임이 `INRUN_MESSAGE_UNAVAILABLE`로 거절하면 그 코드와 함께 실패함.
- L3의 4개 스크립트(correction, why-stopped, terse-yes, topic-return)는 이 검증기로 **모두 통과**함(`evidence/l5-c22/l3-scripts/`). 구성에 `inRunMessages`(bridge가 `EGDESK_INRUN_MESSAGES=on`일 때 `decisionContext.inRunMessages`를 넣음)를 추가했고 드리프트 테스트가 그 키를 먼저 잡아냈음.
- 사전 점검 추가: `EGDESK_DRAFT_CHECK`, `EGDESK_CONVERSATION_FLOW`, `EGDESK_COMMAND_JUDGE`, `EGDESK_WORKING_MEMORY`, `EGDESK_CONTEXT_RELEVANCE`, `EGDESK_TERMINAL_GATE`는 Decision 모델이 답할 때만 동작하므로, 스크립트가 이들을 켜는데 `--decisions`가 없으면 --run을 거부함(`why-stopped`는 `--decisions`와 키가 필요함).
- **발견(L2/Main)**: 메시지를 실행에 steer하려면 제품은 엔진 바이너리의 steer 계약(`inspectNativeCapabilities`의 `boardPeerContract`)을 요구하는데, 코드는 그것을 **0.162.1에만** 인정함. 지금 사람의 Codex(0.171.0-alpha.13)에서는 계약이 없으므로 `settleInRunMessage('steer')`가 `no steer contract`로 실패하고 메시지는 대기 상태로 남아 다음 턴에 실립니다(Main의 실측은 프로토콜 수준에서 steer가 동작함을 보였음). 점검 도구는 플래그가 켜진 대화에서 같은 함수를 바이너리에 대해 실행(`--version`과 스키마 생성, bridge가 시작할 때 하는 일)해서 `engine.nativeContract {version, schemaMatch, boardPeerContract}`로 기록하므로, 실제 실행에서 바로 확인됨. 이번에 계약을 0.171로 넓히는 일은 하지 않았음(검증 근거가 필요함).
- 한계: 가짜 app-server는 `turn/steer`를 구현하지 않음(테스트는 `sent_while_running`, 새 턴이 시작되지 않음, 두 턴의 기록 분리, 너무 늦은 메시지의 거절까지). steer/reply/interrupt의 판정 자체는 L2/L3의 테스트 영역임.
