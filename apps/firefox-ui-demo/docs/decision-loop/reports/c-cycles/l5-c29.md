## 2. 제품에서 발견하고 고친 두 가지 (가짜 검증이 먼저 잡았음)
1. **자체 명령은 답의 초안 점검에게 내용 없는 참조였음.** 엔진이 `egdesk_run_command`로 돌린 명령은 활동이 `dynamicToolCall`이라 `answerFactsEvidence`가 불투명 참조로만 넘겼고, "테스트가 모두 통과했습니다"를 지지하거나 반박할 근거가 없었음(heartbeat 메시지의 근거에만 c21의 요약 줄이 있었음). 이제 실행기가 모든 명령의 기록(명령줄, 종료 코드, 중재자의 읽기, 러너 요약 줄과 집계)을 `run.ownCommands`에 순서대로 두고(`helper/egdesk-own-command-evidence.mjs`), 답의 근거가 그 명령들을 터미널 근거로 줌(요약 줄 인용은 `command_output`이 허용될 때만, 아니면 집계만; 읽기/편집 같은 다른 자체 도구는 그대로 참조). 
2. **거짓 "모든 테스트가 통과했습니다."는 초안 점검이 못 잡았음**(가짜 부정 테스트가 `would_pass`로 통과시킴). 이유 둘: 술어 설계는 숫자/이름/식별자가 있는 문장만 "근거 없음"으로 보고(`isCheckable`; 이 문장엔 없음), 근거 중 하나라도 불투명하면(엔진의 읽기/편집 호출) 근거 없음 판정을 아예 안 함. 그리고 이 설계에는 "반박" 질문이 없음. 수정(작고 코드 규칙, 모델에 묻지 않음): `helper/egdesk-draft-run-facts.mjs`: "테스트가 통과했다"는 문장(실패/부정어 없음, 테스트·빌드 단어나 "전부/모두")이 마지막 자체 명령의 사실(실패 ≥1, 종료 코드 ≠0, 멈춤, 끝나지 않음)과 모순되면 `contradicted` 발견으로 추가(기존 개정 문구 재사용, 새 문구 없음). 모델이 "지지됨"이라 답해도, 모델이 내려가 있어도 발견되고(그땐 다시 쓴 글을 재점검할 수 없어 `withheld`), 다시 쓴 글이 같은 거짓을 반복해도 재점검에서 걸림(재점검이 걸러내던 "구체적인 문장만" 규칙에 이 주장도 포함). 자체 명령 근거가 없으면 동작은 이전과 동일(기존 초안 점검 테스트 전부 통과).
- 영향 범위(L3에게 알림 필요): `egdesk-draft-check.mjs`에 세 줄(import, 근거 행에 `facts` 통과, `judge`에서 규칙 발견 병합과 모델 호출 실패 시 규칙 우선), 규칙은 새 모듈에 있음. 보정(calibration) 행에는 규칙 발견이 모델 판정으로 들어가지 않고 행의 `check`(`would_revise`)로 나타남.

## 3. Main의 두 추가 요청
- **스키마 파일은 등록의 순수 함수**: `helper/egdesk-real-engine-schema-file.mjs`(정규 렌더링: 키 정렬, 배열 순서 유지, 끝 개행), `scripts/real-engine/regenerate-schema.mjs`(`--check`로 최신 여부 확인), 테스트가 재생성한 텍스트와 커밋된 텍스트를 **문자열로 비교**(충돌 표식 없음, 렌더링이 고정점, 정렬 규칙 단위 테스트). 충돌이 나면 항상 스크립트로 다시 생성하면 됨(이번 병합 두 번 모두 그렇게 해결, 파일은 키 정렬이라 서로 다른 키 추가가 서로 다른 줄을 바꿈).
- **레지스트리 테스트는 레인별 불변식**: 정확한 전역 목록 대신 `LANES` 표(L1 collab·from·hook, L2 engine·journey, L4 briefing, L5 deleted·coding·seededWrites·hook, L7 memory·필드·hook, L8 browserAnswer·browserTask·hook)의 각 키가 등록됨, 이름이 둘이 아님, 스키마가 생성 스키마에 있음, 순서 규칙은 `memory` 훅이 `journey`보다 앞인 하나뿐, 코어의 `EXPECT_KEYS`에 레인 키가 글자로 없음(레지스트리가 더함). 레인이 키를 더하면 표에 자기 줄만 더하면 됨(나머지 레인의 키는 이 테스트를 깨지 않음).
- **`whileRunning … ended before afterMs` 부하 불안정(c27 수정 후에도 남았던 원인)**: `deps.sleep` 이음매가 `wait > 0`일 때만 불렸음. 부하에서 이미 afterMs가 지났으면(`wait ≤ 0`) 이음매를 건너뛰고 곧바로 메시지를 보냈고, 그때 run이 아직 끝나지 않아 메시지가 받아들여졌음(그리고 이음매 조건이 "run이 없으면 끝난 것"으로 읽힐 수도 있었음). 이제 이음매는 항상 불리고(`Math.max(0, wait)`), 테스트의 대기는 "run이 존재하고 모두 끝났음"을 기다림. 증명: CPU 점유 프로세스 8개를 띄운 채 **10개 동시 실행 10/10 통과**, 그리고 whileRunning/action/interrupt/steer 테스트 7개를 같은 조건에서 10개 동시 실행 10/10 통과.
