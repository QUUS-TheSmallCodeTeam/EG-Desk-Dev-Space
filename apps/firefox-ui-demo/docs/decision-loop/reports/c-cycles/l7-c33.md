## 1. check-12와 check-15 맞추기, 설계할 한도

모든 항목은 turn당 `egdesk_decision_context` 한 항목 (이 check 구성에는 다른 항목이 없음). 크기는 UTF-8 바이트 기준으로 다시 정리했습니다:

- **check-12의 한글 n2(3,556자)가 실패했는데 check-15의 kr-1400(2,716자)은 통과한 이유**: 글자 수가 아니라 **바이트**가 기준이기 때문입니다. n2는 6,340바이트로 한도를 넘었고 kr-1400은 4,682바이트로 아래였습니다. 결정적 비교: 영어 en-4000은 5,295자인데 통과, 한글 n2는 3,556자인데 실패 → 글자 수 기준은 틀렸고(c32 때 내 가설이었음) 바이트 기준이 맞습니다. 합계 한도도 아닙니다 (split-n8: 항목 9개, 합 약 25kB가 온전).
- 임계값은 **5,295바이트 초과 6,340바이트 이하**입니다. (문서의 2,500 토큰이 이 범위에 닿으려면 토큰당 약 2.1~2.5바이트로 센 셈인데, 이는 추정일 뿐입니다.)
- **설계 한도: 4,000바이트** (`EGDESK_TURN_MEMORY_ENGINE_BYTES` 기본). 근거: 관측된 가장 큰 통과(5,295) 아래로 약 24%, 가장 작은 실패(6,340) 아래로 약 37% 여유; check-15에서 온전히 전달된 가장 큰 부분(3,251)보다 위. 엔진 버전이 바뀌면 한도도 바뀔 수 있으므로 probe v2를 엔진 버전 갱신 때마다 다시 돌리는 것을 권합니다 (대화 8개, 약 1분).
- 코드 변경 (c32의 글자 한도를 바이트로): `splitEngineContext`/`spilledKeys`/`emulateSpill`이 UTF-8 바이트를 잽니다 (기본 4,000; 글자 한도 `EGDESK_TURN_MEMORY_ENGINE_CHARS`는 추가 상한으로만 남김: 이미 보낸 probe v2 JSON이 이것을 씀). 한글 2,000자는 약 6,000바이트라서 c32의 "2,000자" 한도로는 한글 항목이 한도에 닿을 수 있었습니다 — 바이트로 바꾼 가장 큰 이유입니다.
- **한 항목이 혼자 한도를 넘는 경우 처리 추가**: 한 페이지가 4,000바이트를 넘으면 (한글 약 1,300자 이상) c32는 그 항목을 그대로 두고 `oversize`로만 알렸습니다. 이제 그 항목을 **항목 안에서 문장 경계로** 나누고 뒤 조각은 `(continued: item id=…, part k of n)` 줄로 시작합니다 (항목 헤더는 한 번만, 문장은 한 번씩 순서대로: 테스트). 실제 페이지는 길어서 필요한 처리입니다 (scale의 네트워크 페이지 5,397바이트).

## 2. owner용 증거: `EGDESK_TURN_MEMORY_ENGINE_CONTEXT=split`을 기본 켬으로 할 때 (기본값은 바꾸지 않았습니다)

**무엇이 바뀌나**: turn/start의 additionalContext에서 한 항목이 4,000바이트를 넘을 때만, 그 항목이 `key`, `key_part2`, …로 나뉘어 갑니다 (항목 경계, 필요하면 항목 안 문장 경계). 4,000바이트 이하의 항목, `untrusted` 항목은 그대로입니다. 모델에게 가는 내용은 빠지거나 바뀌지 않습니다 (이어 붙이면 원문과 같음: 테스트). Decision 요청은 전혀 바뀌지 않습니다.

**증거 (스크립트 world, 저니 v7; `evidence/l7-c33/split-compare.json`, `sweep-split.jsonl`)**:
- 저니 v7 (기본, one packet 켬 두 경우 모두): 켬과 끔의 Decision 요청, 체크, 패킷 키와 바이트가 **완전히 같음** — 이 저니의 페이지는 짧아 4,000바이트를 넘는 항목이 없습니다 (가장 큰 3,584바이트).
- 페이지 본문 길이를 키운 첫 턴 (one packet 켬, 엔진 대역은 항목당 4,000바이트에서 자름):

| 본문 | 끔: 항목 수 / 가장 큰 항목 / 합계 / 대역이 자르나 | 켬: 항목 수 / 가장 큰 항목 / 합계 | 추가 바이트 | 추정 엔진 입력 토큰 |
|---|---|---|---|---|
| 50자 (저니) | 3 / 3,584 / 4,856 / 아니오 | 3 / 3,584 / 4,856 | 0 | 0 |
| 204자 | 3 / 5,434 / 6,706 / **예** | 4 / 3,860 / 6,791 | +85 (+1.3%) | +28 |
| 743자 | 3 / 11,909 / 13,181 / **예** | 7 / 3,808 / 13,521 | +340 (+2.6%) | +113 |
| 2,283자 | 3 / 29,719 / 30,991 / **예** | 13 / 4,000 / 32,136 | +1,145 (+3.7%) | +381 |

  즉 비용은 조각마다 이어짐 줄 약 95바이트 (추가 2~4%)이고, 이득은 지금 잘리고 있는 항목이 안 잘리는 것입니다. 실제 사용자 페이지는 수백~수천 자이므로 지금은 기본값이 **조용히 모델에게 가운데를 안 보여 주는 상태**입니다.
- 실제 엔진: probe v2의 split-n4/n8에서 표식 전부 (check-15). 항목 안 나누기와 여러 조각 안의 규칙 문장 전달은 scale-v3가 처음 실제로 확인합니다 (아래 3).

**위험과 모르는 것 (켠다면)**:
1. 한도 값은 관측 범위(5,295 통과 ~ 6,340 실패)에서 정한 추정이고 엔진 버전에 의존합니다 → 엔진 갱신 때 probe v2 재실행.
2. 규칙 문장(시제 지침 "계획이나 가정을 현재 사실로 말하지 말 것" 등)은 첫 조각에만 있고 뒤 조각은 "같은 규칙" 한 줄로 이어집니다. 모델이 뒤 조각의 항목에도 적용하는지는 scale-v3의 2턴(계획과 가정 구분)이 실제로 처음 시험합니다 (v1에서 모델이 둘을 정확히 구분했음).
3. 항목 안을 나누면 한 페이지가 여러 항목 조각에 걸칩니다. 모델이 이어 읽는지는 scale-v3 1턴(네트워크 페이지 5.4kB의 마지막 문장 "한유진")이 시험합니다.
4. 나누지 않는 것: `untrusted` 항목(보드 피어 등)은 자체 규칙이 있고, 브라우저 작업 보류 경로(`hold.additionalContext`)와 steer 경로는 이번 모양 변경에서 빠져 있습니다 (그쪽 항목은 작음; 커지면 같은 한도가 걸림).
5. 초안 검사: 나누면 아무것도 잘리지 않으므로 증거는 그대로 (테스트: 켬과 끔의 evidence id 동일). 안 나눈 큰 항목은 c32의 `mark`처럼 "일부만 보임"으로 취급.
6. 한 문장이 4,000바이트를 넘으면 글자 단위로 자릅니다 (극단적인 경우; 테스트).
권고: 기본 켬 (이득 큼, 비용 2~4%, 짧은 항목은 동일). 켜기 전에 scale-v3 실행으로 위험 2, 3을 닫을 것을 권합니다.

## 3. scale-v3 재실행 (Main): `real-engine-memory-scale-v3.json`
- scale-v1과 v2의 질문에 split 켬: 플래그 `EGDESK_TURN_MEMORY_ENGINE_CONTEXT=split`, `EGDESK_TURN_MEMORY_ENGINE_BYTES=4000` 포함 (스크립트가 세팅; 환경 지정 불필요), `PRUNE_HELD`, `ONE_PACKET`, `SELECTION_HELD`도 켬.
- 1턴 (v1의 질문): 긴 페이지 네 개(개요 4.3kB, 네트워크 5.4kB, 데이터베이스 3.3kB, 스토리지 2.0kB)에서 사실을 하나씩 (각 페이지 마지막 5분의 1): 네 사실이 답에 있어야 하고, 어떤 키도 4,000바이트 이하 (`maxKeyBytes`, 새 기대값: 키별 UTF-8 바이트), 본문 두 번 없음, 두 페이지 이상 merged. 네트워크 페이지는 혼자 한도를 넘어 항목 안 나누기를 거칩니다.
- 2턴 (v2의 질문): 본 전환이 끝났는지, 언제로 계획됐는지, 문제가 생기면; 날짜와 숫자가 답에, 완료나 결정으로 말하지 않음, 재전송 없음, 키 4,000바이트 이하.
- 명령: `node scripts/egdesk-real-engine-check.mjs --codex-bin <bin> --person-home --decisions --out <dir> --run --script scripts/real-engine/scripts/real-engine-memory-scale-v3.json`, 채점 `node scripts/egdesk-real-engine-memory-score.mjs <dir>/records` (키별 바이트, 엔진 입력, 빠진 사실이 나옴).
- 가짜 엔진 검증 (스키마 검증됨): 1턴은 4개 이상의 항목, 모두 4,000바이트 이하, 엔진 대역이 아무것도 자르지 않고 네 사실이 모두 보임; 같은 턴의 split 없는 버전은 대역이 가운데 사실을 잃음 (실제 check-8과 같은 모양).
