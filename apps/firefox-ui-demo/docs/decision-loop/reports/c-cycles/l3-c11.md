## 사용자 방향 반영
"별도의 내부 시간 카운터가 필요하다. 현재 시점과 흐름을 보고 중간 메시지가 필요한지 Decision 모델이 판단한다 = 라이브 세션의 하트비트." c9의 틱(5 s·사전 필터·10 s/30 s/실행당 3개/요청 6회)을 **독립 모듈의 하트비트**로 올리고, 런타임의 흐름 판단은 그 비트에서만 일어나게 바꿨다.

## 1. 하트비트 컴포넌트 (`helper/egdesk-heartbeat.mjs`, 신규)
- **자기 시간 카운터**: 단조 시계(`performance.now`, 주입 가능)로 "달린 시간(ms)"을 직접 센다. 엔진 이벤트를 받아서 시간을 재지 않으므로 엔진이 조용하거나 멈춰도 뛴다(시험: 엔진 이벤트 0개로 5/10/15/20/25 s 비트). 엔진 이벤트는 카운터 위의 **표시(mark)** 하나를 옮길 뿐이다.
- **대화당 하나**: `createHeartbeats().open(key)`(키 = 로컬 대화 id). 같은 키의 살아 있는 것이 있으면 `superseded`로 멈춘다. 동시에 최대 64개.
- **수명 주기**: `idle → running ⇄ paused → stopped`. 시작 = 사용자 메시지 접수 시점을 0으로(런타임이 접수 순간의 단조 시각을 기억해 `start({ sinceMs })`로 전달). 일시정지 = 최종 답변을 검사·게시하는 동안(카운터와 비트가 멈춤). 정지 사유(닫힌 집합): `run_end`, `cancel`(중지), `disconnect`, `restart`(엔진 프로세스 소실), `start_failed`, `superseded`, `limit`. 정지 뒤에는 타이머·등록·구독이 남지 않고 다시 시작할 수 없다. **저장하지 않는다**: 재시작 뒤에는 새 메시지가 접수될 때까지 하트비트가 없다(재시작 안전).
- **박동(문서화된 상한)**: 5 s마다 1비트(카운터의 격자에 맞춤), 타이머가 늦으면 **한 번만** 세고 놓친 비트를 재생하지 않음, 하트비트당 최대 720비트(1시간) 뒤 `limit`으로 자진 정지, 타이머는 항상 1개.
- **비트의 사실**(숫자·불리언·닫힌 라벨만; 자유 문자열은 버림): `sinceUserMs`(사용자의 마지막 메시지 이후), `sincePostedMs`(마지막 게시 메시지 이후, 없으면 null), `sinceEngineMs`(마지막 엔진/도구 이벤트 이후), `phase`(`thinking`/`tool_running`/`waiting_user`/`objective_step`; 우선순위는 사용자 대기 > 객관 루프 > 도구 실행 > 생각 중), `pendingQuestion`, `stepsDone`, `stepsRunning`, `stepsRemaining`(알려진 경우만, 아니면 null), `sources`(등록된 제공자별 사실).
- 비트 자체는 비용이 0이다(사실 계산과 구독자 통지뿐). 묻거나 보내는 것은 구독자의 일이다.

## 2. 비트에서의 Decision 판단 (`egdesk-conversation-flow.mjs`, 런타임 `flowEvaluate`)
- 선택지는 런타임이 열거: `none` / `explain_wait` / `ask_missing` / `milestone` / **`stalled`(신규: 엔진이 조용함)**. 요청은 c10의 공통 egress 게이트(`run_facts`)를 그대로 통과하며 사실 줄에 `current_phase`, `seconds_since_anything_came_from_the_work`, (알려지면) `steps_known_to_remain`, 미답 질문 여부가 추가됐다. 텍스트는 없다(시험: 도구 명령·사용자 문장 미포함).
- **사전 필터(요청 0)**: `none`만 가능하면 묻지 않는다. 사용자를 기다리는 단계(승인·입력·객관 루프의 사용자 대기)에서는 `none`만, 메시지 3개를 채웠거나 직전 게시 후 30 s 이내면 `none`만.
- **상한(유지 + 하나 강화)**: 첫 메시지 10 s 이후, 메시지 간 30 s, 실행당 3개, 요청 실행당 6회·10 s당 1회. 추가: 한 번도 제안된 적 없는 종류가 새로 가능해지면 10 s 간격을 한 번 건너뜀(멈춤을 5 s 안에 판단하기 위해), `none` 답이 이어지면 같은 질문의 간격을 10→20→40→80 s로 늘림.
- **수치 근거(주어진 실측: 작은 Decision 호출 warm 0.25-0.6 s, 긴 휴지 뒤 1.3-1.6 s)**: 비트 5 s는 cold 호출의 3배 이상이라 한 비트의 판단이 다음 비트 전에 끝나고, 10 s 기준을 최대 5 s 늦게 알아챈다. 요청 기한 2.0 s(cold 1.6 s + 여유, 비트보다 짧음). 요청 6회는 실행당 판단 시간 합계가 warm 1.5-3.6 s, 전부 cold여도 9.6 s 이하. 이 지연 수치는 이번에 측정하지 않았다(받은 값).
- **요청한 비트마다 내용 없는 보정 기록**: `conversation_flow` 항목에 `flow`(고른 종류), `posted`(`model`/`fallback`/`none`), `beat { n, phase, sinceUserS, sincePostedS, sinceEngineS, stepsDone, stepsRunning, decisionMs }`(초 단위·작은 정수·닫힌 단어만; 시각은 없음)를 추가(`egdesk-decision-calibration-log.mjs`, 추가만).

## 3. 등록 API와 객관 루프 연결 (`helper/egdesk-heartbeat-providers.mjs`, 신규)
- API: `runtime.heartbeatFor(key)` → `hb.register(name, () => facts)`(읽기 전용 사실 제공, 해제 함수 반환) / `hb.subscribe(beat => …)`(비트 수신). 제공자·구독자는 각각 8개까지, 던지는 제공자·구독자는 무시된다.
- **브라우저 작업 루프(L8 `egdesk-browser-task.mjs`)**: 런타임의 실제 진입(`runBrowserEntryOn`)에서 작업 저장소를 **통과형 관찰 래퍼**로 감싸 현재 작업 객체를 읽는다(L8 파일 수정 없음). 사실: 진행 중이면 `objective_step`·`stepsDone`·`stepBudgetLeft`, 일시정지면 `waiting_user`·`task: need_context|cannot_proceed`. 검증: L8의 런타임 수준 하네스(`codex-chat-browser-entry.test.mjs`에 시험 1건 추가)에서 플래그를 켠 실행과 끈 실행의 네이티브 입력 바이트(무작위 작업 id 제외)·Decision 요청·브라우저 동작이 같고, 하트비트가 `stepsDone: 1, task: need_context`를 받음.
- **터미널 상태 판정(L5 `egdesk-terminal-judge.mjs`)**: `runTerminalLoopWithHeartbeat(hb, args)`가 `deps`를 통과형으로 감싸 `runObjectiveLoop`를 그대로 호출(L5 파일 수정 없음). 사실: `objective_step`(게이트/실행 중)·`waiting_user`(y/n·비밀번호·사용자 정보 대기)·판정 횟수·`terminalState`(닫힌 상태 이름). 검증: 관찰한 실행과 안 한 실행의 결과·trace·호출 로그가 동일, 명령·출력 문자열은 사실에 없음. **터미널 루프는 현재 런타임 어디에도 연결돼 있지 않아**(모듈과 시험만 존재) 어댑터까지만 만들었다.

## 4. 멈춘 엔진
- 기준: 엔진·도구 이벤트 없이 **20 s**(`FLOW_LIMITS.stallAfterMs`). 근거는 판단값이다: 10 s 주의 한계의 2배이자 4비트. **실제 엔진의 이벤트 간격은 측정하지 못했다**: 긴 추론 중 이벤트가 없다면 정상 실행도 `stalled` 후보가 된다. 그래서 기록에 침묵 시간(`sinceEngineS`)을 남겨 실측으로 고칠 수 있게 했고, 문구는 진행을 단정하지 않는다.
- 흐름: 침묵이 기준을 넘는 비트에서 `stalled`(및 가능하면 `explain_wait`)가 선택지에 들어가고 Decision이 고른다 → 주관 모델이 비공개 포크에서 작성(6 s 한도: cold Decision 호출의 약 3배; 엔진이 멈췄다면 포크도 답하지 못할 가능성이 큼) → 실패하면 **고정 문구**. 멈춤 안내는 실행당 1회.
- 함께 고친 것: c9의 비공개 포크는 `thread/fork` 자체가 응답하지 않으면 기한이 걸리지 않고 영원히 기다렸다. 이제 기한이 포크 요청·턴 시작까지 덮고, 늦게 도착한 포크는 버린다(`codex-internal-turn.mjs`).

## 7. 한계 (정직하게)
- 브라우저 작업 진입은 제한(bounded) 실행에서만 돌고 그 실행은 보류 대상이 아니라서, **실제 배선에서는 브라우저 작업 중 하트비트가 사실을 받기만 하고 말하지는 않는다.** 표의 "사용자 대기" 시나리오는 등록 API로 같은 제공자를 보류 가능한 실행에 붙여 판단 쪽(요청 0)을 보인 것이다.
- 단조 시계는 호스트 절전 중 진행하지 않을 수 있다(플랫폼 의존). 그 경우 카운터는 깨어 있던 시간만 센다.
- 20 s 멈춤 기준, 6 s 작성 한도, 간격 배증은 판단값이다. 실제 엔진으로 보정 전이다.
- c9의 한계 그대로: 서피스 작성창은 실행 중 전송을 막아 이른 질문에 대한 답을 UI에서 보낼 수 없다. 비공개 포크의 실제 app-server 동작 미검증.
- 내부 포크 타이머를 런타임 타이머로 바꿨다(가상 시계로 시험하기 위해). 기본 동작은 같은 `setTimeout`이다.
