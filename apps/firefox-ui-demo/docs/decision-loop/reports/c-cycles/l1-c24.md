# L1 c24: 방 자기 계정으로 보는 검사 (창 ~20곳, 브라우저 도구 바인딩, 큰 자료 읽기)

브랜치 `lane/c24-room-keyed-checks` (base `int/c14`). 모두 mock. 아무것도 보내지 않음. 위험한 변경은 기존 플래그(`egdesk.roomAccount` 창 pref, `EGDESK_ROOM_ACCOUNT` 브리지) 뒤에 있고, 기본값(꺼짐)에서는 동작이 그대로다. 새 문구 없음.

## 1. 창 검사 (`eee1413`)
- `roomAccountScope(thread, codex)`가 방의 계정 키, 캐시된 키, 접근 상태, 슬롯을 돌려준다. 플래그가 꺼져 있으면 기존 기본 로그인 값과 같다.
- 방 계정 기준으로 바뀐 곳: 입력 읽기, 받은 입력 영수증, 근거(evidence)와 Briefing 울타리, 변경 서명(`roomAccountParts`), 요청 등록(`registerChatRequest` 5번째 인자), 문맥 capability 해석, 선택 문맥, 입력 증명 범위.
- 일부러 기본 로그인에 남긴 곳 두 곳 (방 검사가 아님): Agent 프로필 설정 게이트(`codexAccountKey(authStatus)`), Browser agent 프로필 컨테이너(`engineAccountKey`). 테스트가 이 목록을 고정한다.
- 남은 점: 일부 감시 서명이 프로필 행 전체를 포함해, 다른 프로필의 변화도 그 검사를 무효화한다. 보수적이지 정확성 문제는 아니다.
- 테스트 `scripts/egdesk-room-keyed-checks.test.mjs` 8개: 기본 로그인 없음, 기본이 다른 사람, 검사 도중 계정 변경. 변이 10개 모두 잡힘 (`mutations.txt`).

## 2. 큰 자료 읽기 (native reader), 방 계정 (`5aed893`, `8f2c4f4`)
- 새 `helper/egdesk-profile-readers.mjs`: 프로필마다 자기 `NativeReaderClient`. request/respond는 그 프로필의 app-server, owner key는 `codexEngine.ownerKey(id)`.
- `createEngineReaderFactory(engineId, authority)`: Codex 읽기에 프로필 슬롯 authority가 있으면 그 프로필 reader. reader가 없으면 null이라 읽기 불가가 되고 공유 계정으로 넘어가지 않는다. 플래그 꺼짐이면 `undefined`라 공유 reader (기존).
- 브리지: `EGDESK_ROOM_ACCOUNT=on`일 때만 생성. 프로필 서버의 알림/서버 요청은 그 프로필 reader가 소유하면 거기서 소비.
- 연결 끊김(`disconnect`)은 그 프로필 reader만 끊고, 공유 reader는 건드리지 않는다. `readerReadiness`도 프로필 reader 기준.
- 게시 결과(`readOutput`, `listOutputVersions`)도 HTTP 경로가 이미 구한 방의 authority로 조회한다 (기본 로그인이 로그아웃이어도, 남의 계정이어도 방 계정으로).
- 테스트 `helper/egdesk-profile-readers.test.mjs` 7개 (SmartReadEngine/컨텍스트 저장소는 진짜, reader는 가짜): 공유 서버 다운과 프로필 reader 다운 양방향으로 서로 빌려 쓰지 않음, 계정 변경, 결과 읽기 도중 계정 변경.

## 3. 브라우저 도구 바인딩 owner key (`77fe4ed`)
- 서비스(`egdesk-browser-tool-runtime.mjs`)가 `ownerKeyFor(engineProfileId)`를 받는다. `prepare`가 슬롯을 기록하고, 바인딩이 슬롯을 기억하며, 이후 모든 비교(14 + 4곳)가 `ownerNow(binding|prepared)`로 그 슬롯의 계정과 비교한다.
- 전송(`codex-browser-tool-transport.mjs`)은 `bindRun(…, engineProfileId)`로 슬롯 계정으로 묶고, 요청과 응답 검사도 슬롯 기준. provider는 `route.engineProfileId`를 서비스로 넘기고 `bindRun`/`adoptRun`에서 슬롯을 전송으로 넘긴다.
- 브리지 `browserOwnerKeyFor(id)`: 플래그 on이고 프로필 슬롯이면 `codexEngine.ownerKey(id)`, 그 외는 기본 로그인. 플래그가 꺼져 있으면 모든 방이 기본 로그인 (기존).
- 테스트 `helper/egdesk-browser-room-account.test.mjs` 6개: 기본 로그아웃/남의 계정에서도 프로필 방 바인딩, 기본 변경은 영향 없음, 프로필에 다른 계정이 로그인하면 종료, 바인딩 도중 변경 거부, 기본 방은 이전과 동일, 플래그 꺼짐.
- 변이 (`mutations2.txt`): B1~B6, R1~R8 모두 잡힘 (R6은 처음엔 안 잡혀서 기본 authority가 다른 값이 되도록 테스트를 고쳐 다시 잡음).

## 4. 남은 것 / 한계 (정직하게)
- 창 쪽 Browser 카드 정체성(`engineAccountKey`, 약 9개 `assertBrowserToolBinding` 호출처)은 카드 단위라 아직 기본 로그인 기준이다. 방 단위로 바꾸려면 스레드를 호출처 전반에 전달해야 한다. 이번에는 브리지 쪽만 방 계정이고, 창 쪽은 설계 메모만 남긴다. 따라서 플래그 on에서도 창이 카드 바인딩을 기본 계정과 비교하는 부분은 그대로다.
- 프로필 서버의 읽기 쿼터/권한 실패 처리, 프로필 사용량 추적(B6/B7)은 이번에도 손대지 않았다.
- 프로필 reader는 프로필 서버가 ready이고 로그인되어 있을 때만 의미가 있고, 아니면 읽기가 닫힌 코드로 실패한다 (공유 계정으로 대체하지 않음). 이 동작이 "방 계정으로 읽는다"는 결정의 결과다.
- 모두 합성(mock) 관측이다. 실제 설치 앱에서 프로필 reader의 child thread 동작은 확인하지 않았다.
- 결정 필요: 없음. (B4 작업 그래프/계획 키, B5 portableAttachments owner key는 아직 남음.)
