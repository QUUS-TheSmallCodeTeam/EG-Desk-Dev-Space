## 1. 식별번호가 같으면 코드가 일치로 판정 (R3)

**실측.** c16 recorded-v2의 renamed 단계에서 "가나상사 (987-65-43210)이 기록된 "사업자 987-65-43210"과 같은가?"라는 predicate가 .75로 미결정이었습니다. 그 결과 후보 하나로 `choice_needed`가 나와 hard 실패했습니다.

**`sameByCode(recorded, label)`** (`egdesk-browser-task-memory.mjs`)는 세 가지로 판정합니다.
- **`same`**: 정규화한 라벨이 같거나, 양쪽 모두 긴 식별번호를 가지고 그중 하나를 공유하는 경우
- **`different`**: 양쪽 모두 긴 식별번호를 가지지만 공유하는 것이 없는 경우. 번호가 다른 두 사업자는 다른 곳입니다. 코드가 내리는 판정이고, 결과는 사람에게 묻는 쪽이라 안전합니다.
- **`unknown`**: 한쪽에라도 긴 식별번호가 없는 경우. 이때만 same-thing predicate를 묻고, 그것도 라벨이 단어를 공유할 때에 한합니다. 후보 하나당 predicate 하나이며 인용은 개별로 합니다(R4).

**긴 식별번호의 정의** (`identifiersOf`, `MIN_IDENTIFIER_DIGITS = 8`):
- `-` 또는 `.`로만 이어진 숫자열이고, 구분자를 뺀 숫자가 8자리 이상이어야 합니다.
- 공백은 연결로 보지 않습니다. 그래서 나란히 있는 두 숫자가 하나로 합쳐지지 않습니다.
- 날짜 모양(1900~2099년, 실제 월·일, 예: 2026-11-19, 20261119)은 제외합니다.
- 비교는 숫자열 **전체**로 합니다. 접두·접미·부분 일치는 다른 번호로 봅니다.

**`recordedChoice`의 판정 규칙:**
- 코드상 `same`인 후보가 정확히 하나: 질문 없이 진행합니다(`by: 'identifier'`). 요소·href 가드와 page-state·goal 질문은 그대로입니다.
- 둘 이상: 사람에게 어느 것인지 묻습니다.
- 없음: `unknown`이면서 단어를 공유하는 후보에 대해 predicate를 묻고, 그런 후보도 없으면 `none`으로 처리합니다.

**과잉 일치가 없음을 표 테스트로 확인했습니다** (`egdesk-browser-recorded-choice.test.mjs`, 17행):

| 경우 | 판정 |
|---|---|
| 상호만 바뀌고 번호가 같음 (c16 실측 사례) | same |
| 같은 번호를 구분자 없이 / 점으로 표기 | same |
| 마지막 자리 하나만 다름 (접두 공유) | different |
| 9자리 접두만 있음 | different |
| 번호를 포함하는 더 긴 숫자열 | different |
| 전화번호 vs 사업자번호 | different |
| 같은 전화번호끼리 | same |
| 마스킹된 번호 `***-**-43210` | unknown (묻기) |
| 공백으로 구분한 번호 | unknown |
| 7자리 숫자 | unknown |
| 날짜 두 종류 | unknown |
| 날짜 모양이 아닌 12자리 계약번호 | same |

- 후보 둘이 같은 번호를 가지면 사람에게 어느 것인지 묻습니다.
- 근소하게 다른 번호(`…43211`)와 다른 사업자가 함께 있는 페이지는 `none`으로, 사람에게 어느 것인지 묻습니다.

## 2. 후보가 하나면 "어느 것"이 아니라 확인

기존 closed code 중 맞는 것이 없어 **새 closed code `confirm_needed`**를 제안합니다. 고정 문구는 없습니다.

**노트:** `need_context / confirm_needed`, `candidates: [후보 하나]`, `recorded: "기록된 라벨"`, `next: ask_user_in_chat`

**사람이 받게 될 질문**(주관 모델이 문장을 씁니다)의 내용: "지난번에 고른 '가나상사'가 지금 목록의 '가나상사 주식회사'와 같은 곳인지, 맞으면 그대로 진행할지."

**재개할 때:** "응" 같은 답만으로는 내용이 없으므로(R1), 코드가 step 근거에 다음 줄을 넣습니다.
`Asked to confirm "가나상사 주식회사" as the earlier choice "가나상사", the user answered: 응 맞아`

**결과:**
- "응": 그 후보를 열고 기록에 그날 라벨로 `선택:`을 남깁니다. 기록 레이아웃은 `choice_needed` 그대로입니다.
- "아니": 아무것도 열지 않고 `choice_needed`로 넘어가며, 거절한 사실을 근거에 넣고 묻습니다.
- 후보가 둘이면 지금처럼 `choice_needed`입니다.

c17 이후 c16 renamed 사례 자체는 코드가 일치로 판정합니다. 그래서 확인은 식별번호가 없는 라벨 쌍에서 predicate가 미결정일 때만 나옵니다.

## 3. 로그인/SSO는 사람 전용 (분류기 어휘, `b88fd49` 계승)

**새 카테고리는 만들지 않고 `grant`로 분류합니다.** SSO는 신원을 제공자에게 넘기는 동작이고, OAuth 시작은 제공자 세션이 열려 있으면 조용히 로그인까지 끝날 수 있습니다. 판정 사유는 `sign-in-vocabulary` 또는 `sign-in-destination`입니다.

**라벨은 정밀하게, 라벨 전체가 로그인 동작일 때만 grant입니다.**
- grant: "로그인", "로그인하기", "로그인 후 이용하기", "카카오로 로그인", "네이버 아이디로 로그인", "간편/인증서/휴대폰/SNS 로그인", "Sign in", "Log in with Google", "Continue with Kakao", "Sign in to your account" 등 31개
- 로그인을 **언급만 하는** 라벨은 그대로 제시합니다. 예: "로그인 도움말", "로그인이 안 될 때", "로그인 정보 수정", "로그인 기록", "아이디 찾기", "Sign-in help", "Trouble signing in?", "Login history", "Continue reading" 등 19개
- 근거: 이런 링크는 페이지를 여는 것일 뿐 아무도 로그인시키지 않습니다. 실제로 로그인을 시작하는 링크라면 아래 주소 규칙이 걸러냅니다.

**주소는 fail-closed입니다(C4 이후의 원칙).**
- 경로나 쿼리에 login, signin, logon, sso, oauth, 로그인이 **단어로** 있으면 grant입니다.
- 감수한 오배제: `/help/login-trouble`, `?topic=로그인` 같은 도움말 주소도 함께 걸러집니다.
- 단어 일부만 같은 경우(`loginhistory`, `blog in`, `catalog`)는 통과합니다.

**적용 결과:**
- SSO 페이지(카카오·네이버 버튼, Google OAuth 링크, 도움말 링크)에서는 도움말 링크만 제시됩니다.
- SSO 버튼만 있는 페이지는 c15 규칙에 따라 요청 없이 `human_step`이 됩니다.
- 같은 사이트의 로그인 링크는 라벨로도, 주소로도 걸러집니다.
- census가 바뀌었습니다. 요청 없이 멈추는 모양이 12종 중 9종이 되었고, 라벨을 잃는 경우가 4종(`login-sso-only`의 login_required 추가)이 되었습니다.

**기존 assertion 수정:**
- "Sign in / 로그인 / Log in은 평범하다"는 assertion은 이번 결정으로 뒤집혔습니다. 이 셋은 이제 grant로 확인하고, 평범한 쪽에는 "로그인 도움말", "Sign-in help"를 넣었습니다.
- "네이버 로그인" assertion의 원래 의도('네'는 라벨 전체일 때만 긍정어)는 유지했습니다. 사유가 consent-affirmative가 아님을 확인하고, "네이버 지도"가 none임을 추가했습니다.
