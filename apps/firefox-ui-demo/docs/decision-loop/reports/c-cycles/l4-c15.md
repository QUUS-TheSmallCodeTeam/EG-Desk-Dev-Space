## 1. 진단 — 실제 답과 실제로 보낸 본문에서

| 실측 | 본문에서 확인한 원인 |
|-|-|
| `sk-place-quote`: bubble .65 / board .35 | 질문 문구가 세 번 bubble 쪽으로 밀었다: "답은 이미 채팅에 있다", "보드에 **또** 펼칠 것인가", "~일 때**만** 가치가 있다", "**확신 없으면 bubble**". 안전한 기본값이 있는 2지선다였다(R2). |
| `sk-parts-quote`: .45 / .32 / .23 등 평평 | (1) 한 질문에 두 질문이 들어 있었다("보드에 필요한가, 그렇다면 어떤 컴포넌트인가"). (2) 빠져나갈 보기가 둘(`none_fits`, `bubble_enough`)이고 뜻이 거의 같아 확률이 갈렸다. (3) part를 `M1, M3` 별칭으로만 가리켰고 본문은 떨어진 JSON 덩어리에 있었다(R4). |
| `sk-order-1`: 거절 | **내 요청의 결함.** 보기 설명이 "part P1", "part P2", "part P3"뿐이었고 각 part가 무엇인지 요청 어디에도 없었다. 판단할 내용이 없으니 거절이 옳은 답이었다. |
| fill check: 맞는 가이드 .94/.96/.97, 틀린 가이드 1/1/.96 | "설명이 카드가 보여주지 않는 것을 말하는가?"라는 부정형·광범위 질문 하나를, 세 step이 한 JSON 덩어리에 든 상태에서 별칭으로 물었다. 연결어나 요약만 있어도 "보여주지 않는 것"이 되므로 항상 예가 나온다. |

덧붙여 확인한 것: 실제 API의 choice `confidence`는 최상위 확률이 아니라 1·2위 차이에 가깝다(.65/.35 → .30, .97/.03 → .94). 내 mock은 `confidence`를 최상위 확률로 넣고 있었으니, 기준 .75는 실제로는 최상위 확률 약 .87을 요구하는 훨씬 엄격한 값이었다. 술어로 바꾸면서 이 문제는 사라진다.

## 2. 재설계 (R1–R4)

Decision 질문은 **전부 예/아니오 술어**다. 요청문은 user 메시지 하나로 들어가고, 판단 대상(자료 본문, 슬롯 글, 출처)은 각 질문 안에 따로 인용된다. choice 질문과 "없음/bubble" 보기는 코드에서 사라졌다(테스트가 소스에 `choiceQuestion`이 없음을 고정).

| 단계 | 술어 | 코드가 하는 일 |
|-|-|-|
| place (요청 1) | `several`: 여러 자료를 나란히/차례로 봐야 하는가. `one_sentence`: 한 문장이면 충분한가. | board = several 예 **그리고** one_sentence 아니오. 그 외는 전부 bubble(미결·거절 포함). |
| fit (요청 1) | (part, 보여주는 방식) 쌍마다 1개. 그 part의 자료 본문을 인용하고, 컴포넌트가 무엇이고 무엇이 아닌지를 한 문장으로 적는다(예: "평범한 목록이며 표도 차트도 아니다"). | part별로 예가 확정된 것 중 최선(기존 카드 재사용 > 새로 안 만드는 것 > 새 카드). 전부 아니오면 "맞는 컴포넌트 없음"은 코드가 내리는 결론이다. |
| order (요청 0–1) | 기록이 정하지 못한 쌍만 "X를 Y보다 먼저 보여야 하는가". 두 part를 자료 본문으로 설명. | 먼저 기록으로 정한다: 날짜(날짜 없는 계획은 미래), 링크(뒤 자료가 앞 자료를 가리킴). 미결·거절은 코드 순서. |
| 배치 검사 | 없음 | 넘침 → 행 줄이기, 너무 멀리 떨어진 재사용 카드 → step에서 빼기. 규칙으로 처리(R3). repair 단계 삭제. |
| 접기 제안 | 없음 | 대체된 이전 답변 카드는 규칙으로 제안(사용자가 적용). |
| fill check (요청 1 + 다시 쓴 뒤 1) | 슬롯 글 한 조각마다 "이 글이 **이** 자료로 뒷받침되는가"(둘 다 인용), step마다 "설명의 사실이 전부 step이 보여주는 것 안에 있는가". | 예가 확정된 것만 통과. 실패한 part는 닫힌 단어("P2 line 2")와 함께 한 번 다시 쓰게 하고, 또 실패하면 그 part만 뺀다. 데이터가 없다고 보고된 part는 예였던 다른 방식으로 옮기거나 뺀다. rechoose 단계 삭제. |

카탈로그 항목마다 trait별 평문 설명(`purpose`)을 추가했고, 등록 컴포넌트에도 필수로 했다.

**요청 수와 상한.** 보통 3–4회(place, fit, [order], fill check), 최대 6회(이전: 5–6회, 최대 14회). fill turn은 그대로 최대 3회. Main 실측 지연이 요청당 234–300ms였으므로 4회 순차면 약 1.0–1.2초다.
**비용은 늘었다.** 대표 여정이 4요청·19질문·추정 6,214 입력 토큰이다(이전 형태는 5요청·약 4,400). 술어 하나가 약 135 토큰을 차지하고, 조각마다 출처를 인용하기 때문이다.

단일 버전 사례가 달라졌다: fit 질문이 두 자료 본문을 보여주므로, 수치가 없는 "두 번째 버전"은 **무엇을 쓰기 전에** 맞지 않는다고 판단될 수 있다. 그래도 선택되면 모델의 "채울 수 없음" 보고로 규칙이 그 part만 뺀다(추가 요청 없음).

## 5. 한계

- 새 형태의 실제 답이 없다. 특히 step 설명 술어는 이전에 전부 "불일치"가 나온 질문과 가장 가깝다(이번엔 긍정형, 쌍을 따로 인용, 바꿔 말하기 허용 규칙 추가).
- 토큰이 약 40% 늘었다.
- 실패한 part는 통째로 다시 쓰거나 뺀다. 틀린 행만 빼는 처리는 없다.
- 카드 제목 슬롯은 검사하지 않는다.
- 다른 자료와 링크가 없는 자료는 단독 part가 되어 따로 물어진다(단일 버전 사례의 결정 메모).
- 기준 .7/.3은 임시값이다. 다른 기능의 실측 술어는 0이나 1 근처였다.
- c11–c14 이월(fork 컨텍스트, 발행 원자성, chrome의 주의 장면 트리거 없음)은 그대로다.
