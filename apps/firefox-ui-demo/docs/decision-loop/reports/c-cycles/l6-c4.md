# L6 / C4: answer_type, time_intent는 무엇을 위한 질문인가

브랜치 `lane/c4-unused-questions` (= int/c3 c7e8713, 커밋 없음, 제품 패치 없음 -> 광범위 게이트는 돌리지 않음). 증거: `evidence/l6-c4/` (`replay.mjs`, `results.json`, `cost.mjs`, `cost.json`, `property.mjs`, `property.json`, `transport-probe.mjs/.out`, `latency-slope.json`).
구분: [측정] 영수증/로컬 실행 수치, [재생] 현재 코드를 그대로 돌린 결정적 결과, [해석] 내 판단.

## 0. 결론 먼저
- `answer_type`: 읽는 코드가 없다. 정의상 "추론 호출을 건너뛰기 위한 라우팅" 용도로 설계됐고, 문서가 현재는 그 기능이 없다고 명시한다. **의도적으로 미뤄진 것**이지 잃어버린 소비자가 아니다 (아래 (b)).
- `time_intent`: 소비자가 하나 있다 (`present`이고 후보가 계획/가정일 때 relevant 기준 .5 -> .8). 나머지 값(`past`, `planned`, `what_if`, `cross_time`)은 소비자 없음.
- 두 질문의 요청당 비용: 입력 토큰 약 306~348 (질문 텍스트 1104 B), 기본 설정의 3문항 요청에서는 요청 토큰의 약 55%, 발화 6축이 켜진 요청에서는 약 12%. 웜 연결 지연 영향은 -7~+55 ms (95%, 약함), 콜드 연결 페널티(1.1~1.8 s)에 비하면 작다.
- 문서가 구체적으로 소비자를 지정하지 않았고 §3.1 2항이 "묻는다"고 명시해서 **제품 패치 없음**. 사용자용 결정 노트는 (d).
- int/c3에서 실결과 표 재생: **c3 결과와 비교해 차이 0건** (results.json 전체 비교).

## (b) 잃었나, 안 만들었나, 미뤘나
- 코드 현황 [재생/grep]: `prepareDecisionContext` 결과를 읽는 곳(`codex-chat-runtime.mjs` 2275, 2496-2512, 2522, 2578, 2606-2610, 4452)은 `extraContext`, `status`, `mayDispatch`, `privateBatchCurrent`, `localOnly`, `speechInterpretations`, `calibration`만 쓴다. `answerType`/`timeIntent`를 읽는 파일은 `egdesk-context-setup.mjs` 하나뿐 (함수 반환값, 영수증, 보정 행에만 실림).
- 이력 [측정]: 저장소 이력은 루트 커밋 `30cf73b`(2026-11-22) 하나에서 시작한다 (`git log 30cf73b | wc -l` = 1, int/c3 전체 69커밋). `git log -S answerType/timeIntent/answer_type`의 가장 오래된 히트가 바로 그 루트 커밋이고, 그 시점에 이미 소비자가 없었다. 즉 **저장소가 볼 수 있는 이력 안에서 삭제된 소비자는 없다**. 한계: 11-22 이전(문서는 11-17 작성)의 이력은 이 저장소에 없어서 "그 이전에 소비자가 있었다가 사라졌는가"는 증명할 수 없다.
- 판정 [해석]: `answer_type` = 설계됐으나 의도적으로 미뤄진 라우팅 소비자 (문서가 "현재 없음"을 명시, 기억 기록과 일치). `time_intent` = 일부(present 엄격 기준)만 구현, 나머지는 미연결. "잃어버린 소비자"의 증거는 없음.

## (c) 질문별 요청당 비용
요청 본문에 직렬화되는 질문 크기 [재생: 제품 `choiceQuestion` JSON 바이트]: answer_type 556 B, time_intent 548 B, 둘 합 1104 B, rel_0 105 B, rel_recall 216 B, 발화 6축 6804 B.
- 11/23 영수증 요청(9157 B, 2539 토큰): 질문 합 8229 B로 본문의 90%, 그중 발화 6축이 6804 B(본문의 74%). 두 질문은 본문의 12.1%.
- 토큰 환산 두 방식 [해석: 질문은 영어 텍스트라 토큰/바이트 변환이 불확실해서 범위로 제시]
  - 이 요청 자신의 비율(2539 / 9157 = 0.277 토큰/B): answer_type 154, time_intent 152, 합 306 토큰 (발화 6축 1887).
  - 17개 원장 요청 회귀 (토큰 = 64 + 0.315 x 바이트, R² 0.91, n=18): answer_type 175, time_intent 173, 합 348. 이 회귀는 w3를 2947로 예측해 실제 2539보다 16% 높음 -> 상한으로 취급.
- 기본 설정(발화 꺼짐)의 3문항 요청 (service ledger, 2015 B, 625 토큰): 두 질문이 본문의 54.8%. 이 요청 자신의 비율로는 342 토큰, 회귀로는 348 토큰 = **요청 입력 토큰의 약 55%**. 이 요청은 541 ms (첫 호출).
- 월 환산 [재생 산술]: 1000턴당 두 질문 합계 약 306k~348k 입력 토큰 (answer_type 단독 154k~175k, time_intent 단독 152k~173k). 월 상한 설정 기본값은 없음(`cap`은 사용자 지정, 기본 null).
- 지연 [측정 + 해석]: 웜 호출 17건에서 지연 = 232 ms + 8.3 ms/100토큰 (R² 0.27, 약함). 부트스트랩 95% 기울기 -0.023~+0.158 ms/토큰 -> 두 질문 합계 약 -7~+55 ms. 이 자료로 0과 구분 불가. 콜드 연결 페널티(w3 2062, 첫 문맥 1409, key check 2229 vs 웜 230~370)가 훨씬 큼.
- 캐시 [미상]: 영수증에 `cached_tokens`가 없어 이 질문들이 프롬프트 캐시에 얹히는지 모름 (질문은 `questions`에 있고 캐시 중단점은 후보 목록 쪽).

## 재생: 이 질문들이 선택 결과를 바꾸는가 (결정적, 현재 `prepareTurnContext`)
후보 시간대 5가지 혼합 x relevance 확률 4가지 x time_intent 6값 = 120 케이스.
- time_intent: 질문을 안 한 것과 다른 결과(선택 목록 또는 패킷)가 나온 것 8건, **전부 값이 `present`일 때만**, 계획/가정 후보가 없는 집합 48건에서는 **0건**.
- answer_type: 4값 x 20 조합 = 80 케이스에서 선택/패킷이 바뀐 것 **0건**.
따라서 (1) answer_type은 추론 모델이 받는 것에 어떤 영향도 없고, (2) time_intent는 후보에 계획/가정이 있을 때만 의미가 있다. 이것이 "질문하지 않아도 같은 결과"의 정확한 범위다.

## 실결과 표 재검증 (int/c3)
- `replay.mjs`를 int/c3(wt-l6c4)로 돌려 c3(int/c2) 결과와 전체 JSON 비교: 차이 0건 (confidence 공식 오차, 발화 6/6 거절, 800 ms fallback/4000 ms ready, chooser 프록시 8/8, 합 조건 16/16, 보정 기록 모양까지 동일).
- 이유 [해석]: 이번 병합은 발화 설계 플래그(`speechDesignQuestions`, 기본은 기존 축 방식), 활동 행 문구, keep-alive 전송, 모드 재확인 수정이다. 내 재생은 가짜 fetch로 지연을 주입하므로 전송 계층과 모드 재확인은 대상이 아니고, 기본 발화 축 판독과 보정 기록은 그대로다.
- 전송 계층은 따로 로컬 측정 [측정, 루프백]: int/c3의 `createDecisionTransport`는 서버 힌트가 없을 때 유휴 1, 4.5, 6, 12초 모두 같은 소켓 재사용 (8요청, 새 소켓 1). 이전 측정(c3, 전역 fetch)은 4.5초부터 새 연결이었으므로 내 "4초 유휴 후 콜드" 취약점은 이 전송 계층이 해소하는 방향. 실제 OpenAI 서버가 보내는 Keep-Alive 힌트와 55초 유휴 상한의 효과는 실호출 측정이 필요 (승인 필요).

## 한계
이력은 11-22 이후만 있음. 지연 기울기는 n=17, R² 0.27로 약함. 토큰 환산은 범위. 영수증에 캐시 정보 없음. 실제 사용에서 계획/가정 후보가 얼마나 흔한지는 측정된 적 없음 (B의 절약 빈도를 좌우).

## 철학 점검
"확률은 실행 권한이 아니다": `answer_type`이 아무것도 못 움직이는 현재 상태가 오히려 원칙에 안전하다 (확률이 행동을 바꾸지 못함). 문제는 안전성이 아니라 낭비다. 소비자를 연결하는 쪽(D)은 이 원칙을 다시 시험하게 되므로, 연결 전에 "확률이 낮으면 지금 방식으로" 규칙과 사용자에게 보이는 사유가 문서로 먼저 정해져야 한다.
