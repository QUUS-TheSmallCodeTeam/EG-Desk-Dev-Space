## 0. 범위
c6와 같은 합성 하네스다(실제 런타임·HTTP 핸들러·SQLite 저장소·`EGDeskChatState`·Surface 소스 구간, mock 엔진, 가상 시계). 설치된 앱, 실제 app-server, 말풍선 DOM 루프 전체는 검증하지 않았다. 시스템 알림 줄은 렌더 루프의 해당 블록만 소스에서 잘라 실행했다.

## 1. 충돌 해소 (L3 heartbeat 구조 기준)
L3의 구조(`pauseConversationFlow`, `stopConversationFlow(run, reason)`, `onHeartbeat`, `postIntermediate`, `finally`의 보정 기록, 상한)는 전부 그대로 두고 내 추가분만 얹었다.

| 내 추가분 | heartbeat 구조에서의 위치 (`codex-chat-runtime.mjs`) |
|---|---|
| 질문 열림 표시 | `postIntermediate`가 `ask_missing` 메시지를 게시한 직후 `setReplyOpen(run, id)` (:4883) |
| 닫힘: 사용자 답 수락 | `answerEarlyQuestion`에서 `flow.heartbeat?.mark('user')` 다음 줄 (:4949) |
| 닫힘: 흐름 일시정지(최종 답변 준비) | `pauseConversationFlow` (:4810) |
| 닫힘: 흐름 종료(실행 끝·중지·연결 끊김) | `stopConversationFlow` (:4819) |
| `inRunReplyTo` 거절 | `send` 맨 앞, 변경 없음 (:1640) |
| `run.replyOpen`의 `/chat/state` 포함 | 실행 객체 필드라 그대로 실림 |

- 옛 타이머 틱(`scheduleFlowTick`, `flow.timer`) 쪽 코드는 가져오지 않았다.
- 새 시험: 답하지 않은 질문은 최종 답변이 보류되는 동안에는 열려 있고, 턴이 끝나 흐름이 일시정지되는 순간(`reply.closed`) 최종 답변 게시보다 먼저 닫힌다. 그때 작성창은 busy 규칙으로 돌아가고 steer는 0건, 저장된 실행에 열린 질문이 남지 않는다.
- 내 시험 세계에 `monotonicNow`를 가상 시계로 연결했다(L3 시험과 같은 방식). 연결하지 않으면 heartbeat의 소수점 지연이 가상 시계를 소수로 만들어 저장소가 타임스탬프를 거절하는데, 이는 시험 시계의 문제이고 제품(`Date.now`)에서는 생기지 않는다.

## 2. "한 프레임 이중 글" 수정 재확인 — 방식 변경
- int/c11 제품 코드에 새 시험을 돌린 원 출력(`completed-before-int-c11.tap`): heartbeat의 `postIntermediate` 경로와 **멈춤 대체 문장**에서도 같은 문제가 재현된다.
  - `message.delta: drew "응답이 평소보다 오래 걸리고 있습니다. 더 기다리거나, 중지하고 다시 요청할 수 있습니다.응답이 평소보다 오래 걸리고 있습니다. …"`
  - `message.delta: drew "이 부분은 시간이 좀 걸립니다. 계속 확인하고 있어요.이 부분은 시간이 좀 걸립니다. 계속 확인하고 있어요."`
  - 보류된 최종 답변, 플래그 off에서 완성된 채 도착한 답도 동일.
- c6에서는 런타임이 `message.started`를 글 없이 보내도록 고쳤다. int/c11에서는 그 방식이 다른 레인의 시험과 충돌했다: `helper/egdesk-briefing-engine.test.mjs:181`은 시작 이벤트에 전체 글이 있기를, L3의 `egdesk-held-answers-flow`는 delta 하나에 전체 글이 있기를 기대한다. 둘 다 오늘의 이벤트 형식이다.
- 그래서 **이벤트 형식은 건드리지 않고 화면 reducer에서 고쳤다**(`EGDeskChatState.sys.mjs:1132, 1137`): 완성 상태로 시작한 메시지는 그 글을 그대로 완성으로 받고, 뒤따르는 같은 글의 delta를 더하지 않는다. 결과적으로 그런 메시지는 화면 상태에서 `streaming`을 거치지 않고 처음부터 완성으로 나타난다(c6보다 D1에 더 가깝다).
- 한 번 틀렸던 것: 처음에는 "상태가 complete면 delta 무시"로 썼다가 기존 규칙 시험("복원된 complete 상태는 완성 증거가 아니다, 확인 전까지 delta는 계속 받는다")을 깼다. 전용 표시(`arrivedWhole`)로 바꿔 그 규칙을 유지했다.
- 다른 레인의 시험은 고치지 않았다.

## 3. 시스템이 쓴 문장을 알림 줄로 — 준비만, 기본값 그대로
### 화면이 지금 구분하는 방식
- Agent 메시지: 얼굴·이름이 붙는 말풍선.
- 시스템 줄: 조용한 한 줄(`role="note"`), 두 종류가 이미 있다 — 계획 단계가 이어졌다는 줄(`egd-codex-await-resume`, `ChatState.awaitResumeMessageView`)과 사용자가 Browser 조작을 가져왔다는 줄(`egd-codex-browser-control`). 둘 다 "ChatState의 view 함수가 값을 주면 렌더 루프가 말풍선 대신 한 줄을 그리고 끝낸다"는 같은 패턴이다.

### 준비한 것 (플래그 없음, 메시지의 필드 하나로 선택)
- 필드: 메시지의 `presentation: 'notice'`.
- 런타임(`codex-chat-runtime.mjs:5951`): 이 필드는 런타임이 직접 만든 흐름 메시지(`egdesk-flow:` id)에만 실린다. 엔진이 보낸 항목이 스스로 붙일 수는 없다(시험).
- 화면: `ChatState.systemNoticeMessageView(message)`(`EGDeskChatState.sys.mjs:3601`)가 완성된 assistant 메시지에 그 필드가 있을 때만 값을 주고, 렌더 루프가 기존 조용한 줄 스타일로 그린다(`eg-desk-surface.uc.js:14338`, `data-testid="chat-system-notice"`, 새 CSS 없음). 앞뒤 Agent 말풍선과 묶이지 않는다.
- 저장·복원: 필드가 저장소에 남아 복원 뒤에도 같은 줄로 그려진다(시험).
- **기본값은 바꾸지 않았다**: 지금은 아무것도 이 필드를 붙이지 않으므로 멈춤 대체 문장은 오늘처럼 Agent 말풍선이다. 바꾸려면 `postIntermediate`의 `applyItem` 호출에 `...(by === 'fallback' ? { presentation: 'notice' } : {})` 한 줄이면 된다(시험은 이 한 줄을 시험 쪽에서 적용해 끝까지 확인).

### 두 표시 (같은 문장, 사용자가 고를 것)
| | A. 오늘(기본) | B. 준비된 옵션 |
|---|---|---|
| 모양 | Agent 얼굴·이름이 붙은 말풍선 | 가운데 정렬된 조용한 한 줄 + 시각, 얼굴·말풍선 없음 |
| 읽히는 뜻 | Agent가 직접 한 말 | 앱이 알리는 상태 |
| 문장 | `응답이 평소보다 오래 걸리고 있습니다. 더 기다리거나, 중지하고 다시 요청할 수 있습니다.` | 동일 |
| 채팅 기록 | assistant 메시지 | assistant 메시지 + `presentation: 'notice'` |
| 화면 낭독 | 대화 로그의 일반 메시지 | `role="note"` 한 줄 |
- B의 근거: 이 문장은 모델이 아니라 시스템이 쓴 고정 문구라, Agent 말풍선으로 두면 Agent가 말한 것처럼 보인다.
- B에서 알아둘 점: 실행이 이 줄만 남기고 끝났고 그 실행이 컴퓨터를 조작했다면, "마지막 답변 아래"에 붙는 컴퓨터 조작 표시가 붙을 말풍선이 없다. 그 한 줄을 고치려면 `egdesk-surface-state.test.mjs`가 글자 그대로 확인하는 줄을 바꿔야 해서 이번에는 두었다.

## 6. 철학 점검
- 보이는 것은 완성된 것: 중간 메시지·멈춤 문장·보류된 답 모두 한 번에 통째로 나타난다.
- 누가 말했는지 속이지 않는다: 시스템이 쓴 문장을 Agent의 말과 구분해 보일 수 있는 길을 열어 두되, 어떻게 보일지는 사용자가 정한다.
