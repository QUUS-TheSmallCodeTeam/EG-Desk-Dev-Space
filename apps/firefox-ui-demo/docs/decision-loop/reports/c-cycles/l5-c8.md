## 2. 상태 판정기를 이 스트림으로 이동 (`helper/egdesk-engine-command-watch.mjs`)
- 플래그: `EGDESK_COMMAND_JUDGE=advisory`, 기본 off(off면 추적·타이머·요청·기록 모두 0). 런타임 연결은 출력이 이미 보관되는 바로 그 지점(`keepRunOutput` 다음 줄, `codex-chat-runtime.mjs:3870` → `observeEngineCommand` `:5061`).
- **출력 텍스트를 따로 보관하지 않는다.** 체크할 때 화면이 이미 쓰는 run 출력 보관소(가려진 사본)에서 읽는다.
- 선택지는 실제 사실에서: 실행 중 → 6개 살아 있는 상태; 종료 코드 ≠ 0 또는 `failed` 상태(Claude) → 성공 제외; 종료 코드 0 → 성공/숨은 오류/…; 마지막 출력 이후 시간(quiet)과 tail.
- 체크 포인트(폴링 루프 없음): ① 출력 이벤트가 거는 1회성 타이머(출력 후 1.5 s 조용하면 1회: 입력 대기는 "출력 후 침묵"이다), ② 명령 완료, ③ 대화 heartbeat의 박동.
- 비용 상한: 종료 코드 0이고 실패 표식이 없으면 규칙으로 완료 처리(요청 0 — 에이전트가 돌리는 `ls`/`cat` 대부분), 같은 조용한 tail은 1회, 명령당 4회, run당 Decision 요청 12건. 비밀번호 프롬프트는 규칙으로 처리하고 전송하지 않는다.
- egress: 새 kind **`command_output`** 등록(`egdesk-decision-egress.mjs`). 지배 설정: Agent 도구 상한 `terminal` ≠ none **그리고** 살아 있는 run(두 클래스 모두 필요). Terminal 카드 출력(`terminal_output`)과 구분되며 카드 쪽 gate로는 열리지 않는다(시험).
- 기록(변경 없음): 보정 로그 `terminal_state`에 `stream: 'engine'`, `engine`, 상태, 출처, **했을 일**. 엔진 명령에는 EG-Desk가 입력을 넣을 수 없으므로 yes/no·비밀번호·pager의 "했을 일"은 "사람에게 알림"(`hand_yes_no`/`hand_secret`/`hand_close_pager`)이지 키 입력이 아니다.

### 시험 결과
- 한 run의 판정 흐름(Codex 형태, 단위): `running_output→wait`, 종료 1 `completed_error→repair`, `(y/N)` `waiting_yn_input→hand_yes_no`, pager `stuck_in_pager→hand_close_pager`, 깨끗한 종료 0 `completed_ok(runtime)→report`(요청 0), 종료 0이지만 실패 출력 `completed_error→repair`, 종료 127 `cannot_proceed→hand_subjective`. 요청 8건/명령 6개.
- **동일성(실제 런타임, Codex 알림):** 플래그 없음 vs advisory에서 엔진 응답·호출·이벤트·run 스냅샷(4,340바이트)과 화면이 읽는 보관 출력이 동일. advisory는 요청 4·기록 4를 더할 뿐이며 엔진에 보낸 응답은 0.
- Claude(실제 어댑터·번역기): `failed` → `completed_error(runtime)→repair`, 성공 → `report`, 요청 0, 출력은 어디에도 없음. 거절된 명령은 판정하지 않음.
- egress: 도구 상한 terminal=none / run 종료 / 키 없음 / Decision off → 요청 0, 종료 코드 폴백.

## 3. heartbeat에 사실 공급 — 한 가지 형태
- 형태는 `egdesk-terminal-judge.mjs`의 `terminalFactRow` 하나다. 세 곳이 같은 빌더를 쓴다: 엔진 명령(`engineCommands.facts(runKey)`), L3의 객관 루프 어댑터(`observeTerminalLoop`, 출력 불변 — L3 시험 그대로 통과), c7의 Terminal 카드 `terminalFacts()`(이 형태로 바꿈: `judged{}`·`lastOutputAt` 등 제거).
- 키: `active`, `phase`(`waiting_user`/`objective_step`/`tool_running`), `waitingOnUser`, `terminal`(`gate`/`running`/`waiting`/`idle`), `terminalState`/`terminalSource`/`terminalWould`(판정 후), `runningMs`, `quietMs`, `exitCode`. 엔진 명령은 `commandsRunning`/`commandsDone`/`commandsFailed`를 더한다(heartbeat 자체 집계와 이중 계산되지 않도록 `stepsDone`류는 쓰지 않음). 숫자·불리언·닫힌 라벨만이라 heartbeat의 sanitizer를 손실 없이 통과한다(시험).
- 런타임: run이 첫 명령을 시작하면 그 대화의 heartbeat에 `engine_commands` 제공자 1개와 박동 리스너 1개를 건다(`feedCommandHeartbeat` `:5080`). 예(가상 시계): `{ active: true, phase: 'tool_running', terminal: 'running', terminalState: 'running_output', runningMs: 10000, quietMs: 10000, commandsRunning: 1 }`.
- **남은 것(L3 영역):** 값은 `beat.facts.sources.engine_commands`에 들어 있지만, 현재 `egdesk-conversation-flow.mjs`의 메시지 판정 질문은 `sources`를 읽지 않는다. "테스트가 아직 도는 중"이라고 말하려면 flow가 이 행의 `runningMs`/`terminalState`를 질문의 사실 목록에 넣어야 한다. 손대지 않았다.
- 엔진 명령에서 판정된 대기 상태는 `terminal: 'waiting'` 라벨일 뿐 `waitingOnUser`는 false다(사람이 EG-Desk로 답할 수 없으므로 heartbeat의 phase를 `waiting_user`로 바꾸지 않는다).

## 4. 오류 hand-off (advisory, 기록만)
명령이 오류로 끝나면 보관된 출력에서 런타임이 블록을 열거하고(`enumerateLogBlocks`), 블록당 predicate 1문항을 요청 1건으로 물어 **강조했을 블록의 순번**을 기록한다(`terminal.picked: [2, 3]`, 열거 4개 중 2개). Decision이 불가하면 런타임 실패 표식 블록(`b2,b3,b4`)을 기록한다. 주입·표시는 하지 않는다. Claude는 출력이 없어 블록도 없다.
