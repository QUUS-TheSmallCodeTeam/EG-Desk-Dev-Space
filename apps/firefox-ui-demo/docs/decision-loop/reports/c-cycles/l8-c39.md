## 2. 고친 것 (모두 테스트 있음)
1. **continue와 retry가 둘만 yes이고 나머지 결정 no면 continue 적용** (`readOpenItem`, `overlap: continue_retry`). retry는 단계 기억까지 버리는 continue라서 경쟁 관계가 아님; 약한 쪽(아무것도 버리지 않음)을 적용. 다른 쌍(continue+abandon, continue+ask_page 등), 셋 이상, 나머지가 no가 아닐 때는 여전히 `uncertain`.
2. **ask_page 문구를 페이지에 앵커링**: "이 메시지가 브라우저 작업이 있는 웹페이지에 대한 질문(보이는 것, 지금까지 찾은 것)인가? 다른 것에 대한 질문은 아니다." + 개발자 규칙에 "다른 것에 대한 메시지는 작업에 아무 의미도 없다: 그에 대한 모든 질문에 no". Decision 프롬프트일 뿐 사용자 문구가 아님.
3. **제품에서 두 플래그가 모두 켜졌을 때의 조율** (`codex-chat-runtime.mjs`): 이전에는 해결기(턴 시작 요청)가 항목을 읽은 뒤 사전 턴 `entry.handle`이 일시정지 분기에서 **자기 옵션 요청을 또 보내 다르게 결정**하고, 이어서 해결기의 `apply`가 한 번 더 적용될 수 있었습니다(그리고 해결기가 "이 항목 아님"이라고 해도 진입이 무시). 이제 `readFromResolver(verdict, provider, key)`: 브라우저 항목으로 settled -> 같은 답에 대한 제공자의 read, 다른 항목으로 settled/no_item_referred/several_items -> `none`(일반 턴, 작업 그대로), 해결기가 결정 못 함(타임아웃, 응답 없음) -> null(진입이 스스로 결정, 해결기 꺼졌을 때와 동일). 진입이 이미 적용했으면 `verdictRow.browserApplied`로 해결기 `apply`가 반복하지 않고 상태만 닫힌 말로 전달.
4. **진짜 엔진 훅이 제품처럼**: 이어지는 턴을 해결기 경유로(`buildRegistry` -> `resolveOpenItem`(oi_ref_1 + 옵션 predicate = 한 요청) -> `readFromResolver` -> `handle({ openItemRead })`). 스크립트 플래그에 `EGDESK_OPEN_ITEMS=on` 추가, 새 검사 `resolverSettled`(oi-continue, retry, abandon, ask-page)와 `resolverNotReferred`(oi-unrelated: reason `no_item_referred`).
