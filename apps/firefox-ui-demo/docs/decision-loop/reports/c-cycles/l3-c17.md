## 0. 재현 방법: 실제 여정의 재생

`evidence/l3-c17/replay-journey.mjs` 는 Main 의 실제 all-on 여정(`c16-all-on-journey.json`)을 제품 코드로 다시 돌린다. 네트워크는 쓰지 않는다. 모의 fetch 가 각 요청에 답하는 방식:
1. 바이트가 같은 본문이면 그때의 실제 답 (sha256 로 대조)
2. 다르면 같은 위치·같은 질문 이름의 실제 답
3. 그것도 아니면 여정의 각본 답
4. 술어 설계 본문은 실측된 적이 없으므로 "건전한 판단기" 답 (sup .96 / tense .04). 배선 확인용일 뿐이다.

| 재생 | 실제와 같은 본문 | 같은 위치 실제 답 | 각본 | 결과 (hard 통과) |
|-|-|-|-|-|
| 고치기 전 | 31 | 3 | 6 | 15 (s1.answer, s4.wait 실패) |
| 고친 뒤, choice | 27 | 3 | 6 | 16 (s4.wait 통과, s1.answer 실패) |
| 고친 뒤, predicates | 27 | 0 | 4 (+ 술어 4) | 17 (s1.answer, s4.wait 통과) |

- 실제 실행은 14 였다. 재생에서 s9.reading 이 통과한 것은 뒤쪽 단계 일부가 각본 답이라서다.
- **s4 는 실제와 바이트가 같은 본문으로 재현됐다** (하트비트 요청과 초안 검사 요청 모두).

## 1. 하트비트 메시지의 초안 검사 (과제 1)

### 1.1 원인

s4 의 대기 메시지는 "확인하는 데 시간이 조금 걸리고 있어요. 곧 이어서 말씀드릴게요." 였다.
- 근거로 들어간 것: 그 턴의 기억 페이지 3개 (헬스체크·롤백·후속 체크리스트)와 내용 없는 참조 1개
- 판정: claim not_mentioned .96/.97 (구체 정보가 없는 문장이라 이것만으로는 걸리지 않는다), **present .90/.91**
- 결과: present_tense 지적 → 게시 안 됨

"지금 일어나는 일"을 말하는 문장에, 지금 무엇이 일어나는지 아무것도 말하지 않는 근거를 붙였기 때문이다. s5 의 대기 메시지도 같은 본문, 같은 답으로 막혔다.

### 1.2 수정

`messageEvidence` 가 메시지를 지을 때 쓴 사실을 근거로 만든다. 턴의 자료는 쓰지 않는다.

| 근거 항목 | 종류 / 시제 | 내용 |
|-|-|-|
| request | conversation / present | 사용자 요청 원문 |
| now | run_state / present | 경과 초 + 지금 하는 일 (명령줄은 `terminal_command` 가 허용될 때만, 도구 이름, 단계 수, L5 출력 판정 라벨, 마지막 활동) |
| note | run_state / present | ask 일 때 그 에이전트 메모 |
| (포인터) now | run_state / present | 무엇이 어디서 기다리는지 (작성기에 준 고정 문구와 같음), "아무것도 옮기지 않았다" |

- `run_state` 는 egress 증거 종류로 새로 등록했다 (run 데이터 등급).
- 명령 출력은 넣지 않는다.

### 1.3 검사 요청 수와 생략 판단

| 메시지 | 이전 | 이후 |
|-|-|-|
| s4/s5 대기 메시지 (구체 정보 없음) | 1회 (852 토큰), 막힘 | **0회**, 게시 |
| 구체 정보가 있는 대기 메시지 | 1회 | 1회 (choice 약 618 / predicates 약 497 추정 토큰) |
| 포인터 메시지 ("왼쪽에 결과가 준비되어 있어요") | 0회 | 0회 |
| 고정 문구 (`FLOW_COPY.stalled`) | 0회 | 0회 |

**완전히 생략하지 않은 이유.** 문장은 모델이 자유롭게 쓴다. 닫힌 사실로 지시해도 결과를 지어낼 수 있다 ("128개 중 3개 실패"). 계획의 `wait-check-invented-result` 가 이것을 막는지 잰다.

**부분 생략은 R3 으로 정당하다** (`concreteOnly`). 근거가 모두 "지금"의 사실이면 검사가 정당하게 찾을 수 있는 것은 두 가지뿐이다:

| 검사가 찾는 것 | 지금의 사실만 근거일 때 |
|-|-|
| 사실에 없는 구체 정보 (숫자·이름·식별자) | 그런 정보가 있는 문장만 의미가 있다 |
| 시제 불일치 | 근거가 전부 present 라 생길 수 없다 |

그래서 구체 정보가 없는 문장은 보내지 않고, 남는 문장이 없으면 요청하지 않는다. 기존 검사도 구체 정보가 없는 문장에는 "근거 없음"을 내지 않았다. 실측에서 그런 문장에 붙은 지적은 오작동한 present 질문뿐이었다.

## 2. 초안 검사 술어 설계 (과제 2)

### 2.1 실측이 가리킨 것

진짜 원인은 N-way 선택지만이 아니었다. 세 경우에서 present 질문("does it state a plan, a past log or a relayed report as a present fact")이 맞는 문장에 '예'로 답했다.

| 경우 | 문장 | present | 결과 |
|-|-|-|-|
| s1 | 계획을 계획으로 쓴 문장 ("…발송 예정입니다") | .97 → 고친 뒤 .96 | "근거가 부족해…" 로 대체 |
| s4/s5 | 현재 활동을 말하는 대기 메시지 | .90/.91 | 막힘 |
| s6 | "테스트가 모두 통과했습니다." | .96 | 대체 |

모델은 "AS a present fact"가 아니라 "states a plan"으로 읽는다. 선택지(claim)는 insufficient .69/.76 로 어중간했다.

### 2.2 설계 (`design: 'predicates'`, 선택형)

- 근거 목록을 시제 표시와 함께 한 번 인용한다. 내용 없는 참조는 인용하지 않는다.
- 문장마다 따로 인용하고 (R4), 문장마다 예/아니오 두 개를 묻는다 (R2):
  - `sup_i`: "근거가 문장 Si 가 말하는 것을, 그 안의 구체 정보까지 말하는가"
  - `tense_i`: "Si 가 근거상 계획이거나 과거일 뿐인 것을 지금 끝났거나 사실이라고 말하는가"
- 코드의 조합:

| 조건 | 결과 |
|-|-|
| sup ≤ 0.3 (확신 있는 아니오) + 구체 정보 있는 문장 + 내용 없는 참조 없음 | `unverified` |
| tense ≥ 0.7 | `present_tense` |
| 그 사이, 또는 답 실패 | 아무것도 결론 내지 않음 (통과) |

수정 지시문·부분 게시·문구는 choice 설계와 같다.

**근거를 문장별로 고르지 않은 이유.** 처음에는 단어 겹침으로 문장마다 관련 근거를 골랐다. s1 에서 "견적은"과 "견적서"가 겹치지 않아 관련 근거 0개 → 앞 3개(제목만) 인용이 되는 것을 테스트가 잡았다. 어느 근거가 어느 문장에 해당하는지는 판단기에 맡긴다.

### 2.3 선택과 비교

| 설정 | 동작 |
|-|-|
| `decisionContext.draftCheck.design()` 기본 | `'choice'` (바이트 그대로) |
| `EGDESK_DRAFT_CHECK_DESIGN=predicates` (브리지) | `'predicates'`. 기존 `EGDESK_DRAFT_CHECK` 가 켜져 있을 때만 읽는다 |

- 기록에 `design` 이 남고, 술어 판정은 `claim_supported` / `claim_tense` 로 남는다.
- s1 검증 (모의):
  - 재생에서 L7 수정이 들어간 s1 본문을 제품이 만들었다. 근거 7개 중 E6/E7 에 본문이 들어 있다.
  - 건전한 답이면 답이 그대로 게시된다.
  - 실제 choice 답(.69/.97 → .76/.96)을 같은 문장에 재생하면 `ask_user` 가 된다. 단위 테스트로 고정했다.

## 3. 포인터: 요청한 결과는 코드 규칙 (과제 3)

| 경우 | 이전 (c16) | 이후 |
|-|-|-|
| 그 사람이 요청한 결과 (run 의 requester = 포인터 대상) | "그 사람이 볼 필요가 있나" 질문 (.74/.42 로 실패) | **질문 없음**, 정의상 필요. `told_N` 만 묻는다 |
| 요청하지 않은 결과 (멤버 작업을 소유자에게) | 같은 질문 | "요청하지 않은 결과에 그가 처리하거나 결정할 것이 있나" (인용 하나) |
| 결정·질문 종류 | 질문 없음 | 그대로 |

- 요청자 판정은 원 run 의 audience requester 다 (L1 요청자 식별, `conversationFlow.audience`). audience 가 없으면 로컬 사용자가 자기 대화에서 요청한 것으로 본다. 보관된 포인터는 보관할 때의 그 사람 id 로 판정한다.
- **already-told** (요청한 결과): `told_1` 만 묻는다. c16 실측 1.0 과 같은 인용문이라 다시 재지 않는다. 예 → 포인터 없음.
- **nothing-to-look-at** (요청한 결과): 이제 포인터가 **나간다.** c16 의 .05(아니오)는 맞는 판단이었지만, "요청한 결과는 정의상 필요" 규칙이 우선한다. 비용은 한 줄. 결정 필요 항목에 넣었다.

## 4. "?" 거르기 다시 보기 (과제 4)

| 근거 | 값 |
|-|-|
| 실측 (c16) | "?" 없는 정보 요청 메모: ask .97 / 평범한 메모: ask 0 → c16 에 적은 재검토 조건 충족 |
| 모의 비용 (c16) | 거르기를 없애면 요청 +1, 질문 +3, 바이트 +80% |
| 모의 결과 (c16) | 최신 메모 하나만 인용하므로 12초의 진짜 요청 메모가 끝내 판단받지 못했다 |

**권고: 거르기를 없애기만 하지 말고, 다음 방식으로 바꾼다.** 구현은 하지 않았다 (결정 필요).
1. "?" 로 끝나는 메모는 지금처럼 바로 묻는다 (새 선택지 → 즉시 요청).
2. 그 밖의 메모는 **어차피 나가는 요청에 얹어** 묻는다. 판단 안 된 메모 중 오래된 것부터 최대 2개, 각자 `ask_N` 질문으로 따로 인용한다.
3. 한 번 판단된 메모는 다시 묻지 않는다.

같은 시나리오 추정 (실측 아님): 요청 수 그대로(2), 바이트 약 +40%, 12초 메모는 30초 요청에서 판단된다 (18초 늦게, 지금은 끝내 못 함).

## 8. 결정이 필요한 것

1. **초안 검사 술어 설계를 켤지.** 지금은 꺼져 있다. 재측정 결과(s1/s6/대기 메시지)를 보고 정하는 것을 권한다. 켜면 답·하트비트 메시지 검사 모두 이 설계를 따른다.

3. **요청한 결과는 언제나 가리킨다.** "볼 것 없음" 답 뒤에도 포인터 한 줄이 나간다 (c16 `nothing-to-look-at` 은 .05 로 맞게 판단했었다).
4. **요청하지 않은 결과는 처리·결정할 것이 있을 때만 소유자를 가리킨다.** 평범한 초안은 가리키지 않게 된다 (`pointer-owner-elsewhere` 결과로 확인).
5. **"?" 거르기를 4절 방식으로 바꿀지.** 다음 사이클에 구현할 수 있다.
6. 승인 대기 문구는 그대로다 (`FLOW_COPY.stalled`, `DRAFT_CHECK_COPY` 2건 등). 이번에 새 사용자 노출 문구는 없다.
