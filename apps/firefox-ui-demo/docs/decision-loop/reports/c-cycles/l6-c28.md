# L6 Cycle 28 — 심어 둔 초안(planted draft) 모드: 재작성 → 재검사 → "nothing remains" 경로의 실모델 측정 도구

브랜치 `lane/c28-planted-drafts` (base `int/c14` = 234ad95), 커밋 `e444b17`. 코드 변경은 테스트·측정 도구뿐이고, 제품 동작(`helper/codex-chat-runtime.mjs` 등)은 건드리지 않았다. 실요청은 보내지 않았다(Main이 보낸다). L2의 variant builder·nudges 스크립트는 건드리지 않았고, L2의 c26 재작성 도구는 **수정하지 않고 등록(registration)으로만 확장**했다.

## 1. 왜 필요한가 [측정]
L2의 `check-20rw`(c26 재작성 도구 실행): 8/8 대화가 정직하게 답했다. 실제 모델이 심어 둔 나쁜 초안을 쓰지 않았다(a-number, c-contradicted 모두 `elicited 0`, 초안 검사 4+4회 모두 `as_written`, 재작성 0회). 즉 **발견(finding) 이후 경로 — 실모델 재작성, 실판정 재검사, 게시 결과, "nothing remains" — 는 실모델로 한 번도 측정되지 않았다.** 모델이 나쁜 초안을 써 주기를 기다리지 않고, 나쁜 초안을 **기록된 문장으로 직접 넣는다.**

## 2. 방법 (제품 경로는 그대로, 초안 한 곳만 교체)
- 새 턴 필드 `plant: { draft }` (`helper/egdesk-real-engine-planted.mjs`, 등록은 `helper/egdesk-real-engine-registrations.mjs` 끝 구역, 스키마 파일 재생성).
- 훅 `planted`가 **`chat.checkHeldDraft(run, text)` 한 곳만** 감싼다. 제품이 "붙잡아 둔 초안"을 검사에 넘기는 바로 그 지점에서 `text`를 심은 초안으로 바꾼다. 그 뒤는 전부 제품 그대로다: 그 턴의 실제 근거(evidence), 실판정(Decision) 1차 읽기, finding 안내문, **실모델의 재작성(`reviseOnFork`, 비공개 fork 턴)**, 실판정 재검사, 제품이 정하는 게시(재작성/확실한 부분만/아무것도 안 올림).
- 등록 순서가 중요하다: L2의 `rewrite` 훅 뒤에 등록해서, rewrite 훅이 복사하는 "검사가 읽은 초안"이 심은 초안이 된다(테스트로 확인: `r.draft === 심은 초안`).
- 모델 자신의 답은 `turn.planted.modelDraft`에 남는다(심은 초안과 비교 가능). 심은 초안이 검사에 한 번도 안 닿았으면 `planted.applied` 기대가 **눈에 보이게 실패**한다.
- 기록(턴마다): 재작성 문장·안내문(`turn.rewrite.rewrite.text/note`), 재검사 값(`reread`: 문장별 support/tense/rejects), 게시 결과, nothing-remains, 심은 문장 그대로 게시 여부(`postedAsPlanted`), 금지 구절·미지 숫자 게시 여부.

## 3. 예산·상한 [재계산]
상한 **60,000 Decision input tokens**, 4회 × 4사례 = 16대화. 기존 실측 호출별 토큰(`check-20rw`, `check-20ct`, `check-21ct` 기록의 `inputTokens`):
- 메모리 선택 호출(7페이지): tn_* 731 + answer_type/rel_* 1,719 + pg_* 1,844 = 약 4.3k (대화 1개당). 페이지가 줄면 비례해 줄어든다(페이지당 약 0.4k [해석]).
- 한 문장 초안 검사 약 0.7k, 재검사 약 0.7k. coding 판정 질문은 호출당 0.24~0.68k.
- 그래서 **페이지를 사례가 필요한 2개로 줄였다**(7개 전부 쓰면 16대화가 84k 안팎으로 상한을 넘는다 [재계산]). 선언한 대화당 추정: s13 3,800 / coding 3,500 / number 3,800 / tense 3,700 → 4회분 합계 **59,200**.
- 한계 [한계]: 페이지당 비용의 선형 가정은 측정이 아니라 해석이다. 페이지를 줄여서 실판정이 읽는 근거가 all-on journey 때보다 적다(s13은 `pg-plan`이 그대로 있어 모순 근거는 유지).
- 상한은 도구가 **강제**한다: 대화마다 별도 체크 프로세스로 실행하고, 대화 전에 `이미 쓴 토큰 + 그 사례 추정 > 60,000`이면 멈춘다(`reason: ceiling`). 쓴 토큰은 응답의 `usage.input_tokens`(기록의 호출 행)에서 읽는다. 라운드 순서(1회차 4사례 → 2회차 …)라서 멈춰도 사례 간 회수가 같다. 추정이 틀려도 초과는 대화 1개 분량이며 `overCeiling`으로 기록된다.

## 5. 가짜 실행에서 이미 드러난 제품 관측 두 가지 [측정]/[해석]
1. **게시 라벨은 "모델이 쓴 텍스트"와 비교한다.** `codex-chat-runtime.mjs:6482`는 게시 텍스트가 모델의 원문과 같으면 `as_written`, 아니면 `revised`로 라벨한다. 심은 초안이 검사를 그대로 통과하면(would_pass, 텍스트 불변) 제품 라벨은 `revised`가 된다(가짜 실행에서 확인). 그래서 점수표는 라벨이 아니라 **게시 텍스트**로 단어를 정한다(`postedWordOf`: 아무것도 없음=withheld, 심은 문장 그대로=as_written, 그 외=제품 라벨). 제품 라벨은 `turn.rewrite.posted`에 그대로 남는다. **실사용에서는 모델 원문이 곧 검사 대상이라 이 불일치가 생기지 않는다**(심기 때문에만 생기는 도구 쪽 문제).
2. **근거가 0개면 검사는 읽을 문장이 없다.** 근거 없는 coding 가짜 실행: `evidence.items 0 → judgments []`, `would_pass`. 명령 실행 근거가 있어도 내용 없는 참조(opaque)뿐이면 support .02여도 판단이 `unknown`(reject 아님)이었다. 실제 coding 실행에서는 러너 집계가 근거로 들어가고(c29) 코드 수준 사실 비교가 따로 있으므로 다를 수 있다. 이 사례의 실측이 그 차이를 보여 줄 것이다. 가짜 환경에서는 coding 기대가 두 개 실패해야 정상이고(테스트가 그걸 고정한다), 조용히 통과하지 않는다.

## 7. 읽는 법 / 못 말하는 것 [한계]
- 점수표 한 줄 = 사례별: 심은 초안 적용 n/n, 1차 읽기가 찾은 비율, 재작성 실행 수(빈 응답 수), 재검사 통과, 게시(원문 그대로 / 재작성 / 확실한 부분만 / nothing remains), 심은 문장이 사람에게 도달한 수, 금지 구절·미지 숫자 도달 수, 토큰.
- n=4라서 비율의 구간은 넓다. "재작성이 항상 통과한다/실패한다"는 말은 못 한다. 1회 이상 일어났다는 존재 증명과 텍스트 관찰이 목적이다.
- 심은 초안은 **모델이 스스로 쓸 법한 초안의 대표가 아니다**(모델이 정직하게 답한다는 건 c26에서 이미 봤다). 이 측정은 "그런 초안이 나왔을 때 제품이 어떻게 하는가"만 말한다. "그런 초안이 얼마나 자주 나오는가"는 계속 L2 c26 측정의 몫이다.
- 재작성 모델은 같은 대화의 fork에서 **심은 초안을 자기 초안으로 믿고** 고친다. 이건 제품에서의 정상 입력과 형태가 같지만, 모델이 "내가 쓴 적 없는 문장"을 받는다는 점은 다르다. 재작성 품질 일반화는 조심.
- 메모리 페이지를 2개로 줄인 효과(근거 적음)는 위 3절 참고. coding 세트의 `coding.*` 기대는 c29의 가짜 환경 테스트가 이미 고정했고 여기서는 가짜 러너가 없어 재검증하지 않았다.
- 판정 대역(ruleJudge)은 실판정의 대용이 아니다: 이 테스트는 배관이 맞다는 것만 증명한다.
