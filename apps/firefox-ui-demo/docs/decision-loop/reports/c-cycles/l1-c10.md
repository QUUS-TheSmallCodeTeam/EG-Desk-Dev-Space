## 1. 요청자 식별

### 결론
멤버 B가 낸 Board 질문 요청에 대해, 소유자 Desk가 "누가 냈는지"를 **협업 서비스가 보증한 presence alias**로 알게 되고, 그 alias가 (a) Board ask의 prepare/run 기록, (b) L4 배치 훅의 `work.requester`, (c) L3 audience 규칙의 `conversationFlow.audience`로 전달됩니다. 전부 c9의 presence 플래그 뒤에 있고 기본값은 꺼짐입니다(pref `egdesk.presence` = `"on"`, 브리지 `EGDESK_PRESENCE=on`). 플래그가 꺼져 있으면 새 코드는 한 줄도 실행되지 않습니다.

### 왜 alias를 "받아 적지" 않았나
- alias만으로는 보낸 사람이 증명되지 않습니다. presence 피드를 보는 멤버는 누구나 다른 멤버의 alias를 읽을 수 있어서, 요청 파일이나 요청 본문에 alias를 적게 하면 사칭이 가능합니다.
- 그래서 **alias를 클라이언트가 입력하는 경로를 만들지 않았습니다.** 대신:
  1. 요청을 만든 Desk가 그 요청의 **불투명 태그**(요청 id + digest의 SHA-256, 64 hex)를 presence 교환에 `claim`으로 실어 보냅니다. 질문 내용·요청 id·digest·질문 코드는 서비스로 가지 않습니다.
  2. 서비스(`egdesk-joint-presence.mjs`)는 **인증된, 그 Board에 자리가 있는, presence를 공유 중인** 멤버의 claim만 받습니다. 공유가 `off`면 claim 자체를 400으로 거절합니다.
  3. 요청 파일을 받은 Desk가 같은 태그를 `resolve`로 물으면, 서비스가 claim한 멤버의 alias를 돌려줍니다. 태그는 그 요청 파일을 가진 쪽만 계산할 수 있습니다.
- 즉 alias는 "서비스가 인증한 사람의 alias"이지 "누군가 적어 낸 값"이 아닙니다.

### 세 가지 요구에 대한 확인
| 요구 | 구현 | 테스트에서 확인한 것 |
|-|-|-|
| 내용 없음(content-free) | 태그는 해시, alias는 `m-` + 16 hex. Board ask 기록에는 `{ board, alias }`만 | 서비스로 간 본문 전체에 질문·요청 id·digest·코드·"주차"가 없음. 배치 판단 요청과 포인터 작성 프롬프트에 alias·과제 문구 없음 |
| 권한 확인(그 Board의 착석 멤버) | 서비스: 착석 + 공유 중인 멤버의 claim만. 창: `seated(board, alias)`(서비스가 지금 그 Board에 올린 멤버). 브리지: 미러 스냅샷에 있는 alias만, 아니면 409 | 임의 alias, 다른 Board id + 실제 alias, 이름("B") 모두 거절. 브리지 단독 호출도 409 `unknown-member` |
| 보존 기간 | 전부 메모리. 서비스 claim은 마지막 알림 후 15분, 공유를 끄거나 자리를 잃으면 즉시 삭제. run의 요청자는 30분 또는 run 종료 시 삭제. Board ask는 티켓(메모리)과 응답에만 | Desk 저장 파일 어디에도 alias 없음. 공유 끔 → 다음 교환에서 사라짐. Board 탈퇴 → 사라짐. 15분/30분 경과 → 사라짐 |

run 기록의 기존 보존(채팅 저장소는 영속, Board ask 티켓은 만료까지 메모리)보다 길게 남는 곳은 없습니다. 영속 저장소에는 아예 쓰지 않습니다.

### 종단 간 테스트 (`helper/egdesk-requester-identity.test.mjs`, 5개 전부 통과, 3회 반복 통과)
세 레인의 실제 모듈을 한 흐름으로 묶었습니다: L1(joint presence 서비스 + 클라이언트 + 미러 + 요청자 레지스트리), L4(`EGDeskWorkPlacement` 장면·옵션·주의 요청, 판정 반쪽 `egdesk-work-placement.mjs`를 실제 heartbeat에 붙임), L3(실제 `CodexChatRuntime`의 audience 규칙과 포인터 경로, mock 엔진·mock Decision 모델·가상 시계).

1. B가 요청을 만들고 소유자가 엽니다 → 서비스가 B의 alias를 보증합니다.
2. 소유자의 Agent가 그 요청을 소유자 대화에서 처리합니다.
3. **뷰어 배치 옵션은 B 근처**: `near_requester`가 B의 뷰 바로 바깥. 모든 옵션이 소유자 뷰 밖. 요청자를 넘기지 않으면 같은 옵션이 소유자 뷰 근처로 나옵니다(전/후 비교).
4. **소유자 뷰는 그대로**: 카메라, 포커스, 소유자 카드, 소유자 자신의 presence 행이 run 전과 바이트 단위로 동일.
5. **완료 결과 포인터**
   - 소유자가 할 일이 없을 때: L4가 `pointerFor: requester`로 판단하고, 요청자는 소유자 Desk에 대화가 없으므로 경로가 없습니다(`no_conversation`). 소유자 대화에는 메시지 0건, 메시지 이벤트 0건.
   - 소유자가 결정해야 할 때: `pointerFor: owner`, 소유자 대화에 포인터 메시지 **정확히 1건**, 배치 런타임이 사실을 회수.
6. audience 규칙: B는 기다리는 중이고 접속해 있지만 소유자 대화의 참가자가 아니므로, 진행 메시지는 그 대화에 쓰이지 않습니다(`postable: false`).

변이 확인(`evidence/l1-c10/mutations.txt`): 브리지의 멤버 확인, 창의 착석 확인, 서비스의 선점 규칙, 배치 훅 전달, audience 공급자를 각각 무력화하면 테스트가 실패합니다. 테스트가 빈 통과가 아닙니다.

### 한계 (숨기지 않고 적습니다)
1. **소유자 Agent run을 Board 요청에서 시작하는 화면이 제품에 없습니다.** Board ask의 답은 회신 작성기로 가고 채팅 run이 아닙니다. 그래서 "요청 → 요청자 확인 → Board ask 기록"까지는 제품 경로로 이어져 있지만, "그 요청자를 채팅 run에 붙이는 것"은 훅(`state.runRequesters.set(ref, requester)`)만 있고 부르는 UI가 없습니다. 종단 간 테스트는 이 훅을 직접 부릅니다(제품이 만드는 상태를 모델링한 것이 아니라 아직 없는 트리거를 대신한 것입니다).
2. **Board 요청은 파일로 오가서 어느 joint Board의 것인지 정해져 있지 않습니다.** 요청 Desk는 자기가 presence를 공유 중인 모든 Board에 태그를 알리고, 받는 Desk는 자기 Board들에서 묻습니다. 두 사람이 같은 joint Board에 있고 요청자가 공유를 켠 경우에만 식별됩니다. 그 외에는 지금처럼 로컬 사람으로 처리됩니다.
3. **파일을 가진 사람은 누구나 claim할 수 있습니다.** 먼저 claim한 착석 멤버가 유지되지만, 원래 요청자가 공유를 끄면 같은 파일을 가진 다른 멤버가 그 자리를 차지할 수 있습니다(테스트에 그대로 적어 두었습니다). 요청 파일이 전달·유출된 경우의 한계입니다. 완전히 막으려면 요청 파일 형식에 요청자 서명을 넣어야 하는데, 암호화된 파일 형식을 번들 의존성 테스트 없이 바꾸는 것은 이번에 하지 않았습니다.
4. **창이 닫히면 태그 알림이 끝납니다.** 요청 Desk는 열려 있는 동안 최대 24시간 알리지만 메모리에만 있어서 재시작하면 사라집니다. 로컬 요청 기록에서 다시 계산해 알리는 것은 다음 단계입니다.
5. presence 미러는 Board id를 떼고 행을 합치므로, 브리지의 확인은 "지금 피드에 있는 멤버인가"까지입니다. "그 Board의 멤버인가"는 창이 서비스 응답으로 확인합니다.
6. 요청자에게 가는 포인터는 지금 갈 곳이 없습니다(요청자의 대화는 요청자 Desk에 있음). 요청자 Desk로 알리는 경로는 별도 결정이 필요합니다.
