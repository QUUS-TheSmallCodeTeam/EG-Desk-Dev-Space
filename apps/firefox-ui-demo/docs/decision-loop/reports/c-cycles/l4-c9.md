## 0. D2 반영: 데이터 공유 권한과 L5의 공용 egress 도우미
사용자 결정(D2)대로 Decision 모델도 다른 모델과 같은 데이터 공유 권한 설정을 따른다. **L5의 공용 egress 도우미는 int/c8에 아직 없다**(저장소와 L5 작업 트리를 검색, 해당 파일 없음). 그래서 핸들러에 주입 지점 `egress(kind, preview) → boolean`을 하나 만들었다(`createBoardPresentationHttpHandler({ egress })`). 판정 요청을 보내기 직전마다 호출되고(placement / briefing-reuse / briefing-check), `false`이면 그 요청은 나가지 않고 흐름은 말풍선으로 남는다. 도우미가 들어오면 이 한 곳에 연결하면 된다. 기본값(주입 없음)은 c8과 같은 동작이다. 별도 카드 라벨/본문 동의는 추가하지 않았다.

## 1. 결과 카드를 브리핑 target으로 묶기
- 조사: 기존 `egdesk_publish_briefing_multi`의 target은 `sourceId`(실행에 바인딩된 불변 source) 또는 `artifactId`(**현재 실행의 파일 산출물 후보**를 `pinOutput`으로 고정)뿐이다. 게시된 결과(`egdesk_publish_output`)는 어느 쪽도 아니라서 이전 답변의 결과 카드는 그대로는 target이 될 수 없었다. 도구 스키마는 해시로 고정되어 있어 바꾸지 않는다.
- 해결: `ContextRuntime.bindCardSource(run, { outputId, viewId })`(신규). 브리지 자신의 **출력 저장소**에서 그 결과의 본문을 읽어(화면이 준 내용이 아님) 같은 대화의 결과인지 확인하고, `kind:'board'` 불변 source로 캡처해 그 실행에 바인딩한다(`pinOutput`과 같은 절차와 `context.bound` 이벤트). 그러면 sourceId가 기존 `briefingTarget` 검사를 그대로 통과한다. `viewId`는 힌트로 캡처의 viewId와 같아야 한다. 같은 outputId는 한 번만 캡처(멱등). 다른 대화의 결과, 잘못된 id, 존재하지 않는 id, 브리핑 권한(`publishBriefing`)이 없는 실행은 거절(시험).
- `ContextRuntime.proposeBriefing(run, { title, steps })`(신규): `{outputId, viewId}` target을 바인딩해 `{sourceId, viewId}`로 바꾼 뒤 **`publish()`(= 도구가 쓰는 같은 함수)**로 발행한다. 같은 검증, 같은 `proposed` 기록(`presentationStatus:'proposed'`), 같은 `briefing.published` 이벤트이므로 사용자는 기존 브리핑 UI로 열고 이동한다. 모델 턴을 시작하지 않고 카메라도 움직이지 않는다.
- 흐름 모듈: 컴포넌트에 `targetable`(바인딩할 수 있는 ref가 있는가)을 추가했다. target이 될 수 없는 컴포넌트(메모, ref 없는 카드)는 `reuse` 선택지가 없고, 회수 가능도 아니면 질문 자체를 하지 않는다(브리핑에 포함되지 않음). 크롬 어댑터는 provenance에 `outputId`가 있는 결과 카드에만 `ref:{outputId, viewId}`를 준다.

## 2. `on` 경로 (같은 플래그 뒤, 기본 OFF)
- 플래그: pref `egdesk.briefingFlow`가 정확히 `"on"`(전체 흐름) 또는 `"advisory"`(c8, 기록만). 그 외 값은 모두 off. `on`이 실제로 일하려면 크롬 pref `on` **그리고** Decisions 모드 `on` **그리고** 브리지에 주관 모델(engine)·실행 조회·발행 경로가 주입되어 있어야 한다. 하나라도 빠지면 `skipped`(`mode` / `no-engine` / `run-gone`)로 아무것도 하지 않는다.
- 순서: 말풍선 vs 보드 판정 → 재사용/회수/새 컴포넌트 판정 → 재사용 우선 설계(주관 모델) → 단계별 흐름 점검 루프(재설계 최대 2회) → 통과하면 새 컴포넌트(0..n)를 에이전트 자신의 게시 경로(`publishOutput`)로 만든 뒤 → `proposeBriefing`으로 제안 발행. 실패(점검 미통과, 권한 없음, 새 컴포넌트 본문 미수신, 발행 오류)는 모두 `fallback-chat`: 아무것도 발행·생성·제안하지 않고 채팅 답변이 그대로 남는다(회수 제안도 내지 않음).
- 회수 제안: 응답의 `retrievals:[{viewId}]`를 서피스가 받아 provenance가 있는 결과 카드인지 다시 확인한 뒤 **보류**한다(`state.briefingRetrievalOffer`). 패널을 대신 열지 않고 포커스도 가져가지 않는다. 사용자가 책상 빠른 정리를 직접 열면(`WorkbenchArrange.open('@desk')`) 그때 미리보기 선택지 하나로 올라오고(한 번만 소비), 적용·되돌리기·⌘Z는 기존 history를 쓴다. 공유 Board는 쓰지 않는다.
- 새 컴포넌트가 만들어지는 단계는 아직 캔버스 카드가 없으므로 target이 `{sourceId}`뿐이다(밝힐 창 없이 설명만 보임). 사용자가 결과 칩을 열면 카드가 생긴다.

## 5. 열린 점
- **주관 모델 어댑터 없음**: 브리지에는 설계·재설계·새 컴포넌트 본문을 요청하는 Codex/Claude 호출 경로가 없다(별도의 모델 턴 경로가 필요). 그래서 브리지 배선(`codex-bridge-server.mjs`)은 `engine: null`로 두었고 **프로덕션에서 `on` 경로는 `no-engine`으로 아무것도 하지 않는다.** 실행 조회·제안 발행·출력 게시는 실제 런타임에 연결되어 있다. 이 어댑터가 가장 큰 남은 일이다.
- 실행 종료 후 발행: 시험의 실행은 진행 중 상태다. 종료된 실행의 바인딩이 `assertBound`를 계속 통과하는지는 코드 읽기(바인딩은 실행 단위로 유지)로만 확인했고 실제 종료 후 호출은 검증하지 못했다.
- 브리핑 권한이 없는 실행을 시험하려고 바인딩의 `publishBriefing`을 false로 둔 상태를 모델링했다(권한 없이 보낸 실행이 만드는 바인딩 상태와 같은 필드, 시험 주석에 명시).
- 새 컴포넌트 본문은 주관 모델이 한 번 더 써야 하므로(`briefing_component` 요청) 추가 모델 호출과 비용이 든다. 예산은 Decisions 호출만 계량하고 주관 모델 호출은 그 경로의 몫이다.
- `stale` 신호, 보정 로그의 판정 종류 구분 필드, `outcome.next`는 여전히 없음.
