## 3. 수정 (제품) [측정 가능한 형태로]
고칠 수 있는 "진짜 원인"은 엔진 정지 자체가 아니라 **정지 한 번이 고쳐 쓰기 전체를 25초 동안 막고 빈 답으로 끝내는 구조**다. 수정은 세 가지:
1. **hedge** (`helper/codex-internal-turn.mjs`, `helper/codex-chat-runtime.mjs` `reviseOnFork`): fork 턴이 `REVISE_FORK_HEDGE_MS = 11_000`(측정한 끝난 내부 턴 최대 10.7초보다 큼) 안에 끝나지 않으면 **같은 일을 새 임시 스레드에서도 시작**한다(도구 없음, `fresh` 경로 그대로). 먼저 끝난 쪽이 이기고 둘 다 해제한다. 전체 마감 25초는 그대로 → 최악의 경우도 지금보다 나쁘지 않다. fork 가 제때 끝나면 아무 것도 달라지지 않는다. 실제 효과: 정지 시 25초 침묵 → 약 11 + 8 = 19초에 글(추정: fresh 완료 4/4, 7.3~10.7초).
2. **새 스레드 문장에 근거를 넣는다**: 새 스레드는 대화를 본 적이 없다. 지금까지 새 스레드 경로(한 번성 방, ephemeral)의 고쳐 쓰기 프롬프트는 "the material" 을 가리키지만 근거가 들어 있지 않았다(잠복 결함). `checkHeldDraft` 가 검사에 준 근거 항목(읽을 수 있는 것만, 최대 8개, 항목당 1,200자)을 `revise` 콜백으로 `reviseOnFork` 에 넘기고, 새 스레드 문장 앞에 "The material you were given:" 로 붙인다(`reviseFreshText`). fork 문장은 그대로(대화 기록이 있음). `checkDraft` 는 건드리지 않았다.
3. **내부 턴 추적**(내용 없음, 닫힌 단어·숫자만): 결과와 마감/실패 오류에 `trace` — 시도별 {via, startMs, firstEventMs, 사건 최대 30개 [ms, 방법, 항목 종류, phase/상태], 거부한 서버 요청 방법 목록, completed}. 정지가 "이벤트 0" 인지 "이벤트는 있고 완료만 없음" 인지 "도구 요청을 시도함" 인지 다음 실행에서 보인다. L3 요청대로 fresh 시도의 첫 이벤트 시간도 남겨 두 경로를 비교할 수 있다. 실제 점검 기록(`egdesk-real-engine-check.mjs`)의 `internalTurns` 항목에 `trace`/`hedged` 추가(`closedTrace`).
- 부수 수정(측정 도구): rewrite 훅의 `reviseOnFork` 감싸개가 4번째 인자 이후를 버렸다 → 근거가 전달되지 않을 뻔했다. 나머지 인자를 그대로 전달.

## 5. 못 말하는 것 [한계]
- hedge 가 실제로 7/12 를 줄이는지는 **실측 전**이다. 엔진 정지가 새 스레드에도 닿는 시간대(L3 가 본 180초 주 턴 정지처럼 엔진 전체가 침묵)이면 hedge 도 같이 멈춘다 — 그때는 25초 마감, 지금과 같다. trace 가 두 경우를 가른다.
