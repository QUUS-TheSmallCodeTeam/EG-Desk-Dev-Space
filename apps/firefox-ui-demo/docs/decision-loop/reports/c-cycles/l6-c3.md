# L6 / C3: 실제 결과로 보는 Decision 기능 (int/c2 기준 재생)

증거: `evidence/l6-c3/` (`replay.mjs` 재생 스크립트, `results.json` 전체 수치, `keepalive-probe.mjs/.out`). 제품 코드는 `wt-l6c3`(= int/c2 256c816)의 실제 함수를 그대로 import해서 돌렸다. 제품 패치 없음, 커밋 없음.
읽은 입력은 지정된 영수증만(attachments 미접근): w3 단발 영수증(1건), 실호출 요약 JSON, key-check, ko-responses/ko-scored-final, live/service ledger, text-defaults, delivery-public-v1.

## 1. 측정된 사실 (영수증에 적힌 값, 가공 없음)
- 턴 시작 요청 1건: HTTP 200, 입력 토큰 2539, 출력 0, 지연 2062 ms (IPC 대기 2082 ms), 본문 9157 B, 10문항 모두 이름/타입 일치 응답, `stockBudgetMet: false`.
- w3 각 문항 (top = 분포 최댓값, 2위, `confidence` = API가 준 값):
  - answer_type: `answer`, top .99 / 2위 .01, confidence .99 (4지선다)
  - time_intent: `cross_time`, top .85 / 2위 .07, confidence .82 (6지선다)
  - rel_0: predicate 0, rel_recall: predicate 1
  - speech_source_0: attributed_report, top .37 / 2위 .31(unknown), confidence .24 (6지)
  - speech_form_0: assertion, top .37 / .26, confidence .21 (5지)
  - speech_time_0: unknown, top .39 / .20, confidence .29 (7지)
  - speech_source_1: attributed_report, top .40 / .21, confidence .28 (6지)
  - speech_form_1: assertion, top .33 / .23, confidence .16 (5지)
  - speech_time_1: future_anchored, top .24 / .18, confidence .11 (7지)
- 사전등록 기대와의 비교(Main 영수증): 첫 선택 일치 3, 다름 2, 허용된 기권 1 (n=6).
- **confidence의 정체 (16개 choice 응답에서 확인)**: `confidence = (top - 1/N) / (1 - 1/N)` (N = 선택지 수, 우연 수준 보정 확률). 16개 전부 오차 0.005 이내 (예: 6지 top .37 -> .244 vs 보고 .24; 4지 top .99 -> .987 vs .99). score 4개도 0.015 이내. 즉 `confidence`는 top 확률이 아니고, 같은 top이라도 선택지가 많을수록 낮게 나온다. top과 confidence의 최대 차이는 이 표본에서 0.17.
- 분포 합: choice 16개 모두 정확히 1.00.
- ko 16문항: 이름/타입/모델 일치 100%, 무시/위치 대응/중복 행 0. 의미 일치 13, 판정 유보 3 (순위 하위 동률), 불일치 0. choice 8개 confidence .97~1, margin .97~1. predicate 4개 모두 0 또는 1.
- 지연: 따뜻한 연결 12건(text-defaults) 230~367 ms (중앙 250); service ledger 17건 중앙 246 ms, 최대 541 ms (첫 호출). **차가운 연결 3건: 1409, 2062, 2229 ms** (문맥 첫 요청 / w3 / 공식 key check).
- Board 사진 choice 1건: 582 ms (ledger), 입력 토큰 843, 요청 본문 20896 B (PNG 13510 B). key check: 288 ms(UI) / 2229 ms(공식, cold).
- 로컬 오프라인 측정 (루프백, 서버가 Keep-Alive 힌트를 안 보낼 때 Node v26.5.0 전역 fetch): 유휴 3.5초까지 연결 재사용, 4.5초부터 새 연결. 즉 클라이언트 기본 유휴 한계가 약 4초. (OpenAI 쪽 힌트는 모름.)

## 2. 제품 규칙 재생 (결정적, int/c2 코드, 실제 함수)
임계값: 문맥 choice .75(margin 요구 없음), relevant .5 / strict .8, 발화축 confidence .85 + margin .20, DM chooser top .8 + confidence .8 + margin .2 + 전체 분포 합 1(오차 1e-6), Board choice .75 + margin .2, key check p > .5. 마감: 턴 시작 800 ms(후보 수집 포함), 기본 1500 ms, board excerpt 1000 ms, DM chooser·Board 사진 4000 ms, key 5000 ms.

## 3. 해석 (측정과 구분. 가설은 가설로 표시)
**견고**
1. predicate: 6/6이 0 또는 1 (.2~.8 구간 0건). rel/recall/ko 의미 일치. .5/.8 어디서 갈라도 같은 판정. 상태: 견고 (n=6, 극단값만 본 것이 한계).
2. 선택지가 3개이고 정답이 명확한 choice: 8/8 confidence .97 이상, margin .97 이상. 어느 기능의 임계(.75/.8/.85)로도 통과.
3. 응답 계약: 이름/타입/분포 합/모델 일치 전부 정상. chooser의 엄격한 합 검사 1e-6은 이 표본에서 16/16 통과 (반올림으로 깨질 위험은 관찰되지 않음).
4. 따뜻한 연결의 마감(800/1000/1500/4000/5000)은 모두 여유가 큼 (최대 541 ms).

**사실상 비활성 (이 표본 기준)**
5. 발화축: 실제 응답에서 6축 중 라벨 0개. 이유는 구조적이다: 5~7지선다의 `confidence`는 우연 보정값이라 .85를 넘으려면 top >= .871(7지), .875(6지), .880(5지)이 필요한데 관측 top은 .24~.40. 임계를 .1까지 내려야 3개(margin .1)가 통과하고, 그 3개는 사전등록 일치 여부가 섞여 있어 낮춰도 신뢰는 못 얻는다. 해석 후보: (a) 입력 자체가 모호, (b) 선택지가 많고 `unknown`이 질량을 흡수 (unknown 질량 .18~.39), (c) 질문 정의가 세분화됨. 이 표본(1메시지)으로는 구분 불가. ko의 3지 명확 문항이 전부 결정적이었다는 사실은 "모델이 일반적으로 흐리다"가 아니라 "이 분류 체계에서 흐리다"는 쪽을 지지하지만 선택 편향이 있다.
6. time_intent: accept되어도 `present`일 때만 영향. 이 표본은 cross_time이라 영향 0. answer_type은 읽는 코드가 없음 (관측용).
7. 발화 패킷 비용: 라벨 0개인데도 규칙 블록 + `[]`이 패킷에 실리고, 요청은 10문항/2539 토큰 (발화축 6 + recall 1을 빼면 3문항, service ledger의 3문항 요청은 625 토큰). 토큰은 측정치지만 지연 증가분은 cold와 섞여 분리 불가.

**취약**
8. 800 ms 마감 vs 차가운 연결: cold 3/3 실패(1409, 2062, 2229), warm 12/12 통과. 로컬 측정에서 Node fetch는 4~4.5초 유휴 후 연결을 버린다. **가설 (측정 필요)**: 사람이 메시지 사이에 4초 이상 쉬면 턴 시작 요청은 대개 cold이고 800 ms를 넘겨 fallback이 일상이 될 수 있다. 코드 주석대로 만료된 마감이 소켓을 끊으면 다음 호출도 cold로 돌아간다. int/c2에는 사전 연결/keep-alive 코드가 없다(관련 브랜치 `lane/c3-keepalive-preconnect`는 int/c2에 미포함). fallback 자체는 원칙대로 "지금 방식으로" 안전하게 동작하므로 사용자 해악은 없고 기능이 조용히 꺼지는 문제다.
9. 같은 .85가 선택지 수에 따라 다른 의미: top 기준 2지 .925, 3지 .900, 4지 .888, 5지 .880, 6지 .875, 7지 .871. 같은 임계가 기능마다 다른 엄격함을 가진다. DM chooser는 선택지 N + abstain이므로 conf .8을 맞추려면 top이 2선택 .867, 3선택 .850, 4선택 .840, 8선택 .822 이상 필요.
10. 보정 기록이 게이트가 쓰는 값과 다르다 (재생으로 확인): `calibration` 판정 행은 `top`, `second`, `threshold`만 있고 `confidence`와 선택지 수 N이 없다. 발화축 행은 top .37, threshold .85로 보이지만 실제 비교값은 confidence .24다. 이 기록만으로는 임계를 다시 계산할 수 없고, top에 맞춰 임계를 고르면 최대 0.17 틀어진다 (이 표본).
11. DM chooser는 실샘플 0이라 현재 복원력 판단 불가. 외삽(가설): 주관적인 5~8지 질문에서 발화축처럼 분포가 퍼지면 결과는 `unclear` 또는 `low_confidence`가 되어 "추천 없음"이 잦을 수 있다. 이는 안전한 방향(추천 안 함)이지만 기능의 체감 가치가 낮아질 수 있다.
12. Board 사진: 응답이 기록되지 않아 "조언이 맞았나/확신도가 어땠나"를 알 수 없다. 요청 크기 추정(`estimateInputTokens`): 본문 20896 B에서 이미지(13510 B PNG의 base64 약 18038 B)를 빼면 약 2858 B -> detail 미상이라 1038(low) ~ 1718(그 외) 토큰으로 추정, 실제 843. 추정이 1.2~2.0배 높게 나옴 (예산 가드는 안전 쪽으로 틀림).

## 4. 제품 패치 여부
없음. 재생 중 내 스크립트의 버그 1건(chooser 프록시에서 `authorizeDispatch`를 호출하지 않아 8/8이 manual로 나옴)을 찾아 스크립트에서 고쳤고 제품 결함이 아님.

## 5. 다음 단계 제안 (사용자 승인이 필요한 실호출 포함)
1. 발화축: 5~7지 분류는 단독으로는 .85를 통과하기 어렵다는 것이 이 표본의 사실. 실호출 승인 시 합성 한국어 메시지 약 10개 x 세그먼트별로 같은 6축을 받아 top/confidence/margin을 모으고(n을 늘림) 사람이 정답을 달아 보정. 그 전까지는 발화 질문을 주 요청에서 분리해 recall/relevance 지연·타임아웃에 영향을 주지 않게 하는 안을 시뮬레이션.
2. 보정 기록에 `confidence`와 N 추가 (순수 기록 필드, 동작 무변경). 이후 임계는 confidence 기준으로 계산.
3. cold 연결 가설 검증: 실제 간격(1초/3초/5초/10초)으로 같은 크기 요청을 보내 지연을 재고, `lane/c3-keepalive-preconnect`와 비교 (승인 필요, 약 8회 호출 규모).
4. DM chooser 실샘플 수집: 2/4/6/8지 합성 질문 각 3개, 결과 분포를 기록.
5. 다음 실호출부터 key check와 Board 응답에 확률/선택값을 영수증에 보존 (현재 재판정 불가).

## 6. 철학 점검
"확률은 실행 권한이 아니다"와 "호출이 실패하면 지금 방식으로 돌아간다": 실제 결과가 두 원칙을 둘 다 지지한다. 발화축은 .24 안팎의 확신으로 라벨 0개를 내고 아무것도 단정하지 않았고(원칙 유지), cold 호출은 2062 ms로 마감을 넘겨 fallback으로 안전하게 빠진다. 다만 기능이 "안전하게 조용히" 꺼질수록 사용자에게는 보이지 않으므로, 오히려 화면에서 발견 가능해야 한다는 원칙 쪽 점검이 필요하다: 발화 trace가 accepted 0/6을 보여주는 것은 있지만, "연결이 차가워서 문맥을 못 붙였다"는 사유가 사람에게 보이는지는 이번 자료로는 알 수 없다.
