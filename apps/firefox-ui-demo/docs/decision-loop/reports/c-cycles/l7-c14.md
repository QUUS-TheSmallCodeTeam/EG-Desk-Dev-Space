## 1. 이번 턴의 기억 자료를 데이터로

런타임: `chat.memoryMaterialsFor(key, { excerptChars, max })`, `chat.memoryMaterialsState(key)`. `key` 는 그 턴의 run 객체, 또는 run 이 생기기 전이면 그 send 의 요청 context 객체.
순수 함수: `memoryMaterials(result, wiki, { scope, attached, excerptChars, max })` (`helper/egdesk-turn-memory.mjs`). L8 은 자기 `prepareTurnMemory` 결과에 이걸 직접 쓴다.

행 모양 (동결된 평범한 데이터, 페이지 id·ref·revision·점수 없음):

```
{ alias: 'M1'..'Mn',
  kind: 'board' | 'source' | 'ontology' | 'timeline' | 'utterance' | 'conversation' | 'page',
  time: { slice, at },                  // at: 'YYYY-MM-DD' 또는 null
  provenance: { kind, by, basis },
  status,                               // 기록된 상태: plan | done | superseded | reported_by_other | unknown
  statusReading?,                       // 판정기의 읽기. 채택된 경우만. 검증 아님
  statusPending?,                       // 보고됐지만 사용자가 확인하지 않은 상태
  title (160자 이내), excerpt (기본 400자, 최대 2400자),
  links: [{ type, toAlias }],           // 목록 안의 두 행 사이만
  held }
```

정한 것과 이유:
- **`held` 의 뜻**: `false` 는 이번 턴 묶음에 붙은 페이지, `true` 는 이 스레드의 앞선 턴에서 실제로 전달됐고 내용이 그대로인 페이지다. `held: true` 는 이번 메시지와 관련 있다는 뜻이 아니다. 대화 중 판정은 보유 페이지의 관련성을 따로 판정하지 않으므로, 소비자가 선택지로만 다뤄야 한다.
- **순서**: 붙은 행이 먼저(묶음 순서), 보유 행이 뒤.
- **권한**: 호출할 때마다 페이지별로 다시 확인한다. 읽을 수 없게 된 페이지는 빠지고 그 페이지로 가는 링크도 빠진다.
- **턴 한정**: 같은 대화에서 다음 턴이 수락되면 이전 턴의 자료는 빈 배열이 된다. 메모리에만 있고 저장하지 않는다.
- **전송 전 상태**: 턴이 아직 전송되지 않았으면 `pending` 이고, 이때 `held: false` 행은 "마지막 확인을 통과하면 붙을 것" 이다. 전송 뒤에는 `attached` 또는 `not_attached` (이 경우 보유 행만 남음).
- **빈 배열이 되는 경우**: 턴 기억이 `on` 이 아님, 루프가 상한을 넘김, 이 런타임의 턴이 아님, 다음 턴이 수락됨.
- **링크**: 기록된 5종(`same_task`, `follows_from`, `decided_in`, `supersedes`, `refers_to`)에 파생 1종 `superseded_by` 를 더했다. L4 요청으로 추가한 것이고, 대체하는 기록이 확정(과거/현재이면서 done)일 때만 붙는다. 계획이 현재 기록을 대체할 예정인 경우에는 계획 쪽 `supersedes` 만 있다.

L4, L8 에 모양을 보냈다. L4 는 그대로 읽겠다고 답했고, 두 가지를 바로잡았다: 링크 종류에 `revises`, `replaces`, `version_of` 등은 없고, 상태 어휘에 `open`, `todo`, `in_progress` 등은 없다 (미완료는 `plan` 하나). 소비자가 이 행을 Decisions 요청에 넣을 때는 자기 쪽 송신 게이트(`memory_page`)를 거쳐야 한다고 알렸다.

L4 가 이 접근자를 턴의 어느 시점에 부르는지는 확인하지 못했다. run 으로 선택적으로 부른다고만 답했다.

## 2. 한 묶음

플래그 `turnMemory.onePacket` (기본 꺼짐, `createTurnMemoryConfig({ onePacket })`). 사용자 설정이 아니라 배선 값이다.

켜져 있고 맥락 선택과 턴 기억이 둘 다 붙는 턴에서:
- 기억 페이지를 맥락 선택의 키(`egdesk_decision_context`) 아래, 선택 항목 뒤에 붙인다. `egdesk_turn_memory` 키는 없다.
- 선택 항목 부분은 바이트 단위로 그대로다. 마지막 순간(선택이 좁혀진 뒤)에 실제로 보낼 값을 읽어서 합친다.
- 기억 페이지 본문이 선택 쪽에 글자 그대로 이미 있으면 본문을 빼고 머리줄(시제, 출처, 상태 읽기)만 남긴다. id 가 같을 때와, id 가 달라도 24자 이상이 그대로 들어 있을 때 (최근 발언 항목이 JSON 문자열로 인용한 발언 포함) 적용한다.
- id 는 같은데 선택 쪽이 다른 형태(요약 등)로 보여준 경우에는 기억 본문을 한 번 남기고 "위 선택 항목과 같은 기록이니 한 번으로 세라" 는 줄을 붙인다.

두 번째 경우를 "본문 삭제" 가 아니라 "남기고 표시" 로 한 것은 내 판단이다. 삭제하면 중복은 0이 되지만 기억 판정이 필요하다고 고른 전문이 조용히 사라진다. 이 경우 요약 문장이 본문의 일부라면 그 부분은 두 번 보인다. 반대로 정하길 원하면 한 줄 변경이다.

확인한 것 (`egdesk-turn-memory-on.test.mjs`, `egdesk-turn-memory.test.mjs`):

| 경우 | 결과 |
|-|-|
| 플래그 없음, 둘 다 켬 (오늘) | 같은 본문이 두 키에 각각 들어감 (대조군) |
| 플래그 켬, 둘 다 켬 | 키 하나, 모든 페이지 본문이 정확히 1회, 선택 부분 바이트 동일, `turn/start` 의 나머지 동일 |
| 플래그 켬, 턴 기억 off 또는 advisory | `turn/start` 가 기능이 없는 브리지와 바이트 동일 (선택 항목 포함) |
| 플래그 켬, 선택된 것 없음 | 기억 묶음이 자기 키로, 플래그 없을 때와 동일 |
| 플래그 끔, 둘 다 켬 | 두 키, 이전과 동일 |

남는 한계:
- 중복 판정은 "id 가 같음" 또는 "글자 그대로 들어 있음" 뿐이다. 같은 내용을 다르게 적은 두 기록은 잡지 못한다.
- 본문이 빠진 페이지도 전달 영수증에는 전달된 것으로 남긴다 (내용은 모델 맥락에 있으므로).
- 한 묶음이 실제 모델의 답에 어떤 차이를 주는지는 측정하지 않았다.

## 3. 발언 라벨: 매 턴이 아니라 페이지 생성 시 1회

### 오늘의 동작
발화 동의가 켜진 DM 에서는 모든 메시지의 턴 전 맥락 요청에 문장당 3문항(오프셋 축)이 얹힌다. 턴 기억이 켜져 있으면 기록할 가치가 있는 메시지는 답변 뒤 쓰기 판정에서 격리 축으로 한 번 더 라벨링된다. 즉 기록되는 메시지는 두 번 라벨링되고, 저장되는 것은 턴 경로 쪽 결과다 (실호출 두 번 모두 설치 0).

### 바꾼 것
내부 플래그 발화 설계 `at-page` (기본값 불변):
- 턴 경로에는 라벨 문항이 없다. 회상 문항 `rel_recall` 은 그대로다.
- 답변 뒤 쓰기 판정이 문장별 격리 축으로 라벨링하고, 그때 그 발언의 발화 기록을 설치된 라벨과 함께 한 번 쓴다. 저장되는 것은 오프셋과 라벨 단어뿐이고 점수는 없다.
- 판정이 없던 턴(인사, 질문 등)의 발언은 라벨 없이 기록된다.
- 회상 때는 저장된 속성(시제, 출처, 상태)을 그대로 쓰고 다시 묻지 않는다.

기록 시점을 미룬 이유: 발화 기록 저장소는 같은 메시지를 다른 내용으로 다시 쓰는 것을 거부한다 (정확히 같은 재시도만 허용). 턴 경로에서 먼저 쓰면 나중 라벨이 들어갈 수 없다. 그 저장소 규칙은 건드리지 않았다.

`at-page` 는 턴 기억이 `on` 이고 쓰기 경로가 있을 때만 적용된다. 그 밖(off, advisory)에서는 현재 설계로 동작하고, 요청과 `turn/start` 가 플래그 없을 때와 같다는 것을 테스트로 확인했다.

### 같이 고친 것
쓰기 경로가 만든 발언 페이지와 원래의 발언 페이지가 같은 발언에 대해 둘 다 스냅샷에 있었다 (c9 부터). 회상 턴의 판정기가 같은 문장을 두 페이지로 봤다. 이제 쓰인 페이지가 그 발언을 대표하고, 대화 순서 링크도 그 페이지로 옮긴다 (`egdesk-wiki-adapter.mjs`).

### 확인 (`egdesk-utterance-labels.test.mjs`, 실제 동의 저장소·대화 저장소·어댑터 사용)

### 치르는 것
- 답변 모델이 그 턴에 현재 메시지의 라벨을 받지 못한다. 오늘 받는 라벨은 실호출 두 번 모두 비어 있었다.
- 기록되지 않는 발언은 회상 때 시제가 unknown 으로 남는다.
- 발화 기록이 쓰기 판정이 끝난 뒤에 쓰인다. 그 사이에 다음 메시지가 오면 직전 발언이 회상 창에 아직 없고, 그 사이에 프로세스가 죽으면 그 발언은 기록되지 않는다. 오늘은 전송 직후에 쓴다.
- 여러 문장의 라벨이 서로 다르면 페이지 속성은 unknown 이 되어 페이지가 만들어지지 않는다 (기존 동작). 문장별 라벨은 이제 발화 기록에는 남는다.

## 6. 결정이 필요한 것
- `onePacket` 과 `at-page` 를 켤지. 둘 다 기본 꺼짐이다.
- 같은 기록이 다른 형태로 선택된 경우 기억 본문을 남길지 뺄지 (2장).

- 4장 실측 실행 여부.
