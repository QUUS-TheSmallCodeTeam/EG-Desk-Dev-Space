# L1 c32: 열린 항목 해소기 (open-item resolver) — 층 감사 ① 구현

브랜치 `lane/c32-open-items` (base `int/c14` `cbad751`). 기본 꺼짐 (브리지 플래그 `EGDESK_OPEN_ITEMS=on`, 체크의 대화 플래그 같은 이름). 가짜 엔진과 대본 Decision만 사용했다. Codex 바이너리 미실행, 아무것도 보내지 않음. **사용자에게 보이는 새 문구/요소 없음** (아래 "승인 필요"는 비어 있다).

## 1. 무엇이 바뀌나

턴이 오면 **엔진보다 먼저** (`send()` 맨 앞) 코드가 그 대화의 열린 항목 등록부를 만든다. Decision 모델은 항목마다 한 질문(`oi_ref_<n>`, 메시지와 그 항목 하나만 인용, R2/R4)에 답한다. 코드가 결합한다: 하나만 분명히(≥0.85) 가리키면 그 항목이 "정리됨", 아니면 **아무것도 정리하지 않는다**. 그 뒤 **그 항목의 기존 판단만** 돌린다. 엔진은 "무엇이 정리됐는지"를 닫힌 단어 블록(`egdesk_open_items`)으로 받고 말만 한다.

| 항목 종류 | 코드가 만드는 곳 | 정리됐을 때 부르는 **기존** 판단 (새 질문 없음) | 정리 안 됐을 때 |
|---|---|---|---|
| `approval` (대기 승인) | `gate-hook-broker.awaitingAsk` (읽기 전용 접근자 추가) | `readGateHookReply` → `broker.readReply` (`reply_runs/declines_command`, L3의 경로 그대로) | **읽지 않는다. 대기 질문이 소비되지 않고 남는다** |
| `question` (run의 되묻기) | `openEarlyQuestion` | (판단 없음: 답이면 답) 기존 경로 그대로 | 기록만 (아래 갭) |
| `run` (진행 중) | 대화의 비종료 run | 기존 `personPredicates` 경로 그대로 | 기록만 |
| `browser_task` | L8이 `registerOpenItemProvider`로 제공 (계약 합의) | L8의 `read/apply` (`task_resume`) | 호출 안 됨 |
| `memory` (확인 대기 기록) | `turnMemoryNoted.offered` (L7 c38이 병합되면 `openMemoryItems`) | 기억 루프의 `confirmNotedRecords` (`rc_*`) 이 항목에 대해서만 | **확인 판단을 건너뛴다** (`offered` 유지) |

Decision이 실패하거나 못 읽으면 (`timeout`, `unanswered`, 송출 불가 등) **오늘의 경로 그대로**: 대기 명령의 답을 읽는다.

코드 줄 (`codex-chat-runtime.mjs`, 이 브랜치): `send` 맨 앞 `resolveOpenItems`, 그 뒤 `inRun` 줄에서 오늘의 경로 기록 (`record.today`), `startTurn`에서 `applyOpenItems` (원래 `readGateHookReply`가 있던 자리, dfLocal 뒤), `runTurnMemoryOn`의 `confirmNotedRecords` 앞 `openItemRoute(…, 'memory')`. 새 모듈 `helper/egdesk-open-items.mjs` (등록부, 질문, 결합, 엔진 블록, 제공자 등록). 송출 종류: `run_text`, `terminal_command` (`EGRESS_SITES`에 선언; 항목이 없으면 요청 자체가 없다).

## 2. 규칙 (코드가 정한 것)

- 등록부: 최대 5개, id `oi1..`, 종류 닫힘, 요약 ≤300자, 실패한 제공자는 0개.
- 정리됨 = 정확히 한 항목 p ≥ 0.85 **그리고** 다른 항목 모두 p < 0.5. 두 개 이상, 애매(0.5~0.85), 무응답, 메시지가 비었거나 길면 → 정리 없음 + 사유 (`no_item_referred`, `several_items`, `unanswered`, `message_unsuited`).
- 말이 나가도 되는지는 그 대화의 마지막 run의 송출 문(`run_text`, 명령이 있으면 `terminal_command`)이 정한다. 막히면 해소기는 돌지 않고 오늘의 경로.
- 엔진 블록은 항목 id와 종류와 상태 단어만 (항목의 원문을 싣지 않는다). 상태: `approved`, `not_approved`, `unclear`, `confirmation_read`, 제공자가 돌려준 말(`continue` ...).

## 3. 검증 (가짜 엔진, 대본 Decision)

새 테스트 4파일 (모듈 7, 런타임 9, 실엔진 훅/스크립트/비교 5 + 1 e2e):
- 해소기 규칙: 한 항목만 정리 / 애매(0.6, 0.84)·무관 → **정리 없음, 대기 명령 소비되지 않음**, 다음 메시지 "그냥 해"로 승인 가능 / 두 항목 모두 가리킴 → 없음 / 무응답은 "아니오"로 읽지 않음 / Decision 실패 → 오늘의 경로.
- 항목이 없으면 Decision 요청이 **0회**. 플래그 꺼짐이면 오늘과 같다 (기록·블록 없음).
- 등록된 제공자 항목이 정리되면 그 제공자의 `apply`만 불리고 승인 판단은 안 돈다 (L8 계약, 가짜 제공자).
- 메모리 확인 판단이 해당 항목일 때만 돈다 (정리 없음이면 건너뜀, 플래그 꺼짐이면 기존대로).
- 실엔진 체크: `expect.openItems { settled, reason, approvalWaiting, maxResolverMs }`, 훅이 `turn/start` 횟수와 런타임 기록과 브로커의 대기 여부를 읽는다. 스키마 재생성 후 `--check` 통과. 구성 보호(composition guard)에 플래그 등록.
- 변이 16개 (`evidence/l1-c32/mutations.txt`): M2(두 항목 중 첫째 채택)는 다음 줄(다른 항목 ≥0.5)이 같은 역할이라 **동치** (생존, 중복 방어). 나머지 모두 잡힘. (M14, M15는 첫 시도에서 살아남아 테스트를 추가해 잡았다.)

## 4. 실엔진 스크립트 (Main이 돌림)

`real-engine-open-items-v1` (빌더 `helper/egdesk-open-items-real-engine-script.mjs`, 쓰기 `scripts/egdesk-open-items-real-engine-script.mjs`). 대화 5개, 열린 항목은 실제 엔진이 이미 만드는 것 (게이트가 막고 되묻는 `git push --force`):

| 대화 | 플래그 | 보는 것 |
|---|---|---|
| open-off-approve / open-on-approve | 끔 / 켬 | "그냥 해": **같은 명령이 실행되는가**, 초 차이 = 해소기 Decision 1회 (`maxResolverMs 4000`) |
| open-on-unrelated | 켬 | 승인 대기 중 "그건 그렇고, 지금 폴더에 뭐 있어?" → `settled none`, **대기 질문 유지**(`approvalWaiting true`), 명령 실행 안 됨 → 이어서 "그냥 해" → 정리됨, 실행됨 |
| open-on-ambiguous | 켬 | "음… 글쎄" → 정리 없음, 실행 안 됨, 대기 유지 |
| open-off-unrelated | 끔 | 같은 대화, 기록만: 오늘의 경로가 무관한 말을 답으로 읽고 대기 질문을 버리는지 |

## 5. 승인 필요 (사람에게 보이는 새 요소·문구)

없음. 해소기는 내부 상태이고, 엔진 블록은 모델용 닫힌 단어다. (등록부를 사람에게 보여 주는 표시를 두게 되면 그때 새 요소로 별도 승인.)

## 6. 갭과 확인 안 됨 (정직하게)

1. **question / run 항목은 "기록만"**: `send()`의 오늘 경로(`openEarlyQuestion`가 어떤 메시지든 그 run의 답으로 삼음, 진행 중 run이면 `RUN_IN_PROGRESS`)는 바꾸지 않았다. `record.today`에 오늘의 경로(`question_route`/`new_turn`)를 같이 남겨, 해소기가 "무관"이라 본 메시지를 오늘은 답으로 삼켰는지 Main의 실행에서 센다. 이 둘을 실제로 라우팅하려면 사람에게 보이는 동작(거절·큐)이 바뀌므로 별도 결정이 필요하다.
2. **실엔진 확인은 아직 없다.** 승인 대화(`git push --force`가 게이트에 막히고 `awaiting`이 생기는 흐름)는 가짜 앱서버로 재현하지 못했다. 그 경로는 런타임 테스트에서 브로커 스텁으로, 훅은 단위로 검증했다. 가짜 앱서버 e2e는 "항목 없음" 한 경우뿐이다.
3. 대기 승인이 오래 남는다: 무관한 말이 여러 번 오가도 승인 대기는 소비되지 않는다 (의도). 만료 정책은 정하지 않았다 (오늘은 소비되어 사라짐). 오래된 명령에 "응"이 붙는 위험은 매번 해소기가 *그 명령 원문*을 인용해 묻는 것으로 막지만, 만료 시간은 사용자 결정 거리다.
4. 두 질문이 같은 메시지를 서로 다른 항목에 붙이는 경우(예: 승인 대기 + 되묻기 둘 다 "응")는 `several_items`로 정리 없음이 되고, 그 메시지는 일반 턴이다. 실제 모델이 이 경우를 얼마나 자주 내는지는 미측정.
5. L3의 승인 빠른 경로가 `readGateHookReply` 또는 브로커를 바꾸면 이 호출이 그대로 따라간다 (나는 `return` 하나와 `awaitingAsk` 접근자만 추가했다). L7 c38의 `openMemoryItems`는 아직 병합 전이라 지금은 `turnMemoryNoted`를 쓴다 (있으면 쓰도록 분기만 넣었고 가짜로 테스트했다).
6. 결정 우선 명령(`EGDESK_DECISION_FIRST`)과의 순서: 해소기의 승인 읽기는 원래 읽던 자리(dfLocal 뒤)에서 돈다. 엔진 맥락 조립보다 앞으로 옮겼을 뿐 순서는 같다.

## 7. 병합 이후 추가 (d0dbdc4, int/c14 793c14a)

- **접근자 하나**: L3의 `pendingAsk`만 쓴다 (내 `awaitingAsk` 제거). L3의 `decisionFirstReply`(승인 빠른 경로)는 해소기가 "이 말은 다른 것에 속한다/아무것도 아니다"라고 하면 **읽지 않는다**(대기 질문이 소비되지 않는다). 읽었으면 그 결과(`approval_ran`, `approval_declined`, ...)가 승인 항목의 상태가 된다 (답을 두 번 읽지 않는다).
- **제공자 읽기/적용 경로**: 제공자가 `read`를 가지면 정리된 항목에 대해 그 제공자의 `read(answers, key, thresholds, item)`를 부르고 **정리된(settled) 읽기만** 적용한다 (fail closed). 등록 제공자(L8 브라우저)에는 대화 키를 문자열로, 내장 제공자에는 `{ cid, clientThreadId }`를 준다.
- **L3 제안 등록부** (`proposals`, 새 `helper/egdesk-open-proposal-items.mjs`): 항목은 `proposal`(제안, 대기 행동) 또는 `question`(사람에게 기다리는 것). 제안이면 같은 요청에 `open_prop_<i>_accept/_decline/_skip_<n>`을 실어, 메시지를 제안 전체와 **단계 하나씩**(R4) 읽는다. "응 근데 테스트는 빼고" → 수락 + 단계 2 제외 → 항목 닫기(`closeOpenItem`) + 엔진 블록에 `accepted_without_steps; steps left out: 2`. 단계에 대한 답이 애매(0.2~0.85)하면 추측하지 않고 적용 안 함. 엔진이 수락된 단계를 하는 것은 오늘과 같다 (코드가 단계를 실행하지 않는다).
- **L8 브라우저**: `browserOpenItemSource`가 L8의 `createBrowserOpenItems`를 같은 항목 입력기(`createDirectBrowserEntry`)로 만들어 등록부에 넣는다 (플래그 `EGDESK_BROWSER_OPEN_ITEMS`와 `EGDESK_OPEN_ITEMS` 둘 다 켜야 함). 가짜 제공자로 읽기/적용 경로를 검증했고, L8의 실제 provider는 L8의 테스트가 검증한다.
- **L5 `openCommandItems`**: int/c14에 아직 없어 배선하지 않았다 (모양을 모르는 채로 추측하지 않음). 들어오면 같은 방식의 제공자로 꽂는다.
- 스크립트에 대화 2개 추가: `open-off-proposal`, `open-on-proposal` ("실행해도 될까요?" 제안 뒤 "응 근데 테스트는 빼고": 파일 `build.done`, `deploy.done`만 생김, `test.done` 없음; `openItems.settled = proposal`). 실엔진에서는 L3의 등록이 답 뒤 백그라운드(최대 3초)라 둘째 턴이 그 전에 오면 항목이 없을 수 있다 (L3 한계 5절과 같음).
- 변이 10개 더 (P1~P10) 모두 잡힘.
