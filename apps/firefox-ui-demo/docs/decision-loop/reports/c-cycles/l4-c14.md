## 1. Skeleton 흐름을 실제 turn memory에 연결

**자료.** `briefingDeps.materialsFor`가 L7의 `chat.memoryMaterialsFor(run)`을 그대로 부른다. mount 테스트에서 L7의 turn memory를 `on`으로 켜고(공개 합성 위키) "A사 견적 건 정리해줘"를 보내면, 실제 루프가 붙인 6행(A사 5건 + 무관한 B사 1건)이 그대로 자료가 되어 `presented`(step 3, 새 카드 3, fill 1회)로 끝난다. turn memory를 끄면 그때만 `no-materials`다.
- 이 하니스에는 Agent 프로필이 없어 L7의 `eligible` 훅으로 "직접 대화"를 대신했다. 페이지 선택은 L7의 mock judge가 했다.
- **이번 turn에 붙은 행(held:false)만 자료로 쓴다.** 이전 turn부터 들고 있던 행은 이 메시지와의 관련성을 아무도 판단하지 않았으므로, 붙은 행이 하나도 없을 때만 쓴다.

**링크로 묶기.** 자료를 기록된 링크의 연결 요소로 묶고 part를 묶음별로 만든다. 전에는 날짜 있는 자료 전부가 한 "순서" part에 들어갔다. 이제 B사 페이지는 A사 순서에 섞이지 않는다(실제 6행에서 확인: 비교 M2·M4, 순서 M1·M2·M3·M5, 미완료 M4, B사는 단독).

**"이 카드가 이 자료를 보여준다" 판정 순서.**
1. provenance: 이 흐름이 카드를 발행할 때 bridge가 `outputId → {자료 key들, trait, component}`를 기억한다. 자료 key는 L7의 `row.key`(페이지별 불투명 HMAC, non-enumerable이라 요청에 복사되지 않음)이고, 없으면 제목·날짜·종류의 지문이다.
2. 제목이 정확히 같음.
3. 한 제목이 다른 제목 안에 있음: 그렇게 맞는 자료와 카드가 각각 하나뿐일 때만. "A사 견적"처럼 여러 제목에 들어가는 라벨은 아무것도 잡지 않는다.

대체된 카드, 접힌 카드, 묶을 수 없는 카드는 대상이 아니다. 같은 자료 집합과 같은 part 종류로 이미 만든 카드가 있으면 그 part의 옵션에서 "새 카드"가 사라지고 재사용만 남는다.
- mount 테스트: 같은 대화에서 두 번째 답변이 오면 첫 브리핑이 만든 카드 3장이 재사용되고(step 3, 새 카드 0, 발행 0), part 질문 옵션은 `reuse_T#, none_fits, bubble_enough`뿐이다.
- **`row.key`는 L7의 c15(미병합)에 있다.** `int/c13`의 행에는 key가 없어 오늘 실제로 도는 것은 지문 경로다. key 경로는 non-enumerable 속성을 모델링한 테스트로만 확인했다. 기억은 bridge 메모리에만 있고 재시작하면 사라진다.

**advisory 기록을 새 순서로.** bridge의 의존성 factory가 있으면 advisory도 완료된 답변의 run에서 자료를 읽어 place와 parts 두 판단을 묻고 기록만 한다(engine 불필요, 이벤트 0, fork 0). chrome은 두 모드에 같은 사실(run id, 요청문, 보이는 영역)을 보내고 `flow: 'on'`만 다르다.
- **행동 변화 주의:** advisory에서도 이제 사용자 요청문과 자료 제목·발췌가 Decision model로 간다. D2(다른 모델과 같은 공유 권한)와 같은 gate를 통과하지만, 이전 advisory는 개수와 카드 라벨만 보냈다.

## 2. Heartbeat nudge와 포인터 왕복

- 장면을 큐에 넣을 때 `nudge()` → 0.5초 안에 판단. 포인터 사실을 올릴 때 다시 `nudge()`. 두 번째는 같은 beat 간격(5초) 안이라 보통 거절되므로 5초 뒤 한 번 더 시도한다.
- 포인터 사실은 `EGDESK_WORK_PLACEMENT=on`일 때만 올린다. advisory는 "point했을 것"만 기록한다. L3가 이제 포인터 사실을 실제 메시지로 바꾸므로, advisory 플래그가 채팅 메시지를 만들면 안 되기 때문이다.
- 철회는 두 경로 모두 받는다: heartbeat의 `acknowledge('work_placement', 'attention')`와 bridge의 `attentionPosted → acknowledgePointer`.

**왕복 검증** (L3의 실제 세션 heartbeat와 conversation flow, 실제 `CodexChatRuntime`, 가상 시계, 이 lane의 실제 placement 모듈):
run 종료 후(heartbeat `running`/`idle`) 주의 장면 제출 → 0.5초 안에 판단 1회("point") → 포인터 사실 → 약 6초 뒤 **owner 자신의 대화에 완성된 메시지 1건** → acknowledge → 사실 철회. 요청자 대화에는 아무것도 없고, 캔버스 스냅샷은 그대로이며, 이후 60초 동안 추가 판단·메시지 0. 세 모델 입력 어디에도 멤버 id·제목·좌표가 없다.

- 6초는 nudge가 beat 간격당 1회로 제한되어 생긴다. 줄이려면 L3가 attention용 두 번째 nudge를 허용해야 한다.
- **제품에서 주의 장면을 제출하는 트리거는 여전히 없다.** chrome 어디에서도 `attentionRequest`를 부르지 않는다. 즉 왕복은 bridge 수준에서만 성립하고, 실제 앱에서는 포인터가 아직 뜨지 않는다.

1. **입력 형태.** skeleton judge는 `input_json` content part를 쓰고 있었는데, 지금까지 실제로 보내 측정된 요청은 전부 `developer`/`user` 문자열 메시지였다. skeleton 요청을 그 형태로 바꾸고(카탈로그를 앞에 둬 prompt cache 접두가 되게) cache key를 붙였다.
