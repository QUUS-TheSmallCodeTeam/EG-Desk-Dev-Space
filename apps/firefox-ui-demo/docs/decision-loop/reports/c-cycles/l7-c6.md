# L7 / cycle 6 / lane/c6-wiki-reconstruction 보고서

패러다임 정정(사용자, 권위 있음)을 먼저 못 박는다: Decision 모델은 주관 모델(Codex/Claude)을 위해 기억을 재구성하는 **시스템 수준 판정자**이며 사용자용 결정 도우미가 아니다. 발화의 시간·출처 라벨은 대화 흐름 정리(토픽 라우팅, 별도 기능)가 아니라 **온톨로지(시간축 + 근거 출처)**에 속한다. Decision 모델은 제목이 아니라 **자료 본문**을 읽고, 코드는 링크·권한·범위를 맡는다. 전제 조건은 **런타임에 보기가 실제로 존재하는 것**(위키 페이지와 링크, 또는 코드가 정의한 보기 집합)이다. 그래서 이번에는 보기를 만드는 런타임부터 만들었다. 이번에도 실호출 0회(목만 사용).

## 1. 현황 조사: 무엇이 있고, 위키 재구성 루프에 무엇이 없는가

있는 것:
- 턴 시작 컨텍스트 선택(`prepareTurnContext`, egdesk-context-setup.mjs): 한 번의 Decisions 요청. 모델이 보는 것은 `catalogLine` = `kind | time=slice/status | title | summary(≤400자)` 한 줄뿐이다. 본문은 선택된 뒤 `loadText`로 읽는다(후보 정규화 `summary: compactText(…,400)`). 즉 **관련성 판정이 제목·요약으로 이루어진다**.
- 후보 생성(egdesk-decision-candidates.mjs): 선택한 자료·Board·기억 조회의 제목과 짧은 요약, 시간대 태그. 링크 정보 없음.
- 온톨로지 저장소(egdesk-ontology-store.mjs): nodes, **edges**(source/target/relation/declaredBy), snapshots(timeSlice/status/continuesFrom), occurrences. 하지만 `candidatesFromOntologyGraph`는 노드·스냅샷만 후보로 만들고 **edges는 버린다**. 판정 루프가 링크를 따라가는 경로가 없다.
- MemBrain 규약(DECISION_MODEL_CONTEXT_SETUP.md "MemBrain에 파일과 기억 조각을 넣는 규약"): 원본 고정(sourceId+revision+범위), 조각은 주장 하나, 발언자와 인용자 분리, 예정과 완료 구분, 시점·권한 검사, `supports/contradicts/supersedes` 관계. 문서가 명시하듯 **범용 등록 API·정정 관계 그래프는 설계일 뿐 미구현**.
- 기억 근거(egdesk-memory-evidence.mjs): 장부 행+원본 줄 바인딩과 관계(counted/posted/scheduled…)가 있는 좁은 도메인. 범용 페이지 모델이 아니다.
- 세션 토픽 트리(egdesk-session-topic.mjs): 대화 쌍의 topic/parent/needs 그래프와 `topic_route` 판정. **대화 흐름 정리**이지 자료 재구성이 아니다. 문서는 "토픽별 문서 재검색, 전송 영수증 기반 중복 조각 제거, 자동 후속 판정은 범용 기능으로 구현되지 않았다"고 직접 적는다(DECISION_MODEL_CONTEXT_SETUP.md 59–100행 구간).
- 발화 grounding(egdesk-speech-grounding.mjs): 현재 메시지의 문장별 source/form/time 라벨을 **턴 시점에** 판정해 같은 요청의 packet에 싣고 발언 저장소에 기록. 온톨로지 관점의 "근거 출처·시간축"을 턴 경로에서 매번 새로 읽는 구조다.
- JEV 문서(§5 해마, §6 시간축 온톨로지 챗 파이프라인, §9.4 JEV-CTX-01/02, JEV-READ-01): 목표 구조는 시제 슬라이싱, 시제 머리말 부착, 답 초안 검증, 완료 보고의 전이 제안. 코드는 이 중 일부 분류 도우미만 있다.

없는 것(재구성 루프에 필요한데 부재):
1. 페이지 모델: 본문 + 메타(시간대, 근거 출처, 상태, 원본 리비전)를 한 레코드로 가진 읽기 단위. 지금은 후보마다 제각각.
2. 코드가 유지하는 **유형 있는 링크**(같은 작업/이어짐/결정됨/대체/참조)와 그것을 판정의 보기로 내보내는 경로.
3. **본문을 읽고** 고르는 판정(현재는 제목·요약), 그리고 한 요청 안에서 끝나는 구조(현재 최대 1회) 대신 링크를 따라 여는 **다단계 무상태 루프**.
4. 기록 자체의 상태 판독(계획/완료/대체됨/전언)과 메타데이터 상태의 나란히 표시, 쓰기 없이.
5. 이미 전달한 조각의 **영수증**(리비전+해시)과 판정 전 중복 제거, 압축 후 재전달.
6. 예산 인식(호출 수, 카탈로그 문자 수, 추림 한도)과 부분 결과 반환, 자르면 흔적을 남기는 것.
7. 발화 라벨을 턴 경로가 아니라 **수집 시점(발언 페이지 생성 시)**에 한 문장씩 붙이는 경로(아래 3·4장).

## 2. 설계와 프로토타입 (`helper/egdesk-wiki-reconstruction.mjs`, 턴 경로에는 연결하지 않음)

역할 분담
| 코드 | 판정자(Decision) |
|---|---|
| 페이지·메타·링크 유지, 권한/범위, 예산, 영수증, packet 배치, 시계 표기 | 이 메시지에 이 페이지 본문이 필요한가, 링크로 이어진 페이지를 열 가치가 있는가, 기록 본문이 보여주는 상태가 무엇인가 |

- 페이지: `{id, title, body, revision, time:{slice, at?}, provenance:{kind: own_record|document|agent_note|utterance|reported_by_other, by?}, status, scope?, links:[{type,to}], mayRead?}`.
- 링크(코드 유지, `buildWiki`가 검증): `same_task / follows_from / decided_in / supersedes / refers_to`. 잘못된 유형·없는 대상·자기 링크·중복은 버리고 개수를 센다(추측 수선 없음). `supersedes`는 **대체한 쪽이 완료·과거/현재일 때만** "superseded-by"로 취급한다(계획인 v2가 v1을 대체한다고 해서 v1이 이미 대체된 것은 아님).
- 루프(모든 호출 무상태, 요청마다 메시지 + 질문 시계 + 명시 상태 블록 `State: round=… picked=[…]`, 별칭 P1.. 은 호출마다 새로):
  1. **스캔**: 읽을 수 있는 모든 페이지의 본문 발췌를 예산 안에서 나눠 병렬 배치로 판정(`pg_i` 술어). yes ≥ 0.8이면 선택, 0.2 이하 제외, 중간은 "두 번째 보기" 후보.
  2. **확장**: 선택된 페이지의 링크 이웃(+두 번째 보기)이 **보기**. 같은 호출에서 선택된 기록의 상태를 닫힌 선택(plan / done / superseded / reported_by_other / unknown)으로 판독(`st_*`, 신뢰 0.75·마진 0.2 미달이면 판독 없음 = 억지로 분류하지 않음)하고 링크 페이지를 열지 `op_*` 술어로 묻는다. 깊이·호출 수 한도까지 반복.
  3. 판정자는 코드가 내놓지 않은 페이지를 지명할 수 없다(시험: 모르는 이름의 답은 무시).
- 호스트 조립 packet(주관 모델용): 머리말 규칙(계획·가정은 현재 사실 아님, 전언은 귀속이며 독립 근거 아님, 판독·점수는 증명도 쓰기 권한도 아님, 질문 시계; 날짜는 계산하지 않음), 페이지별 `[page id time provenance status-recorded status-read superseded-by rev via]` + 본문, 보유 페이지 사이 링크 목록.
- **영수증**: `delivered = {usable, pages:{id:{revision, hash}}}`. 같은 스레드에서 같은 리비전·해시가 이미 전달되었고 압축되지 않았으면(`usable`) **판정 전에** 제외하고 내용은 다시 보내지 않는다. 본문이 바뀌면 새 조각, 압축 뒤(`usable:false`)에는 전부 다시 대상. `nextDelivered()`는 순수 값이며 호스트가 턴이 실제 시작된 뒤에만 커밋한다. 영수증에는 텍스트가 없다.
- 예산: `maxCalls 4, maxScanCalls 2, maxCatalogChars 9000, excerptChars 600, maxPicks 6, maxDepth 1, maxOpenOptions 12, maxPacketChars 8000, deadlineMs 선택`. 넘치면 `unscanned / truncated(pick_limit·option_limit·page_chars·packet_chars) / withheld` 영수증에 이유가 남고 조용히 사라지지 않는다. 첫 라운드가 실패하면 fallback, 이후 라운드 실패는 **partial**(그때까지의 선택 유지).
- 권한: 페이지 `scope`와 `mayRead`를 요청 구성 전에, 그리고 packet 조립 때 다시 검사. 허용 밖 페이지의 제목·본문은 어떤 요청에도 실리지 않는다(시험).
- 쓰기 없음: 판독한 상태는 메타데이터 옆에 나란히 표시될 뿐 위키를 바꾸지 않는다(시험: 전후 동일). 상태 전이는 별도 제안·확인 경로(planTimelineTransition 등) 몫.

기존 코드와의 접점(연결은 다음 사이클): 어댑터가 위키 페이지를 현재 `candidates`(`kind:'document'`, `loadText`)와 온톨로지 edges로부터 만들고, 호출은 `prepareTurnContext`의 단일 요청 한도(최대 1회, 800 ms 예산)와 충돌하므로 별도 비동기 경로(재구성은 응답 지연 예산 밖, 이전 턴 사이 또는 다음 턴 준비)를 소유자가 정해야 한다.

## 3. 발화 라벨의 스팬 대상 문제와 격리 설계 (플래그 뒤, 기본값 불변)

실호출 결과(`evidence/main-real/speech-results.json`): 현행 축 질문은 이번에도 평평했고(설치 라벨 0), 예/아니오 설계는 결정적이었지만 두 스팬 모두에 relay .99/.97, plan .93/.98, before .95/.78, after .98/.95로 **메시지 전체**에 대해 답했고 입력 토큰은 6,017(내 추정 3,350)이었다. 추정이 틀린 원인은 바이트 비례 모델 오류다. 두 실요청으로 적합한 모형은 토큰 ≈ 180×문항 수 + 0.081×바이트이며 문항 수가 지배한다(예: 28문항 6,017).

원인 판단: 모델은 UTF-16 오프셋 구간을 신뢰성 있게 해석하지 못하므로 `[0,39)` 표기는 격리가 아니었다. 수정: 모든 문항에 해당 **문장 원문을 JSON 문자열로 인용**하고 "이 한 문장만 판정, 다른 문장은 무시, 나머지 메시지는 이 문장의 지시어 해석용 맥락일 뿐"이라고 쓴다(`axes-isolated`, `predicates-isolated`, 측정 전용 `compare-isolated`). 문자열 인용이라 따옴표 탈출이 안 되고(시험) 추가 공개도 없다(같은 요청에 이미 있는 텍스트의 반복). 300자를 넘는 스팬은 질문을 만들지 않는다(앞부분만 잘라 추측하지 않음). 질문 이름·선택지·매핑·임계값(yes ≥ 0.8, no ≤ 0.2)은 기존 그대로. 기본값은 `axes` 그대로이며 요청이 바이트 단위로 같다(재현 해시 `dd4e8434…`, `measure-request.json`).
