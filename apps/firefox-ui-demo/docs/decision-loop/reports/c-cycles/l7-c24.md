## 2. previous_reply와 PRUNE_HELD를 실제 신호로 닫는지 확인

Codex 0.171 스키마(`evidence/codex-0171-schema/`)에서 확인한 신호입니다.

| 스키마 이름 | 종류 | 확인 전 런타임 |
|---|---|---|
| `thread/compacted` | ServerNotification, deprecated | 처리함 |
| `contextCompaction` item (`item/started`, `item/completed`) | ServerNotification | 처리함 |
| `thread/reverted` (ThreadRevertedNotification) | ServerNotification | **처리 안 함** |
| `thread/compact/start`, `thread/revert`, `thread/fork`, `thread/resume` | 클라이언트 요청 | 런타임은 `thread/compact/start`와 `thread/revert`를 보내지 않음. 보내더라도 결과는 위 알림으로 옴 |

### 찾은 문제 두 가지

1. **`thread/reverted`를 처리하지 않았습니다.** revert는 그 턴 이후의 기록을 지웁니다. 그런데 기존 영수증과 previous_reply가 계속 열려 있었습니다.
   - 수정: `compactionSignal`에서 이 알림도 compaction과 같은 신호로 받습니다. 그러면 `markContextCompacted`가 영수증 세 종류를 지우고, 다음 턴을 first로 판정합니다.
2. **previous_reply가 resume된 thread에서 열렸습니다.** `turnPosition`은 bridge 재시작 뒤 resume된 thread를 mid(`resumed_thread_with_history`)로 봅니다. 재시작 전에 compaction이 있었다면 그 신호는 이미 사라졌을 수 있습니다.
   - 수정: previous_reply(class `thread`)와 held 가지치기는 모두 **live thread**(`reason === 'live_thread'`)일 때만 열립니다. live thread는 이 프로세스가 직접 불러와서 그 뒤로 계속 따라간 thread입니다.
   - 그래서 재시작 + resume 직후의 턴, fork의 첫 턴은 닫힌 채로 갑니다.
   - 영수증 자체는 원래 프로세스 메모리에만 있어서, 재시작하면 비어 있습니다.

### 가짜 app-server 테스트 (`scripts/egdesk-held-lifecycle.test.mjs`, L2의 all-on world)

플래그는 PREVIOUS_REPLY와 PRUNE_HELD를 켜고 draft check는 껐습니다.

| 상황 | 결과 |
|---|---|
| live 상태 | 직전 메시지가 들어가고(턴 컨텍스트, triage 둘 다), 이미 보낸 기록은 다시 묻지 않음 (12개 미만만 질문) |
| `thread/compacted` | 다음 턴은 직전 메시지 없음, 12개 모두 다시 질문 |
| `item/completed` contextCompaction | 위와 같음 |
| `item/started` contextCompaction | 위와 같음 |
| `thread/reverted` | 위와 같음 |
| 위 네 신호 각각의 그다음 턴 | 다시 열림. 새 답은 live thread에 있음 |
| 재시작 (프로세스 메모리 비움, store는 유지) | `thread/resume`이 일어나고, 그 턴은 닫힘. 다음 live 턴에서 다시 열림 |
| fork (`chat.fork`) | 새 대화는 live가 아님. `previousReplyFor`는 null, 영수증 없음 |

- 이 변경을 빼고 같은 테스트를 돌리면 revert와 재시작 두 케이스가 실패합니다 (`mutation-check.txt`). 두 문제가 실제로 있었다는 확인입니다.
- 테스트 자체에서 하나 손봤습니다. 재시작 케이스는 처음에 `thread/resume`이 정확히 한 번 일어난다고 가정했는데, 실제로는 그 턴에 두 번 일어났습니다. 그래서 "한 번 이상"으로 고쳤습니다. 이 테스트 자체의 전제 조건이고, 제품 쪽 assertion은 그대로입니다.

### 남은 점

turn memory의 영수증(`usableReceipts`)은 아직 resume도 mid로 봅니다. 같은 프로세스 안에서 thread를 내렸다가 다시 불러오는 경우(`mustReload`)에는 영수증이 남습니다. 재시작하면 비므로 위험은 같은 프로세스 안에서 다시 불러오는 경우에만 있습니다. 여기도 live thread로 좁힐지는 결정 2에 적었습니다.
