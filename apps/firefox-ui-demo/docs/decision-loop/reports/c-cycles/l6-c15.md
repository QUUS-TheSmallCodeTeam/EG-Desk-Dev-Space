## 1. 첫 턴 지연: 946 / 1,098 ms 는 무엇이었나

[측정] 실제 파일 전부에서 지연이 기록된 요청 498개를 모았다 (러너 351, 여정·multiuser 147).

**같은 본문, 다른 결과.** multiuser 의 첫 turn_context 는 네 번 모두 같은 3,935 바이트, 2,583 토큰 본문이었다.

| 실행 (KST) | 직전 실측 이후 유휴 | 첫 turn_context | 같은 크기의 후속 turn_context |

같은 크기의 본문이 317 ms 에도, 1,797 ms 에도 왔다. 그래서 **본문 크기로는 설명되지 않는다.**

**첫 요청과 유휴 시간 (러너 49 + 여정 7):** "유휴" 는 이 기계의 직전 실측 파일 기록 시각으로부터 잰 시간이다 (근사).

| 직전 실측 이후 | 첫 요청 | 800 ms 초과 | 1,500 ms 초과 |
|-|-|-|-|
| 2 분 미만 | 31 | **0** | 0 |
| 2~5 분 | 6 | 1 (3,617 ms) | 1 |
| 5~10 분 | 8 | **5** | 0 |
| 10 분 이상 | 6 | **4** | 4 |
| 그날 첫 요청 | 1 | 1 (1,668 ms) | 1 |

- **새 프로세스라는 것만으로는 느려지지 않는다.** 다른 실측 직후에 시작한 새 프로세스의 첫 요청 31개는 모두 255~475 ms 였다.
- 첫 요청이 아닌 요청 302개는 최대 722 ms, p90 352 ms 다.

**느린 첫 요청은 두 부분이 같이 커진다** (서버 처리 ms 가 기록된 러너 첫 요청 49개):

| | 서버 처리 (중앙값) | 경과 − 서버 (중앙값) |
|-|-|-|
| 느린 첫 요청 12개 | 578 ms | 1,028 ms |
| 빠른 첫 요청 37개 | 195 ms | 107 ms |

서버 쪽(+약 400 ms) 과 이쪽 연결 쪽(+약 0.9 s) 이 함께 늘고, 둘 중 하나만 큰 경우도 있다 (서버만 785·845 ms, 연결만 3,382 ms).

**오늘 probe:** 1.5·4.2 분 유휴 뒤에 제품 transport 로 보냈다. 첫 요청 306·312 ms (connect 8~12, TLS 18~22, 서버 206~216) 였다. 연결 설정 자체는 30 ms 정도다. 오늘 probe 는 "느린 꼬리"가 생기는 유휴 구간에 들지 않았다.

**크기 효과 (따뜻한 요청):** 0~600 토큰 243 ms, 600~2,000 토큰 266~268 ms, 2~3k 토큰 291 ms, 3k 이상 354 ms. 2.5k 토큰 본문은 작은 본문보다 약 50 ms 느리다.

**캐시 토큰:** 기록된 317개 중 0 이 아닌 것은 2개(60, 65 토큰) 뿐이다. 프롬프트 캐시는 이 데이터에서 요인이 아니다.

**[해석] 데이터가 뒷받침하는 것:**
- 첫 턴 지연의 큰 값은 **직전 Decisions 요청 이후 몇 분(5 분 이상) 쉰 뒤의 첫 요청**에서 생긴다. 서버 처리와 이쪽 연결이 모두 늘어난다.
- 본문 크기는 약 50 ms 수준이고 원인이 아니다.
- 이 실측 구간에서 5 분 이상 쉰 뒤의 첫 요청은 14개 중 9개가 800 ms, 4개가 1,500 ms 를 넘었다. 제품의 cold 예산 1,500 ms (L7 c19, 55 s idle 이후 적용) 로도 그런 첫 턴의 약 3분의 1 은 놓친다.

**뒷받침하지 못하는 것:**
- 연결 쪽 +1 s 의 원인 (DNS, 네트워크 깨어남, IPv6 fallback, TLS 재개 실패 등). 그 요청들에는 단계 trace 가 없다. 러너의 기본 fetch 와 여정 하네스는 trace 를 남기지 않았다.
- 기계 단위인지 계정 단위인지.
- 시간대 효과. 전부 같은 저녁(20:20~23:35 KST) 이라 분리할 수 없다.
- 2~5 분 사이 어디가 경계인지.
- 다른 날의 분포.

**제안 probe (보내지 않음):** `proofs/decision-real-measure/turn-context-idle/`, `node scripts/egdesk-turn-context-latency-plan.mjs --idle [--write]` / `analyze-idle`, 테스트 1개 추가.
- 열린 질문은 본문 크기가 아니라 유휴이므로, 실제 크기 본문과 가장 작은 본문을 둘 다 "유휴 뒤 첫 요청"으로 보낸다.
- **run-A**: A1 실제 크기 본문 (카탈로그 12개, 질문 14개, 추정 2,651 토큰) 첫 요청 → A2 같은 크기 바로 다음 → A3 가장 작은 본문 바로 다음.
- **run-B**: B1 가장 작은 본문 첫 요청 → B2 바로 다음.
- 추정 7,266 토큰, 상한 6,300 + 1,400 = **7,700 (≤ 8k)**. 제품 transport 로 보내고 단계 trace 를 남기며, 기록만 한다.
- **전제조건 (러너가 강제할 수 없음):** 각 run 은 이 기계에서 Decisions 요청이 **10 분 이상 없었던 뒤**에 Main 이 시작한다. passRule 에 적었다.
- 등록한 읽기:
  - A1·B1 이 느리고 A2·A3·B2 가 빠르면 → 유휴가 원인, 크기와 무관.
  - A1 만 느리면 → cold 경로에서 크기가 중요.
  - 모두 빠르면 → 꼬리가 간헐적이라 두 표본으로는 보이지 않음.
- 이번에는 단계 trace 가 있으므로, 느리면 연결 쪽 원인(dns / connect / tls / 응답) 도 갈라 볼 수 있다.
