## 1. flaky 테스트
- 재현: 단독 30회(6 병렬)는 0/30 실패. **CPU 부하(바쁜 루프 8개) 아래서 파일 전체 30회: 3/30 실패**(`flaky-b2-*.log`). 실패한 테스트는 "timeout reason ..." 한 개가 아니라 같은 경로를 쓰는 3개: 키 조회 정지 테스트 1회, "provider timeout ... never produce a retry" 2회. 모두 기대 `reason: 'timeout'|'timeout_unsent'`, 실제 `{ status: 'manual' }`(이유 없음).
- 시간 가정: `runChatChoice`가 데드라인 경과를 `performance.now() >= deadline`으로만 판정했다. Node 타이머는 `performance.now()`가 데드라인에 닿기 **약 1 ms 전**에 발화할 수 있어(타이머 발화 → 즉시 `abort`, 시계는 아직 미달) 그때 이유가 사라졌다. 즉 테스트 문제가 아니라 제품 코드의 실제 경합 버그(타임아웃 이유가 가끔 누락)였다.
- 수정(`egdesk-chat-choice.mjs`, +8/−2): 자체 데드라인 타이머가 발화하면 `expired` 플래그를 세우고, 이유 판정은 `expired || 시계` 및 `expired`일 때의 `aborted`/`timeout`/비 DecisionError 오류를 timeout 계열로 매핑. 시계를 믿지 않는다.
- 결정적 회귀 테스트(sleep 없음, `node:test` mock timers로 "타이머는 발화했지만 시계는 미달"을 극단적으로 재현): 수정 전 코드에서는 실패, 수정 후 통과 확인. 기존 두 테스트는 그대로(무엇을 증명하는지 약화 없음).
- 확인: 같은 부하 조건에서 **수정 후 0/50 실패**(`flaky-after-*.log`), 수정 전 3/30.

## 7. 실측 결과로 typing pre-connect 훅 재평가 (Main이 승인받아 측정한 값, `evidence/main-real/latency-results.json`)
실측: 새 연결 TCP 7 ms + TLS 18 ms(DNS 1 ms), R3 총 239 ms(openai-processing-ms 153); 연결이 끊긴 뒤 10 s idle 481 ms(처리 369); 60 s idle 재사용 소켓 471 ms(처리 402); 서버 Keep-Alive hint 없음(`connection: keep-alive`, alt-svc h3). Main 메시지의 프로세스 시작 후 첫 요청 2,484 ms(처리 773, OpenAI 처리 밖 약 1.7 s)는 이 JSON의 R1(518 ms)과 다른 측정이라 **출처를 직접 확인하지 못했다**; 아래는 두 값을 모두 전제로 한 판단이다. 장기 idle(3/10/20분) 결과는 아직 없음.

내 c3 판정 규칙에 대입:

- 규칙 2/3: 끊긴 연결 재접속 후 481 ms vs 재사용 471 ms → keep-alive 이득은 사실상 10 ms 내외(상한 55 s는 문제 없이 동작, 소켓 재사용 확인, 오류 0).
- 모의 하네스의 "연결 지배" 프로파일(P1)은 실제와 맞지 않는다. 실제는 P2에 가깝고(첫 요청/서버 쪽 비용), 거기서 pre-connect 이득은 0이었다.

### 추천
1. **타이핑 pre-connect 훅과 `[보기 추천]` 열기 훅은 제거를 추천.** 이득은 많아야 약 25~100 ms인 반면 사용자가 아직 아무 결정도 하지 않은 상태에서 매 타이핑 구간마다 바깥 연결이 열린다(내용 없음이지만 접촉은 접촉). 이번 사이클에서는 지시대로 확장하지도 제거하지도 않았다(제거는 훅 2곳과 라우트/함수, 테스트 정리로 작은 변경).
2. **"프로세스 시작 후 첫 요청만" 으로 좁히는 안은 근거가 없다**: 그 1.7 s의 원인이 DNS/첫 경로/서버 중 무엇인지 미규명이고, TCP/TLS는 25 ms뿐이라 pre-connect(TCP+TLS만 수행)가 그 비용을 숨긴다는 증거가 없다. 판별 실험 한 번이면 된다: 새 프로세스에서 pre-connect만 하고 약 1 s 뒤 첫 요청을 보내 첫 요청 시간이 2.4 s → 약 0.5 s로 줄면 "시작 시 1회 warm-up"(사용자 동의 범위인 mode 사용/기록만+키 저장 때만)으로 좁혀 유지, 줄지 않으면 전부 제거. 이 실험은 키 확인 수준의 요청 1~2건이면 된다(미실행, 승인 필요).
3. **keep-alive transport는 유지**: 재사용이 실제로 동작하고(R4) 하드닝(재시도 없음, 상한, close, hint 존중)이 끝났으며 이득은 작지만 비용·위험이 없다. 실사용 결정 지연은 대부분 OpenAI 처리 시간(150~400 ms 이상)이라, 턴 시작 800 ms 예산은 warm 호출(약 240~480 ms)에 맞다. 시작 직후 첫 요청이 예산을 넘는 문제는 위 실험 결과와 별개로 (c) 폴백 수용 또는 시작 시 1회 warm-up 중 하나로 결정.
