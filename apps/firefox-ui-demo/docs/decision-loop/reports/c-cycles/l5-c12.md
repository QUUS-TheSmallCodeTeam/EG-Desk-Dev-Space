## 1. 오늘의 경로 (코드 근거)
**Codex.** 일반 턴은 `approvalPolicy`나 `sandbox`를 지정하지 않음(`codex-chat-runtime.mjs:2687` `engine.startTurn({...})`. `approvalPolicy:'never'`는 QA, bounded 턴에서만 씀: `codex-chat-execution-policy.mjs:121,179`). 따라서 사람의 Codex 설정이 결정하고, 기본값은 `workspace-write` + `on-request`임. 문서: "With on-request, commands allowed by the sandbox can run without approval" (https://developers.openai.com/codex/agent-approvals-security). 이 기본값에서는 `.git`이 읽기 전용 보호 경로이고 네트워크가 꺼져 있음(같은 문서의 "Protected paths in writable roots").
- **묻지 않고 실행됨(브리지가 실행 전에 볼 수 없음)**: 작업 트리 안에서만 쓰는 명령. 예: `git clean -fdx`, `rm -rf build/`, `rm -rf node_modules`, `rm -f .env.local`. 브리지가 처음 보는 것은 `item/started`인데, 이 시점에 명령은 이미 실행 중임(`egdesk-engine-command-watch.mjs:17` "Nothing is typed, interrupted…").
- **엔진이 물음**: 샌드박스를 넘는 명령. `.git` 쓰기(`reset --hard`, `branch -D`), 네트워크(`push`, `publish`, `scp`, `curl|sh`), 작업 공간 밖(`rm -rf ../x`), docker나 DB 소켓 등. 흐름은 다음과 같음. `item/commandExecution/requestApproval`이 정규화되고(`:3842-3856`. Codex에는 `acceptForSession`이 제공되지 않음, `:3856`), `receiveApproval`(`:4049`)에서 Agent 상한 검사 → 게이트 시작(`:4097`) → 카드 `approval.required`(`:4123`)로 이어짐. 사람은 대화 안의 승인 카드에서 [이번만 허락]/[거절]/(취소)를 고름. `replyApproval`(`:3651`)이 사람의 선택만 엔진에 보냄. 그 사이 엔진은 JSON-RPC 응답을 기다리며 멈춰 있으므로 **물어보는 동안 아무것도 실행되지 않음**.

**Claude.** `--permission-mode manual`과 `--permission-prompt-tool stdio`로 실행됨(`claude-engine-adapter.mjs:526`). 허용 규칙이 없는 Bash는 모두 `can_use_tool`로 옴. `routePermissionRequest`(`claude-engine-permissions.mjs:229`)가 이를 같은 Codex 형태의 요청으로 바꾸고, 같은 카드로 감. 여기에는 [세션 동안 허락]이 추가됨. 사람이 세션 허락을 고르면 CLI의 제안 규칙이 `destination:'session'` 규칙이 되고(`:293`), **이후 그 규칙에 맞는 명령은 CLI가 묻지 않고 실행함**. EG-Desk는 그 명령을 실행 전에 보지 못함.

**터미널 카드**(사람 본인의 셸)는 엔진이 명령을 넣는 경로가 아님(엔진이 터미널 카드에 입력하는 도구는 없음). 따라서 여기서는 대상이 아님.

**결론.** EG-Desk가 명령을 실행 전에 붙잡을 수 있는 곳은 엔진의 승인 요청뿐임. "엔진이 묻지 않고 실행할 명령"은 두 종류임. (a) Claude 세션 규칙에 맞는 이후 명령: 규칙을 **주기 전에** 막을 수 있음. (b) Codex 샌드박스 안의 명령: 지금 붙잡을 지점이 없음.

## 2. `on` 설계와 구현 (R5: 추가만 함)
플래그는 기존 `decisionContext.terminalGate.mode`(`EGDESK_TERMINAL_GATE`)임. 기본값은 off이고, 사람의 Decision 모드가 상한임(기존과 같음).
- **불변식**: 게이트는 엔진 요청에 절대 답하지 않음(자동 허락 없음, 자동 거절 없음). 한 번만 허락과 거절은 항상 사람의 몫임. 카드는 기다리지 않음.
- **(a) 세션 허락 보류 (기존 + c12 확장)**: 다음 경우 Claude 카드에서 [세션 동안 허락]을 뺌.
  - 명령이 바닥에 해당하면 즉시 뺌(기존).
  - 술어가 승인을 요구하면, 사람이 세션 허락을 고르는 시점에 거절함(`COMMAND_RISK_SESSION_FORBIDDEN`, 기존).
  - **신규**: 명령 자체는 무해해도, 그 세션 규칙이 바닥 명령까지 맞으면 뺌. 예: `git status`에서 `git:*`, `docker ps`에서 `docker:*`, 규칙 내용 없음(도구 전체), 읽을 수 없는 규칙.
  - 판정은 `sessionRuleCoversFloor`(`egdesk-terminal-command-gate.mjs:510`)이 코드로 함(R3). CLI 규칙 문법(`prefix:*`, `*` glob, 정확한 명령)으로 바닥 탐침 33개(`FLOOR_PROBES`, `:490`. 모두 바닥에 해당함을 테스트로 확인)와 대조함.
  - 규칙 내용은 메모리에서 게이트로만 전달되고 이벤트, 스냅샷, 기록에는 남지 않음(테스트로 확인). 기록에는 `sessionRuleBroad` 불리언만 남김.
- **(b) 묻지 않고 실행된 명령: 기록만 함 (신규)**: `observeUnaskedCommand`(`codex-chat-runtime.mjs:5823`). 요청 없이 `item/completed`에 도달한 명령에 대해 바닥 판정만 기록함(`unasked`, `rule`, `reasons`). 모델 요청과 egress는 0이고 내용은 기록하지 않음. advisory와 on 둘 다 같음. 목적은 이 틈이 얼마나 자주 생기는지 재는 것임.
- **U4 대화 질문**: 엔진이 묻는 경로에는 이미 이 경로용 버튼(대화 안의 승인 카드 [이번만 허락]/[거절]/취소)이 있음. 그래서 과제 조건("이미 버튼이 있으면 버튼")에 따라 새 대화 질문은 만들지 않음. 새 고정 문구도 없음. 묻지 않는 경로(b)에는 질문을 걸 지점 자체가 없음. 대화 질문(run/cancel/give context, 답은 yes/no 술어로 읽음)은 아래 결정 1의 네이티브 지점을 고른 뒤에야 의미가 생김.

**증명 (`helper/egdesk-terminal-gate-on.test.mjs`, 6개 테스트, 실제 런타임과 Claude 어댑터 경로, 모의 모델은 2026-11-25 실측 술어값)**
- 표 20개 명령: 바닥 10, 술어 위험 4(push, .env.local, scp, `docker rm -f web`=미측정 .5), 무해 2, 유사 명령 4.
  - on(Claude): 바닥 10개는 세션 허락이 처음부터 없음. 술어 4개는 세션 허락을 고르면 거절됨. 나머지 6개는 사람이 세션 허락을 줄 수 있음. 모델 요청은 6회(술어 4 + 무해 2)뿐이고 바닥과 유사 명령은 0회.
  - 기록: 표와 정확히 일치함(rule = 바닥, withheld와 attached = 바닥 또는 술어).
- advisory = off: 카드 선택지와 엔진에 보낸 답이 완전히 같음. advisory는 기록만 하고(`attached=false`) 넓은 `git:*` 규칙을 알아챔.
- 거절하거나 답하지 않은 경우: 카드 3개가 대기하는 동안 CLI에 보낸 답은 0개임. 거절하면 deny, 취소하면 deny + interrupt, 답하지 않은 카드는 계속 pending이고 allow는 한 번도 없음. Codex: 요청 20개를 받는 동안 게이트가 보낸 답은 0개이고, 카드 선택지는 전부 accept/decline/cancel로 on이 Codex 카드를 바꾸지 않음.
- 묻지 않고 실행된 명령: `git clean -fdx`(deletes_untracked), `rm -rf build/`, `npm test`는 각각 1건씩 기록됨. 물어본 `git push`는 기록되지 않음. off는 기록 0건.
- 변이 검사: 넓은 규칙 보류나 asked 집합을 끄면 해당 테스트 2개가 실패함(테스트가 비어 있지 않음).
- 수정한 버그: 빈 규칙 내용이 '정확한 명령' 분기로 빠져 "안 맞음"으로 나오던 것을 "가장 넓음"으로 고침.

## 3. git clean 문구 대조군 (.06)
실측 본문은 `{command:"git clean -fdx", git_working_tree:"clean", targets:[], stated_intent:"Remove every untracked and ignored file…"}`. 답은 unrestorable .06, outside 0, personal .46. git에서 "clean"은 추적하지 않는 일반 파일도 없다는 뜻이므로, 남는 것은 무시된(ignored) 파일뿐임. 문구의 예외("build output, caches, installed dependencies do not count")를 따르면 .06은 **사실에 맞는 읽기**임. 문제는 문구가 아니라 **사실이 부족한 것**임(무시된 파일 중 손으로 관리하는 `.env*` 같은 것이 있는지를 런타임이 주지 않았음). **결정: 문구는 고치지 않음.** 바닥이 요청 0회로 막고 있고, personal .46(unsure)만으로도 승인이 걸림. 개선 후보(미구현): `clean -x` 계열에 "무시된 파일 중 생성물이 아닌 것의 개수"를 코드 사실로 넣는 것. 숫자는 쫓지 않음.

## 6. 결정 필요
1. **Codex 샌드박스 안 명령의 틈(가장 큼)**: 이 틈을 막을 네이티브 수단과 각각의 대가.
   - (i) Codex 실행 정책 규칙 `decision="prompt"`: 엔진이 직접 묻게 함. "A command rule can also require review inside the sandbox"(위 문서). 접두사 규칙이라 "다른 커밋으로 reset" 같은 조건은 표현할 수 없음.
   - (ii) Codex `PreToolUse` hook: deny만 확실함. 정리 글 https://agenticcontrolplane.com/blog/codex-cli-hooks-reference 기준이고 1차 문서는 아님.
   - (iii) EG-Desk가 턴마다 `sandboxPolicy`나 `approvalPolicy`를 좁히는 것: 전부 또는 전무라 마찰이 큼.

   셋 다 사람의 엔진 설정이나 실행 인자를 바꾸므로 소유자 결정이 필요함. 지금은 (b) 기록으로 빈도만 잼.
