## 1. 진행 답의 경과 시간 (L2가 본 "about 1 seconds")

- **원인:** 사람이 run 도중 보낸 메시지가 `mark('user')`를 다시 찍어서 `sinceUserMs`가 메시지 시점부터 다시 센다. 쓰기 프롬프트는 이 값을 "작업이 걸린 시간"으로 썼다.
  - 실제 run 기록(check-2)에서도 같다. 4초에 보낸 메시지의 beat는 `sinceUserS: 1`이었다.
- **수정:**
  - `workMsOf(heartbeatFacts, flow)`는 heartbeat 시계에서 `flow.runStartedMs`를 뺀 값이다. `runStartedMs`는 run의 flow가 시작될 때 기록한다.
  - `beatFlowFacts.workMs`가 이 값을 담는다.
  - 프롬프트는 `round((workMs ?? elapsedMs)/1000)`을 쓴다. 중단(stalled) 프롬프트는 침묵 시간(`sinceEngineMs`)을 쓰고, 그 값이 없을 때만 작업 시간을 쓴다.
  - 10초/30초 같은 문턱은 그대로 `sinceUserMs`를 쓴다.
- **사실 줄 추가:** 사람이 run이 시작된 뒤에 다시 썼고 작업 시간이 마지막 메시지보다 1초 이상 길 때만, beat의 run 맥락과 검사의 run_state 증거에 한 줄이 붙는다: "The work began N seconds ago (the person wrote again into the running work M seconds ago)." 그 밖의 모든 요청은 바이트가 그대로다.
- **테스트 (heartbeat 가상 시계):**
  - 12초 일한 뒤 메시지를 보내면 프롬프트가 12–14초를 말한다.
  - 순수 프롬프트 사례도 확인한다.
  - 변이 2건이 잡혔다.
- **L2에 알렸다:** 사실 이름은 `workMs`이고, 프롬프트 문구 형식은 그대로다. 같은 줄에 있는 대기(wait) 숫자와 침묵 숫자는 별개의 값이다.

## 2. s3b tense 오탐 (v6 .86)

**본문 읽기:** s3b 답 "PostgreSQL 전환 설계에서 스키마 변환, 데이터 이관, 롤백 순서를 정하기로 확정했습니다."는 맞는 회상이다.

증거 목록의 문제는 두 가지였다.
- 같은 기록이 두 번 들어 있었다. E1은 제목만("PostgreSQL 전환 설계"), E3은 제목 + 본문이다. E2와 E4(계획 페이지)도 마찬가지다.
- 질문이 한 문장에 두 조건을 담고 있었다. c18 문구는 "…done or true now that the evidence records only as planned or only as past"였다. 모델이 "확정했다 / 정해져 있다"를 "done"으로 읽었다.

**같은 원인의 다른 사례 (L6의 over-correction 실측):**
- `c-sales` "4분기 목표는 4억 5천만 원으로 정해져 있습니다" → planned 기록 앞에서 tense .97 (옳은 문장).
- `c-quote` "…팀장 승인 뒤에 보내기로 정했습니다" → .41.
- s3b → .86.
- 모두 "정했다 / 정해져 있다"가 done으로 읽힌 것이다.

**수정 (기준 변경 없음):**
- **질문 문구:** "Does sentence S present something as already carried out, or as true right now, when the evidence records it only as planned, or only as it was at an earlier time? Saying that something is planned, is decided, was decided or was so before is not."
- **증거 중복 제거(코드):** 한 항목의 텍스트가 다른 항목 텍스트의 앞부분(공백 정리 후, 낱말 경계)이고 시간 태그와 status가 같으면 그 항목을 뺀다. 검사가 증거를 묶는 곳에 있어서 모든 호출자가 혜택을 본다. s3b 본문은 7개에서 6개로 줄었다.
- **L6의 over-correction 계획:** 문구가 바뀌어 `--write`로 다시 썼다(코드가 만드는 계획).
- **heartbeat 계획 바이트 테스트:** 술어 설계의 검사 요청 2건(`wait-check-predicates`, `wait-check-invented-result`)도 같은 문구를 담아서 '바뀜, 보내지 않음, 이유'로 등록했다.

## 4. 사람 메시지는 다음 beat에서 바로 판정 (Main 추가 요청 a)

heartbeat의 ask 간격(10초, 모두 none이면 2배씩), nudge 한도(5초에 한 번), ask 예산(6)은 비서가 먼저 꺼내는 알림에만 적용한다.

- **solicited 질문:** 사람 메시지 질문이 `solicited: true`로 표시한다.
  - 간격, back-off, ask 예산을 건너뛴다.
  - 그 라운드에는 solicited 질문만 묻는다. 다른 provider의 비서 질문은 자기 beat를 기다린다.
  - 그 라운드는 ask 횟수, `lastAskAt`, 모두-none back-off에 들어가지 않는다. 비서가 먼저 꺼내는 알림의 시점은 그대로다.
- **solicited nudge:** `hb.nudge({ solicited: true })`는 nudgeMs(0.5초) 바닥 하나만 적용한다. 판정 라운드가 진행 중일 때 온 nudge는 기억해 두었다가 라운드가 끝나자마자(0.5초 안에) beat를 만든다.
- **L2 코드 한 줄:** `acceptInRunMessage`의 `nudge()` 호출에 인자 하나를 더했다. L2에 알렸다.

**테스트 (가상 시계):**
- **계약 수준:**
  - 간격 안에서 0.5초 만에 판정한다.
  - 연속 메시지(0.6초 뒤)도 판정한다.
  - 비서 알림은 정확히 5초와 25초에 나간다.
  - 예산이 소진된 뒤에도 판정한다.
  - 라운드가 진행 중이면 그 라운드가 끝난 뒤 0.5초 만에 판정하고 5초 격자에 맞추지 않는다.
- **제품 수준:** 메시지를 보낸 1초 뒤 "그만해, 취소할게"를 보내면 0.6초 안에 중지된다.
- **변이:** 6건 + 문구 변이 등 12건이 모두 잡혔다.
  - 처음에 살아남은 변이는 테스트 질문 이름이 매번 달라 항상 "처음 묻는 것"이 되던 것이 원인이었다. 같은 이름으로 고치고 solicited 질문도 `offered`에 기록하도록 맞췄다.

## 6. 실제 엔진에서 나온 이번 사이클의 중요한 발견 (check-2, why-stopped)

why-stopped는 통과했다(2턴, 28.2초). Decision은 맞았다: status 1.0, change 0, stop .02 → 판정 `reply`.

그런데 기록에 **`posted: none`**이 남았다.
- 이 run에서 진행 답은 게시되지 않았다.
- 원인: 진행 답을 쓰는 `thread/fork`가 **-32600으로 거부**되었다. 이 기록에서 `thread/fork`는 이 한 번뿐이다.
  - 제품의 fork 호출 파라미터는 `{ threadId, excludeTurns: true, ephemeral: true }`이고, 0.171 프로토콜 부분집합에 모두 있는 필드다. 오류 메시지 본문은 기록에 없다.
  - 가장 그럴듯한 원인은 **턴이 진행 중인 스레드는 fork할 수 없다**는 것이다. (`lastTurnId`는 "진행 중이면 안 된다"고 문서에 적혀 있다.) 이것은 추측이다.
- 결과:
  - 쓰기가 실패했으니 코드가 `steer`로 넘어갔다(안전한 기본값).
  - 스크립트의 `posted: true`는 첫 턴의 마지막 답이 채웠다. 그래서 통과했다. 이 기대는 "답이 따로 게시되었다"를 구분하지 못한다.
  - L5에 필요한 것은 턴 구간 안에서 게시된 메시지 개수를 세는 기대 키다(예: `postedMin: 2`).

**파급:**
- 모든 heartbeat 메시지(진행 알림, 질문, 포인터)가 같은 fork 경로로 쓰인다. 진행 중인 턴에서는 실제 엔진에서 쓸 수 없을 가능성이 있다. 지금까지의 실제 엔진 검증은 steer와 interrupt뿐이었다.
- 중단(stalled) 줄만 고정 문구로 되돌아가는 경로가 있다.
- 이 가설은 Main이 확인해야 한다. 제안:
  - 진행 중인 스레드에서 `thread/fork`를 호출하고 오류 메시지를 기록한다.
  - `lastTurnId`(마지막으로 끝난 턴)를 줘서 다시 호출한다.
  - 끝난 스레드에서 호출한다.
  - L5의 기록에는 오류 메시지 본문도 남기게 한다.
- 만약 가설이 맞으면 쓰기 경로를 새로 설계해야 한다. 후보는 진행 중 턴이 아닌 별도의 짧은 스레드(thread/start ephemeral + 요약 사실)다. 이것은 결정 사항이다.
