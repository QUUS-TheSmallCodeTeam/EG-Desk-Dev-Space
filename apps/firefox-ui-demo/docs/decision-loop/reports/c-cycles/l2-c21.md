### 새 기대 `expect.engine` (`helper/egdesk-real-engine-journey.mjs`)

L5의 점검에는 엔진 요청과 메시지 종류를 말하는 기대가 없어서, L7의 memory hook처럼 **자기 모듈**로 만들고 점검에는 표시된 등록 지점만 더했습니다(`// journey hook`). L5의 hook 목록(`egdesk-real-engine-hooks.mjs`)은 요청마다·창마다 부르는 API가 없어서 쓰지 못했습니다.

| 키 | 뜻 |
|-|-|
| steers, interrupts | 창 안의 `turn/steer`, `turn/interrupt` 요청 개수 |
| steerCarries | (whileRunning 턴) 첫 steer가 사람의 말 그대로 하나의 text 입력이고 client message id가 있음 |
| flowMessages, agentMessages | 시스템 자신의 메시지(`egdesk-flow:`)와 Agent 자신의 메시지 개수 `{equals/max/min}` |

- 창은 점검의 것: 일반 턴은 전체(턴 + 거기에 친 메시지), whileRunning 턴은 그 메시지를 보낸 뒤.

### 가짜 app-server 검증 (`helper/egdesk-real-engine-journey.test.mjs`, 13개)

여정의 대본 Decision 답을 제공자로 쓰고 명령·app-server는 가짜입니다. 실제 모델의 행동은 측정하지 못하고, 통과는 "장치가 돈다"는 뜻입니다.

  - "중지"를 "상태 질문"으로 읽는 모델 → interrupt 없음, `turnStatus` 실패, 시간 상한 실패.

  - steer 계약이 없는 바이너리 → 변경이 steer되지 않고 `steerContract: false`를 상세에 적고 실패.
  - 페이지를 고르지 못하는 모델 → `memory.attached` 실패.

## 2. 실제로 돌리기 전에 알아야 할 발견

1. **steer 계약**: 제품은 steer 계약을 **0.162.1에만** 인정합니다(`inspectNativeCapabilities`). 지금 사람의 Codex 0.171에서는 `journey-change`의 `engine.steers`가 **실패합니다**(`steerContract: false`). 메시지는 대기하다 다음 턴에 실립니다. 0.171의 생성 스키마는 steer 모양 검사를 통과합니다(c18 증거: `boardPeer: true`). 허용 버전 표를 넓히는 일은 제품 결정입니다(Main/L5).
2. **interrupt가 명령을 멈추지 않음**: `helper/egdesk-command-executor.mjs`는 러너를 `signal` 없이 부르고(113행) 실행기에 `cancelRun`이 없습니다. 그래서 사람이 "그만해"라고 해서 턴이 `interrupted`가 되어도 **EG-Desk가 시작한 명령 프로세스는 계속 돕니다**. 여정의 `s12.interrupted`는 엔진 쪽만 보므로 이것을 못 잡았습니다. `journey-stop`의 `commandStopped`가 잡고, 가짜 세계에서도 실패로 재현됩니다(테스트가 이 실패를 고정; 고치면 뒤집힘). 되돌릴 수 없는 명령(배포 등)에서 위험합니다. 담당 L5(own tools). 고치기는 작은 일이지만(실행기 제공자에 `cancelRun`, 러너에 신호 넘기기) 제 레인이 아니고 이번 요청 범위도 아니라서 하지 않았습니다.
3. 가짜 app-server(L5)는 도구 호출이 진행 중인 턴을 interrupt로 바로 끝내지 않습니다(명령이 끝날 때 끝남). 실제 0.171이 대기 중인 `item/tool/call`을 어떻게 다루는지는 모릅니다(Main의 실측은 글만 있는 턴). 그래서 `maxLatencyMs`(30초)는 가짜에서 증명되지 않고 실제 실행의 몫입니다.
4. 12초에 보내는 메시지 판단은 하트비트 한도에 걸릴 수 있었으나, L3 c24/c25가 사람의 메시지를 다음 beat에 판단하게 했으므로 지금은 문제 없습니다.
