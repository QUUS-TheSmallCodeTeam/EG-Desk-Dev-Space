# L7 c41: 기억 먼저(memory-first)의 Decisions 전용 재생(replay) 계획

기준: int/c14 = `4877565`. 실제 Codex가 11-30까지 꺼져 있어 memory-first v2를 실제 엔진에서 돌릴 수 없으므로, **엔진 없이 Decisions만으로** 기록된 실제 턴의 턴 시작 요청을 다시 보내 보는 계획입니다. 이 계획을 만든 코드는 아무것도 보내지 않고 키도 읽지 않습니다 (Main 전송, dry-run 확인 완료).

## 1. 무엇을 재생하나
- **입력은 기록된 것**: 사람 메시지는 check-20mw, check-27mw, check-31mf의 것 그대로 (대본 `write-v3`, `memory-first-v1/v2`의 말과 일치하는지 시험이 확인), 저장 상태는 그 대본이 시드한 기록(일정 3건: 신제품 리뷰 회의, 거래처 점검 방문, 법무 검토 마감; 워크숍 2건). 두 번째 턴의 "붙잡고 있는 기록"은 기록된 첫 턴이 전달한 페이지(제품이 첫 턴을 먼저 걷고 `nextDelivered`를 받아 `mid`, `live_thread` 위치로 두 번째 턴을 만든다).
- **요청 본문은 제품 자신의 함수가 만든 것**: `prepareTurnMemory`(기록 분류 triage, 쓰기 판단 `judgeWrite`: 문장별 세 축 `speech_source/form/time` + `tw_status` + 후보마다 `tw_about_i`, hybrid-ask의 두 번째 단계 `speechs_*` (own 문구 v4), 새 기록의 링크 질문), `judgeRecordConflict`(`cf_differs`), `judgeConfirmation`(문구 v2, 실제 답은 check-20mw 3턴의 것), `contradictionRequest`. 엔진은 관여하지 않습니다. 체인을 걷기 위한 대역 답은 본문에 들어가지 않고 기대값도 아닙니다 (시험: 본문에 답 필드 없음).
- 시나리오 (사람 말 / 기록된 실제 결과):
  | 시나리오 | 말 | 실제 기록 (기대값의 근거) |
  |---|---|---|
  | own | "아 그거 다음 주 화요일로 확정했어" | 신제품 리뷰 기록에 pending 읽기, 근거 self_reported_observation (check-20mw/27mw); 기록은 "미정", 말은 "확정" → 충돌 |
  | hedged | "아 그 점검 방문은 아마 화요일쯤일 거야" | 자기 진술로 설치되지 않음, 전달된 말도 아님 (check-20mw/27mw/31mf) |
  | relayed | "법무팀 말로는 그 마감을 수요일로 정했대" | pending 읽기, 근거 attributed_report, **충돌 yes p=1.0, 1,341 ms** (check-31mf) |
  | control | "신제품 리뷰 회의 일정 아직 안 정해졌지?" | 쓰기 판단 없음, 충돌 없음 (check-31mf control-first) |
  | newrecord | "아 그리고 다음 달 둘째 주에 재고 실사를 할 거야" | memory-first-v2의 새 기록 대화 (실제 엔진 미실행); 어느 저장 기록과도 무관 |
  | confirm | "응 맞아" (직전 답은 실제 20mw 답) | check-20mw 4턴 / c36 `confirmation-stated-v1` 6/6 |
  | contradiction | 워크숍 두 날짜(12월 5일, 12월 12일) 대 서로 다른 일 | memory-first-v2 (check-32mf는 실행 안 됨) |

## 2. 계획 `memory-first-replay-v1`
- 11개 요청, 추정 입력 토큰 **10,173**, 선언 상한 **12,000** (c57 실측이 추정보다 +5~10%이므로 10% 더해도 상한 안; runner의 fitted+margin 11,741). 전송: `transport: "product"` (제품의 Decisions 전송, 요청마다 소켓이 따뜻했는지 `warmBefore` 기록).
- 요청과 기대값 (코드가 만든 것, 제품 바 그대로, 근거는 각 note에 명시):
  | 요청 | 기대 (hard = 실제 실행이 보여 준 것) |
  |---|---|
  | own-write | `tw_about`: 리뷰 기록 yes ≥ .8; `tw_status` ∈ {plan, done} (결정됨); `speech_source` 설치 시 ∈ {self_reported_observation, unspecified} |
  | own-write-second | `speechs_own_0` ≥ .85, `speechs_other_0` ≤ .15 (c36 own v4 10/10) |
  | own-conflict | `cf_differs` ≥ .8 (미정 대 확정) |
  | hedged-write | `speech_source` 설치 시 own도 relayed도 아님 (hard); `tw_about` 방문 기록은 soft |
  | relayed-write | `tw_about` 법무 기록 yes; `tw_status` ∈ {plan, done}; `speech_source` 설치 시 attributed_report |
  | relayed-conflict | `cf_differs` ≥ .8 (check-31mf p=1.0) |
  | control-triage | `tn_record` ≤ .79 (쓰기 판단을 원하지 않음), ≤ .2 soft |
  | newrecord-write | 모든 `tw_about_i` ≤ .2 (→ 새 기록), `tw_status` = plan |
  | own-confirm-yes | `rc_stated` ≥ .8, `rc_confirms` ≥ .8, `rc_rejects` ≤ .2 |
  | contradiction-yes / -control | `ct_0` ≥ .8 / ≤ .79 |
- 상한 때문에 **만들었지만 보내지 않는 요청** (`captureScenario`가 계속 만든다; 더 큰 계획이 필요하면 보낼 수 있음): own, relayed, newrecord, hedged의 양성 triage (실제 실행에서 쓰기 판단이 돌았다는 사실이 이미 그 결과), hedged와 control의 충돌 (conflict-pair-v1 6/6, c57이 같은 모양을 측정), newrecord의 두 번째 단계와 링크 (soft뿐). 시험이 이 요청들이 실제로 만들어지는지 확인합니다.
- 합격 규칙: hard 검사 전부 통과. soft는 처음 묻는 질문. 바는 바꾸지 않았습니다 (runner가 제품 바보다 느슨한 hard를 거부하고, 축은 .85/.20, 쓰기 상태 .75/.2, 예/아니오 .8/.2).

## 3. 타이밍
- runner가 요청마다 `elapsedMs`와 `warmBefore`를 기록합니다. `node scripts/egdesk-c41-replay.mjs report <results.json> [plan.json]`이 요청별 표와, **턴 시작 단위**로 합계를 냅니다: 쓰기 판단 → 두 번째 단계 → 충돌은 순차 합, 모순 질문은 쓰기 판단과 나란히라서 느린 쪽, 확인은 루프 앞. 소켓이 따뜻하면 예산 2.5초(warm), 차가우면 4초(cold; `TURN_MEMORY_CAPS`)와 비교해 `within`을 냅니다. 이 합계는 **루프(분류, 기록 고르기) 뒤에 추가되는 시간**이라, 예산 전체를 쓰는 것은 아닙니다.
- 기대 (추정): 요청 하나 약 0.2~0.5초(c57 conflict/contradiction 실측 211~454 ms), 쓰기 요청은 본문이 커서(5.5 KB, 축 세 개) 0.3~0.8초 예상 → own: 쓰기+두 번째+충돌 약 1.0~1.8초, relayed: 약 0.6~1.3초 (실제 31mf 1,341 ms와 같은 규모). 예산 안 여부는 실측이 정합니다.

## 4. 명령 (Main)
```
# 계획 만들기 (이미 만들어 둠: $L/evidence/l7-c41/plans/memory-first-replay-v1/)
node scripts/egdesk-c41-replay.mjs plan <dir>
# 확인 (dry-run, 아무것도 안 나감)
node scripts/egdesk-decision-real-measure.mjs <dir>/memory-first-replay-v1/plan.json
# 전송 (소유자 승인 후)
OPENAI_API_KEY=... node scripts/egdesk-decision-real-measure.mjs <dir>/memory-first-replay-v1/plan.json --send --out <results.json>
# 타이밍 표
node scripts/egdesk-c41-replay.mjs report <results.json> <dir>/memory-first-replay-v1/plan.json
```

## 5. 테스트 (`helper/egdesk-c41.test.mjs`, 6개)
상한과 결정성(두 번 빌드한 해시 동일), 일반 실행기 로드와 제품 바, 기록된 입력(말은 실제 대본의 것, 시드, 두 번째 턴의 붙잡은 기록), 본문이 제품 것(요청 모양, own 문구 v4, 확인 요청이 c36의 것과 같음, 답 없음), 기대값이 코드가 기록 결과에서 만든 것(대상 하나만 yes, 새 기록은 전부 no, 축 바, hedged는 own/relayed 설치 불가), 타이밍 보고 (순차/병렬 합, warm/cold 예산), 모듈에 네트워크, 키, 환경 접근이 없음.

## 6. 하지 않은 것과 한계
- 후보 목록은 기록된 첫 턴이 전달한 기록 하나 위주입니다 (두 번째 턴에서 쓰기 후보는 붙잡은 것과 고른 것). 실제 실행에서 후보가 더 많았다면 `tw_about`의 개수가 다를 수 있습니다 (기록에 후보 수가 남아 있지 않음).
- 요청 본문 자체는 기록에 남아 있지 않아서(check 기록에는 호출 수만 있음) 제품 함수로 다시 만든 것입니다. 같은 입력이면 같은 본문이지만, 실제 실행의 본문과 바이트 단위로 같다고는 주장하지 않습니다.
- 엔진이 필요한 것(엔진의 말이 기록을 따르는지, 수락 직후 저장, 예산 안에서 기다림)은 이 재생이 볼 수 없고, 11-30 이후 실제 엔진 실행(`memory-first-v2`)의 몫입니다.
