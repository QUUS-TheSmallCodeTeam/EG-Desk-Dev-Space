# L7 c34: 메모리 쓰기 경로를 실제 엔진에서 (`real-engine-memory-write-v1`)

기준: int/c14 = 1a9515f (c33 포함). 확장 API(`helper/egdesk-real-engine-extensions.mjs`)로 만들었고, 실제 엔진은 돌리지 않았습니다 (Main 실행, 가짜 엔진으로만 검증).

## 1. 무엇을 확인하나
가상 일정 기록 3개(신제품 리뷰 회의, 거래처 점검 방문, 법무 검토 마감: 모두 날짜 미정, 기록된 status 없음)를 심은 Agent DM 방에서, 사람이 지나가듯 한 말을 쓰기 경로가 어떻게 저장하는지 봅니다. 대화마다 먼저 질문(질문은 아무것도 쓰지 않음), 사람의 말, 그다음 중립 질문(모델이 적어 둔 것을 말할 기회)입니다.

| 대화 | 사람의 말 | 기대값 (저장소에서 코드로) |
|---|---|---|
| own-confirm | "아 그거 다음 주 화요일로 확정했어" | **pending** reading, 출처 축(basis) = 사람 자신의 말 `self_reported_observation`, status plan 또는 done (결정), 기록 자체의 status는 unknown 그대로; 한 턴 뒤에도 pending (**자동 승격 없음**); 이어서 "응 맞아" → **accepted**, 사람의 확인(`confirmedAt`), 기록 status가 reading의 것으로 |
| hedged | "아 그 점검 방문은 아마 화요일쯤일 거야" | 아무것도 확정/승격 안 됨; reading이 있더라도 pending이고 출처 축이 사람 자신의 확정 진술(`self_reported_observation`)이 아님; 기록 status는 unknown 그대로 |
| relayed | "법무팀 말로는 그 마감을 수요일로 정했대" | pending reading, 출처 축 = `attributed_report` (전해 들음), 승격 안 됨, 기록 status unknown |

- "시간 축(결정됨/계획)"은 reading의 status(plan 또는 done)로 확인합니다 (저장된 reading은 status, 출처 축, 말한 시각만 가짐; 슬라이스는 제안 단계의 값).
- 출처 축은 제품이 설치하는 문장 라벨(바 이상일 때만)이라서, 라벨이 안 서면 basis가 null이고 own와 relayed 턴이 실패합니다. 그것이 발견이지 스크립트 오류가 아닙니다 (hedged는 null도 허용: 라벨이 안 서는 것이 오히려 기대되는 모양).
- 문장 라벨 설계는 `EGDESK_TURN_MEMORY_SPEECH_DESIGN=hybrid`(측정으로 가장 좋았던 두 단계)와 `EGDESK_TURN_MEMORY_CONFIRM=on`을 스크립트가 켭니다 (제품 기본은 아님: 기본 axes, 확인 끔).

## 2. 확장 API로 한 일
- `helper/egdesk-real-engine-recording.mjs` (내 모듈) + 등록 한 구역 (`helper/egdesk-real-engine-registrations.mjs`, L7 c34): expect 키 **`recording`** (`page`, `reading` none/pending/accepted/rejected/pending_or_none, `status`, `basis`, `pageStatus`, `confirmed`, `readings`, `newPages`), 대화 필드 **`speechConsent`**, 턴 훅 `recording`. 핵심 파일(L5의 check, script.mjs)은 건드리지 않았습니다.
- 턴 훅 `afterTurn`: 턴의 답이 게시된 뒤 백그라운드 쓰기 판단이 끝날 때까지(`turnMemoryIdle`) 기다리고, 제품 자신의 위키 스냅샷(저장소의 reading이 심은 기록 위에 겹쳐진 모습과 범위 안에 쓰인 페이지)에서 사실을 읽어 기대값을 코드로 대조합니다. 모델에게 "기록이 맞았나"를 묻지 않습니다. 레코드의 턴마다 `recording`(페이지별 readings, 쓰인 페이지)이 남고, 채점기가 "turn N store: …" 줄로 보여 줍니다.
- **발견: 확인 단계(응 맞아)는 check에 지금까지 조립되지 않은 것이 필요합니다.** 확인은 직전 답을 읽어야 하는데, 그것은 DM의 지난 발화이므로 제품은 **Agent DM + 사람이 DM 발화 재사용에 동의(opt-in)한 경우에만** 읽게 합니다 (`directSpeech`: 프로필, `memoryEvidence`의 speech grant). check는 프로필 방(c25 `agentProfile`)은 있지만 `memoryEvidence`가 없어서 확인이 항상 `no_previous_answer`로 끝납니다 (기본 check의 일회용 대화는 그렇게 설계됨). 그래서 스크립트의 대화 필드 `speechConsent: true`가 첫 턴 뒤(그때 DM이 생김)에 이 가상 사람의 opt-in을 **제품 자신의 API**(`MemoryEvidenceStore.enableSpeech`, 제품 DM 권한으로 얻은 범위)로 합니다. 임시 폴더의 증거 저장소이고 대화와 함께 지워지며, 레코드에 `speechConsent: { granted }`가 남고, 스크립트가 명시한 경우에만 합니다 (동의를 숨기거나 우회한 것이 아니라 사용자의 설정 하나를 이 가상 사람에게 켠 것). 이것이 없으면 "응 맞아"는 아무것도 확정하지 않고 스크립트는 코드로 실패합니다 (테스트로 확인).
- 이 때문에 대화는 Agent 방이라 `--persisted-with-cleanup`이 필요합니다 (기존 규칙).

## 3. 가짜 엔진 검증 (제품의 쓰기와 확인 경로 전체, 대역 판단자)
`helper/egdesk-real-engine-memory.test.mjs`에 테스트 6개 추가 (총 32): 
- **전체 대본 통과**: 실제 런타임, 실제 쓰기 저장소, 실제 쓰기 판단(`judgeTurnWrite` 'about' 설계)과 확인 판단(`judgeConfirmation`)을 지나, 대역 판단자(코드는 "그거"가 가리키는 기록, 전언 표지, 헤지 표지만 알려 줌)로: own는 pending(plan, self_reported_observation, 기록 unknown) → 한 턴 뒤 여전히 pending → 확인 뒤 accepted+`confirmedAt`+기록 status plan; relayed는 `attributed_report`; hedged는 own 아님.
- **모델이 적어 둔 것을 말하지 않으면** "응 맞아"가 아무것도 확정하지 못하고 (stated가 아님) pending 그대로이며 스크립트가 reading 기대값에서 실패.
- **opt-in 없음**: 같은 대화가 pending에서 멈추고 실패, opt-in 있음: 레코드에 `speechConsent.granted` true, 승격됨.
- 기대값 판단, 검증(없는 페이지/키/값 거부), 위키 스냅샷에서 사실 만들기, 채점기 출력, `speechConsent` 검증 (Agent 프로필과 memory on 필요).
- 확인된 안전: 자동 승격 없음(한 턴 뒤에도 pending), 승격은 사람의 확인 메시지 뒤에만.
