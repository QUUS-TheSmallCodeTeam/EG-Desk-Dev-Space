## 2. 답의 근거에 run 자신의 사실 (과제 2)

### 2.1 s6 를 정확히 읽기

c17 실측에서 s6 "테스트가 모두 통과했습니다." 는 PG 페이지만 근거로 sup .01 / tense .31 이었다.

L2 는 "술어 설계에서도 근거 없음으로 막힌다"고 했지만, **이 문장은 막히지 않는다.**
- 구체 정보(숫자·이름·식별자)가 없는 문장에는 `unverified` 를 내지 않는다.
- 내용 없는 명령 참조가 있으면 어떤 문장에도 내지 않는다.
- tense .31 은 기준 0.7 아래다.

`replay-before` 가 실제 답으로 s6 를 게시하는 것으로 확인했다. 하지만 이유가 틀렸다. "40개 모두 통과"처럼 구체 정보가 있었다면, 결과를 담은 근거가 없어 막혔을 것이다.

### 2.2 수정

`answerFactsEvidence(run)` 가 run 의 사실로 증거를 만든다.

| 단계 | 증거 항목 | 조건 |
|-|-|-|
| 명령 | 명령줄, 종료 코드, 걸린 시간, L5 판단기가 출력을 읽은 상태(고정 문구), 출력 마지막 3줄 (최대 300자) | `terminal_output` 이 허용될 때. 아니면 이전처럼 내용 없는 참조 |
| 브라우저 작업 | 닫힌 결과 노트 (`subjectiveNote` JSON 한 줄) | `browser_task_record` 가 허용될 때. 맥락 키는 더 이상 내용 없는 참조로 세지 않는다 |
| 그 밖의 도구 | 내용 없는 참조 | 그대로 |

**순서와 상한.** 검사는 8개까지만 받는다.
- s6 에서는 페이지 5개 + 기억 2개 + 내용 없는 참조가 자리를 채워 명령 사실이 잘렸다. 처음 고친 뒤에도 재생 본문에 명령이 없었던 이유다.
- 이제 순서는 run 사실 → 턴 자료 → 내용 없는 참조다.
- 내용 없는 참조가 하나라도 있으면 그중 하나는 상한 안에 늘 남긴다. 그것이 "확인 못 한 자료가 있다"는 신호라서 `unverified` 를 막는다.
- s1 은 이 규칙 덕에 c17 실측 본문과 바이트가 같다 (다시 재지 않는다).

s6 재생 결과 (`replay-after/bodies/s6-answer-draft_check-1.json`):
- E1: "In this turn the assistant ran `npm test -- --suite=payroll-secret`; it finished with exit code 0. The command check read its output as: The command finished and its output shows success. Last lines of its output: running 40 tests"
- 그다음 PG 페이지 4개 + 기억 페이지 2개

**정책 변경 하나.** c7 의 "도구 출력은 검사기에 보내지 않는다"를 바꿨다. 이제 run 의 모델이 터미널 데이터를 받을 수 있을 때(U9, 같은 허용 설정) 출력 마지막 3줄을 보낸다. `egdesk-draft-check-advisory.test.mjs` 의 해당 테스트는 두 경우 모두 단언하도록 고쳤다: 허용 시 사실로 들어감, 터미널 none 이면 이전처럼 참조만, 기록에는 어느 쪽이든 글자가 없음.

## 3. 사람이 본 것을 다음 턴에 (과제 3)

- 검사가 답을 바꾸거나 잘랐을 때 (`revised` / `certain_part` / `ask_user`), 그 대화의 다음 엔진 턴에 `egdesk_posted_answer` 애플리케이션 맥락을 **한 번** 싣는다. 내용은 다음과 같다:

  ```
  Your previous answer in this conversation was not posted as you wrote it (a check before posting: <outcome>). The person saw exactly this instead:
  """
  <게시된 글>
  """
  Build on what the person saw, not on your earlier draft.
  ```
- 다음 턴이 시작될 때 소비된다. 답이 그대로 게시되면 남은 것을 지운다. 묶인(bounded) 턴은 받지 않는다. 대화 화면에는 나오지 않는다.
- 다음 턴의 검사에서 이 키는 내용 없는 참조로 세지 않는다.
- choice 재생에서 s1 이 대체된 뒤, s2 의 턴 시작에 `egdesk_posted_answer` 가 그 대체 문구와 함께 실렸다. s4 턴에는 없다 (소비됨). L2 의 `toldWhatWasPosted` 판정 방식(턴 파라미터에 게시된 글이 JSON 이스케이프된 그대로 있는지)을 만족한다.
- 한계: 메모리에만 있다. 브리지가 재시작되면 잃는다. 대화마다 하나씩, 최대 64개 대화까지 보관한다.

## 4. 보류 문구 대안 (과제 4, 문구는 내보내지 않음)

현재 문구 두 개는 그대로 두었다. 둘 다 U1/U4 와 충돌한다.

| 키 | 현재 | 충돌 이유 |
|-|-|-|
| `askUser` | "확인할 수 있는 근거가 부족해 지금은 답하기 어렵습니다. 어떤 자료를 기준으로 할지 알려 주세요." | 사람에게 자료를 고르라고 한다 (U4: 양식 채우기 금지). 확인 판단은 시스템의 일인데 사람에게 넘긴다 (U1) |
| `partial` | "확인되지 않은 부분은 답하지 않았습니다. 필요하면 기준으로 삼을 자료를 알려 주세요." | 같은 이유 (뒷문장) |

제안 (승인 필요). 무엇이 확인됐고 무엇이 안 됐는지만 말하고, 자료 선택을 요구하지 않는다:

| 키 | 제안 |
|-|-|
| `askUser` | "가진 자료로는 이 내용을 확인하지 못해 답하지 않았습니다." |
| `partial` | "확인되지 않은 부분은 빼고 답했습니다." |

이어서 묻는 일은 3절의 메모를 받은 Agent 가 대화 안에서 자연스럽게 한다 (U4: 주관식으로 빠져나옴).

## 5. 포인터 표면 규칙과 따라붙는 메모 판단 (과제 5)

### 5.1 포인터: 표면이 있어야 가리킨다 (Main 규칙 3)

- `pointerBlocked` 에 `no_surface` 를 추가했다. 끝난 결과(result)는 provider 가 그 사람의 시야 밖 방향(left/right/above/below)에 놓은 표면이 있을 때만 가리킨다.
- 요청한 결과와 요청하지 않은 결과 모두에 적용한다. 가리킬 곳이 없으면 메시지가 할 말이 없기 때문이다.
- 결정·질문 종류는 표면이 필요 없다.
- 보관된 포인터는 보관할 때 표면이 있었는지(`located`)를 함께 기록한다. 방향은 여전히 버린다.
- L4 배치 사실은 늘 방향을 갖는다 (시야 안은 이미 `in_view`). 걸리는 것은 방향 없이 결과를 알리는 일반 provider 뿐이다.

### 5.2 "?" 거르기 대체 = 따라붙는 판단 (Main 결정 5)

- "?" 로 끝나는 메모는 이전처럼 바로 묻는다.
- 그 밖의 메모는 **어차피 나가는 요청(진행 알림 질문이 있는 요청)에만** 따라붙는다. 판단 안 된 것 중 오래된 순으로 최대 2개, 각자 `message__ask_N` 으로 따로 인용한다.
- 답을 받은 메모는 다시 묻지 않는다. 예이면 그 메모에 대한 이른 질문이 된다 ("?" 메모 다음 우선순위).
- 메모만으로는 요청이 생기지 않는다. 선택지 문턱(10초/30초 하한 등)을 통과해 질문이 이미 있을 때만 붙기 때문이다 (구조로 보장).

모의 비용 (`evidence/l3-c18/ask-ride-along-cost.json`, c16 과 같은 60초 시나리오, 같은 코드에서 변형만 바꿈):

| 변형 | 답 정책 | 요청 | 시각(초) | 질문 | ask 질문 | 바이트 | 추정 토큰 | 이른 질문 |
|-|-|-|-|-|-|-|-|-|
| 거르기만 (c17 동작) | 모두 아니오 | 2 | 10, 30 | 2 | 0 | 2,846 | 949 | 없음 |
| 거르기만 | 진짜 요청에만 예 | 2 | 10, 30 | 2 | 0 | 2,846 | 949 | **없음** |
| 거르기 제거 (c16 시뮬) | 모두 아니오 | 3 | 5, 10, 50 | 5 | 3 | 5,126 | 1,709 | 없음 |
| 거르기 제거 | 진짜 요청에만 예 | 3 | 5, 10, 50 | 5 | 3 | 5,126 | 1,709 | **없음** |
| **따라붙기 (c18)** | 모두 아니오 | **2** | 10, 30 | 6 | 4 | 4,387 (+54%) | 1,462 | 없음 |
| **따라붙기** | 진짜 요청에만 예 | 3 | 10, 30, 60 | 7 | 4 | 5,874 | 1,958 | **30초** |

- 요청 수는 거르기만 있을 때와 같다 (진짜 요청이 잡힌 경우 질문 게시 뒤의 다음 요청이 하나 더 생긴다).
- 바이트는 +54% 로, c17 보고서의 추정(+40%)보다 크다.
- 12초의 진짜 요청 메모가 30초 요청에서 판단되어 질문이 나간다. 앞의 두 방식은 끝내 못 잡았다.

1. **보류 문구 두 개 교체.** 4절의 제안을 쓸지, 다른 문안을 쓸지. 사용자 노출 문구라 승인이 필요하다.
