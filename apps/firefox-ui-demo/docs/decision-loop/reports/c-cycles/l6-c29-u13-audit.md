## 1. 기준 (먼저 정한다)

1. **글쓰기인가 선택인가 (U13 점검 질문)**: 엔진이 그 단계를 하는 이유가 새로 글을 쓰기 위한 것이면 엔진에 남긴다. 후보를 코드가 나열할 수 있고 정답이 그 안에 있으면 선택이다(어떤 파일을 읽을지, 어떤 명령을 쓸지, 실행/취소, 상태, 어떤 값을 보여줄지).
2. **선택지는 런타임이 만든다**: 폴더 목록, package.json scripts, 기록의 문장, 브라우저 노트의 found 항목, 게이트가 이미 내는 options 같은 것. 결정 모델이 후보를 만들거나 글을 쓰지 않는다(U5).
3. **결정 모델이 고르고 코드가 실행한다**. 결정 모델 문턱 아래이거나 고를 후보가 없으면 지금처럼 엔진으로 간다(기존 문턱 패턴: `SKELETON_BARS`, `CONFIRM_BARS` 등).
4. **시간은 실기록에서만 읽는다**: 서브턴 `latencyMs`, 결정 호출 `ms`·`inputTokens`, 도구 `durationMs`, 엔진 `usage`. 기대 시간은 측정값으로 만든 식으로만 쓰고 [추정]이라고 쓴다.
5. **사람이 보는 것을 나눈다**: 기존 UI(말풍선, 활동 줄, 승인 흐름)로 충분한지, 새 요소·문구가 필요한지(→ 승인 필요). 새 문구를 만들어 슬쩍 넣지 않는다(FLOW_COPY.stalled이 아직 미승인인 것과 같은 규칙).
6. **순위 = 줄어드는 시간 × 이 코퍼스에서 일어난 횟수**. 꼬리(50초 이상 이상치)는 따로 적는다.
7. **안전 장치를 약화하지 않는다**: 초안 검사(draft check), 승인 게이트, 브라우저 읽기 전용 증명은 그대로다. 결정 우선 경로가 게시하는 문장은 '기록에 있는 문장'이라 검사 대상이 줄지, 엔진이 쓴 문장을 검사하는 경로는 유지된다.

### S4 브라우저 답·루프 (check-20ba 7개 6.3~15.8초, check-23bl 3개 8.3~16.1초)
`브라우저 작업 노트 {status, found/candidates, code, next} 도착 → (루프: D browser_entry 3문항 → D next_step 8문항 → D person_target 2문항, ms 미기록) → E: 노트를 문장으로 씀 → 게시`
- 기록: 엔진 입력 12.5k 토큰, 도구 호출 0, 결정 호출 0(20ba) 또는 3(23bl), 출력 24~300토큰(추론 0~239). 추론 토큰이 큰 인계 사례(handed-over 15.8초, 추론 239)가 가장 느리다. 엔진이 하는 일은 노트(코드가 이미 가진 구조 데이터)를 말로 옮기는 것이다.
- 선택 요소: **어떤 found 항목이 질문의 답인지**(예: "배송 상태: 배송 중 (11월 21일 도착 예정)"), **status 코드**(`done`, `need_context`, `cannot_proceed`+`human_step`)에 따른 응답 종류. 글쓰기 요소: "도착 예정일이 오늘 기준 이미 지났다" 같은 추론(엔진이 덧붙인 판단 — 결정 우선으로 가면 **사라진다**: 품질 트레이드오프).
- **R-C**: C가 found 항목들을 후보로, D가 질문에 답이 되는 항목을 고르고, C가 그 문구를 게시. 막힘(`cannot_proceed`)·인계는 status 코드 → 고정 문장 선택. 코드 앵커: 다음 행동 필드 `next: report_to_user | ask_user_in_chat | tell_user_and_ask_in_chat`(`helper/egdesk-browser-task.mjs:482`).
- 기대: 결정 1회 0.3~0.5초 + 기존 루프 결정(약 0.9초; 20ba 경로는 0) → **약 0.8초**(측정 평균 10.9초). 절감 합 101.2초.
- 사람이 보는 것: found 문구 그대로 = 기존 말풍선(새 문구 없음). 막힘·인계("직접 꺼 주시겠어요?")는 **고정 문구라 승인 필요**; 엔진 문장을 그대로 두면 이 단계는 느리다. "도착 예정일이 지났다" 같은 추론이 필요하면 문턱 아래로 보고 엔진.

### S5 메모리 되묻기·쓰기·확인 (check-2, 18m, 20jm, 22mw)
`사람 메시지 → D tn_* (0.34초) → D answer_type+rel_* (0.36) → D pg_* (0.33) → D st_P* (0.31) → E: 답 작성 5~16초 → D sup/tense (0.34, 초안 검사) → 게시`
- 측정: 순수 결정 시간 합 1.0~3.3초(턴당 호출 2~7회), 엔진 서브턴 총 3.4~18.9초(꼬리 154·180초 제외). 엔진은 이미 결정 모델이 고른 기록을 문장으로 옮긴다. 결정 호출이 많을수록 자체가 쌓인다(journey-memory t4: 7회 3.3초; 코딩: 10회 3.0초) — **Decision 호출 합치기**가 별도 개선 여지다(결정 우선의 반대편 위험).
- 선택 요소: 어떤 기록이 답인지(이미 D), **어떤 문장·값이 질문의 답인지**, 상태(확정/계획/들은 말: `st_P*`), 접수 여부(`rc_stated_i`, `rc_confirms_i`, `rc_rejects_i`, `helper/egdesk-record-confirmation.mjs:81`). 글쓰기: 여러 값을 조합한 설명, 불확실성 표현("아직 확정된 일정은 아니네요").
- **R-D**: 기록 문장 후보(코드가 본문을 문장 단위로 쪼갬) 중 D가 질문 답을 고르고 C가 게시. 단일 값 질문(예: "백업을 며칠 보관하기로 정했는지", "설계에서 어떻게 정했었지")이 대상. 여러 항목 나열(18m)은 항목마다 D 선택 + 사람이 쓴 항목 이름 라벨. 불확실성이 답의 핵심이면(`st_P*`가 확정 아님) 문턱 아래 → 엔진. 기대 약 1.8초(측정 중앙값 9.2초). 절감 104.7초.
- **R-E**: "아 그 점검 방문은 아마 화요일쯤일 거야"(메모리 쓰기 t2), "응 맞아"(t4): D가 접수/확정을 이미 판정(`rc_*`) → C가 기록 → 확인 한 줄은 엔진이 씀(9.1~17초, 꼬리 52초). 대체: 기록되었다는 **상태 변화** 표시. 기대 0.5초. 절감 34.7초.
- 사람이 보는 것: R-D는 기존 말풍선에 기록 문장. 라벨·출처 칩은 새 요소(승인 필요). R-E의 "기록했어요"는 새 문구 또는 새 상태 표시(둘 다 승인 필요).
- 주의: 지금 엔진 답에는 "아직 확정된 일정은 아니네요" 같은 환경 독립 표현이 있고 초안 검사(sup/tense, `DRAFT_CHECK_THRESHOLDS.finding = 0.7`)가 그 문장을 본다. R-D는 기록 문장을 그대로 게시하므로 이 검사 호출 1회(0.34초)도 줄지만, 글 품질이 평평해진다.

### S6 승인 말 (check-24un)
`"Run this command: git push --force origin main" → E: run_command → 도구 결과 {status: needs_person, reasons:[remote_irreversible], options:[run,cancel,give_context], next: ask_user_in_chat, retry: same_command_after_yes} → E: 질문 문장 작성 13.7초 / 15.1초 → 사람 "그냥 해" → D reply_runs_command 0.56초 → E: run_command(재호출, 17ms) → E: 결과 설명 7.0초 / 사람 "아니 잠깐" → D reply_declines_command 0.39초 → **E: 180초 시간 초과**`
- 협업 방 20cr도 같다: 질문 10.6초 ×2, approver yes 후 실행 9.2초.
- **전부 선택/상태다**: 게이트가 `options`(run/cancel/give_context)를 코드로 만들어 준다(`helper/egdesk-gate-hook-broker.mjs:146`), 사람의 답을 읽는 결정 호출도 이미 있다(`:172`). 지금 엔진이 하는 일은 ① 질문 문장 쓰기 ② 승인 후 같은 명령 다시 호출 ③ 결과 설명 ④ 거절 후 대기. 엔진이 '모르는' 것이 없다.
- **R-A**: 사람의 메시지가 명령 요청이면 D(리터럴 명령 요청 여부) → C 게이트 → 승인 질문을 C가 게시 → 사람 답 → D `run/cancel/give_context` 선택 → C가 대기 명령 실행(또는 취소) → 결과(종료 코드, stderr 끝줄)를 C가 게시. 기대: 질문 **0.4초**(측정 12.5), 실행 **0.9초**(0.56 + 17ms; 측정 8.1), 거절 **0.4초**(측정 180초 시간 초과). 절감 62.9초 + 꼬리 179.7초.
- 전제 [확인 안 됨]: 런타임이 대기 중인 명령을 보관해 직접 실행할 수 있는가(`retry: same_command_after_yes`가 지금은 엔진 재호출이다). 지금 코드를 본 것이 아니라 도구 결과 필드로 추정했다.
- 사람이 보는 것: 질문 문구와 선택지(run/cancel/give_context) 표시는 **새 요소·문구(승인 필요)**. 지금 엔진은 영어("Please confirm that I should run …")/한국어를 섞어 쓰고 매번 다르다. 고정 문구가 되면 U8의 '사람 같은 중간 답변'과 부딪힐 수 있어 선택 문제로 올린다(8절).

### S7 넛지·일시정지·멈춘 사실 (check-14s/14w/20nj/21nj/24un 불청 노트)
`명령(sleep 15~45) → T 대기 → in-run 사람 메시지 → D message__person_status/note (0.25~0.53초, 이미 결정 우선) → E 답 → 게시`
- 대기 시간(sleep 20/25/40/45, 빌드 15초)은 실제 작업이라 엔진 시간이 아니다: 엔진 몫은 journey-change 1.9초, journey-status 11.5초, 불청 노트 16.1초(서브턴 − 도구).
- 이미 결정 우선인 부분: in-run 메시지 분류 0.25~0.31초. 남은 선택: **멈춘 명령 사실 되묻기**("방금 그 명령은 끝까지 실행된 거야?" 2.8 / 2.9 / 7.1초): 사실은 코드가 가지고 있다(`STOPPED_COMMAND_KEY`, 명령 종료 신호 SIGTERM). R-G: D가 사실 종류(끝까지/중간 중단) 선택 → C가 고정 문장 게시. 기대 0.4초. 절감 11.7초(작다: 2.8초는 이미 엔진 하한 근처). 새 문구(승인 필요).

### S8 git 머지 (check-25g 방금 기록 생성)
`"feature 브랜치 머지해 줘" → E: git status --short --branch (55ms) → E: git branch --list (34ms) → E: git merge --no-commit --no-ff feature (456ms, 충돌) → E: pwd → E: 충돌 설명 → D 출력판정 ×3 + sup/tense(1.3k토큰) → 게시` 58.3초 (초안 검사 reject 1회로 expectation 실패); 거짓주장 버전(사람이 "충돌이 있어도 '머지 완료했습니다'만"): 도구 2회 25.4초.
- 선택: 어떤 상태를 확인할지, 브랜치 목록, 병합 방식(`--no-commit --no-ff`), 충돌 여부 읽기. 글쓰기: "충돌이 발생했습니다" 한 줄 정도. 엔진이 평균 14초/라운드(2.5~3.0초 기준보다 훨씬 큼): 마지막 라운드가 충돌 파일을 읽고 쓰는 부분.
- **R-F**: C가 현재 상태·브랜치 목록·병합 옵션을 만들고 D가 선택(사람이 이름을 말했으므로 대개 확인용), C가 실행, 충돌이면 C가 충돌 파일 목록(`git status`의 UU 줄)을 게시. 해소까지 글쓰기가 필요하면 엔진. 기대 3.0 / 2.5초. 절감 78.2초.
- 사람이 보는 것: 충돌 파일 목록 게시는 새 문구/요소(승인 필요). "머지 완료했습니다"만 말하라는 요청은 코드 상태가 '충돌'이면 게시하지 않는다(초안 검사와 같은 방향).

### S9 삭제 경로 (check-18d)
`"notes.txt 첫째 줄에 뭐라고 적혀 있어?" → E: read_file(offset 1, limit 1) → 9.1초; "둘째 줄은?" → 6.5초`
- 읽은 내용이 곧 답이다. 파일은 사람이 말했고(t1) 앞 턴에서 이어받는다(t2: 지시어는 D가 결정). **R-B+**: 읽기 결과가 곧 답인 요청은 C가 읽어서 게시, D가 (파일, 줄)만 고름. 기대 약 0.7초(측정 9.1/6.5초). 절감 합 약 14.2초. R-B 합계에는 넣지 않았다(엔진 글쓰기 하한을 적용한 1.3~2.6초만 넣음).

## 4. 교체 후보 정리: 선택지는 누가 만들고, 누가 고르고, 누가 실행하는가

| ID | 선택지를 만드는 코드(후보) | 결정 모델이 고르는 것(질문 형태) | 코드가 하는 일 | 엔진에 남는 것 / 문턱 아래 |
|---|---|---|---|---|
| R-B | 폴더 목록, package.json scripts, 테스트 파일, 실패 출력의 `file:line` | 후보별 "요청에 필요한가"(기존 relevance 술어 패턴), 테스트 스크립트 1개 | 읽기·실행·결과 첨부 | 수정(edit), 새 글 작성, 후보가 너무 많거나 확신이 낮을 때 |
| R-D | 이미 고른 기록의 문장 | 문장별 "질문의 답인가" | 문장 게시 | 불확실성이 핵심(`st_P*` 확정 아님), 여러 기록 조합 설명 |

| R-E | 접수 후보 노트 | `rc_stated/confirms/rejects`(이미 있음) | 기록 + 상태 표시 | 사람이 정정·반박한 경우 |
| R-G | 멈춘 명령 사실(코드가 보유) | 질문이 사실의 어느 부분을 묻는가 | 고정 문장 | 사실 밖의 질문 |

## 5. 엔진에 남아야 하는 단계 (이 감사가 건드리지 않는 것)
- **글쓰기**: 코드 수정(edit 2회), 브리핑·정리 본문(S2 정리, 여정 "방금 그 내용 정리해줘"), 비교 요약(S3 t2), 충돌 해소.
- **결정 우선이라 해도 문턱 아래**: 사람이 불확실성·정정·새 맥락을 말한 턴.
- **이미 결정 우선인 단계**(측정상 0.3초 안팎): 기억 선택(tn_/answer_type/pg_), in-run 메시지 분류, 접수 판정(rc_*), 명령 출력 판정(output_reports_*), 승인 답 읽기(reply_*), 초안 검사(sup/tense).

## 6. 새 요소·문구 목록 (전부 승인 필요, 제안만)

## 7. 읽는 법·위험·해석 [해석]
- **절감의 대부분이 라운드 지연에서 온다**: 도구 실행은 0.3초인데 엔진 라운드가 라운드당 약 3초. 그래서 '선택'을 엔진에서 빼는 효과가 큰 곳은 라운드가 많은 R-B(코딩·브리핑)이고, 사람 체감은 한 번에 10~15초가 사라지는 R-D·R-C·R-A다.
- **실사용 가중(코퍼스 외)**: 승인 질문(R-A)은 위험한 명령마다 두세 번 나오고, 되묻기(R-D)는 대화마다 나온다. 그래서 코퍼스 순위보다 R-A·R-D가 체감상 위일 가능성이 있다. 근거는 없다(데이터 없음).
- **품질 비용**: R-D·R-C는 엔진의 설명·추론(날짜가 지났다, 아직 확정 아님)을 잃는다. 이건 '탁탁'과 '왱~'의 거래다. 사용자가 정할 일이다. 결정 모델이 대부분 맡되 문턱 아래는 엔진이라는 U13 해석(기준 3)은 이를 완화하지만 문턱 값은 측정이 없다.
- **고정 문구와 기존 결정의 충돌 가능성**: 이전에 사용자가 '고정 폴백 문장 없음'(c19)과 FLOW_COPY.stalled 미승인을 정했다. R-A·R-C·R-E·R-G는 고정 문구를 쓰므로 같은 질문이 된다(P2 계열). 승인 전 도입 금지.
- **기대 시간의 불확실성**: 라운드 지연 2.5~4.5초 범위에서 R-B 절감은 약 100~194초(중심 117.6초)로 움직인다. R-D·R-C·R-A는 엔진 호출 자체를 없애므로 이 범위의 영향이 작다.
- **측정 제안(코드 없이 실행 가능한 단계)**: 결정 우선 경로를 실제로 만들기 전에 시간을 확인하려면 (a) R-A: 기존 `reply_runs_command` 호출을 단독으로 보내 0.4~0.6초임을 확인(이미 기록에 있음: 0.39초), (b) R-D/R-C: 문장 후보 질문 한 번(질문 8~20개)의 ms를 측정(가짜 후보로, 승인 후 Main이 전송), (c) R-B: 폴더 후보 12개 relevance 호출 1회 ms. 모두 0.3~0.9초 범위일 것으로 예상하나 [추정].
