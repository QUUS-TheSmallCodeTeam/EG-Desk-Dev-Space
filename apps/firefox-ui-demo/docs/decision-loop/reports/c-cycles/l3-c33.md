# L3 사이클 33 — 엔진의 제안/되묻기 등록부 (layer audit c31b ③, A-a / A-e)

브랜치 `lane/c33-proposal-registry` (c32 `47d8356` 위, c32는 int/c14 `cbad751`와 병합 완료). 증거 `evidence/l3-c33/`.

## 1. 무엇을 만들었나 (기본 꺼짐, 새 문구/UI 없음)
플래그 `EGDESK_PROPOSAL_REGISTRY=on` (`decisionContext.proposalRegistry`, Decision 클라이언트가 켜져 있어야 함). 답이 게시되어 run이 `completed`가 된 뒤 백그라운드에서, 그 답이 사람에게 **열어 둔 것**을 정의된 항목으로 등록한다.

| 항목 종류 | 의미 | 예 (오늘의 실제 엔진 답) |
|---|---|---|
| `proposal` | 아직 안 한 일을 제안하고 해도 되는지 묻는다. `steps`(답의 마지막 목록), `options`("A 아니면 B") | conditional-yes T1: 3단계 + "이 순서대로 실행해도 될까요?" |
| `person_request` | 사람이 직접 하거나 알려 줘야 할 것을 기다린다 | "로그인하신 뒤 알려주시겠어요?", journey의 "이 항목들도 모두 처리됐나요?" |
| `waiting_action` | 질문은 없지만 사람이 말한 행동이 사람의 승인을 기다리며 멈춰 있다 | terse-yes T1: "지울 항목은 2개입니다 … 파일은 변경하지 않았습니다" (+ 항목 2개) |

- **코드(R3)**: 후보 span을 찾고(질문 끝 문장 최대 3개, 마지막 목록 최대 8개, "A 아니면 B" 분리, 질문이 없을 때만 마지막 문단) 항목 구조를 만들고 판정을 합친다.
- **Decision(R1, R2, R4)**: span마다 예/아니오 하나. `pq_i`(제안인가), `ph_i`(사람에게 기다리는가), `pw`(보류된 행동인가). 각 span은 따로 인용하고 사람의 요청은 한 번만 따로 인용한다. .8 이상만 항목이 된다.
- **수명**: 새 답이 오면 그 대화의 항목을 대체한다(오래된 제안이 "응"을 가로채지 않게). 60분 뒤 만료. 대기 중인 승인(`broker.awaitingReply`)이 있으면 등록하지 않는다(승인은 장부의 상태). 이그레스가 `run_text`를 막으면 Decision을 부르지 않는다. 하트비트 노트는 답이 아니다.

## 2. L1 해소기와의 접점 (제공자 계약)
**`lane/c32-open-items` 브랜치는 저장소에 없다**(전체 브랜치 검색: 해소기는 `egdesk-context-resolver.mjs`뿐이고 열린 항목 API는 없음. L1의 에이전트 ID도 몰라 Main에게 전달을 요청한다). 그래서 둘째 해소기를 만들지 않고 **제공자 API**만 정의했다.
- `chat.openItemsFor(conversationId)` → `[{ provider, kind, id, text, steps:[{n,text}], options:[{n,text}], runId, answerId, at }]` (모든 제공자의 항목; 호출자가 고쳐도 원본은 안 바뀐다; 예외를 던지는 제공자는 다른 제공자를 막지 않는다)
- `chat.registerOpenItemProvider(name, listFn)`: L1의 다른 제공자(브라우저 과제 `lane/c37-browser-open-items` 등)가 같은 자리에 꽂는다. 내 것은 provider `'proposals'`.
- `chat.closeOpenItem(conversationId, id, outcome)`: 해소기가 "응/아니/~빼고"로 항목을 처리한 뒤 닫는다.
- `chat.proposalRegistryIdle()`: 테스트와 체크가 등록이 끝나길 기다린다.
- 해소기가 쓰는 쪽: 열린 항목이 1개면 "응"의 대상이 정해지고, `steps`가 있으면 "~빼고"는 단계별 질문(R4)이 된다. **그 판단은 이 등록부가 하지 않는다.**

## 3. 테스트 (실제 엔진 답으로)
`helper/egdesk-open-proposals.test.mjs` 12건. 답은 오늘 Main의 실제 기록(check-2b, 6, 20jm, 26bl, 20ba)에서 가져왔고, 가짜 Decision은 인용된 span의 **내용**으로 답한다(span을 잘못 인용하면 테스트가 실패).
- conditional-yes → proposal 1개 + 3단계; terse-yes → waiting_action + 2항목; 로그인/스위치 handover → person_request(단계 없음); journey → person_request.
- 음성: 단순 진술 답, 사람이 "ㅇㅇ" 한 뒤의 답, Decision이 .5/.79를 낸 경우 → 항목 없음.
- 런타임: 플래그 켬 → 등록, `openItemsFor`/`closeOpenItem`, 새 답이 대체, 만료, 제공자 예외 격리; 플래그 끔 → Decision 호출 0; 이그레스 닫힘, 대기 승인 → 호출 0.
- **변이 11건 전부 검출**(기준선 낮춤, span에 단계까지 인용, 요청에 단계 부여, 문단 항상 후보, 첫 목록 사용, 대체 안 함, 플래그 무시, 이그레스 무시, 만료 무시, 제공자 예외 전파, 장부 무시).
- 실제 엔진 체크: 스크립트 `real-engine-proposal-registry-v1`(conditional-yes, terse-yes 두 대화, `--decisions` 필요). 새 훅 `proposals`(`expect.proposals {kinds, stepsAtLeast, optionsAtLeast, none}`)가 매 턴 뒤 항목을 기록한다. 플래그는 브리지, 체크 구성, all-on 미러에 모두 배선했다.

## 4. 등록 질문의 드라이런 계획 (Main이 전송)
`evidence/l3-c33/registration-plan/plan.json`: 7요청, **2,712토큰**(ceiling 3,390), 전송 0. 제품이 보내는 본문을 실제 클라이언트로 캡처했다.
- hard: conditional-yes T1 `pq_0 ≥ .8`; terse-yes T1 `pw ≥ .8`; **가드** terse-yes T2(이미 처리됨) `pw ≤ .2`, 끝난 진술 `pw ≤ .2`; 로그인 handover `ph_0 ≥ .8`, `pq_0 ≤ .2`.
- soft(발견용): journey 상태 질문(`ph_0 ≥ .8`, `pq_0 ≤ .2`), A-아니면-B 합성 사례(`pq_0 ≥ .8`), conditional의 `ph_0 ≤ .2`.
- 합성 사례 2개(진술, A-아니면-B)는 표시했다. "A 아니면 B?"의 실제 엔진 답은 아직 기록에 없다. 이 계획의 결과가 문구의 실측이다(문구는 플래그 뒤에서만 쓰인다).

## 5. c32 노트 문구 실측 결과 (c53, 5/6 통과)
- 현재 문구: 원래 표현 .83, V1 표현 .75 → 취약함이 확인됨. 후보 문구("말을 못 듣고 기다리는데 일은 아직 도는가"): 세 표현 모두 1.0.
- **3초 가드도 1.0**이라 hard 기대(≤.2)가 실패했다. 해석: 이 질문은 "지금 노트를 보낼까"가 아니라 "사람이 기다리고 있는가"를 묻는데, 3초 시점에도 그 말은 참이다. 언제 묻는지는 이미 코드(`firstAfterMs` 10초)가 정하므로(R3) 시간 가드를 질문에 넣은 것이 잘못이다. 문구는 출하하지 않았다.
- 다음: 가드를 "약 8초 전에 노트가 나갔는가" 또는 "사람이 방해하지 말라고 했는가"로 바꿔 다시 측정(후속). 후보 문구 자체는 취약성 해소에 유효해 보인다.

## 6. 한계
- 질문 끝 판별(한국어 어미 목록)은 **후보 선정**일 뿐이다. 의미는 Decision이 정한다. 어미 목록에 없는 말투("~할지 알려 주세요")는 후보가 못 되어 놓친다(미탐, 오탐은 Decision이 거른다).
- 등록은 답 게시 뒤 최대 3초 타임아웃의 백그라운드 호출이라, 사람이 3초 안에 "응"을 보내면 항목이 아직 없을 수 있다(그 경우는 지금과 같이 엔진이 처리).
- 하나의 답에서 질문이 여러 개면 최대 3개, 단계 목록은 마지막 목록 하나뿐이다.
- 승인 질문(force push 등)은 장부가 쥐고 있어 등록하지 않는다(중복 방지).
