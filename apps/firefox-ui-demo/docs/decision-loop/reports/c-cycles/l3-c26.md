## 2. 한 일

**(a) why-stopped** (`96f716e`): 둘째 턴에 `postedMin: 2`(답 + 최종 답)와 `engine.flowMessages {min: 1}`(시스템 자신의 메시지)을 요구한다. 더는 최종 답으로 통과하지 못한다. 스크립트 테스트는 L5의 검증기와 키 목록을 쓴다.

**(b) 실시간 상태 증거** (`8db95ff`, Main 결정: 문구와 기준은 그대로):
- `liveRunLines`(메시지 증거에만 들어가고 beat 질문의 자료는 그대로): "As of now the run is still in progress: the assistant began working N seconds ago. Nothing has finished it." 그리고 EG-Desk 자신의 명령 실행기가 명령을 실행 중이면 "the command `…`, started N seconds ago, and the command has not finished yet." 명령줄은 실행의 egress가 `terminal_command`를 허용할 때만 들어간다. 끝난 run, 끝난 단계, 다른 도구는 아무것도 말하지 않는다.
- `egdesk_run_command` 호출을 보낼 때 명령을 run에 기록하고(`run.ownCommandRunning`) 조건 기록이 지운다.
- 게시 결과의 닫힌 단어 `write`(passed, no_fork, writer_failed, writer_empty, repeat, no_turn, check_failed, check_timeout, run_moved_on, not_postable)를 `conversation_flow` 행에 넣었다. L5의 `flowRows`가 그대로 옮긴다. 다음 기록에서 "작성기가 못 썼나, 점검이 막았나"가 한 줄로 보인다.
- 테스트: check-6 재현(fork 거부 → 새 스레드, 내용을 읽는 모의 판정): 올바른 글은 게시되고 증거에 실시간 줄이 있다. **"이미 끝났어요"라는 거짓 글은 명령이 도는 동안 계속 걸린다**(`check_failed`, 안전 기본값으로 run에 전달). 작성기가 빈 글이면 `writer_empty`. 변이 10건이 잡혔다.
- 하트비트 계획 바이트 테스트: `wait-check-*` 3건의 본문이 바뀌어 사유와 함께 등록했다.

**(c) pause 스크립트** (`96f716e`): 제품이 이제 명령을 멈춘다. 셋째 답이 "`cleanup-finished` 출력은 확인하지 못했어요"라고 말한 것을 일반 `answerExcludes`가 주장으로 읽었다. 중요한 것은 코드로 고정했다: 첫 턴에 `engine.commandStopped`(명령이 끝난 것이 아니라 신호로 종료됨), 셋째 답은 출력 블록(```` ```text\ncleanup-finished ````)으로 결과를 보고하지 못한다. 약화가 아니라 사실 검사가 늘었다. 남는 한계: "끝났다"는 말투의 주장 자체는 코드로 일반 탐지가 안 된다. check-6의 거짓 주장(계속 실행되고 있었다)은 `commandStopped`가 잡는다.

**(d) HIGH: 기억 있는 턴의 미지원 문장 규칙** (`3cf2648`): L2 확인대로, 턴 메모리가 붙으면 점검의 증거에 기억 쪽 `ctx` 불투명 참조가 하나 있고, 불투명 항목이 하나라도 있으면 미지원 문장은 무시된다. 그래서 기억이 있는 턴에는 tense만 걸 수 있었다.
