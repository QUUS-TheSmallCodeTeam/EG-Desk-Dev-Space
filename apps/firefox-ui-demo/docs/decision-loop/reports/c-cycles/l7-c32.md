# L7 c32: 엔진이 additionalContext를 자르는 문제 (spill): 스키마, 설계, 증명, 재실행

기준: int/c14 = ff4c519. 실제 엔진은 돌리지 않았습니다 (Main 실행).

## 1. 스키마에서 무엇이 적용되는가 (`evidence/codex-0171-schema/codex_app_server_protocol.v2.schemas.json`)
- spill 한도는 **훅 핸들러에만** 있습니다: `ConfiguredHookHandler.additionalContextLimit` ("이 훅의 `additionalContext`를 디스크로 spill하는 대략적 토큰 임계값. `null`이면 2,500, `0`이면 해제. 임계값은 **원본 컨텍스트** 기준이고, spill된 미리보기에는 복구 메타데이터가 포함됨")와 `HookMetadata.additionalContextLimit`.
- `TurnStartParams.additionalContext`(와 `TurnSteerParams`)는 "client-provided context fragments keyed by an opaque source identifier"일 뿐 **한도 매개변수가 없습니다**. `AdditionalContextEntry`는 `kind`(`untrusted` | `application`), `name`(untrusted 전용, "tool output 라벨"), `value`뿐입니다. `Config` 객체의 키(analytics … web_search, `model_context_window`, `model_auto_compact_token_limit` 등)에도 이것과 관련된 것이 없습니다. 바이너리 문자열에는 훅 출력용 `hooks/src/output_spill.rs`와 "Full hook output saved to:"가 있습니다.
- 결론: **EG-Desk가 자기 turn/start 항목의 한도를 스레드 단위로 올리거나 끌 방법이 스키마에는 없습니다** (pure-engine overrides에 넣을 키가 없음; L5에게 알림). 실제 실행에서는 그 한도가 turn/start 항목에도 걸리는 것으로 보입니다 (check-12/13).
- 실측으로 본 규칙 (`check-12`, `check-13` score.txt, 제품이 보낸 크기는 `sizes-per-script.json`): 이 check 구성에서 additionalContext는 사실상 `egdesk_decision_context` 한 항목뿐입니다.
  | 실행 | 항목 크기 | 결과 |
  |---|---|---|
  | held-v4 (실제 통과) | 1,461~1,650자 | 온전 |
  | scale-v1 2턴 | 약 3,291자 | 중간 손실 가능 (본 전환 페이지 마지막 문장의 날짜 없음, 되돌리기 페이지 끝은 있음) |
  | probe n2 | 3,556자 (6,388바이트) | **1번 문서 첫 문장과 2번 문서 끝만 보임**, "중간 내용이 생략되어 있어", 원문 조회 거절 |
  | probe n4/n6/n8, scale 1턴, v2 1턴 | 6k~11k자 | 앞 한 문장과 맨 끝 몇 개만 보임 |
  → 한도는 **항목 하나당 약 2,500~3,300자 사이**(1.6k는 통과, 3.3k는 잘림)로 보입니다. 한글 3.5k자(≈6.4k바이트)가 이미 잘렸으므로 **바이트/4 추정(≈1.6k 토큰)이 아니라 글자 수(또는 그에 가까운 추정)로 세는 것**처럼 보이지만, 항목당인지 합계인지, 글자인지 바이트인지는 이 데이터로 구분되지 않습니다 (check에서는 항목이 하나뿐). 그래서 probe v2를 만들었습니다.

## 2. 설계: 한도를 끄지 못하니 항목을 한도 아래로 나눈다 (`helper/egdesk-engine-context.mjs`)
- 선택: **나누기(split)**, 총량 예산 아님. 이유: 나누기는 모델에게 가는 내용을 하나도 바꾸지 않습니다 (빼거나 고쳐 쓰지 않음). 한도가 항목당이면 이것으로 충분히 해결되고, 합계라면 probe v2의 split 대화가 그것을 보여 줍니다 (그때는 총량 예산이 다음 일입니다: 어떤 항목을 뺄지는 모델이 고른 순서로 정하고 뺀 것은 초안 검사에 안 보인 것으로 알림). 총량 예산은 한도의 범위를 모르는 지금 임의의 값으로 만들지 않았습니다.
- `splitEngineContext(additionalContext, { limit })`: 한도보다 긴 `application` 항목을 `[item id=…]`/`[page id=…]` 경계에서 `key`, `key_part2`, …로 나누어 각 부분이 한도 이하가 되게 합니다 (순서 유지, 이어짐 줄 한 줄 추가, 부분을 이어 붙이면 원문과 byte 동일: 테스트). 한 블록만으로 한도를 넘으면 그 블록은 혼자 두고 `oversize`로 보고. `untrusted` 항목과 한도 이내 항목은 그대로.
- 플래그 (개발자 플래그, 기본 꺼짐; 기존 turn memory 플래그 배선에 올려서 check 구성이 자동으로 따라옴): `EGDESK_TURN_MEMORY_ENGINE_CONTEXT=split|mark`, `EGDESK_TURN_MEMORY_ENGINE_CHARS=<n>` (기본 2000, 400 미만은 무시). `mark`는 항목을 그대로 보내고 초안 검사에만 "다 보이지 않음"이라고 알립니다 (비교용).
- 런타임 (`codex-chat-runtime.mjs`): 전송 직전 `shapeEngineContext()`가 최종 additionalContext를 나눈 것으로 바꿔서 `engine.startTurn`에 넘깁니다. 영수증, 병합, 가지치기 등 앞 단계는 그대로입니다.
- 스키마 검증된 가짜 엔진: 가짜 app-server는 모든 클라이언트 요청을 0.171 스키마로 검증하므로 (잘못된 additionalContext면 실행이 3으로 끝남) 나눈 항목들이 스키마에 맞는다는 증명이 됩니다. 엔진의 자르기는 `emulateSpill()` (머리와 꼬리를 남기고 가운데를 표지로 바꾸는 시험용 대역: 실제 미리보기 모양은 모르고 "머리와 꼬리가 남는다"만 가정)로 시험합니다.

## 3. 증명 (가짜 엔진, 변이 확인 포함)
- 단위 (`egdesk-engine-context.test.mjs`): 나눔은 경계에서, 부분 합 = 원문, 한도 이하, 큰 블록 보고, 대역이 가운데를 잃고 나눈 것은 그대로 보임, 합계 범위 대역은 나눈 것도 자름.
- 런타임 (`egdesk-engine-context.test.mjs` scripts): off = 한 항목이 한도를 넘고 대역이 가운데 항목을 잃음; **mark** = 같은 바이트, 초안 검사의 항목 증거가 모두 opaque 하나로 바뀌고 메모리 항목은 비움; **split** = 부분이 모두 한도 이하, 이어 붙이면 off와 같은 텍스트, 대역이 아무것도 자르지 않고 항목이 모두 보임, 초안 검사의 증거는 off와 같음.
- 실행 대본 (`egdesk-real-engine-memory.test.mjs`): split-n8을 가짜 엔진으로 돌린 요청: 키 8개 이상, 각 2,000자 이하, 대역이 자르지 않고 여덟 페이지 앞뒤가 모두 보임. 플래그만 빼면 한 항목이 되어 대역이 일부 페이지의 마지막 문장을 잃음.
- 변이: `shapeEngineContext`를 끄면 이 세 테스트가 실패 (`mutation-check.txt`).

## 4. 초안 검사가 "답하는 모델이 본 것"과 맞도록 (L3)
- 엔진이 자르는 항목(`mark` 모드 또는 한 블록이 한도를 넘는 `split`의 부분)은 답하는 모델이 일부만 본 것이므로, `noteDraftCheckTurn`이 새 선택 인자 `spilled`(키 집합)을 받아 그 키의 항목 증거를 비우고 opaque 참조 하나로 바꿉니다 (one packet이면 메모리 키도). `split`에서는 아무것도 잘리지 않으므로 증거가 그대로입니다. 플래그가 꺼져 있으면 집합이 비어 아무것도 변하지 않습니다. L3에 알렸습니다 (`memoryKeyCovered`와 `memN` id는 건드리지 않음).
