## 2. 재설계: `split-isolated` (`helper/egdesk-speech-grounding.mjs`)

R1–R4를 따랐습니다. 구분할 수 있는 라벨은 따로 떼어 낸 yes/no 질문으로 바꾸고, 합치는 건 코드가 합니다 (R3). bar는 낮추지 않았습니다.

### 질문

- **source** (4개):
  - `other`: 다른 사람, 팀, Agent에게서 온 정보라고 말하는가
  - `own`: 문장 자체가 본인이 직접 보거나 듣거나 확인하거나 해 봤다고 말하는가. 어떻게 아는지 말하지 않는 사실 진술은 no
  - `record`: 기록, 로그, 메일, 메시지, 메모, 공지, 보고서, 문서처럼 읽은 출처를 대는가
  - `guess`: 아는 것이 아니라 추측, 예상, 결론으로 말하는가
- **time** (5개):
  - `before`: 이미 일어난 일인가 (계속되는 중이라고 한 것은 제외)
  - `now`: 말하는 순간의 상태나 의견인가
  - `ongoing`: 한동안 계속되어 지금도 이어진다고 분명히 말하는가
  - `after`: 계획, 제안, 요청, 예보, 마감처럼 이후의 일인가
  - `when`: 날짜, 요일, 시각, 또는 상대 시간어(어제, 방금, 아까, 오늘 새벽, 지난주 화요일, 다음 달, 금요일)를 주는가. "언젠가", "예전에", "나중에"는 no. 날짜 계산은 하지 않습니다.
- **form**: 기존 axes 질문을 그대로 씁니다 (75%였고, 이번 범위가 아님).
- 문장이 하나뿐인 메시지에서는 문장을 다시 인용하지 않고 `The message is a single sentence; judge it.`로 묻습니다. predicate 하나에 고정 비용이 약 135 토큰 들어서, 문장을 9번 인용하면 요청이 두 배가 되기 때문입니다. 문장이 여럿이면 기존 isolated 설계처럼 문장마다 인용합니다.

### 코드 결합 (`splitLabels`)

| 축 | yes인 것 | 결과 |
|---|---|---|
| source | 정확히 하나만 yes, 나머지는 모두 decided no | 그 라벨 |
| source | 넷 다 decided no | `unspecified` (근거 없음. 보기로 주지 않고 코드가 도출) |
| source | 여럿이 yes, 또는 undecided가 있음 | `unknown` |
| time | {now} | `at_utterance` |
| time | {ongoing} 또는 {ongoing, now} | `ongoing_no_end` |
| time | {before} 또는 {after}, 그리고 `when`이 decided | `past_*` / `future_*` (when이 yes면 `_anchored`, no면 `_unspecified`) |
| time | 그 밖 (없음, 둘 이상, undecided) | `unknown` |

- 임계값은 `SPEECH_SPLIT_BARS`입니다. yes는 ≥ `SPEECH_THRESHOLDS.confidence`(.85), no는 ≤ .15이고 그 사이는 undecided입니다. .80으로 낮추는 대안은 L6 데이터에서 틀린 설치를 늘렸으므로 쓰지 않았습니다.

### 선택 방식

- `WRITE_SPEECH_DESIGNS = ['axes-isolated', 'split-isolated']`. 기본값은 `axes-isolated`이고, 이때 `judgeTurnWrite` 요청은 바이트 단위로 같습니다 (테스트로 확인).
- `split-isolated`는 `judgeTurnWrite({ speechDesign })`, `prepareTurnMemory({ speechDesign })`, `turnMemory.speechDesign`으로 고르고, 개발자 플래그 `EGDESK_TURN_MEMORY_SPEECH_DESIGN=split`(기본 off)로 켭니다.
- 턴 단위 `SPEECH_DESIGNS` 목록에는 넣지 않았습니다. write judgment 전용입니다.

## 3. 재측정 플랜 `axis-split-v1` (`proofs/decision-real-measure/axis-split/`)

### 캡과 대상 집합이 충돌해서 줄였습니다

- 요청하신 집합은 "source나 time이 .85에서 설치되지 않은 문장"인데, 이게 **55개**입니다. 두 축 모두 설치된 문장은 5개(c01, c02, c10, c11, c38)뿐입니다.
- 문장 하나를 제품 본문 그대로(두 축, form, tw_status 포함) 묻으면 split 설계로 약 2,900 est 토큰입니다. 55개면 약 160k로 25k 캡을 크게 넘습니다.
- 그래서 아래 기준을 **요청을 만들기 전에** 정하고 그대로 골랐습니다. 대상을 다 덮는 측정은 결정 2로 넘깁니다.

### 선택 기준 (모듈 머리 주석에 고정)

1. **단위**: 요청 하나에 문장 하나, 축 하나입니다.
   - 입력은 그 문장에 대한 제품의 write-judgment 입력 그대로입니다 (`judgeTurnWrite`, 'about', 저장 기록 없음, study 시계).
   - 질문은 그 축의 제품 split predicate만 넣었습니다. 제품이 만든 객체를 순서 그대로 쓰고, 빌더가 제품 출력과 같은지 확인합니다.
   - tw_status와 form은 묻지 않습니다. 둘 다 이번 측정 대상이 아닙니다.
2. **targets** (11개): 명확한 축(허용 라벨이 unknown만인 경우가 아님) 가운데 .85에서 설치되지 않은 것을, study에서 본 실패 유형마다 한두 개씩 골랐습니다.
   - source: c20, c15 (맨 계획/질문), c26, c30 (.80에서 틀림), c22 (메일), c12 (inference .78)
   - time: c32 ("방금"), c07 (ongoing), c37 (.80에서 틀림), c30 (wrong top), c08 ("지금")
3. **guards** (4개): 일부러 모호하게 만든 축이라 어떤 라벨이든 설치되면 틀린 것입니다. source a09, a14 / time a13, a16. study에서는 넷 다 틀린 라벨이 bar 아래 최상위였습니다.
4. **controls** (6개): study에서 .85로 맞게 설치된 축입니다. source c01 (own), c02 (other), c10 (record) / time c01 (past_anchored), c04 (future_anchored), c26 (past_anchored, "작년 이맘때").

## 4. 명령 실행 요청의 relevance 문구 (c19 결정 4): `action-relevance-v1`

- **문구**: `egdesk-context-setup.mjs`에 `CONTEXT_RULE_SETS = ['default', 'action']`을 추가했습니다.
  - `action`은 규칙 한 줄을 더합니다: "An item is needed only when the response has to use what the item says. A request to carry out an action (run, build, test, deploy, open, send) needs an item only when the item is about that very action (its procedure, target or expected result); records of other work are not needed because they are recent or belong to the same project."
  - 질문은 바꾸지 않았습니다. 기본 rules는 바이트 단위로 같습니다.
  - 켜는 방법: `prepareTurnContext({ ruleSet: 'action' })`, 런타임은 `decisionContext.relevanceRules === 'action'`일 때만 넘깁니다. bridge와 harness는 개발자 플래그 `EGDESK_CONTEXT_RELEVANCE=action`(기본 off)에 연결했습니다.
- **플랜** (`proofs/decision-real-measure/action-relevance/`, 2개 요청, **4,299 est**, ≤ 5k):
  - 두 요청 모두 all-on journey 안에서 제품이 만든 본문이고, `productBars`는 `rel_#` { yes .5, no .49 }입니다. 선택은 ≥ .5에서 붙이므로 그대로 적었습니다.
  - `s4-action`: **실제 v3 s4 본문과 비교하면 rule 한 줄 말고는 같습니다** (model, input, questions, prompt_cache_key 모두 같음. `evidence/l7-c20/s4-vs-real.txt`). 그래서 이전 실제 답(배포 계획 .56, 헬스체크 .69)과 바로 A/B가 됩니다. HARD: 12개 모두 < .5.
  - `s3b-control`: 설계 질문에 rule을 켜고 held pruning도 켰습니다 (7개). HARD: "PostgreSQL 전환 설계"가 여전히 ≥ .5 (실제 v3에서 1.0). rule 때문에 필요한 기록이 빠지는지 보는 대조군입니다.
- **한계**: 이 문구는 **selection만** 다룹니다. v3 s4에서는 turn memory도 무관한 페이지를 붙였습니다 (triage need .99 → scan .87). soft `s4.no-unrelated-pages`가 통과하려면 그쪽도 필요합니다 (결정 4).
