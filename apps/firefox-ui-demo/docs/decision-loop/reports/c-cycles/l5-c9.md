# L5 / C9 — `engine_commands` heartbeat 제공자를 c12 계약에 맞춤

브랜치 `lane/c9-command-facts-on-c12` (기준 `int/c12` = 2ad24e5), 커밋 `8b1be5b`, `6423499`. 증거 `evidence/l5-c9/` (`gate.out`, `c12-message-request.json`). 가짜 transport·가상 시계·mock 모델만 사용.

## 1. 실패 원인
`helper/egdesk-engine-command-wiring.test.mjs:123`은 "명령이 없으면 heartbeat의 제공자 목록이 `[]`, 명령이 시작되면 `['engine_commands']`"라고 단언했다. c11에서는 대화 흐름이 `setSource`만 썼기 때문에 맞았다. **c12에서는 대화 흐름 자신이 같은 heartbeat에 제공자 두 개(`audience`, `message`)를 등록한다**(`codex-chat-runtime.mjs:4867-4868`). 그래서 실제 목록이 `['audience', 'message']`가 되어 첫 단언에서 실패했다.
- 제품 코드의 등록 자체는 c12에서도 동작했다(`hb.register(name, fn)`와 `hb.subscribe`는 c12 계약에 그대로 있다). 깨진 것은 "이 heartbeat에는 내 제공자만 있다"는 시험의 가정이다.

## 2. 변경
- `codex-chat-runtime.mjs` `feedCommandHeartbeat`: c12 계약의 객체 형태로 등록 — `hb.register('engine_commands', { facts })`. 이 기능은 박동에 낼 질문이 없으므로 `propose`/`onVerdict`는 없다. 박동은 계약 3번(`hb.subscribe`)으로 받는다. 추가로, heartbeat가 가득 차 등록이 거절되면(제공자 상한 8) "등록됨"으로 기억하지 않고 다음 명령에서 다시 시도한다(이전에는 거절돼도 등록된 줄 알았다).
- 형태는 그대로 하나(`terminalFactRow`).
- 시험(단언 약화 없음): 내 제공자가 정확히 하나만 추가되고 다른 제공자는 그대로임을 검사한다 — 명령 전에는 `engine_commands` 없음, 명령 후 목록이 `[...기존, 'engine_commands']`와 정확히 같음, 두 번째 명령 뒤에도 같음, 플래그 없는 같은 heartbeat는 `기존`과 같음. 다른 lane의 제공자 이름은 고정하지 않았다. 나머지 단언(phase, 행 값, 요청 1회, 완료 후 값)은 그대로다.

## 3. c12에서 명령 사실이 메시지 판정에 도달하는가 — 아니오
c12의 박동 요청은 (a) 공통 세션 줄(`egdesk-heartbeat-judge.mjs:21` `sessionLines`: 경과 시간, `current_phase`, `tool_steps_done/running` 등 집계값)과 (b) 각 질문의 자체 facts로 구성된다. 메시지 질문의 facts는 `egdesk-conversation-flow.mjs:135` `flowQuestion`이 만들며 `beat.facts.sources`를 읽지 않는다. L3의 실제 모듈로 요청을 만들어 확인했다(`c12-message-request.json`): `sources.engine_commands`에 `runningMs: 20000`, `terminalState: 'running_output'`이 있어도 요청에는 `current_phase: tool_running`, `tool_steps_running: 1`만 나오고 명령 시간·판정 상태는 없다.
- 지금도 간접 효과는 있다: 명령이 도는 동안 phase가 `tool_running`이라 `stalled` 선택지가 나오지 않고 `explain_wait`가 열거된다. 그러나 "테스트가 20초째 돌고 있고 출력이 20초 전"이라는 사실은 판정에 없다.

### 내 쪽에서 한 것
`helper/egdesk-engine-command-watch.mjs`에 `commandQuestionFacts(row)` 추가: heartbeat가 주는 행을 질문 facts 규칙(숫자·불리언·닫힌 라벨, 키 `/^[a-z][a-z0-9_]{0,63}$/`)에 맞는 값으로 바꾼다 — `command_running`, `commands_finished`, `commands_failed`, `command_running_seconds`, `seconds_since_command_output`, `command_state`. 행이 없으면 `{}`. 실제 heartbeat 한 라운드와 실제 `beatRequest`로 시험했다: 화이트리스트가 값을 하나도 버리지 않고, 요청 본문에 `command_running_seconds: 20 / seconds_since_command_output: 20 / command_state: running_output`이 나오며 출력 텍스트는 없다.

### L3가 바꿔야 할 것 (정확히)
`egdesk-conversation-flow.mjs`는 L3 모듈이라 손대지 않았다. 두 줄이면 된다.
1. `beatFlowFacts` (`:84`)의 반환 객체에 `command: heartbeatFacts.sources?.engine_commands ?? null` 추가.
2. `flowQuestion` (`:135`)의 `facts`에 `...commandQuestionFacts(facts.command)` 펼침 추가(`import { commandQuestionFacts } from './egdesk-engine-command-watch.mjs'`). 질문 facts는 현재 6~9개, 추가 6개로 상한 24 안이다. 새 egress kind는 필요 없다(숫자·라벨뿐인 run 사실, `run_facts`).
- 메시지 **문장**까지 "테스트가 아직 도는 중"이라고 쓰게 하려면 `writerPrompt` (`:171`)에도 같은 사실을 넘겨야 한다. 이것도 L3 결정이다.
- 더 일반적인 대안: `sessionLines`가 `facts.sources`의 모든 행을 줄로 내보내면 모든 제공자가 혜택을 본다. 다만 모든 질문이 그 줄을 보게 되므로 L3가 판단할 일이다.
