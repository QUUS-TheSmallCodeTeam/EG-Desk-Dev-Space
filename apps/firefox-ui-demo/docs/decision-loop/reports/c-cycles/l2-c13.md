### 회상 단계 s3b-recall (s3 다음)

- 질문: **"PostgreSQL 전환은 설계에서 어떻게 하기로 정했었지?"**
- 필요한 자료는 `ontology:db/pg-design`("설계를 확정했다", 11-12)입니다. 이 시점의 대화는 A사 페이지만 가지고 있습니다.
- **s2 바로 뒤가 아니라 s3 뒤에 두었습니다.** s3 브리핑은 직전 답을 대상으로 합니다. s2 뒤에 넣으면 s3가 회상 답을 브리핑하게 되어 c16과 비교할 수 없습니다. "s2 이후 A사 대화 안"이라는 조건은 지킵니다.
- 합성 페이지에 지난달 날짜가 없어서 질문에 "지난달"은 넣지 않았습니다.

| ID | 등급 | 담당 | 기대 | 예측 |
|-|-|-|-|-|
| s3b.fetched | hard | L7 | 설계 페이지가 묶음에 들어감(A사 페이지는 다시 오지 않음) | 통과 예상: 가진 페이지가 A사뿐이라 need 질문("가진 페이지가 이미 다루는가")이 yes. 위험: s2가 여전히 PostgreSQL 페이지를 붙이면(c16), 그것이 이미 다룬다고 판단되어 L7의 회상 규칙이 조회를 건너뛸 수 있음 |
| s3b.no-repeat | hard | L7 | 이미 보낸 페이지를 다시 보내지 않음 | 통과 |
| s3b.own-words | hard | L3 | 설계 페이지에 근거한 답이 쓴 그대로 게시됨 | 위험: c16에서 현재형 술어가 사실 문장마다 걸림. L3 c18 미머지 |
| s3b.triage-need | soft | L7 | need가 .8 이상 | 처음 측정 |
| s3b.triage-recall | soft | L7 | recall 값 기록(기준 없음) | 처음 측정 |

triage 값은 질문 이름이 아니라 보정 기록의 단어(`turn_memory` 항목의 `triage_need` / `triage_recall`)로 읽습니다. 그래서 질문 모양이 바뀌어도 계획을 고칠 필요가 없습니다. 대조용으로 s2에도 soft 두 개를 넣었습니다: `s2.triage-need`(.3 이하, c16은 0)와 `s2.triage-recall`(기록, c16은 .96).

### 대본 주관식 모델이 제품이 준 것을 따르게 함 (측정 충실도)

- **기록 규칙**: 턴에 `egdesk_recording`이 실리면 기록을 약속하지 않습니다("네, 알겠습니다."). 그래서 v2 `s9.claim-backed`는 이제 규칙이 Agent에게 닿았는지를 재는 기대가 됩니다.
- **작업 메모의 선택지**: 질문에 메모의 후보를 그대로 붙입니다.
- **대기 안내**: 프롬프트가 준 대기 이유("a command is still running")로 "명령이 아직 실행 중이라 조금 더 걸리고 있어요."라고 씁니다.

## 2. 드라이런 중 찾은 제품 문제 (L7)

v3 드라이런에서 v1의 `s9.reading`이 실패했습니다. 대본 판정기 탓으로 보였지만 요청 본문을 보니 코드 문제였습니다.

- `judgeTurnWrite`는 후보를 **앞에서 8개만** 씁니다(`maxCandidates = 8`). 순서는 이번 턴에 고른 페이지 다음에 이미 가진 페이지를 **보낸 순서대로** 붙입니다.
- 회상 단계 뒤 s9의 후보: 헬스체크, 롤백, A사 5개, 전환 설계 = 8개.
- s3b부터 가지고 있던 **마이그레이션 계획 페이지는 9번째라 잘립니다.** "배포 끝났어"를 그 페이지에 기록할 수 없습니다. 모델이 무엇을 답하든 마찬가지입니다.
- v2 여정(회상 단계 없음)에서는 그 페이지가 첫 번째라 문제가 드러나지 않았습니다. 세션이 길어지면 생기는 문제입니다.
- 계획에는 `s9.target-offered`(soft, L7, 실패 예측)로 넣었습니다. 사람에게 보이는 결과는 v1의 `s9.reading`입니다.

## 3. `--rerun` diff: v3와 c16 비교

```
node scripts/egdesk-all-on-live-measure.mjs --rerun $L/evidence/main-real/c16-all-on-journey.json --out new.json        # 재생, 보내지 않음
```

- `--rerun`은 이제 최신 계획(v3)이 기본입니다. v2로 돌리려면 `--plan …plan-v2.json`을 주면 됩니다.
- **계획마다 단계 목록이 다릅니다.** `since`가 없는 핵심 단계 11개는 모든 계획에 있어야 하고, 나중에 더한 단계는 넣어도 되며, 순서는 여정 순서를 따라야 합니다. 실행은 계획에 있는 단계만 돕니다. 그래서 v1/v2 실행은 이전과 같습니다(회상 단계 없음).
- **앞 실행에 없던 단계는 "새 단계"로만 나옵니다.**
  - 머리 줄은 `== s3b-recall [new in this plan, done]`입니다. 요청 종류만 요약하고, 기대는 모두 `new -> …`입니다.
  - 요청 수·답·본 것의 "변화"나 앞 실행의 실패로는 나오지 않습니다.
  - 재생일 때는 그 단계의 답이 대본이므로 기대 판정 옆에 "[not a model result]"를 붙입니다.
- 증거 `replay-c16-v3.txt`에서 실제 c16 파일과 비교해 확인했습니다. 테스트로도 고정했습니다(v1 계획으로 만든 앞 실행 대비).
