# L8 / C9 직접 브라우저 진입의 챗 런타임 연결 (flag 기본 off, advisory 먼저)

브랜치 `lane/c9-browser-entry-wiring` (base int/c7 0020b10), 커밋 `1357e56`. 합성 검증만(CodexChatRuntime 하네스 + 실제 provider/Browser service + UI 대역 + mock Decisions). 실제 Firefox·네트워크·codex 없음. 기본값은 전부 off이며 어떤 호스트 설정도 켜지 않았다.

## 1. 설정과 모드
`decisionContext.browserEntry = { mode(): 'off'|'advisory'|'on', hosts?, memory?({ body, context }) → { packet, pages, scope }|null, outcomeSink?(candidate, { memoryPages }) }`. 없거나 다른 값이면 off(`browserEntryMode()`). off에서는 Decisions 호출·바인딩·네이티브 입력 어느 것도 바뀌지 않는다.

## 2. 구현 (`codex-chat-runtime.mjs` +95, provider +32, service +18)
- **advisory**: 네이티브 턴이 dispatch되고 `bindRun`이 끝난 뒤 L7의 `startTurnMemoryAdvisory`와 같은 자리에서 백그라운드로 작업 하나(`startBrowserEntryAdvisory`)를 시작한다. 허용된 interact 카드를 열거해 진입 결정 요청 1건(`browser_entry`)만 보내고, 결과(`enter` / `not_browser` / `ask_user` / `uncertain` / `fallback`)를 메모리 내 shadow(`browserEntryShadow`, 최대 50)와 내용 없는 calibration 항목(`feature: 'browser_reflex'`, `mode: 'advisory'`, `attached: false`, 숫자와 닫힌 단어만)으로 남긴다. 브라우저 동작 0, 네이티브 입력 변경 0, 턴을 기다리게 하지 않는다. 게이트: 결정 모델 키와 mode, provider의 reflex 게이트.
- **on**: 제한된 브라우저 턴(BROWSER_BOUNDED + interact 선택)에서 `engine.startTurn` 직전에 `runBrowserEntryOn`이 c7 제안대로 동작한다.
  1. 조용한(`quiet`) pre-run 객체로 provider `bindRun`(Activity는 발행하지 않음). 선택 토큰은 UI에서 한 번 쓰이므로(`eg-desk-surface.uc.js` cancel에서 토큰 삭제, `usedRunId` 고정) 두 번 바인딩할 수 없다.
  2. `createDirectBrowserEntry().handle()`이 진입 결정 -> 객관 루프를 실행(c8의 `memory`/`outcomeSink` 훅 포함). 실패는 모두 "일반 턴"으로 처리.
  3. 닫힌 노트가 있으면 네이티브 `additionalContext`에 **새 키 하나** `egdesk_browser_task`(`kind: 'application'`)만 추가. 사용자 메시지 텍스트·ID·옵션은 그대로.
  4. 턴의 run이 만들어지면 같은 바인딩을 인수한다: `service.adopt(preRun, run)`(바인딩 이동, UI에는 원래 runId 유지), `provider.adoptRun`(transport 등록, `browserBinding` 복사, `adoptedFrom` 기록). `cancelRun`은 두 id를 모두 해제한다. 네이티브 턴이 실패하면 pre-run 바인딩을 취소한다(유출 방지).
- **`bounded ? {}` 규칙**은 그대로 두고 `startTurn` 직전 한 곳에서만 `turnAdditionalContext`로 노트를 합친다. 노트가 없으면 기존과 같은 객체가 그대로 전달된다.
- **L7 `turnMemory`와의 조정**: L7 advisory는 `!bounded` 턴에서만 도는 제한된 브라우저 턴에는 아직 돌지 않는다. 그래서 브라우저 진입은 기억 가져오기를 스스로 하지 않고 호스트가 주는 `browserEntry.memory` 훅(그 턴의 한 번의 fetch)을 소비한다. L7이 bounded 턴에도 fetch를 돌리면 같은 결과를 이 훅에 넘기면 된다(중복 fetch 없음). 두 advisory는 서로의 입력을 바꾸지 않고 독립적으로 기록한다.

## 4. 한계와 실제 Firefox에서 확인해야 할 것(합성 검증으로 주장하지 않음)
- UI 쪽 가정: 바인딩이 pre-turn runId로 계속 UI에 전달되어도 서피스가 그 id로 만든 이벤트·취소·lease를 문제없이 처리하는지(`usedRunId` 고정과 `browserToolCancelledRuns` 키가 run id 기준). 합성 UI 대역은 이를 흉내낼 뿐이다.
- `on`은 객관 루프가 끝날 때까지 네이티브 턴 시작이 늦어진다(최대 구간 6단계 x 단계 결정 지연). 사용자에게 보이는 대기 표시는 만들지 않았다(복사 승인 필요).
- 기억 packet(`memory` 훅)은 호스트가 공급해야 하며 기본 설정에는 연결하지 않았다. 결과 기록(`outcomeSink`)도 마찬가지다.
- 기본값은 off이며 이 브랜치는 어느 모드도 켜지 않는다. 사용자에게 보이는 새 문구나 기능 이름은 없다.

## 6. 철학 점검
"확률은 실행 권한이 아니다": advisory는 결정을 기록만 하고 동작하지 않으며, on도 후보 필터·분류기·URL 정책·revision 검사를 그대로 거치고 제출·결제·권한·삭제는 사람에게 남는다. 기본 off, 실패는 항상 일반 턴.
