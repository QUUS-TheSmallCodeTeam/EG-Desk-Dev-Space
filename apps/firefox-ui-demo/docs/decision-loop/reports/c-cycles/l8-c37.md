## 2. 브라우저 슬라이스 (`fa38d13`)
`helper/egdesk-browser-open-items.mjs`, 플래그 `EGDESK_BROWSER_OPEN_ITEMS`(기본 꺼짐). 새 문구와 새 UI 요소 없음(엔진은 닫힌 노트를 읽음).
- **항목(코드가 등록):** 대화당 살아 있는 작업 하나. 상태: `waiting`(물어봄), `handed_over`(로그인, 코드, 사람 전용 컨트롤, 결제 등 사람의 단계), `stuck`(그 밖의 중단), `running`. 요약은 코드가 만든 닫힌 문장 ≤300자: 요청 원문(120자), 상태, 코드, 단계 수. 페이지 텍스트, 라벨, 주소 없음. kind `browser_task`.
- **옵션과 적용 코드:** `continue`(사람의 단계 후 다음 단계부터 루프 이어감, 사람이 한 말은 맥락으로), `retry`(단계 기억과 예산을 처음부터, 같은 목표와 이미 정한 선택과 사람의 말은 유지), `abandon`(코드가 작업을 취소하고 진행 중이면 중단 신호), `ask_page`(작업은 그대로, 페이지 첫 줄을 노트에 담음: 페이지 텍스트 권한이 있을 때만), `change`(인런 메시지가 켜졌을 때만: 요청 교체). 상태별로 가능한 옵션만(waiting은 retry 없음, running은 abandon과 ask_page).
- **결정(R2, R4, R5):** 옵션마다 예/아니오 predicate 하나(`open_browser_<옵션>`), 메시지를 인용하고 continue와 change는 무엇을 물었는지도 인용, 한 요청. 정확히 하나가 yes(제품의 done 기준 0.85)이고 나머지가 모두 no(0.15 이하)일 때만 적용(`settled`). 모두 no면 `none`(일반 턴, 작업 그대로), 그 밖(둘 yes, 미결정, 중간값)은 `uncertain`: 아무것도 적용하지 않음. 포괄 옵션 없음.
- **적용 시점과 엔진 맥락:** 엔진 턴 전에 코드가 적용합니다(`entry.settle`, 또는 기존 `handle()`의 일시정지 분기: 플래그가 켜지면 resume 판단 대신 이 요청). 엔진은 확정된 상태의 닫힌 노트를 받습니다: continue와 retry는 루프가 끝난 노트(done 등), abandon은 `status: cancelled, settled: abandon, next: tell_user`, ask_page는 현재 상태(`cannot_proceed` 등)와 `settled: ask_page`, `next: answer_user`와 페이지 줄. `none`과 `uncertain`은 노트 없음(이전과 동일).
- **L1 계약(합의함):** `createBrowserOpenItems({ store, entry })` -> `{ id:'browser', items(key) 동기, questions(key, message), read(answers, key, thresholds), apply(ctx) }`; apply는 `{ handled, note?, settled, reason }`. L1의 `oi_ref_<n>`으로 지시 대상이 이 항목일 때만 read/apply를 호출. `handle({ openItemRead })`로 레지스트리가 이미 결정한 읽기를 그대로 적용(자체 요청 없음). 호출 지점은 `EGRESS_SITES`에 등록(`browser_task_record`, `page_text`). 런타임과 브리지 배선: `decisionContext.browserEntry.openItems()` <- `EGDESK_BROWSER_OPEN_ITEMS`.
- **테스트:** `egdesk-browser-open-items.test.mjs` 15건(상태, 항목, 질문, 읽기 규칙 전 경우, 요청 모양, 저장소 active와 retry, 엔진 쪽 continue, retry, abandon, ask_page, 미결정 닫힘, 플래그 꺼짐 동일성과 레지스트리 읽기, 제공자 계약, running 작업) + `egdesk-real-engine-browser-open-items.test.mjs` 3건(5개 대화 x 2턴 종단 간: 진짜 제품 진입과 루프가 티켓 고정 페이지 위에서 돌고, 사람의 단계 후 페이지가 바뀌며, continue는 `/my/bookings/9001`만 이동). 기록된 고정 작업은 c35 티켓 로그인 벽과 c24/c35의 일시정지 상태들.

## 4. 제안과 알려진 한계
1. L1 병합 후 레지스트리가 provider.apply를 부르면 `handle()`의 자체 열린 항목 분기와 중복되지 않게 `openItemRead`를 넘기거나 handle을 건너뛰어야 합니다.
2. running 상태의 abandon과 ask_page는 코드와 테스트가 있으나 선행 턴이 루프를 막고 있어 현재는 인런 메시지 경로(L2)에서만 닿습니다(배선하지 않음, 제안).
3. 최근에 끝난 작업(done)은 열린 항목이 아닙니다(이번 범위 밖).
