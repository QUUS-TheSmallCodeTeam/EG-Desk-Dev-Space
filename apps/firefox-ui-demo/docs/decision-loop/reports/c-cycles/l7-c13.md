## 1. 결론: 테스트 가정이 아니라 제품 로직의 경합

게이트에서 실패한 `helper/egdesk-turn-memory.test.mjs:419` 는 테스트가 느려서 실패한 것이 아니다. 기한이 지난 뒤 자료 인출이 시작되어 묶음이 붙는 실제 경합이었다.

원인 위치 (`int/c11` 기준):

| 위치 | 내용 |
|-|-|
| `helper/egdesk-turn-memory.mjs:304` | 분류 호출을 `settleBy(triageCall(), Math.max(1, remaining()))` 로 끊는다. 끊는 주체가 타이머다. |
| `helper/egdesk-turn-memory.mjs:288-289` | 남은 시간은 `performance.now()` 로 다시 계산한다. 타이머와 시계가 서로 다른 기준이다. |
| `helper/egdesk-turn-memory.mjs:310` | 분류가 기한으로 끊겼는지 확인하지 않고 인출(`reconstructMemory`)을 시작한다. |
| `helper/egdesk-wiki-reconstruction.mjs:199, 202` | 남은 시간이 0 보다 크기만 하면 요청을 시작하고, 남은 시간을 최소 1 ms 로 올려 잡는다. |

Node 타이머는 정수 ms 단위 이벤트 루프 시각으로 돌기 때문에 `performance.now()` 기준으로는 일찍 깨어날 수 있다. 실측 400회 중 35회가 일찍 깨어났고 가장 이른 것이 -1.197 ms 였다 (`timer-early.txt`). 그래서 "타이머는 끊었는데 시계로는 아직 1 ms 남았다" 가 생기고, 그 1 ms 로 인출이 시작된다. 대역 판정기는 즉시 답하므로 묶음까지 만들어진다.

재현 (`repro.mjs`, 테스트와 같은 기한 200 ms, 분류는 응답 없음):

| 코드 | 실행 | 끊긴 뒤 인출 시작 | 끊긴 뒤 묶음 생성 |

| c13 | 60 | 0 | 0 |

런타임 쪽에도 같은 종류의 구멍이 있었다. `helper/codex-chat-runtime.mjs:5229-5234` (`int/c11`) 는 상한 타이머와 루프 완료 중 먼저 실행된 콜백으로 판정했고, 결과가 있으면 `Boolean(turn.result)` 로 받아들였다. 프로세스가 바빠 타이머가 늦으면 상한 뒤에 준비된 묶음도 붙는다. 이 경로는 병합 코드에서 실시간으로 재현하지는 않았고, 새 테스트에 옛 판정식을 되돌려 넣었을 때 실패하는 것으로 확인했다 (`mutations.txt` E).

원칙: 기한은 한 시계 위의 한 시점이다. 타이머는 기다림을 깨우는 용도일 뿐이고, 판정은 전부 그 시계를 읽어서 한다.

| 위치 (c13) | 변경 |

| `egdesk-wiki-reconstruction.mjs:135` `REAL_CLOCK` | 시계와 타이머를 한 묶음으로 주입 가능하게 함 (`now`, `setTimer`, `clearTimer`). |
| `egdesk-wiki-reconstruction.mjs:143` `settleBefore` | 응답이 도착한 순간 시계가 기한 전일 때만 받아들인다. 일찍 깬 타이머는 다시 건다. 타이머가 안 울렸어도 기한 뒤 응답은 거부한다. |
| `egdesk-turn-memory.mjs:288` | `prepareTurnMemory` 가 절대 시점 `deadlineAt` 하나를 정하고 인출 루프에 그대로 넘긴다 (남은 시간을 다시 계산해 넘기지 않음). |
| `egdesk-turn-memory.mjs:308-315` | 분류가 기한으로 끊기면 인출을 시작하지 않는다. 결과는 `empty`, `partial: true`, `reason: 'deadline'`. |

동작이 바뀐 점 하나: 150 ms 최소 창은 경합 수정에 더해진 제품 동작 변경이다. 근거는 지금까지 실측한 가장 빠른 응답이 238 ms 라는 것 하나다. 남은 150 ms 미만에서 시작한 요청은 보내고 버릴 가능성이 높다고 봤다. 값 자체는 표본이 적어 조정 대상이다.

## 3. 테스트: 주입한 시계로 결정적으로

`egdesk-wiki-reconstruction.fixture.mjs` 에 `createFakeClock`, `deferred`, `until` 을 추가했다. 시간은 테스트가 움직일 때만 흐른다. 타이머를 일찍 울리는 옵션(`earlyMs`)과, 타이머를 울리지 않고 시계만 넘기는 `set` 으로 "이른 타이머" 와 "바쁜 프로세스" 를 각각 만든다.

원래 테스트가 증명하던 것은 유지하고 범위를 넓혔다.

| 테스트 (`egdesk-turn-memory.test.mjs`) | 증명하는 것 |

| `:434` | 기한에 분류가 끊기면 인출 요청이 0건. 타이머가 정시, 1.2 ms 이름, 30 ms 이름인 경우 모두. 기한 1 ms 전에는 아직 기다림. |
| `:456` | 타이머가 늦어도 기한 뒤 응답은 거부. 타이머가 일러도 기한 전 응답은 수용. 남은 시간 150 ms 경계에서 요청 시작 여부. |

작업 중 내가 쓴 새 테스트 두 곳이 처음에는 변이를 잡지 못했다. 하나는 시계를 너무 일찍 넘겨 루프 자체가 응답을 거부해 버렸고, 하나는 "아직 기다리는 중" 을 대역의 미응답 여부로 확인하고 있었다. 둘 다 고쳐서 변이에 실패하는 것을 확인했다.

## 5. Main 요청: pg-first 에 `jev/flow-note` 가 붙은 이유

라이브 결과(`evidence/main-real/memory-live-results.json`)에서 이 페이지는 스캔에서 뽑힌 것이 아니다. 스캔에서는 미결정이었고, 링크 라운드의 재확인(second look)에서 0.87 로 뽑혔다.

같은 메시지, 같은 페이지에 대한 실제 응답 (`flow-note-diagnosis.txt`, `first-scan-plan.txt`):

| 문구 | `jev/flow-note` | `db/pg-plan` | `db/pg-health` | `db/pg-followup` |
|-|-|-|-|-|
| 예전 ("답하는 데 도움이 되면") | 0.02 | 0.91 | 0.40 | 0.01 |
| 넓힌 문구 (c11) | 스캔 미결정, 재확인 0.87 | 1.00 | 1.00 | 0.95 |

넓힌 문구가 원인일 가능성이 높다. 페이지 본문에 "완료 보고는 전이 제안으로 돌린다" 가 있고, 메시지는 완료 보고다. "이 메시지가 요구하는 일을 하는 데 도움이 되는 페이지" 라는 기준에서는 완료 보고 처리 절차를 적은 다른 주제의 설계 메모도 해당된다고 읽힌다. 다만 문구별 표본이 1회씩이라 인과가 증명된 것은 아니다. 또 넓힌 문구로 첫 턴 스캔을 실제 측정한 것은 이번 라이브가 처음이다 (c11 재측정 6건에는 pg-first 스캔이 없었다).

수정 (`egdesk-wiki-reconstruction.mjs:165` `JUDGE_RULES`, 첫 턴 전용):
- "결정, 검증, 실행에 필요한 것" 은 유지하되 "메시지와 같은 사안의 기록일 때" 로 묶었다.
- "같은 종류의 사건을 언급하거나 설명한다는 이유만으로 다른 사안의 페이지는 필요하지 않다" 를 추가했다. 예외로 답변 모델을 향한 상시 지시와 선호를 남겼다.
- 대화 중 규칙 `NEXT_RULES` 는 바꾸지 않았다. pg-mid 개선은 이 규칙에서 나온 것이고, sha256 을 테스트로 고정했다.

이 문구의 효과는 측정되지 않았다. 대역 판정기는 규칙 문장을 읽지 않으므로 오프라인으로는 확인할 수 없다. 예외 문장(상시 지시)도 검증할 픽스처 페이지가 없다.
