## 1. 기능별 비용 모델

### 읽는 법과 한계
- 입력은 증거 v8 의 **여정 v6 (c28, 요청 43개, 사용자 턴 6개 + 실행 중 메시지 2개)** 와 **현재 설계의 계획 실측** 이다. 여정과 계획은 정해진 시나리오라서 턴당 수치는 그 시나리오의 값이지 평균적인 사람의 값이 아니다 (브리핑 1번, 브라우저 작업 1번, 회상 1번이 들어 있다).
- **"더해지는 지연" 은 측정한 차이가 아니다.** 같은 턴을 그 플래그를 켜고 끄고 잰 실행은 없다. 그 칸은 **코드가 허용하는 대기 한계** 와, 그 플래그가 더하는 요청의 **측정된 시간** 을 나란히 놓은 것이다. 한계는 코드의 상수를 import 해서 만든 값이고, 테스트가 상수와 표를 묶어 둔다 (상수가 바뀌면 테스트가 실패한다).
- 계획의 요청 시간은 따로 보낸 값이라 동시에 여러 일이 돌 때의 값이 아니다. 여정 요청 사이의 시각은 기록되지 않아서, 한 턴의 시작 전 요청들이 병렬인지 직렬인지는 이 자료로 알 수 없다 (아래 "턴 시작 전" 의 `합` 은 직렬이라고 가정한 상한이다).
- 토큰은 입력 토큰이다. 출력 토큰은 거의 0이다. 모든 요청은 클라이언트 경로로 월 예산 합계에 들어간다.
- 도구: `node scripts/egdesk-cost-model.mjs --journey <여정 결과> --rows <증거 행>`, 같은 숫자가 `evidence/l6-c20/cost-model-repo.json`, 표는 `cost-model.md`.

### 이 표가 말하는 것
- **가장 싼 켜기:** `decisionContext` 만 켜면 턴에 요청 1개, 입력 약 1.6k 토큰 (첫 턴 2.6k) 이다. 그 턴은 최대 800 ms (cold 1,500 ms) 만 기다리고 그 안에 못 끝나면 컨텍스트 없이 진행한다.
- **턴 시작 전 비용은 `turnMemory` 가 키운다.** 컨텍스트와 기억 요청이 함께 턴당 2~5개, 3.1k~8.6k 토큰이다 (후속 질문과 명령 턴은 약 3.1~3.3k, 첫 턴·회상·상태 확인은 약 8.2~8.6k). 기다리는 시간은 같은 한계 (0.8 s / 1.5 s) 안이다.
- **토큰을 가장 많이 쓰는 것:** `turnMemory` 의 페이지 스캔 (요청당 0.8k~3.0k), 브리핑 한 번 (5요청, 8.5k), 기억 쓰기 (3.2k), 첫 턴 컨텍스트 (2.6k). **가장 싼 것:** 작업 배치 (0.3k), 명령 판단 (0.3k), 브라우저 진입 (0.4k).
- **사람이 기다리게 만드는 것은 몇 개뿐이다:** `decisionContext` / `turnMemory` / `CONFIRM` (한계 안에서 턴 시작 전), `DRAFT_CHECK` 의 `on` (답을 올리기 전 최대 1.5 s + 재검사 1.2 s), 브라우저 단계 (단계마다), 터미널 게이트 (명령마다, 최대 4 s), 결과 카드 (작업 배치, 최대 1.5 s). 나머지(대화 흐름, 브리핑, 명령 판단, 작업 기억, HUD)는 기다리게 하지 않는다.
- **켜는 순서의 누적:** 전부 켠 여정은 턴당 7.2 요청, 약 10.1k 토큰이다. `decisionContext` + `turnMemory` 까지가 턴당 5.7k 토큰으로 전체의 절반을 넘는다.
- **`DRAFT_CHECK` 의 숨은 비용:** 위 표는 Decisions 요청만 센다. 검사가 문제를 찾으면 주관 모델의 수정 한 번과 재검사가 더해진다 (최대 45 s 보류). 대화 흐름의 메시지마다 짧은 fork 턴 (주관 모델) 도 든다. 둘 다 Decisions 요청이 아니라서 이 표에는 없다.
- 하루 비용은 이 표에 턴 수를 곱해서 owner 가 정한다. 이 자료는 하루 몇 턴인지를 모른다.

## 2. warm-up 최종 판독 (여섯 점이 모두 들어옴)

`--analyze`: **`warm-up works`** (등록한 규칙: A 가 한 번 이상 느리고 B 와 C 가 두 번 모두 빠름). 여섯 점 모두 다른 실행이 끼어들지 않았다 (`interleaved` 없음), 각 점은 600 s 이상 쉰 뒤에 시작했다.

| 점 | 측정 요청 | 느림 (800 ms 초과)? | warm-up 요청 | 소켓 |
|-|-|-|-|-|
| A1 (warm-up 없음) | **1,812 ms** (서버 556) | 느림 | - | 새 소켓 |
| B1 (warm-up 후 1 s) | 324 ms (서버 229) | 빠름 | **1,597 ms** (서버 652) | 재사용 |
| C1 (warm-up 후 10 s) | 269 ms (서버 175) | 빠름 | **1,187 ms** (서버 373) | 재사용 |
| A2 (warm-up 없음) | 561 ms (서버 468) | 빠름 | - | 새 소켓 |
| B2 (warm-up 후 1 s) | 322 ms (서버 208) | 빠름 | 522 ms (서버 415) | 재사용 |
| C2 (warm-up 후 10 s) | 316 ms (서버 192) | 빠름 | 507 ms (서버 408) | 재사용 |

[해석] 판독은 "works" 이지만 **증거의 힘은 한 번의 꼬리에 기댄다.**
- 꼬리가 나타난 것은 반복 1뿐이다 (A1 1,812 ms, B1·C1 의 warm-up 1,597 / 1,187 ms). 반복 2는 꼬리가 없었다: A2 561 ms, 두 warm-up 도 507~522 ms. 그래서 반복 2의 빠른 B2·C2 는 warm-up 의 효과를 구분해 주지 못한다.
- 구분해 주는 것은 반복 1이다: 꼬리를 막 겪은 직후(warm-up 이 끝난 1 s 뒤, 10 s 뒤)의 측정 요청이 324 / 269 ms 였다. 이것이 "warm-up 이 데운다" 를 뒷받침하는 전부다.
- **lead 시간은 중요하지 않아 보인다:** 1 s 뒤 (324, 322) 와 10 s 뒤 (269, 316) 가 비슷하다. 필요한 lead 는 warm-up 이 도착하는 시간이고 (꼬리가 있으면 1.2~1.6 s), 그 뒤 1 s 만 지나도 빨랐다. 도착 *전에* 실제 요청이 나가는 경우(lead 0)는 측정하지 않았다.
- **교란:** 빠른 측정 요청은 모두 재사용 소켓이었고 느린 A1 은 새 소켓이었다. 그러나 A2 는 새 소켓인데도 561 ms 였고, c14 의 70 s 유휴 뒤 새 소켓 요청도 295, 338 ms 였다. 소켓 재사용만의 효과는 아니라고 보지만, 이 probe 는 소켓과 서버 온기를 분리하지 않았다.
- 서버 시간도 꼬리의 일부다: 꼬리 때 서버 556~652 ms, 따뜻하면 175~229 ms. 꼬리가 약한 A2 와 반복 2의 warm-up 도 서버 시간은 408~468 ms 로 높았다.

**설계에 대한 함의** (c18 설계와 비교):
- composer 트리거 (타이핑 시간이 lead) 는 이 결과와 맞는다. 필요한 lead 는 warm-up 이 도착할 시간 (최대 약 1.6 s) 이다. **사람이 타이핑하는 시간은 여전히 모른다.** 붙여넣기나 짧은 메시지는 lead 가 거의 없다.
- `turn` 트리거는 이 결과로도 도움이 되지 않는다: warm-up 자신이 꼬리를 먹는다 (1.2~1.6 s). `joinMs` 로 기다리면 cold 예산 (1.5 s) 과 같아진다.
- 플래그는 기본 꺼짐으로 둔다. 켜는 결정은 owner 의 몫이다. 켠다면 먼저 `advisory` 로 `wouldWarm` (유휴 조건이 얼마나 자주 생기는가) 과 composer 신호가 실제 요청보다 얼마나 앞서는지 세는 것을 권한다.
