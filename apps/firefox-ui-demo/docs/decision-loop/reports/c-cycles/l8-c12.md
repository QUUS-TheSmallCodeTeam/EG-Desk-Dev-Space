# L8 / C12 브라우저 `on` 경로를 int/c11 위로 재배치 (heartbeat·memory `on`과 통합)

브랜치 `lane/c12-browser-rebased` (base int/c11 edbec8b), 커밋 `1653793` (c11 `409eca0` cherry-pick + 충돌 해결 + 이번 변경을 한 커밋으로). 합성 검증만(실제 `CodexChatRuntime.send`, 실제 provider/Browser service/reflex, 채팅 저장소, L7 어댑터·영속 쓰기, L3 heartbeat; UI 대역, mock Decisions, 각본 주관 엔진, 가상 시계). 실제 Firefox·네트워크·codex 없음. 어떤 flag도 켜지 않았다.

## 0. c11이 한 일 (Main이 받지 못한 보고의 요약, 6줄)
1. 왕복: `on` 경로의 질문/최종 보고가 스트리밍되던 것을(제한된 턴은 보류 대상이 아니었음) L3의 보류 가드로 완성 메시지 한 건씩으로 바꿨다. 기록 순서 user -> 질문 -> user 답 -> 보고, 답은 같은 task id를 재개.
2. 사실: `chat.browserTaskFacts(clientThreadId)`와 저장소 `facts()`(단계 수, 사용자 대기 여부·종류·코드, 마지막 동작 경과; 숫자와 닫힌 단어만), 루프 중 갱신용 읽기 전용 관찰자(`onStep`).
3. triage 얹기: `triageTurn({ extraQuestions })` + `entry.handle({ entryAnswers })` + 런타임 훅. triage가 있는 턴이라면 요청 1건·왕복 0.25~0.45 s 절감, triage 요청에 약 130 토큰 추가(단독 진입 요청 약 230 토큰; 하네스 바이트 913/525에서 추정, provider 실측 아님).
4. 단, 제한된 브라우저 턴에는 턴 시작 triage가 없어 지금 배선에서는 이득 0이라 브리지에 연결하지 않았다. 얹은 답이 "브라우저 작업 아님"이면 기억 fetch를 건너뛴다.
5. 안전: 기존 매트릭스 120 pass, c4 측정 재실행(놓침 0/50·0/36, href 거짓 제외 13/50 그대로), 새 어휘 20개(라벨·경로) 후보 0·요청 0, 런타임 경로에서 위험 요소·제출 요청 0, 페이지 변경 override 유지.
6. egress(D2): 기억·진입 훅에 넘기는 클라이언트를 run 권한으로 감쌌다. 새 Decisions 호출 지점 없음.

## 1. 충돌 해결
- `egdesk-turn-memory.mjs`: 양쪽 모두 유지(`deadlineMs`, `packetFirst`, `extraQuestions`). triage 호출은 L7의 `timeoutMs: triageTimeout()`에 `extraQuestions`를 더했다.
- `codex-chat-runtime.mjs`: `runBrowserEntryOn`은 내 egress/얹기 블록 + L3의 heartbeat 연결을 함께 유지. `startConversationFlow`는 L3의 heartbeat 판을 유지하고 내 c11의 "브라우저 작업 턴은 flow 제외" 조건은 버렸다(아래 3으로 대체).

## 2. 사실 provider 하나로 정리
- 유일한 출처는 작업 저장소의 `facts(conversationKey)`. L3의 pass-through 저장소 래퍼(`observeBrowserTaskStore`)와 별도 계산(`browserTaskFacts(task)`)을 제거했다.
- `feedBrowserTask(heartbeat, store, conversationKey?)`는 저장소를 그대로 쓰고 `browserTaskRow(store.facts(key))`를 등록한다. key 기본값은 heartbeat의 key(둘 다 로컬 채팅 id).
- heartbeat 행: `{ active, phase, waitingOnUser, stepsDone, stepsRemaining, task, awaiting, awaitingCode, lastActionAgeMs, idleMs }`. task id와 중첩 개수는 빼고(Decisions로 가는 사실이므로) heartbeat가 이해하는 `stepsRemaining`을 쓴다. 래퍼가 없어져 루프 중 단계 수가 단계 단위로 갱신된다(이전에는 구간 단위).
- `chat.browserTaskFacts()`는 같은 출처를 읽는 접근자 한 줄로 남겼다.

## 3. 중간 대화가 실제 배선에서 동작하게
**택한 방식: 제한된 브라우저 작업 턴을 L3 경로의 대상으로 만든다(장치 하나).** 객관 루프는 네이티브 턴 이전에 돌고, 넘겨받는 순간 주관 모델의 턴이 시작된다. 그 턴의 메시지(질문 또는 보고)는 보류 가드로 완성 메시지 한 건이 되고, 같은 턴에서 heartbeat가 말할 수 있다.
- int/c11 상태(재현, 변이 C): 작업 턴이 보류 대상이 아니어서 질문이 스트리밍되고 heartbeat는 말하지 못했다.
- 변경 1 (c11에서 가져옴): 닫힌 노트가 있는 턴은 `draftHold`를 켠다 -> `flow.canSpeak`가 참.
- 변경 2: heartbeat가 살아 있는 동안 일시정지된 작업은 "사용자 대기"가 아니라 **넘겨주는 중**이다(질문이 아직 작성 중이고, 질문이 게시되면 턴과 heartbeat가 끝난다). 이전 provider는 이때 `waiting_user`를 보고해 flow를 완전히 막았다(변이 B로 확인). 이제 `phase: 'handing_off'`, `waitingOnUser: false`, `awaiting: need_context|cannot_proceed`.
- 변경 3: 작업 턴에서는 `ask_missing`(턴 안 질문)을 후보에서 뺀다. 작업의 질문은 그 턴의 메시지 자체이고, 답이 턴 안으로 steer되면 일시정지된 작업에 닿지 않는다(변이 A로 확인: 필터가 없으면 주관 모델의 메모 속 물음표로 `ask_missing`이 제안됨).
- 답의 경로: 질문이 턴을 끝내므로 답은 다음 메시지로 들어와 `task_resume` 판단 후 같은 작업을 재개한다. L2의 `run.replyOpen`/턴 안 답장에 의존하지 않고 충돌하지도 않는다(작업 턴에서는 턴 안 질문이 열리지 않음).

### 검증 (codex-chat-browser-task-roundtrip.test.mjs, 13개)
- R1/R2: 보류 on에서 질문·보고가 각각 완성 메시지 1건, 턴 종료 전 assistant 이벤트 0, 기록 순서 유지, 같은 task id 재개(need-context, 2FA).
- H1(가상 시계, flag 3개 모두 on): 작성이 느린 턴 26초 -> heartbeat가 `explain_wait`를 골라 주관 모델이 private fork에서 쓴 문장 1건이 완성 메시지로 게시, `ask_missing` 제안 0, steer 0, 동작 0 -> 질문 -> "두 번째 사업자로" -> 같은 작업 -> 보고. 기록: user, assistant(대기 안내), assistant(질문), user, assistant(보고). heartbeat 질문 본문에 요청·사업자·호스트 문자열 없음.
- H2: 보류 off면 heartbeat는 사실만 받고 말하지 않는다(기존 동작).
- 변이 3종(필터 제거 / waiting_user 복원 / 보류 제거)에서 H1(및 R1)이 실패함을 확인하고 원복했다.
- 브리지: `EGDESK_BROWSER_ENTRY=on`, `EGDESK_DRAFT_CHECK=on`, `EGDESK_CONVERSATION_FLOW=on` 세 개발자 flag가 모두 켜졌을 때의 경로이며 브리지 코드는 바꾸지 않았다(전부 기본 off).

### 남은 한계
- **턴 전 객관 루프 구간에는 run이 없어 heartbeat가 뛰어도 말할 수 없다**(게시에는 run이 필요). 루프가 길면(최대 24단계) 그동안 조용하다. 사실은 heartbeat에 들어오므로 run 없이 게시하는 수단이 생기면 바로 쓸 수 있다.
- 작업 턴의 질문 문장은 초안 검사를 받지 않는다(제한된 턴 부적격, L3 규칙). 브라우저 작업이 아닌 제한된 턴은 여전히 스트리밍된다.
- 질문을 쓰는 턴의 주관 모델은 브라우저 도구를 갖고 있어 묻는 대신 조작할 수 있다(모델 행동, mock으로 검증 불가).
- L3의 테스트 2개와 L3가 추가한 내 파일의 테스트 1개의 기대값을 새 의미(`handing_off`)로 바꿨다. L3 확인 필요.
