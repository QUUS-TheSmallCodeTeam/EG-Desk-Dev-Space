## 4. 시나리오가 찾은 제품 결함과 수정
1. **실행 파일 뷰어의 배치 요청이 heartbeat를 못 찾았다.**
   - 뷰어는 `{ runId, conversationId }`만 보내고, `heartbeatFor`는 로컬 chat id만 알았다. 그래서 bridge 답이 `no-heartbeat`이었고 판단이 아예 일어나지 않았다.
   - `heartbeatFor`가 run의 native 대화 id로도 같은 session heartbeat를 찾게 했다(읽기 전용, 기존 thread 지도 사용). 모르는 키는 예전처럼 `null`이다.
   - `placementContextFor`도 같은 경로를 쓴다.
2. **draft check가 꺼져 있으면 run의 요청문이 사라졌다.**
   - `runUserText`가 draft check의 턴 기록이나 `run.messages`(assistant만 있음)에서만 읽었다. 그래서 배치의 내용 질문(요청문 인용)과 L3의 idle 문맥이 요청 없이 돌았다(`no_material`).
   - 요청문을 run 단위 WeakMap에 draft check 모드와 무관하게 남긴다.
3. **L2 bridge 세계의 배선이 실제 bridge와 달랐다.** 배치에 `contextFor`가 없었다(c12에서 bridge에는 넣었음). 수정했고, 요청자 레지스트리를 노출했다. L2 테스트 32/32는 그대로다.
- 변이 확인: 1·2를 되돌리면 시나리오 테스트가 실패한다(각각 5건, 1건).

## 5. 발견 (고치지 않음, 결정 필요)
- **B는 그 작업 화면을 보지 못한다.** 정본 §12대로 개인 배치는 공유 원장에 쓰지 않는다. 그래서 A의 캔버스에서 "B가 보는 구역"에 열린 뷰어는 B의 Desk에 전달될 길이 없다. 시나리오는 이것을 hard 기대(P8, R7)로 고정했다. U7의 의도("내 자료로 초대받은 사람이 작업하는 걸 그 구역에서 보이게")와 실제 전달 사이에 빈 곳이 있다.
- **창 `on`은 규칙 자리에 즉시 연다.** same_matter 판단은 그 뒤에 도착해 기록만 된다. dry run에서는 판단이 `beside_related`였지만 뷰어는 규칙 자리에 남았다. 판단을 반영하려면 열기 전에 기다리거나(지연), 연 뒤에 옮겨야 한다(이동 규칙 위반 소지).
- **포인터 메시지는 draft check `on`일 때만 게시된다**(L3 규칙: 모든 시스템 메시지는 검사된 메시지). 시나리오는 draft check를 켰다. 그래서 result 단계에 draft_check 요청 1건(848 토큰)이 들어 있다.
- **가장 큰 비용은 ask 단계의 turn_context(2,496 토큰)다.** 매 메시지마다 Decision 문맥이 L2 세계의 온톨로지 후보를 판정한다. 시나리오와 무관하지만 제품 경로라 그대로 두었다.
- **제품 트리거 없음(이전과 같음).** 멤버 요청으로 소유자 run을 시작하는 화면과 창의 attention 장면 전송이 없다. 시나리오는 그 훅(`runRequesters.set`, attention 요청)을 직접 부른다(L2 여정과 같은 방식).
- L3의 `told_1`(이미 게시된 메시지가 "어디에 있는지"를 말하나)이 Agent 답에 대해 물어진다. 답이 위치를 말하지 않으므로 포인터가 나가는 것이 예상이다. 실측에서 모델이 예라고 하면 R4가 실패하고, 그것도 발견이다.
