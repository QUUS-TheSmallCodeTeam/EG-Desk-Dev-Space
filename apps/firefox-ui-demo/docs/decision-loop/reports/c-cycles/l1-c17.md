## 1. 창의 attention 트리거 (기존 플래그 `egdesk.workPlacement`, 기본 꺼짐)
- **이벤트 루프**: chat.event v2를 받을 때마다 `state.noteChatAttention?.(event, run)` 바로 다음에 `state.noteWorkChatEvent?.(event, run)`을 호출한다.
- **대상 표시**: run이 연 파일 뷰어(`spawnFileCard`, run 파일만, 복원 제외)는 `dataset.workRunId`/`workConversationId`를 단다(`state.workSurfaceMark`). pref가 꺼짐이면 표시하지 않는다. DOM 안에만 있고 저장하지도 보내지도 않는다.
- **`noteWorkChatEvent`**: `run.completed`이고 status가 `completed`일 때만 동작한다. 실패·차단·다른 이벤트·꺼짐이면 아무것도 하지 않는다. 그 run이 연 표면 중 가장 최근 것으로 scene을 만들어 `WorkPlacement.attentionRequest`를 호출한다.
  - task는 finished, 표면은 agent 카드로 둔다.
  - 요청자는 `runRequesters.for`(로컬 채팅 기준)에서 온다.
  - run마다 한 번만 보낸다.
  - 소유자와 요청자 모두 이미 보고 있으면 보낼 것이 없다. 창 기록(`sent: false`)만 남긴다.
  - 그 밖에는 `POST /decision/work-placement/request {clientThreadId, conversationId, dto}`를 보낸다. 기존 attention DTO 계약 그대로(bridge `normalizePlacementDto`가 그대로 받음)다.
  - 나가는 것은 member alias(M#), card의 creator·movable, distance·direction 단어뿐이다.
  - **숫자 값(좌표·크기·나이)은 하나도 없다.** member id, card id, run id도 없다.
  - 아무것도 옮기지 않고(카메라 0), Board에 쓰지 않는다.
  - 요청자 쪽 결과가 `surface_near_requester`여도 bridge에는 "would" 기록으로만 남는다. 창은 attention 결과를 읽지 않으므로 아무것도 움직이지 않는다.
- **테스트** (`helper/egdesk-work-placement.test.mjs` §12, 5개. 실제 창 함수, 합성 DOM, 실제 bridge 경로):
  1. 기본 꺼짐이면 표시도 전송도 없다. completed가 아니면 없다. 표시 없는 카드는 없다. 같은 run은 한 번만 보낸다.
  2. 소유자가 볼 수 없는 뷰어는 attention DTO 1건이 된다. 키가 정확하고, 잎값은 문자열·불리언·null뿐이며, id 값이 없고, alias만 있고, 카메라는 0이다.
  3. 두 사람 모두 보면 전송하지 않는다.
  4. **bridge 경로**: 창이 보낸 body는 그대로 유효하다. queued → beat → owner 질문(run의 답) → `owner / point / decision`이 되고, live이면 pointer fact(`owner_action`)가 올라간다.
  5. 소스 고정: 파일 카드의 run 표시, 이벤트 루프 호출, 표시로 찾기.

## 2. 요청자는 사람과 대화에 묶이고, 엔진 프로필·CODEX_HOME·폴더에 묶이지 않음 (결정 c)
- **찾은 결합 (제거함)**: 창의 실행 파일 뷰어는 `{kind, runId, conversationId}`만 넘긴다. `placeWorkSurface`와 `noteWorkSurfacePlacement`는 요청자를 엔진의 native conversation id로만 찾았고, 배치 요청도 그 id로만 보냈다.
  - 엔진 프로필이나 계정이 바뀌면 같은 로컬 채팅이 새 native conversation으로 이어지는데, 그때 요청자 B를 잃었다(테스트가 이 결합을 재현한다).
  - **수정**: `workRunRef(work)`가 창의 run 목록(`chatProtocol.runs`)에서 그 run의 로컬 채팅(`clientThreadId`)을 먼저 찾는다. 요청자 조회와 bridge 요청 키에 로컬 채팅을 쓴다(native id도 함께 보낸다).
- **확인함 (결합 없음)**:
  - bridge 요청자 registry(`egdesk-presence-mirror`)는 `[clientThreadId, conversationId]`로 키를 두고, audience는 `run.clientThreadId`로 찾는다.
  - 세션 heartbeat는 `context.clientThreadId || cid`로 키를 두고 native id마다 같은 heartbeat에 매핑한다.
  - placement runtime은 heartbeat 키를 쓴다.
  - 요청 요청자(`createRequestRequesters`)는 request id와 digest 해시로 키를 둔다.
  - 공유 선택 저장소는 서비스 인스턴스와 EG-Desk 계정(사람)이 범위이고, Firefox 프로필의 pref에 있다.
  - run의 데이터 권한(`decisionEgressFor`)은 run의 도구 상한·브라우저 권한에서 오고, 엔진 프로필·home·폴더는 읽지 않는다.
  - 이 경로의 모듈과 창 함수에는 `engineProfile`, `CODEX_HOME`, `cwd`, `folder`, `ownerKey`, `accountKey`가 없다(테스트로 고정).
- **테스트** (`helper/egdesk-requester-across-engines.test.mjs`, 3개): 세션 중간 전환을 모델링했다. 같은 로컬 채팅에서 다른 엔진 프로필, CODEX_HOME, 폴더, 새 native conversation.
  1. 창: native id만으로는 B를 잃지만(결합 재현), `workRunRef`로는 B가 유지된다. 뷰어 배치 요청은 로컬 채팅 키와 B를 요청자로 담고, 프로필·home·폴더는 없다. advisory 훅도 같은 키를 쓴다.
  2. bridge: registry audience가 새 native id에서도 B다. 다른 채팅은 B가 아니다. `heartbeatFor`는 세 키 모두 같은 heartbeat이고, 데이터 권한은 두 run이 같다.
  3. 코드 경로 검사.
- **c1 코드(복원 DM 게이트) 확인 필요**: 복원된 방의 retained pair가 `bindingAccountKey`와 같아야 `[보기 추천]`을 허용한다. 이것은 native binding 무결성 검사이고, 요청자나 승인을 계정에 묶는 것은 아니다. 다만 결정 (c)에서 계정 전환 뒤 이 게이트가 어떻게 동작해야 하는지는 소유자·Main이 확인해 주어야 한다. 바꾸지 않았다.

## 3. 시나리오 v4 (v1–v3은 등록된 그대로)
- 계획 `scripts/egdesk-multiuser-live-measure.plan-v4.json`(기본), set `multiuser-collaboration-v4`, 해시 **f2d5ed5f1e2f56d5**, 보내기 전인 2026-11-25T03:10+09:00에 등록했다. v1, v2, v3 파일은 바꾸지 않았다(해시가 서로 다르고 v4 검사 없음, 테스트).
- **runner가 attention scene을 보내지 않는다**:
  - runner는 L2의 `screen(w, DM, { onEvent })`로 bridge의 chat.event를 제품의 reducer 경로(canAdmit → reduce → sync)로 흘려 보낸다. 그리고 제품 루프처럼 각 이벤트를 창의 `noteWorkChatEvent`에 넘긴다(transport).
  - runner 소스에는 `attentionRequest(`와 `work-placement/request`가 0회다(테스트).
  - 뷰어 노드는 `spawnFileCard`가 만드는 그대로 제품의 `workSurfaceMark`를 단다(제품 상태 모델링).
- **follow-up run은 자기 뷰어(납기 일정표)를 연다**: run의 attention은 그 run이 연 표면에 대한 것이다. c16까지는 runner가 첫 run의 뷰어를 둘째 run의 것처럼 보냈다. 그래서 follow-up 단계에는 work_placement가 2건(배치, attention) 있다.
- **v4 검사**:
  - F1/F2: owner 질문을 고르는 `select`.
  - **R9/F8 (hard)**: 창 스스로 scene을 보냈다(1건).
  - **F9 (hard)**: A가 본 follow-up 답에 등록된 고정 안내문 두 문장이 없다.
- 950 ms 재현(c21)에서는 이 기준선에 아직 L3의 안내문 제거가 들어오지 않아서 **F9만** 실패한다(의도한 동작, 테스트로 고정). 나머지 hard는 모두 통과한다.
- 남은 harness 대역: B의 요청으로 시작한 A의 run에 요청자를 설정하는 `runRequesters.set`. 멤버 요청으로 소유자 run을 시작하는 제품 화면은 없고, 이것은 소유자 결정이다. 계획의 `changes`에 적었다.
- 주의: v1–v3 계획을 새 runner로 돌리면 follow-up 기대(work_placement 1건)가 맞지 않는다. v1–v3은 이전 전송의 기록이고, 다시 돌리려면 c16 runner를 써야 한다.
