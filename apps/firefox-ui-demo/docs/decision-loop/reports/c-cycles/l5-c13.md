## 1. 프로토타입: "거부 → 대화에서 묻기 → 정확한 명령 한 번 허용"
**근거(공식 문서)**: https://learn.chatgpt.com/docs/hooks
- "Common input fields": `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `model`, `permission_mode`
- "PreToolUse": 추가로 `turn_id`, `tool_name`(셸과 unified exec는 `Bash`), `tool_use_id`, `tool_input.command`
- 거부: `hookSpecificOutput.permissionDecision:"deny"` + `permissionDecisionReason`(모델이 읽음)
- "`permissionDecision: \"ask\"` … parsed but not supported yet … continues the tool call"
- "Exit `0` with no output is treated as success and Codex continues"

**구성 (저장소 안에만 있음)**
- `scripts/egdesk-codex-gate-hook.mjs`: 의존성 없는 node 훅. 본문은 `gateHookMain(process)`이고 로직은 `helper/egdesk-gate-hook-core.mjs`에 있음.
  - stdin의 PreToolUse 입력(최대 1 MB)을 읽음. `Bash`가 아니거나 이벤트가 다르면 아무 말도 하지 않음.
  - `EGDESK_GATE_HOOK_URL`(loopback만)과 `EGDESK_GATE_HOOK_TOKEN`이 없으면(= EG-Desk가 띄운 엔진이 아님. 사람이 직접 쓰는 Codex CLI가 같은 hooks 파일을 읽는 경우) 아무 말도 하지 않음.
  - 브리지에 묻고, `deny`면 공식 거부 형태를 출력함. `allow`나 `none`이면 **아무것도 출력하지 않음**. 훅에는 "허용 출력"이 아예 없으므로 Codex 자체 샌드박스와 승인은 그대로 적용됨(추가만 함).
- `scripts/codex-hooks/hooks.prototype.json`과 `README.md`: 공식 "Config shape" 형태임. **설치되지 않았고 EG-Desk도 설치하지 않음.**
- `helper/egdesk-gate-hook-broker.mjs`(브리지 쪽, in-process):
  - `check({sessionId, turnId, cwd, command})` → `allow | deny | none`
    - 이 턴에 기록된 정확한 승인이 있으면 소비하고 allow.
    - 바닥이면 deny(모델 요청 0).
    - 바닥이 아니면 카드와 같은 게이트(`gateHookAssess` → `startCommandGate`: 플래그, Decision 모드, 런의 egress)로 술어를 묻고, 승인이 필요하면 deny, 그 밖에는 none.
  - **횟수 제한**: 같은 명령, 같은 턴에서 첫 거부는 `needs_person`이고, 두 번째부터는 `stop_asking` + `onStop`.
  - **거부 사유는 닫힌 어휘의 구조화된 한 줄임**(브라우저 작업 `subjectiveNote`와 같은 방식): `{"egdesk_command_gate":{"status":"needs_person","reasons":[…],"options":["run","cancel","give_context"],"next":"ask_user_in_chat","retry":"same_command_after_yes"}}`. 질문 문장은 답하는 모델이 씀(U4). 따라서 사람에게 보이는 고정 문구가 없음.
  - **승인 기록에는 외부 엔드포인트가 없음(보안 결정)**: 훅의 주소와 토큰은 엔진의 셸 환경에서 보이므로, 그곳에 승인 엔드포인트가 있으면 모델이 스스로 승인할 수 있음. 승인은 `readReply`로만 생김. 거부가 있었던 턴 **다음의 첫 메시지**(한 번만 건너감)를 yes/no 술어 둘로 읽음. `reply_runs_command` ≥ .8이고 `reply_declines_command` ≤ .2일 때만 승인함. egress는 `run_text`와 `terminal_command`(직전 런의 권한)임.
  - 승인은 그 메시지가 시작하는 **다음 턴에 묶임**. 한 번 쓰면 소비되고, 그 턴이 끝나면 만료됨.
  - 명령의 정체성(`commandKey`) = cwd + 단순 명령마다의 단어, 리다이렉트, 파이프 + 연산자 순서. 공백 차이는 같은 명령으로 보지만, 옵션 하나만 바뀌어도 다른 명령임.
- `createGateHookHandler`: `POST /egdesk/gate-hook/check`만 있음. loopback, Bearer 토큰(timingSafeEqual), 본문 64 KB 제한.
- 런타임 연결(`codex-chat-runtime.mjs`): `startTurn`이 accept되면 `turnStarted`, `finish`에서 `turnEnded`, 턴 시작 직전에 `readGateHookReply`(기다리는 질문이 없으면 비용 0). 묻지 않고 실행된 명령 기록에 `hooked` 불리언을 추가함.
- **U4 해석**: 대화 안의 열린 질문 → 사람의 답 → 객관식(yes/no 술어)으로 복귀. 카드나 양식은 없음.

## 2. 실패 모드 (모두 테스트함, `helper/egdesk-gate-hook.test.mjs` 8개 테스트)
- **브리지 다운**(연결 실패, 타임아웃, HTTP 500, 이상한 답): 바닥 명령은 **거부(fail closed, `gate_unavailable`)**, 나머지는 조용히 통과함.
  - 이유: 바닥 명령은 되돌릴 수 없는 명령임. 잘못 거부하면 한 턴을 잃을 뿐이지만(모델이 사람에게 말함), 잘못 통과시키면 되돌릴 수 없음.
  - 나머지까지 막으면 브리지가 없을 때 모든 작업이 멈춤. 이는 지금의 동작이 아님(P2).
  - 실제 프로세스로도 확인함: 포트 9(닫힘)를 대상으로 스크립트를 직접 실행하면 deny `gate_unavailable`(`evidence/l5-c13/hook-script-bridge-down.out`).
- **훅이 신뢰되지 않았거나 설치되지 않음**: check가 한 번도 오지 않으므로 런타임은 c12와 똑같이 기록만 함(`hooked:false`). 모델 요청은 0.
- **재사용(같은 승인 두 번)**: 두 번째는 deny.
- **복합 명령**: `npm test && git push --force origin main`은 위험한 부분(remote_irreversible)으로 deny됨. 복합 명령의 승인이 그 부분만 단독으로 승인하지는 않고, `&&`와 `;`도 서로 다른 명령임.
- **승인 뒤 모델이 명령을 바꿈**(`--force` → `-f`, 다른 cwd): 새 승인이 필요함(deny).
- 그 밖에 테스트한 것:
  - 승인이 턴과 함께 만료됨.
  - no, 애매한 답, 읽을 권한이 없는 답, 모델 오류는 승인하지 않음.
  - 기다리는 질문이 없을 때 오는 yes는 아무것도 승인하지 않음.
  - advisory는 기록만 하고, off는 침묵함.
  - 모르는 턴: 바닥은 즉시 stop_asking.
  - 토큰이 틀리면 401. 승인 엔드포인트는 없음(404).
  - 기록에 내용이 없음.
- 테스트 게이트의 안전 프리로드가 프로세스 생성을 막기 때문에, 스크립트 본문은 in-process로 실제 loopback 서버에 대해 테스트함. 실제 child process 실행 결과는 프리로드 없이 돌린 것을 증거로 남김(`hook-script-spawn-unguarded.tap`, pass).

## 3. 결정 3 (늦게 오는 술어)
카드는 즉시 뜨고, 술어나 git 사실을 기다려야 하는 명령이면 **세션 선택지 없이** 뜸. 답이 4 s 안에 와서 허용하면 **같은 카드(같은 approvalId. 화면은 upsert함, `EGDeskChatState.sys.mjs:1185`)에** 세션 선택지를 더함. 승인이 필요하다는 답이면 끝까지 선택지가 없음. 따라서 거부 문구가 필요 없음. 4 s가 지나도 답이 없으면 그대로 둠. 판정 불가(fallback, 예: 모델 타임아웃)는 P2에 따라 지금 동작으로 돌아가므로 선택지가 돌아옴. 아래 결정 3을 참고.
- 테스트:
  - 첫 화면 이벤트에는 세션 선택지가 없고, 허용되면 업데이트가 한 번 옴.
  - 위험한 명령은 업데이트가 0번임.
  - 위험하지 않은 명령은 처음부터 선택지가 있음.
  - git 사실이 오지 않으면 4.2 s 뒤에도 그대로임.
- c12의 테스트 3곳은 새 동작에 맞춰 **더 엄격하게** 바꿈: "세션을 골랐다가 거절됨"이 "애초에 선택할 수 없음(INVALID_DECISION)"이 됨. 단언은 약화하지 않음.

## 4. 소유자를 위한 비교 (시나리오)
**(A) 거부하고 묻는 훅 (이번 프로토타입)**
- 사람이 겪는 것: 에이전트가 `git reset --hard HEAD~5`를 실행하려다 멈추고, 대화에서 "이렇게 하려는데 실행할까요, 취소할까요, 다른 맥락이 있나요?"라고 자기 말로 물음. 사람이 "응, 해"라고 답하면 다음 턴에서 정확히 그 명령이 한 번 실행됨. 다르게 고친 명령은 다시 물음. 그 외 명령은 지금과 똑같이 돌아감.
- 설정 변경: 사람의 hooks 위치(`$CODEX_HOME/hooks.json`, 신뢰된 프로젝트의 `.codex/hooks.json`, 또는 `[hooks]`) 중 한 곳에 훅 정의를 두고, `/hooks`에서 **사람이 직접 검토하고 신뢰**해야 함(해시 고정. 정의가 바뀌면 다시 신뢰해야 함). EG-Desk가 띄운 app-server 환경에 주소와 토큰을 넣어야 함.
- 문서가 보장하는 것: PreToolUse는 셸 명령이 실행되기 **전에** 돌고, 거부할 수 있음. 거부 사유는 모델이 봄. 비관리 훅은 신뢰하기 전에는 실행되지 않음.
- 문서가 보장하지 않는 것:
  - 'ask'는 지원되지 않음(그래서 거부 후 대화).
  - "Treat tool hooks as a useful guardrail, not a complete enforcement boundary"(일부 특수 도구 경로는 빠질 수 있음).
  - 훅 프로세스가 app-server의 환경 변수를 물려받는다는 것은 문서에 명시되지 않았음(**확인 필요**).
  - `session_id`가 EG-Desk의 conversationId(thread id)와 같다는 것도 미확인임. 그래서 프로토타입은 `turn_id`(= EG-Desk runId)로 묶고, `session_id`는 등록보다 훅이 빠를 때의 보조로만 씀.
  - 같은 hooks 파일을 사람의 CLI도 읽음. 환경 변수가 없으면 훅이 침묵하도록 만들어 둠.

**(B) 프로젝트 `trust_level = "untrusted"` + rules**
- 사람이 겪는 것: 그 프로젝트에서는 규칙이 허용하지 않은 **모든** 명령에 대해 엔진이 승인을 요청함. 지금의 카드가 훨씬 자주 뜸(`npm test`, `ls`도 규칙이 없으면 물음).
- 설정 변경: 사용자 수준 `~/.codex/config.toml`에 `[projects."<경로>"] trust_level = "untrusted"`를 둬야 함. 이 경우 프로젝트 로컬 설정이 꺼짐. 묻지 않을 명령은 rules 파일(`prefix_rule … decision="allow"`)로 허용해야 함. 누군가 `approval_policy = "on-request"`를 명시하면 이 정책을 덮어씀.
- 문서가 보장하는 것: "Commands then require approval unless an execution-policy rule allows them". rules는 `forbidden > prompt > allow`.
- 문서가 보장하지 않는 것: 규칙은 **접두사만** 볼 수 있음("다른 커밋으로 reset"이나 "WHERE 없는 DELETE" 같은 조건은 표현할 수 없음). 복합 `bash -lc` 스크립트는 단순할 때만 쪼개짐. 술어(내용 판단)를 끼울 자리가 없음.

**(C) 턴마다 샌드박스나 승인을 좁히기**
- 사람이 겪는 것: EG-Desk가 턴을 시작할 때 `sandboxPolicy: readOnly`(turn/start가 받는 필드. `codex-native-schema-probe.mjs:117`)로 시작하면, 파일 수정과 명령 실행 대부분이 승인 요청이 됨. 편집할 때마다 fileChange 카드, 테스트 실행에도 카드가 뜸.
- 설정 변경: 사람의 설정은 바꾸지 않고 EG-Desk가 턴 인자만 바꿈. 대신 Codex의 기본 작업 방식(`workspace-write`)을 EG-Desk 안에서는 포기하게 됨.
- 문서가 보장하는 것: read-only 샌드박스에서는 샌드박스 밖의 작업에 승인이 필요하고, `on-request`에서는 샌드박스가 허용한 것만 묻지 않고 실행됨.
- 문서가 보장하지 않는 것: 명령 단위의 구분. 전부 아니면 전무이고, 위험하지 않은 작업까지 모두 마찰이 생김.

**권장**: (A)임. 바닥과 술어를 그대로 쓰고, 위험한 명령만 멈추며, 사람의 신뢰 단계(`/hooks`)가 명시적임. 다만 설치와 신뢰는 사람이 해야 하고, 위의 미확인 2가지(환경 변수 상속, session_id)는 실제 Codex로 검증해야 함. 이 검증은 전송이 아니라 로컬 실행이므로 Main이나 소유자의 승인이 필요함.
