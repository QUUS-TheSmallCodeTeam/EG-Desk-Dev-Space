## 1. 설정이 같으면 매 턴 `thread/unsubscribe + thread/resume`을 건너뛰기

### 무엇이 reload를 일으키나

- Agent 프로필 DM은 매 턴 thread를 내려놓고(`releaseThread`) 다시 resume합니다 (`mustReload`, `profileRun`). 목적은 프로필의 도구 ceiling과 지침을 thread에 다시 적용하는 것이고, resume 응답으로 `verifyCeilingNativeThread`가 ceiling을 다시 확인합니다 (AGENT-04).
- resume에 실리는 값은 프로필이 정하는 것만이 아닙니다. 아래가 모두 들어갑니다. 그래서 "프로필이 같다"만으로는 안전한 기준이 못 되고, **실제로 보낼 resume 파라미터 전체**를 기준으로 삼았습니다.
  - 프로필 지침, 모델, cwd
  - ceiling이 만드는 설정. 이것은 엔진의 현재 설정(sandbox 모드, 엔진이 나열하는 MCP 서버)을 읽어서 계산합니다.
  - computer control, own tools 설정

### 안전 장치 (모두 테스트로 확인)

1. **키는 "실제 resume 파라미터 전체"의 해시**입니다 (정렬한 JSON의 sha256). 병합된 overrides, policy, shell 스위치, computer control 상태, ceiling이 들어갑니다. ceiling 설정은 매 턴 다시 계산하고, 기억하는 것은 그 결과의 해시뿐입니다.
2. **그 thread가 마지막으로 로드되고 검증을 모두 통과했을 때의 키와 같을 때만** 건너뜁니다. 검증이 한 번이라도 실패한 로드는 키를 남기지 않습니다. 그래서 다음 턴은 다시 reload합니다.
3. **ceiling 검증은 건너뛰지 않습니다.** 건너뛰는 턴에도 마지막 resume이 보고한 sandbox와 thread의 현재 MCP 및 기능 목록으로 `verifyCeilingNativeThread`를 다시 돌립니다. ceiling 알림도 그대로 만들고, computer control 확인도 합니다.
4. **재확인이 실패하면 reload로 되돌아갑니다.** 엔진의 thread가 적용한 설정에서 벗어났을 때입니다. reload도 같은 검증을 거치므로, 벗어남이 남아 있으면 거절합니다.
5. 건너뛰지 않는 경우는 다음과 같습니다.
   - 키가 다른 모든 경우: ceiling, 프로필 지침, 엔진 설정(새 MCP 서버 등), computer control이 바뀜
   - 재시작이나 thread를 새로 불러오는 경우
   - QA(bounded) thread: 매 턴 reload
6. **플래그 `EGDESK_AGENT_RELOAD_REUSE=on`, 기본 off.** 규칙이 "플래그 기본 off"여서 그렇게 했습니다. 꺼져 있으면 기존 동작과 바이트 단위로 같고, 기존 런타임·브리지 테스트 552개가 통과합니다.

### 한계

- 새 대화의 첫 턴은 `thread/start`이고 비교할 키가 없으므로, **그다음 턴이 reload를 한 번 하고 키를 남깁니다.** 건너뛰기는 3번째 턴부터입니다 (테스트로 확인).

### 실제 모델이 내 가짜와 달랐던 점

1. **더 단호했습니다.** 선택(selection)의 관련도는 보관 기간 페이지 1, 나머지 모두 0이었습니다 (가짜는 .95 / .02). turn memory 쪽 scan도 보관 기간 페이지 1, 나머지 0이었습니다. 연결된 복원 절차 페이지는 scan에서 0이었고, 연결을 따라가 다시 본 `op_P2`도 0이었습니다. 이 페이지를 한 번도 붙이지 않았습니다.
2. **2턴의 turn memory가 가짜와 다르게 움직였습니다.** 실제 triage는 `tn_need` 0이면서 `tn_recall` .81을 줬습니다. "그럼 그 기간이 지나면…"을 앞의 것을 가리키는 질문으로 읽으면서도, 이미 가진 페이지로 충분하다고 본 것입니다.
   - c18 규칙은 recall을 보지 않습니다. need가 decided no이고 held 페이지가 보였고 목록이 완전하면 건너뜁니다. 그래서 fetch가 일어나지 않았습니다. 2턴에 scan 숫자가 없는 것이 그 증거입니다.
   - 옛 c11 규칙(recall이 no일 때만 건너뜀)이었다면 이 턴은 fetch했을 것입니다. **실제 모델이 c18 규칙의 필요성을 보여 준 사례**입니다. L3 시나리오의 recall .13과는 반대 방향으로 같은 결론입니다.
3. **PRUNE_HELD가 실제 모델에서도 작동했습니다.** 2턴의 선택은 후보 4개 중 보관 기간 페이지를 뺀 3개(rel_0..2)만 물었고, 모두 0이었습니다.
4. **1턴에 같은 페이지가 두 번 나갔습니다.** 선택의 `[item …]`과 메모리 packet의 `[page …]` 양쪽에 같은 본문이 있었습니다 (`duplicatesInTurn` 1, 두 대화 모두). 제품 기본(ONE_PACKET off)의 동작이고, 가짜에서도 같습니다. 짧은 페이지라 비용은 작지만, 페이지가 크거나 여럿이면 첫 턴 비용이 그만큼 두 배가 됩니다. 이번 스크립트의 `noResends`는 턴 사이만 비교하므로 이것은 실패로 잡히지 않습니다. 다음 실측에서 `EGDESK_TURN_MEMORY_ONE_PACKET=on`을 켜 보는 것을 권합니다.
5. **held-v1의 2턴 답은 판별력이 약했습니다.** 실제 모델은 1턴 답에 두 사실(47일과 자동 삭제)을 모두 말했습니다. 그래서 2턴의 "자동 삭제"는 페이지에서 왔는지 모델 자신의 앞선 답에서 왔는지 구분되지 않습니다. 반면 recall 대화의 1턴 답은 "47일간 보관"만 말했습니다. → `real-engine-memory-held-v2` (§3).

### 시간과 토큰

- **Decision 호출**: 1턴은 4번(triage, scan, 선택, 상태 읽기 `st_P1`)이고 각각 230~350 ms입니다. 선택은 .30 / .35 s로, 첫 턴 cold 예산 1.5 s 안입니다. 2턴은 2번(triage .25 s, 선택 .25 s)입니다.
- **엔진 입력 토큰** (턴별): 12,766 → 12,836입니다. 같은 thread의 1턴과 2턴 사이에 +75뿐이고, 이는 1턴 답(56)과 새 메시지 정도입니다. 보관 기간 페이지 본문이 다시 들어갔다면 그만큼 더 늘었을 텐데 늘지 않았습니다. 다만 이 페이지는 짧아서 분해능이 낮습니다. 캐시된 입력은 2턴에 12,672/12,836이었습니다.
- **Decision 토큰 수**: check 기록은 이름, ms, 상태, 확률만 남기고 토큰은 남기지 않습니다. 그래서 Decision 쪽 토큰은 이 기록에서 잴 수 없습니다. check의 Decision 호출 행에 `usage`(입력 토큰)를 넣으면 다음 실측부터 잴 수 있습니다 (L5 파일이라 건드리지 않았습니다).
- **지연**: 1턴 전체가 약 9.2~10.0 s이고, 2턴은 3.35 s입니다. Decision 호출을 턴 전체와 분리해서 보여 주는 값은 기록에 없습니다. cold 첫 대화의 `initialize`가 4.1 s, `mcpServerStatus/list`가 4.8 s 걸렸습니다 (턴 시간에는 포함되지 않음).

### 부수 발견: 이 check에서는 draft check가 한 번도 돌지 않습니다

- 두 대화 모두 calibration에 `draft_check ... fallback: evidence_unavailable`이 남았습니다. 원인은 코드로 확인했습니다. draft check는 direct 이면서 stateless가 아닌 DM 턴만 대상인데 (`turn.skip = 'ineligible'`), check의 대화는 모두 일회성 thread이고 Agent 프로필이 없습니다.
- 그래서 check가 기본으로 켜는 advisory draft check(`DEFAULT_DECISION_FLAGS`)는 실제로는 아무것도 하지 않습니다. turn memory와 같은 구조의 한계이고, L3와 L5가 정할 일입니다. 같은 방식의 옵트인이 필요합니다.
