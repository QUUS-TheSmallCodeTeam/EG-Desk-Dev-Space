## 1. 제공자 429 분류
### 1-1. 시뮬레이션 (8개 본문, 항목당 decide / DM(`runChatChoice`) / Board(prepare→run) / 키 검증 POST 4회 호출)
원본(`before-429.log`):
| 본문 (code / type) | EG-Desk code | retryable | DM·Board 호출자 | 키 검증 화면 문구 |
|---|---|---|---|---|
| credit_balance_exhausted / insufficient_quota | no_credit | false | `{status:'manual'}` | 크레딧 없음 |
| organization_spend_limit_exceeded / insufficient_quota | **rate_limited** | **true** | manual | "요청 한도에 걸림… 잠시 뒤 다시 시도" |
| project_spend_limit_exceeded / insufficient_quota (+Retry-After 60) | **rate_limited** | **true** | manual | 동일(오안내) |
| project_spend_limit_exceeded (type 없음) | **rate_limited** | **true** | manual | 동일 |
| organization_usage_limit_exceeded / insufficient_quota | **rate_limited** | **true** | manual | 동일 |
| code 없음 / insufficient_quota | no_credit | false | manual | 크레딧 없음 |
| rate_limit_exceeded / requests | rate_limited | true | manual | 잠시 뒤 다시 시도 |
| slow_down / rate_limit_error (+Retry-After 5) | rate_limited | true | manual | 잠시 뒤 다시 시도 |

- 자동 재시도: **없음**. 호출당 제공자 요청 정확히 1회, 300ms 유휴 후 합계 32 = 8 본문 x 4 호출(재시도 0). Retry-After는 어디서도 읽지 않는다.
- 키·모드: 모드 저장 호출 0회. 키 값은 그대로(검증 POST는 사용자가 누른 저장이라 `savedAt`만 갱신되는 기존 동작; 표의 "changed by verify-save" 표식은 이 savedAt 갱신을 뜻함). 키는 삭제되지 않는다.
- 문제: 지출·사용 한도 429가 `rate_limited`+`retryable:true`로 분류된다. 현재 호출자가 재시도하지는 않지만(DM/Board는 모든 오류를 manual로 삼킴, 키 검증 화면만 문구가 달라짐), (a) 검증 화면이 "잠시 뒤 다시 시도하세요"라고 오안내하고 (b) `retryable` 플래그를 읽는 미래 호출자가 헛되이 재시도하게 된다. 위치: `egdesk-decision-client.mjs` `classifyDecisionFailure`(원본 :68-78), `NO_CREDIT_CODES`(:44).

### 1-2. 결정과 근거
- `no_credit` 재사용 vs 새 코드: **새 닫힌 집합 코드 `spend_limit_reached`** 추가, apiCode 보존. 이유: `no_credit`의 소비자 문구는 "크레딧이 생기면 바로 쓸 수 있습니다"(설정 화면 `EGDeskAccountSettingsView.sys.mjs`)인데 지출 한도는 크레딧 충전으로 풀리지 않고 한도 상향/제거 또는 월 초기화가 필요하다(https://developers.openai.com/api/docs/guides/spend-limits). 복구 행동이 달라 메시지를 구분해야 한다. 이는 canon의 "provider가 계량한 사용량과 로컬 상태는 별개로 정직하게 말한다" 취지에도 맞다(DECISION_MODEL_CONTEXT_SETUP 사용량 서술).
- 비재시도: https://help.openai.com/en/articles/5955604-troubleshooting-api-rate-limits-and-429-errors "Retrying a billing, spending, or quota error does not restore access."; 오류 코드 목록 https://developers.openai.com/api/docs/guides/error-codes (credit_balance_exhausted, organization/project_spend_limit_exceeded는 비재시도, `slow_down`/"Rate limit reached"는 재시도·Retry-After).
- 본문의 `type`이 `insufficient_quota`일 수 있어도(Help Center) 한도 코드가 이긴다: `code`를 먼저 검사해 `spend_limit_reached`, 그 다음 `code` 또는 `type`이 no_credit 집합이면 `no_credit`, 나머지는 `rate_limited`(재시도 가능). 순서 때문에 `{code: project_spend_limit_exceeded, type: insufficient_quota}`가 `no_credit`으로 잘못 가지 않는다.
- Retry-After: 자동 재시도가 없고 호출자도 쓰지 않으므로 이번에는 보존·처리하지 않음(후속 후보).

### 1-3. 소비자 점검 (grep: helper, overlay, scripts의 `no_credit|rate_limited|retryable|apiCode|DECISION_ERROR_CODES`)
- `DecisionError`는 `DECISION_ERROR_CODES`에 없으면 `bad_response`로 바뀌므로 목록에 추가(필수).
- `egdesk-decision-http.mjs` `SAVE_ON`: 인증된 키는 저장해야 하므로 `spend_limit_reached` 추가(`no_credit`과 동일 취급).
- `egdesk-context-setup.mjs`(`failureCode`)와 browser-reflex는 `error.code`를 닫힌 목록 없이 reason 문자열로 전달 → 변경 불필요.
- `codex-chat-runtime.mjs` DM 선택과 Board 경로는 모든 오류를 manual로 처리 → 변경 불필요.
- 설정 화면 `EGDeskAccountSettingsView.sys.mjs` `DECISION_VERIFICATION_TEXT`: 코드 없으면 `unreachable` 문구("OpenAI에 연결하지 못했습니다")로 떨어지므로 문구 추가가 **엄격히 필요**.

### 1-4. UI 문구 (Main이 L2와 정리할 것)
- 추가 문자열 1개(설정 화면 키 검증 결과, DM 결과 렌더링 아님): `spend_limit_reached: '지출·사용 한도에 도달 · 키는 저장했습니다. OpenAI에서 한도를 올리거나 다음 달 초기화 뒤에 쓸 수 있습니다.'` DM outcome 문구는 건드리지 않았다.

### 1-5. 이후(after-429.log)
- organization/project spend limit, organization_usage_limit_exceeded → `spend_limit_reached`, retryable=false, apiCode 보존, 검증 화면 코드도 `spend_limit_reached`(키 저장됨).
- credit_balance_exhausted와 type만 insufficient_quota → `no_credit` 유지. 일반 rate limit·slow_down → `rate_limited` retryable=true 유지.
- DM·Board 호출자 결과는 이전과 같이 manual(변화 없음), 자동 재시도 0(합계 32=32), 모드 저장 0.

## 2. 월 롤을 앞으로만
- 문제(c1 관찰 재현, `clock.log` before = `5edf124`): 12월에 상한 3000 소진 → 재시작 시 시계가 11월 → `{month:'2026-11', inputTokens:0}`, `canSpend true`, 파일이 11월/10으로 덮여 12월 3000이 소실. 그 뒤 시계가 12월로 돌아와도 0부터. 상한 우회 경로.
- 수정: `roll()`이 `current > month`일 때만 초기화(문자열 `YYYY-MM` 비교). 이른 시계는 저장된 월·합계 유지.
- 근거: 벽시계는 NTP·수동 설정·부팅 직후 오류로 되돌아갈 수 있다(MDN High precision timing https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/High_precision_timing: `Date`는 단조 증가하지 않음; clock_gettime(3) https://man7.org/linux/man-pages/man3/clock_gettime.3.html: CLOCK_MONOTONIC만 불연속 점프에 영향받지 않음). 다만 단조 시계는 재시작을 넘지 못하고 "달력상 월"에는 쓸 수 없어 벽시계를 쓰되, **저장된 상태를 앞으로만 가는 래칫**으로 취급한다. 지출 가드이므로 불확실할 때는 더 엄격한 쪽(합계 유지)을 택한다.
- 이후: 시계가 11월을 가리켜도 `{2026-12, 3000, cap 3000}` 유지, `canSpend false`, 파일 3010으로 누적, 12월 복귀 후에도 3010. 다음 달(2027-01)에는 0으로 초기화(테스트).
- 잔여 위험(기록): 시계가 한 번 크게 미래(예: 2030)로 맞춰진 채 결정이 저장되면 그 월까지 합계가 유지되어, 상한이 있는 소유자는 막힌 채로 남는다. 현재 상한 설정 UI가 없고 기본 상한이 없으므로 영향은 상한을 직접 지정한 소유자에 한정. 상한 UI가 생길 때 "합계 초기화" 동작과 함께 다뤄야 함.

## 5. 철학 점검
원칙: **사용자가 지출을 통제하며, 모델 추천과 승인된 실행을 분리한다.** 지출 한도에 막힌 것을 "잠깐 기다리면 된다"로 오안내하거나 재시도 가능으로 표시하면, 소유자가 직접 건 한도를 시스템이 우회하려는 신호가 된다. 비재시도·고유 코드로 소유자가 해야 할 행동(한도 상향 또는 월 초기화)을 정확히 알려 주고, 로컬 합계는 시계 되감김으로 소유자의 상한을 풀지 못하게 래칫으로 고정했다. 재시도는 여전히 새 승인 요청에서만 생긴다.
