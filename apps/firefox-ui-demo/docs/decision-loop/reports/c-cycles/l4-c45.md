## 설계

채움 요청은 가이드와 재료뿐이고 답 본문을 읽지 않는다. 가이드는 요청과 턴의 기억 재료로 Decision이 정한다. 그래서 턴이 받아들여질 때 같은 흐름을 답 없이 채움 요청까지만 돌려 채움 턴을 먼저 보내고, 답이 게시된 뒤의 흐름은 **전부 예전 그대로** 돌린다(답을 인용한 placement, fit, order, fill_check, coverage, 게시). 단 하나만 다르다: 첫 채움 요청이 바이트 단위로 같으면(해시) 먼저 받은(또는 아직 오는 중인) 응답을 쓴다. 보드는 답이 있고 coverage가 통과한 뒤에만 게시된다.

- 새 `helper/egdesk-briefing-prefill.mjs`: 답 하나당 한 칸(`createPrefillStore`), 채움 요청의 해시로 응답을 기억, 한 번만 내줌(복사본), null 응답은 내주지 않음, 한 요청은 한 번만 보냄, 칸 수와 나이 제한. `cachingFill`이 본 흐름의 `fill` 자리에 들어간다.
- `runSkeletonFlow({ prefill: true })`: 답 없이(예전 several / one_sentence 경로) 첫 채움 요청까지만 하고 멈춘다(재시도, 조각 채움, 검사, coverage 없음). 아무것도 게시하거나 제안하지 않는다.
- `egdesk-board-presentation-http.mjs`: `handle.prefill({ run, request, candidates?, viewport? })`와 observe에서의 칸 가져가기. 이 핸들러는 Decision 요청을 한 번에 하나만 허용(둘째는 manual)하므로, prefill의 판단 요청은 진행 중인 요청을 기다리고, 답 뒤 흐름은 prefill의 판단 요청이 끝나길 먼저 기다린다(`idle()`, 최대 15초). 시험에서 5번의 자체 Decision 요청 중 manual 처리 0.
- 런타임(L5 합의, 새 한 줄과 한 메서드만): 보내기 경로에서 `noteTurnMemoryOn` 호출 바로 뒤에 `this.startBriefingPrefill(run, body)`, 그리고 `startConversationFlow` 옆에 그 메서드(`decisionContext.briefingPrefill`이 있을 때만, 백그라운드, 절대 던지지 않음, 턴을 지연시키지 않음). `internalText`, `internalTurns`, `canInternalTurn`은 건드리지 않았다.
- 브리지: `EGDESK_BRIEFING_PREFILL=on`과 `EGDESK_BRIEFING_FLOW=on`일 때만 `decisionContext.briefingPrefill`을 달고 `briefingDeps({ prefill })`를 켠다. 기본은 둘 다 없음.
- 점검 훅: 새 플래그 `EGDESK_BRIEFING_PREFILL`(등록), 켜면 훅이 `chat.decisionContext.briefingPrefill`을 달고, 기록의 시작 표시를 보내기 시점으로 앞당겨 prefill 쪽 비공개 턴, 엔진 요청, Decision 요청이 그 턴의 기록에 들어가게 한다(`flow.prefill = { sent, served, missed, nullReplies }`). 점검 구성 목록(`BRIDGE_COMPOSITION.keys`)에 `briefingPrefill` 한 단어 추가(L5 파일).
- 시나리오 `real-engine-briefing-realistic-v4` = v3 + PREFILL on(schema on, 손수 전달 on, LAYERS on), 기대값은 v1과 같다.

## 시험 (녹음된 답이 아니라 모의 앱 서버의 실제 런타임과 실제 핸들러 경로)

끝에서 끝까지(`mounted`): prefill 뒤 포크 턴 1번, Decision 요청 place, fit, order 3개만, 답 인용 없음, 게시 0; 이어 observe는 채움을 다시 묻지 않고(`prefill = { sent:1, served:1, missed:0 }`) 요청 8개(3 + 5) 뒤 `presented`, 만들어진 카드는 prefill 없는 대조 실행과 같다. 진행 중인 prefill을 기다리는 경우, 다른 재료(미스, 엔진 다시 호출), null 응답은 내주지 않음, 기본 꺼짐은 아무 일도 안 함, 보드를 모르는 prefill의 미스(문서화된 한계), 런타임 훅(던지는 훅, 거부하는 훅, 훅 없음에도 턴 정상), 스토어 단위 시험 4개, v4 시나리오 파일과 플래그 등록.

## 한계와 다음 확인

- 시간 이득은 추정이다. 실측은 v4 실행이 필요하다. 기대: 총 시간 약 max(답 턴, 3초 + 채움 턴) = 40~63초 대 v3의 93초 안팎(29bh v2 92.9초 기준).
- prefill은 크롬이 보여 준 보드를 모른다(보드 카드는 크롬이 답 뒤 observe에서만 보낸다). 그 대화에서 직전 observe가 본 보드를 쓰고, 처음이면 빈 보드로 가정한다. 보드에 카드가 있으면 가이드의 재사용 항목이 달라져 요청이 다르고 **미스**(엔진을 예전처럼 한 번 더 부름, 손해는 한 번의 낭비된 채움 턴). 점검 환경(빈 보드)에서는 적중한다. 제품에서 적중률을 올리려면 크롬이 보내기 요청에 보드 후보를 같이 실어 주면 된다(`prefill({ candidates, viewport })`는 이미 받는다). 크롬 쪽 변경이라 이번에는 하지 않았다.
- L5 답: 새 스레드(fresh)의 내부 턴은 별도 엔진 스레드라 부모 실행과 섞이지 않는다. 진행 중인 부모 스레드를 **포크**하는 경우는 검증되지 않았다(엔진이 거부하거나 직렬화할 수 있음). 그 경우 prefill은 null을 받고 본 흐름이 예전처럼 채운다(시험으로 확인한 null 대체 경로). 켜기 전에 실제 엔진으로 v4를 돌려 `flow.prefill`을 봐야 한다.
- L5는 c34가 같은 보내기 경로(디스패치 꼬리)를 건드리므로 c34 병합 뒤 int/c14 위로 리베이스하라고 했다. 현재 int/c14 기준 병합은 충돌 없음.
