# L4-c7 보고서: 이미 렌더된 컴포넌트의 재사용·회수를 의식하는 Answer Briefing

브랜치 `lane/c7-briefing-reuse` (기준 `int/c6` 828c150). 커밋 `d3f1e64`(시험+지원 모듈), `276561b`(구현). 합성 하네스 결과이며 설치된 앱 검증이 아니다.

## 1. 런타임 옵션: 보드에 이미 있는 컴포넌트의 실제 사실 (`helper/egdesk-briefing-flow.mjs`)
컴포넌트 = 보드에 올라온(`onBoard`) 후보 중 보내도 되는(`maySend`) 것만(아닌 카드는 개수에도 안 잡힘). 별칭 `T#`(불투명)과 사실:
- `owner`(agent / user / shared; 출처 불명은 user로 간주), `createdForAnswer`(어느 답변을 위해 만들었나) → `origin`: `agent-earlier`(이전 답변) / `agent-current` / `user` / `shared`.
- `superseded`(같은 outputKey의 더 새 출력이 대체), `stale`(신선도), `visibility`(visible / collapsed / offscreen).
- **회수 가능(`retrievable`)은 코드가 정한다**: `origin === 'agent-earlier'` 그리고 (`superseded` 또는 `stale`) 그리고 이미 접힌 상태가 아님. 사용자가 만든 노트(stale 표시가 있어도), 공유 컴포넌트, 이번 답변을 위해 만든 출력, 출처를 모르는 컴포넌트, 이미 접힌 컴포넌트는 회수 선택지가 아예 없다. 브리지 쪽 DTO 검증도 이 규칙을 다시 적용해서, chrome이 `retrievable:true`를 위조해도 거부한다(시험).
- 보고서의 "부분"(`P#`): 제목(`##`) 절 단위(제목이 없으면 문단), 20자 이상, 최대 6개. 각 부분마다 이미 그 부분이 이름을 대는 보드 컴포넌트(`coveredBy`)를 로컬에서 계산.

## 2. Decision 단계 (`/decision/briefing-reuse/*`, 기존 Board 핸들러의 판정 테이블에 추가)
한 요청: 컴포넌트마다 choice `component_T#`(`reuse` / `irrelevant`, 그리고 코드가 허용한 컴포넌트에만 `retrieve`), 부분마다 predicate `new_P#`("기존 컴포넌트가 못 보여줄 때만 새 컴포넌트가 필요한가?"). 막대(자리표시자): 컴포넌트 0.75·여유 0.2, 새 컴포넌트 필요 0.7. 불확실한 컴포넌트는 `undecided`(재사용도 회수도 안 함), 쓸 수 없는 답(거부, 제공하지 않은 선택지)은 전체 `manual`. 모드·예산·4초 마감·티켓·중단 시 추정 예산·응답 시점 재확인은 기존 핸들러 경로 그대로(시험: advisory는 기록만, 월 한도는 전송 전 거절, 응답 없는 판정은 약 4초에 timeout). 보정 로그는 기존 API만(컴포넌트별 `choice`+`attach/act/skip/hold`, 부분별 `relevance`), 내용 없음.
- **새 컴포넌트 허용 규칙**: 판정이 "필요"라고 했고 **그리고** 그 부분을 이미 덮는 재사용 컴포넌트가 없는 부분에만 허용(재사용 우선 가드; 막힌 부분은 `newBlocked`로 보고).

## 3. 주관 모델 설계 제약 (`resolveDesign`의 `constraint`)
- 설계 요청에는 재사용 판정된 컴포넌트만 target 후보로 나가고(회수·무관 컴포넌트는 목록에도 없음), `reuse`, `retire`(정보), `newAllowed`(허용 부분과 라벨), `maxNew`가 붙는다.
- 검증 사유: 재사용 별칭 외 target(`not-reusable-target`), 재사용 판정된 것을 하나라도 안 씀(`reuse-unused`), 새 컴포넌트는 `new:P#` 토큰으로만, 허용된 부분만(`new-not-allowed`), 부분당 하나(`new-duplicate`), 제목·요약 명세 필수(`new-missing-spec`), 쓰이지 않는 명세(`new-unreferenced`), 새 컴포넌트만 가리키는 단계만 있는 설계(`only-new`). 위반하면 사유와 함께 재요청(최대 2회, c6의 한도).
- 새 컴포넌트를 가리키는 단계는 `pendingSteps`로 남고(발행 인자에는 아직 없음), 호스트가 컴포넌트를 만든 뒤 `completeBriefingArgs(outcome, { N1: ref })`로 완성한다. 완성본은 기존 `egdesk_publish_briefing_multi` 스키마와 `validBriefing`에 맞는다(시험). 흐름 점검은 새 컴포넌트의 제목·요약을 계획된 target(`N#`)으로 보고 다른 단계와 똑같이 판정한다.
- **회수는 제안일 뿐**: 통과한 브리핑과 함께 `retrievals:[{alias,id,ref}]`가 나가고, 호스트가 `retrievalPlan()`을 컨트롤러 `offerRetrieval()`에 올리면 미리보기 선택지 하나가 뜬다. 적용 시 기존 경로(모드·키·권한·시간창 재확인 → commit → history) 사용. 동작은 **내 화면에서 카드를 접는 것**(`egd-card-collapsed`, 카드의 위치·크기·z는 그대로, 삭제 없음, 공유 Board 쓰기 없음). 실행취소는 패널 되돌리기와 ⌘Z/Shift+⌘Z가 하나의 history를 쓴다(c2의 `extra`/`token`/`guard` 확장에 `collapsed`를 실었다). 사용자가 직접 펼쳤으면 ⌘Z는 건너뜀(기존 알림). 점검을 통과하지 못해 채팅으로 떨어지면 회수 제안도 내지 않는다.

## 6. 열린 점·결정 요청
- **출처 사실이 아직 캔버스에 없다**: `owner`/`createdForAnswer`/`superseded`는 호스트가 줘야 하는데, 오늘 캔버스 카드에는 "이 Agent가 이 답변을 위해 만든 컴포넌트"라는 기록이 없다(출력 저장소에는 `answerId`/`outputKey`/`version`/`previousId`가 있음). 어댑터(출력 저장소 + 열린 뷰 → 후보)와 출처 기록이 필요하다. 출처가 없으면 안전하게 user로 취급되어 회수가 일어나지 않는다.
- **'숨김/철회'는 캔버스에 개념이 없어 '접기'만 구현**했다. 접힘은 Desk 세션 저장의 `collapsedViewIds`로 남는데, Board 공동 카드는 `markAgendaDirty`가 `recordPose`로 빠져 세션 저장을 예약하지 않는 기존 동작이 있어(코드 읽기) 접힘이 다음 세션 저장까지 보존되는지는 실제 앱에서 확인해야 한다.
- 전송 동의 정책(c6에서 이월): 재사용 판정에는 컴포넌트 라벨·요약·출처 표지가 외부로 나간다(사용자 노트 포함, 보내도 되는 것만). 상시 동의(mode on)로 둘지 실행마다 검토할지는 사용자 결정. `allow` 콜백이 둘 다 지원.
- 보정 로그: `feature`가 닫힌 어휘라 말풍선 판정·재사용 판정·흐름 점검·배치 점검을 구분하는 필드가 없다(질문 행 모양으로만 구분). `outcome.next` 미배선.
- 호스트 연결(최종 보고 시점 트리거, 후보 어댑터, 주관 모델 호출, 기존 도구로 발행, 새 컴포넌트 생성, 회수 미리보기 표시)은 이번에도 미구현.
