## 2. 이 대본이 드러낸 코드 결함 하나와 고친 것
- c35의 "줄 텍스트 null = 자료 문장 중 줄에 들어가는 만큼" 복사는 긴 원장 항목에서 위험: 예 "…표준 게이트 교체: 242개 파일 5752건 통과" 항목은 첫 문장만 복사되어 **수치가 빠지고**, 그 줄은 자료에 의해 "지지됨"이라 아무 검사도 못 잡음. 수정: 복사는 **자료 전체가 줄에 들어갈 때만**(`copyThatFits`), 아니면 그 줄은 모델이 써야 하고 못 쓰면 줄 이슈(mismatch). 프롬프트의 복사 규칙도 그렇게 바꿈("자료 글이 max보다 길면 null 대신 id, 숫자, 날짜, 이름을 남긴 max 이내 줄을 쓴다"). 기존 check-9/11의 실제 줄(82자 이하)은 그대로 복사됨.
- fake 테스트(0.171처럼 ephemeral fork 거부)로 재현: 충실한 모델은 통과(두 대화), 줄을 첫 90자로 자르는 모델은 판정기(스크립트 yes)가 "자료로 지지됨"이라 `presented`지만 **`factsInCards`가 잃은 사실을 이름으로 지적**(12개 중 6개 이상), 모든 줄을 null로 쓰는 모델은 `presented`가 되지 못함(복사 거부), 한 흐름의 줄 순서를 거꾸로 쓰면 `inOrder`가 어느 목록의 어느 사실인지 지적.
- 남은 한계(보고): 답의 사실은 코드가 최대 6개만 coverage에 묻는다(`SKELETON_LIMITS.maxFacts` 6). 이 대본의 12행 표는 6개를 묻고 7개를 자름(`$L/evidence/l4-c37/facts-count.txt`). 잘린 사실은 coverage가 검증하지 않고 대본의 `factsInCards`만 검증. 한도 상향은 제품 결정이라 하지 않음(소유자 결정).

## 3. L7의 발견(additionalContext 약 2,500토큰 초과분이 디스크로 빠짐)이 브리핑 요청에 영향을 주는가
- 아니오(설계상, 와이어로 확인). 브리핑의 비공개 턴은 글을 turn/start의 `input`(사용자 메시지)에 넣고 `additionalContext`를 쓰지 않음: fake 테스트가 모든 브리핑 fill의 turn/start 키(`threadId, input, clientUserMessageId, effort, model[, outputSchema]`)와 fresh thread의 thread/start에 `additionalContext`가 없음을 고정. Decision 모델 요청은 Codex로 가지 않는 별도 HTTP. additionalContext를 쓰는 것은 사람의 턴(turn memory 패킷, decision context, extraContext)뿐.
- 크기는 참고: 이 대본의 fill 프롬프트는 6,884자(자료 12개 + 안내)로 2,500토큰 항목을 넘는 크기이지만 additionalContext 항목이 아니라 입력 메시지. 실제 엔진에서 입력 메시지가 잘리는지는 이 대본의 재실행이 확인함(보드에 12개 사실이 있으면 아니다). `EGDESK_TURN_MEMORY_ENGINE_CONTEXT=split` 플래그는 L7 c32(미병합, 현재 int/c14 소스에 없음)에 있고 브리핑에는 필요 없음.
- 간접 영향: 브리핑의 자료는 EG-Desk의 저장된 기억 행(`memoryMaterialsFor`)에서 오지 Codex가 본 additionalContext에서 오지 않으므로, 답이 넘침으로 사실을 잃어도 자료에는 남음(그때 답의 사실이 자료보다 적을 뿐).
