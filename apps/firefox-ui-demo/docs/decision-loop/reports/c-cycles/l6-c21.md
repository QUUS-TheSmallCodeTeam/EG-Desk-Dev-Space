## 1. 분리 warm-up probe 설계 (보내지 않음)

### 물을 것
[측정] 여섯 점에서 빠른 측정 요청은 모두 방금 도착한 warm-up 의 소켓을 재사용했고, 느린 요청은 모두 새 소켓이었다. 소켓 재사용과 "최근 트래픽" 이 항상 같이 왔다. A2 (새 소켓인데 빠름) 는 꼬리가 거의 없던 반복이어서 둘을 가르지 못한다. 이 probe 는 둘을 가른다. 제품의 transport 를 그대로 쓴다.

### 구성 (`proofs/decision-real-measure/turn-context-warmup-sep/{N1,N2,Y1}/plan.json`)
빌더 `buildSeparationPlan` / `analyzeSeparation`, CLI `node scripts/egdesk-turn-context-latency-plan.mjs --sep [--write]`, 등록부에 등록. 추정 입력 **3,748 토큰 (한도 4,000)**, run 상한 합계 4,140, 요청 8개.

| run | 요청 (순서대로) | 가르는 것 |
|-|-|-|
| **N1, N2** (각각 10분 이상 쉰 뒤) | `warmup` 제품 warm-up 본문 → 1 s 뒤 `same` turn_context (**같은 transport**, warm-up 의 소켓을 재사용) → 1 s 뒤 `fresh` turn_context (**새 transport**: 이전 것을 먼저 닫아 새 TCP 와 TLS 연결, 재사용 불가) | 소켓 재사용이 *필요한가*: warm-up 이 도착한 직후인데 새 소켓에서도 빠른가 |
| **Y1** (10분 이상 쉰 뒤) | `first` 제품 warm-up 본문 (꼬리 검출, 소켓을 11분 유지하는 transport) → **600 s** 기다림 → `after` turn_context (같은 transport, 소켓이 살아 있으면 재사용) | 소켓 재사용이 *충분한가*: 최근 트래픽 없이 재사용된 소켓이 빠른가 |

- `warmup`/`first` 가 800 ms 를 넘으면 그 run 에 유휴 꼬리가 있었다는 뜻이다 (꼬리는 간헐적이므로 이 검출이 필요하다: A2 는 꼬리가 없었다).
- N 의 `same` 은 그 run 에서 warm-up 이 유지됐는지 보는 기준이다. `same` 이 빠르면 warm-up 이 유지된 것이고, 그때 `fresh` 가 느리면 새 소켓 때문이다.
- Y1 은 10분 동안 이 기계에서 Decisions 요청을 더 보내면 안 된다. 점 러너가 끼어든 전송을 `interleaved` 로 표시한다 (테스트로 확인).

### 러너 확장 (보호 장치 유지, 제품 코드는 그대로)
- 요청별 `freshSocket: true`: 그 요청 직전에 transport 를 닫고 새로 만든다 (`beforeRequest` 훅). 제품 transport 계획에서만, `true` 만 허용.
- 계획의 `transportIdleMs` (1 s ~ 15분): transport 가 놀고 있는 소켓을 얼마나 두는지. 제품 transport 계획에서만. 제품의 55 s 는 그대로다.
- 계획의 `waitLimitMs` (600 s 초과 ~ 15분): 요청별 대기와 합계 상한을 올린다. **record-only 요청만, 제품 transport 계획에서만**. 선언이 없으면 이전 상한 (요청당 120 s, 합계 600 s) 이다. 대기는 쉬는 것일 뿐 재시도가 아니다.
- 점 러너: `--set sep --point N1|N2|Y1 [--send]`, `--set sep --status|--analyze`, 결과 파일 `<HOME>/turn-context-warmup-sep-results.json` (0600). 10분 규칙, 끼어듦 표시, 점별 덧붙이기는 이전과 같다. 여섯 점의 결과 파일과 섞이지 않는다.
- 테스트: 상한 선언의 거부 규칙 (범위, 제품 transport 필요, record-only 필요), `freshSocket`/`transportIdleMs` 검증, `runPlan` 훅 호출 순서 (대기 뒤, `warm()` 읽기 전, 그 요청에만), 실패한 교체는 그 요청과 이후를 보내지 않음, `main` 에서 교체된 transport 에 `fresh` 가 실리고 이전 것이 먼저 닫힘, 점 러너가 Y1 에 600 s 대기와 11분 소켓 상한을 쓰고 끼어듦을 표시, 빌더 파일 일치와 한도.

### 등록한 판독
N run 은 `warmup` 이 느렸고 (꼬리 있음) `same` 이 빠를 때 (warm-up 유지) 만 "의미 있는" run 이다.

| 판독 | 조건 |
|-|-|
| **warmth, not the socket** | 의미 있는 N run 이 하나 이상 있고, 모두 `fresh` 가 빠르며, Y1 이 (재사용되고 빠름) 이 아니다 |
| **the socket matters** | 의미 있는 N run 에서 `fresh` 가 느린 것이 하나 이상 |
| **mixed** | 의미 있는 N run 끼리 엇갈림 (하나는 빠르고 하나는 느림): 반복 |
| **reuse alone is fast too** | Y1 이 재사용됐고 `after` 가 빠름. 꼬리가 간헐적이라 이것만으로는 약하다: Y1 을 반복 |
| **inconclusive** | 의미 있는 N run 이 없음 (꼬리가 없었거나 warm-up 이 유지되지 않음) |

Y1 자체의 읽기: `after` 의 소켓이 재사용되지 않았으면 "긴 유휴 뒤에는 소켓이 살아 있지 않다: 재사용은 제품이 얻을 수 없다" (이 경우 소켓 재사용만으로는 A 와 B/C 의 차이를 설명할 수 없다는 쪽으로 읽힌다), 재사용되고 느리면 "재사용이 꼬리를 막지 못한다", 재사용되고 빠르면 위의 "약함".

[한계] Y1 은 한 번뿐이다 (토큰 한도). `after` 의 꼬리 유무는 따로 알 수 없어서, Y1 이 "재사용 + 빠름" 이어도 꼬리가 없었을 수 있다. 소켓이 10분 넘게 살아 있을지는 서버 쪽 keep-alive 에 달려 있다 (살아 있지 않으면 그것이 곧 결과다). 이 probe 는 소켓과 TLS 세션 재개를 따로 가르지 않는다 (새 transport 는 둘 다 없앤다).

| `EGDESK_CONVERSATION_FLOW` | advisory (유지) | 실제 엔진에서 메시지를 쓰는 fork 가 점검 환경(임시 스레드)에서는 불가능하다. 저장된 스레드의 fork 는 smoke-5 에서 성공했다. `FLOW_COPY.stalled` 승인 대기는 그대로 |
| `EGDESK_BRIEFING_FLOW` | 아직 아님 (유지) | 실제 엔진 점검 0/2 (fork 불가 환경이라 정확도 증거가 아님). owner 의 문구·렌더러 결정이 막고 있다 |
| 나머지 | 유지 | 새 실측 없음 |

[한계] "켜도 됨" 둘 (`WORK_PLACEMENT`, `PRESENCE`) 은 이번에도 새 실행이 없다. 여정 v7 은 v6 와 다른 계획 (66개 hard 검사, 문구 `faithful`) 이어서 v6 와 곧바로 비교하지 않았다.

## 5. 크기 probe 판독 (S1, S2 모두 들어옴)

`--set size --analyze`: **`size does not matter`** (등록한 규칙: 두 warm-up 이 모두 느려서 꼬리가 두 run 에 모두 있었고, 두 측정 요청이 모두 빠름). 두 run 모두 600 s 이상 쉰 뒤에 시작했고 끼어든 전송이 없었다.

| run | warm-up 본문 | warm-up 요청 | 측정 turn_context (1 s 뒤) | 측정 소켓 |
|-|-|-|-|-|
| S1-small | 제품 warm-up 본문, **실제 입력 161 토큰** | **1,360 ms** (서버 546, 꼬리 있음) | **248 ms** (서버 170, 857 토큰) | 재사용 |
| S2-large | 648 토큰 본문 (실제 653) | **1,703 ms** (서버 530, 꼬리 있음) | **271 ms** (서버 173, 856 토큰) | 재사용 |

[해석]
- c18 설계의 가정 ("작은 제품 warm-up 본문도 648 토큰 본문처럼 데운다") 이 이 자료에서 맞았다. 161 토큰 warm-up 뒤 1 s 에 248 ms, 653 토큰 warm-up 뒤 271 ms 였다.
- 두 warm-up 이 모두 꼬리를 겪었고 (1.4 s, 1.7 s), 서버 시간이 거의 같다 (546 / 530 ms). 꼬리의 크기는 본문 크기와 무관해 보인다 (c15 와 같은 방향).
- **구간당 비용은 추정이 아니라 측정값이다: 161 입력 토큰** (적합 모델 추정 159, c20 의 근거였던 11/24 지연 probe 의 161 과 같다).
- [한계] 크기마다 한 번씩이다 (반복 없음). 두 측정 요청 모두 재사용 소켓이어서 소켓 재사용과의 교란은 그대로 남아 있다: 이것을 가르는 것이 위 1절의 분리 probe 다.
