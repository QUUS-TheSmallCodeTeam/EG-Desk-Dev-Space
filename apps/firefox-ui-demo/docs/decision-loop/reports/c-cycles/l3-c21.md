## 1. run 도중 사람 메시지의 heartbeat 쪽 (Main 결정 4)

**L2와의 계약** (런타임 쪽은 내가 구현했고, 화면·브리지는 L2가 한다):

| 항목 | 내용 |
|-|-|
| 플래그 | `decisionContext.conversationFlow.inRunMessages()` → true. 브리지 제안 이름은 `EGDESK_IN_RUN_MESSAGES=on`(개발자 플래그, 기본 꺼짐)이고 L2가 연결한다. heartbeat(conversationFlow)가 켜져 있어야 동작한다. |
| 보내는 쪽 | 화면이 run 진행 중 입력된 메시지를 `/chat/send` 본문 그대로, `inRunMessage: true`만 붙여 보낸다. |
| 응답 | `{ accepted, durable, inRun: true, held: true, requestId, conversationId, runId, localMessageId }` |
| 기록 | 메시지는 즉시 그 run의 사람 메시지로 기록된다(`message.completed`). |
| 플래그 꺼짐 / 진행 중 run 없음 | 기존과 같다(RUN_IN_PROGRESS, 또는 새 턴). |
| 이후 사건 | 진행 메시지 하나(`message.completed`, assistant), 또는 `turn/steer`(사람의 글 그대로), 또는 `run.stop_requested` |

**판단 흐름**
- 메시지는 heartbeat 사실이 된다(대기 최대 8개, 인용 600자). `heartbeat.nudge()`로 다음 beat가 0.5초 안에 온다.
- beat는 그 메시지 하나만 인용해 yes/no 3개를 묻는다(R1/R4). 맥락으로는 run의 자기 글을 쓴다(run의 데이터 허용 범위 안에서):
  - `person_status` "Does this message ask what is happening, how far along the work is, or why it stopped?"
  - `person_change` "Does this message change or redirect the task …?"
  - `person_stop` "Does this message ask the assistant to stop or cancel the work?"
- 결정은 코드가 한다(R2):

| 답 | 동작 |
|-|-|
| stop | run 중지 |
| change | steer |
| status만 | 짧은 진행 답. 주관 모델이 fork에서 쓰고, 다른 메시지처럼 검사한다. 쓰기·검사가 실패하면 steer로 넘어간다. |
| 그 외, 판정 실패, 끝나지 않은 라운드 | steer (안전한 기본값: run이 사람의 글을 받는다) |

- 보정 기록 어휘를 추가했다: `beat_person_*`, flow `reply/steer/stop`.
- 테스트(`helper/egdesk-in-run-messages.test.mjs`):
  - "아니 지금 왜 멈췄니?" → 판정 1회, 진행 답 1개, steer와 중지 0
  - "그거 말고 B부터 해줘" → `turn/steer`로 사람의 글 그대로 전달, 답 게시 없음
  - 중지 요청 → interrupt
  - 판정 실패 → steer
  - 플래그 꺼짐 → RUN_IN_PROGRESS
- 변이 5건 모두 잡혔다: 순서 뒤집기, 기본값을 reply로, steer 문구 바꾸기, 플래그 무시, 인용 제거.
