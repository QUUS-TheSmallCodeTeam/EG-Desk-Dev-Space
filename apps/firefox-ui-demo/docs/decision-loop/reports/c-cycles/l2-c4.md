# L2 / c4 — DM chooser 보정(calibration) 기록

브랜치 `lane/c4-chooser-calibration` (base `int/c2` 256c816), 커밋 `4f71aa5`.
증거: `$L/evidence/l2-c4/` (`calibration-after.tap`, `gate-l2c4.tap`; 게이트 원본은 `$L/evidence/gate-l2c4/`).

## 0. 범위
- 합성 하네스(실제 client/runtime/HTTP 핸들러/실제 `openCalibrationLog`, mock Decisions, 합성 키). 실제 앱·실제 provider 아님. UI 변경 없음, 신규 라벨/카피 없음.
- 보정 모듈은 **기존 API(`record`)만** 사용. 의미 변경 없음.

## 1. 무엇을 기록하는가 (요청당 최대 1개 `dm_chooser` 항목)
| 필드(모듈 기존 필드) | 값 |
|---|---|
| `feature` / `mode` | `dm_chooser` / `on` (chooser는 `on`에서만 호출됨. advisory는 호출 전에 manual로 끝나 요청 자체가 없음) |
| `candidates` | 보기 개수(2~8). 필드 의미는 "후보 수"를 재사용 |
| `judgments[0]` | `q:'choice'`, `top`, `second`(전 행 중 상위 두 확률, abstain 행 포함), `p`(모델 confidence), `threshold`=0.8, `minMargin`=0.2, `would`=`act`(추천) / `hold`(그 외) |
| `fallback` | 닫힌 결과 코드: timeout(timeout_unsent도 timeout으로), unreachable, bad_response, no_credit, rate_limited, budget_exceeded, spend_limit_reached, invalid_key, not_configured, server_error, model_unavailable. 이때 `judgments`는 비어 있음 |
| `day` | 모듈이 UTC 날짜만 기록 |
- 흐름: `readRecommendation`이 확률 판정 시 숫자만 선택적 콜백 `onMeasure`(프로세스 내부)로 전달 → `chatChoice`가 요청 종료 시 `recordChoiceCalibration`에서 `log.record`. HTTP 응답에는 확률이 **절대 실리지 않음**(테스트로 응답 키 고정: `{status,index}` / `{status,reason}`).
- 기록하지 않는 경우: 중복 요청 ID(일회 영수증), 호출 전 가드(모드/권한 불일치), 로그 없음. 로그가 예외를 던져도 응답·유료 요청 수는 불변(테스트).
- 내용 없음 검증: 질문, 보기, 방/대화/프로필 ID, 요청 ID, 키, reviewRevision, 시스템 지시문이 파일 텍스트에 없음(테스트), 파일 권한 0600, 필드 집합 `candidates/day/feature/judgments/mode`.
- **발견(요청 문구와 다름)**: chooser의 실제 bar는 **0.80 / 0.20**이다(`egdesk-chat-choice.mjs` `MIN_CONFIDENCE=0.8`, margin `DEFAULT_DECISION_THRESHOLDS.margin`=0.2). 0.75는 턴 컨텍스트의 `thresholds.choice` 기본값이며 chooser는 쓰지 않음. 기록의 `threshold`는 0.8이고, 새 상수 `CHAT_CHOICE_BAR`로 노출.

## 2. 기존 API로는 기록할 수 없는 필드 (모듈 변경 제안 아님, L7/Main 판단용)
1. **라벨(사용자의 다음 명시 행동)**: `complete(id, outcome)`의 outcome 화이트리스트는 `run`(completed/failed/interrupted/cancelled)과 `toolActivities`뿐이라 `asked_why / asked_agent / edited / retried / closed / sent_ordinary` 같은 값은 저장되지 않고 버려진다. 그래서 UI의 라벨 추적과 라벨 전달 경로는 **만들지 않았다**(저장할 곳이 없는 죽은 코드가 되므로). 필요한 확장: `outcome.label`을 닫힌 단어 집합으로 추가. 그러면 UI가 패널 수명 안의 첫 명시 행동을 닫힌 단어로 bridge에 보내고 `complete`로 연결하면 된다(내용 없음 유지).
2. **no-pick 세분화**: `WOULD` 어휘에 abstain / unclear(동률) / low_confidence 구분이 없어 `act`/`hold`만 쓴다. top 두 확률만으로는 top이 abstain 행인지 알 수 없음. 제안: `would`에 `abstain`, `tie`, `below_bar` 추가.
3. 결과 코드: `FALLBACK` 어휘에 `timeout_unsent`(L5), `abstain`/`unclear`/`low_confidence`/`recommended`가 없음(앞의 둘은 `timeout`으로 접힘, 나머지는 `would`+숫자로만 추론).
4. `margin`은 필드가 없고 `top-second`로 유도해야 함. `candidates`는 보기 수를 담는 데 의미를 빌려 씀.
5. `record()`가 돌려주는 id를 쓰지 않음(라벨용 `complete`가 없으므로).

## 3. 실제 측정 제안 (Main이 사용자 승인을 받을 것, 실행하지 않음)
질문: "0.80/0.20 bar가 일상 질문에서 추천을 통과시키기는 하는가, 통과한 추천이 맞는가?"
- **무엇을 돌리는가**: 사용자 본인 키로 실제 DM에서 `[보기 추천]`을 일상 질문 약 30~40건(사용자가 실제로 고민하는 2~4개 보기짜리 선택: 파일 정리 방식, 일정/순서 정하기, 문서 버전 고르기 등) 실행. 모드 `on`, 질문당 provider 요청 1건(비용은 사용자 키로 청구, 요청당 입력 토큰은 질문+보기 수준).
- **기록되는 것**: 위 1절의 항목(요청 순서·UTC 날짜·확률). 사용자 라벨은 앱 밖에서 요청 순서대로 사용자가 직접 적는다(질문/보기 내용은 기록하지 않으므로 사용자 메모와 순서로만 대응).
- **판독할 값 4개**: (a) 통과율 = `would:act` 비율, (b) `top` 분포와 `top-second` 분포(요청별), (c) 격자 재계산 — 같은 기록으로 (0.70/0.10), (0.75/0.20), (0.80/0.20), (0.85/0.25)에서 통과율이 어떻게 변하는지, (d) 사용자가 "내가 고를 것과 같다/다르다"로 표시한 통과 건의 정밀도와, hold 건 중 "추천이 있었으면 좋았다" 비율.
- **결정 규칙(제안)**: 통과율이 낮아 대부분 hold이면 bar 문제(또는 질문·보기 품질 문제)로 보고, 정밀도가 높은 통과 건이 충분하면 bar 유지. 표본이 30건 미만이면 결론 보류. 모듈 상한(100건/30일)으로 충분.
- **전제**: 실제 키·비용 승인, 사용자 일상 질문 사용 동의. 현재 실제 chooser 표본은 없음(키 확인, 턴 컨텍스트, Board 사진, 발화 배치만 있음)이라 위 값은 지금은 알 수 없다.
