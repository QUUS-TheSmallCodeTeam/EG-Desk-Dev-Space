# L52-e 보고: 제출 클릭 16초, "확인할 수 없습니다" 답

## 원인
- 16초: 클릭은 helper(requestUi, egdesk-browser-tool-runtime.mjs:539~560)가 UI 응답을 15초(`timeoutMs`) 기다리다 BROWSER_UI_TIMEOUT으로 throw하는 구조입니다. UI 쪽 `browserToolAct`(overlay/JS/eg-desk-surface.uc.js, `browserAgentActorRequest('act')`)는 자체 타임아웃 없이 페이지 actor의 sendQuery 응답만 기다립니다. POST가 최상위 문서를 JSON 뷰어로 바꾸면 actor가 사라지는데 응답이 오지 않는 경로가 있고, 그때 helper의 15초 만료까지 걸립니다. 코드로 확인한 부분: 대기에 상한이 없고 actor 소멸을 UI가 따로 감지하지 않는다는 점. 실제로 응답이 유실된다는 것은 실창 로그가 없어 추정입니다.
- "확인할 수 없습니다": 답변 검사/답변 모델에 가는 증거(`task_steps`, codex-chat-runtime.mjs `browserTaskStep`)는 "fill "Customer name:": went through"처럼 값이 없었고, 도착 주소도 없었습니다(노트에는 `arrivalUnobserved`만). 그래서 "차민수로 채움", "주문 제출됨"을 뒷받침할 근거가 없어 hedge로 고쳐졌다고 판단합니다(추정, 문구 출처는 로그로 확인하지 못함).
- 케이스 1(3회 중 1회 hedge): 원인이 코드로 확정되지는 않았습니다. 같은 증거 부족(입력값 없음)이 가장 유력해 같은 수정으로 완화합니다. 실창 반복으로 확인 필요.

## 수정
1. overlay/resources/EGDeskActDocumentGone.sys.mjs(신규): click/pointer-click/press의 act 요청을 "요청 시점의 문서가 더 이상 현재 문서가 아님"과 경주시킵니다. 문서가 바뀐 뒤 1.2초 안에 actor 응답이 오면 그 응답을 씁니다. 안 오면 `dispatchPhase:'unknown'`으로 즉시 reject합니다(15초 대기 없음). 'not-dispatched'를 주장하지 않으므로 helper는 BROWSER_ACTION_UNVERIFIED로 받고, L50의 `settle()`이 최상위 주소로 도착을 판정합니다. 클릭은 다시 누르지 않고, 진짜 실패는 그대로 실패입니다. surface.uc.js는 호출부 한 곳만 바꿨습니다.
2. 증거 보강: (a) `browserTaskStep`의 step 줄에 fill/select 성공 시 분류된 미리보기(`displayValue`)를 `= "차민수"`로 붙입니다. 마스킹/민감 필드는 `●●●` 그대로, 실패 단계는 값 없음. (b) POST 도착 3곳(reflex)에 `postedTo`를 추가하고, done 노트에 `submittedTo: "httpbin.org/post"`(호스트+경로, query 제거)를 넣습니다. 도착 문서를 읽지 못해도(`arrivalUnobserved`) 들어갑니다. task-tool 경로에도 동일. 제출 버튼 이름은 기존 `submit "Submit order": went through`가 담당합니다.
3. 선택 항목(JSON 뷰어 원문 읽기): 하지 않았습니다. JSON 뷰어는 특권 문서라 페이지 actor가 못 들어가는 구조라, 읽으려면 parent에서 별도 경로(권한·마스킹 설계)가 필요합니다. 별도 작업으로 문서화만 합니다.

## 수정 3 (실창 회귀: 라디오/체크박스/Start/제출 클릭 실패)
- 코드 결론: race의 isReplaced는 요청 시점의 browsingContext/currentWindowGlobal과 비교하고, 문서가 바뀐 뒤 1.2초가 지나야만 reject합니다. 같은 문서 클릭은 바뀌지 않으므로 느려도(테스트: 4배 느린 응답) 결과가 그대로 전달됩니다. 또 실패 시간이 0.3~0.6초라 1.2초 창으로는 설명되지 않습니다.
- 가장 유력한 원인(추정, 실창 확인 전): 이전 버전은 act 요청을 보낸 뒤 ChromeUtils.importESModule(.../EGDeskActDocumentGone.sys.mjs)를 불렀습니다. 실행 중인 창에 이 새 파일이 없거나 로드가 실패하면 요청이 나간 뒤 throw되고, catch가 lease를 끝내 actor의 authorizeAct가 거부되어 클릭이 실제로 일어나지 않습니다. click/pointer-click/press만 이 경로를 타서 입력(type-text)과 증상이 갈립니다. 실행 창이 새 파일을 로드하는지는 확인하지 못했습니다(설치/복사 방식 미확인).
- 수정: 모듈을 요청 전송 전에 try/catch로 해석하고, 실패하면 race만 끄고 act는 항상 그대로 보냅니다. act는 race 모듈에 더 이상 의존하지 않습니다. 모듈이 없는 창에서는 POST 제출이 예전처럼 16초 걸릴 뿐입니다.
- 라벨: 내 증거 변경이 아닙니다. 실패한 select/fill 단계의 displayValue를 마스킹 표시로 바꾸는 기존 코드(egdesk-browser-task.mjs taskStepEvent: ok가 아니면 마스킹)입니다. 클릭이 실패해서 나온 결과이고, 클릭이 성공하면 라벨이 돌아옵니다. 내 증거 줄은 성공 단계에만 값을 붙입니다.
- 테스트: act-document-gone에 같은 문서 click/press(느린 응답), 일시적 판독 복귀, 실제 이동, 연결 순서(모듈 해석이 전송 앞, try/catch, 항상 전송) 추가. 묶음(transport, act-document-gone, post-arrival, claude-browser-reply, surface-modules, reflex*, task*, step-candidates) 258건 중 256 통과. 실패 2건은 surface-modules의 cardSleepReport 키(기존 int/e 이슈).
- 커밋: 53c568a4 (lane/e-submit-answer)
- 한계: 위 원인은 로그로 확인하지 못했습니다. 이 수정으로도 클릭이 실패하면 race만 되돌리는 것이 안전하고, 증거 변경은 독립입니다.

## 수정 4 (실창 이분 결과: L52가 라디오/체크박스/press/제출 클릭 실패의 원인)
- 결론: 원인을 증명하지 못했습니다. 코드만으로는 STALE(document/viewport/revision/focus 불일치)을 만드는 경로를 못 찾았습니다. 내 변경 중 act 주변에서 실행되는 것은 (1) 모듈 해석(act 전송 전, try/catch), (2) 문서 교체를 100ms마다 보는 폴링 타이머(parent 쪽 읽기뿐, 문서/포커스/revision을 건드리지 않음), (3) 문서 교체 후 1.2초 뒤에만 reject, 이 셋뿐입니다. op=select는 도구상 click이라 race 대상입니다(Main 지적과 달리 GONE_ACTION_TYPES의 click에 해당). 그래도 0.3초 만에 STALE로 실패하는 것은 race로 설명되지 않습니다.
- helper 쪽 변경(step 증거 줄, postedTo/submittedTo)은 act 도구 호출 경로에 닿지 않습니다(이벤트 후처리, 노트 생성).
- 조치: act 경로의 UI 변경을 전부 제거한 커밋을 추가했습니다(surface.uc.js를 base로 복원, EGDeskActDocumentGone.sys.mjs와 그 테스트 삭제). helper 증거 변경은 유지합니다. 이 상태에서 실창을 돌리면 race가 원인인지 helper 변경이 원인인지 갈립니다. race 제거 후에도 실패하면 L52 helper 변경 또는 병합 상호작용(L51)을 의심해야 합니다.
- 16초 대기 문제(과제 1)는 이 커밋에서 다시 열려 있습니다. 다음 라운드에서 실창 로그(act 응답 유실 여부, UI 쪽 에러 코드)를 먼저 확보한 뒤 다시 시도하는 것을 권합니다.
