# L49-e 방 삭제 신뢰성

## 원인
**증명된 것**
- 화면 쪽 deleteThread는 forget POST를 await 없이 쏘고 실패를 버림(.catch(() => {})). 재시도·기록 없음.
- 브리지 핸들러(/chat/conversation/forget, LOCAL_WRITES)에는 동시성 가드·타임아웃·연결 제한 코드가 없음. forgetConversation은 native thread 삭제를 await하고 **히스토리 행 삭제는 맨 마지막**. 그래서 중간에 멈추거나 요청이 끊기면 저장 대화만 남음.
- 브리지 로그: 11/28 01:51-01:53 KST(= 11/27 16:51-16:53 UTC) 구간에 줄이 없음(16:40, 16:59 사이 비어 있음). 즉 로그로는 실패 원인 증거를 못 찾음.
**추정(증명 불가)**
- 250ms 간격 x 건당 ~1s 로 요청이 겹치며 engine.deleteThread 겹침/지연 또는 요청 중단으로 마지막 단계(히스토리 삭제)에 도달 못 함. SQLite busy는 아님(동기 호출). 겹침 vs 개별 hang 중 무엇인지는 구분 못 함.

## 변경
- overlay/resources/EGDeskForgetQueue.sys.mjs (신규): 직렬 큐, 네트워크/5xx/408/429 백오프 재시도(1,2,4,8,15,30s), 그 외 4xx는 폐기, pref `egdesk.pendingForgets.v1`에 대기열 저장.
- overlay/JS/eg-desk-surface.uc.js: deleteThread가 큐에 enqueue, 시작 5초 후와 브리지 연결 성공 시마다 resume. 방은 화면에서 즉시 삭제 유지. (L47/L48 영역 미접촉)
- helper/codex-chat-runtime.mjs: forgetConversation을 브리지 안에서 직렬화(forgetConversationNow로 본문 이동, 실패가 다음을 막지 않음).
- 엔진 deleteThread 타임아웃은 추가 안 함(hang 시 큐 전체 정체 위험이 남음, 아래 위험 참고).

## 실창 검증 (Main)
1. 방 N(예 30)개 생성 후 250ms 간격으로 빠르게 삭제.
2. 화면에서 사라진 뒤 1~2분 대기하며 GET /chat/history/threads 개수가 기대치로 감소하는지 확인.
3. 삭제 중 브리지만 재시작해 보고, 남은 id가 pref `egdesk.pendingForgets.v1`에 있다가 재연결 후 비워지는지 확인(재시작 허용 환경에서만).

## 위험
- 큐 head가 영구 5xx/hang이면 뒤 항목이 막힘(30s 간격 재시도 지속). 필요 시 엔진 삭제 타임아웃 후속.
- 브리지가 재시작되지 않은 구버전이면 브리지 직렬화는 적용 안 됨(화면 큐만 효과).
- 실패 알림 문구는 추가 안 함. 필요하면 제안: "일부 채팅방 삭제를 마치지 못했어요. 연결되면 자동으로 이어서 지울게요."
