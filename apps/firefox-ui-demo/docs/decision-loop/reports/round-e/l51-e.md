# L51-e 진입이 첫 단계를 못 잡은 5·7·19번 (브랜치 lane/e-entry-first-step, 커밋 b9614c38)

## 원인 (녹화된 호출 + 실모델 재현)
녹화(calls.json)에는 결정 내용·확신값이 없고 토큰 수·시각만 있다. 그래서 같은 쪽수를 흉내낸 메모리 페이지로 실모델을 돌려 재현했다 (scripts/egdesk-entry-route-real-measure.mjs, egdesk-entry-first-step-real-measure.mjs).
- **라우팅(5번·7번의 주원인)**: L33(본문 기본 전송) 뒤 observeCardLines는 본문이 켜지면 카드를 "첫 3줄"로만 인용하고 제목·컨트롤을 뺀다 (withText 분기). 주문 폼 카드는 "Customer name: / Telephone: / E-mail address:"만 보여 토핑·시간 칸이 없다. 실모델: browser_entry 0.00, 카드 0.00 → 'not_browser' (2회 2회 동일, 후속 wall 질문까지 감, 이것이 d-live의 285토큰 두 번째 호출). 진입이 아예 열리지 않아 채팅 모델이 전부 했다. b-live(본문 꺼짐)는 컨트롤을 인용해 통과했다.
- **단계(5번 두 번째 상자)**: 베이컨 뒤 next_step의 '양파 체크' 1순위가 0.61~0.63, 문턱 0.75 미만 → uncertain (4/4). choice_requested는 0.98이었다. 순위 확률이 페이지의 다른 선택지로 갈라지는 것이 원인 (L39 보고서의 .78 하락 경고와 같은 방향).
- **19번**: 같은 방식 재현에서는 라우팅(web 1.0, 카드 1.0)도 단계('Start' 0.99, named 버튼)도 정상이었다. 실창에서 안 잡은 이유는 녹화만으로 확정 못 한다 (카드의 실제 첫 3줄 모양을 모름: 첫 3줄에 Start가 없으면 5·7번과 같은 경로로 해석된다). 이 가설은 아래 수정이 같은 경로를 막는다. 확정은 실창 확인 필요.

## 수정 (최소·국소)
1. egdesk-browser-task.mjs observeCardLines: 카드 제목(단일 카드)·컨트롤 라벨(최대 16개, controlLines, 가려진 컨트롤은 그대로 개수만)을 본문 줄과 나란히 싣는다. 본문 줄이 있으면 요청 문구는 측정된 ENTRY_WEB_ASK 그대로 (entryExtra 표지로 운영 문구로 안 바뀜; c27-c29 계정 데이터 읽기 문구 보존).
2. egdesk-browser-reflex.mjs decideReflexStep: 체크박스·라디오(input 선택지, 12개 이하)를 목록의 select_N처럼 box_N 술어로 사람 말에 하나씩 대조. 모두 결정(예 ≥.75/아니오 ≤.25)이고 예가 하나 이상일 때만, 예들 중 페이지 순서 첫째를 단계로 (사람이 지명한 상자만이라 안전). next_step 문턱·margin은 낮추지 않음. 순위가 지명 안 된 상자를 확신 있게 고르면 기존처럼 user_context. 같은 요청 안(추가 호출 없음).
- 허가 정책 불변: 대화가 권한, 상자는 사람이 말한 것만 고른다. 결제·민감 라벨 상자는 기존 gated로 후보에서 빠진다. 제출은 건드리지 않음.
- 느려짐(3/5/7번): 5·7번은 진입이 못 열려 채팅 모델 4~6조각이 일한 것이 원인 (d-live 5번 D2 28.7초, 호출 6조각/도구 5). 진입이 열리면 사라짐. 3번(9.9→17.4)은 진입이 일했으므로 이 수정과 무관: d-live에서 진입 호출 뒤 첫 단계 호출까지 3~4초 공백이 b-live(0.2초)보다 길어졌고(5번 D1 2.8→6.9초) 원인은 녹화로 확정 불가. 미해결, 실창 시간표 계측 필요.

## 추가 수정 (Main 요청, C5 roundtrip 시험)
