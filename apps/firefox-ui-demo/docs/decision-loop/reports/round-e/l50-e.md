# L50-e 보고: 케이스 15 제출 성공이 "제출 실패"로 표시되는 문제

## 원인 (helper/egdesk-browser-reflex.mjs)
- 단계 줄의 "제출 실패"는 `act()`(약 929행)의 catch에서 나옵니다. 제출 클릭(`egdesk_browser_click`)이 throw하면 그 자리에서 `failed` 단계가 즉시 발행됩니다.
- L43의 `postArrived` 판정(기존 1256~1275행)은 `act()`가 이미 실패를 알린 뒤에 실행됩니다. 그래서 나중에 done으로 판정돼도 이미 나간 "제출 실패" 줄은 되돌릴 수 없습니다.
- JSON 뷰어 문서로 교체되는 동안 클릭 응답이 유실되거나 시간 초과가 나면 클릭이 throw합니다. 이 추정은 코드를 읽어 낸 것입니다. 증거 로그(matrix/calls)에는 클릭 에러 코드가 없어서 직접 확인하지는 못했습니다.
- 시간 소모는 두 군데입니다.
  - 클릭 throw 자체: D3에서 16초. UI 타임아웃으로 추정합니다.
  - 그 뒤 observe 실패 → `wait load` 5초 → observe 재시도가 이어지고, 마지막에 "더 진행할 수 없음" 단계가 붙습니다.
- 증거: matrix.jsonl 케이스 15 Codex D2/D3/D5에서 "제출 실패 → 더 진행할 수 없음 실패"가 나오고 35초 안팎이 걸렸습니다. 같은 실행에서 URL 확인은 `/post`로 통과했습니다.

## 수정
- 제출 클릭에 `landed` 콜백을 `act()`에 넘깁니다. `act()`는 이 콜백 덕에 throw를 잡았을 때 실패 줄을 내기 전에 navigation 사실로 먼저 판정합니다.
- 판정은 `settle()` 하나로 합쳤습니다. 한 번 계산하면 캐시하고, 클릭을 다시 누르지 않습니다.
  - observe가 새 문서에서 `url === action`이고 documentId가 달라졌으면 `arrived`입니다.
  - observe가 거부되면서 최상위 주소를 알려 주면(JSON 뷰어, 특권 문서) `postArrived`(같은 origin·path, 폼 페이지가 아님)로 `unobserved` 성공 처리합니다. load 대기는 하지 않습니다.
  - 둘 다 아니면 `wait load` 5초를 한 번 하고 다시 봅니다. 그래도 아니면 `no`이고, 실패 줄과 `escalated/tool_failed`를 그대로 냅니다.
- 성공이면 단계 줄이 성공으로 나옵니다. 클릭이 정상 반환된 경우의 기존 흐름도 같은 `settle()`을 씁니다.
- 판정에는 DOM이 아니라 최상위 주소와 documentId만 씁니다. 권한 정책, 허가 질문, 1회 누름 규칙은 건드리지 않았습니다.

## 위험
- 클릭 throw의 정확한 코드와 16초 대기(UI 타임아웃으로 추정)는 그대로입니다. 이번 수정은 그 뒤의 재대기와 거짓 실패 표시를 없앨 뿐이고, 클릭 자체의 지연은 줄이지 못합니다. 이 대기를 줄이려면 호출 쪽에서 act 예산을 짧게 하는 별도 작업이 필요합니다.
- 같은 경로(origin·path)로 다시 POST되는 폼은 `postArrived` 때문에 폼 페이지와 구분되지 않아 unobserved 성공이 되지 않습니다. 이 경우는 기존처럼 실패로 처리됩니다.
- 새 사용자 문구는 없습니다.
