# L56-f: fill/transport 상한 제거

## 무엇이 왜 제한했나 (git -S)
- 8000자 `MAX_FILL_TEXT`: 5c3b7e4d(frames/shadow roots 작업)에서 도입. 관측값을 길이+지문으로 비교하려는 "bounded observation" 설계였고, 8000 초과는 지문 없이 `[over 8000 chars]`라 guard가 비교 불가 -> 채우기 거부. 채널 한계 때문이 아니라 설계상 편의 상한.
- 48000 전송 상한: 043416c0(tool ownership/receipts)에서 도입된 방어적 값. fill 40000 JSON 상한(MAX_FILL_REQUEST_JSON)도 이 값에서 유도.

## 제거한 것
- Child actor: MAX_FILL_TEXT, MAX_EDITOR_NODES, fill/type 텍스트 길이 거부, 현재값 길이 거부, `[over N chars]` 분기(boundedValue는 항상 `N chars, #지문`). editorText는 길이/노드 제한 없이 반복(비재귀) 순회로 전체 읽기(깊이 5000도 OK).
- helper tool-runtime: MAX_FILL_TEXT/MAX_FILL_REQUEST_JSON, fill/type 길이 검사, 후조건 길이(fill/type만 Infinity, 타 도구는 512 유지), boundedFieldValue의 over 분기, 도구 설명 "8000 characters" 문구.
- reflex: MAX_VALUE_TEXT.
- transport: `data.length > 48000` 검사.
- docs/BROWSER_AGENT_OBSERVATION_RUNTIME.md 갱신. fill 스키마에는 maxLength 없었음.

## 채널 조사
- bridge -> UI: SSE(EventSource, `event: browser-tool-request` 한 줄 `data:`). JSON은 개행을 이스케이프해 한 줄이고 EventSource에 이벤트 크기 제한 없음 -> 청킹 불필요.
- UI -> actor: 브라우저 UI(chrome JS)에서 actor 메시지(message manager/JSWindowActor, structured clone). 실질 한계는 IPC 수십~백 MB 수준이라 수십만 자에 무관. 청킹 불필요(코드상 크기 제한 없음; 실창 확인은 아래).
- 응답 쪽: UI -> bridge HTTP POST `/browser-tool/respond`(readJsonBody 190000 bytes) + transport.receive/runtime의 JSON 180000자 검사. 이건 관측/스크린샷(150000 budget) 응답용이고 fill 응답은 작아 fill 경로에 영향 없음 -> 건드리지 않음(L57 모델 컨텍스트 영역과 겹칠 수 있어 남김). 큰 관측 응답이 필요해지면 별도 결정 필요.
- 페이지 반영: 이미 `target.value = text` + input/change 한 번(에디터는 beforeinput + replaceChildren + input). 글자 단위 아님. 변경 없음. type-text는 TextInputProcessor 경로이며 상한만 제거(매우 긴 type은 느릴 수 있으니 긴 입력은 fill 권장).
- 진짜 실패(스트림 닫힘 BROWSER_UI_DISCONNECTED, 타임아웃, 읽기 불일치)는 그대로 정직한 오류.
