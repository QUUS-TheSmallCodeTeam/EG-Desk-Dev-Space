# L55-f: 페이지가 바뀌어 act가 거절되면 decision model이 보고 결정

커밋: `6fa9be5f` (branch lane/f-change-decision, base a6e70dd0). push 안 함.

## 원인
- 액터 guard(`assertGuard`, Child.sys.mjs ~1449)는 관찰의 `revision`과 현재 revision을 비교한다. revision은 MutationObserver가 문서의 어떤 DOM 변화에서도 올린다.
- 시계, 티커, 배너, 채팅 위젯이 있는 페이지는 관찰 → decision 요청(약 1초) → act 사이에 revision이 움직인다. 그래서 대상은 그대로인데 BROWSER_OBSERVATION_STALE(staleBy `revision`)로 거절된다.
- 리플렉스의 재시도는 fill 값당 1회뿐(`staleRetried`)이고, 재시도도 같은 경쟁(관찰 → 1초 → act)이라 또 거절된다. 그 뒤 채팅 모델로 넘어가는데, 채팅 모델의 도구도 같은 guard를 만난다.

## 설계 (helper만 수정, 액터 guard는 그대로)
새 파일 `helper/egdesk-browser-change.mjs`와 `egdesk-browser-reflex.mjs`의 `actThroughChange`.
1. 같은 문서에서 아무것도 보내지 않은 거절(staleBy `revision/viewport/focus/observation/target`, 단 `not-editable` 제외)이면 한 번 더 관찰한다.
2. 코드가 닫힌 변화 요약(`summarizeChange`)을 만든다.
   - 대상: same / moved / changed(role, label, href, value, enabled) / gone
   - 바뀐, 나타난, 사라진 컨트롤 수
   - 변화가 대상 영역과 겹치는지(yes / no / unknown)
   - 대화상자 등장 여부, 새 텍스트 줄 수
   - 페이지 본문 텍스트는 넣지 않는다. 대상 이름만 들어간다.
3. decision 요청 1회: 기존 `decideReflexStep`을 새 관찰 위에서 그대로 쓴다. 증거에 "Page change check ... Decided action: ..." 줄이 붙고, 질문 `change_wait`("대상 주변이 아직 바뀌는 중이라 기다려야 하나")가 하나 늘어난다. page_state 술어와 goal_met도 같이 물으므로 로그인 벽, 모달 같은 사람 전용 상태는 매번 다시 판정된다.
4. 결과별 처리:
   - 같은 ref를 고르면 그대로 진행.
   - 같은 종류의 다른 요소를 고르면 재타깃(fill, choice, 읽기 전용 view/named 버튼만. 링크 이동과 get_form은 재타깃하지 않고 루프의 새 결정으로 보낸다).
   - `change_wait` yes면 `wait idle`을 하고 다음 라운드.
   - handoff / blocked는 그 자리에서 종료한다.
   - 그 밖(uncertain, scroll 등)은 `replan`: 루프가 새 관찰로 처음부터 결정한다.
5. act의 guard는 decision 요청 뒤에 다시 본 관찰로 만든다. 결정된 대상이 코드상 같은 요소(`targetKey`: ref, role, label, href, tag, enabled, fill이 아니면 value)일 때만 보낸다. 요청 중에 바뀌었으면 다시 결정한다(라운드 소모).
6. 승인된 같은 대상이 또 거절되면(시계가 빨라서) 모델에 다시 묻지 않고 새로 본 뒤 바로 보낸다.
7. 한 번 거절된 act당 새 관찰 최대 `CHANGE_REDECISIONS = 3`회. 그래도 안 되면 `escalated / tool_failed / BROWSER_OBSERVATION_STALE` + `unsettled: true`로 정직하게 넘긴다. 이 경우 act는 첫 시도 포함 최대 4번이고 decision 요청은 최대 3번이다.
8. 문서 교체(staleBy `document/url/identity/frame`) 또는 문서 id/url이 달라진 경우는 `replan`(새 페이지를 새 관찰로 결정). 연속 replan도 3회로 제한한다(실제 act 성공 시 초기화). fill은 값당 replan 1회를 유지한다(기존 L6 a1b 규칙).
9. 기록: `entry.change.rounds[]`에 닫힌 단어와 숫자만 남는다(target, fields, changed/added/removed, onTarget, dialog, text, decided same/other/wait/…, acted).

### 사람 전용 게이트
- 후보는 `buildReflexCandidates`로만 만들어진다. 로그인/비밀번호/결제/권한/삭제 컨트롤은 후보가 아니므로 모델이 고를 수 없다.
- POST 제출(`postUrl`)과 사이트 요청(`askSite`)은 제자리 재시도 대상이 아니다(`changeEligible`). 루프의 원래 경로가 `authorizePostSubmit` 등을 다시 거친다.
- 페이지가 로그인 벽으로 바뀌면 ps_sign_in이 같은 요청에서 yes가 나와 handoff하고 아무것도 보내지 않는다(테스트와 실제 모델 둘 다 확인).

### 대상 한정 guard(과제 2): 하지 않음
- `revision` 우회 플래그를 액터에 넣으려면 도구 스키마, Card, parent, actor까지 한 줄로 이어야 한다. L54와 L56이 건드리는 구역과 겹치고, 모든 호출자(채팅 모델 포함)의 안전 모델이 바뀐다.
- 대신 "결정 직전에 본 새 관찰 + 코드의 대상 동일성 검사"로 경쟁을 줄였다. 액터는 여전히 새 관찰의 revision과 비교한다.
- 한계: 매 수십 ms마다 바뀌는 페이지에서는 관찰 → act IPC 구간에서도 거절될 수 있다(위의 3회 제한에서 정직하게 종료). 정말 필요하면 후속으로 "decision이 승인한 target-scoped guard" 플래그를 액터에 따로 설계하는 것이 맞다.

## 위험과 한계
- 모델 호출이 거절된 act당 1회 늘어난다(요청 약 1초). 승인된 같은 대상의 재시도에는 늘지 않는다.
- 아주 빠른 변화(수십 ms)는 액터의 전역 revision에 계속 걸려 3회 뒤 `unsettled`로 넘어간다(위 한계).
- 채팅 모델의 직접 도구 act는 이 경로를 안 타고 같은 guard를 그대로 만난다(리플렉스 안에서만 해결). `unsettled: true`가 결과에 있으니 채팅 모델 안내문에 "페이지가 계속 바뀌는 중" 문구를 붙일 수 있다. 새 UI 문구는 넣지 않았다. 제안 문구: "이 페이지가 계속 바뀌어서 지금은 조작하지 못했어요."
- L56이 actor fill 길이 한도를 푸는 것과는 독립이다. L57이 `observeCardLines`를 바꿔도 이 경로는 snapshot 필드(`interactiveElements`, `text`, `viewport`)만 읽는다.
- modal 감지는 snapshot에서 role dialog/alertdialog가 목록에 새로 뜬 경우뿐이고 나머지는 page_state 술어(ps_covered)에 맡긴다. 새 창(popup)은 관찰에 없어 요약에 못 넣었다.
