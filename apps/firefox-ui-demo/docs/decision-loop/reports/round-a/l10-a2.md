## 무엇이 확인됐나

- **실창 기록**: DB/WAL/SHM 읽기 전용 사본에서 19:32:07, 19:42:15·21·28, 19:48:56 KST `browser.tool.failed` 모두 `BROWSER_OBSERVATION_STALE`, `staleBy=input-authority`, `inputDeniedBy` 없음. 사본 삭제. 내용·주소 없이 확인한 결과: `$L/evidence/l10a2-real-words.txt`.
- **엔진과 독립적인 진단 누락 [확인]**: Codex 제공자는 원래도 헬퍼 오류에 `inputDeniedBy`가 있으면 도구 결과와 `browser.tool.failed` 둘 다에 실었다. 빠진 경로는 `authorizeAct` 부모/액터가 카드의 `deny()`를 거치지 않는 경우다. 액터는 `Browser action authority was revoked before input [missing-authorizer]`처럼 이미 닫힌 낱말을 쓰지만 런타임은 `input-authority`만 남겼다. Claude에서도 같은 종류의 부모 거절이면 빠진다.
- **카드 안에 지속되는 결함 [수정 전 재현, 수정 후 통과]**: `EGDeskBrowserAgentRuntimeParent.sys.mjs`는 카드 등록을 Gecko `BrowsingContext.id`로 찾는다. 반면 `eg-desk-surface.uc.js`의 `browserToolBinding()`은 이전 등록 해제 함수 유무만 보았다. 같은 브라우저 요소가 살아 있는 상태에서 컨텍스트 ID가 바뀌면 이후 모든 새 바인딩·관찰에서 옛 등록을 그대로 둔다. 읽기는 되지만 새 ID의 부모는 `missing-authorizer`로 입력을 계속 거절하고 lease에는 사유가 안 쓰인다. 실제 카드 binding 함수와 실제 Parent registry를 사용한 시험에서 기준판은 `rebind exact current context after replacement: false !== true`. 컨텍스트 ID가 그대로이고 window global만 바뀌면 이 버그가 아니다.
- **실창 사건과의 연결 [추정]**: 이 결함은 카드 하나에만 누적, 새 카드/재시작 정상, 늦은 승인 거절, 빈 `inputDeniedBy`를 동시에 설명한다. 당시 카드 1에서 컨텍스트 교체가 실제로 일어났다는 증거는 없다. 따라서 실창 원인을 확정하지 않는다. 19:47→19:48 Codex→Codex 실창 증거로 Claude 선행은 필요조건이 아니다.
- **선택/실행 상태를 무작정 지우지 않은 이유**: 명시 선택은 UUID와 `usedRunId:null`로 시작한다. bind는 대화·카드·계정·토큰·미사용 여부를 관찰 전후에 검사하고 해당 runId를 쓴다. 앞 대화에서 쓴 토큰으로는 새 대화가 bind조차 안 된다. `CardLeases`는 act 동작의 finally가 같은 requestId만 해제한다. 이전 lease가 단순히 남았다면 observe/act 사전검사에서 `card-busy`다. `RunBindings`와 `CancelledRuns` 키는 run/card/generation이며 Stop은 run/thread로 분리된다. account·transport epoch 변화는 재바인딩 대상이지 새 대화에 권한을 넘겨주는 근거가 아니다. 사용자가 카드를 직접 잡은 상태는 bind 이전의 `user-hold`로 구별된다. 취소와 입력 사이 경합 가능성까지 배제한 것은 아니다.

## Main 실창 확인

1. 병합본으로 Firefox와 헬퍼를 **한 번만** 다시 시작. 첫 Claude 대화에서 카드 1에 `Chat 조작 허용`, `egdesk_card_type`으로 입력이 실제 한 번 들어오는지 본 뒤 종료. 카드 1을 닫거나 앱을 재시작하지 않는다.
2. 새 Codex 대화에서 같은 카드 1에 다시 허용. 읽은 뒤 결정 루프 fill 및 Codex `egdesk_card_type`을 각각 한 번 확인. 별도 새 세션에서 **첫 Codex → 두 번째 새 Codex** 순서로도 반복한다(19:47→19:48 경로). 가능하면 첫/둘째 사이에 이동하지 않는 경우와 첫 입력 후 검색 결과로 이동한 경우를 구분한다.
3. 새 대화 무허용과 중지된 실행은 여전히 입력을 보내지 않아야 한다. 한 번의 허용 입력이 두 번 실행되면 실패다.
4. 실패하면 실 DB가 아닌 `chat-*.sqlite`와 WAL·SHM 사본의 `events`에서 아래처럼 제한해서 읽는다. 원문, 전체 JSON, 주소는 읽지 않는다. 재현 직후의 시각만 채택하고 사본 삭제.

```sql
SELECT datetime(ts/1000,'unixepoch','+9 hours'),
       json_extract(details_json,'$.code'),
       json_extract(details_json,'$.staleBy'),
       json_extract(details_json,'$.inputDeniedBy')
FROM events WHERE event='browser.tool.failed'
  AND json_extract(details_json,'$.originalProviderId')='egdesk-browser'
  AND json_extract(details_json,'$.code')='BROWSER_OBSERVATION_STALE'
ORDER BY ts DESC LIMIT 5;
```

`missing-authorizer`: 부모가 현 컨텍스트에 맞는 chrome 카드 등록을 찾지 못함(이 단어만으로 사유가 ID 교체 하나로 정해지지는 않음). `selection-run-mismatch`/`card-lease-changed`: 해당 검사에서 실제로 거절. `ui-denied`만: 부모가 콜백을 불렀지만 현재 요청 lease에 개별 deny 단어가 없음. `parent-callback-error`: 부모 콜백 예외. 어느 경우에도 권한 검사를 생략하거나 같은 입력을 강제로 재전송하지 않는다.
