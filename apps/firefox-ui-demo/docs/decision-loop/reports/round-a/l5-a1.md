### 2.1 같은 맥락: 규칙이 note 옆에 붙는다 (두 엔진 같은 문장)
- 진입 결과 note의 context 값이 `{"egdesk_browser_task": {...그대로...}, "rule": "..."}` 가 됨. note 자체(L8의 `subjectiveNote`)는 바꾸지 않음. 첫 턴(`startTurn`)과 진행 중 재개 턴(`continueBrowserRunTurn`) 둘 다.
- 규칙 문장(모델용, 영어, `egdesk-browser-task-turn.mjs`의 `browserTaskRule`): 결정 모델이 이미 한 단계·멈춘 곳은 note에 있다, 다시 하지 말고 note에 없는 것만 페이지에서 읽어라 / done이면 한 메시지로 결과 보고 / 값·선택이 필요한 상태(need_context, needs_value, needs_guidance)는 대화로 이미 정해지면 **브라우저 작업 도구(egdesk_browser_task)에 note의 이름으로 값·선택을 넘겨 이어 가라**, 아니면 한 줄 질문 / cannot_proceed면 사람이 페이지에서 할 일을 말하라 / 이미 말한 것을 되묻지 마라.
- 도구 이름은 **그 턴에 도구가 실제로 있을 때만** 문장에 들어감(지금은 아무 제공자도 내놓지 않으므로 도구 없는 문장).
- 스레드 지시(thread instructions)는 손대지 않음 → Codex `thread/start`가 `on`과 바이트 동일(시험). Main이 제안한 `claudeBoundedHarnessInstructions`에는 **붙이지 않음**. 이유: ① Codex bounded 스레드에는 EG-Desk 지시가 없어 "같은 문장"을 지키려면 어차피 note 옆이어야 함, ② 스레드 지시는 프로세스 시작 시 고정이라 note 없는 턴에도 실리고 "this note"를 가리킬 수 없음, ③ 한 곳에만 두어 중복·충돌을 피함. 원하면 한 줄로 옮길 수 있음.
- 대화 모델 턴 수: 진입이 끝냈으면 Claude는 메시지당 1턴(시험: 두 메시지에 Claude 턴 합계 2).

### 2.2 단계 이벤트 `browserTaskStep` (화면 몫은 L1)
- 통로: 런타임의 기존 화면 통로(`emitEvent` → 브리지 `broadcast(…, 2)` → SSE `event: codex`)로 **chat.event v2**, `event: 'browserTaskStep'`. **transient**(`durable: false, transient: true`): 화면에만 가고 저장소·기록·run checkpoint에는 남지 않음. seq는 일반 이벤트와 같은 번호 줄을 씀(화면 reducer가 seq 중복을 버리기 때문).
- 식별: 진입 단계(턴 전) = 그 전송의 `requestId` + `clientThreadId` + `conversationId`, `runId: null`. 진행 중 재개·도구 단계 = 그 실행의 `runId`/`conversationId`.
- details(이것만 나감, 각각 형식 검사): `taskId, cardId, seq, op, target(조작 대상 라벨 ≤80자), valueName(값의 이름 ≤80자), ok, ms, by, status, phase('entry'|'tool')`. **입력한 값 원문·주소·페이지 글은 절대 안 나감**(시험: value/url/text 넣어도 빠짐).
- 지금 루프(L8 이전 형식 `{step, action}`)는 실제로 바꾼 동작(press/type/open/scroll/select/key)만 줄이 됨. L8 새 형식(`{taskId, cardId, seq, op, …}`)은 그대로.
- 받는 길: ① 진입·진행 중 재개: 저장소의 progress 훅(`(task, info)`)을 감싸서 받음, L8이 `createDirectBrowserEntry`에 `onStep` 옵션을 추가하면 그것도 이미 연결됨(같은 seq는 한 번만). ② 도구 경로(L8): 제공자에서 `this.runtime.browserTaskStep(run, info, { taskId, cardId })` 호출. `alternate`가 아니면 아무것도 안 보냄(false).
- 화면 reducer 영향 없음 확인: `runId: null`이면 `ensureRun`이 null → 기존 화면 상태 불변. L1은 `event.event === 'browserTaskStep'`을 reducer와 별도로 받아 그려야 함(진입 단계는 대기 중 전송 `requestId`로 묶기).

### 2.3 속도
- 진입 판단 합치기: bounded 턴에는 진입 말고 다른 턴 시작 결정 요청이 없음(시험: 첫 메시지 결정 요청 = 진입 1 + 1단계 1). 유지. **L8 제안**: 진입 질문과 첫 단계 next_step을 한 요청에 묶으면 왕복 1회(약 0.3초) 절약(`egdesk-browser-task.mjs`, L8 파일이라 손대지 않음).
- 대화 모델 프로세스 미리 시작: `alternate`일 때 진입을 기다리는 동안 Claude CLI를 그 턴의 사양(model·effort)으로 미리 띄움(새 어댑터 메서드 `prepareTurn`). 재생 시험: 프로세스 생성이 진입 결정 완료 전에 일어나고, 프로세스 1개, 첫 메시지는 시작 완료 후에만 씀. `on`에서는 전처럼 턴과 함께 시작. 실제 절약 시간은 미측정(새 대화 첫 턴에서 CLI 시작 시간만큼 예상, 이미 떠 있는 프로세스면 이득 없음). Codex는 해당 없음(앱 서버가 이미 떠 있음).
- 어댑터 `ensureProcess` 순서 수정: 시작 중인 프로세스가 있으면 그것부터 기다림(이전에는 `session.proc`이 시작 완료 전에도 반환될 수 있었음). 미리 시작과 턴이 겹칠 때 시작 전 쓰기를 막는 안전 수정, 기존 동작에는 더 안전한 쪽만.

### 2.4 L8 도구가 bounded 턴에 실리도록
- 런타임의 bounded 상호작용 허용 목록에 `egdesk_browser_task`(L8 임시 이름) 추가. `egdesk-browser` 제공자가 내놓을 때만 실리고, 조작 허용 카드에서만, 일반 대화·관찰 허용에서는 안 실림(시험). 지금은 아무도 안 내놓으므로 변화 없음.
- 도구 호출 검사상 인자에 `cardId`가 있어야 함(런타임 dispatch가 `event.arguments.cardId`로 카드 허용을 확인).
- `this.runtime.browserTasks()`: 진입의 작업 저장소(진입 꺼짐이면 null) → 도구가 진입이 멈춘 **같은 작업**을 이어받을 수 있음(대화 키 = `run.clientThreadId`).

## B. 고친 것 (L8과 겹치지 않게, 런타임 연결만)
1. **진입 칸 채우기(L8 `fieldText`) 배선**: 진입 생성 3곳(`directBrowserEntry` = 사전 진입·진행 중 재개, `browserOpenItemSource`)에 `fieldText: () => browserAlternateOn()`. 새 플래그 없음: `EGDESK_BROWSER_ENTRY=alternate`에 포함. 재생 시험: `alternate` → 진입이 메시지 구간 "장화 신은 고양이"를 결정 모델로 골라(field_text) 입력하고 GET 검색 → **Claude 턴보다 먼저 카드가 움직이고**, Claude는 `done` note로 한 번만 말함. 단계 = fill·submit·done.
2. **화면 단계는 L1 채널 하나로**: 내 chat.event `browserTaskStep`(transient)과 저장소 훅·옛 단계 형식은 **삭제**. 진입·재개는 L8의 `onStepEvent`, 도구는 `runtime.browserTaskStep(run, event, ids)` → 모두 `decisionContext.browserSteps.publish(step)`(L1 형식: clientThreadId·taskId·seq·op…). op 변환: open→navigate, submit, press→click(버튼), fill, scroll, end→done / handoff(+이유) / blocked. 이유: detail_needed·needs_value→needs_value, needs_guidance·uncertain·page_unclear→low_confidence, choice_needed·confirm_needed→needs_user, human_step 계열→human_step. 진입이 끝날 때 마지막 한 줄(done 또는 넘김)을 런타임이 같은 seq 줄로 냄(도구는 자기 end를 냄). 값 원문·주소·본문 없음(시험). L1 플래그(`EGDESK_BROWSER_STEPS_UI`)가 꺼지면 채널이 아무것도 안 보냄. `on`·`alternate` 공통.
3. **`browserTaskMessage(run)`**(L8 `messageOf` 훅): bounded 브라우저 턴의 사람 메시지(요청 id와 사전 실행 id 기준, 메모리만, 최근 100개, 진입이 켜졌을 때만). 진행 중 재개는 그 답장으로 갱신.
4. **키 불일치**: L8 도구가 `conversationId` 우선으로 작업을 찾아, 실제 실행(Claude·Codex 턴)에서 goal 없이 부르면 진입이 멈춘 작업을 못 찾음. `clientThreadId` 우선으로 바꾸는 한 줄을 L8에 알렸고 L8이 d5f7aa7로 반영(내 수정은 빼고 L8 것을 받음). 재생 시험: `on`에서 진입이 멈춘 뒤 Claude가 MCP로 `egdesk_browser_task({})`를 부르면 같은 작업(taskId 동일)을 이어 받아 메시지 구간으로 입력·검색, done.
5. **허용 목록**: 내가 넣었던 `egdesk_browser_task`의 bounded 허용 목록 항목 삭제(L8 도구는 page 도구라 page 관문(첫 조작 카드를 navigate 권한으로 검사)으로 통과, cardId 불필요). 도구 이름은 L8 모듈 상수(내 모듈은 그것을 다시 내보내기만, 사본 없음).
6. **결정 호출 종류표**: `browser_entry*` → `browser`(`egdesk-decision-call-log.mjs` 한 정규식).
7. 제거한 것(중복): "진입이 값 때문에 멈추면 작업 도구로 자동 이어 가기"는 L8 fieldText와 같은 일이라 뺌.

## C. 속도 "+4.1초" 분석 (구현 안 함)
- 4회 `other`는 **턴 시작 판단이 아니라 진입 자신의 질문**(이제 `browser`로 찍힘). bounded 턴에는 진입 말고 턴 시작 결정 요청이 없어 rideAlongEntry로 묶을 대상이 없음.
- Claude: 진입 첫 호출 +13~23ms(지연 없음). Codex(16:51): 첫 진입 호출 +2336ms = 진입 **앞**의 bounded Codex 스레드 준비(app-server MCP 목록 읽기 등, c25 기록상 1~2초). 
- 병렬 시작(진입을 스레드 준비와 동시에)은 진입이 카드를 **움직인 뒤** 스레드 준비가 실패(예: 409 오래된 대화)하면 거절된 메시지에 카드만 바뀌는 문제가 있어 이번에 넣지 않음. 제안: 진입의 판단·관찰은 스레드 준비와 동시에, 첫 **행동**만 스레드 준비 성공 뒤로(Codex 첫 턴 약 2초 절약 예상, 미측정).
- Claude 프로세스 미리 시작(`prepareTurn`, alternate)은 그대로 있음.

## D. 못 한 것 / 제안
- bounded 턴의 결정 호출 행을 run에 닫힌 값으로 남기기(L2 제안): bounded 턴에는 decisionContext 활동 행이 없어 지금은 기록 메모리(재시작 시 사라짐)에만 있음. 새 활동 행은 화면에 보일 수 있어 이번에 넣지 않음. 제안: run checkpoint에 화면에 안 보이는 닫힌 필드로 붙이거나, 진입 전용 닫힌 활동 행을 L1과 합의 후 추가.
