## 1. D27: 브라우저 대화의 답이 영어로 오는 원인

**원인 (재생 세계에서 확인)**
- 브라우저(bounded) Claude 스레드는 own-tools 스레드가 아니다(`ownTools = !bounded && ...`, codex-chat-runtime 2653). 그래서 하네스 지침(`claudeHarnessInstructions`)이 한 번도 전달되지 않았다.
  - 재생 세계 실측: bounded 프로세스의 `appendPrompt`가 `null`이었다. EG-Desk 지시는 0줄이고, Claude Code 기본 프롬프트만 있었다.
- 그 턴에 EG-Desk가 모델에게 넣는 것은 전부 영어이거나 페이지 언어다.
  - 진입 note JSON(`next: report_to_user`)
  - 도구 결과의 표시와 거절 문구(예: `codex-tool-errors.mjs`의 'Browser tool request was rejected; inspect the selected Card and Run state.')
  - `forYouOnly` 메모, 페이지 줄
  - 사람이 어느 언어로 읽는지 말해 주는 곳이 없다.
- Main의 16:18 실창 재현과 맞는다. 거절된 도구 결과가 여러 번 쌓인 뒤 답이 전부 영어로 왔고, 같은 대화에서 실패 없이 끝난 검색 답은 한국어였다.

**다른 갈래 점검 (해당 없음 또는 작음)**
- 새 스레드에서 도는 사적 턴(고쳐 쓰기, 하트비트 작성): `internalFresh`가 사람의 마지막 메시지를 preamble로 붙인다("Context: the person's last message to you was ..."). 그래서 "in the language they wrote in"을 판단할 수 있다. 하트비트는 `EGDESK_CONVERSATION_FLOW`가 꺼져 있어 오늘 설정에서는 말하지 않는다.
- 적용된 언어 지침(눈치)은 bounded 턴에 가지 않는다(D26, `nunchiText = bounded ? null`). 기본값이 사람 언어이므로 이번 증상과는 무관하다. 다만 사람이 "영어로 답해"를 적용해 두고 한국어로 쓰면, 브라우저 대화에서는 그 지침이 무시된다(D26 결정에 포함).

**수정**
- `REPLY_LANGUAGE`(모델용, 화면 문구 아님) 원문:

  > Write to the person in the language they write to you in (for example Korean when they write in Korean), unless they asked you for another language. Tool results, EG-Desk's notes and page text may be in English or another language: they are for you and do not set the language of what you write to the person.
- 하네스가 켜져 있을 때만, bounded Claude 스레드가 시작·재적재될 때 `developerInstructions`를 넣는다. 내용은 Agent 글(있으면), `COMMENTARY`, `REPLY_LANGUAGE` 순서다.
  - own-tools 블록과 기억 줄은 bounded에 해당하지 않아 넣지 않았다. 명령·파일 도구가 없고, EG-Desk가 지침을 전달하지 않기 때문이다.
  - CLI 옵션은 이미 쓰는 `--append-system-prompt`이고 `--restricted`와 같이 써도 된다(CLI 도움말 확인).
  - bounded 프로세스는 `--system-prompt-snapshot off`이고 매 턴 재적재된다. 따라서 이미 있는 브라우저 대화도 다음 턴부터 적용된다.
- 일반 하네스 지침 끝에도 같은 줄을 붙였다. 그 앞부분은 한 글자도 바뀌지 않았다(기존 시험 그대로 통과).
- 하네스 꺼짐(SUB-10 단독)과 Codex는 그대로다.
- 언어는 모델이 지켜야 하는 부분이다. 시험은 지시가 들어가는 것까지만 보장하므로, 실창에서 확인해야 한다(아래 절차).

## 2. 보류·해설 정합

**원인**
- bounded 턴의 보류는 `browserTaskHoldEligible()`일 때만 걸렸다. 즉 점검이 켜져 있고 결정 모델이 설정됐을 때뿐이었다.
- u8의 하네스 보류(`claudeHarnessHold`)는 bounded가 아닌 턴에만 적용됐다(`context.draftHold = !bounded && ...`).
- 그래서 결정 모델을 '끔'으로 두거나 점검을 끄면, 브라우저 턴의 도구 사이 글이 답보다 먼저 별도 말풍선으로 올라왔다.
  - 재생 실측: 말풍선 2개 ["Value is "우산" (replaced)...", "검색창에 우산을 입력했습니다."]

**수정 (한 줄)**
- bounded 브라우저 턴에서 `browserTaskHoldEligible() || claudeHarnessHold(body, context)`이면 기존과 같은 `holdOnly` 보류를 건다.
- 결과: 도구 사이 글은 작업 메모(기존 활동 행)가 되고, 답(또는 사람에게 묻는 질문) 1개만 게시된다.
- 그대로인 것:
  - 점검은 여전히 bounded에서 돌지 않는다(원문 게시).
  - `holdOnly`라서 하트비트가 말을 시작하지 않는다.
  - 진입 note가 있고 점검이 켜진 경우의 `browserTaskTurn` 경로는 기존 첫 분기 그대로다.

**이중 보류와 흐름 막힘**
- 가드는 실행당 하나다(`startTopicAnswerGuard(run, 'draft')`).
- `draft` 가드에는 시간 제한이 없어서, 오래 걸리는 도구(L8 작업 도구) 중간에 강제로 방출되지 않는다.
- 도구 시작 때 방출되는 글은 하네스 아래에서는 작업 메모다(u8).

**needs_value 질문**
- Claude가 사람에게 묻는 질문은 그 턴의 마지막 글이므로, 답 말풍선 1개로 게시된다(시험 6). bounded Claude에는 AskUserQuestion이 없다(`--tools ""`).
- 참고: bounded 실행은 답 속 제안·질문 등록 대상에서 빠져 있다(`registerProposals`의 `run.executionPolicy` 조건). 그래서 사람의 짧은 답("응")은 열린 항목으로 해석되지 않고, Claude가 대화 기록으로 이어받는다. 기존 설계이고 바꾸지 않았다.

## 3. 초안 점검이 단계 기록(steps)을 근거로 쓰는지: 쓰지 않음 (D26은 그대로)

**지금**
- bounded 턴은 점검하지 않는다(`draftCheckTurns.skip = 'ineligible'`, 점검 질문 0개; 시험 8).
- 점검이 돌았다고 해도, 근거로 남는 것은 이것뿐이다.
  - 브라우저·페이지 도구 호출: 내용 없는 참조(`opaque`)뿐이다. 실행 활동 기록에는 `{ tool, executedBy }`만 있고, 결과·대상·단계는 남지 않는다(시험 8이 고정).
  - 진입 note: `browser_task_record`가 허용될 때만 읽을 수 있는 근거가 된다. stepsDone, actions 개수, found/page 줄이 들어 있다.
  - L8의 새 작업 도구 결과(steps): 지금 구조로는 역시 opaque 참조가 된다.

**D26을 켜면 달라지는 것**
1. 브라우저 턴의 답도 점검·고쳐 쓰기 대상이 된다. 보류 시간이 점검만큼 늘고, 고쳐 쓰기가 생기면 Claude 새 스레드 6~10초가 더 든다.
2. "제가 검색했습니다" 같은 이번 실행 주장은 그대로 통과한다. opaque 참조가 뒷받침할 수 있다고 보고, 점검은 근거가 전혀 없을 때만 잡기 때문이다. 단계 기록으로 맞는지 보려면 다음이 필요하다.
   - 실행에 도구 결과를 `ownCommands`/`ownEdits`처럼 남긴다(동작, 대상 이름, 결과 상태, 이동 후 경로).
   - `answerFactsEvidence`가 이를 `browser_task_record` 범위 안에서 읽을 수 있는 항목으로 바꾼다.
   - 실행 사실 규칙을 하나 추가한다(입력·검색·누름 주장을 성공한 단계와 대조, `claimsEdit`와 같은 모양).
3. 페이지 줄이 점검 근거로 결정 모델에 간다. 사용자는 15:58에 버튼·입력칸 이름은 전부 허용하고 본문은 제외했으므로, found/page 줄은 `page_text` 허용에 묶여 있어야 한다.
4. 맥락·눈치가 브라우저 턴에도 들어간다. 적용된 언어 지침 같은 사용자 지침이 브라우저 대화에도 전달된다.
