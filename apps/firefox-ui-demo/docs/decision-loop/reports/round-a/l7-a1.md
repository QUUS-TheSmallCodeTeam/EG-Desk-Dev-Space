# L7 a1: 다른 전역에서 만든 값의 `instanceof` 확인 (D25와 같은 종류)

브랜치 `lane/a1-cross-realm` (base `c37ab23`), 커밋 `2d03d1a`. 작업 사본 `$L/wt-l7-a1`.

## 사용자에게 보이는 동작 변화 (먼저 읽을 것)
- 답의 브리핑을 중간 단계(첫 단계와 마지막 단계가 아닌 곳)에서 닫았다가 같은 답의 브리핑을 다시 열면, 실제 창에서 처음으로 "지난번에 N단계까지 읽었습니다." 안내와 [N단계부터 이어보기] [처음부터] 버튼(`data-testid="briefing-resume"`)이 나온다.
- 지금까지 실제 창에서는 이 안내가 한 번도 나올 수 없었다(코드 흐름으로 확인, 아래 근거). 기억은 창이 켜져 있는 동안만, 최대 40개 유지되는 기존 설계 그대로다. [처음부터]는 그 기억을 지운다(이것도 이제 실제로 동작한다).
- 그 밖의 동작, 문구, 플래그, 도구 이름은 바뀌지 않았다.

## 원인 (코드로 확인)
- 창 코드 `overlay/JS/eg-desk-surface.uc.js`가 기억을 창의 Map으로 만든다: 3136행 `closeAnswerBriefing._stepMemory ||= new Map()`, 3513행·3768행도 같은 Map을 넘긴다.
- `EGDeskBriefingState.sys.mjs`는 22행에서 옵션 없는 `ChromeUtils.importESModule`로 불러오므로 Firefox의 공유 모듈 전역에서 돈다. 창과 다른 전역이라 창의 Map은 모듈 안에서 `instanceof Map`이 false다. 같은 사실이 `EGDeskViewportExtras.sys.mjs` 172행 주석, `EGDeskPortableState.sys.mjs`·`EGDeskReviewHandoff.sys.mjs`의 "IOUtils bytes from a different Gecko realm" 주석, L6의 D25 원인 분석과 일치한다.
- 결과: `rememberBriefingStep`이 매번 바로 돌아가 아무것도 기억하지 않았고, `briefingResumeOffer`는 늘 null, `forgetBriefingStep`은 아무 일도 하지 않았다. Node 시험은 한 전역이라 통과해 왔다.

## 고친 것
- `EGDeskBriefingState.sys.mjs`: `memory instanceof Map` 3곳(149·159·162행)을 모듈 안의 `isMap`으로 바꿨다. `isMap`은 `Map.prototype.size`의 고유 getter를 `call`해서 내부 슬롯을 확인한다. 어느 전역의 Map이든 통과하고, Map처럼 생긴 객체나 Set·WeakMap은 통과하지 않는다. 기존 코드(PortableState·ReviewHandoff의 typed array 고유 getter)와 같은 방식이다. 새 모듈이나 새 import는 없다(QA 프로필 스크립트의 파일 목록에 영향 없음).
- 시험 `scripts/egdesk-briefing-focus.test.mjs`(게이트 목록에 있음):
  - `vm.runInNewContext('new Map()')`로 다른 전역의 Map을 만들어 기억, 제안, 지우기가 모두 되는지 확인. 수정 전 코드에서 실패(30개 중 1개 실패)하는 것을 확인한 뒤 고쳤고, 고친 뒤 30/30 통과.
  - Map이 아닌 값(undefined, null, {}, [], Map 흉내 객체, 같은 전역·다른 전역의 Set, WeakMap)은 기억도 제안도 없음을 고정(덕 타이핑으로 느슨해지지 않게).
- 새 시험 `scripts/egdesk-cross-realm-checks.test.mjs`: `overlay/resources` 아래 모듈(vendor 제외)에서 내장 타입 `instanceof`를 세어, 아래에서 검토한 곳의 개수 상한을 넘으면 실패한다. 줄어드는 것은 실패하지 않으므로 L6이 BrowserGrant의 3곳을 없애도 병합 순서와 무관하게 통과한다. BriefingState에는 0개임을 따로 고정했다.

## 남은 위험
- 실제 창에서는 확인하지 않았다(지시대로 실행 중인 EG-Desk를 건드리지 않음). 근거는 코드 흐름, 같은 저장소의 실측 주석, L6 분석, 두 전역 재현 시험이다.
- AccountContext·CanvasLayout의 잠재 위험 2곳은 지금 호출 흐름에서는 해가 없어 지시대로 바꾸지 않았다. 새 점검 시험의 주석과 이 보고서에 남겼다.
- 새 점검 시험은 내장 타입 `instanceof`만 센다. 다른 형태의 전역 의존 확인(예: 다른 전역 객체의 `constructor` 비교)은 지금 0건이지만 시험이 잡지는 않는다.
- L6도 전역 무관 확인 도우미를 만들 수 있다. 내 쪽은 BriefingState 안의 작은 함수(`isMap`) 하나라서 병합 충돌 위험이 낮고, 나중에 하나로 합치면 된다. L6의 BrowserGrant 수정과 파일이 겹치지 않는다.

## Main이 실제 창에서 확인할 절차
1. 병합 후 EG-Desk를 다시 켠다(모듈은 시작할 때 읽힘).
2. 브리핑이 있는 답에서 브리핑을 열고 2단계나 3단계(첫·마지막이 아닌 단계)로 옮긴 뒤 닫는다.
3. 같은 답의 브리핑을 다시 연다 → "지난번에 N단계까지 읽었습니다." 와 [N단계부터 이어보기] [처음부터]가 보여야 한다(`[data-testid=briefing-resume]`).
4. [N단계부터 이어보기] → N단계로 이동. 다시 닫고 열어 [처음부터] → 안내가 사라지고, 그 뒤 다시 열면 안내가 없어야 한다.
