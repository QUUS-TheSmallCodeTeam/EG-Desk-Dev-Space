## 1. 로드 기제 (확인)

EG-Desk 쪽 관찰자가 아니고 MozBrowser의 JS setter도 아니다. Gecko C++의 속성 변경 처리다. 설치된 Firefox(`~/Applications/Firefox.app`, 160.0.1, mozilla-release)의 omni.ja와 `FIREFOX_160_0_1_RELEASE` 태그 소스를 읽기만 해서 확인했다.

- EG-Desk: `src`를 보는 MutationObserver가 없다(attributeFilter는 style/class/hidden/disabled/aria-hidden/tabindex 등뿐).
- MozBrowser(omni.ja `chrome/toolkit/content/global/elements/browser-custom-element.mjs`): `observedAttributes`는 `["remote"]`뿐이고 `src` 접근자가 따로 없다.
- `xulBrowser.src = url`은 `XULElement.webidl`의 `attribute DOMString src` → `nsXULElement::SetSrc` → `SetAttr(nsGkAtoms::src)`다. 즉 `setAttribute`와 같은 경로이고, 바로 앞 줄에서 setAttribute를 했으므로 XUL에서는 늘 같은 값 대입(아무 일 없음)이다.
- 다른 값일 때: `Element::SetAttr` → `XULFrameElement::AfterSetAttr`(160.0.1 191행: `if (aName == nsGkAtoms::src && aValue) LoadSrc();`) → `LoadSrc()` → 카드의 기존 `nsFrameLoader::LoadFrame()` → `GetURL()`이 src 속성을 읽고, triggering principal은 `<browser>`의 `NodePrincipal()`(chrome 문서) → `LoadURI` → `ReallyStartLoadingInternal`(LOAD_FLAGS_NONE, `SetIsFromProcessingFrameAttributes`, 소유 요소 기준 referrer) → 원격이면 `mRemoteBrowser->LoadURL(loadState)`. 이미 있는 frame loader와 browsing context를 그대로 쓰므로 컨테이너(userContextId)도 그대로다.
- 같은 값일 때: `Element::MaybeCheckSameAttrVal`(`valueMatches` → true) → `OnlyNotifySameValueSet` → `OnAttrSetButNotChanged`. 기본 Element 구현은 custom element의 observedAttributes 콜백만 부르고(MozBrowser는 `remote`만 봄), `XULFrameElement`는 이 함수를 재정의하지 않는다. 그래서 로드가 일어나지 않는다. HTML iframe은 `nsGenericHTMLFrameElement::OnAttrSetButNotChanged`가 `LoadSrc()`를 부르기 때문에 같은 값에서도 로드된다(HTML 규격).
- src 제거: `XULFrameElement::AfterSetAttr`는 값이 있을 때만 `LoadSrc()`를 부르므로 XUL에서는 아무것도 로드하지 않는다. HTML iframe은 제거해도 `LoadSrc()`가 불려 about:blank를 로드한다.

Main이 실창에서 본 것(같은 문자열은 무시되고 `?t=h_`는 바로 이동)과 정확히 맞는다.

## 2. 수정

`loadBrowserUri`에 한 줄을 넣었다.

```js
if (xulBrowser?.localName === 'browser' && xulBrowser.getAttribute('src') === url) xulBrowser.removeAttribute('src');
xulBrowser?.setAttribute?.('src', url);      // 기존
if ('src' in xulBrowser) xulBrowser.src = url; // 기존
```

- 조건이 Gecko가 무시하는 조건과 정확히 같다(속성 값과 문자열이 정확히 같을 때). 이때만 먼저 지우고(로드 없음), 다시 넣으면 `AfterSetAttr` → `LoadSrc` → 같은 frame loader가 돈다. 그래서 다른 값일 때와 로더, triggering principal(NodePrincipal), browsing context·컨테이너, LOAD_FLAGS_NONE과 docshell 기록 처리가 모두 같다. 새로고침(`reload()`)이 아니라 그 주소로 이동하는 것이고, 결과 페이지에서 `https://duckduckgo.com/`로 가면 첫 화면이 뜬다. 카드 자체 기록(`pushBrowserHistory`, historyIndex)은 손대지 않았다.
- 다른 값일 때는 전과 똑같다. 지우는 단계가 없다.
- 컨테이너 확인(`requireBrowserContext`)이 지우기보다 먼저라서, 컨테이너를 확인할 수 없으면 src를 건드리지도 로드하지도 않는다(전과 같음).
- HTML iframe 대체 경로는 `localName === 'browser'` 조건 때문에 빠진다. 지우면 about:blank를 한 번 더 로드하게 되기 때문이고, 원래 같은 값에서도 로드되므로 고칠 필요가 없다.
- 플래그, 화면 문구, 도구 이름은 새로 만들지 않았다. 기본 동작으로 고쳤다.

이 함수를 지나는 경로(모두 이제 같은 주소여도 로드된다):
- 주소창 Enter(`navigateBrowser(url)`)
- 홈 버튼(`browserCardControl(card,'home')` → `home: () => navigateBrowser(browserState.homeUrl)`)과 메뉴의 '홈' 항목
- 카드 자체 뒤로·앞으로(`goBrowserBack`/`goBrowserForward`에서 카드 history 안을 이동하는 분기). 네이티브 `goBack`/`goForward`로 넘어가는 분기는 손대지 않았다.
- 에이전트: `performBrowserAgentAction` navigate, `browserToolNavigateChrome`(허용 사이트 이동), `browserToolHistory` back/forward
- Firefox Library의 `navigateCard`, 공개 `browserRuntime.navigate/home/back/forward`

부수 효과(바로잡는 쪽): 에이전트 이동 가드의 `loadBrowserUri('about:blank')`와 자격 증명 페이지 정리의 `navigateBrowser('about:blank', { replaceHistory: true })`도 같은 함수를 쓴다. 전에는 src가 이미 `about:blank`이면 아무 일도 하지 않아 페이지가 남을 수 있었는데, 이제는 실제로 비운다. 시험 4로 고정했다.

그대로 둔 경로(같은 주소면 다시 로드하지 않는 것이 맞거나 이번 범위 밖):
- 카드 생성과 복원의 첫 src(`if (!options.deferInitialLoad) xulBrowser.setAttribute('src', normalizedUrl)`). 복원은 새 카드를 만드는 것이라 이 함수를 지나지 않는다.
- Codex 로그인 카드 재사용(`ensureCodexAuthBrowserCard`의 `existing._xulBrowser?.setAttribute('src', url)`)
- 새로고침: XUL은 `xulBrowser.reload()`를 쓴다. 대체 경로 `loadBrowserUri`는 reload가 없는 iframe에서만 쓰이므로 동작이 같다.

## 3. 시험 `scripts/egdesk-browser-card-same-address.test.mjs`

기존 방식(`readSurfaceSource()` + `between()`으로 실제 소스 구간을 잘라 `new Function`에 가짜 의존성을 넣어 실행, `egdesk-browser-tool-transport.test.mjs`와 같은 방식)을 따랐다. 실제 코드 구간은 `readNativeHistoryFlags`부터 `readRequestedBrowserUri`까지, `syncBrowserStateFromBrowser`와 `requireBrowserContext`, `loadBrowserUri`부터 `goBrowserForward`까지다. 가짜 `<browser>`는 Gecko처럼 동작한다. 같은 값 대입은 무시하고, 제거는 로드하지 않으며, iframe일 때는 HTML 동작을 따른다. `loadURI`, `fixupAndLoadURIString`, `reload`, `goBack`, `goForward`는 불리면 실패한다.

1. Main 재현: about:blank → `https://duckduckgo.com/` → 페이지 안 검색 결과로 이동 → 같은 주소로 이동. 로드가 정확히 1번, 같은 컨테이너로 일어나고, 페이지·카드 상태·주소창이 일치하며, 카드 기록에는 다른 주소처럼 쌓인다. `?t=h_`(다른 문자열)는 전과 같은 경로(지우기 없음)로 간다.
2. 홈이 처음 주소일 때 홈 버튼
3. 카드 뒤로로 처음 주소에 돌아감, 앞으로, 기록 중간에서 뒤로, 앞으로 분기의 같은 값
4. 가드나 자격 증명 정리로 비울 때, src가 이미 about:blank여도 비워짐
5. 컨테이너를 확인할 수 없으면 로드 없음, src 그대로, 알림 1번
6. HTML iframe 대체 경로: 지우기 없음, about:blank 로드 없음
7. 소스 고정: 주소창·홈·뒤로·앞으로가 이 경로로 오는지, `removeAttribute('src')`가 소스 전체에서 `loadBrowserUri` 한 곳뿐인지, 카드 생성과 로그인 카드의 src 대입이 그대로인지

## 4. 남은 문제

- 실창 확인은 하지 않았다(규칙). 실행 중인 EG-Desk는 int-c14 overlay라서, 이 수정이 통합·설치되고 앱이 다시 시작되어야 반영된다.
- iframe 대체 경로는 `setAttribute` 다음에 `.src = url`을 또 해서 원래부터 두 번 로드한다(기존 동작). 동작이 바뀌므로 정리하지 않았다.
- Codex 로그인 카드 재사용 경로도 같은 URL이면 다시 로드하지 않는다. 로그인 URL은 보통 state 값이 달라 문제가 되기 어렵다고 보고 그대로 두었다. Main 판단 사항이다.
- 같은 주소를 다시 쳤는데 페이지가 실제로 이미 그 주소일 때(페이지 안 이동이 없었을 때)도 이제 다시 로드된다. Firefox 주소창에서 같은 주소로 Enter를 친 것과 같고, 기록 처리는 Gecko의 같은 URL 처리 규칙을 그대로 따른다(다른 값일 때와 같은 로더).
- 기존 코드에서는 같은 주소 이동 때 `setBrowserLoading(true)` 뒤에 로드가 없어서 8초 타이머가 끝날 때까지 카드가 '로딩 중'으로 남았을 것이다(코드상 추정). 이 수정으로 실제 로드가 일어나므로 함께 없어진다.

## 5. Main 실창 확인 절차 (Marionette chrome 문맥)

먼저 이 커밋을 통합·설치하고 EG-Desk를 다시 시작한다. 그다음 chrome 문맥에서 실행한다.

```js
const card = document.getElementById('<카드 id>'); // 또는 document.querySelector('#egd-canvas-layer > .egd-browser-card')
const c = card._browserControls, b = () => c.toolBrowser();
const wait = async (pred, ms = 10000) => { const t = Date.now(); while (!pred() && Date.now() - t < ms) await new Promise(r => setTimeout(r, 100)); return pred(); };
const DDG = 'https://duckduckgo.com/';
const inPage = async () => { // 페이지 안 이동 대용: src를 건드리지 않음(페이지에서 직접 검색해도 됨)
  b().fixupAndLoadURIString('https://duckduckgo.com/?q=eg-desk&ia=web',
    { triggeringPrincipal: Services.scriptSecurityManager.getSystemPrincipal() });
  await wait(() => b().currentURI.spec.includes('q=eg-desk')); c.sync();
};
const ctx0 = b().browsingContext.originAttributes.userContextId;
```

1. 주소창 경로(navigate): `c.navigate(DDG); await wait(() => b().currentURI.spec === DDG)` → `await inPage()` → 전제 확인: `b().getAttribute('src') === DDG`이고 `b().currentURI.spec`이 결과 페이지 → `c.navigate(DDG); await wait(() => b().currentURI.spec === DDG)`. 기대: true, `c.getState().uri === DDG`, `b().browsingContext.originAttributes.userContextId === ctx0`. 원하면 `b().browsingContext.sessionHistory.count`가 늘어나는 폭이 `?t=h_` 이동과 같은지도 본다.
2. 홈: `const home = c.getState().homeUrl; c.navigate(home); await wait(() => b().currentURI.spec === home)` → `await inPage()` → `c.home(); await wait(() => b().currentURI.spec === home)`. 기대: true.
3. 카드 뒤로·앞으로: `c.navigate(DDG); await wait(() => b().currentURI.spec === DDG)` → `await inPage()` → `const i0 = c.getState().historyIndex; c.back(); await wait(() => b().currentURI.spec === DDG)`. 기대: true, `c.getState().historyIndex === i0 - 1`. 이어서 `c.forward(); await wait(() => b().currentURI.spec.includes('q=eg-desk'))`로 다른 값 경로도 확인한다.
4. 대조: 같은 상태에서 `c.navigate('https://duckduckgo.com/?t=h_')`가 전처럼 바로 이동하는지 본다.
