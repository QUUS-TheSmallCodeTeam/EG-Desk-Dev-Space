## 코드로 확인한 원인과 수정

1. Codex의 `registerPending`이 초안과 `inputSources` 전체를 비웠고, 다음 전송의 `browserToolSelectedSources`는 해당 대화의 이번 초안에 있는 선택만 검사한다. 따라서 유효한 standing grant가 있어도 선택 토큰을 갱신할 입력이 없었다. 일반/Board 전송 후 명시적으로 선택한 interact만 같은 대화 입력에 유지한다. 관찰·파일은 소모한다. 기존 대화 ID, 실제 카드, 사이트/계정, epoch, hold, 만료와 1회 토큰 검사를 우회하지 않는다. 메뉴 해제 시 두 엔진 모두 해당 대화 칩을 제거한다. 확실히 거절된 Codex 요청의 초안 복구 비교도 그 칩을 고려한다.
2. 로그인·2FA·봇 확인의 닫힌 페이지 상태가 `HANDOFF_OF`에 없었다. 코드의 세 상태를 `human_step`으로 번역하며 정상 넘김 end에 실패 비트를 싣지 않는다. 결제·권한의 기존 민감 흐름 맵은 유지한다. 재개 도구도 종료 이유 코드를 싣는다.
3. POST에서 제출자만 withheld이고 unsupported 제어가 없으면 기존 person-target 질문의 `personOnly.length` 조건이 false였다. 채팅 작업의 실제 POST submit은 중립 이름이어도 후보에서 빼고, withheld 버튼만 있어도 기존 목표 일치 판정을 한다. 다른 작업의 확신 낮음을 일괄 사람 차례로 바꾸지 않는다.
4. 도구의 `staleBy: user-hold`는 이미 구별되지만 루프가 일반 도구 오류/재시도로 처리했다. 이 신뢰된 거절이면 즉시 정지하고, `human_step` + 닫힌 `staleBy: user-hold`를 직접 진입/재개 메모에 보존한다. 대화 모델에는 사람이 직접 조작했다는 사실을 말하고 다시 시도하지 말라고 지시한다. 제공된 케이스 17 실행 자체에서 이 코드가 실제 발생했는지는 미확인이다.
5. `goal_met`의 대상이 최종 대화 답인지 브라우저 작업인지 불분명했다. 채팅 작업에 한해 지금 페이지에서 읽고 답하는 것만 남으면 브라우저 완료라고 묻는다. 페이지 상태 안전 판정이 먼저이고, 미완료·불확실을 강제로 done으로 바꾸지 않는다. 읽기·POST에 관한 실제 모델의 확률 변화와 케이스 12/14/15의 실행별 원인은 추정이며, 실창 검증이 필요하다. 과거 측정용 비채팅 요청 바이트는 유지했다.
