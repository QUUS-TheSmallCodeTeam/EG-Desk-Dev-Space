# L1 u1: '위' 작업 표면 (Desk·카드·터미널) 결함과 배치

브랜치 `lane/u1-desk-surface` (작업 사본 `$L/wt-l1-u1`, 기준 int/c14 `cf086b8`), 커밋 1개. 실제 창에서는 확인하지 못했다(합성 DOM·단위 시험·실제 zsh PTY 한 번). 실제 Codex·Claude 실행, 네트워크, 사용자 EG-Desk 접근 없음.

플래그: 로그인 카드 배치·성공 시 닫기는 기존 `EGDESK_TERMINAL_OPEN_URL` 경로에서만 일어난다. 터미널 환경 변수 정리, 줄 편집기 대기, 가장자리 점, 방 이름, 사용량 문구, 기록 없이 시작은 결함 수정이라 플래그가 없다. 휠 가드는 pref(`egdesk.wheelScrollGuard`, 기본 꺼짐), 검색창 라우팅 연결은 브리지가 알릴 때만 켜진다.

## 1. 로그인 카드가 화면 밖(오른쪽)에 열림
- 원인: 터미널이 연 카드는 `spawnBrowserCard(..., { background: true })`로 열린다. 위치는 `resolveCanvasCardPlacement('browser')`가 정하는데, 이 규칙은 "보이는 영역 안의 가장 가까운 빈 자리"를 찾고 터미널이 화면을 거의 채우면 영역 안에 자리가 없어 "가장 가까운 빈 캔버스 자리"(`inView:false`, 보통 오른쪽)로 간다. 그리고 `background:true`는 `revealPlacedCanvasCard`를 건너뛰므로 카메라가 따라가지 않는다. 그래서 화면 밖에 열려 가장자리 점만 남았다.
- 수정: 터미널 카드 옆 배치를 단순 코드 규칙으로 추가(`SurfaceState.placeBesideOpener`): 오른쪽, 왼쪽, 아래, 위 순서로 터미널의 윗변(또는 왼변)에 맞추고 보이는 영역에 들어오도록 가장자리를 따라 밀어, 다른 카드와 24px 이상 떨어진 첫 자리를 쓴다. 영역 안에 자리가 없으면(터미널이 화면을 채움) 터미널 옆 첫 빈 자리에 열고 `inView:false`로 표시, 이때 `revealPlacedCanvasCard`가 터미널과 새 카드를 함께 프레임에 넣고(`pairedRevealCamera`, 줌은 필요한 만큼만 줄어듦), 함께 못 넣으면 새 카드를 보인다(`revealAlone`). 카드는 계속 입력 포커스를 받지 않는다(`activate:false`). 결정 모델 배치는 제안으로 남긴다(c13 `workPlacement`의 `placeWorkSurface`에 `beside_related`가 이미 있어 같은 자리를 모델이 정하게 이을 수 있음).
- 시험: 순서·슬라이드·점유·화면을 채운 터미널·잘못된 입력(`egdesk-u1-desk-surface.test.mjs`), 터미널이 `besideOpener`/`revealBackground`를 넘김(`egdesk-terminal-window.test.mjs`), 표면 연결 정규식. 변이 U1~U6 모두 잡힘.
- 실창 확인: 설정 카드에서 로그인을 누른다. (a) 로그인 카드가 터미널 바로 옆(보통 오른쪽)에 보이는가, (b) 터미널과 로그인 카드가 둘 다 화면 안에 있는가(화면이 좁으면 줌이 조금 줄 수 있음), (c) 터미널에 입력 커서가 남아 있는가(로그인 카드가 포커스를 가져가지 않음). 터미널 창을 최대로 키운 상태에서도 같은 절차.

## 2. 로그인 성공 후 로그인 카드가 남음
- 원인: c36은 "터미널 세션이 끝나면" 닫았다. CLI가 성공하고 끝나도 셸 세션은 살아 있어 카드가 남았다. 또한 c36의 Settings 감시에는 결함이 하나 더 있었다: 성공하면 Settings 행이 더 이상 로그인을 권하지 않아 `isCurrent`가 false가 되고, 감시가 `signedIn`보다 먼저 `changed`로 끝나 성공을 놓칠 수 있었다.
- 수정: Claude 로그인 주소(`SurfaceState.claudeSigninPageUrl`: claude.ai, claude.com, anthropic.com. OpenAI 주소는 아님)로 카드가 열릴 때 표면의 `watchClaudeSignedIn(card, href)`가 터미널 카드당 감시 하나를 시작한다. `/engines/claude/refresh`(Settings 행과 같은 점검)를 3초마다(최대 5분) 호출하고, `claudeAccountView(...).status === 'signedIn'`이 되면 터미널 존이 연결된 카드를 닫는다. 감시는 Settings 로그인 행과 공유되며 끝나면 잊힌다(같은 터미널에서 다음 로그인이 앞의 성공으로 바로 닫히지 않음). 열 때 이미 로그인 상태였으면(두 번째 계정 로그인) `already`: 읽을 변화가 없으므로 이전처럼 세션 종료 때 닫힌다. `watchClaudeLogin`은 `signedIn`을 먼저 판정한다.
- 시험: 감시 순서, 표면 감시(샌드박스 추출: 한 번에 하나, 이미 로그인, 가드 꺼짐, 브리지 없음, 세션 끝남, 터미널 카드 사라짐), 터미널 존이 성공 때만 닫고 실패/끝남엔 닫지 않음. 변이 U7~U11 모두 잡힘.
- 실창 확인: 로그인을 끝낸 직후 3초 안팎(최대 몇 초)에 로그인 카드가 닫히고 설정 카드가 로그인됨으로 바뀌는가. 터미널 카드는 남는다.
- 한계: 로그인 중에 이미 다른 계정이 로그인된 상태면 감시가 읽을 변화가 없다(`already`).

## 3. 로그인 명령이 터미널에 두 번 찍힘 (c35 수정이 효과 없음)
- 원인(재현함): c35는 "첫 출력 뒤 400ms 조용하면 셸이 준비됨"으로 봤다. 실제 zsh를 PTY에 올려(`evidence/l1-u1/pty-probe.py`, 임시 ZDOTDIR의 `.zshrc`에 경고 한 줄 출력 후 1.5초 지연) 재현했다: 경고(0.02초) 뒤 침묵이 800ms면 c35의 규칙이 통과해 그때 입력하면 줄이 출력에 **2번**(tty 에코 + 줄 편집기 재그림) 나타난다. 프롬프트 뒤(2.5초)에 입력하면 1번. 4번 항목의 nvm 경고가 바로 그 "첫 출력"이다. 즉 원인은 입력 타이밍(프롬프트 감지)이며, 셸 초기화 출력이 그것을 속였다. 줄 편집기가 뜨는 시점은 zsh가 bracketed paste(`ESC[?2004h`)를 켜는 순간(위 실험에서 1.53초)과 정확히 일치했고, 그 순간(+0.1초)에 입력하면 1번이었다. bash 3.2(macOS 기본 /bin/bash)는 이 신호를 내지 않는다(실험으로 확인).
- 수정: 터미널(`egdesk-terminal-init.js`)이 `lineEditorReady()`를 노출한다(xterm 5.5의 `term.modes.bracketedPasteMode`: true=줄 편집기가 줄을 읽는 중, false=시작 파일 실행 중, null=판단 불가). 로그인 입력은 `shellReadyToType`로 결정: 편집기 true면 프롬프트가 안정(120ms)된 즉시, false면 2.5초 침묵일 때만(bracketed paste 없는 셸 대비), null이면 c35 규칙. 전체 대기 상한은 기존 8초(`readyTimeoutMs`)로, 상한에 닿으면 이전처럼 입력한다. 시작 파일이 2.5초 넘게 조용하면서 편집기 신호도 없는 셸은 여전히 일찍 입력될 수 있다(상한이 끝냄).
- 시험: 판정 함수 표, 실제 시간선(경고 0.02초, 편집기 1.53초 → 1.65초대 입력 1번), bash 3.2형(2.5초대), 상한(8초), 터미널의 `lineEditorReady` 값. 변이 U12~U15 모두 잡힘.
- 실창 확인: nvm 경고가 뜨는 셸에서 로그인을 눌러 명령이 한 번만 찍히는가. (4번 수정 뒤에는 경고 자체가 사라져야 하므로, 두 수정을 따로 보려면 4번 전의 빌드나 `NPM_CONFIG_PREFIX` 설정 상태에서 3번을 보면 된다.)

## 4. 터미널 첫 줄 "nvm is not compatible with the NPM_CONFIG_PREFIX ..."
- 원인: `terminalEnvironment()`가 브리지 프로세스 환경 전체(`{...process.env}`)를 셸에 넘긴다. 브리지는 Aside 런타임 아래에서 돌아 `NPM_CONFIG_PREFIX=…/.aside/runtime/node` 등을 갖는다. 이 에이전트의 환경에서 확인한 Aside 전용 값(이름만): `NPM_CONFIG_PREFIX`, `NPM_CONFIG_USERCONFIG`, `NPM_CONFIG_CACHE`, `NODE_PATH`, `VIRTUAL_ENV`, `OPENSSL_CONF`, `PIP_CACHE_DIR`, `TMPDIR`, `ASIDE_SKILL_RUNTIME`.
- 수정(`helper/terminal-platform.mjs`, `withoutAsideRuntimeEnv`): 값이 `~/.aside` 경로를 가리키거나 이름이 `ASIDE_`로 시작하는 변수는 터미널 셸에 넘기지 않는다. `PATH`, `PWD`, `OLDPWD`, `HOME`은 그대로 둔다(도구를 못 찾는 것이 폴더 하나 더 있는 것보다 나쁨). 사용자의 자체 `NPM_CONFIG_PREFIX`(예: `~/.npm-global`)와 그 외 모든 변수는 그대로 넘기고, 셸이 사용자 rc 파일을 읽는 것도 그대로다. 플래그 없음(결함 수정). `openUrl.envFor()`의 변수는 이 뒤에 합쳐진다.
- 한계/제안: `PATH` 앞부분에 Aside 런타임 `bin`이 남는다(이 PATH 정리는 도구 해석에 영향이 있어 제안으로 둠). 이 필터는 `~/.aside` 경로 값만 보므로 다른 경로의 Aside 값은 못 거른다.
- 시험: 이름·값 규칙, 사용자 값 유지, PATH 유지, Windows 경로, 입력 불변. 변이 U16~U18 모두 잡힘.
- 실창 확인: 새 EG-Desk 터미널의 첫 줄에서 nvm 경고가 사라지는가, `echo $NPM_CONFIG_PREFIX`가 비거나 사용자 값인가, `nvm use`/`node -v`가 사용자 도구를 가리키는가. (브리지를 재시작해야 반영됨: Main만.)

## 5. 화면 가장자리 점이 카드·글자를 가림
- 원인: c35(#2)는 **아래쪽** 점만 도크 옆으로 옮겼다. 왼쪽·오른쪽·위쪽 점은 안전 영역 가장자리(안쪽 6px)에 그대로 놓여, 그 가장자리까지 닿은 카드 위(글자 위)에 22px 버튼이 얹혔다. 아래쪽 점도 도크 높이대에 카드가 닿으면 겹친다. 로그인 카드가 오른쪽 화면 밖에 있던 11/25에는 오른쪽 점이 터미널 오른쪽 글자 위에 놓였을 가능성이 크다(추정). "c35 수정이 실창에 반영 안 됨"은 코드상으로는 반영돼 있고(아래쪽 점만 대상), 실창이 그 코드를 갖고 있는지(오버레이가 다시 설치됐는지)는 내가 확인할 수 없다.
- 수정(`EGDeskViewportExtras.edgeDotsAvoidCards`, 도크 규칙 뒤에 실행): 각 점의 눌림 영역(22px, "+N" 점은 더 넓게)이 보이는 어떤 카드와도 겹치지 않는 가장 가까운 위치로 같은 가장자리를 따라 민다. 가장자리 전체가 카드로 덮이면 창 가장자리 여백(8px)으로, 그것도 안 되면 겹침 면적이 가장 작은 곳으로 간다. 점끼리 26px 간격과 순서는 유지, 겹치지 않는 점은 같은 객체를 돌려준다.
- 시험: 슬라이드, 전체 덮임, "+N", 간격·순서, 입력 불변, 빈 입력, 깨진 사각형, 표면 연결. 변이 U19~U20 모두 잡힘.
- 실창 확인: 카드를 창 오른쪽·왼쪽·위 가장자리까지 늘려 놓고 화면 밖에 다른 카드를 둔다. 점이 카드 위가 아니라 카드 밖 빈 곳이나 창 가장자리로 가는가. 점을 눌러 이동도 되는가. 그래도 겹치면 `document.getElementById('egd-edge-dots')`의 점 좌표와 카드 사각형을 알려 달라.

## 6. 설정 카드 안에서 스크롤하면 캔버스 배율이 바뀜 (미확정)
- 코드 분석: 휠로 배율(`zoomTarget`)이 바뀌는 길은 `ctrlKey` 휠(핀치 포함)과 최대화 중 ⌘/ctrl 휠뿐이다. 일반 스크롤은 배율을 바꾸지 않는다. 활성 설정 카드 위의 일반 스크롤은 카드가 자체 스크롤하고(아무것도 소비하지 않음), 비활성이면 캔버스가 **이동**한다(시험으로 고정함: 표면의 휠 라우터를 추출해 실행).
- 발견한 한 가지 경로: 라우터는 `ctrlKey`를 "활성 카드 스크롤 세션" 판정보다 **먼저** 본다. 트랙패드 스크롤 중 손가락 간격이 조금 바뀌어 `ctrlKey`가 붙은 휠 이벤트가 하나만 섞여도 그 이벤트는 배율을 바꾸고, 같은 제스처의 나머지 이벤트는 캔버스 소유가 되어 카드는 스크롤을 멈추고 캔버스가 움직인다. 이것이 "스크롤하면 배율이 같이 바뀌는 것 같다"와 맞지만, 실창에서 `ctrlKey`가 섞이는지는 확인하지 못했다(미확정).
- 수정(확인 전이라 pref 뒤, 기본 꺼짐): `egdesk.wheelScrollGuard = "on"`이면, 활성 카드에서 시작한 스크롤 제스처(세션 140ms 이내)의 `ctrlKey` 휠은 스크롤로 보고 소비하지 않는다. 세션이 끝난 뒤 새로 시작한 ctrl/핀치는 이전처럼 줌, ⌘은 그대로. 확인되면 기본을 켠다.
- 시험: 가드 꺼짐/켜짐, 세션 만료, ⌘, 다른 카드. 변이 U21~U22 모두 잡힘.
- 실창 확인(재현 조건): 줌 표시(`#egd-zoom-indicator`)를 보면서 (1) 활성 설정 카드 위에서 두 손가락으로 길게 스크롤: 퍼센트가 변하는가, (2) 설정 카드를 클릭하지 않은 채(비활성) 스크롤: 캔버스만 움직이는가(배율 유지), (3) (1)에서 퍼센트가 변하면 about:config에 `egdesk.wheelScrollGuard` = `"on"`(문자열 JSON, 따옴표 포함)을 넣고 다시. 변하지 않으면 이 항목은 배율이 아니라 (2)의 캔버스 이동을 본 것일 수 있다.

## 7. 검색창 라우팅(`egdesk.hudRouting`)을 L3의 '위' 묶음 설정으로 켤 수 있나
- 확인 결과: **지금 구조로는 묶음이 켜도 검색창은 묻지 않는다.** 켜지려면 세 문이 모두 열려야 한다. (1) 브리지: `EGDESK_HUD_ROUTING` = advisory|on 일 때만 `/decision/hud-routing`이 답함(`hudRoutingEnabled`, 요청마다 읽는 함수라 묶음 설정이 읽도록 바꾸기 쉬움). (2) 결정 모델 모드가 advisory|on. (3) 창의 Firefox pref `egdesk.hudRouting`(`readSurfacePref`): 이것이 "아예 묻는지"를 정하며, 브리지 설정은 Firefox pref를 쓸 수 없다. 묶음이 (1)(2)만 열면 (3)이 off라 키 입력마다 타이머도 안 돈다.
- 수정(L3와 겹치지 않는 창 쪽만): `HudRouting.hudRoutingModeFor(pref, chatCapabilities)`: 사용자가 정한 pref(advisory, on, 명시적 off)가 이기고, pref가 없으면 브리지가 `chatCapabilities`로 알린 `hud-routing-advisory` / `hud-routing-on`이 정한다(c36의 `terminal-open-url`과 같은 방식). 알림이 없으면 off(기본 동작 그대로). 표면의 `hudRoutingModeNow()`가 이를 쓴다.
- **L3에게 넘길 계약**(브리지 쪽은 내가 건드리지 않음: `codex-bridge-server.mjs`는 L3가 만질 파일): 묶음 설정이 hud 라우팅을 켤 때 (a) `hudRoutingEnabled()`가 묶음 값도 보게 하고, (b) `/v1/state`의 `chatCapabilities`에 `hud-routing-advisory` 또는 `hud-routing-on` 중 하나를 넣는다. 이름은 `HUD_ROUTING_CAPABILITIES`(overlay)와 같아야 한다.
- 시험: pref 우선(명시적 off 포함), 알림만 있을 때, 잘못된 값, 표면 연결. 변이 U23 잡힘.
- 실창 확인: 묶음이 연결된 뒤 pref 없이 검색창에 문장을 쳐 보고(약 300ms 뒤 한 번 묻고 하이라이트가 움직이는가). 연결 전에는 아무 변화가 없는 것이 정상.

## Main 추가 요청 (01:25 실창 관찰)
### 8. 'AI 설정'의 '기록 없이 시작' 설명이 Claude에서도 코덱스 문구
- 원인: `chatStatelessStartView`의 설명이 코덱스 문구로 고정이고 방의 엔진을 보지 않는다. 게다가 스위치 가용성은 브리지 전체 능력(`stateless`)만 보는데, Claude 어댑터는 `ephemeralThreads` 능력이 없다(`claude-engine-adapter.mjs`: CLI가 자체 세션을 남김). 그래서 Claude 방에서도 스위치가 켜졌고, 보내면 `STATELESS_UNSUPPORTED`로 거절될 상황이었다.
- 수정: `chatStatelessStartView(thread, capabilities, codex)`에 창의 codex 상태를 넘겨 방의 엔진 행의 능력 목록을 본다. 목록이 있는데 `ephemeralThreads`가 없으면 스위치 없음(`available:false, on:false`, 보낼 때도 꺼짐) + 설명 `이 AI 엔진은 기록 없이 시작을 지원하지 않습니다.`. 네 곳(전송 옵션, 요청 구성, 엔진 패널, 빈 방)에 반영. Codex나 목록이 없는 엔진은 이전과 같다. 시험과 변이 U25 잡힘.
- **제안(승인 대기)**: 이 설명 문장은 기존 `STATELESS_UNSUPPORTED` 오류문의 앞 문장을 그대로 떼어 쓴 것이라 새 문구에 가깝다(`STATELESS_ENGINE_UNSUPPORTED_NOTE` 한 곳). 대안: 스위치와 설명을 아예 숨기기.
- 실창 확인: 새 대화에서 AI 설정을 열고 Claude를 고르면 '기록 없이 시작' 스위치가 사라지거나(위 설명으로) Codex 문구가 없는가. Codex를 고르면 이전과 같이 나오는가.

### 9. 대화 카드 제목·DM 이름이 엔진을 Claude로 바꿔도 'Codex 1'
- 원인: 새 DM 방의 이름은 만들 때 `Codex ${번호}`(상대 이름 'Codex')로 고정되고 `setThreadEngine`은 `engineId`만 바꾼다.
- 수정: (a) 엔진을 고를 때(첫 전송 전) 방 이름이 아직 기본 이름(`Codex N`/`Claude N`/`Codex`/`Claude`)이면 제목, 상대 이름(participants, 역할), 부제(`Agent DM · …`)를 고른 엔진 라벨로 바꾼다(`ChatState.relabelDefaultRoom`, 표면 `relabelRoomPatch`). 사람이 바꾼 이름, 이미 시작한 방(엔진 잠김), 그룹은 건드리지 않는다. (b) 새 DM 방은 처음부터 답할 엔진(최근/기본 엔진)의 라벨로 만든다. 시험과 변이 U26~U27 잡힘.
- 한계: 이미 저장된 `Codex 1` 방은 시작했다면 그대로다. 엔진 라벨은 엔진 목록의 `label`(Claude)을 쓴다.
- 실창 확인: 새 대화를 만들고 AI 설정에서 Claude를 고른다. 카드 제목과 대화 목록의 이름이 `Claude 1`로 바뀌는가. 직접 이름을 바꾼 방은 유지되는가.

### 10. 사용량 44%인데 "Claude 사용 한도에 가까워졌습니다"
- 원인: 문구와 수준은 우리 임계값이 아니라 제공자가 보낸 `status: allowed_warning`만으로 정해졌다(`runRateLimitNotice`). Claude CLI는 이 상태를 일찍 보낸다: 저장소의 기록된 이벤트에 5시간 창 42.5%가 `allowed_warning`으로 들어 있고(`claude-stream-translate.test.mjs`), Main이 실창에서 본 주간 44%도 같은 경우다. "가까워졌습니다"는 이 상태가 말해 주지 않는 주장이다.
- 수정: `RATE_LIMIT_WARN_FROM_PERCENT = 70`(실엔진 사용량 가드의 중단 기준 `CLAUDE_USAGE_STOP_PERCENT`와 같은 값)이상이거나 사용량 값이 없을 때만 경고(`warn`)로 보인다. 70% 미만이면 기존 문장 `Claude 사용량을 확인했습니다. 주간 한도 · 사용량 44%…`로 나온다(새 문구 없음). `rejected`는 한도 그대로. 시험과 변이 U24 잡힘.
- **제안(승인 대기)**: 임계값 70은 내가 고른 기준이다(소유자가 바꿀 수 있음, 상수 한 곳).
- 실창 확인: 사용량이 70% 미만일 때 대화 활동에 경고 대신 "사용량을 확인했습니다"가 나오는가.
