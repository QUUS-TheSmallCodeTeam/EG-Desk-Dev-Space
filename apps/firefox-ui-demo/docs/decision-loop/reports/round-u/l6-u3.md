# L6 u3: D12 승인 뒤 `egdesk_computer_read_elements` 가 계산기 창을 못 찾음

브랜치 `lane/u3-computer-read` (기준 int/c14 `e148fc9`), 커밋 `ff83234`. 게이트는 맨 아래.

## 1. 결론 [측정]
**창을 식별하는 방식이 어긋난 것이 아니라, 그 시각에 Mac 화면이 잠겨 있었다.** 화면이 잠기면 모든 앱의 접근성 창이 '프레임 없는 자리표시자'로만 읽히는데, 도우미가 이것을 "접근성 창 중 프레임이 같은 것이 없음" = `window_not_found` ("화면에 그런 창이 없다")로 잘못 보고했다. 창 목록(CGWindowList)은 잠금 중에도 창을 그대로 보여 주므로 "목록은 찾는데 읽기는 못 찾는" 모양이 되었다.
- 근거 1(화면 잠금 시간표): 통합 로그의 loginwindow 기록: 02:30:02 잠금 화면 표시, **02:53:31 해제**(사람이 돌아옴, Main 의 02:5x 실창 확인 시간대), **03:13:45 다시 잠금**(현재까지 유지: `CGSessionCopyCurrentDictionary` 의 `CGSSessionScreenIsLocked=1`, 03:28 측정). D12 의 두 시도는 03:13 이후다.
- 근거 2(같은 도우미 바이너리, 상태만 다름): u1 때(02:19, 잠금 전) 같은 바이너리가 실제 창 9개를 읽었다. 03:2x 에 같은 바이너리로 Finder, Aside, Brave, 미리보기, 계산기 등 **모든 앱의 모든 창이 `window_not_found`**. 계산기만의 문제가 아니다.
- 근거 3(도우미와 무관): 별도 Swift 스크립트(`AXIsProcessTrusted` true)로 Finder 의 `AXWindows` 를 읽으면 창 3개의 역할이 `AXApplication, AXApplication, AXScrollArea`(정상이면 `AXWindow`)이고 `AXPosition` 이 -25205(없음). 계산기의 `AXWindows` 도 `AXApplication` 하나뿐이고, 그 앱 요소의 첫 자식이 자기 자신(`CFEqual` true), 화면 중앙의 hit-test 도 앱 요소만 돌려준다. 즉 시스템 전체의 접근성 응답이 자리표시자 상태.
- 이름 문제(한국어 '계산기' vs 'Calculator'): 이번 증상의 원인은 아니다(그 경우는 `app_not_found` 가 나온다). 다만 같은 계열의 실제 약점이라 같이 고쳤다(아래 2-3).

## 2. 수정
1. **Rust 도우미** (`helper-rust/src/host`): 세션 잠금 판정 `session_blocked()`(`CGSessionCopyCurrentDictionary` 의 `CGSSessionScreenIsLocked`, 또는 콘솔이 아닌 세션). `capture`·`readElements` 는 접근성 읽기 전에 이것을 확인해 `screen_locked` 로 거절한다(메시지: 화면이 잠겨 어떤 창도 읽을 수 없음). `permissions` 응답에 `screenLocked` 필드 추가(덧붙임만, 기존 필드 불변).
2. **접근성 창 매칭 오류 세분화** (`observe.rs` `FrameMatch`): `NoWindows`(앱이 창을 하나도 안 내놓음), `NoFrames`(창은 있는데 위치·크기가 없음) → `ax_unavailable`, 프레임이 있으나 불일치 → `window_mismatch`, 겹침 → `ambiguous_window`. 예전에는 전부 `window_not_found` 였다. 프레임 허용 오차(2pt)와 '모호하면 거절'은 그대로(가림 위치가 어긋나지 않게).
3. **Node 제공자** (`egdesk-computer-observe.mjs`):
   - `screen_locked`·`ax_unavailable`·`window_mismatch` 를 모델용 닫힌 코드와 고정 안내로 변환(잠금이면 "사람에게 잠금 해제를 부탁하고 그때까지 재시도하지 말 것").
   - 앱 읽기·캡처는 **승인 카드를 띄우기 전에** 잠금을 확인한다(잠긴 화면에서 허락만 받고 실패하지 않게).
   - `list_windows` 결과에 `screenLocked: true` 와 안내를 붙임(창 목록 자체는 그대로).
   - 앱 찾기: 번들 id, 현지 이름('계산기'), 번들 id 끝 조각(`Calculator` ↔ `com.apple.calculator`, `Notes` ↔ 메모) 순서, 겹치면 `app_ambiguous`.
   - wiring: 도우미 `permissions` 요청을 제공자에 연결.

## 4. Main 이 다시 확인할 것
1. **화면 잠금을 풀고**(사람이 직접) EG-Desk 에서 같은 요청을 한다. 새 도우미 바이너리가 필요하므로 `cargo build` 를 다시 하고 브리지를 재시작한다.
2. 기대: 승인 카드 → [이번만 허용] → 요소 목록. 잠긴 상태로 다시 시도하면 카드 없이 "화면이 잠겨 있어 읽을 수 없다"는 안내가 나온다(= 이번 수정의 확인).
3. 잠금을 푼 상태에서도 계산기 읽기가 `window_not_found`/`window_mismatch`/`ax_unavailable` 이면 그것은 별도 문제(코드가 이제 구분해서 알려 준다): 그때의 코드를 알려 주면 된다.

## 5. 한계 [미확인]
- **잠금이 풀린 상태에서 계산기를 읽어 보지 못했다**(사람이 필요한 단계, 잠금을 건드리지 않음). u1 때 잠금 전의 다른 앱 창 읽기는 성공했으므로 일반 경로는 동작하지만, 계산기 자체(SwiftUI 앱)의 접근성 창이 프레임을 정상으로 내놓는지, CGWindow 와 AX 프레임이 2pt 안에서 일치하는지는 직접 측정하지 못했다. 불일치하면 `window_mismatch`(위치 어긋남 방지를 위해 일부러 엄격)로 나온다.
- `open -g` 로 뒤에서 연 앱의 접근성 창이 처음에 비어 있을 수 있는지(잠금과 무관한 경우)도 확인하지 못했다. 그 경우는 `ax_unavailable` 로 구분되어 나온다.
- 잠금 판정은 `CGSSessionScreenIsLocked` 키(비공개 이름이지만 `CGSessionCopyCurrentDictionary` 의 오래된 관례)에 의존한다. 화면 보호기만 켜지고 잠기지 않은 상태는 잠금으로 보지 않는다(이 경우의 접근성 응답은 측정하지 않음).
