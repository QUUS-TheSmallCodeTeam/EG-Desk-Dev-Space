## 1. D19 제출: 'Google 검색' 버튼이 읽기 전용 GET 증명을 통과하지 못한 정확한 이유 (실제 구글 DOM으로 확인)
방법: `curl`로 받은 google.com/?hl=ko의 폼 구조와, Aside 브라우저의 실제 구글 페이지(검색어 입력 후 자동완성 열린 상태 포함)의 `form.elements`를 읽어, 그 구조를 가짜 DOM으로 재현하고 **Firefox 자식 프로세스의 진짜 코드(`navigationFacts`)**를 돌려 `egdesk_card_read structure`가 내놓는 nav 사실을 만들었습니다(픽스처 `googleSearchFacts`). 실제 폼: `<form action="/search" method="GET" role="search">`, 안에 `<input type=file hidden>`(이름 없음, 이미지 검색), `textarea[name=q][role=combobox]`, `<button type=button role=link>`, btnK/btnI 제출 input 각 2벌(페이지와 자동완성 목록, 자동완성이 열려도 폼 구성은 같음, 둘 다 폼 안), hidden input 6개(sca_esv, hl, sxsrf, source, ei, iflsig).
증명이 실패한 이유는 **두 가지**였고, u7의 `textarea` 추가만으로는 풀리지 않았습니다.
1. **hidden input이 폼을 'sensitive'로 만듦**: 자식의 `navigationFacts`가 폼의 각 칸에 `isSensitiveControl(field)`를 쓰는데, 이 함수는 화면 읽기 마스킹용이라 `type=hidden`이면 무조건 true. 즉 hidden이 하나라도 있는 폼은 전부 `sensitive: true`, `submitUrl: null`이 되어 `readOnlyPress`가 null. (기존 시험은 이 함수를 대역으로 바꿔서 못 잡았음.)
2. **이름 없는 `<input type=file>`**: `ftype === "file"`이면 무조건 sensitive + 칸 종류 `file`(안전 목록에 없음).
- 재현: 실제 구조 사실을 만든 뒤 수정 전 코드로는 `form.sensitive: true`, `submitUrl: null`, 수정 후 `sensitive: false`, `submitUrl: https://www.google.com/search?...q=...&btnK=...`, `readOnlyPress -> get_form`(자동 누르기). 버튼의 `regionLabel`('Google 검색', 자신의 aria-label)은 분류 `none`이라 문제 아님.
- 수정(`EGDeskBrowserAgentRuntimeChild.sys.mjs`, 두 줄 성격): ① `isSensitiveControl(node, { allowHidden })`: 기본은 그대로(읽기 마스킹은 hidden을 계속 가림), 제출 증명(`navigationFacts`)만 `allowHidden: true`로 호출해 **hidden 자체는 사유가 아니게** 함(이름이 token, secret, otp 같은 hidden, data-sensitive/private 표시, password 칸은 여전히 sensitive). ② 이름 없거나 disabled인 file 입력은 제출에 안 들어가므로 칸 종류에도 sensitive에도 넣지 않음(이름 있는 file 입력은 그대로 sensitive).
- 안전 조건 유지(시험으로 고정): POST 폼은 URL도 증명도 없음, 비밀번호 칸, 이름 있는 file, 비밀 이름 hidden, data-private, otp 칸은 sensitive, 로그인 링크, 비밀번호 칸(combobox로 자칭), `<select>` 입력, 결제, 자격 칸 분류 그대로. 이 수정은 목표 루프(Codex 포함)의 읽기 전용 GET 증명에도 적용됩니다(같은 규칙 공유).

## 2. D24: 사람의 '네' 뒤에도 같은 호출이 다시 거절된 이유
재생(실제 런타임, 결정 우선 승인과 열린 항목 켬, 실제 장부, Claude 어댑터, 페이지 도구; 결정 모델은 대본)으로 흐름을 따라가 보니, **예상 가능한 경로 자체는 동작합니다**: 거절 `needs_person`(장부가 질문 보관) -> '네'(열린 항목이 승인 항목으로 읽고 `reply_runs_command`로 승인, 다음 턴에 묶임) -> 같은 호출 `via: approved`로 1회 통과. 실창에서 안 된 것은 **재생으로 재현되지 않는 두 지점**이라, 둘 다 막았습니다(실제 모델 확률은 이 창에서 볼 수 없음: 결정 호출 기록은 메모리에만 있고 확률을 남기지 않음).
1. **승인 식별자가 엔진이 정한 `expectText`에 묶여 있었음**(가장 유력): 장부 키 = 명령 설명 + `identity`이고 page 도구의 identity는 `host + sha(ref|label|expectText)`였음. 사람이 승인한 것은 "이 사이트의 이 컨트롤을 누른다"인데, 엔진이 다시 호출하며 `expectText`(누른 뒤 보일 글)를 조금이라도 다르게 쓰면 다른 호출로 보여 다시 거절. 수정: identity에서 `expectText`를 뺌(ref, label, host만). 승인 범위는 같은 컨트롤 하나로 좁게 유지(다른 ref나 다른 라벨은 승인 안 됨, 승인은 1회만, 시험으로 고정).
2. **답을 읽는 질문이 셸 명령 문구**: 장부의 답 읽기 질문은 "run exactly this command now"와 "stopped before running one shell command"인데 대상은 `press "…" on host`. '네' 같은 짧은 답에서 실제 모델이 0.8에 못 미칠 수 있음(`not_approved`로 처리, Claude의 "승인되지 않음으로 처리"와 일치). 수정: 장부 `check`가 `own: 'page'`를 받아 보관하고, `readReply`가 page 질문에는 같은 이름, 같은 문턱의 두 술어를 **page 문구**("press exactly this control now", "stopped before pressing one control on a web page")로 읽음. 셸 명령 질문은 기존 문구 그대로(시험으로 고정). 이 문구는 결정 모델용이며 사람에게 보이는 글이 아님.
3. 방어: 결정 우선 승인 경로(`decisionFirstReply`)가 page 질문을 **셸 명령으로 실행**하고 그 과정에서 승인을 임시 턴으로 가져가 버리는 구멍을 막음(page 질문은 코드가 실행하지 않고 승인을 장부에 둔 채 엔진 턴에서 같은 호출이 통과). 바운드 턴은 이 경로를 쓰지 않아 실창 원인은 아니지만 비바운드 대화에서 같은 사고가 날 수 있었음.
- 명령 승인 경로 회귀 없음: 셸 명령 질문의 문구, 키, 실행 경로는 그대로(기존 장부, 결정 우선, own-tools 시험 전부 통과).
- 한계(솔직히): 위 1, 2번 중 어느 쪽이 실창의 원인이었는지는 실제 모델 확률 없이는 확정 못 합니다. 다음 실창에서 또 실패하면 '네' 직후 `egdesk_card_press`의 응답(`needs_person` 재질문인지, `person_step`인지)과 열린 항목 문구(`state=approved` 또는 `not_approved`)를 알려 주세요.
