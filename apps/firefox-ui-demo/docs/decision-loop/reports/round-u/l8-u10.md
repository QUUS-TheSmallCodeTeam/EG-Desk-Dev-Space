# L8 u10: 사이트 질문에 '이 대화에서 허용'을 눌러도 이동하지 않음 (D25 후속)

- 브랜치 `lane/u10-site-answer` (기준 int/c14 `b805079`), 작업 사본 `$L/wt-l8-u10`, 커밋 `6377d93`, `6b316ea`. 게이트는 5절. 실제 Claude 실행 없음. 새 화면 문구 없음.
- **먼저 솔직한 상태**: 실창의 끊긴 지점을 코드와 재생만으로는 **재현하지 못했습니다**. 아래는 확인된 사실, 그 사실에서 좁힌 가설, 가설이 맞든 틀리든 안전한 보강, 그리고 다음 실창에서 원인을 확정하는 진단입니다.

## 1. 확인된 사실
1. **실제 대화 기록**(읽기 전용 사본, 도구 이름, 시각, 상태만)으로 본 세 번의 시도(run 4개, UTC 21:16~21:18):
   - 21:16:40 누르기 -> 요청 -> 21:17:35 `site-pending`(**54.5초**, 아무도 안 누름, 정상).
   - 21:18:11.5 누르기 -> 21:18:12.288 `site-pending`(**0.74초**). Main의 "8초에 클릭"은 run 시작(21:18:04.9) 기준 8초 = 21:18:12.3, 즉 **클릭 직후 곧바로 pending**으로 끝난 것과 시각이 일치합니다.
   - 21:18:50.963 누르기 -> 21:18:50.996 `site-pending`(**0.03초**, 질문이 보일 틈 없음). 허용 집합에 이미 들어 있어 카드가 즉시 답한 경우와 일치합니다.
2. 헬퍼는 카드가 `site-allowed`를 답했는데도 **그 run의 탐색 정책이 그 사이트를 아직 담고 있지 않으면** `site-pending`으로 돌려줍니다(`requestSite`의 `reflected` 검사). 위 시각 패턴(클릭 직후 pending, 이후 즉시 pending)은 "카드는 허용, 헬퍼 사본은 미반영"과 정확히 맞습니다. 반면 "카드가 pending으로 답함"이라면 두 번째, 세 번째가 즉시 끝날 이유가 없습니다.
3. **재생으로 확인한 정상 경로**(진짜 `BrowserToolTransport`(SSE 프레임, 와이어 요청 ID, 마감, 수신 검사) + 카드의 `allow-site` 처리와 질문 패널 의미를 그대로 옮긴 클라이언트 + 진짜 헬퍼, 제공자, 런타임, Claude 어댑터): 즉시 허용, 0.3초 뒤 허용 모두 `site-allowed` -> 같은 run에서 이동 **1회**, 같은 사이트 재요청은 즉시 허용. 즉 헬퍼, 전송 계층, 페이지 도구는 정상이고, 실창과 재생의 차이는 **화면(카드) 쪽 실제 상태**(허용 집합이 돌려주는 정책 내용 등)에 있을 가능성이 큽니다. 그 화면 코드는 여기서 실행할 수 없습니다.
4. 참고(원인 아님): Claude가 `egdesk_browser_request_site`를 직접 부르면 `site-pending`은 성공이 아닌 결과라 **일반 오류 문구로 가려져** Claude에게 전달됩니다(기존 동작). 그래서 Claude는 "허용 답을 받지 못했어요" 정도로만 말합니다.

## 2. 한 일
1. **보강(가설 2번이 맞을 때 고침, 틀려도 안전)**: 카드가 **정확히 그 사이트**에 대해 `site-allowed`를 답했는데 그 run의 정책 사본에 없으면, 헬퍼가 그 사이트 패턴을 **그 run의 사본에만** 보관하고(`holdVouchedSites`, 이후 카드가 보내는 정책으로 덮여도 유지, block 규칙은 여전히 우선) `site-allowed`로 처리. 결과에 `policySync: 'card-vouched'`가 붙어 이 경로가 쓰였음을 알 수 있습니다. 근거: 카드가 모든 이동, 히스토리, 새 카드를 자기 허용 집합으로 **다시 검사**하므로(코드 주석 D-B1/D-B2) 헬퍼 사본은 요청을 보낼지만 정합니다. 다른 사이트나 거절, 무응답은 이전 그대로.
2. **진단(다음 실창에서 원인 확정)**: 사이트 질문이 허용으로 끝나지 않으면 닫힌 말과 숫자만으로 이유를 남김: `pendingBy`(`unanswered` 카드 질문이 시간 초과, `helper-timeout`, `unreflected` 허용됐으나 정책 미반영), `waitedMs`, 카드가 본 남은 시간과 답까지 걸린 시간(`ui.askedLeftMs`, `ui.answeredAfterMs`). 페이지 도구 결과(`not_done`)에도 `pendingBy`, `waitedMs`가 실립니다. 사람 말과 주소는 넣지 않았습니다.
3. **상태가 다음 요청을 막는지 확인**: 응답된 질문과 만료된 질문의 상태는 다음 요청을 막지 않습니다(카드의 패널 변수는 답이나 시간 초과 때 비워지고, 헬퍼의 `refusedSites`는 run 단위, 허용 집합은 대화 단위로 "이미 허용"이면 즉시 허용).
4. 재생 시험 3건 추가(`helper/egdesk-claude-browser-site.test.mjs`, 총 8건), 픽스처에 진짜 전송 계층 모드와 정책 미반영 모드를 추가.

## 3. 실창에서 확인할 것(결정적)
같은 흐름("Google 정보 눌러줘" -> 질문 -> 허용 클릭)을 한 번 더:
- 이동하면 보강이 맞았던 것입니다(결과에 `policySync: card-vouched`가 있으면 **가설 2번 확정**: 카드가 돌려준 정책에 허용한 사이트가 빠져 있었음. 그 정책을 만드는 화면 쪽 `BrowserGrant.browserNavigationPolicy`와 `browserToolThreadSiteSet`을 더 파야 함).
- 여전히 이동하지 않으면 활동 기록의 `request_site` 행 또는 `egdesk_card_press` 결과에서 `pendingBy`, `waitedMs`, `ui`를 알려 주세요: `helper-timeout`이면 헬퍼가 먼저 포기, `unanswered`이고 `askedLeftMs`가 작으면(수초 이하) 카드가 짧은 마감을 받은 것(마감 전달 경로 문제), `answeredAfterMs`가 클릭 시각과 맞는데도 `unanswered`이면 클릭이 허용 버튼의 처리기를 거치지 않은 것(합성 클릭 입력 경로 문제).
- Main이 쓰는 합성 click이 문제일 가능성: 허용 버튼은 `onclick`에서 `finish('allowed')`만 부르고 `stopPropagation`을 쓰며, 기존 카드 버튼과 같은 방식이라 합성 click이 안 먹을 이유는 코드에서 못 찾았습니다.

## 4. 판단 한 줄
- 질문 상태가 다음 요청을 막지 않음, 허용 뒤 같은 run에서 한 번 이동, 다음 요청은 이미 허용된 사이트라 즉시 이동(재생으로 확인). 실창 끊김의 최종 원인은 위 진단이 알려 줍니다.
