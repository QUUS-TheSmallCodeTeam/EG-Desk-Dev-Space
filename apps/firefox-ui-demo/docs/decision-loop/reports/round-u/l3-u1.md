# L3 라운드 u1 — '위' 기본 경로 묶음

브랜치 `lane/u1-upper-bundle` (int/c14 `cf086b8` 위). 증거 `evidence/l3-u1/`. 새 기능은 기본 꺼짐, 새 화면 문구 없음. Codex 실행, Claude 스크립트 실행, 결정 모델 실호출 없음(가짜 app-server, 가짜 Claude transport, 가짜 fetch).

## 1. 묶음 설정 `EGDESK_UPPER=on` (이름은 임시: 제안, 승인 대기)
- `helper/egdesk-upper-bundle.mjs`: `applyUpperBundle(process.env)`를 브리지가 **어떤 플래그도 읽기 전에** 한 번 부른다(`codex-bridge-server.mjs`, `requireEGDeskNodeRuntime()` 바로 위). 설정되지 않은 플래그만 채운다. **개별 플래그를 직접 정하면 그 값이 이긴다**('off', 'none', 'advisory' 포함. 빈 문자열은 지정이 아님). 로그에 `EGDESK_UPPER=on: N flags set, M kept` 한 줄(이름 수만).
- 묶음은 **개발자 플래그만** 채운다. **결정 모델을 켜지 않는다**: 모드(끔/기록만/사용)와 저장된 키는 사용자 설정이다.
- 실제 엔진 체크도 같은 함수를 쓴다: 스크립트의 대화 `flags: {"EGDESK_UPPER": "on"}`가 묶음을 채운다(스크립트가 정한 플래그는 유지). 등록: `--decisions` 필요.

**묶음에 넣지 않은 것(제안, 이유 있음):** `EGDESK_CONVERSATION_FLOW`, `EGDESK_INRUN_MESSAGES`(사람에게 모델이 쓴 중간 메시지를 게시하는 별도 소유자 결정), `TURN_MEMORY_ONE_PACKET/PRUNE_HELD/KEEP_LATE/ENGINE_CONTEXT`(엔진 입력 절감, 소유자 결정 C2 열림), `CONTEXT_RELEVANCE`, `BROWSER_OPEN_ITEMS`, `BROWSER_ENTRY`(L8), `WORKING_MEMORY`(활동 줄 문구 승인 대기), `COMMAND_JUDGE`, `CHAT_CHOICE`([보기 추천], U4). 목록과 이유는 `NOT_IN_BUNDLE`에 코드로 있다. 이 묶음에 `OWN_TOOLS`와 `DRAFT_CHECK=on`이 들어 있어 **게시되는 답이 점검으로 바뀔 수 있다**는 점은 소유자가 알아야 한다(기존 c30/c31 hedge 이후의 측정을 근거로 지시에 따라 포함).

**L8 페이지 도구를 묶음에 넣은 판단**: 넣었다(`lands: lane/u1-browser-tools`). 이유: ① '위'의 정의에 브라우저 조작과 카드가 들어 있고, 묶음을 켜도 대화 엔진이 브라우저를 도구로 쓸 수 없으면 기본 경로가 반쪽이다. ② 도구는 사람이 허용한 카드에 묶인 실행에만 열리고, 위험한 단계(결제와 권한은 사람 전용, 삭제와 제출은 승인)는 코드가 정한다(엔진이 아니다). ③ 결정 모델을 쓰지 않으므로 U9와 충돌하지 않는다. ④ L8이 밝힌 준비 조합이 `PAGE_TOOLS` + `TERMINAL_OPEN_URL` + `OWN_TOOLS`라서 선행 둘도 묶음에 있다(`OWN_TOOLS`는 이미 있음). **주의**: `TERMINAL_OPEN_URL`은 터미널 카드의 주소 열기 동작도 바꾸는 독립 기능이다. 싫으면 `EGDESK_TERMINAL_OPEN_URL=off`로 덮어쓸 수 있지만 그러면 로그인 불투명 처리가 빠진다고 L8이 적었다. **소유자 결정이 남은 L8 항목**(도구 이름 확정, 삭제와 제출을 승인으로 둘지 사람 전용으로 올릴지, 카드 허용 없이 열기)은 L8 보고서의 것이고, 묶음은 현재 기본 정책 그대로 켠다. L8 브랜치는 이 브랜치에 합치지 않았다(Main이 합친다): 코드가 아직 없으므로 이 값은 병합 전까지 아무 효과가 없다(묶음 테스트가 `lands`로 표시하고 병합 뒤에는 일반 규칙이 코드가 읽는지 확인한다).

**검색창 라우팅(L1 계약, Main 전달)**: (a) `hudRoutingEnabled()`는 요청마다 `process.env.EGDESK_HUD_ROUTING`을 읽는 함수이고 묶음이 브리지 시작에 그 값을 채우므로 따로 고칠 필요 없이 묶음 값을 본다(테스트로 고정). (b) 브리지가 `chatCapabilities`(`chat:` 목록, `terminal-open-url`과 같은 자리)에 `hud-routing-advisory` 또는 `hud-routing-on`을 넣는다(`hudRoutingCapability(process.env)`; 사람이 `off`로 정했으면 알리지 않음). 낱말은 L1의 `HUD_ROUTING_CAPABILITIES`와 같다(테스트로 고정; L1 브랜치는 합치지 않았다). 값은 `advisory`로 했다: 결정 모델 모드가 끔이면 `createHudRouting`이 묻지 않고, 모드가 켜져 있어도 입력 글은 `hud_text`로 거절되어 요청이 0건이다(D1이 정해지기 전). 창의 pref `egdesk.hudRouting`을 사람이 정했으면 그것이 이긴다는 L1의 규칙은 창 쪽 일이다.

## 2. 턴 순서 (U13): 기억, 행동 → 엔진 한 번 → 게시 전 점검
- 순서는 이미 `send()`의 공유 경로에 있다: 턴 컨텍스트와 기록 상태 → 요청한 명령(decision-first) → 답이 해소하는 열린 항목 → 엔진 시작 → 답 후 점검. 이번에 **순서를 상태로 남겼다**: `turnStagesFor(requestId)` → `[{stage, at}]` (`memory`, `action`, `engine`, `check`, 단계마다 첫 표식만, 문구 없음, 최대 64턴). 코드는 단 4줄(+점검 두 곳)이다.
- 실제 엔진 체크: `expect.stages: {order|includes}` 훅(`egdesk-real-engine-stages-hook.mjs`), 스크립트 `real-engine-upper-order-v1`(`--engine claude`로 같은 스크립트가 Claude 경로를 본다, 자동 실행하지 않음).
- **Claude와 Codex가 다른 점 (L5와 겹치는 파일은 건드리지 않음):**
  1. **행동 층(decision-first)은 Codex 전용**이다(`ownTools = engine.id === 'codex' && ownToolsOn()`). Claude에서는 `action` 표식은 찍히지만 명령을 먼저 처리하는 일은 없다. Claude의 도구 연결(MCP)과 승인은 L5 몫이다.
  2. **게시 전 점검은 Agent 방(직접 답장)에서만 붙잡는다**: 브리지의 `draftCheck` 설정에는 `eligible`이 없어서 일반 채팅 스레드는 대상이 아니다(`draftHoldEligible`: `channelKind === 'direct'`). **일반 Claude 대화 한 턴에는 점검이 없다**(테스트로 문서화: `FINDING`). 점검을 일반 스레드에도 쓰려면 `draftCheck.eligible`을 주는 소유자 결정이 필요하다(제안, 하지 않음).
  3. 기록만(advisory) 점검은 `phase === 'final_answer'`인 항목에서만 도는데, Claude 번역기의 답은 `phase: null`이라 **Claude에서는 advisory 점검이 돌지 않는다**. 묶음의 값은 `on`(붙잡기 경로, phase와 무관)이라 영향 없음.
  4. 기억 층, 열린 항목, 제안 등록, 점검 후의 모든 것은 엔진과 무관한 공유 경로다. Claude 가짜 transport로 `memory → action → engine`(+ 점검 대상이면 `check`) 순서를 테스트로 확인했다.

## 3. 결정 모델 키 경로와 U9
- **제품 경로 확인**: 결정 모델 클라이언트는 `openDecisionCredentialStore({ dataDir/settings })`의 키(`egdesk-decision-credential.json`)와 `bridgeSettings.decisionContext.mode`를 쓴다. 제품 모듈 중 환경변수에서 키를 읽는 것은 없다(테스트: 제품 `.mjs`에서 `OPENAI_API_KEY`, `EGDESK_REAL_CHECK_DECISION_KEY`를 읽는 파일 0개). 환경변수 키를 읽는 것은 **측정 도구뿐**: `egdesk-decision-real-runner.mjs`(`--send`), `egdesk-all-on-live-measure.mjs`, 실제 엔진 체크(`EGDESK_REAL_CHECK_DECISION_KEY`). 시험용 환경변수 전용 경로에 묶인 **기능은 없다**. 묶음의 플래그 14개 중 L8 페이지 도구(병합 대기) 하나를 뺀 12개 모두 브리지가 `process.env`에서 직접 읽거나 `process.env`를 넘겨받은 모듈이 읽는다(테스트).
- **발견 (고침)**: 결정 모델 모드가 **끔**인데 턴 기억 설정이 켜져 있으면 `turnMemoryMode()`가 `advisory`를 돌려주고 `beginTurnMemory`는 키 유무만 봐서 **결정 모델을 부를 수 있었다**. 두 곳에 `mode === 'off'`를 명시했다(U9).
- **한 곳 보장**: 브리지가 `decisionContext.client`에 `modeGatedClient`를 준다. 모드가 끔이거나 읽을 수 없거나 키가 없으면 `decide`가 **보내지 않고** 거절한다(`decision_mode_off`, `decision_not_configured`). 기록만과 사용은 통과. 설정 화면의 키 확인(`verifyKey`)은 게이트를 지나지 않아 모드 끔에서도 동작한다.
- 게이트 밖의 소비자와 각자의 모드 확인(이번에 바꾸지 않음): 작업 배치와 HUD 라우팅(`mode` 인자), 웜업(`decisionsMode`), 보드 질문(모드 끔이면 null), 브라우저 도구(`mode: 'on'` 필요). 이들은 `decisionContext.client`가 아니라 원래 클라이언트를 쓴다.

## 4. 문구
새 문구 없음. 기존 승인된 행만 쓴다("컨텍스트 세팅 · 자료 N개"). **제안(승인 대기)**: ① 묶음 설정 이름 `EGDESK_UPPER`. ② 점검이 화면에 보이게 하려면 활동 기록 한 줄이 필요하다(지금은 점검이 통과하면 화면에 아무것도 없음). 예: `답 점검 · 통과` / `답 점검 · 문장 N개 보류`. 소유자가 정하기 전에는 넣지 않았다.

## 5. 화면 검증 절차 (EG-Desk를 직접 띄워 Claude 대화 한 턴)
사전 조건: 설정 > 계정에 결정 모델 키 저장, 모드 '사용'(기억 기능도 쓰려면 기억 켬). EG-Desk를 띄우는 셸에서 `export EGDESK_UPPER=on` 후 실행. 브리지 로그에서 `[egdesk-codex-bridge] EGDESK_UPPER=on: 14 flags set, 0 kept` 한 줄 확인(이미 직접 정한 플래그가 있으면 kept 수가 늘어남).
1. **U9 음성 대조 먼저**: 모드를 '끔'으로 하고 Claude 대화에서 한 턴(예: 작업 폴더의 파일 내용을 묻는 말). 기대: 답은 정상 도착, 활동 기록에 "컨텍스트 세팅" 줄이 **없음**, 설정 화면의 "이번 달 집계된 입력 N 토큰"이 **그대로**(결정 모델에 아무것도 안 보냄).
2. 모드를 '사용'으로 하고 같은 대화에서 한 턴: `notes/todo.md 에 남은 항목이 뭐야?` 처럼 파일을 읽어야 하는 말. 기대 순서(활동 기록, 위에서 아래): ① `컨텍스트 세팅 · 자료 N개` (기억, 컨텍스트 층) → ② Claude의 도구 줄(`egdesk_read_file` 등, 엔진) → ③ 답 말풍선. 설정 화면의 토큰 집계가 늘어남.
3. **점검(맨 끝 단계)**: 일반 Claude 스레드에서는 **점검이 없다**(위 §2-2). Agent 방에서 같은 한 턴을 하면 점검이 돌지만 **통과하면 화면에 흔적이 없다**. 화면으로 순서를 끝까지 확인할 수 없다는 뜻이다. 대체 확인: 실제 엔진 체크로 `real-engine-upper-order-v1`를 `--decisions`(Claude는 `--engine claude`)로 돌리면 턴 기록 `stages`에 `["memory","action","engine"]`이 남고 `expect.stages`가 판정된다. 화면에서 보려면 §4의 점검 줄(제안)이 필요하다.
4. (L8이 병합된 뒤) 브라우저 카드를 연 새 대화에서 카드를 허용하고 "이 페이지에서 ○○ 검색해 줘" 한 턴: 활동 기록에 `egdesk_card_read`, `egdesk_card_type`, `egdesk_card_press`(이름은 임시) 줄이 엔진 줄로 나타나고, 결제나 로그인은 사람에게 넘어가는지 본다(L8 보고서의 화면 절차를 따름).
5. 기대와 다르면 적을 것: 줄의 순서, "컨텍스트 세팅" 줄이 엔진 도구 줄보다 아래에 나오는지, 토큰 집계가 모드 끔에서도 늘었는지.

## 6. 테스트와 변이
