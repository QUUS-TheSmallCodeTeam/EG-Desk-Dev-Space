## 0.6 (4) 맥락이 잘렸을 때: "판단 보류"는 옵트인으로 구현해 두고 기본은 그대로 (제안과 근거)

- 근거 수치: 맥락 호출 시간이 예산 근처에 몰려 있다(이 기록에서 3개가 672, 679, 813 ms, 예산 800 ms; 1개 잘림, 표본이 작아 빈도는 단정하지 않음). 맥락 예산 자체는 L2의 몫이다.

## 0.7 04:57 사례: 미리 넣은 파일의 **내용**이 점검과 고쳐 쓰기의 근거에 없었다 (고침: 플래그 뒤)
- 확인(코드와 재생): 본 엔진에는 선택된 파일의 본문이 간다(`itemText`의 `blockText`, 항목당 6,000자까지). 그러나 점검의 증거는 `draftEvidenceOf`가 **제목과 요약만** 만든다(주석: "never the loaded body"). 작업 폴더 파일의 요약은 "README.md — 93 bytes, 2026-11-25"뿐이다(재생에서 점검 요청에 실린 증거 그대로). 그래서 내용에 대한 맞는 요약은 근거 없음으로 잘리고, 고쳐 쓰기는 같은 증거로 만들어져 "내용은 제공된 자료에 없어 요약할 수 없다"를 낸다. Main의 의심이 맞다.
- 고침(`EGDESK_DRAFT_CHECK_FILES=on`, 기본 꺼짐; 새 문구 없음): 미리 넣은 **작업 폴더 파일**(id가 `workspace:`)의 본문이 엔진에 전달됐다면(`textSource` full) 그 본문을 증거 항목(`kind: 'file'`, 엔진이 받은 범위와 같은 텍스트; 점검의 항목당 1,200자 한도는 그대로)에 넣는다. 다른 선택 항목(문서, 기억)은 그대로 제목과 요약뿐이다. 고쳐 쓰기는 같은 증거를 쓴다(고쳐 쓰는 모델은 엔진 자신이다).
- **자료 등급 결정이 필요하다**: 결정 모델이 작업 폴더 파일의 텍스트를 본다. 게이트에 새 증거 종류 `file`(등급 `files`)을 만들었고, `files`는 **바인딩된 폴더가 있는 실행이면서 Agent 천장이 터미널과 파일을 둘 다 닫지 않았고 플래그가 켜졌을 때만** 열린다(시험으로 고정). 근거는 U9: 엔진이 이미 받은 텍스트다. `workspace_names` 설명의 "Never file text"는 **선택 단계**(결정 모델이 파일을 고르는 질문)에 대한 약속으로 그대로 지켜진다. 이 플래그를 `EGDESK_UPPER` 묶음에 넣었다(`requires` DRAFT_CHECK와 PREFETCH). 묶음에서 빼려면 `EGDESK_DRAFT_CHECK_FILES=off`. 소유자가 데이터 등급을 정할 사항이다.
- 재생(가짜 Claude, 가짜 결정 모델이 증거에 있는 낱말로 지지 여부를 판단): 플래그 켬 → 맞는 README 요약이 **쓴 대로 게시**, 끔 → 같은 요약이 크기와 날짜만 보고 근거 없음으로 **잘림**(D18 재현).
- 한계: 이전 턴에 이미 전달되어 "다시 묻지 않는" 파일(held)은 이번 턴 맥락 단계가 다시 붙이지 않으므로 이번 점검의 증거에도 본문이 없다. 이 경우는 이전 턴의 도구 사실(0.4)이 일부만 메운다.

## 2. 점검 단계의 닫힌 이름 (L5와 나눔)
- 호출 기록 파일(`egdesk-decision-call-log.mjs`)은 **L5가 소유**하고, 이번에 L5가 (a) `proposals`, (b) 모델 호출 없이 끝난 단계를 위한 `recordStage`와 kinds `check_local`, `recheck`, `revise`, `observe_pick`, `observe_app`, (c) 런타임의 `noteDecisionStage(run|requestId, kind, {startAt,endAt,outcome})`를 `lane/u5-observe-first`에 넣었다. 내 브랜치는 **그 파일을 건드리지 않고** 호출만 넣었다(`this.noteDecisionStage?.(…)`, 로그가 꺼졌거나 L5가 병합 전이면 no-op).
- 내가 넣은 호출: **`check_local`** (첫 점검이 모델 호출 없이 끝났을 때), **`revise`** (비공개 고쳐 쓰기 턴이 실제로 시작됐을 때: 결과 있음 `ok`, 빈 답 `bad_response`, 시간 초과 `timeout`, 그 밖의 실패 `error`), **`recheck`** (고쳐 쓴 문장의 재점검). 모델을 부른 첫 점검은 클라이언트의 `check` 행이 이미 있어 중복 행을 만들지 않는다. 단계 행은 토큰이 null이다.
- 이로써 04:30 같은 턴의 호출 기록은 `nunchi, context, pick, check_local, revise, recheck, proposals`로 읽힌다(L5 병합 뒤).

| 점검, 지지되는 답 (04:27) | +0.25 s (점검 호출 245 ms, 876토큰) | 1 | 1 | **쓴 대로 게시** (`as_written`) |

| 점검, PRIVATE 켬, 고침 전 (04:30) | **+4.8 s** (게시 12.16 s) | **2** (둘째는 답이 버려짐) | 0 (+ 등록부 1) | **남은 문장만**(원문에서 주장 문장을 뺀 38자) (`certain_part`) |

읽는 법:
- 빈 화면(전체 보류)은 싸다(+0.3 s, 턴 1개)지만 사람이 답을 못 받는다. 고쳐 쓰기는 사람이 문장 있는 답을 받을 가능성을 올리는 대신 **약 +5 s와 Claude 턴 1개**가 든다.
- **지금까지의 PRIVATE 켬은 고쳐 쓰기가 아니라 "원문에서 문장 빼기 + 5초 낭비"였다.** P1을 판단할 때 04:30의 12초는 고침 후에도 거의 같을 것이고, 달라지는 것은 결과 문장이다.
- 04:28 같은 자료가 있는 턴은 점검이 `would_withhold`일 수 있다(남는 문장이 없을 때). 04:30처럼 남는 문장(안내 한 줄)이 있으면 PRIVATE 없이도 `certain_part`로 그 문장이 게시된다.
