# L3 u8 — D23b: 하네스 Claude 대화의 도구 전후 해설이 말풍선으로 올라오던 문제 (+ D26 조사)

브랜치 `lane/u8-claude-commentary-hold` (int/c14 `9393078` 위). 실제 Codex와 Claude 실행 없음(L5의 재생 세계).

## 원인
u4 설계는 Claude의 해설 글(도구 호출 앞의 글)을 **도구가 시작될 때 말풍선으로 게시**했다(점검 없이). 하네스 지침(L5)은 모델이 내부 표시를 말하지 않게 부탁할 뿐이라, 모델이 그래도 말하면(실창 05:54, 05:37: 영어로 내부 상태를 말하는 줄) 그 글이 본 답 앞에 따로 올라왔다. 소유자 원칙 U8(스트리밍 없음, 완성 메시지만, 중간 말 걸러짐)과 어긋난다. 게다가 점검이 꺼져 있으면 보류 자체가 없어 글이 흐르는 대로 올라간다.

## 변경 (`helper/codex-chat-runtime.mjs`만, 새 문구 없음)
- `claudeHarnessHold`(새): Claude이고, 하네스(`EGDESK_CLAUDE_HARNESS`)가 켜져 있고, 비상태 보존형(stateless) 아님, Board 아님, 주제 답변 가드 없음, 채널이 없거나 direct일 때 참. `draftHoldEligible`이 이것이 참이면 참을 돌려준다: **점검이 꺼져 있어도** 하네스 Claude의 글은 어느 것이 답인지 알려질 때까지 보류된다. 점검은 따로 `checkEnabled`(모드 on, 결정 모델 설정됨)일 때만 돈다(점검이 꺼지거나 결정 모드가 끔이면 요청 0개, 답은 쓴 대로 게시).
- `releaseHeldNarration`(도구 시작 때 보류분 방출): 하네스 아래에서는 `phase: 'commentary'`로 적용한다. 기존 작업 메모 경로(`chatWorkNoteActivity`)를 타므로 **말풍선이 아니라 기존 활동 행**이 된다. 하네스 밖은 그대로(말풍선).
- `settleDraftAnswer`: 하네스 아래에서 글이 여러 개(도구 없이 글 뒤에 글)면 마지막(답)만 점검과 게시 대상이고 앞의 글은 작업 메모로 낮춘다(그 id를 `guard.finalIds`에서도 지워야 말풍선으로 새지 않는다).
- Codex 경로와 하네스 꺼짐은 그대로(모든 새 분기가 Claude와 하네스 켜짐으로 막혀 있음). 도구 없는 턴은 글 하나가 답이므로 이전과 같다.

## 실창 확인 방법
`EGDESK_CLAUDE_HARNESS=on`: 도구를 쓰기 전에 해설을 말하는 요청(예: 검색창에 값 넣고 검색 버튼 누르기)을 보낸다. 기대: 작업 중 표시 동안 말풍선이 없고, 해설은 활동 행으로만 남고, 끝에 답 1개만 게시(점검이 켜져 있으면 점검 후). 점검이 꺼져 있어도 같다.

## D26 (브라우저 조작 Claude 대화에 턴 판단이 안 돈다): 조사 결과, 수정 안 하고 보고만
- 원인은 버그가 아니라 **bounded 정책의 설계**다. `BROWSER_BOUNDED`는 QA 읽기 전용 정책과 같은 분기를 쓰며(`bounded = qa || policy === BROWSER_BOUNDED || ...`, codex-chat-runtime 2649), 그 분기는 일부러 이렇게 막혀 있다: `memoryTurn`(2700), `prepareDecisionContext`(`decision = bounded ? null`, 2706), `nunchiText`(2971), 확장 맥락 `extraContext = bounded ? {}`(2722), 주제 방(shares), 미리 넣기(prefetchFolder null), `noteDraftCheckTurn` 입력, `draftHold = !bounded && ...`(2985). 그래서 Claude 5의 05:55, 05:56 턴에는 결정 모델 호출이 0이다('네' 턴의 open_items와 approval_reply만 도는 것은 bounded 밖의 별도 경로).
- 이미 있는 것: bounded + 점검 켜짐이면 `browserTaskHoldEligible`이 **보류만** 한다(점검은 안 돈다, 주석에 "the draft check stays ineligible for a bounded turn"). 이번 변경으로 이 보류에서 방출되는 해설도 하네스가 켜져 있으면 말풍선이 아니라 작업 메모가 된다(Claude 5의 05:54 말풍선이 이 경로에서 나온 것으로 보임). 즉 D23b의 증상은 bounded 경로에서도 막힌다.
- 맥락, 눈치, 점검까지 bounded 런에 넣는 것이 위험한 이유: 이 분기는 "검증된 정책 영수증(qaReceipt) 아래에서는 엔진에 EG-Desk가 만든 확장 맥락을 넣지 않는다"는 안전 경계를 겸한다. claude-browser 능력만 가르면 (a) 같은 경계를 쓰는 QA 경로와 갈라지는 분기를 만들고, (b) 점검의 증거에 브라우저 도구 사실(페이지 읽기, 클릭 결과)이 없어 유효한 답을 근거 없음으로 자를 위험이 있다(D21과 같은 모양), (c) 결정 모델에 페이지 내용이 간다(소유자 자료 결정). 소유자 결정과 설계(브라우저 사실을 점검 증거로, 눈치의 입력, 맥락 제공 범위)가 먼저 필요하다. 다음 단계 제안: 브라우저 도구 결과를 `answerFactsEvidence`에 넣고, bounded에서 점검만(맥락 없음) 켜는 옵트인(예: `EGDESK_DRAFT_CHECK_BROWSER`)을 L3 별도 배정으로.
