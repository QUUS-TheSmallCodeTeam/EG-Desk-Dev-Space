## 1. 원인: 판정이 아예 시작되지 않았다 (D3의 진짜 뿌리)
u2에서 "결정 모델이 이웃 종류 사이에서 갈려 후보가 안 생긴다"를 고쳤지만 03:30 실창에서도 후보가 없었습니다. 실제 경로를 코드로 따라가 보니 **결정 모델 요청이 한 건도 나가지 않았습니다**:

| 단계 (Claude 하네스 스레드, EGDESK_UPPER=on EGDESK_NUNCHI=on, 모드 '사용', 키 저장) | 결과 |
|---|---|
| 플래그 해석: `createNunchiConfig`가 호출 때마다 `process.env.EGDESK_NUNCHI === 'on'`을 읽음 (번들 `EGDESK_UPPER`는 이 플래그를 건드리지 않음, 명시한 값이 유지됨) | 통과 |
| `nunchiOn`: 결정 모델 모드 `'on'`, `configured()`(키 저장), 클라이언트 존재. 클라이언트는 `modeGatedClient`(모드가 '사용'이면 통과) | 통과 |
| `bounded` (QA, 브라우저 제한 정책만 true; 하네스 Claude 스레드는 `ownTools`일 뿐 bounded 아님) | 통과 (bounded 아님) |
| `context.clientThreadId`, `body.message` | 통과 |
| **적격성: `context.channelKind === 'direct'`** | **막힘** |

`channelKind`는 요청에 `replyDestination: 'direct'`와 Agent 프로필이 있을 때만 `'direct'`입니다 (`codex-chat-runtime.mjs` 1907~1919줄). **Agent DM이 아닌 일반 방(시험 프로젝트 방의 Claude 대화)은 `channelKind`가 null**입니다. u1에서 메모리 루프의 적격성 규칙(`direct`만)을 그대로 베꼈고, 단위 시험은 모두 Agent DM으로 보냈기 때문에 잡히지 않았습니다. u2의 합친 읽기는 이 앞단이 열려야만 의미가 있었습니다.
- **재현 시험 (수정 전)**: 일반 방, `engineId: 'claude'`, 채팅 저장소와 지침 기록 포함, 결정 모델 `on`으로 "너무 길어. 앞으로는 짧게 말해"를 보내면 결정 요청 0건, 엔진 입력에 `egdesk_nunchi` 없음, 후보 0.
- **수정**: 적격성은 "그 사람의 대화에서 그 사람의 반응"이면 어디서나: Board가 아니고(`context.board`, `body.boardId`, `channelKind === 'board'`), stateless가 아니면 됩니다 (`nunchiEligible`). Agent DM, 일반 방 둘 다.
- **전체 규칙은 아니다**: 메모리 루프, 쓰기 우선 등 다른 기능은 같은 `direct` 규칙을 쓰므로 일반 방에서는 켜져 있어도 돌지 않습니다. 이것은 각 기능의 소유자가 정할 일이라 건드리지 않았고, 이번 원인을 보고합니다 (제안: 메모리 층이 '위'의 모든 대화에 적용되어야 하는지 소유자 확인).

## 2. '앞으로는 짧게'가 후보 조건에 걸리는가
걸립니다. 새 검증(plan nunchi-merge-v1, 실제 호출, 아래 §4)에서 **정확히 이 문장**(직전 어시스턴트 메시지가 있을 때)이 변경 요구 합 1.00, 대상 length, 방향 less, 세기 clear .99로 읽혔고 → `length / less`, 장기 후보 대상(언어, 길이, 형식, 반복 확인 질문, 범위)에 해당합니다. 재생 시험(§5)은 그 실제 답으로 후보 1건이 생기는 것을 확인합니다. **Claude 경로는 직전 메시지를 보내지 않으므로**(egress 게이트가 Codex 살아 있는 스레드만 허용) 같은 문장이 메시지 없이도 읽히는지는 새 plan(§4-2)이 실호출로 확인합니다.

## 3. 영수증을 볼 수 있는 경로 (검증용, 플래그 뒤)
- `GET /v1/user-guidance/receipts?recent=5` (1~20, 기본 5; 루프백 전용, GET만, `EGDESK_NUNCHI`가 꺼져 있으면 404). 최근 턴의 nunchi가 한 일을 **닫힌 단어, 숫자, id로만** 돌려줍니다 (사람의 문장 없음, 대화 id는 해시 8자리, 시험으로 확인).
- 항목: `at`, `conversation`(해시 8자), `engine`, `position`(first/mid), `started`, `reason`, `status`, `inTime`, `late`, `withPrevious`, `ms`, `reading`(kind, change, changeMass, forceful, forceMass, about, strength, direction, language), `directive`(guidance, value), `candidate`(id, status, seen), `lineSent`.
- **시작하지 않은 턴도 기록**하고 이유를 닫힌 단어로 남깁니다: `bounded`, `not_eligible`, `no_message`, `no_thread` (모드가 '끔'이거나 키가 없거나 플래그가 꺼져 있으면 기록하지 않음: 그때는 기능이 꺼진 것). 이번 원인 같은 문제가 다음에는 `not_eligible`로 바로 보입니다.
- 구현: 런타임 안 최근 20턴 링 버퍼(메모리만; 새 파일 없음), `nunchiRecent(n)` 메서드, 지침 기록 경로 핸들러의 `receipts` 인자, 브리지는 한 줄(`receipts: n => chat.nunchiRecent(n)`). 화면 문구 없음.

## 6. 사용량 증가에 대하여
Main이 본 "이달 입력 313,308 + 응답 없는 요청 1건"은 **nunchi가 낸 것이 아닙니다**: 이번 추적에서 일반 방 Claude 대화에서는 nunchi가 결정 요청을 한 건도 보내지 않았습니다(원인 §1). 다른 기능(턴 컨텍스트 선택, 기억 루프 등)의 호출로 보입니다. 이번 수정 뒤에는 **사용자 메시지마다 1요청(약 1.2k 입력 토큰, 출력 0)**이 추가되므로 대화가 길어지면 비용이 늘어납니다 (제안, 구현 안 함: 아주 긴 메시지 건너뛰기, `change`가 계속 false인 대화는 간격을 두기).

5. 그 턴의 Claude 입력에 줄이 들어갔는지: `grep -l "EG-Desk context: egdesk_nunchi" <Claude 설정 폴더>/projects/*/*.jsonl`.
