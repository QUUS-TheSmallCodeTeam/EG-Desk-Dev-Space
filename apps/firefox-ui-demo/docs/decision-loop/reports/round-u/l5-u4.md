# L5 u4: 결정 모델 호출 기록 + 맥락 호출 캐시 분석

- 브랜치 `lane/u4-decision-call-log` 최종 `906b7e8`(기준 int/c14 `3b8e191`, 병합 충돌 없음). 게이트 `l5u4`: **`files=512 rc=0`, `# tests 8115 / # pass 8076 / # fail 0`**. 실제 Codex·Claude·결정 모델 호출 0회(가짜 클라이언트). 새 화면 문구 0. 임시 폴더는 시험이 끝날 때 지움(u3의 채팅 저장소 복사본도 삭제 확인, 증거 폴더 합계 72KB).
- 새 개발자 플래그 `EGDESK_DECISION_CALL_LOG=on`(기본 꺼짐). **`EGDESK_UPPER` 묶음에는 넣지 않았음(L3 영역)**: 제안 = 승인 후 `egdesk-upper-bundle.mjs`의 묶음 플래그에 이 한 줄을 추가(내부 기록이라 사람에게 보이는 변화 없음).

## 1. 기록이 하는 일 (내부 기록, 화면 문구 없음)
- **한 곳에서 잡음**: 결정 모델을 부르는 모든 기능(맥락·고르기·답 읽기·열린 항목·눈치·점검·명령 판단·기억·브라우저…)은 이미 같은 클라이언트를 지나므로, 브리지가 만드는 **그 클라이언트를 한 번 감쌌다**(`recordDecisionCalls`; 꺼져 있으면 클라이언트 그대로). 호출하는 곳 수십 곳은 한 줄도 안 바뀜.
- **호출마다 닫힌 한 행**: `kind`(닫힌 18개 이름: context, pick, approval_reply, open_items, nunchi, check, command_gate, run_conditions, terminal_state, memory, working_memory, record, browser, placement, hud_routing, heartbeat, warmup, other; 프롬프트 캐시 키와 **질문 이름의 접두어**로 분류하고 질문 문장은 읽지 않음), `startMs`·`endMs`(턴 시작 기준 상대 ms), `inputTokens`, `cachedTokens`, `outcome`(ok, refused, timeout, budget, unreachable, bad_response, aborted, error). **사람 말·질문 원문·후보 문장·답은 넣지 않음**(시험이 저장된 행에서 사람 말·질문 이름·후보 제목이 없음을 직접 확인).
- **턴 귀속**: 호출이 시작될 때 처리 중이던 요청(요청 id)의 것으로(AsyncLocalStorage). 런타임이 `send()`에서 범위를 열고, 답 뒤에 이어지는 일(점검·하트비트 등)은 이벤트 큐에서 그 런의 요청 id 범위로 돎 → 답 뒤의 점검 호출도 같은 턴(시험: context 호출 뒤 check 호출이 같은 턴에 `startMs ≥ context.endMs`로 잡힘). 범위 밖 호출(예: 요청과 무관한 워밍업)은 기록 안 함.
- **저장(기존 저장소)**: 턴의 `decisionContext` 활동 행의 detail에 `calls` 목록을 둠 → 기존 저장소가 런과 함께 영속화(시험이 저장된 이벤트에서 확인). 호출이 끝날 때마다 `activity.updated`로 갱신. 결정 모델이 꺼져 맥락 행이 없는 턴은 메모리 링에만 남음.
- **내부 경로(플래그 뒤)**: `GET /chat/decision-calls[?limit=N]`(N 1–64, 기본 10; 그 밖은 400): 최근 N턴의 `{requestId, runId?, startedAt, calls}`. 플래그가 꺼져 있으면 라우트가 없음(처리 안 됨 → 404). 메모리 링은 최근 64턴, 호출은 턴당 48개까지.
- **턴 단계표**: `scripts/egdesk-decision-call-table.mjs db <채팅 저장소 복사본>`(읽기 전용; `--since/--until/--engine/--json`)과 `route <json>`. 단계 ① 맥락(보낸 시각→dispatching) ② 디스패치→엔진 시작 ③ 엔진 라운드 ④ EG-Desk 도구 ⑤ 첫 글자→게시와, 턴별 호출 목록·결정 wall(겹침은 한 번)·입력/캐시 토큰, 전체 합계(결정 wall이 게시 시간에서 차지하는 비율, 캐시 적중). 사람 말은 읽지 않음. (이 표는 u3에서 손으로 뽑던 것을 도구로 만든 것이며 같은 정의.)
- 새 파일: `helper/egdesk-decision-call-log.mjs`, `helper/egdesk-decision-call-table.mjs`, `scripts/egdesk-decision-call-table.mjs`, 시험 `helper/egdesk-decision-call-log.test.mjs`(7개). 공유 핫스팟 최소 수정: `codex-chat-runtime.mjs`(`send`→`sendTurn` 이름 변경과 얇은 `send`, 이벤트 큐의 `applyScoped`, `noteDecisionCall`, 맥락 행 생성 시 호출 합치기, `decisionCallTurns`), `codex-bridge-server.mjs`(클라이언트 한 줄), `codex-bridge-http.mjs`(라우트), `egdesk-decision-egress.mjs`(통과 전용 파일 등록 한 줄: 호출 지점 등록 시험이 요구).
- Main 화면 확인: 브리지를 `EGDESK_DECISION_CALL_LOG=on`(+ 결정 모델 켬)으로 시작해 대화 몇 턴 → `GET /chat/decision-calls?limit=5`에 턴별 `context`(그리고 프로젝트 방이면 `pick`, 승인 답이면 `approval_reply`, 답 뒤에 `check` 등)가 보이고, 저장소 복사본으로 `node scripts/egdesk-decision-call-table.mjs db <복사본>`이 표를 냄(복사본은 쓴 뒤 지울 것). 플래그 없이는 라우트가 404이고 행에 `calls`가 없어야 함.
- 한계: ① 상대 시각은 같은 프로세스 시계(ms). ② 호출 종류는 질문 이름 접두어 표로 분류 — 새 기능이 새 접두어를 쓰면 `other`로 보이므로 표에 한 줄 추가(시험이 알려진 이름만 검증). ③ 같은 요청의 호출이 동시에 여럿이면 wall은 겹침을 한 번만 셈.

- **사실 1**: 캐시되는 앞부분은 **언제나 3,036토큰 안팎(입력의 15%)**이고 그 이상은 한 번도 안 읽힘. 캐시 쓰기도 0인 턴 직후에만 약 3.06~3.08K(새 접두부를 처음 쓸 때).
- **사실 2**: 캐시 0인 5턴은 전부 "최근(수 분 내)에 본 적 없는 카탈로그 해시"(첫 호출, 편집 턴의 새 해시, 새 해시 2건, 35분 뒤 재등장)이고, 읽힌 턴은 전부 "수 분 내에 본 해시". 해시는 편집(c4ec9b1c)→되돌리기(원래 해시로 복귀)처럼 **프로젝트 파일 상태를 따라 움직임**(카탈로그 줄이 파일 상태에 의존). 캐시 키(`promptCacheKey`)에도 해시가 들어 있어 해시가 바뀌면 키도 바뀜.
- **추정(근거 있는 계산)**: 맥락 요청은 입력 메시지(규칙+카탈로그, 명시적 캐시 경계가 카탈로그 끝)와 별도의 `questions`(110개)로 이뤄지는데, 캐시되는 3K는 규칙+카탈로그(카탈로그 108줄 ≈ 28토큰/줄)에 맞고, 나머지 약 **17.2K 토큰(85%)은 질문 110개 + 메시지** → 질문당 약 156토큰, 이 부분은 경계 뒤라 캐시되지 않음(서버가 `questions`를 입력 뒤에 붙인다는 추정: 증거는 위의 상한 3,036).
**기대 효과(전부 추정, 실호출 검증 전)**:
1. **카탈로그 정렬·키 안정화**(`forced`를 앞으로 보내는 재배열과 해시 키를 없애고, 카탈로그는 id 순으로 두고 '언급된 항목'은 캐시 경계 뒤 메시지 쪽에 적음): 캐시 0 턴이 5/15 → 처음·만료 때만(약 2/15), 입력 약 3% 절감(0.6K/턴), 지연 효과는 0.05s 미만. **상한이 낮다: 캐시 가능한 부분이 3K뿐이라서.**
2. **질문 블록(85%)이 진짜 지렛대**: (a) `questions`가 입력 앞에 렌더되어 같은 N이면 캐시되는지 서버 의미를 확인해 정렬(Main이 실제 키로 같은 요청 두 번 + 질문 위치만 바꾼 요청 비교: 약 20턴 분량 비용) — 되면 입력 약 20K 전부 캐시 대상, 지연은 읽기 비용만 남아 0.15~0.3s 수준(중앙값 0.62s에서 0.3~0.45s 감소 추정), 비용은 캐시 단가 비율만큼. (b) **후보 사전 거름**: 108개 중 작업 폴더 파일이 대부분이라 코드로 (언급·최근·종류) 거른 20~24개만 묻기 → 입력 약 5K(−75%), 지연 0.15~0.3s 추정. 단 '결정은 모델이' 원칙과 부딪히고 재현율 위험이 있어 L1/L7의 평가가 먼저(언급·강제 항목은 항상 포함).
3. **겹치기**(구조): 맥락 호출(중앙값 0.62s)이 끝난 뒤에야 디스패치가 시작됨. 디스패치→엔진 시작(0.2~0.4s, 스레드 묶기 등)을 맥락 호출과 병행하면 턴당 0.2~0.3s 단축 추정(맥락 결과는 시작 입력에 필요하므로 엔진 준비만 병행).
- **효과의 크기 감**: 위 세 가지를 모두 해도 줄일 수 있는 것은 턴당 약 0.3~0.7s(u3 기준 총 5.3~14.9s의 3~10%)이고 토큰은 최대 약 75~90% 절감(비용). 속도의 큰 지렛대는 여전히 엔진 라운드 수(u2의 ToolSearch 제거가 중앙값 2.3s)이며, 결정 모델 호출 정리는 **비용과 잔여 지연**용이다.
