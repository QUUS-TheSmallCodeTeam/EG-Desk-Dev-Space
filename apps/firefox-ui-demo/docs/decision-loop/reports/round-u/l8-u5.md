# L8 u5 (U19): u4 실창 실패 수정 (Claude 대화의 Browser 조작이 BROWSER_TOOLS_UNAVAILABLE로 거절됨)

- 브랜치 `lane/u5-claude-browser-fix` (기준 int/c14 `f72ddd6`), 작업 사본 `$L/wt-l8-u5`, 커밋 `d90d2c0`, `ecdeb05`. 게이트는 아래 5절. 실제 Codex와 Claude는 실행하지 않음(전부 재생).

## 1. 원인(코드 추적으로 확인, 재생으로 재현)
BROWSER_TOOLS_UNAVAILABLE은 서로 다른 두 원인이었고, 화면이 둘 다 같은 "등록되기 전에 만들어졌습니다" 문장으로 보여 줘서 구분이 안 됐습니다.
| 실패 | 코드 | 원인 |
|---|---|---|
| 새 Claude 3 대화 (04:42) | **503** `Native Browser tool contract is not verified` (`codex-browser-tool-provider.mjs:92 prepare`) | 브리지가 Browser 제공자의 준비 판정을 `slotReadiness.qaReady(route.engineProfileId)`로 연결해 둠. 이것은 **Codex 공유 슬롯**(Codex 앱 서버가 떠 있고 qaReadOnly 프로브가 참)의 답이라서, Claude 경로(engineProfileId 없음)도 Codex 상태로 판정됨. Codex가 준비되지 않았으면 Claude 첫 전송에서 막힘. |
| 기존 Claude 2 대화 (04:01) | **409** `This native thread predates Browser tools` (`codex-chat-runtime.mjs` ~2111, 또는 provider `requireThread`) | 그 대화는 첫 턴에 Browser 도구 없이 만들어진 일반 대화라 `browserRegisteredThreads`에 없음. 이 경우는 문장이 맞는 편(아래 3절). |
화면(`eg-desk-surface.uc.js` ~19877)은 두 코드를 구분 없이 같은 문장으로 덮어씀(오해의 원인).

## 2. 수정
1. **Claude 경로의 준비 판정을 Claude 기준으로(1)**: 새 `helper/egdesk-claude-browser-route.mjs`의 `browserSchemaReady({claudeLive, claudeReady, codexReady})`. route.engineId가 claude이고 능력이 살아 있으면(하네스 켜짐 + page tools 제공자 등록, `claudeBrowserLive`) `claudeEngine.isReady() && capabilities().has('boundedQa')`로 판정, 아니면 기존 Codex 슬롯 답 그대로. 브리지는 Browser 제공자 `schemaReady`를 이 함수로 감싸기만 함(한 줄). 런타임에는 `claudeBrowserLive()` 접근자 하나만 추가. **Codex 경로 불변**(Codex route는 항상 codexReady, 시험으로 고정). 플래그가 꺼져 있으면 모든 답이 이전과 같음.
2. **화면 문구 매핑(3)**: `BROWSER_TOOLS_UNAVAILABLE`의 "등록되기 전에 만들어졌습니다" 문장을 `error.status === 409`일 때만 씀. 503은 서버 메시지(기존 일반 실패 문구 + 자세히)를 그대로 보여 줌. 새 문구 없음.
3. **기존 Claude 대화(도구 켜기 전 생성)는 막아야 하는가(1의 판단)**: **막는 것을 유지**합니다. 이유는 도구 등록(Claude는 프로세스마다 도구를 싣기 때문에 불필요)이 아니라 **정책 승격**입니다. 일반 대화에 Card 조작을 허용하면 그 대화가 browserBounded로 영구 고정되어 이후 자체 도구(명령, 파일)가 없는 대화로 바뀝니다(Codex가 "새 Chat" 요구하는 것과 같은 이유, `POLICY_TRANSITION_FORBIDDEN` 규칙과 같은 계열). 사람이 요청하지 않은 변화라 조용히 허용하면 안 됩니다. 또 이 길은 지금 바로 풀어도 동작하지 않습니다: `persistExecutionPolicy`가 소유자 해시를 `'codex'`로 하드코딩해(`codex-chat-runtime.mjs` ~2585) Claude 승격은 `ACCOUNT_CHANGED`로 끝남(재생에서 확인한 기존 결함). 풀려면 이 한 줄 수정 + 등록 예외 + 소유자의 "대화를 영구 제한해도 되는가" 결정이 필요 -> **제안(승인 대기)**. 대신 처음부터 Card와 함께 시작한 Claude 대화는 2턴째 이후도 동작함(시험으로 확인).

## 3. 재생 시험 `helper/egdesk-claude-browser-route.test.mjs` (7건)
실제 런타임, 대화 저장소, own-tools 배선, Claude 어댑터, MCP 다리, Browser와 page 도구 제공자, 브리지가 쓰는 준비 판정 함수까지 진짜. Claude 프로세스(대본 전송)와 페이지만 가짜. **가짜 schemaReady 없음**(Codex 슬롯만 "준비 안 됨"으로 둠).
1. 실패 재현: u4 방식(Codex 슬롯이 모든 엔진을 판정)이면 새 Claude 대화 + Card가 `BROWSER_TOOLS_UNAVAILABLE` 503, Claude 프로세스 0개.
2. 수정 확인: 같은 조건에서 전송 수락, 턴 완료, 바운드(`tools: []`, `dontAsk`, 허용 `mcp__egdesk`), 카탈로그에 `egdesk_card_read/press/type/open`.
3. Card와 함께 시작한 대화의 2턴째도 수락 + 바운드.
4. 일반 대화는 능력이 있어도 409 유지(턴 시작 없음, 이력과 초안 유지).
5. 플래그 꺼짐: page tools 없음이면 409 그대로, 하네스 꺼짐이면 Codex 슬롯이 판정(503) 그대로.
6. 순수 규칙: Claude + 능력 + Claude 준비일 때만 Codex 슬롯을 벗어남, Codex route 불변, Claude 미준비면 Codex가 참이어도 거짓.
7. 정적: 브리지가 `browserSchemaReady`를 쓰고, 화면이 409에만 그 문장을 씀.
