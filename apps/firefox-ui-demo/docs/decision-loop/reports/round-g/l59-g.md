## Act 저널
- `createBrowserToolService({... procedureJournal, procedureFlag})`. 서비스 반환 객체에 `procedureJournal` 추가. 저널 API는 `record(thread,card,entry)`, `lastRun(thread,card)`(가장 최근 runId의 entry만, 복사본), `size()`, `clear()`. 한도는 200개/키, 50키(LRU).
- 기록 위치: `executeDispatch` 래퍼. 플래그가 off이면 원래 함수(executeDispatchInner)를 그대로 호출하므로 변화 없음. 호출 전에 card.observation에서 pageUrl/title/요소 facts를 읽어 두고, 결과 status가 `ok`, `postcondition-observed`, `history-dispatched`, `key-dispatched`이면 기록.
- entry: `{at, runId, tool, expectedTarget, text?, url?, key?, direction?, amount?, action?, postcondition?, afterUrl?, pageUrl, pageTitle?, displaySafe?, facts?}`. text는 요소가 displayValueSafe일 때만 저장(비밀번호류 값은 메모리에도 남지 않음).
- 계약 대비 차이: OK 상태에 history-dispatched, key-dispatched를 추가했다(history와 키 전용 press의 정상 결과 status가 이 둘이라서). `afterUrl`은 클릭 후 URL이며 계약에 없는 추가 필드다.

## 저장소 (계약과 다른 점)
`records` 테이블에 CHECK(kind IN plan/source/gate-answer)가 있어서 기존 DB에 새 kind를 넣을 수 없다. 스키마 버전을 올리면 기존 DB와 하위 호환이 깨지므로, 같은 `store.records` API(list/count/insert/replace/remove, kind `'browser_procedure'`)를 쓰되 별도 테이블 `procedure_records`로 보냈다. 이 테이블은 처음 쓸 때만 만들어지므로 절차를 저장하지 않는 DB는 바뀌지 않는다. update는 `replace`, delete는 `remove`로 이미 있었고 테스트를 추가했다. 최대 200개.

## 서비스
`createProcedureService({store, journal, now})` (`egdesk-browser-procedure-service.mjs`)

## HTTP (loopback만, 플래그 off면 404 `{status:'off'}`)
- `GET /v1/procedures` -> `{procedures:[summary]}`
- `GET /v1/procedures/:id` -> `{procedure}` (없으면 404 `{status:'not-found'}`)
- `POST /v1/procedures` body는 `{procedure:{...}}` 또는 procedure 자체 -> 201 `{procedure}`, 검증 실패 400 `{status:'invalid',errors}`
- `PUT /v1/procedures/:id` -> 200 `{procedure}`
- `DELETE /v1/procedures/:id` -> `{status:'deleted'}`
- `POST /v1/procedures/capture {clientThreadId,cardId,name?}` -> 200 `{draft}` (저장 안 함), act 없으면 409 `{status:'empty'}`
- 그 외: 403 loopback 아님, 405(Allow 헤더), 415/400 본문 오류, 503 서비스 없음. 마운트는 screenRecording.handle 바로 아래. `/v1/state`의 `capabilities.browserProcedures: true`는 플래그가 on일 때만 나온다.

## L61 호출 방법

## 위험, 미완
