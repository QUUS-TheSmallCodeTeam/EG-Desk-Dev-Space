## 요약

AI 기술의 급속한 발전에도 불구하고 기업들의 실제 AI 도입 성과는 기대에 현저히 미치지 못하고 있습니다. 글로벌 AI 프로젝트의 70-85%가 목표 ROI 달성에 실패하며[^1], 국내 기업의 AI 활용률은 필요성 인식 대비 절반에도 못 미치는 30.6%에 불과합니다[^7]. 이러한 실패의 근본 원인은 AI의 성능 부족이 아닌, AI가 실제 업무 시스템을 실행할 수 없는 AI 실행 단절(AI Execution Disconnect)이라는 구조적 한계와 기업의 핵심 자산을 외부로 유출해야 하는 데이터 주권의 상실에 있습니다.

본 백서에서는 이 문제를 해결하기 위한 새로운 아키텍처인 AI Agent Scaffold를 제안합니다. 현대의 모든 업무 시스템은 사람이 브라우저를 통해 접속하도록 설계되어 있습니다. EG-DESK는 이러한 브라우저 엔진 자체를 유니버설 인터페이스로 활용하여, API가 없는 시스템의 내부 기능까지 즉시 제어할 수 있는 실행 접근 인프라(Execution Access Infrastructure)를 구축했습니다. 이를 통해 사용자의 로컬 환경을 침해받지 않는 독립적인 영토로 보호하는 데이터 주권을 실현합니다. 또한, 평소에는 데이터를 로컬에 안전하게 보관하다가 업무 수행 순간에만 필요한 지능을 공급받는 데이터 관개(Data Irrigation) 모델을 통해 보안과 효율의 딜레마를 해결합니다.

이러한 기술적 기반 위에 EG-DESK는 기술과 사람을 결합한 지능 관리 서비스(Managed Intelligence)를 제공합니다. 전담 프로젝트 매니저(PM)가 Scaffold를 활용하여 고객의 업무 흐름을 설계하고, 그 과정에서 축적된 암묵지를 Ontology 지식 모델로 자산화합니다. PM의 서비스가 반복될수록 실패 유형과 성공 패턴이 Ontology에 누적되어 시스템 전체가 진화하며, 이는 후속 사용자들이 겪을 시행착오를 원천적으로 제거하는 강력한 네트워크 효과를 창출합니다.

## 1. 서론: AI 도입의 딜레마

현대 업무 환경은 AI 도구의 급속한 성장에도 불구하고 근본적인 딜레마에 직면해 있습니다.

대규모 언어 모델(LLM)은 텍스트 생성과 추론 영역에서 비약적인 발전을 이루었습니다. 하지만 실제 업무 환경에서는 AI의 뛰어난 사고 능력이 시스템을 직접 제어하지 못하는 AI 실행 단절(AI Execution Disconnect)이라는 구조적 장벽에 부딪힙니다.

AI가 이메일 초안을 작성해도 실제로 Gmail에 접속하여 보내는 것은 사람의 몫이며, 복잡한 세무 계산을 해주어도 홈택스에 로그인하여 신고하는 것은 사람이 직접 해야 합니다. AI의 역할은 사고에서 끝나고 실행은 여전히 인간의 영역으로 남겨져 있습니다. 이러한 구조적 한계는 AI 도입 프로젝트의 대규모 실패로 이어지고 있으며, 동시에 기업들은 자신들의 핵심 노하우를 외부 클라우드에 헌납해야 하는 데이터 주권 상실의 위기를 겪고 있습니다.

## 2. AI 도입 실패의 현실

AI 실행 단절은 전 세계적으로 측정 가능한 규모의 실패로 나타나고 있습니다.

### 2.1 글로벌 AI 프로젝트의 실패
NTT DATA의 2024년 보고서에 따르면 생성형 AI 배포 프로젝트의 70-85%가 목표 ROI 달성에 실패하고 있습니다[^1]. BCG가 2024년 10월에 발표한 보고서는 더욱 명확한 수치를 보여줍니다. 74%의 기업이 AI로부터 실질적 가치 창출에 실패했으며, 단 26%의 기업만이 POC(개념 증명) 단계를 넘어섰고, 단 4%만이 상당한 가치를 창출했습니다[^3]. 도입률은 72%까지 급증했으나 성숙 단계에 도달한 기업은 1%에 불과한 현실은 실행 계층의 부재를 시사합니다[^4].

### 2.2 국내 기업의 AI 도입 격차
대한상공회의소 조사에 따르면 국내 기업의 78.4%가 AI 기술의 필요성을 인식하고 있으나 실제 활용률은 30.6%에 불과합니다[^7]. 특히 대기업(48.8%)과 중견기업(30.1%), 중소기업(28.7%) 간의 격차가 뚜렷하며, 제조업의 경우 활용률이 4.2%에 불과해 대기업과 10배 이상의 격차를 보입니다. AI 기술은 발전하는데 이를 활용할 준비가 된 기업은 오히려 줄어들고 있는 역설적 상황이 발생하고 있습니다[^8].

## 3. 왜 실패하는가: 구조적 원인과 그 결과

### 3.1 70%는 인력과 프로세스 문제
BCG의 10-20-70 규칙에 따르면, AI 구현 과제의 70%는 알고리즘이나 기술이 아닌 인력 및 프로세스 관련 문제입니다[^3]. 국내 기업 도입 장애 요인에서도 내부 인력 부족(60%)이 가장 큰 원인으로 꼽힙니다[^7]. 이는 AI 기술 자체가 어려워서가 아니라 해당 기술을 실제 업무 환경에서 운용할 수 있는 인력과 연결 고리가 부재하기 때문입니다.

### 3.2 다섯 가지 구조적 장벽
1. 실행 능력의 부재: AI가 웹사이트 버튼을 클릭하거나 폼을 입력하는 물리적 능력이 없습니다.
2. 서비스의 사일로화: 각 SaaS 서비스가 독립적으로 작동하여 사용자가 매 단계 수동으로 컨텍스트를 재구성해야 합니다.
3. API 장벽: 많은 시스템이 API를 제공하지 않거나 접근이 제한적입니다. 사람은 웹에서 모든 것을 할 수 있지만 AI는 API가 없으면 무용지물입니다.
4. 기술 장벽: API를 우회하는 자동화를 구축하려면 전문 프로그래밍 지식과 막대한 비용이 필요합니다.
5. 실무 인사이트의 부재: LLM은 일반 지식은 풍부하나 특정 시스템의 실시간 운영 제약(접속 시간 제한, 브라우저 호환성 등)과 같은 실무 암묵지가 부족하여 마지막 20%의 완성도를 채우지 못합니다.

## 4. 기존 솔루션의 한계: 인력 병목 구조

시장의 기존 솔루션들은 인력 병목 구조(Human Bottleneck Structure)를 벗어나지 못했습니다.

* AI Provider (ChatGPT, Claude 등): 서비스 범위가 사전에 연결된 시스템으로 제한되며 사용자의 세밀한 업무 흐름을 반영하기 어렵습니다.
* 개발자용 AI 도구 (Cursor, Windsurf 등): 높은 자유도를 제공하지만 높은 세팅 노고와 학습 비용을 사용자에게 전가하여 기술 장벽을 강화합니다.
* 워크플로우 플랫폼 (Zapier, Make 등): API가 있는 시스템만 연결 가능하며 사용자가 직접 플로우를 설계하고 오류를 감시해야 합니다.
* RPA 솔루션 (UiPath 등): 전문 인력과 막대한 비용이 필요하며 UI 변경 시 유지보수 부담이 과도합니다.

결국 자동화 도구가 도입되어도 세팅, 감시, 수습의 핵심 운영이 여전히 인력에 종속되어 있어 직원의 업무 부담이 오히려 가중되고 번아웃률이 높아지는 결과를 초래합니다[^11][^13].

## 5. EG-DESK의 접근: AI Agent Scaffold (적응형 실행 계층)

본 백서에서는 AI 실행 단절을 해소하기 위한 실행 접근 인프라(Execution Access Infrastructure) 아키텍처를 제안합니다. EG-DESK는 정적인 API 통합 방식의 한계를 넘어, 브라우저 엔진을 유니버설 런타임으로 활용하여 시스템의 심부로 즉각 도달하는 실행 경로를 확보합니다.

### 5.1 API 격차와 통합 지연
기존의 SaaS 상호운용성은 애플리케이션의 실제 기능과 프로그램적으로 노출된 엔드포인트 사이의 괴리인 API 격차에 의해 제한됩니다. 이는 벤더 정의 정적 스키마(Vendor-defined Static Schema)에 의존해야 하는 환경을 만들며, 비즈니스 크리티컬한 워크플로우를 자동화하려는 에이전트의 활동 범위를 축소시킵니다.

### 5.2 적응형 실행 계층 (Adaptive Execution Layer)
EG-DESK는 의도를 인터페이스의 제약으로부터 분리하는 적응형 실행 계층인 AI Agent Scaffold를 도입합니다. 표준화된 API가 완성되기를 기다리는 대신, Scaffold는 브라우저 네이티브 레벨에서 DOM(Document Object Model)을 인터페이스 추상화(Interface Abstraction) 도구로 활용합니다. 이를 통해 모든 웹 기반 애플리케이션을 에이전트를 위한 구조화된 실행 기질(Substrate)로 전환합니다.

### 5.3 SaaS 상호 연결 파이프라인
이러한 실행 접근 인프라를 통해 EG-DESK는 SaaS 상호 연결 파이프라인의 신속한 배포를 가능하게 합니다. PM은 이 파이프라인을 설계하여 ERP, CRM, 그리고 내부 레거시 시스템 등 단절된 환경 사이에서 데이터 스트리밍과 동작 트리거를 유기적으로 연결합니다. 이는 하부 API의 성숙도와 관계없이 기업 전체의 자동화를 수평적으로 확장할 수 있는 즉각적인 경로를 제공합니다.

## 6. Ontology: 업무 맥락 지식 체계

실무 현장의 암묵지를 구조화하여 원샷 실행(Oneshot Execution)을 가능하게 하는 EG-DESK의 핵심 엔진입니다.

### 6.1 4가지 지식 계층
1. Dimension 1 (Sovereign Layer): 사용자나 조직 고유의 맥락. 개인 선호, 내부 기밀, 관계 맥락을 포함하며 데이터 주권 보호를 위해 로컬에 저장됩니다.
2. Dimension 2 (System Pattern): 특정 시스템의 실무 패턴. 로그인 대기 시간, 팝업 처리 순서, 시스템 점검 시간대 등 실행 환경의 암묵적 인사이트를 기록합니다.
3. Dimension 3 (Domain Knowledge): 업무 고유 규칙. 법규, 회계 기준, 비즈니스 로직 등 처리 시스템과 무관하게 적용되는 공식 지식입니다.
4. Dimension 4 (Workflow Composition): 위 3개 차원의 지식을 조합한 실행 시퀀스입니다. 실제 환경에서 검증된 성공적 경로를 담고 있습니다.

### 6.2 AI 브릿징 (AI Bridging)
AI 에이전트는 분산된 Ontology(로컬의 개인 맥락 + 클라우드의 검증된 패턴)를 실행 시점에 자동으로 통합합니다. 이를 통해 전 세계의 검증된 노하우를 내 업무에 즉시 적용하면서도 사용자의 데이터 주권을 완벽하게 보호합니다.

## 7. Ontology와 미니앱: 실무 지식의 축적과 전달

Ontology가 지식이라면 미니앱(Mini-apps)은 이 지식을 사용자 인터페이스로 연결하는 접점입니다.

### 7.1 프론트엔드 로직의 극소화
EG-DESK 아키텍처에서 미니앱의 프론트엔드 코드는 수백 줄 수준으로 극소화됩니다. 복잡한 비즈니스 로직, 상태 관리, API 호출 등은 플랫폼 레이어(AI + Ontology + Scaffold)가 담당하며, 미니앱은 오직 뷰어와 요청자 역할만 수행합니다.

### 7.2 세 가지 사용 방식
* 완전 자동: 정형화된 반복 작업을 스케줄에 따라 자동으로 처리합니다.
* 반자동 (Graceful Fallback): 대부분 자동으로 진행하되 판단이 필요한 순간에만 사용자에게 확인을 요청합니다. 이 과정에서 얻은 해결책은 다시 Ontology에 축적됩니다.
* 직접 실행: 특수한 케이스나 긴급 상황에서 미니앱을 직접 열어 유연하게 대응합니다.

## 8. 핵심 기술 아키텍처

### 8.1 시스템 구조
사용자가 자연어로 요청하거나 미니앱을 실행하면 다중 AI 모델 통합 계층이 Ontology 4계층을 결합합니다. 이후 Firefox chrome JS 기반의 브라우저 우선 실행 계층을 통해 실제 웹 시스템(금융, 소셜미디어, CMS 등)을 제어합니다. Playwright류 자동화는 보조 검증/외부 자동화 경로로 둘 수 있으나, 현재 제품 구현 기준은 EG-DESK 내부의 real browser surface를 직접 제어하는 Firefox shell입니다.

### 8.2 동적 환경 적응
전통적 RPA가 UI 변경 시 스크립트 실패와 수동 재작성을 반복하는 것과 달리, EG-DESK는 예외 발생 시 AI 에이전트가 즉시 개입하여 문제를 분석하고 Ontology를 자동 업데이트합니다. 이는 시스템이 스스로 환경 변화에 적응하는 지능형 구조임을 의미합니다.

## 9. 전담 인력 서비스: 실행 아키텍트로서의 PM

AI 도입 실패의 70%를 차지하는 인력 문제를 해결하기 위해 EG-DESK는 2-layer 전담 서비스를 제공합니다.

### 9.1 실행 아키텍트로서의 PM 역할
전담 프로젝트 매니저(PM)는 단순한 운영 보조자가 아닙니다. 이들은 EG-DESK 플랫폼이라는 Scaffold를 도구 삼아 SaaS 간의 복합적인 연결 파이프라인을 설계하고 구축하는 아키텍트입니다. 
* 고객 담당자: 고객의 니즈를 탐색하고 이를 미니앱 UI로 신속하게 변환합니다.
* 기술 담당자: 실제 시스템 통합과 워크플로우 로직을 구축하여 검증된 Ontology를 생산합니다.

### 9.2 제로 러닝 커브와 비대칭 확장
기업인은 본업에 바빠 새로운 AI 프레임워크를 학습할 시간이 없습니다. EG-DESK의 PM 서비스는 이 학습의 계곡(Learning Chasm)을 대신 건너줍니다. 또한 기술 담당자가 구축한 지식을 다수의 고객 담당자가 재사용하는 비대칭 확장 구조를 통해 인력 부족 문제를 플랫폼의 생산성으로 상쇄합니다.

## 10. 네트워크 효과: Working Pattern의 자산화

사용자와 PM이 늘어날수록 EG-DESK 생태계는 기하급수적으로 강력해지는 질적 네트워크 효과를 가집니다.

### 10.1 지식의 누적과 선순환
최초 사용자가 겪은 시행착오는 Ontology로 구조화되어 저장됩니다. 이후 동일한 문제를 겪는 백 번째 고객은 이미 축적된 패턴을 통해 원샷 성공을 경험합니다. 사용량이 증가할수록 시스템의 정확도와 성공률이 지속적으로 향상됩니다.

### 10.2 시간의 장벽
기술 스택은 복제할 수 있지만, 수천 개 기업의 실제 업무 현장에서 검증된 실무 패턴(Working Pattern)은 오직 시간과 경험의 투입을 통해서만 획득됩니다. 축적된 Ontology는 경쟁자가 넘을 수 없는 EG-DESK만의 거대한 시간 장벽이 됩니다.

## 11. 데이터 주권과 데이터 관개 (Data Irrigation)

EG-DESK는 단순한 보안을 넘어 데이터 주권이라는 적극적 권리를 지향합니다.

### 11.1 데이터 주권의 보장
사용자의 로컬 환경은 외부 간섭을 받지 않는 독립된 디지털 영토(Local Territory)입니다. 기밀 데이터와 개인적 맥락은 이 영토 내에 머물며, 사용자는 자신의 데이터를 외부 클라우드에 맡기는 것이 아니라 로컬에 보유한 상태에서 지능만 호출합니다.

### 11.2 데이터 관개 모델
데이터를 한곳에 모으는 데이터 레이크 방식을 거부하고 데이터 관개(Data Irrigation) 방식을 채택합니다.
* 기능적 맥락 수화 (Functional Context Hydration): 데이터는 발생한 원천인 로컬 영토(지하수)에 그대로 둡니다.
* 실시간 수화: 업무 수행 찰나의 순간에만 필요한 최소한의 데이터를 끌어올려(Pump-up) 지능과 결합시킵니다.
* 흔적 없는 실행: 작업 완료 후 연결 흐름은 즉시 차단되며 서버에 흔적을 남기지 않습니다. 이는 데이터에 대한 완전한 통제권을 보장하는 주권의 구현입니다.
