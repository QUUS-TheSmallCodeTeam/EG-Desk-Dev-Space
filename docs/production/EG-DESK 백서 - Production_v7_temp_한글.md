## 요약

AI 기술의 급속한 발전에도 불구하고, 기업들의 실제 AI 도입 성과는 기대에 현저히 미치지 못하고 있습니다. 글로벌 AI 프로젝트의 70-85%가 목표 ROI 달성에 실패하며[^1], 국내 기업의 AI 활용률은 필요성 인식(78.4%) 대비 절반에도 못 미치는 30.6%에 불과합니다[^7]. 이러한 실패의 근본 원인은 AI의 성능 부족이 아닌 AI가 실제 업무 시스템을 실행할 수 없는 "AI 실행 단절"이라는 구조적 한계에 있습니다.

본 백서에서는 이 문제를 해결하기 위한 새로운 아키텍처인 AI Agent Scaffold를 제안합니다. AI Agent Scaffold는 브라우저 자동화 기술을 통해 AI 에이전트가 모든 웹 시스템을 직접 제어할 수 있는 통합 실행 환경을 제공하는 EG-Desk의 기술적 기반입니다. 사용자의 로컬 환경에 설치되어 API 제약 없이 모든 웹 기반 업무 시스템에 접근함으로써, 앞서 언급한 AI 실행 단절을 해소합니다.

이러한 기술적 기반에 더해, EG-Desk의 진정한 차별점은 기술과 사람의 결합에 있습니다. EG-Desk에서 각 고객 기업에 전방 배치한 전담 기술 인력(PM/TA)이 현장에서 AI Scaffold를 설치하고 업무별 AI 시스템을 구축하는 과정에서, 특정 웹사이트의 로그인 구조, 공동인증서 인증 과정, 시스템별 타이밍 이슈 등 실무에서만 얻을 수 있는 인사이트가 Ontology에 자연스럽게 축적됩니다. 이 Ontology는 사용자가 증가할수록 더 견고해지며, 대상 시스템의 변화가 있어도 PM 네트워크를 통해 실시간으로 대응하여 갱신됩니다. 일반 LLM으로는 여러 번의 시행착오가 필요한 작업이 EG-Desk에서는 첫 시도에 성공하는 oneshot execution을 구현합니다.

## 서론: AI 도입의 딜레마

현대 업무 환경은 AI 도구의 급속한 성장에도 불구하고 근본적인 딜레마에 직면해 있습니다.

대규모 언어 모델(LLM)은 텍스트 생성과 추론 영역에서 급격한 발전을 이루었습니다. ChatGPT는 출시 2개월 만에 1억 사용자를 확보했고[^21], 기업들은 경쟁적으로 AI 도입을 선언했습니다. 그러나 실제 업무에 적용하려 하면, **AI 실행 단절(AI Execution Disconnect)**에 직면합니다. 이는 AI의 추론 능력과 실제 시스템 제어 능력 사이의 구조적 단절을 의미합니다.

이 문제는 생각보다 광범위합니다. AI가 이메일 초안을 작성해도 실제로 Gmail에 접속해서 보내는 것은 사람의 몫이며, AI가 복잡한 세금 계산을 해주어도 홈택스에 로그인해서 신고하는 것은 사람이 해야 하고, AI가 마케팅 전략을 수립해도 각 소셜 미디어에 접속해서 콘텐츠를 발행하는 것은 사람의 일입니다. AI의 역할은 "생각하는 것"에서 끝나고, "실행하는 것"은 여전히 사람에게 남습니다.

이 괴리는 AI 도구와의 일반적인 상호작용 방식에서 명확히 드러납니다:

```
LLM에게 업무 환경 설명 →
    LLM이 콘텐츠 생성 →
        복사-붙여넣기로 적용 →
            결과를 다시 LLM에게 설명하여 다음 단계 요청 →
                LLM이 추가 콘텐츠 생성 →
                    복사-붙여넣기로 적용 →
                        ... 반복 ...
```

이러한 AI 실행 단절은 현대 업무 환경에 고착화되어 있습니다. 이것은 단순한 불편함의 문제가 아닙니다. 이 구조적 한계는 AI 도입 프로젝트의 대규모 실패로 이어지고 있으며, 그 규모는 대부분의 예상을 뛰어넘습니다.

## AI 도입 실패의 현실

AI 실행 단절은 전 세계적으로 측정 가능한 규모의 실패로 나타나고 있습니다.

### 글로벌 AI 프로젝트의 실패

NTT DATA의 2024년 보고서에 따르면, 생성형 AI(GenAI) 배포 프로젝트의 70-85%가 목표 ROI 달성에 실패하고 있습니다[^1]. RAND Corporation의 분석은 더 심각한 현실을 보여줍니다. AI 프로젝트 전체의 80% 이상이 실패하며, 이는 비(非)AI 기술 프로젝트 실패율의 2배에 해당합니다[^2].

이러한 수치가 단순한 추정치가 아님을 확인해주는 대규모 조사가 있습니다. BCG(Boston Consulting Group)가 2024년 10월에 발표한 보고서는 1,000명의 CxO 및 시니어 임원을 대상으로 20개 이상의 섹터, 59개국에 걸쳐 조사를 수행했습니다[^3]. 그 결과는 더욱 명확합니다:

- 74%의 기업이 AI로부터 실질적 가치 창출에 실패
- 단 26%의 기업만이 POC(개념 증명) 단계를 넘어 실질적 가치를 생성
- 4%의 기업만이 AI 투자로부터 상당한 가치를 창출

이 수치가 의미하는 바는 분명합니다. 4분의 3에 달하는 기업이 AI에 투자하고도 실질적 성과를 얻지 못하고 있습니다.

McKinsey의 "The State of AI" 보고서(2024-2025)는 이 상황을 더욱 극명하게 보여줍니다[^4]. AI 채택률은 약 50%에서 72%로 증가했으나, 기업 임원의 1%만이 자사의 AI 롤아웃이 성숙 단계에 도달했다고 평가했습니다. 도입은 늘어나는데 성과는 나지 않는 이러한 현실은 AI 모델의 성능 한계가 아니라 이를 실제 업무에 연결하는 실행 계층의 부재를 시사합니다.

### 국내 기업의 AI 도입 격차

글로벌 상황에 비해 국내 격차는 더욱 심각합니다.

대한상공회의소의 '국내 기업 AI 기술 활용 실태 조사'에 따르면, 국내 기업의 78.4%가 AI 기술의 필요성을 인식하고 있으나 실제 활용률은 30.6%에 불과합니다[^7]. 필요성 인식과 실제 활용 사이에 47.8%포인트의 격차가 존재합니다. 10명 중 8명이 "AI가 필요하다"고 말하면서, 실제로 사용하는 것은 3명에 불과한 셈입니다.

이 격차가 더욱 심각한 이유는 기업 규모와 업종에 따른 불균형 때문입니다:

| 기업 규모 | AI 활용률 | 대기업 대비 격차 |
|---------|---------|--------------|
| 대기업 | 48.8% | - |
| 중견기업 | 30.1% | -18.7%p |
| 중소기업 | 28.7% | -20.1%p |
| 중소기업 제조업 | 4.2% | -44.6%p (10배 이상) |

특히 중소기업 제조업의 경우 대기업과 10배 이상의 격차가 존재합니다. 업종별로는 서비스업이 53%인 반면 제조업은 23.8%로 서비스업의 절반에도 못 미칩니다. 지역별로도 수도권(40.4%)과 비수도권(17.9%) 간에 2배 이상의 격차가 나타납니다.

더 우려스러운 것은 이 격차가 줄어들지 않고 있다는 점입니다. 시스코의 AI 준비도 조사에 따르면, AI를 충분히 활용할 준비가 갖춰진 국내 기업은 3%에 불과하며, 이는 전년의 5%에서 오히려 감소한 수치입니다[^8]. AI 기술은 발전하는데, 이를 활용할 준비가 된 기업은 오히려 줄어들고 있습니다.

이러한 수치는 AI 혁명의 혜택에서 소외되는 기업의 규모가 예상보다 훨씬 크며, 대기업과 중소기업, 수도권과 비수도권, 서비스업과 제조업 사이의 격차가 시간이 경과할수록 더욱 확대되고 있음을 보여줍니다.

## 왜 실패하는가: 구조적 원인과 그 결과

이처럼 많은 AI 프로젝트가 실패하는 이유는 단순히 AI가 어렵다는 것으로는 설명할 수 없습니다. 표면적 이유 너머의 구조적 원인을 분석해야 합니다.

### 70%는 인력과 프로세스 문제

BCG는 AI 성공 기업의 패턴을 분석하여 "10-20-70 규칙"을 제시합니다[^3].

| 구성 요소 | 비율 | 설명 |
|---------|------|------|
| 알고리즘 | 10% | AI 모델 자체 |
| 기술과 데이터 | 20% | 인프라, 데이터 품질 |
| 인력과 프로세스 | 70% | 조직 변화, 워크플로우 재설계 |

이 규칙이 말해주는 것은 명확합니다. AI 구현 과제의 약 70%가 기술이 아닌 인력 및 프로세스 관련 문제입니다. 아무리 좋은 AI 모델을 도입해도, 그것을 실제 업무에 연결하는 "사람의 일"이 해결되지 않으면 효과가 없습니다. 이 "사람의 일"이 가장 해결하기 어려운 부분입니다.

이 점은 국내 기업들이 꼽는 주요 도입 장애 요인에서 더욱 명확해집니다[^7]:

| 장애 요인 | 비율 |
|---------|------|
| 내부 인력 부족 | 60% |
| 투자 효과 불확실성 | 57% |
| 데이터 부족 및 품질 문제 | 52.9% |
| 정보 유출 우려 | 41.9% |
| 기술 및 IT 인프라 부족 | 34.6% |
| 비용 부담 | 23.1% |

내부 인력 부족이 60%로 가장 높은 비율을 차지합니다. 이 수치는 글로벌 통계(69%, IBM Think 2024)[^19]와도 일치합니다. 주목할 점은 이것이 AI가 어려워서가 아니라 AI를 업무에 연결할 수 있는 사람이 없어서라는 것입니다. AI 기술 자체의 난이도가 아니라, 해당 기술을 실제 업무 환경에서 운용할 수 있는 인력의 부재가 핵심 문제입니다.

### LLM의 80-20 문제

AI 도입 실패의 또 다른 구조적 원인은 LLM 모델 및 서비스 구조에 있습니다. 본 백서에서는 이를 "80-20 문제"라고 명명합니다.

LLM은 일반적인 업무 요청에 대해 합리적인 작업 계획을 수립하여 업무의 80% 완성도까지 빠르게 도달하지만, 실제 운영 환경의 구체적 제약사항 - 시스템별 접근 제한, 고객사별 양식 요구사항, 플랫폼별 승인 프로세스 - 을 반영하는 마지막 20%에서 반복적 조정이 필요하며, 이 20%가 실제 환경에서의 작동 여부를 결정합니다.

LLM의 훈련 데이터는 공개된 텍스트 기반으로 구성되어 일반적인 도메인 지식은 포함하나, 특정 시스템의 실시간 운영 제약 - 접속 시간대 제한, 브라우저 호환성, 인증 프로세스 변경, 고객사별 맞춤 요구사항 - 과 같은 실무 환경 특성은 포함하지 않습니다. 이러한 정보는 훈련 데이터에 존재하지 않으므로, LLM은 추론 시점(test-time)에 이를 보완해야 하며, 이것이 평균 5-6회의 반복 시도로 나타납니다.

### 다섯 가지 구조적 장벽

이러한 실패 패턴을 분석하면, AI 시대의 업무 환경이 직면한 다섯 가지 구조적 장벽을 식별할 수 있습니다. 중요한 것은 이 장벽들이 개별적으로 작용하는 것이 아니라 서로를 강화하는 악순환을 형성한다는 점입니다.

**장벽 1: AI의 실행 능력 부재**

현재의 AI 도구들은 텍스트를 생성하고 조언을 제공할 수 있지만 실제로 웹사이트에서 버튼을 클릭하거나 폼을 입력하는 것은 불가능합니다. 이러한 실행 능력의 부재가 가장 근본적인 장벽으로 작용하며, 이것이 해결되지 않는 한 다른 모든 장벽은 불가피하게 남게 됩니다.

**장벽 2: 클라우드 서비스의 사일로화**

AI가 실행 능력을 갖추지 못한 상태에서, 기업들은 각 서비스를 수동으로 연결해야 합니다. 그러나 CMS, 소셜 미디어, 금융 시스템, 공공 포털 등 각 서비스는 독립적으로 작동하며 서로 데이터를 주고받지 않습니다. 각 애플리케이션이 격리된 상태를 유지하여 사용자가 매 단계에서 수동으로 컨텍스트를 재구성해야 합니다. 이러한 사일로화는 자동화의 복잡성을 기하급수적으로 증가시킵니다.

**장벽 3: API 장벽**

사일로화된 서비스들을 연결하려면 API가 필요합니다. 그러나 공공기관, 금융기관 등 많은 시스템은 API를 제공하지 않거나 접근이 제한됩니다. API가 있더라도 비용이 높거나 기능이 제한적인 경우가 대부분입니다. Deloitte의 2024년 조사에 따르면, 60%의 AI 리더가 레거시 시스템 통합을 가장 큰 도전 과제로 꼽았습니다[^20]. 사람은 웹사이트에서 모든 것을 할 수 있지만, AI는 API가 없으면 아무것도 할 수 없습니다.

**장벽 4: 기술 장벽**

API 장벽을 우회하여 자동화를 구현하려면 전문적인 프로그래밍 지식이 필요합니다. 엔터프라이즈 RPA 솔루션은 연간 수천만원의 비용이 들어 대부분의 중소기업은 접근 자체가 불가능합니다. 60%의 기업이 내부 인력 부족을 꼽는 이유가 이것입니다. 기술 인력이 있어도 비용을 감당할 수 없고, 비용을 감당할 수 있어도 인력이 없습니다.

**장벽 5: 실무 인사이트의 부재**

앞의 네 가지 장벽을 극복하더라도 마지막 장벽이 남습니다. LLM은 이론적 지식은 풍부하지만 특정 웹사이트의 실제 동작 방식, 예외 케이스 처리, 타이밍 이슈 등 실무에서만 얻을 수 있는 인사이트가 부재합니다. 이것이 80%는 되는데 20%에서 막히는 현상의 원인이며, 이 20%가 실제 운영 환경에서의 작동 여부를 결정합니다.

AI가 실행하지 못하므로 사람이 서비스들을 수동으로 연결해야 하는데, 서비스들은 사일로화되어 API가 필요하며, API가 없거나 제한적인 경우 전문 기술이 필요하고, 기술이 있어도 실무 인사이트가 없으면 결국 실패합니다. 하나를 해결해도 다른 장벽이 남아있으면 효과를 기대할 수 없습니다. 이것이 74%의 기업이 AI 투자에서 실패하는 구조적 이유입니다.

이러한 구조적 장벽이 만들어내는 악순환은 단순한 실패에서 그치지 않습니다. 반복되는 실패 경험은 조직 전반에 측정 가능한 피로 현상으로 확산됩니다.

### AI 피로감의 확산: 악순환의 결과

이 악순환의 핵심인 80-20 문제가 반복될 때 나타나는 현상은 단순한 불편함이 아닌, 측정 가능한 수준의 조직적 피로입니다. 기업들이 AI 도입을 시도하면 80%까지는 순조롭게 진행되지만, 마지막 20%에서 반복적으로 막히는 경험이 누적되면서 전방위적인 피로 현상으로 확산됩니다.

이 피로감은 먼저 개인 수준에서 나타납니다. Upwork의 2024년 조사에 따르면, 77%의 직원이 GenAI 도구가 생산성을 감소시키고 업무량을 오히려 증가시켰다고 응답했으며, GenAI 도구를 사용하는 직원 중 47%는 고용주가 기대하는 생산성 향상을 어떻게 달성해야 하는지조차 파악하지 못한다고 답했습니다[^11]. AI가 업무를 줄여주는 것이 아니라 관리해야 할 또 하나의 도구가 된 것입니다.

더욱 우려되는 것은 AI 사용 빈도와 번아웃의 상관관계입니다. Quantum Workplace의 2024년 조사에서는 AI 도구를 자주 사용하는 직원이 그렇지 않은 직원보다 45% 더 높은 번아웃률을 경험하는 것으로 나타났습니다[^13]. AI를 더 적극적으로 활용하려 할수록 오히려 더 지치는 역설적 상황이 발생하고 있습니다.

이러한 개인 수준의 피로는 조직 전체로 확산됩니다. DHR Global의 조사에 따르면, 북미, 아시아, 유럽의 지식 근로자 1,500명 중 82%가 번아웃 상태라고 보고했습니다[^12]. 이것은 더 이상 일부 직원의 문제가 아닌, 조직 전반의 현상입니다.

개인의 피로가 조직으로 확산되면 최종적으로 기업 수준의 포기로 이어집니다. S&P Global Market Intelligence의 2025년 조사에서는 AI 이니셔티브를 완전히 포기한 기업의 비율이 2024년 17%에서 2025년 42%로 급증했습니다[^5]. 1년 만에 포기율이 2.5배 증가한 것은 AI 피로감이 일시적 적응 과정이 아니라 구조적 문제임을 시사합니다.

이러한 AI 피로감의 상당 부분은 앞서 설명한 LLM의 80-20 문제에서 기인합니다. 80%까지는 빠르게 도달하지만, 나머지 20%를 해결하기 위한 반복적인 시행착오가 누적되면서 사용자를 지치게 만들고, 이 피로감이 개인에서 조직으로, 조직에서 기업 전략 수준으로 전이되어 결국 AI 도입 자체를 포기하게 만드는 것입니다.

이러한 구조적 문제에 대해 시장은 다양한 솔루션을 제시해왔으나, 모두 근본적 한계에 직면했습니다.

## 기존 솔루션의 한계

AI 실행 능력 부재로 시작되어 사일로화, API 제약, 기술 장벽을 거쳐 실무 인사이트 부재로 귀결되는 악순환. 시장의 기존 솔루션들은 이 악순환의 일부를 해결하려 했으나, 전체를 해결하지는 못했습니다.

### AI Provider 서비스 (ChatGPT, Claude, Gemini)

ChatGPT, Claude, Gemini 등의 생성형 AI 서비스는 텍스트 생성 영역에서 상당한 성능을 달성했으며, 최근에는 Function Calling, Custom GPT, MCP(Model Context Protocol) 등 외부 시스템과의 연동을 위한 기능도 제공하기 시작했습니다. MCP는 USB가 다양한 기기를 컴퓨터에 연결하듯, AI 모델이 다양한 외부 도구와 데이터를 표준화된 방식으로 연결할 수 있게 해주는 프로토콜입니다.

이러한 기능들이 문제를 해결한 것처럼 보이지만, 두 가지 본질적 한계가 존재합니다. 첫째, 이들 서비스의 실행 범위는 Provider가 사전에 연결해둔 시스템으로 제한되며, 사용자가 직접 MCP 서버를 구성하여 추가 시스템을 연결하려면 개발 지식이 필요합니다. MCP나 Function Calling을 통해 일부 실행이 가능하지만, Provider가 미리 연동해둔 서비스를 사용하거나 직접 개발하는 두 가지 선택지만 존재합니다. 예를 들어, 블로그 글을 작성해달라고 요청하면 초안이 나오지만, 사용자가 사용하는 특정 CMS는 Provider의 기본 연동 범위에 포함되지 않아 실제 발행은 여전히 사용자가 직접 해야 하거나, MCP 서버를 개발해야 하는 등 기술 장벽에 직면합니다. 둘째, 대규모 서비스를 운영하는 Provider들은 불가피하게 기능과 데이터를 'silo'화하며, 사용자의 구체적인 업무 흐름에 맞춘 세밀한 커스터마이징이 어렵습니다.

### 개발자용 AI 도구

더 높은 자유도를 제공하는 개발자용 도구도 검토해볼 필요가 있습니다. Cursor, Claude Code, Windsurf 등 터미널을 제어하고 로컬 파일 시스템에 접근할 수 있는 AI 도구들이 있습니다. 사용자가 원하는 방식으로 환경을 구성하고, AI에게 복잡한 작업을 지시할 수 있습니다. 이론적으로는 모든 것이 가능해 보입니다.

그러나 이 자유도는 양날의 검으로 작용합니다. 이러한 도구들은 개발 지식을 전제로 하고, 또한 정렬된 시스템이 부재하여 무엇을 어떻게 시켜야 하는지를 사용자가 스스로 파악하고 구조화해야 합니다. 높은 자유도는 높은 세팅 노고와 학습 비용으로 이어지며, 장벽 4(기술 장벽)가 해결된 것이 아니라 오히려 강화됩니다.

### 워크플로우 자동화 플랫폼

Zapier나 Make 같은 서비스는 수천 개의 SaaS 애플리케이션을 미리 연결해둔 커넥터를 제공함으로써 API 연동의 기술적 장벽을 상당 부분 낮췄습니다. 비개발자도 드래그 앤 드롭으로 자동화 워크플로우를 구축할 수 있습니다. 장벽 2(사일로화)를 부분적으로 해결한 것처럼 보입니다.

그러나 핵심적인 한계가 있습니다. 첫째, 워크플로우 자체를 AI가 관리하는 것이 아닙니다. 사용자는 여전히 플로우를 직접 설계하고, 오류 발생 시 알림을 받을 감시 체계를 세팅하고, 예외 상황에 대응해야 합니다. 둘째, API를 제공하지 않는 시스템, 많은 국내 서비스, 레거시 웹 시스템, 관리자 전용 페이지 등은 여전히 연동 범위 밖에 있습니다. 장벽 2(사일로화)는 부분 해결되었으나, 장벽 3(API 장벽)은 미해결이며, API가 있는 시스템만 연결할 수 있다는 근본적 제약은 그대로입니다.

### RPA 솔루션

UiPath, Automation Anywhere 등은 웹뿐 아니라 데스크톱 애플리케이션까지 UI 수준에서 자동화할 수 있다는 강점이 있습니다. API 장벽을 우회할 수 있다는 점에서 이론적으로는 가장 포괄적인 솔루션입니다.

그러나 현실은 다릅니다. AI 없이는 워크플로우 자동화 플랫폼보다 더 높은 기술적 장벽을 가집니다. 스크립트 작성, 화면 요소 인식 설정, 예외 처리 로직 구현 등 전문 인력이 필요합니다. 대상 시스템의 UI가 변경되면 자동화 스크립트를 재작성해야 하는 유지보수 부담이 따릅니다. 구축 비용과 기간 또한 중소기업이 감당하기 어려운 수준입니다. 연간 수천만원의 라이선스 비용, 수개월의 구축 기간이 필요하며, 장벽 4(기술 장벽)를 오히려 강화하는 결과를 초래합니다. 장벽 5(실무 인사이트)도 해결되지 않습니다. 매번 처음부터 구축해야 하기 때문입니다.

### 공통된 한계: 인력 병목 구조

이들 솔루션에는 공통된 특징이 있습니다. 본 백서에서는 이를 **인력 병목 구조(Human Bottleneck Structure)**라고 정의합니다. 자동화 도구가 도입되어도 세팅, 감시, 수습 등 핵심 운영이 여전히 인력에 종속되어 있는 구조를 의미합니다.

**공통 패턴 1**: AI가 똑똑해져도 세팅은 사람의 몫입니다. AI 챗봇이 아무리 발전해도, 그것을 업무에 연결하는 초기 설정은 사용자가 해야 합니다. 개발자 도구는 말할 것도 없고, 쉽다고 광고하는 워크플로우 플랫폼도 플로우 설계는 사용자 몫입니다.

**공통 패턴 2**: 자동화해도 감시는 사람의 몫입니다. 자동화가 작동하기 시작해도 오류 알림 체계를 세팅하고 예외 상황을 모니터링하며 문제 발생 시 대응해야 합니다. 자동화라는 이름이 무색하게 사람은 여전히 시스템을 지켜봐야 합니다.

**공통 패턴 3**: 실패하면 수습은 사람의 몫입니다. 80-20 문제가 발생했을 때 나머지 20%를 해결하는 것, 시스템 UI가 변경되었을 때 스크립트를 수정하는 것, 예외 케이스가 발생했을 때 판단하는 것 모두 사람이 처리해야 합니다.

도구만 바뀌었을 뿐, 인력 병목 구조는 전혀 변하지 않았습니다.

이것이 앞서 인용한 Upwork 통계, 77%의 직원이 AI가 업무량을 증가시켰다고 응답한 것의 구조적 원인입니다. AI 도입이 AI 활용으로 이어지지 않고, 오히려 관리해야 할 시스템이 추가로 증가한 것입니다.

더 근본적인 문제는 이 솔루션들이 실무 패턴을 축적하지 않는다는 점입니다. A 회사에서 구축한 자동화는 A 회사에서만 사용되며, B 회사가 비슷한 문제를 겪어도 처음부터 다시 구축해야 합니다. A 회사가 이 사이트는 이렇게 해야 작동한다는 것을 알아냈어도 그 지식은 A 회사에 갇혀 있어 실무에서 검증된 패턴이 축적되지도 공유되지도 않습니다. 모든 사용자가 같은 시행착오를 반복합니다.

### 기존 솔루션 종합 비교

| 솔루션 유형 | 접근 방식 | 해결하는 장벽 | 남는 장벽 | 핵심 한계 |
|----------|---------|------------|---------|---------|
| AI Provider | Function Calling, MCP | 장벽 1, 2 부분 해결 | 3, 4, 5 | Provider 틀에 종속 |
| AI 챗봇 | 텍스트 생성 및 조언 | 없음 | 1, 2, 3, 4, 5 | 실행 능력 부재 |
| 개발자 도구 | 터미널 제어, 코드 생성 | 장벽 1 해결 가능 | 2, 3, 4, 5 | 높은 기술 장벽 |
| 워크플로우 플랫폼 | API 연결, 드래그앤드롭 | 장벽 2 부분 해결 | 1, 3, 4, 5 | API 의존성 |
| RPA | UI 자동화, 스크립트 | 장벽 1, 3 해결 가능 | 2, 4, 5 | 과도한 비용/복잡성 |
| 공통 문제 | - | - | 장벽 5 (실무 패턴 축적) 미해결 | 매번 처음부터 시작 |

기존 솔루션들의 공통된 한계는 인력 병목 구조에 있습니다. EG-Desk는 이 구조 자체를 전환합니다.

## EG-Desk의 접근: AI Agent Scaffold

본 백서에서는 AI 실행 단절을 해소하기 위한 Agent Scaffold 아키텍처를 제안합니다. EG-Desk는 Provider가 정해둔 틀을 벗어나, 사람이 웹에서 할 수 있는 모든 것을 AI가 대신 할 수 있게 합니다. API가 없는 시스템이라도 브라우저 자동화로 직접 접근하며, 웹 인터페이스만 있으면 자동화가 가능합니다.

### Scaffold(비계)란

건축에서 비계는 건물마다 다르게 설계됩니다. 고층 빌딩과 저층 주택에 같은 비계를 세우지 않듯이, 건물의 특성에 맞춘 지지 구조가 있어야 작업자가 일할 수 있습니다.

EG-Desk의 AI Agent Scaffold도 마찬가지입니다. 표준화된 클라우드가 모든 사용자에게 동일한 환경을 제공하는 것과 달리, EG-Desk는 각 사용자의 업무 환경에 맞춰 구성됩니다. AI가 웹사이트를 조작하고 업무를 완료하는 실행 과정 전체를, 사용자 개인에게 맞춤화된 인프라가 지탱합니다. 이것이 Scaffold가 로컬 환경에 장착되는 이유입니다.

### 구조의 전환

기존 솔루션들의 공통된 실패는 인력 병목 구조에서 기인합니다. 기존 솔루션들은 사용자가 도구를 세팅하고, 도구가 작업을 실행하면, 사용자가 결과를 감시하고 유지보수하는 구조를 벗어나지 못했습니다.

EG-Desk는 이와 다른 접근을 취합니다. 사용자가 요구사항을 표현하면 시스템이 세팅과 실행을 모두 담당하며, 축적된 패턴을 통해 첫 시도에 성공합니다. 도구 설정과 유지보수의 부담이 사용자에서 시스템으로 이전되어, 사용자는 업무 자체에만 집중할 수 있습니다.

### 핵심 개념

AI Agent Scaffold의 핵심 아이디어는 AI가 사람처럼 웹 브라우저를 직접 조작하게 하는 것입니다. 사람이 웹사이트에 접속하여 로그인하고, 필요한 데이터를 입력하며, 버튼을 클릭하여 작업을 완료하듯이, AI 에이전트가 동일한 과정을 자동으로 수행합니다.

### 장벽별 해결 방식

| 장벽 | 기존 솔루션 | EG-Desk | 개선점 |
|------|----------|---------|-------|
| 장벽 1: AI 실행 능력 부재 | AI 챗봇: 텍스트만 생성, 실행은 사용자 몫 | 브라우저 자동화로 AI가 직접 실행 | 사용자가 복사-붙여넣기할 필요 없음 |
| 장벽 2: 서비스 사일로화 | 워크플로우 플랫폼: API가 있는 서비스만 연결 가능 | 통합 실행 환경에서 모든 웹 서비스를 단일 워크플로우로 연결 | API 존재 여부와 무관하게 연결 |
| 장벽 3: API 장벽 | Zapier, Make: API 없으면 자동화 불가능 | 브라우저 우선 접근으로 API 없는 시스템도 자동화 | 사람이 웹에서 할 수 있는 모든 것을 AI도 가능 |
| 장벽 4: 기술 장벽 | 개발자 도구, RPA: 프로그래밍 또는 전문 지식 필요 | 자연어 인터페이스 + 전담 인력 서비스로 기술 지식 불필요 | 자연어로 요청하면 완료 |
| 장벽 5: 실무 인사이트 부재 | 모든 솔루션: 매번 처음부터 구축, 80-20 문제 반복 | 검증된 워크플로우 축적으로 oneshot execution 지원 | 같은 시행착오를 반복하지 않음 |

핵심적인 차이는 장벽 5의 해결 방식입니다. 기존 솔루션들이 도구를 제공한다면 EG-Desk는 검증된 패턴을 제공합니다.

### 설계 원칙

**원칙 1: 기능이 아닌 인프라로서의 AI**

EG-Desk는 AI 존재를 가정하도록 핵심 인프라를 설계합니다. AI가 추가 기능이 아니라 시스템의 기본 전제입니다.

**원칙 2: API 독립적 데이터 모델**

웹 브라우저를 통한 직접 제어를 기본 표현으로 합니다. API는 있으면 활용하고, 없어도 작동합니다.

**원칙 3: 사용자 진입 장벽 제거**

EG-Desk는 두 가지 사용자 그룹을 고려합니다:

- B2C(개인 사용자): 업무 자동화가 필요한 개인을 위한 플랫폼. AI의 도움을 받아 미니앱을 커스터마이징하고 조합하여 개인화된 자동화 환경을 구성할 수 있습니다.

- B2B(기업 고객): 전담 서비스를 통한 완전 관리형 자동화. 기업은 별도의 기술 학습 없이 자연어로 요구사항을 전달하면, 전담 인력이 모든 구현을 담당합니다.

**원칙 4: 패턴 누적 효과(Pattern Accumulation Effect)**

기존 솔루션들은 매번 처음부터 시작합니다. EG-Desk는 패턴 누적 효과(Pattern Accumulation Effect)를 통해 이 한계를 극복합니다. 한 사용자의 시행착오가 Ontology에 구조화되어 저장되면, 이후 동일한 문제는 첫 시도에 해결됩니다. 개별 경험이 전체 생태계의 성공률 향상으로 전환되는 이 메커니즘이 EG-Desk의 핵심 경쟁력입니다.

이 구조화된 해결책을 저장하고 재사용하는 메커니즘이 EG-Desk의 Ontology입니다. EG-Desk의 Ontology는 아키텍처의 핵심이자, 앞서 분석한 다섯 가지 장벽 중 마지막 장벽(실무 인사이트 부재)을 해결하는 열쇠입니다.

## Ontology: 업무 맥락 지식 체계

EG-Desk의 설계 원칙 중 실무 패턴의 축적과 재사용을 가능하게 하는 핵심 메커니즘이 Ontology입니다. 이 섹션에서는 Ontology가 무엇이며, 어떻게 구성되고, 실제로 어떻게 작동하는지 설명합니다.

### Ontology란 무엇인가

EG-Desk의 Ontology - 업무 맥락 지식 체계는 단순한 개념 정의를 넘어, 실제 업무 자동화에 필요한 통합 지식 체계입니다.

전통적인 AI에서 Ontology는 개념과 관계의 정의를 의미하나, 실제 업무 자동화에서는 이것만으로 불충분합니다.

### 왜 필요한가: 마지막 20%의 해결책

LLM은 일반적인 업무의 80%까지 빠르게 도달하지만, 실제 운영 환경의 마지막 20%에서 반복적 조정이 필요합니다. 이 20%가 실패와 성공을 가릅니다.

일반 LLM이 마지막 20%에서 실패하는 이유는 실무 환경의 구체적 제약사항이 훈련 데이터에 존재하지 않기 때문입니다. 이 사이트는 로그인 후 3초 대기가 필요하다와 같은 정보는 실제로 업무를 수행해봐야만 얻을 수 있습니다.

문제는 이러한 실무 인사이트가 구조화되지 않으면 재사용할 수 없다는 점입니다. A 회사가 이 사이트는 이렇게 해야 작동한다를 알아내도, 그 지식이 담당자의 머릿속에만 있으면 B 회사는 같은 시행착오를 반복해야 합니다.

EG-Desk의 Ontology는 이 실무 인사이트를 구조화하여 저장하고 재사용할 수 있게 만듭니다. 패턴 누적 효과에 의해 한 번 겪은 시행착오는 Ontology에 기록되어, 같은 문제가 다시 발생했을 때 첫 시도에 성공하는 "oneshot execution"을 가능하게 합니다.

### 구성 요소: 4가지 지식 계층

Ontology는 업무 자동화에 필요한 네 가지 계층의 지식을 통합합니다.

첫째, 개념 정의(Business Context)는 시스템의 분류와 도메인 특성을 정의합니다. 금융 웹 서비스는 공동인증서 기반 인증과 다단계 보안을 사용한다는 도메인 지식이 여기에 포함됩니다.

둘째, 업무 규칙(Business Rule)은 조건부 판단 로직을 포함합니다. 입금 여부에 따라 청구용과 영수용을 구분하거나, 마감 시간대에 동시접속 제한을 적용하는 의사결정 규칙이 이에 해당합니다.

셋째, 실행 절차(Execution Logic)는 검증된 워크플로우를 단계별로 정의합니다. 로그인 후 3초 대기, 메뉴 클릭, 데이터 입력과 같은 구체적 실행 순서가 이 계층에 저장됩니다.

넷째, 운영 노하우(Operational Knowledge)는 실무에서만 얻을 수 있는 타이밍, 예외 케이스, 실무 팁을 포함합니다. 로그인 후 3초 대기가 보안 모듈 로딩을 위해 필요하다는 암묵지가 여기에 축적됩니다.

이 네 가지 계층이 통합되어 EG-Desk는 실제 업무에서 첫 시도에 성공합니다. 세금계산서 발행 사례를 통해 구체적으로 살펴보겠습니다.

### 자동화 사례: 세금계산서 발행

일반 LLM의 지식 범위:
- 세금계산서는 청구용과 영수용으로 구분된다 (개념적 이해)

Ontology의 지식 범위:
- 개념 정의: 세금계산서는 청구용과 영수용으로 구분되며, 각각 입금 전후에 발행된다
- 업무 규칙: 입금 여부 확인 결과에 따라 청구용 또는 영수용을 선택한다
- 실행 절차: 입금 내역 조회 -> 고객 확인 -> 유형 선택 -> 발행 버튼 클릭

이 세 가지 요소가 통합되어, EG-Desk는 세금계산서 발행 요청에 첫 시도에 성공합니다.

네 가지 계층으로 구성된 Ontology는 저장 위치와 접근 방식에서 기존 접근법과 다른 구조를 따릅니다.

### 분산 구조: 로컬과 클라우드의 결합

직관적인 해결책은 모든 데이터를 하나의 클라우드에 모으는 것처럼 보입니다. 그러나 이 접근은 두 가지 문제가 있습니다.

첫째, 새로운 사일로(Silo)를 생성합니다. 중앙화된 클라우드 서비스 자체가 또 하나의 격리된 시스템이 되어, 사용자는 해당 클라우드에 종속됩니다.

둘째, 표준화된 클라우드는 개인화와 보안을 동시에 만족할 수 없습니다. 각 기업과 개인은 고유한 환경을 가지며, 이를 중앙 서버로 통합하는 것은 비용 측면(커스터마이징)과 규제 측면(보안/컴플라이언스) 모두에서 실현 불가능합니다.

EG-Desk는 이 딜레마를 분산 저장 + AI 통합으로 해결합니다. Ontology는 두 가지 계층으로 분산됩니다.

로컬 Ontology(개인/기업 고유 맥락)는 사용자의 환경에 저장되며, 개인 선호(보고서 양식, 그래프 색상, 알림 빈도), 기업 내부 시스템 접근 정보, 관계 맥락(거래처별 특별 양식, 고객별 처리 방식), 보안이 필요한 업무 규칙을 포함합니다. 이러한 정보는 외부로 전송되지 않으며, 프라이버시가 보장됩니다.

클라우드 Ontology(검증된 공통 패턴)는 EG-Desk 클라우드에 저장되며, 업무 유형별 표준 절차(세금계산서 발행, 월말 결산), 검증된 실행 패턴(특정 웹사이트의 인증 플로우), 다른 사용자가 검증한 성공 패턴을 포함합니다. 이러한 지식은 모든 사용자가 재사용할 수 있습니다.

AI 브릿징(AI Bridging): AI 에이전트는 분산된 Ontology(로컬의 개인 맥락 + 클라우드의 검증된 패턴)를 실행 시점에 자동으로 통합합니다. 이를 AI 브릿징 메커니즘이라 합니다. 사용자가 "월말 보고서 만들어줘"라고 요청하면, AI는 클라우드에서 "월말 보고서" 표준 템플릿을 가져오고, 로컬에서 "나는 그래프를 파란색으로 선호", "CEO에게는 요약본만" 같은 개인 맥락을 가져와 자동으로 결합합니다. 사용자는 정보가 어디서 왔는지 알 필요 없이, 자신에게 최적화된 결과를 받습니다.

이러한 분산 구조가 실제 사용자 경험에서 어떻게 나타나는지 시나리오로 확인해 보겠습니다.

### 초개인화의 실제 동작: 시나리오

```
사용자: "월말 보고서 만들어줘"

AI Agent 동작:
1. 클라우드 Ontology: "월말 보고서" 표준 템플릿 검색
2. 로컬 Ontology: "나는 그래프를 파란 계열로 선호" 확인
3. 로컬 Ontology: "CEO에게는 요약본만, 팀장에게는 상세" 규칙 확인
4. AI가 자연스럽게 결합 → 맞춤형 보고서 생성

사용자 경험: Seamless (어디서 왔는지 몰라도 "내가 원하는 대로")
```

이것이 초개인화의 의미입니다. 공통 패턴(클라우드) + 개인 맥락(로컬) + AI 브릿징 = 사용자별 최적화된 결과.

개인 맥락은 로컬 Ontology에 저장되므로 외부로 전송되지 않으며, 공통 패턴은 클라우드 Ontology에서 모든 사용자가 활용합니다. 한 번 정의된 개인 맥락이 모든 워크플로우에 자동 적용되어, 분산된 설정 파일로 인한 관리 부채를 근본적으로 해결합니다.

이후 본 백서에서 Ontology는 로컬과 클라우드에 분산되어 AI가 통합하는 이 지식 체계를 의미합니다.

다음 섹션에서는 Ontology에 축적된 실무 지식이 미니앱을 통해 어떻게 사용자에게 전달되는지 설명합니다. 이어서 이를 지원하는 시스템 아키텍처를 다룹니다.

## Ontology와 미니앱: 실무 지식의 축적과 전달

앞 섹션에서 설명한 브라우저 자동화와 다중 AI 모델 통합이 EG-Desk의 실행 능력을 담당한다면, Ontology와 미니앱은 실무 지식의 축적과 전달을 담당합니다. 이 섹션에서는 Ontology에 축적된 실무 지식이 미니앱을 통해 어떻게 사용자에게 전달되는지, 그리고 왜 이것이 경쟁자가 복제할 수 없는 자산인지 설명합니다.

### Ontology: 실무 인사이트의 구조화

EG-Desk는 Ontology를 구축하여 실무 패턴을 구조화합니다. Ontology는 전담 기술 인력이 특정 시스템을 자동화하면서 얻은 실무 인사이트를 구조화한 통합 지식입니다.

Ontology 예시:

```
[개념 정의] - 시스템 분류와 특성
카테고리: 금융 웹 서비스
인증 방식: 공동인증서 기반
보안 특성: 다단계 인증, 시간 제약

[업무 규칙] - 조건부 판단 로직
- 계약금 발생 시: 입금 여부 확인 → 입금 완료면 영수용, 미입금이면 청구용
- 결산 시즌(3월/9월): 영수용 우선 확인 절차
- 고객 선호 양식: 개별 설정 자동 적용

[실행 절차] - 검증된 워크플로우
1. 메인 페이지 접근 및 보안 모듈 로드
2. 인증서 선택 (새 창 또는 팝업 처리)
3. 비밀번호 입력 (보안 키패드 처리)
4. 인증 완료 및 세션 관리
5. 업무 수행 (데이터 조회, 거래 실행 등)

[운영 노하우] - 실무 제약과 팁
- 동시 접속 제한 (특히 마감 시간대)
- 로그인 후 3초 대기 필요 (보안 모듈 로딩)
- 특정 시간대 서비스 중단 (야간, 주말)
- 결산 시즌: 추가 검증 단계 적용

[검증 이력] - 품질 보증
- 다수의 금융기관에서 반복 테스트
- 예외 케이스 수집 및 대응 방안 문서화
- 시간대별, 상황별 성공률 데이터 축적
```

이러한 Ontology는 실제 업무 환경에서 수십, 수백 번의 시행착오를 통해 축적됩니다.

### 미니앱: Ontology를 제품으로 만드는 메커니즘

Ontology가 업무의 무엇을, 왜, 어떻게에 대한 지식이라면, 미니앱은 이 지식을 사용자 인터페이스로 연결하는 접점입니다.

세금계산서 발행의 경우, Ontology는 입금 여부 확인 -> 유형 선택 -> 발행이라는 업무 플로우와 판단 규칙을 저장하고, 미니앱은 [입금확인] 버튼, [청구용/영수용] 선택 UI, [발행] 버튼으로 이를 시각화합니다. 사용자는 미니앱의 간단한 인터페이스만 보지만, 실제 자동화는 Ontology에 축적된 업무 지식으로 작동합니다.

이러한 분리는 미니앱을 경량화하여 빠른 개발과 수정을 가능하게 하며, Ontology의 재사용을 통해 동일한 업무 지식을 여러 인터페이스에 적용할 수 있게 합니다.

미니앱의 핵심 특성:

1. Ontology 연결 기반
- 미니앱 자체는 프론트엔드 UI (입력/출력 인터페이스)
- 실제 로직과 지식은 Ontology에 존재
- 여러 미니앱이 동일한 Ontology를 공유 가능

2. 모듈화와 초개인화
- 미니앱끼리 조합 가능
- Ontology와의 다양한 조합으로 맞춤형 워크플로우 구성
- 사용자가 직접 미니앱 수정 가능 (HTML/CSS/JS 기반)

3. AI 기반 개발 및 커스터마이징
- 미니앱 제작 과정 전체에 AI 활용
- 오픈소스 기반으로 커뮤니티 기여 촉진

Ontology에서 미니앱으로의 생성 과정:

```
1. 기술 담당자의 시스템 통합: 금융 업무 자동화 반복 구현 → 실패 원인 분석 → 해결 패턴 도출
    ↓
2. Ontology 구축: 인증 플로우, 시간 제약, 양식 요구사항 등 체계화
    ↓
3. 고객 담당자가 UI 제작: 입력 폼 + 결과 뷰어 (AI 도움으로 빠르게 제작)
    ↓
4. 미니앱 등록: 클라우드 저장 → 모든 담당자 재사용 가능
    ↓
5. 사용자 커스터마이징: 필요시 AI 도움받아 개인화
    ↓
6. Oneshot execution: 다른 사용자 동일 요청 → 미니앱 활용 → 첫 시도 성공
```

### 왜 미니앱인가: 프론트엔드 로직의 극소화

EG-Desk 아키텍처에서 미니앱의 프론트엔드 코드는 극도로 최소화됩니다. 플랫폼 레이어가 복잡한 일을 모두 처리하고, 미니앱 프론트엔드에는 최소한의 역할만 남기 때문입니다.

전통적인 웹/모바일 앱:

```
UI/UX (복잡) → 비즈니스 로직 (복잡) → 상태 관리 (복잡)
→ API 호출 로직 (복잡) → 데이터 검증 (복잡) → 백엔드 API (복잡)

결과: 프론트엔드만 수만 줄의 코드
개발 기간: 수개월
유지보수: 지속적 투자 필요
크로스 플랫폼: iOS/Android/Web 각각 별도 개발
```

EG-Desk 미니앱:

```
뷰어 (View만) - 최소한의 HTML+CSS → 요청자 (Request 트리거만) - 간단한 JS
    ↓
[EG-Desk 플랫폼 레이어가 처리]
AI 에이전트 (추론, 의사결정) → 브라우저 컨트롤 (실행) → Ontology (도메인 지식, 로직)

결과: 프론트엔드 코드: 수백 줄
개발 기간: 수일
유지보수: 최소
크로스 플랫폼: HTML 기반으로 자동 지원
```

#### 미니앱 프론트엔드의 두 가지 역할

EG-Desk가 브라우저 컨트롤과 Ontology를 담당하기 때문에, 미니앱 프론트엔드에는 뷰어(Viewer)와 요청자(Requester) 역할만 남습니다:

- 뷰어(Viewer): 사용자에게 정보를 표시하는 최소한의 UI. 플랫폼에서 전달받은 결과를 단순히 표시합니다.

- 요청자(Requester): 사용자의 요청을 EG-Desk 플랫폼으로 전달하는 트리거. 버튼 클릭이나 폼 제출을 플랫폼 호출로 변환합니다.

비즈니스 로직, 상태 관리, 데이터 검증, API 호출, 에러 처리 등 복잡한 처리는 모두 AI 에이전트 + Ontology + 브라우저 컨트롤 조합이 담당합니다.

#### 크로스 플랫폼 자동 지원

미니앱이 극도로 가벼운 HTML 기반이기 때문에, 별도의 개발 없이 모든 플랫폼에서 동작합니다:
- PC (Windows/Mac/Linux): EG-Desk 데스크톱 앱 내 브라우저 뷰로 표시
- Android: HTML 파일 다운로드 후 기본 브라우저로 열기
- iOS: EG-Desk 클라우드 호스팅 + Tunneling으로 서빙

| 지표 | 전통 앱 | EG-Desk 미니앱 | 개선 |
|------|--------|--------------|------|
| 프론트엔드 코드량 | 수만 줄 | 수백 줄 | 100배 감소 |
| 복잡도 | 높음 | 극히 낮음 | 진입 장벽 제거 |
| 제작 시간 | 수개월 | 수일 | 30배 단축 |
| 유지보수 부담 | 지속적 | 최소 | 운영 비용 절감 |
| 크로스 플랫폼 | 별도 개발 필요 | 자동 지원 | 개발 비용 3분의 1 |
| 필요 전문성 | 풀스택 개발자 | 기본 HTML/CSS 지식 | 인력 요건 완화 |

미니앱 예시: 금융 데이터 추출 및 보고서 생성

```
[기본 정보]
이름: financial-data-reporter
카테고리: 재무/회계 자동화
생성 배경: 회계법인 월말 결산 업무 자동화

[연결된 Ontology]
- financial-auth-system: 금융 시스템 인증 처리
- data-extraction: 다중 소스 데이터 수집
- report-generator: 맞춤형 보고서 생성
- approval-workflow: 다중 채널 승인 프로세스

[입력]
- 데이터 조회 기간
- 보고서 양식 선택
- 발행 채널 (WordPress, 이메일 등)

[출력]
- 정리된 데이터 파일
- 맞춤 양식 보고서
- 실행 로그 및 결과 알림

[활용 특징]
- 고객사별 양식 맞춤 설정 가능
- 다른 미니앱과 조합하여 확장 워크플로우 구성 가능
- 사용자가 AI 도움받아 개인화 가능
```

### 미니앱의 활용 범위

한 고객사에서 만들어진 미니앱은 동일한 문제를 겪는 모든 고객에게 즉시 적용됩니다.

```
A 회계법인: "월말 결산 보고서 자동화가 필요합니다"
    → 담당자가 미니앱 개발 (시행착오 끝에 성공) → 미니앱 등록: financial-data-reporter

B 세무사무소: "월말 결산 보고서 자동화가 필요합니다" → 기존 미니앱 즉시 적용 (oneshot)

C 법무법인: "월말 결산 보고서 자동화가 필요합니다" → 기존 미니앱 즉시 적용 (oneshot)

D 자산운용사: "월말 결산 보고서 자동화가 필요합니다" → 기존 미니앱 즉시 적용 (oneshot)
```

A 회계법인이 겪은 시행착오를 B, C, D가 겪을 필요가 없다는 것이 EG-Desk의 차별점입니다.

### 왜 복제 불가능한가

경쟁자가 EG-Desk를 따라하려 할 경우, Playwright, Electron, OpenAI API 등 기술 스택은 모두 공개된 기술이므로 복제할 수 있지만 Ontology와 미니앱은 복제할 수 없습니다.

첫째, 실무 지식은 체득해야 합니다. 전담 기술 인력이 수백, 수천 개의 다양한 업무를 자동화하면서 배운 인사이트는 실제로 겪어봐야만 얻을 수 있습니다.

둘째, 암묵지(Tacit Knowledge)는 문서화할 수 없습니다. 이 고객사는 이 시간대에 이 양식으로 보고해야 하고 담당자 A는 이렇게 커뮤니케이션해야 원활하다는 것은 직접 겪어본 담당자만 알 수 있습니다.

셋째, 전담 인력 시스템은 복제할 수 없습니다. 결과물(미니앱)은 볼 수 있지만 그 뒤에 있는 인력 네트워크와 Ontology 축적 시스템은 보이지 않습니다.

핵심은 전담 인력 시스템입니다. 실무에서 지속적으로 패턴을 생산하고 공유하는 시스템이 작동하는 한, 정보의 격차는 시간이 지날수록 벌어집니다.

지금까지 Ontology가 어떻게 미니앱으로 제품화되는지 살펴보았습니다. 다음 섹션에서는 이를 지원하는 핵심 기술 아키텍처를 설명합니다.

#### 계층 분리의 근거

4개 계층으로 분리한 이유는 세 가지입니다. 이 세 가지 특성이 결합되어 각 계층이 독립적으로 관리되면서도 실행 시점에 유연하게 조합될 수 있는 구조가 완성됩니다.

사용자 접근 방식의 차이: 지식의 성격에 따라 사용자의 접근 방식이 상이합니다. 사용자 맥락(Dimension 1)의 경우, 사용자가 자신의 로컬 환경에서 즉시 작업을 시작할 수 있어야 하므로 로컬 저장이 적합합니다. 반면 시스템 패턴, 도메인 지식, 워크플로우(Dimension 2-4)는 다른 사용자들이 검증한 패턴의 재사용이 가능해야 하므로 클라우드 기반 공유가 효과적입니다. 이러한 분리 구조를 통해 사용자는 자신의 상황에 적합한 시작점을 자유롭게 선택할 수 있습니다.

변경 주기의 차이: 이러한 시작점 분리와 함께, 각 계층의 지식은 상이한 주기로 갱신됩니다. 개인 선호는 수시로 조정되고, 시스템 패턴은 대상 시스템의 업데이트 시점에 갱신되며, 도메인 지식은 법규나 업무 규칙의 변경 시에만 수정됩니다. 계층 분리를 통해 변경의 영향 범위를 최소화하는 것이 가능합니다.

독립성과 재사용성: 접근 방식과 변경 주기가 다르기 때문에, Dimension 1-3은 각각 독립적인 지식 단위로 구성됩니다. 워크플로우(Dimension 4)는 이러한 지식 단위들을 필요에 따라 유연하게 조합하여 활용할 수 있습니다. 이 구조적 특성으로 인해 하나의 지식 자산이 다수의 워크플로우에서 재사용될 수 있으며, 이는 EG-Desk 생태계 전체의 효율성 향상에 기여합니다.

#### Dimension 1: 사용자 맥락 (User Context)

사용자(개인 또는 조직)에 특화된 맥락 정보를 포함합니다. 거래처별 양식 요구사항, 내부 승인 체계, 알림 채널 선호 등이 이에 해당합니다. 동일한 업무라 하더라도 Dimension 1의 설정에 따라 최종 결과물의 개인화가 이루어집니다. 예를 들어, "A거래처는 품명을 상세히, B거래처는 간략하게"와 같은 설정이 여기에 저장됩니다.

#### Dimension 2: 시스템 패턴 (System Pattern)

특정 웹 시스템의 실제 동작 방식에 관한 지식을 체계화합니다. 로그인 후 필요한 대기 시간, 팝업 처리 순서, 인증 플로우, 시스템 점검 시간대 등 해당 시스템의 자동화 경험을 통해서만 획득 가능한 인사이트가 여기에 포함됩니다. 예를 들어, "홈택스는 로그인 후 3초 대기 필요, 보안 프로그램 팝업은 '다음에' 클릭"과 같은 패턴이 축적됩니다. 이러한 지식은 LLM의 훈련 데이터에 포함되어 있지 않으며, 직접적인 실행 경험을 통해서만 축적될 수 있는 암묵적 지식에 해당합니다.

#### Dimension 3: 도메인 지식 (Domain Knowledge)

특정 시스템에 종속되지 않는 업무 고유의 규칙을 정의합니다. 세금계산서의 청구용/영수용 구분 기준, 발행 기한 규정, 계산 공식 등 처리 시스템과 무관하게 동일하게 적용되는 비즈니스 로직이 이에 해당합니다. 예를 들어, "입금 확인 전 발행은 청구용, 입금 확인 후 발행은 영수용"이라는 규칙은 홈택스든 어느 시스템이든 동일하게 적용됩니다. 법규, 회계 기준 등 공식적인 규칙이 여기에 포함됩니다.

#### Dimension 4: 워크플로우 (Workflow Composition)

Dimension 1-3의 지식을 특정 순서와 조건에 따라 조합한 실행 패턴을 구성합니다. 각 단계에서 참조할 지식, 분기 조건, 예외 상황 처리 방식이 이 계층에서 정의됩니다. 실제 환경에서 검증된 성공적 실행 순서를 담고 있으며, 이러한 구조가 oneshot execution을 가능하게 하는 필수 요소입니다.

구체적인 예시를 통해 Dimension 4의 작동 방식을 살펴보겠습니다:

```
Dimension 4: 세금계산서 발행 워크플로우

Step 1: 입금 확인
        -> Dimension 3 참조 (청구용/영수용 판단 규칙)
        -> 결과에 따라 다음 단계 분기

Step 2: 홈택스 로그인
        -> Dimension 2 참조 (3초 대기, 팝업 처리, 인증서 플로우)

Step 3: 정보 입력
        -> Dimension 3 참조 (공급가액, 부가세 계산)
        -> Dimension 1 참조 (거래처별 특별 양식)

Step 4: 발행
        -> Dimension 2 참조 (발행 버튼 위치, 확인 팝업 처리)

Step 5: 후속 작업
        -> Dimension 1 참조 (Slack 알림, PDF 저장 경로)
```

동일한 Dimension 1-3 지식이라도 Dimension 4의 조합 방식에 따라 다른 업무가 됩니다. 예를 들어, "청구용 세금계산서 발행"과 "영수용 세금계산서 발행"은 동일한 시스템 패턴(Dimension 2: 홈택스 로그인, 공동인증서 처리, 공급자/공급받는자 정보 입력)과 도메인 지식(Dimension 3: 공급가액 계산, 발행 기한 규정)을 사용합니다. 차이점은 Step 1에서 발생합니다: 대금을 아직 받지 않은 외상거래 상태라면 "청구용"으로, 현금/카드/계좌이체 등으로 이미 입금이 확인된 상태라면 "영수용"으로 분기하여 Step 4의 발행 유형 선택이 달라집니다. 마찬가지로, "세금계산서 발행"과 "세금계산서 수정"도 동일한 Dimension 1-3 지식을 공유하지만, 수정 워크플로우는 Dimension 4에서 추가 단계가 정의됩니다: 기존 계산서 조회 후 수정 사유(기재사항 착오정정, 공급가액 변동, 환입, 계약 해제 등)를 선택하고, 음(-) 세금계산서로 원본을 취소한 뒤 정(+) 세금계산서를 재발행하는 절차입니다. 이처럼 조합 패턴이 축적될수록 새로운 업무 요청에 대한 대응 속도가 빨라집니다.

### 분산 저장 아키텍처: 두 개의 시작점

Ontology가 로컬과 클라우드 양쪽에 분산 저장되는 근본적 이유는 사용자의 시작점이 두 가지로 구분되기 때문입니다. 이는 로컬과 클라우드의 단순한 이분화가 아니라, 어느 쪽에서 시작하더라도 모든 지식에 접근할 수 있는 이중 지원 구조를 의미합니다.

시작점 1 - 사용자 환경 기반 시작(로컬 Ontology)

사용자가 자신의 로컬 환경에서 업무를 시작하는 경우에 해당합니다. 사용자의 파일, 설정, 선호가 이미 로컬에 저장되어 있어 즉시 활용이 가능합니다. 별도의 업로드나 변환 과정 없이 즉각적인 작업 착수가 가능하며, 거래처별 양식, 내부 승인 체계, 알림 채널 선호 등 개인화된 맥락이 이 범주에 포함됩니다.

시작점 2 - 검증된 패턴 기반 시작(클라우드 Ontology)

사용자가 다른 사용자들에 의해 이미 검증된 워크플로우를 기반으로 시작하는 경우에 해당합니다. "홈택스 세금계산서 발행"과 같이 다수의 사용자가 공통적으로 수행하는 업무의 경우, 이미 시행착오를 거쳐 최적화된 해결책이 구축되어 있습니다. 처음부터 새로 구축할 필요 없이 검증된 패턴을 즉시 활용할 수 있습니다.

핵심 메시지 - 시작점에 관계없는 완전한 지원

로컬이든 클라우드든, EG-Desk는 사용자에게 완전한 지원을 제공합니다. 개인 환경에서 시작하는 것과 검증된 패턴에서 시작하는 것 모두 동등하게 지원되며, AI 브릿징을 통해 로컬과 클라우드 Ontology가 자동으로 통합됩니다.

- Dimension 1(로컬): 개인/조직 내부에서만 사용. 사용자가 자신의 환경에서 즉시 작업을 시작할 수 있도록 로컬에 저장됩니다.
- Dimension 2-4(클라우드): 모든 사용자와 공유. 검증된 시스템 패턴, 도메인 지식, 워크플로우를 재사용하여 시행착오 없이 바로 성공할 수 있습니다.

AI 브릿징을 통해 AI 에이전트는 로컬과 클라우드 Ontology를 연결합니다. 앞서 살펴본 세금계산서 발행 워크플로우를 실제로 실행할 때, AI 에이전트는 다음과 같이 동작합니다:

```
AI Agent 동작:
1. 클라우드에서 Dimension 4 워크플로우 검색 ("세금계산서 발행")
2. Dimension 3 참조: 청구용/영수용 판단 규칙 로드
3. Dimension 2 참조: 홈택스 자동화 패턴 로드
4. 로컬에서 Dimension 1 참조: 거래처별 양식, 후속 작업 설정
5. 4개 차원 결합하여 실행

사용자 경험: "세금계산서 발행해줘" -> 완료
```

사용자는 정보의 출처를 인지할 필요 없이 자신에게 최적화된 결과를 제공받습니다. 검증된 패턴을 기반으로 시작하고자 하는 경우 클라우드의 공통 지식(Dimension 2-4)을 활용하고, 개인 환경을 기반으로 시작하고자 하는 경우 로컬의 사용자 맥락(Dimension 1)을 즉시 활용할 수 있습니다. AI 브릿징을 통해 양측의 지식이 자동으로 통합되어 개인화된 결과가 제공됩니다.

### Ontology의 효과: Oneshot Execution

Ontology 체계의 가장 중요한 효과는 패턴 누적 효과에 있습니다. 개인이 시행착오를 통해 획득한 지식이 전체 사용자 집단에 의해 공유되고 활용될 수 있는 구조가 형성됩니다.

기존 LLM 기반 자동화 환경에서는 각 사용자가 독립적으로 동일한 시행착오를 반복해야 합니다. 사용자 A가 특정 시스템의 예외 케이스를 발견하더라도 사용자 B는 동일한 과정을 처음부터 경험해야 합니다. 이러한 구조가 앞서 분석한 80-20 문제가 개인 수준에서 조직 수준으로 확산되는 메커니즘입니다.

EG-Desk의 Ontology(업무 지식 체계)는 이러한 구조적 한계를 근본적으로 전환합니다. 최초 사용자(또는 전담 인력)가 문제를 해결하면 해당 패턴이 Ontology에 저장되며, 이후 동일한 요청을 수행하는 사용자는 축적된 패턴을 활용하여 시행착오 없이 성공할 수 있습니다. 이것이 "oneshot execution"의 핵심이며, 패턴 누적 효과에 의해 사용자 증가에 비례하여 EG-Desk 생태계 전체의 성공률이 향상됩니다.

Ontology는 지식의 저장과 조합을 담당하는 체계입니다. 그렇다면 이러한 지식이 사용자에게 어떻게 전달될까요? 그 인터페이스가 바로 미니앱입니다. 미니앱이란 스마트폰의 앱처럼 특정 업무에 특화된 경량 애플리케이션으로, 복잡한 자동화 로직을 간결한 버튼과 화면 뒤에 숨기고 사용자에게는 직관적인 인터페이스만 제공합니다.

## Ontology와 미니앱: 실무 패턴의 축적

Ontology가 업무의 무엇을, 왜, 어떻게에 대한 지식이라면, 미니앱은 이 지식을 사용자 인터페이스로 연결하는 접점입니다.

### 미니앱이란 무엇인가

세금계산서 발행을 다시 예로 들어보겠습니다.

```
Ontology에 저장된 것:
- Dimension 2: 홈택스 자동화 패턴 (3초 대기, 팝업 처리, 인증 플로우)
- Dimension 3: 업무 규칙 (청구용/영수용 판단)
- Dimension 4: 검증된 실행 순서

미니앱이 제공하는 것:
- [거래처 선택] 드롭다운
- [입금 확인] 버튼 -> 자동으로 청구용/영수용 판단
- [발행] 버튼 -> 홈택스 자동화 실행
- 결과 화면: 발행 완료, PDF 저장됨, Slack 알림 완료
```

사용자에게는 미니앱의 간결한 인터페이스만 노출됩니다. 몇 개의 버튼과 결과 화면으로 구성된 단순한 화면이지만, 그 이면에서는 4개 차원의 Ontology가 유기적으로 조합되어 작동하므로 사용자는 복잡한 로직을 의식하지 않고도 원하는 결과를 얻을 수 있습니다.

### 미니앱과 워크플로우의 관계

미니앱은 Dimension 4 워크플로우 전체가 아니라 워크플로우를 구성하는 "노드(작은 단위)"에 해당하는데, 이 구분을 이해하면 EG-Desk 아키텍처의 유연성을 파악할 수 있습니다.

```
미니앱 = 작은 단위의 업무
- 단일 목적 (예: "세금계산서 발행", "입금 확인")
- 사용자 인터페이스 있음 (버튼, 입력 폼)
- 독립적으로 실행 가능

Dimension 4 워크플로우 = 여러 미니앱의 조합
- 복합 프로세스 (예: "월말 결산 전체")
- 여러 미니앱을 순서대로 연결
- 자동 또는 스케줄 실행
```

월말 결산 프로세스를 예로 들면:

```
[Dimension 4 워크플로우: "월말 결산"]
|
+-- Step 1: 입금 확인 -----------> 미니앱 A
|
+-- Step 2: 세금계산서 발행 -----> 미니앱 B (반복 호출)
|
+-- Step 3: 회계 기록 -----------> 미니앱 C
|
+-- Step 4: 보고서 생성 ---------> 미니앱 D
```

이 구조의 주요 장점은 재사용성입니다. "세금계산서 발행" 미니앱은 "월말 결산" 워크플로우에서도, "분기 정산" 워크플로우에서도 호출할 수 있고, 사용자가 단독으로 직접 실행하는 것도 가능합니다. 이처럼 미니앱은 모듈화된 구성 요소이기 때문에 다양한 워크플로우에 유연하게 조합할 수 있습니다.

### 미니앱의 기술 구조

미니앱은 경량 HTML 페이지로 구현됩니다. 복잡한 네이티브 앱 대신 웹 기반 인터페이스를 선택한 이유는 개발 속도, 유지보수 용이성, 플랫폼 호환성 세 가지입니다.

빠른 제작과 유연한 수정

HTML/CSS/JavaScript만으로 UI를 구성하므로, 전문 앱 개발자 없이도 빠르게 미니앱을 제작할 수 있습니다. 업무 요구사항이 변경되면 HTML 파일만 수정하면 되므로, 앱 스토어 배포 과정 없이 즉시 반영이 가능합니다.

복잡도의 분리

미니앱 자체에는 비즈니스 로직이 포함되지 않습니다. API 호출, 데이터 검증, 에러 처리, 브라우저 자동화 같은 복잡한 처리는 모두 EG-Desk 플랫폼이 담당하므로, 미니앱은 오직 두 가지 역할만 수행하면 됩니다:

- 뷰어(Viewer): 플랫폼이 처리한 결과를 화면에 표시
- 요청자(Requester): 사용자의 클릭을 플랫폼 호출로 변환

이러한 분리 구조 덕분에 전통적인 앱이 수만 줄의 코드를 필요로 하는 반면, EG-Desk 미니앱은 수백 줄의 HTML/CSS만으로도 동일한 기능을 제공할 수 있습니다.

크로스 플랫폼 호환성

HTML 기반이므로 Windows, Mac, Linux 데스크톱은 물론 Android, iOS 모바일 기기에서도 별도 개발 없이 동작하며, 플랫폼별 접근 방식은 다음과 같습니다:

- PC (Windows/Mac/Linux): EG-Desk 데스크톱 앱 내 브라우저 뷰로 표시
- Android: HTML 파일 다운로드 후 기본 브라우저로 열기
- iOS: EG-Desk 클라우드 호스팅을 통한 접근

### 미니앱의 세 가지 사용 방식

앞서 설명한 HTML 기반 구조 덕분에 미니앱은 자동화 수준에 따라 세 가지 사용 방식을 지원하며, 사용자는 상황에 맞게 선택할 수 있습니다.

#### 방식 1: 완전 자동 - 알아서 해줘

정형화된 반복 작업의 경우 워크플로우가 미니앱들을 자동으로 연결하여 실행합니다.

```
시나리오: 매월 1일 정기 결산

Workflow 자동 시작 (스케줄)
    -> 미니앱 A 호출 (입금 확인)
    -> 미니앱 B 호출 (세금계산서 발행) x 47건
    -> 미니앱 C 호출 (회계 기록)
    -> 완료 알림: "월말 결산 완료. 세금계산서 47건 발행됨."

사용자 개입: 없음
아침에 출근하면 이미 완료되어 있음
```

이 방식은 업무 패턴이 충분히 축적되어 예외 상황이 거의 없을 때 적용할 수 있으며, 사용자 개입 없이 작업이 완료됩니다.

#### 방식 2: 반자동 - 이것만 확인해줘

대부분의 과정은 자동으로 진행되지만, AI가 독자적으로 판단하기 어려운 상황에서는 사용자에게 확인을 요청하여 의사결정을 받습니다.

```
시나리오: 자동 결산 중 판단이 필요한 순간

Workflow 자동 진행 중
    -> 미니앱 B 실행 (세금계산서 발행)
    -> AI: "이 거래처는 프로모션 할인이 적용됩니다.
           할인 적용된 금액으로 발행할까요?"
    -> 미니앱 UI 오픈 -> 사용자가 [예/아니오] 선택
    -> Workflow 재개
    -> 나머지 46건 자동 처리
    -> 완료

사용자 개입: 최소 (판단이 필요한 순간만)
```

이러한 메커니즘을 Graceful Fallback이라고 명명합니다. 자동 실행이 중단되거나 판단이 필요한 시점에서 시스템 전체가 정지하는 대신, 해당 단계에서만 사용자 개입을 요청하고 해결 후 자동으로 프로세스가 재개되기 때문에 작업 흐름이 끊기지 않습니다.

#### 방식 3: 직접 실행 - 이번에는 내가 할게

워크플로우를 거치지 않고 미니앱을 직접 실행하는 방식으로, 특수한 케이스나 복잡한 맥락, 긴급한 상황에서 유연하게 대응할 수 있습니다.

```
시나리오: 신규 거래처에 특별 조건으로 발행

사용자: 미니앱 직접 열기
    -> 거래처 정보 직접 입력
    -> 특별 할인율 설정
    -> 비고란에 특이사항 기재
    -> [발행] 클릭
    -> 완료

사용자 개입: 전체
표준 패턴에서 벗어나는 경우에 유연하게 대응
```

### 양방향 흐름: 점진적 자동화와 Graceful Fallback

이 세 가지 방식은 고정된 것이 아니라 상황에 따라 유연하게 전환됩니다.

```
    점진적 자동화 -->
수동 <--------------------> 자동
    <-- Graceful Fallback
```

점진적 자동화: 초기에는 방식 3(직접 실행)으로 시작하여 모든 과정을 수동으로 수행하면서 패턴을 파악합니다. 패턴이 식별되기 시작하면 방식 2(반자동)로 전환하여 대부분을 자동화하되 예외 상황에 대해서는 확인을 받습니다. 충분한 안정화가 이루어지면 방식 1(완전 자동)로 전환할 수 있습니다.

Graceful Fallback: 완전 자동(방식 1)으로 운영 중 예외 상황이 발생하면 해당 단계에서 사용자 개입(방식 2)을 요청합니다. 해결 후에는 프로세스가 자동으로 재개됩니다. 특히 주목할 점은, 이러한 예외 상황의 해결 방법이 Ontology에 축적된다는 것입니다. 동일한 상황이 재발하는 경우 자동 처리가 가능해집니다.

이러한 양방향 흐름이 EG-Desk의 근본적인 메커니즘입니다. 처음부터 완벽한 자동화를 추구하는 대신, 사용 과정에서 점진적으로 자동화 수준을 높여가면서 예외 상황에도 유연하게 대응합니다. 그 결과, 사용량이 증가할수록 시스템의 정확도와 효율성이 함께 개선됩니다.

### 미니앱의 생성 과정

EG-Desk에서는 전담 인력이 고객의 업무를 자동화하는 과정에서 미니앱이 자연스럽게 생성되는데, 이 과정을 단계별로 살펴보면 다음과 같습니다.

```
1. 기술 담당자의 시스템 통합
   -> 금융 업무 자동화 반복 구현
   -> 실패 원인 분석 -> 해결 패턴 도출
   -> Dimension 2 (시스템 패턴) 축적
       |
       v
2. Ontology 구축
   -> Dimension 2: 인증 플로우, 시간 제약, 팝업 처리
   -> Dimension 3: 업무 규칙 (청구용/영수용 판단)
   -> 클라우드에 저장
       |
       v
3. 고객 담당자가 UI 제작
   -> 입력 폼 + 결과 뷰어 (AI 도움으로 빠르게 제작)
   -> 미니앱 등록: 모든 담당자 재사용 가능
       |
       v
4. 사용자 커스터마이징
   -> Dimension 1 설정: 거래처별 양식, 후속 작업
   -> 로컬 Ontology에 저장
       |
       v
5. Dimension 4 Workflow 구성 (선택)
   -> 여러 미니앱을 연결하여 복합 프로세스 구성
   -> 자동/스케줄 실행 설정
       |
       v
6. 실행 경로 선택
   -> 경로 1: Dimension 4에서 완전 자동 호출
   -> 경로 2: 반자동 (Graceful Fallback)
   -> 경로 3: 직접 실행
```

### 미니앱이 가능한 이유

EG-Desk의 미니앱이 실제로 미니한 규모를 유지할 수 있는 이유는 복잡한 처리를 플랫폼이 전담하기 때문입니다. 비즈니스 로직, API 호출, 데이터 검증, 에러 처리를 AI 에이전트와 Ontology가 모두 담당하므로, 미니앱에는 UI만 구현하면 됩니다.

```
전통적인 앱:
UI/UX → 비즈니스 로직 → 상태 관리 → API 호출 → 데이터 검증 → 백엔드 API
(모든 계층이 복잡, 프론트엔드만 수만 줄)

EG-Desk 미니앱:
뷰어(View) + 요청자(Request 트리거)
    ↓
[플랫폼이 처리: AI 에이전트 + 브라우저 컨트롤 + Ontology]
(프론트엔드 수백 줄)
```

미니앱 프론트엔드에는 두 가지 필수 역할만 구현됩니다:

- 뷰어(Viewer): 결과를 표시하는 화면
- 요청자(Requester): 실행을 시작하는 버튼

이외의 복잡한 처리는 전적으로 플랫폼이 담당합니다.

#### 크로스 플랫폼 자동 지원

미니앱이 경량 HTML 기반으로 구현되어 있으므로 별도의 개발 과정 없이 모든 플랫폼에서 동작하며, 구체적인 접근 방식은 다음과 같습니다:
- PC (Windows/Mac/Linux): EG-Desk 데스크톱 앱 내 브라우저 뷰로 표시
- Android: HTML 파일 다운로드 후 기본 브라우저로 열기
- iOS: EG-Desk 클라우드 호스팅 + Tunneling으로 서빙

| 지표 | 전통 앱 | EG-Desk 미니앱 | 개선 |
|------|--------|--------------|------|
| 프론트엔드 코드량 | 수만 줄 | 수백 줄 | 100배 감소 |
| 복잡도 | 높음 | 극히 낮음 | 진입 장벽 제거 |
| 제작 시간 | 수개월 | 수일 | 30배 단축 |
| 유지보수 부담 | 지속적 | 최소 | 운영 비용 절감 |
| 크로스 플랫폼 | 별도 개발 필요 | 자동 지원 | 추가 개발 불필요 |
| 필요 전문성 | 풀스택 개발자 | 기본 HTML/CSS 지식 | 인력 요건 완화 |

*주: 위 비교는 전통적인 풀스택 웹 애플리케이션과 EG-Desk 미니앱(경량 HTML 기반 뷰어)의 구조적 차이를 나타냅니다. 실제 수치는 프로젝트 복잡도에 따라 달라질 수 있습니다.*

### 미니앱 예시: 금융 데이터 추출 및 보고서 생성

실제로 운영 중인 미니앱의 구조를 살펴보겠습니다.

```
[기본 정보]
이름: financial-data-reporter
카테고리: 재무/회계 자동화
생성 배경: 회계법인 월말 결산 업무 자동화

[연결된 Ontology]
- financial-auth-system: 금융 시스템 인증 처리
- data-extraction: 다중 소스 데이터 수집
- report-generator: 맞춤형 보고서 생성
- approval-workflow: 다중 채널 승인 프로세스

[입력]
- 데이터 조회 기간
- 보고서 양식 선택
- 발행 채널 (WordPress, 이메일 등)

[출력]
- 정리된 데이터 파일
- 맞춤 양식 보고서
- 실행 로그 및 결과 알림

[활용 특징]
- 고객사별 양식 맞춤 설정 가능
- 다른 미니앱과 조합하여 확장 워크플로우 구성 가능
- 사용자가 AI 도움받아 개인화 가능
```

### 한 번 만들면 모두가 사용한다

한 고객사에서 생성된 미니앱은 동일한 문제를 경험하는 모든 고객이 즉시 활용할 수 있습니다.

```
A 회계법인: "월말 결산 보고서 자동화가 필요합니다"
    → 담당자가 미니앱 개발 (시행착오 끝에 성공) → 미니앱 등록: financial-data-reporter

B 세무사무소: "월말 결산 보고서 자동화가 필요합니다" → 기존 미니앱 즉시 적용 (oneshot)

C 법무법인: "월말 결산 보고서 자동화가 필요합니다" → 기존 미니앱 즉시 적용 (oneshot)

D 자산운용사: "월말 결산 보고서 자동화가 필요합니다" → 기존 미니앱 즉시 적용 (oneshot)
```

A 회계법인이 겪은 시행착오를 B, C, D가 겪을 필요가 없다는 것이 EG-Desk의 차별점입니다.

### EG-Desk의 복제 불가능성

기술 스택은 복제가 가능합니다. Playwright, Electron, OpenAI API는 모두 공개된 기술입니다. 그러나 Ontology와 미니앱은 복제가 불가능합니다.

첫째, 실무 지식은 체득을 통해서만 획득됩니다. 홈택스는 로그인 후 3초 대기가 필요하다는 것은 직접 실패를 경험하고 해결해본 경우에만 알 수 있는 지식입니다. 수백, 수천 개의 다양한 업무를 자동화하면서 축적된 인사이트는 시간 투자를 통해서만 획득이 가능합니다.

둘째, 암묵지(Tacit Knowledge)는 문서화가 불가능합니다. 이 고객사는 특정 시간대에 특정 양식으로 보고해야 하고, 담당자 A와는 특정 방식으로 커뮤니케이션해야 원활하다는 것은 직접 경험한 담당자만이 보유할 수 있는 지식입니다.

셋째, 전담 인력 시스템은 복제가 불가능합니다. 결과물인 미니앱은 외부에서 관찰 가능하지만, 그 이면에 존재하는 인력 네트워크와 Ontology 축적 시스템은 외부에서 파악할 수 없습니다.

중요한 요소는 시간입니다. 시간은 구매할 수 없는 자원입니다. EG-Desk가 1년 동안 축적한 Ontology를 경쟁자가 따라잡기 위해서는 동일한 기간이 필요합니다. 그러나 1년 후 EG-Desk는 이미 2년치의 축적을 보유하게 됩니다. 실무에서 지속적으로 패턴을 생산하고 공유하는 시스템이 작동하는 한, 격차는 시간 경과에 따라 확대됩니다.

## 핵심 기술 아키텍처

### 시스템 구조

```
[사용자] 자연어 요청 또는 미니앱 실행
    |
    v
[AI 에이전트 실행 환경]
    다중 AI 모델 통합 계층 (OpenAI, Claude, Gemini)
    |
    v
    Ontology 4계층 통합
    +-- 로컬 Ontology
    |   +-- Dimension 1: 개인 Preference (선호, 조직 규칙, 관계 맥락)
    |
    +-- 클라우드 Ontology
        +-- Dimension 2: 시스템 실행 패턴 (브라우저 자동화 디테일)
        +-- Dimension 3: 도메인 지식 (업무 규칙, 비즈니스 로직)
        +-- Dimension 4: Workflow 조합 (미니앱, 복합 프로세스)
    |
    v
    브라우저 우선 자동화 계층 (Playwright 기반)
    |
    v
[웹 기반 시스템들] 금융 | 소셜미디어 | CMS | 공공포털
```

사용자는 자연어로 요청하거나 미니앱을 직접 실행합니다. AI 에이전트는 요청을 분석한 후:

1. Dimension 4(클라우드): 적합한 Workflow/미니앱 검색
2. Dimension 3(클라우드): 업무 규칙과 도메인 지식 로드
3. Dimension 2(클라우드): 대상 시스템의 자동화 패턴 로드
4. Dimension 1(로컬): 개인 선호와 조직 맥락 적용

4개 차원을 결합하여 실행합니다. 적합한 Workflow가 클라우드에 있으면 즉시 실행하고, 없으면 새로 생성하여 클라우드에 저장합니다. 사용자 맥락(Dimension 1)은 사용자가 자신의 환경에서 즉시 시작할 수 있도록 로컬에 저장됩니다.

### 브라우저 우선 자동화

브라우저 우선 자동화는 API 제약 없이 대부분의 웹 시스템에 접근할 수 있는 방법을 제공합니다. 시스템은 Microsoft의 Playwright 프레임워크를 사용하여 브라우저 인스턴스를 제어합니다.

AI의 세 가지 개입 시점

EG-Desk에서 AI 에이전트는 다음 세 가지 시점에 개입합니다:

1. 워크플로우 생성 시

사용자로부터 업무 설명을 듣고 대상 웹사이트를 직접 조작하며 자동화 패턴을 학습하여 워크플로우를 생성합니다. 예를 들어, 금융 사이트에서 거래내역을 가져와야 한다는 요청을 받으면, AI가 사이트를 탐색하며 로그인 폼을 찾고, 인증 절차를 학습하고, 데이터 추출 방법을 파악하여 자동화 시퀀스로 저장합니다.

2. 예외 발생 시

기존 워크플로우 실행 중 오류 발생 시 AI가 즉시 개입하여 문제를 분석하고 해결하며, Ontology의 실행 절차와 예외 규칙을 자동 업데이트합니다. 웹사이트 UI가 변경되거나 예상치 못한 팝업이 나타나는 등의 상황에서 사람의 개입 없이 AI가 스스로 대응합니다.

3. 맥락 의존 작업 시

업무 내용이 실시간 판단을 요구하는 경우 AI가 맥락을 이해하고 적절한 액션을 결정합니다. 예를 들어, 고객 문의를 분석한 후 적절한 답변 템플릿을 선택하거나, 승인 조건에 따라 다른 경로로 워크플로우를 진행하는 등의 상황적 판단을 수행합니다.

동적 환경 적응

이러한 AI 개입 메커니즘은 EG-Desk를 전통적 RPA와 구분짓는 핵심 요소입니다.

전통적 RPA와의 차이:
- 전통적 RPA: 웹사이트 UI 변경 시 -> 스크립트 실패 -> 사람이 스크립트 재작성 -> 수동 배포
- EG-Desk: 웹사이트 UI 변경 시 -> 예외 감지 -> AI 에이전트 호출하여 해결 -> Ontology의 실행 절차 자동 업데이트 -> 워크플로우 수정 완료

통합 시스템 범위

EG-Desk는 현재 주요 국내 웹 시스템과의 통합을 완료했습니다. 금융 서비스, 소셜미디어 플랫폼, 콘텐츠 관리 시스템, 전자상거래 등 업무에 필수적인 시스템들을 자동화할 수 있습니다.

### 다중 AI 모델 통합

EG-Desk는 특정 AI 모델에 종속되지 않습니다. 사용자의 요구사항과 상황에 따라 다양한 AI 모델을 선택할 수 있습니다. 비용 효율이 중요한 경우 경량 모델을, 높은 정확도가 필요한 경우 최신 대형 모델을, 데이터 보안이 중요한 경우 로컬 LLM(Ollama)을 사용하며, 특정 작업에 특화된 모델이 있는 경우 즉시 통합할 수 있습니다.

OpenAI GPT, Anthropic Claude, Google Gemini 등 주요 모델뿐 아니라, 오픈소스 모델과 사용자 커스텀 모델도 통합할 수 있습니다.

---

Ontology가 지식을, 미니앱이 전달 수단을 담당한다면, 이 시스템을 지속적으로 확장하는 것은 사람입니다. EG-Desk의 전담 인력 서비스는 기술과 사람을 결합합니다.

## 전담 인력 서비스: 기술과 사람의 결합

AI 도입 실패의 70%는 기술이 아닌 사람 문제입니다. 내부 인력 부족(60%), 투자 효과 불확실성(57%). EG-Desk의 전담 인력 서비스는 이 문제를 근본적으로 해결합니다.

### 서비스 개념

EG-Desk 전담 인력 서비스는 IT 리소스가 제한된 중소기업을 위한 완전 관리형 자동화 서비스입니다. 전담 인력이 기업에 배정되어 자동화의 모든 과정을 대신 처리합니다. 이 과정에서 생성된 Ontology와 미니앱은 EG-Desk 생태계 전체의 자산이 됩니다.

### 서비스 프로세스

```
1단계 [업무 분석]
전담 인력이 기업 방문/원격 미팅
→ 현재 업무 프로세스 파악
→ 자동화 가능 영역 식별
→ 우선순위 및 기대 효과 정리
    ↓
2단계 [워크플로우 구축]
전담 인력이 EG-Desk 클라우드 검색
→ 기존 미니앱 활용 (있으면 oneshot)
→ 없으면 신규 개발 및 테스트
→ 기업 담당자와 결과 확인
    ↓
3단계 [운영 및 관리]
자동화 작업 모니터링
→ 오류 발생 시 즉시 대응
→ 정기 성과 리포트 제공
→ 지속적 최적화
    ↓
4단계 [확장]
추가 자동화 니즈 발굴
→ 새로운 워크플로우 구축
→ 기업 성장에 맞춘 확장
```

### 2-layer 구조

EG-Desk의 전담 인력 서비스는 고객 담당자와 기술 담당자 두 레이어로 구성됩니다.

```
고객 담당자:
- 입력: 고객의 문제
- 처리: 문제를 미니앱 UI로 변환
- 출력: 사용 가능한 제품

기술 담당자:
- 입력: 고객 담당자가 발견한 자동화 니즈
- 처리: 실제 시스템 통합 및 워크플로우 구축
- 출력: 검증된 Ontology
```

#### Layer 1: 고객 담당자

고객 담당자는 고객과의 접점에서 활동합니다.

주요 업무:
- 영업 및 니즈 탐색: 고객의 업무 환경과 pain point 파악, 자동화 기회 발굴
- 현장 방문: 실제 업무 프로세스를 직접 관찰하고 이해, 문서화되지 않은 암묵지 수집
- 미니앱 프론트엔드 제작: HTML+CSS+JS 기반의 가벼운 UI 구현 (뷰어 + 요청자)
- 고객 소통: 요구사항 수렴, 피드백 반영, 결과 전달, 교육 및 지원

필요 역량:
- 고객의 언어를 이해하는 능력
- 업무 프로세스를 자동화 요구사항으로 변환하는 능력
- 기본적인 HTML/CSS/JS 지식 (미니앱 프론트엔드 제작)
- 커뮤니케이션 및 영업 역량

#### Layer 2: 기술 담당자

기술 담당자는 기술적 구현을 담당합니다.

주요 업무:
- Ontology 설계: 특정 시스템의 실무 인사이트를 구조화, 로그인 플로우/예외 케이스/타이밍 이슈 등 문서화
- API 연결 구현: 외부 시스템과의 연동 처리, 인증/데이터 변환/에러 핸들링
- 워크플로우 로직 구축: 복잡한 비즈니스 로직을 자동화 시퀀스로 변환
- 백엔드 인프라 관리: 플랫폼 안정성 및 성능 유지, 모니터링, 장애 대응
- 기술 지원: 고객 담당자가 해결하지 못하는 기술적 문제 해결, 복잡한 예외 케이스 처리

필요 역량:
- 브라우저 자동화 (Playwright, Selenium 등)
- AI 통합 및 프롬프트 엔지니어링
- 웹 기술 전반 (HTML, JavaScript, 네트워크 프로토콜)
- 예외 처리 및 디버깅 능력
- 시스템 아키텍처 이해

#### 협업 프로세스

```
고객 요청
    ↓
1단계 [고객 담당자] 요구사항 수집
고객 미팅/현장 방문
→ 업무 프로세스 파악 및 문서화
→ 자동화 범위/우선순위 정의
→ 미니앱 UI 설계 (와이어프레임)
    ↓
2단계 [기술 담당자] 기술 구현
대상 시스템 분석 (로그인, 네비게이션, 데이터 구조)
→ Ontology 설계 및 구축
→ 브라우저 자동화 스크립트 개발
→ API 연결 및 워크플로우 로직 구현
→ 테스트 및 예외 케이스 처리
    ↓
3단계 [고객 담당자] 미니앱 완성 및 전달
미니앱 프론트엔드 구현 (기술 담당자가 만든 로직 연결)
→ 고객과 함께 테스트
→ 피드백 수렴 및 수정 요청 (필요시 2단계 반복)
→ 고객 교육 및 인수인계
    ↓
4단계 [플랫폼] 축적
검증된 Ontology → EG-Desk 클라우드 등록
미니앱 → 미니앱 라이브러리 등록
다른 담당자들이 즉시 재사용 가능
```

#### 왜 2-layer로 나누는가

1. 전문성 집중

각 역할이 자신의 강점에 집중할 수 있습니다. 고객 담당자는 고객과의 소통과 비즈니스 이해에, 기술 담당자는 기술적 구현에 집중합니다.

2. 효율 극대화

고객 담당자가 기술적 문제로 시간을 소모하지 않고, 기술 담당자가 고객 미팅으로 개발 시간을 할애하지 않습니다.

3. 확장성 확보 - 비대칭 확장 구조

기술 담당자가 만든 Ontology를 고객 담당자 10명이 재사용하기 때문에 비대칭적 확장이 가능합니다. 기술 담당자 한 명이 금융 시스템 인증 Ontology를 구축하면, 그 Ontology를 사용하는 미니앱은 모든 고객 담당자가 즉시 활용할 수 있습니다.

확장 시나리오:
- 초기 단계 (고객 담당자 3명 : 기술 담당자 2명): 기술 담당자가 기본 Ontology 구축에 집중
- 성장 단계 (고객 담당자 10명 : 기술 담당자 3명): 기존 Ontology 재사용으로 고객 담당자 확장 용이
- 성숙 단계 (고객 담당자 30명 : 기술 담당자 5명): 대부분의 요청이 기존 미니앱으로 해결, 기술 담당자는 신규 시스템에만 집중

4. 진입 장벽 완화와 비용 경쟁력

전통적 개발자가 알아야 할 것:
- 서버 아키텍처, 도메인 관리, 데이터베이스 설계
- React/Vue 같은 복잡한 프론트엔드 프레임워크
- 백엔드 API 개발 및 보안
- 인프라 관리 및 배포

EG-Desk 고객 담당자가 알아야 할 것:
- 기본적인 HTML/CSS/JS (미니앱 UI 제작)
- 고객 소통 및 업무 이해 능력
- AI 활용 능력 (개발 과정 전체를 AI가 도움)

고객 담당자는 EG-Desk 플랫폼 내에서 미니앱을 개발합니다. 복잡한 서버/도메인/인프라는 플랫폼이 제공하고, 어려운 로직은 기술 담당자가 Ontology로 구축하며, 실제 개발도 AI를 활용합니다.

5. 품질 보장

모든 Ontology와 워크플로우 로직이 기술 담당자의 검토를 거치므로, EG-Desk 생태계 전체의 기술 품질이 일관되게 유지됩니다.

| 효과 | 결과 | 비즈니스 영향 |
|------|------|------------|
| 전문성 집중 | 각자 강점에 집중 | 개인 생산성 향상 |
| 효율 극대화 | 시간 낭비 제거 | 전체 처리량 증가 |
| 확장성 확보 | 비대칭 확장 가능 | 고객 증가 대응 용이 |
| 진입 장벽 완화 | 채용 풀 확대 | 빠른 조직 성장 |
| 품질 보장 | 기술 검토 집중화 | 플랫폼 신뢰도 유지 |

#### 미니앱과 담당자 역할의 연결

```
[미니앱 프론트엔드 - 고객 담당자]
뷰어 (View): 결과 표시 UI → HTML + CSS
요청자 (Requester): 실행 트리거 → 간단한 JS

코드량: 수백 줄
제작 시간: 수일
필요 기술: 기본 HTML/CSS/JS
    ↓ 호출
[EG-Desk 플랫폼 레이어 - 기술 담당자]
Ontology: 대상 시스템의 실무 인사이트
워크플로우 로직: 자동화 시퀀스
API 연결: 외부 시스템 연동
브라우저 컨트롤: 실제 실행

한 번 구축하면 모든 고객 담당자가 재사용
복잡한 기술은 기술 담당자가 담당
```

고객 담당자는 복잡한 기술 없이도 고객에게 가치를 전달하는 미니앱을 제작할 수 있습니다. 기술 담당자가 금융 시스템 인증 Ontology를 한 번 구축하면, 10명의 고객 담당자가 각자 담당하는 고객들에게 금융 자동화 미니앱을 즉시 제공할 수 있습니다.

### 전담 인력의 역할: 실무 패턴 생산자

```
고객 A 요청 접수
    ↓
EG-Desk 클라우드 검색 ─→ 적합한 미니앱 있음 → 즉시 적용 (oneshot)
    ↓ (없음)
신규 워크플로우 구축 (시행착오 발생)
    ↓
실무 패턴 발견 → Ontology 업데이트 → EG-Desk 생태계 전체 공유
    ↓
다른 담당자들과 고객들이 활용 가능 (이후 oneshot)
```

담당자 한 명이 겪은 실무 경험이 EG-Desk 생태계 전체의 성공률을 높입니다.

### 업무의 시간에 따른 변화

초기 단계에서는 시행착오로 인해 첫 번째 고객의 월말 결산 자동화 요청에 일주일이 소요될 수 있습니다. 그러나 10번째 고객에게는 반복 패턴이 축적되어 하루로 단축되며, 100번째 고객에게는 대부분 oneshot으로 해결하여 5분 이내에 완료됩니다.

### 적합한 기업

전담 인력 서비스는 다음과 같은 기업에 적합합니다:

- IT 전담 인력이 없는 중소기업
- 반복적인 수작업에 시간을 쏟고 있는 조직
- AI/자동화 도입을 시도했지만 실패한 경험이 있는 기업
- 빠르게 자동화 효과를 보고 싶은 기업

70%의 문제(인력과 프로세스)를 전담 인력이 해결하고, 나머지 30%의 문제(기술과 알고리즘)는 EG-Desk 플랫폼이 해결합니다.

---

전담 인력이 만들어내는 패턴은 개별 고객에게만 가치가 있는 것이 아닙니다. 이 패턴들이 축적되면 EG-Desk 생태계 전체의 가치가 상승합니다.

## 네트워크 효과: Working Pattern의 축적

Ontology와 전담 인력 서비스를 결합하면 시스템이 사용할수록 더 강력해집니다. 이것은 단순한 학습이 아니라 메타적 학습입니다. 시스템이 학습하는 것이 아니라, 사용자들의 경험이 구조화되어 다른 사용자에게 전달됩니다.

### 선순환 구조

```
[1단계] 초기 담당자의 시행착오
새 고객 유입 → 담당자가 문제 해결 → 실무 패턴 발견 → Ontology 업데이트 → EG-Desk 생태계 전체 공유
→ 이 단계가 가장 비용이 많이 듭니다. 경쟁자도 여기서 시작해야 합니다.
    ↓
[2단계] 패턴 재사용 시작
EG-Desk 클라우드 확장: 더 많은 검증된 미니앱, 더 높은 oneshot 성공률, 더 넓은 시스템 커버리지
→ 여기서부터 경쟁 우위가 발생합니다. 속도가 기하급수적으로 빨라집니다.
    ↓
[3단계] Oneshot 성공률 향상
플랫폼 가치 상승: EG-Desk에서 하면 즉시 성공한다는 평판, 신규 고객 유치 용이, 담당자 생산성 증가
→ 이제 경쟁자는 따라잡을 수 없습니다. 시간 격차가 경쟁 장벽이 됩니다.
    ↓
(순환) → 새 고객 유입
```

### 네트워크 효과의 구체적 메커니즘

1. 고객이 늘어날수록 성공률이 높아진다

첫 번째 고객사의 경우, 담당자는 기존 미니앱이 없으니 기술 담당자와 함께 처음부터 구축하여 시행착오 끝에 성공한 후 미니앱을 만들어 플랫폼에 등록합니다.

열 번째 고객사가 비슷한 요청을 하면, 담당자는 기존 미니앱을 찾아 즉시 적용하여 Oneshot 성공합니다. 이 고객사가 특별한 양식을 요구할 경우, 담당자는 미니앱을 약간 수정하고 이 변형도 플랫폼에 추가합니다.

백 번째 고객사에 이르면, 담당자는 대부분의 요청에 대해 기존 미니앱을 즉시 활용할 수 있습니다.

2. 담당자가 늘어날수록 패턴 생산이 가속화된다

담당자 한 명이 한 달에 5개의 새로운 패턴을 발견한다고 가정하면, 담당자가 10명이 되었을 때 한 달에 45개 정도가 생산됩니다. 담당자들이 서로의 패턴을 재사용하여 중복된 시행착오가 제거되기 때문입니다. 담당자가 30명이 되면 패턴 생산 속도가 더욱 가속화되어 경쟁자가 따라잡기 어려운 속도에 도달합니다.

3. 사용자도 미니앱을 직접 활용할 수 있다

EG-Desk가 AI-agent infused 시스템이기 때문에, 담당자도 이 시스템 안에서 AI 도움을 받아 빠르게 기술력을 향상시킬 수 있으며, 일반 사용자도 AI에게 물어가며 미니앱을 사용하고 커스터마이징할 수 있습니다.

플랫폼이 성숙할수록 변화합니다:
- 초기: 모든 것을 담당자가 처리
- 성장기: 자주 쓰이는 미니앱은 사용자가 직접 사용
- 성숙기: 대부분의 표준 업무는 미니앱으로 셀프서비스. 담당자는 새로운 패턴 발굴에 집중

### 양적 성장 vs 질적 성장

일반적인 플랫폼의 네트워크 효과는 양에 관한 것이지만, EG-Desk의 네트워크 효과는 질에 관한 것입니다. 사용이 많아지면 성능이 향상됩니다.

```
금융 데이터 추출 미니앱 진화 과정
├── 초기: 기본 기능 구현
├── 사용이 늘어나며 발견된 예외 케이스들:
│   ├── 특정 시간대 시스템 접근 제한
│   ├── 브라우저 버전에 따른 호환성 이슈
│   ├── 보안 모듈 업데이트 후 인증 플로우 변경
│   ├── 고객사별 보고서 양식 요구사항
│   └── ... 다수의 실무 예외 케이스
├── 발견할 때마다 Ontology 정교화
└── 결과: Oneshot 성공률 지속 향상
```

미니앱이 실제 환경에서 사용될수록 더 많은 예외 케이스가 발견되고 Ontology가 정교해지며 성공률이 올라갑니다.

### 복제 불가능한 경쟁 장벽

1. 선발 주자 우위(First-Mover Advantage)

먼저 시작한 자가 더 많은 Ontology를 보유합니다. EG-Desk가 1년 동안 1,000개의 미니앱을 축적했다면, 경쟁자는 오늘 시작해도 1년 후에야 비슷한 수준에 도달하지만 1년 후 EG-Desk는 이미 3,000개를 보유하게 됩니다.

2. 가속도의 법칙

시간이 지날수록 격차는 축소되지 않고 확대됩니다. EG-Desk의 담당자가 100명이 되면 월간 500개의 새로운 패턴이 생산되는 반면, 경쟁자가 담당자 10명으로 시작하면 월간 50개에 불과하여 격차는 매월 450개씩 벌어집니다.

3. 전환 비용(Switching Cost)

사용자는 검증된 플랫폼을 떠날 이유가 없으며, 미니앱 라이브러리는 사용자를 묶어두는 자산으로 작용합니다.

4. 복제 불가능성

시간은 구매할 수 없으므로, 수백 개 기업의 실제 업무에서 검증된 working pattern은 시간을 투입해야만 축적됩니다.

## 보안 및 프라이버시

### 브라우저 기반 보안 모델

EG-Desk는 브라우저처럼 작동하도록 설계되었으며, 일반 웹 브라우저에 적용되는 보안 원칙들이 동일하게 적용됩니다:

- 샌드박스 격리: 각 자동화 세션은 격리된 환경에서 실행
- HTTPS 기본: 모든 웹 통신은 암호화된 연결 사용
- 쿠키 및 세션 관리: 브라우저 수준의 보안 정책 적용
- 자격증명 보호: OS 수준 키체인 통합

### Data Irrigation: 분산된 데이터 관리

EG-Desk는 전통적인 Data Lake 방식을 취하지 않습니다. 모든 데이터를 한 곳에 모으는 대신, Data Irrigation(데이터 관개) 방식을 사용합니다.

- Data Lake: 모든 데이터를 중앙 서버에 저장 -> 단일 실패 지점, 유출 시 전체 피해
- Data Irrigation: 데이터는 원천에 그대로 두고 필요할 때 연결 -> 분산 저장, 제한된 피해

구체적 구현:
- 로컬 우선: 대부분의 고객 데이터는 로컬에 저장
- 분산 클라우드: 클라우드 사용 시에도 third-party providers 분산 활용
- 워크플로우가 곧 데이터 연결: 여러 SaaS 앱을 연결한 워크플로우 자체가 데이터 흐름이며, EG-Desk 서버에 data lake를 만들지 않음

### Ontology와 미니앱의 보안: 계약 기반 NDA

담당자가 고객사와 EG-Desk 도입 계약을 체결할 때, NDA(비밀유지계약)가 포함됩니다.

Parameter화 원칙:

자동화 구현 시, 고객 특정 정보는 처음부터 parameter로 분리됩니다.

고객 A 환경에서 개발:
```
계정: customer-a@company.com (parameter)
API 키: sk-xxx-actual-key (parameter)
업무 로직: 월말 결산 프로세스 (Ontology)
```

플랫폼 공유 시:
```
계정: [사용자 입력 필요] <- parameter
API 키: [사용자 입력 필요] <- parameter
업무 로직: 월말 결산 프로세스 (Ontology, 검증됨) ← 공유 가능
```

고객의 민감 정보는 애초에 하드코딩되지 않습니다. 플랫폼에 공유되는 것은 업무 로직(Ontology)뿐이며, 이는 NDA에 따라 익명화 처리됩니다.

## 결론

본 백서는 다음 문제를 다룹니다: AI 모델의 성능은 이미 상용화 수준에 도달했으나, 기업들의 AI 도입은 70-85% 실패합니다.

분석 결과, 문제는 AI 모델의 성능이 아니라 실행 계층의 부재였습니다.

EG-Desk는 이 실행의 격차를 해소합니다:
- 브라우저 자동화로 AI가 직접 실행
- Ontology로 실무 패턴을 축적
- 전담 인력 시스템으로 지속 가능하게 확장

### 왜 지금인가

AI 도입 포기율이 급증하고 있습니다(2024년 17% -> 2025년 42%). 이것은 AI 기술의 실패가 아니라 실행 계층의 부재가 원인입니다. EG-Desk는 이 시점에 AI가 실제로 업무를 수행할 수 있게 하고 첫 시도에 성공하게 만드는 해답을 제시합니다.

### 차별점: 전담 인력 시스템

기술 스택은 Playwright, Electron, AI API 등 모두 공개된 기술이므로 복제할 수 있지만, 실무에서 지속적으로 패턴을 생산하고 공유하는 전담 인력 시스템은 복제할 수 없습니다. 이 시스템이 작동하는 한 시간이 지날수록 정보의 격차가 벌어집니다.

### 우리가 만드는 미래

2025년: 국내 시장에서 EG-Desk로 하면 첫 시도에 된다는 평판 확립

2026년: 글로벌 확장, AI 기술 발전(파인튜닝, Physical AI)과 함께 진화

장기: AI가 실제로 일하는 것이 당연한 세상에서 사람은 무엇을 원하는지만 말하면 됩니다.
