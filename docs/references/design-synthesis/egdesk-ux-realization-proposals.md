## 1. 흐름의 출발점

Desk는 하나의 Canvas를 제공하고 여러 Agenda가 그 위에 열린다. Agenda는 여러 폴더·
계정·PC의 자료와 실행 자원을 연결할 수 있다. 하나의 Canvas라는 화면 관계는 실행 PC가
한 대라는 뜻이 아니다. 담당 Agent와의 Chat은 사람에게 보이는 관계를 이어 가며, 하나의
방에서도 여러 업무가 실행될 수 있다. 각 업무의 자료·지시·실행 상태는 구분된다. 다른 PC의
작업도 Canvas에서 실행 위치와 상태를 찾을 수 있고, 화면 탐색은 작업 대상을 바꾸지 않는다.

예시의 `검토 Agent`, `자료 비교`, `문서 수정`은 상대와 업무를 구별하기 위한 가칭이다.
최종 Agent 카탈로그나 새 제품 객체가 아니다. 아래 버튼은 모두 포커스 가능한 컨트롤로
가정한다. `Tab`으로 이동하고 `Enter`로 활성화할 수 있으며, 열린 보조 화면의 `Esc`는
해당 화면만 닫고 시작한 컨트롤로 돌아간다. 작성 중인 내용·첨부·업무 연결은 유지하고,
다른 답장을 쓰러 갔다면 `[이전 초안으로 돌아가기]`로 그 초안을 다시 연다. 원 컨트롤이
사라졌으면 해당 대화·자료 목록의 가까운 진입점으로 돌아가며 닫힌 실행을 다시 켜지 않는다.
Chat 전송은 이 안에서 `⌘/Ctrl+Enter`, 줄바꿈은 `Enter`로 제안한다. 파일 편집기·Terminal에
포커스가 있을 때는 그 입력을 Chat 전송으로 가로채지 않는다.

한글 등 IME 조합 확정에 쓴 `Enter`·전송 키 입력은 메시지 전송으로 이어지지 않는다.
조합이 끝난 뒤 별도의 전송 조작을 해야 한다. File view의 bar를 선택해 복사하면 파일/view
참조를, 내용 안의 텍스트를 선택해 복사하면 해당 텍스트와 허용된 출처 범위를 붙여 넣는 안이다.
드래그로 하는 자료 첨부·항목 이동·크기 변경에는 각각 `[파일 선택]`, `[이동]`에서 목적지 선택,
`[크기]`에서 값 입력처럼 클릭·탭만으로 끝내는 경로와 키보드 경로를 함께 제공한다. 모션 감소
설정에서는 Canvas 이동을 즉시 전환하고 같은 대상·활동·Briefing 단계에 접근할 목록을 제공한다.
진행·입력 담당자·연결 끊김은 색이나 움직임뿐 아니라 이름·상태 텍스트로 구별한다.

§4.1은 확정된 제품 경계이고, §3의 구체 control·문구·기본값은 그 안에서 비교하는 제안이다.
§4.3은 이 제안을 검증할 시나리오이며 관찰된 구현 성과가 아니다.

### 화면 배치와 조작 거리

아래는 비교용 초기 배치다. Chat은 Canvas 위의 이동 가능한 View이며 오른쪽 고정 패널이라는
뜻은 아니다. 그림의 선은 영역 경계를 표시할 뿐 실제 모서리·색·서체 디자인을 정하지 않는다.

```text
┌ EG-Desk ───────────────────────────────────── [설정] ┐
│ Sidebar  │ 화면에 보이는 Canvas 영역                  │
│ Agenda A │                                           │
│ Agenda B │  Browser A       File B      ┌ Chat View ┐ │
│ …        │                            │ 담당 Agent │ │
│ Library  │  비교표 + Memo               │ 대화/상세  │ │
│ 휴지통   │                            │ 작성기     │ │
│          │                            └───────────┘ │
│          │       Dock: Browser · File · Chat          │
└──────────┴───────────────────────────────────────────┘
```

| 표면 | 기본으로 남는 것 | 펼쳤을 때·닫았을 때 |
|---|---|---|
| Sidebar | Agenda 이름·열림/주의 상태와 행의 `[⋯]`; Library·휴지통은 제안된 목록 진입점 | 행 메뉴는 해당 행 옆에 열린다. 삭제·권한 확인은 그 메뉴를 닫고 별도 상세로 전환하며 메뉴 위에 메뉴를 계속 쌓지 않는다 |
| Canvas View bar | 자료 이름·Live/당시 자료·주의가 필요한 상태와 로컬 `[⋯]` | 해당 자료의 메뉴는 bar에 붙는다. 화면 밖 View의 원래 위치·가벼운 상태 표현은 유지하며 혼잡을 줄인다는 이유로 실행을 지우지 않는다 |
| Chat View | 상대, 대화, 현재 업무, 간단한 활동 표시, 작성기 | 실행·읽기·정책 상세는 이 View의 본문 영역을 바꿔 보여 주고 `[대화로 돌아가기]`를 남긴다. 작성기는 유지하며 별도 inspector를 연속 증식시키지 않는다 |
| 비교·근거 View | 선택한 자료/변경과 출처·현재/과거 구분 | 기존 비교 View가 열려 있으면 그곳에서 대상을 바꾼다. 두 내용을 실제로 함께 봐야 할 때만 나란히 연다. 사용자 편집 중인 사본은 바꾸지 않는다 |
| 설정·공유 관리 | 선택한 설정 범주 또는 대상 사람의 상세 | 다른 설정 범주로 이동하면 같은 상세 영역을 교체한다. 되돌릴 수 없는 적용의 마지막 확인만 그 영역에 표시하고 완료 뒤 결과를 읽을 수 있게 남긴다 |

자주 쓰는 전송·업무 연결·활동 관찰은 대화 가까이에 두고, 실행 설정·적용 기준·PC 변경은
작성기 위 `이어갈 업무` 줄의 `[업무 메뉴 ⋯]` 안에 둔다. 진행 중인 업무의 중지는 활동 표시
옆에 직접 제공한다. Agent의 움직이는 `··· 활동` 버블과 고정된 메뉴 아이콘은 모양·위치·
접근 가능한 이름으로 구별한다. 변경 내역은 해당 자료 bar의 `[⋯]` → `[변경 내역]`,
공유 관리는 앱 상단 `[설정]` → `[공유 관리]`로 들어간다. 수신한 소유권 이전 요청은 그 안의
`[받은 요청]`에서 찾는다. 조용한 알림이 있는 경우에는 해당 요청 상세로 바로 갈 수도 있다.

**조작 수 표기**: 각 흐름에 적힌 출발 상태부터 목표 화면/행동까지의 포인터 클릭을 센다.
문장 입력·드래그·스크롤은 별도이며 로그인·OS 파일 선택기의 조작을 임의로 1회로 세지 않는다.
확인 창이 없는 정상 경로와 미저장 내용·권한 차이 때문에 추가되는 경로를 구별한다.
키보드는 같은 컨트롤에 `Tab`으로 접근하고 `Enter`로 실행하며, 전송은 `⌘/Ctrl+Enter`,
닫기는 `Esc`를 쓴다. 클릭 수는 이 후보 경로의 계산값이며 실제 사용시간의 측정값은 아니다.

**화면이 좁거나 내용이 많을 때**: Sidebar 접기는 사용자가 선택하며 자동으로 Canvas의 자료
크기·Browser 내부 viewport를 바꾸지 않는다. Chat 상세의 긴 원문·호출 이력은 내부 목록에서
펼치고, 대상·계정·현재 상태·다음 조작은 같은 화면에 남긴다. 공간이 부족한 비교는 탭으로
전환하되 현재/당시 표시를 탭 밖에 유지한다. 경고는 해당 업무/자료 옆에 요약하고 원인을
펼칠 수 있게 하며, 다른 업무 경고가 현재 입력을 덮는 팝업으로 차례로 튀어나오지 않는다.

```text
활동을 펼친 Chat                 실행 설정을 연 같은 Chat
┌ 담당 Agent ───────────────┐    ┌ 담당 Agent ───────────────┐
│ 최근 대화                 │    │ [대화로 돌아가기]          │
│ ··· 활동 3개              │    │ 대상 업무 · 실제 계정       │
│   Browser B · PC B · 입력  │    │ Profile / 모델 / 현재 한도  │
│   Reader · 자료 읽기       │    │ [자동 조정 범위 ▸]          │
│   문서 수정 · 조치 필요     │    │ [적용 내역 ▸]               │
├ 이어갈 업무: 자료 비교 ─────┤    ├ 이어갈 업무: 자료 비교 ─────┤
│ 보존한 초안          [전송] │    │ 보존한 초안          [전송] │
└──────────────────────────┘    └──────────────────────────┘
```

**혼잡한 상태의 비교안**: 이 숫자는 부하·배치 검토용 가정이며 실제 이용 건수가 아니다.

| 늘어난 내용 | 기본 화면에서 유지할 단서 | 상세 화면·돌아오는 위치 |
|---|---|---|
| Sidebar의 Agenda 30개·긴 한국어 이름 | 열린 상태·이름 식별부·주의 상태. 선택 행 메뉴에는 생략하지 않은 대상 이름 | 목록 스크롤 위치를 유지하고 선택 행 옆 메뉴를 연다. 확인 화면의 대상은 메뉴를 연 행에 고정하며 스크롤로 바뀌지 않음 |
| 한 방의 활동 3개·사용자 초안 | 활동 개수·주의가 필요한 업무 표시·작성 중인 업무 이름 | 활동 목록만 펼친다. 선택 상세를 연 뒤에도 초안·업무 연결을 유지하고 `[대화로 돌아가기]`는 원 스크롤로 복귀 |
| Browser·원문·결과표·Chat이 함께 필요 | 현재 작업 자료와 Chat의 대상/작성기, 각 View의 현재/당시 구분 | 보조 원문은 요청한 위치에서 열고 비교가 끝나면 원 결과표로 돌아간다. 작은 글씨로 모든 View를 동시에 맞춰 넣는 방식을 기본으로 쓰지 않음 |
| 여러 자료의 긴 PC·계정·파일명 | 지금 조작할 대상의 PC·계정·자료 식별 정보 | 긴 값은 선택 상세에서 줄바꿈해 전부 표시한다. 서로 다른 계정을 같은 생략문으로 보이게 한 채 적용하지 않음 |
| 권한/연결 경고 2건과 진행 중 업무 | 각 해당 업무의 상태와 `조치 필요 2건` 요약 | 사용자가 고른 경고 하나의 대상·이유·행동만 상세에 연다. 다른 경고는 남고 새 경고가 현재 입력 위로 강제 전환하지 않음 |

## 3. 구체 사용 흐름

<a id="flow-first-use"></a>
### 처음 켜고 첫 요청을 보낸다

**상황**: 저장한 Agenda도 연결한 Engine도 없다. 사용자는 먼저 파일을 열어 보고, 이어 Agent에게
검토를 요청한다. **연결**: 후보 14·13, ECS-01/02, CAP-01/12,
[Atlas 최초 설정](../../../ideas/confirmed/EGDESK_PRODUCT_INTERACTION_TRACE_ATLAS.md#atlas-manual-start),
[Engine 계약](../../../ideas/confirmed/EGDESK_INTERACTION_AND_ORCHESTRATION_CONTRACT.md#tech-engine-profile).

**추천안**: 제한된 기본 Agent를 제공하고, 조직 지식 연결 없이도 제품 기본 정책으로
개인 업무를 시작한다. Engine 로그인은 AI를 처음 사용할 때 연결한다. 이 기본 Agent와
정책 제공은 `HUM-AGENT-001`의 검토안이다.

```text
Desk                                  Chat · 기본 Agent
  File view: 자료.pdf                   AI 계정을 연결하면 요청할 수 있습니다
                                       [AI 계정 연결]
  Dock: Browser · File · Chat           자료.pdf ×
                                       질문을 입력하세요        [전송: 사용 불가]
```

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | OS에서 EG-Desk를 실행한다 | 빈 Desk와 Dock이 바로 보인다 | 로컬 화면·설정을 구성 | 없음 |
| 2 | Dock의 `[파일]` → 로컬 파일 선택 → `[열기]` | File view에 자료가 보인다 | 권한과 지원 형식을 확인해 뷰를 연다 | 없음 |
| 3 | Dock의 `[Chat]`을 누른다 | 기본 Agent 방, 작성기, 계정 연결 안내가 보인다 | 저장된 기본 Profile·Engine 상태를 표시 | 없음 |
| 4 | `[AI 계정 연결]`을 누르고 provider 인증 화면에서 계정 B를 선택한다 | 원래 Chat에는 연결 진행 상태, 인증 영역에는 provider 화면이 보인다 | 선택한 Engine Profile의 인증 흐름을 열고 결과 identity를 확인 | 없음 |
| 5 | 인증을 완료한다 | 계정 B와 확인 가능한 사용량 상태가 표시되고 Chat으로 돌아온다 | 인증 성공·quota 제한·도구 가용성을 구별 | 없음 |
| 6 | File view의 bar를 선택해 `⌘/Ctrl+C`, Chat 작성기에서 `⌘/Ctrl+V` 후 `이 자료를 요약해줘`라고 입력한다 | 파일 참조와 질문 초안이 보인다 | 객체 참조 붙여넣기와 텍스트 붙여넣기를 구별하고 첨부 범위를 검사 | 없음 |
| 7 | `[전송]` 또는 `⌘/Ctrl+Enter` | 메시지와 Agent 활동 표시가 나타난다 | Profile·Engine·제품 기본 정책과 필요한 context를 결합하고 첫 호출을 시작 | 전달된 요청을 해석하고 필요한 읽기를 요청 |
| 8 | 자료를 더해 후속 메시지를 전송한다 | 같은 업무의 조정 수신·반영 상태가 보인다 | 다음 호출에 새 자료·지시를 포함 | 같은 업무를 이어 간다 |

**연결이 다를 때**: 계정 B를 골랐는데 실제 인증 결과가 C이면 `선택한 계정과 다릅니다`와
두 계정을 보여 주고 그 연결로 첫 호출을 시작하지 않는다. `[계정 다시 선택]`은 같은 Chat의
초안·첨부를 유지한 채 인증으로 돌아간다. 인증 화면만 닫혔거나 응답이 늦으면
`연결 확인 중`으로 결과를 재조회하고, 확인하지 못하면 `[다시 연결]`을 제공한다.
늦게 도착한 취소된 연결 결과로 현재 선택을 바꾸지 않는다.
**취소·복귀**: 인증 화면을 닫으면 Chat 초안과 파일 참조는 남는다. quota 제한은 로그인
실패로 표시하지 않는다. 기본 Agent 제공을 채택하지 않으면 3단계의 같은 Chat에서
`[Agent 만들기]`로 이름·역할을 설정한 뒤 4단계로 이어진다. 요청을 보낸 뒤 중지하면
접수한 요청·이미 읽은 근거와 중지 상태는 남고, 아직 보내지 않은 문장은 초안으로 남는다.
**확인 기준**: 전송 전에는 Agent 호출이 없고, 첫 활동에서 실제 Engine B·대상 자료를
확인할 수 있다. 파일·Browser의 업무 계정은 바뀌지 않는다. 완료된 요약에는 열 수 있는
근거가 연결되고, 판독에 실패한 자료가 있으면 해당 범위와 함께 부분 결과로 표시된다.
**대안**: 먼저 Agent를 직접 만드는 방식은 초기 역할 통제가 쉽지만 첫 사용 단계가 늘어난다.

**배치·진입 비용**: `Canvas: File view │ 오른쪽에 연 Chat: 안내 → 작성기`.
Dock이 보이는 출발 화면에서 Chat 열기는 1클릭, 그 Chat에서 인증 화면 진입은 `[AI 계정 연결]`
1클릭이다. provider 로그인은 별도다. 인증 뒤에는 같은 Chat의 안내 자리만 대화로 바뀌고
작성기·첨부는 그대로다. 초기 화면에 역할·모델·정책·사용량 설정을 모두 펼치지 않는다.
대신 연결된 실제 계정과 전송 가능 여부는 첫 요청 전에 볼 수 있다.

<a id="execution-settings"></a>

**실행 설정을 확인하거나 바꾸는 분기 — 제안**: 첫 전송 전 또는 진행 중인 업무에서
`[실행 설정]`을 열면 Profile·모델·실제 Engine 계정·실행 한도와 각 값의 출처·편집 가능 여부가
보인다. 방의 기본값과 이번 업무에 실제 적용된 값은 따로 표시한다.

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | 대상 업무의 `[실행 설정]` → Profile·모델·한도 항목 선택 | 현재 값·선택 가능한 값·강제 상한·변경 권한·사용 계정이 보인다 | 현재 가용성과 실제 위임·자원 권한을 확인 | 필요하면 변경의 영향 설명 |
| 2 | 값을 선택하고 `[이번 업무에 적용]` | `변경 요청됨`과 적용 예정 시점, 영향을 받는 Reader·Worker가 보인다 | 요청 범위·권한·상한 검사; 가능한 가장 이른 다음 호출에 구성 전달 | 적용된 구성으로 같은 Run 계속 |
| 3 | 재사용할 값이면 별도로 `[새 업무의 기본값으로 저장]` | 저장 대상 방/Profile과 바뀔 기본값이 보인다 | 해당 설정 편집 권한 확인·저장; 다른 진행 중 Run에는 소급 적용하지 않음 | 없음 |
| 4 | `[자동 조정 범위]` → 허용 Profile·모델·한도·대상 업무·기간 선택 → `[위임 저장]` | 자동으로 선택할 수 있는 값과 금지된 계정·비용·전송 범위가 보인다 | 사전 위임을 기록하고 parent·child의 총 사용 상한을 함께 적용 | 그 범위 안에서 선택·분할·검토·복구, 매번 추가 확인 없음 |
| 5 | `[적용 내역]`을 펼치거나 `[자동 조정 해제]`를 누른다 | 실제 적용한 호출·값·계정 또는 위임 해제 확인 상태가 보인다 | 실제 호출 구성 기록; 위임 해제 후 그 위임에 의한 새 변경은 허용하지 않음 | 이미 유효한 현재 구성으로 허용된 업무 계속 |

**적용·실패·복귀**: 이미 실행한 호출·도구·과거 구성은 수정하거나 재실행하지 않는다.
권한 회수·상한 축소는 확인된 실행 경계에서 다음 행동 허용 검사에 반영한다. 진행 중 행동을
멈춰야 하면 중지 요청과 실제 중지 확인을 구별하며, 끊긴 PC의 적용을 확인했다고 표시하지 않는다.
선택한 전환을 지원하지 않으면 이유·가능한 적용 시점·`[허용된 다른 설정 선택]`·`[기존 설정 유지]`를
보여 준다. 필수 변경을 수행할 수 없는 해당 호출만 대기하고 독립 작업은 계속한다. 새 계정이나
상위 예산을 자동으로 선택하지 않는다. `[취소]`는 미전달 변경만 철회하고, 전달 여부가 불명확하면
먼저 상태를 확인한다. 적용 후 `[이전 값으로 변경]`은 후속 호출의 변경이며 이전 사용량·외부 효과를
취소하지 않는다. 저장·전환 실패는 선택값과 초안을 유지한다. `Esc`로 닫으면 원 업무·초안으로 돌아간다.
**완료 근거·대안**: 기본값 저장, 현재 업무의 변경 요청, 실제 다음 호출 적용을 각각 확인한다.
명시한 범위의 사전 위임을 추천하며, 모든 선택을 수동으로 하는 대안은 예측하기 쉽지만 반복
조작·대기가 늘어난다. 위임 해제는 현재 Run 중지와 다르며 과거 설정 이력은 남는다.
[첫 사용 정책](#decision-first-use)·[적용 기준](#policy-conflicts)에서 같은 선택을 비교한다.

**배치·조작 세부**: `[업무 메뉴 ⋯]` 1 + `[실행 설정]` 1로 같은 Chat 본문에 설정을 연다.
모델 선택기를 여는 1 + 값 선택 1 + `[이번 업무에 적용]` 1을 더해, 해당 업무가 선택된 Chat부터
모델 변경까지 5클릭이다. 이력·자동 조정 범위는 접고 대상 업무·실제 계정·현재 값·강제 상한·
변경 상태를 먼저 보인다. `[새 업무의 기본값으로 저장]`은 현재 업무 적용 버튼과 다른 구역에
두며, 눌렀을 때 같은 상세 안에서 저장 대상 방/Profile을 고르게 한다. 작성기는 가리지 않는다.

<a id="flow-chat"></a>
### 한 담당자 방에서 두 업무를 진행하고 하나만 조정한다

**상황**: 같은 검토 Agent에게 `자료 비교`와 `문서 수정`을 맡긴다.
**연결**: 후보 1–2·13, ECS-02/06, CAP-02/03/04,
[Atlas AI-03](../../../ideas/confirmed/EGDESK_PRODUCT_INTERACTION_TRACE_ATLAS.md#atlas-ai-03),
[공유 대화 계약](../../../ideas/confirmed/EGDESK_INTERACTION_AND_ORCHESTRATION_CONTRACT.md#tech-multi-agent-chat).

**추천안**: 담당자 방의 대화는 하나로 유지한다. 메시지·결과에서 선택한 업무를 작성기에
연결하고, Canvas 이동만으로 그 대상을 바꾸지 않는다. 위임 대화·기여는 같은 방에서 필요한
부분을 펼친다. 업무를 가리키는 표시는 새 Thread 객체를 요구하지 않는다.

```text
검토 Agent

나                 자료 두 개를 비교해줘                 자료 비교
검토 Agent         납기와 가격을 확인하고 있어요.        ···
나                 설명 문서도 고쳐줘                   문서 수정
검토 Agent         비교는 Reader, 문서는 편집 작업으로 진행 중입니다.
                   [진행 2건] [참여자·교환]

이어갈 업무: 자료 비교 ×       [새 업무]
가격보다 납기를 우선해줘                         [전송]
```

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | 방의 `[새 업무]` → 비교 요청 입력 → `[전송]` | 원 메시지와 `자료 비교·진행 중`, 작성기의 연결 업무가 보인다 | 메시지·자료·실행의 귀속 기록 | 비교를 계획하고 필요한 읽기 수행 |
| 2 | `[새 업무]` → 문서 수정 요청 입력 → `[전송]` | 같은 방에서 두 업무가 진행된다 | 독립 지시·자료·실행 상태를 유지 | 위임된 범위에서 병렬 또는 순차 진행 |
| 3 | 비교 요청 메시지의 `[이 업무에 지시]` | 작성기에 `자료 비교`가 연결된다. 입력 중 텍스트는 유지된다 | 대상 업무와 선택 메시지 참조를 초안에 연결 | 없음 |
| 4 | `가격보다 납기를 우선해줘` 입력 → `[전송]` | 그 업무에 `조정 수신` 후 실제 다음 호출에 포함되면 `반영됨`이 보인다 | 실제 전달 시점을 기록하고 관련 child로 전파 | 같은 업무의 다음 호출에서 기준 조정; 다른 업무에는 미적용 |
| 5 | `[참여자·교환]` → 특정 기여 선택 | 작성자 avatar·이름·담당 업무와 공유 가능한 질문·답변이 펼쳐진다 | 개별 실행 identity와 발언 귀속·접근 범위를 표시 | 담당자는 통합 책임을 유지; 다른 참여자의 말을 자기 발언으로 바꾸지 않음 |
| 6 | 해당 기여의 `[이 업무에 지시]`에서 추가 지시 전송 | 작성기에 업무와 기여 참조가 보인다 | 담당 업무에 지시 연결, 자동 권한 확대 없음 | 관련 참여자에게 필요한 부분만 전달 |
| 7 | 대상이나 새 업무 여부가 불명확한 메시지를 전송해 확인이 나오면 `[자료 비교에 반영]`, `[문서 수정에 반영]`, `[새 업무로 시작]` 중 해당 항목을 누른다 | 적용 대상을 묻는 메시지에 원 지시·첨부가 남는다. 선택 후 연결이 보이고 `[보내기 취소]`는 초안으로 돌린다 | 해당 지시만 선택 전 미적용; 기존 업무는 계속. 한 번 선택한 지시를 중복 접수하지 않음 | `이것도 고쳐줘`의 대상처럼 해석에 필요한 점만 확인; 연결된 업무의 명확한 후속 지시는 바로 처리 |
| 8 | 뒤늦은 결과의 `[변경 지시와 비교]` | `이전 지시로 작성됨·현재 요청에 맞춰 반영 중`과 영향을 받는 부분이 보인다 | contribution의 실제 입력 revision과 조정 전달 시점을 연결 | 영향 없는 부분을 재사용하고 충돌하는 부분만 재작업·통합; 열람·별도 수락을 기다리지 않음 |
| 9 | `문서 수정` 상태의 `[중지]` | 해당 업무의 `중지 중`과 보존된 결과가 보인다. 확인되면 `중지됨`, 원격 응답이 없으면 `중지 확인 안 됨`으로 남는다 | 해당 업무의 후속 실행을 막고 종료 결과를 확인; 비교 작업은 유지 | 이미 수행한 변경·아직 확인 못한 효과·남은 범위를 구별 |
| 10 | `[교환 접기]` 또는 `Esc` | 원 대화 위치와 작성기 초안으로 돌아온다 | 펼침 상태만 변경 | 작업 상태 불변 |

**취소·복귀**: 전송 전 `[연결 해제 ×]`는 대상 연결만 해제하고 입력 문장을 보존한다.
전송된 조정은 새 정정 메시지로 수정한다. 다른 업무의 활동을 관찰한 뒤에도 작성 중인
업무 대상은 바뀌지 않는다. 이미 전달된 자료를 다음 입력에서 제외하는 것과 과거 전달을
취소하는 것은 구별한다. 대상 업무가 닫혔으면 `닫힌 업무에 대한 초안`으로 표시하고
`[업무 열기]`나 `[다른 업무에 연결]`을 제공한다. 열기만으로 실행을 재개하지 않는다.
중지 뒤 도착한 Worker 결과는 작성 시점과 함께 보존하되 그 결과가 후속 실행을 깨우지 않는다.
**확인 기준**: 사용자 열람·일반 검토 승인을 기다리지 않고 통합이 진행된다. `반영됨`은
해당 업무의 실제 다음 호출에 지시가 전달된 경우에만 보인다. 완료 결과에서 최신 기준과
사용한 기여·근거를 확인할 수 있고, 취소된 문서 수정은 저장된 변경·미완료 범위를 남긴다.
완료된 비교 작업까지 함께 취소·재작성하지 않는다.
**대안**: 업무별 화면을 항상 분할하면 귀속은 선명하지만 담당자와 하나의 대화를 나누는
감각이 약해진다. 이 안은 통합 대화와 선택적 상세 교환을 기본으로 추천한다.

**배치·진입 비용**: `Canvas: 작업 자료 │ Chat: 대화 / 하단 현재 업무 + 작성기`.
업무 시작·결과 메시지의 `[이 업무에 지시]`는 해당 메시지 가까이에 두고 모든 일반 버블마다
동일한 버튼 묶음을 반복하지 않는다. 해당 메시지가 보이면 대상 연결 1클릭 + `[전송]` 1클릭
(문장 입력 별도), `[새 업무]`부터 보내기도 2클릭이다. `[진행 2건]`은 작성기 위 한 줄에서
펼쳐 보고, `[참여자·교환]`은 대화 본문 안에서 확장한다. 활동·교환 목록을 동시에 항상 열어
대화와 작성기를 밀어내지 않는다. 작업이 늘면 목록만 스크롤하고 작성기와 대상 표시는 남는다.

<a id="flow-memo"></a>
### 짧은 메모에서 필요한 대화로 이어지고 원 위치로 돌아온다

**상황**: 비교표 옆에 `납기 2주 맞나?`라는 메모를 붙이고 Agent에게 확인을 맡긴다.
**연결**: 후보 3·4, ECS-02/06, CAP-08,
[Atlas CANVAS-01](../../../ideas/confirmed/EGDESK_PRODUCT_INTERACTION_TRACE_ATLAS.md#atlas-canvas-01),
[Memo·Chat 계약](../../../ideas/confirmed/EGDESK_INTERACTION_AND_ORCHESTRATION_CONTRACT.md#tech-answer-projection).

**추천안**: 개인 메모 저장만으로 모든 Agent를 깨우지 않고, 담당자에게 묻거나 담당 범위에
명시적으로 연결한 메모에 응답한다. 짧은 답만으로 부족하면 원 메모 참조를 가진 질문을
담당자 방에 한 번 남긴다. 미응답만을 이유로 자동 재촉하지 않는 안을 제안한다.

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | Canvas의 `[메모]` → 표 옆 위치 선택 → 문장 입력 → `[저장]` | 작성자·메모가 그 위치에 나타난다 | 위치·대상·본문 revision 저장 | 개인 메모만 저장한 경우 없음 |
| 2 | 메모의 `[담당 Agent에게 묻기]` → 상대 확인 → `[보내기]` | 원 메모 아래 답변 진행 상태가 보인다 | 권한이 있는 대상·업무·Agent에 요청 연결, 중복 요청 방지 | 필요한 원 자료를 확인 |
| 3 | 다른 view에서 계속 작업한다 | Agent 이름으로 짧은 답글이 붙는다 | 사용자 본문과 Agent 답글을 별도로 보존 | 예: `자료에는 3주입니다. 2주가 요청 조건인지 확인이 필요해요.` |
| 4 | 별도 조작 없이 작업한다 | 담당자 방에 메모 참조가 있는 질문과 조용한 알림 1건이 생긴다 | 원 메모·쟁점·수신자로 연락 연결; 카메라·입력 focus 유지 | 짧은 답으로 해결 안 된 필요한 질문만 담당자 명의로 보냄 |
| 5 | 알림의 `[대화에서 보기]` | 담당자 방의 해당 메시지가 보인다. 기존 작성기 초안·업무 연결은 유지된다 | 원 Canvas 시점·Chat 위치를 보존; 열람만으로 지시 대상 변경 없음 | 관찰만으로 새 업무 시작 안 함 |
| 6 | 그 메시지의 `[이 메모에 답장]` → `요청 납기라는 뜻이야` 입력 → `[전송]` | 메모·업무가 연결된 답장 작성기가 열리고 전송된 답장이 원 질문에 연결된다. 기존 초안이 있으면 보관 사실과 복귀 경로가 보인다 | 이전 초안·귀속을 보존하고 명시적으로 선택한 reply draft에 원 메모와 최신 차이를 연결 | 의도를 반영해 답글·결론 보완; 메모 원문은 고치지 않음 |
| 7 | `[메모로 돌아가기]` | 원 표와 메모가 보이고 최신 답글을 확인할 수 있다 | 원 시점·대상으로 복귀 | 별도 호출 없음 |
| 8 | 메모 답글의 `[접기]` 또는 다른 곳 선택 | 답글만 접힌다. 본문·답글·방 연결과 실제 처리 상태는 남는다 | 열람·접기를 완료 승인이나 업무 종료로 취급하지 않음 | 필요한 질문이 해결됐으면 재접촉 종료 |

**원문이 바뀔 때**: 답변 전에 메모를 고치면 답글에 `수정 전 메모에 대한 답변`과 원문 차이를
표시한다. 같은 요청의 다음 호출에 수정 내용을 전달해 보완하며 모든 Agent에게 새 요청을
복제하지 않는다. 연결 자료 권한이 사라지면 내용을 노출하지 않고 `자료 접근 필요`와
`[다른 자료 연결]`을 보인다. 확인 가능한 부분의 답과 원 메모는 남는다.
**중복·취소**: 응답 도중 `[이 응답 중지]`는 원 메모를 남기고 응답만 중지한다.
`[이 쟁점 알림 끄기]`는 알림만 중지하며 업무 중지가 아니다. 메모 수정·Agent 답글 자체를
반복 알림의 새 트리거로 쓰지 않는다. 의미가 달라진 새 사용자 질문은 새 요청으로 받을 수 있다.
답장 작성 중 `Esc`는 내용을 지우지 않고 원 위치로 돌아간다. 원 메모가 이동했으면 현재
위치로 돌아가고, 삭제·접근 제한 상태면 그 사실과 `[원 대화로 돌아가기]`를 보여 준다.
**확인 기준**: Agent 답글의 작성자와 근거를 알 수 있고, 메모가 자동으로 긴 채팅창이 되지
않으며, 대화 왕복 뒤 원 위치와 초안이 유지된다. 확인 질문의 답이 도착하면 원 메모에도
보완된 답·남은 확인 사항이 표시되고 같은 쟁점을 미응답으로 다시 알리지 않는다.
**대안**: 방의 proactive 질문 대신 메모의 `[방에서 이어가기]`만 제공하면 방해는 줄지만
사용자가 메모로 돌아오기 전까지 필요한 확인을 놓칠 수 있다.

**배치·진입 비용**: `Canvas: 비교표 ↔ 옆 Memo(본문 + 짧은 답글) │ Chat: 연결된 질문`.
Canvas의 `[메모]` 1 + 놓을 위치 1 + `[저장]` 1 = 생성 3클릭, 입력은 별도다. 알림이 보이는
상태에서 `[대화에서 보기]` 1 + `[이 메모에 답장]` 1 + `[전송]` 1 + `[메모로 돌아가기]` 1 =
답장 후 복귀 4클릭이다. 알림이 나타나도 Chat을 자동으로 앞으로 올리지 않는다. Memo에는
전체 Chat 이력·참여자 목록을 붙이지 않고 짧은 답글과 원 쟁점의 연결만 남긴다.

### 두 Agenda를 열고 하나만 닫은 뒤 다시 연다

**상황**: Canvas에서 `자료 검토`와 `문서 수정` Agenda를 함께 사용한다. 자료 검토는 PC A의
Browser와 PC B의 파일을, 문서 수정은 그 파일 일부를 참조한다. **연결**: 후보 5–8, ECS-01/05, CAP-09/11,
[Atlas AG-01](../../../ideas/confirmed/EGDESK_PRODUCT_INTERACTION_TRACE_ATLAS.md#atlas-ag-01),
[수명주기 계약](../../../ideas/confirmed/EGDESK_INTERACTION_AND_ORCHESTRATION_CONTRACT.md#tech-desk-lifecycle).

**추천안**: Agenda는 구성·배치·명시적으로 포함한 메모·대화 범위·결과와 live 원본의
연결을 저장한다. 모든 Browser 내용을 자동 archive하지 않고, 당시 근거는 별도로 선택해
포함한다. 같은 URL만으로 서로 다른 Browser instance를 자동 합치지 않는다. 닫기에서는
전용 실행·대기를 멈추고 미래 예약을 pause 상태로 보존하며, 재열기만으로 실행을 재개하지
않는 안을 제안한다. 저장 범위·예약 pause·공유 재사용 기본값은 아직 정책 후보다.

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | 포함할 Browser·File·Memo를 다중 선택하고 `[Agenda로 저장]` | 선택 항목·이름·포함 범위가 보인다 | view 배치와 원본 참조를 수집 | 없음 |
| 2 | 이름을 `자료 검토`로 입력하고 `[저장]` | Sidebar에 Agenda 행, Canvas에는 기존 배치가 남는다 | 확인한 구성의 revision을 저장; 원본 파일 저장은 별개 | 없음 |
| 3 | Sidebar에서 `문서 수정`을 선택한다 | 같은 Canvas에 두 번째 Agenda가 열린다 | 기존 열린 Agenda는 재사용하고 다른 내용은 유지 | 없음 |
| 4 | 자료 검토의 파일에서 `[다른 Agenda에 연결]` → `문서 수정` → `[자료 참조 추가]` | 두 Agenda에 같은 원본을 가리키는 뷰가 생기지만 별도 실행이 새로 시작되지는 않는다 | 참조·view와 실행 소유권을 구별 | 없음 |
| 5 | 실행까지 함께 유지해야 한다면 같은 연결 화면의 `[실행 함께 사용]`을 선택하고 영향 내용을 확인한다 | 어디를 닫아도 어느 실행이 남는지 두 Agenda 이름으로 보인다 | 명시된 공유 실행 소유관계를 기록 | 기존 위임 범위를 유지 |
| 6 | `자료 검토`의 `[닫기]`를 누른다 | 전용 실행·예약과 `문서 수정`에서 유지될 실행을 구별해 보여 준다 | 종료 대상과 미저장 상태를 확인 | 전용 작업에는 새 행동을 만들지 않음 |
| 7 | 미저장 내용이 있으면 `[변경 저장 후 닫기]`, `[복구용 초안으로 남기고 닫기]`, `[취소]` 중 선택한다 | 무엇이 원본에 저장되는지, 임시 초안만 남는지 보인다 | 저장 가능한 편집기를 처리; 지원하지 않는 form 상태 보존은 보장하지 않음 | 별도 저장 작업을 위임한 경우만 수행 |
| 8 | 닫기를 확정한다 | 전용 실행의 PC별 종료 진행을 보인다. 모두 확인되면 Agenda 영역이 사라지고 다른 Agenda와 Saved Agenda 행은 남는다 | 전용 실행·대기·자동 재개를 차단하고 각 종료를 확인; 예약은 제안 정책에 따라 pause | 전용 실행 중단; 뒤늦은 결과로 새 작업을 만들지 않음 |
| 9 | Sidebar의 `자료 검토`를 다시 연다 | 저장 구성과 보존 가능한 초안이 열린다. 이전 작업·예약은 중지 상태다 | 자동 Desk 복원과 별개로 saved 구성·필요 원본을 조회 | 없음 |
| 10 | 특정 업무의 `[계속]` 또는 예약의 `[예약 재개]`를 누른다 | 선택한 업무만 현재 조건으로 이어진다 | account·자원·현재 지시를 다시 연결하고 중복 실행을 검사 | 이어지는 호출에서 작업 진행 |

**Agenda를 닫지 않고 자동화 하나만 조정하는 분기 — 제안**: Agenda bar의 `[⋯]` →
`[실행·예약]`은 해당 Agenda의 현재 실행과 미래 예약을 나눠 보여 준다. 자동화 항목을 선택하면
이름·식별자·실행 PC·서비스 계정·다음 조건·현재 실행 상태가 같은 상세에 보인다.
`[예약 일시정지]`는 그 자동화의 미래 시작만 막고, 실제 적용 확인 뒤 `예약 일시정지됨`으로
표시한다. 원문 데이터를 되돌리거나 다른 예약·Agenda를 닫지 않는다. 이미 돌고 있는 실행이
있으면 그 상태와 `[현재 실행도 중지]`를 바로 옆에 보여 주며, 미래 예약을 막은 것만으로 현재
실행의 데이터 변경까지 멈췄다고 표시하지 않는다. 중지 미확인은 Canvas에 남긴다.
권한 범위 안의 일시정지는 추가 확인창 없이 처리하고 `[예약 재개]`는 그 자동화만 재개한다.
밀린 실행의 처리 정책은 기존 예약 정책을 따르며 재개 클릭만으로 중복 실행을 만들지 않는다.
상세의 `[목록으로 돌아가기]`는 원 항목으로, `Esc`는 원 Agenda로 돌아간다. 실패는 원 상태와
`[상태 다시 확인]`을 남긴다. Agenda bar가 보이는 상태에서 메뉴 1 + `[실행·예약]` 1 + 자동화
선택 1 + `[예약 일시정지]` 1 = 4클릭이다. 닫힌 Agenda 찾기·열기와 현재 실행 중지는 별도다.

<a id="library-groups"></a>

**자료를 재사용하고 화면을 묶는 분기 — 제안**: 사용자는 검토가 끝난 자료를 다음 Agenda에서도
찾고, 두 Agenda의 뷰를 함께 정리하려 한다. Library는 명시적으로 등록한 Resource·Saved Agenda·
결과·Snapshot을 찾는 독립 재사용 영역으로 추천한다. 등록은 기존 대상의 참조를 보존하며 모든
PC의 파일·Chat·실행·로그인을 자동 수집하지 않는다. 이 분기는 Library 후보가 채택될 때의
사용 흐름이며 독립 Library가 이미 확정됐다는 뜻은 아니다. 임시 그룹·실행 중 process·로그인
자격 자체는 등록하지 않는다. 등록한 Snapshot의 보존은 기존 참조 기반 보존 정책 안에서 처리하며
전체 원문을 추가 캡처하거나 권한·보존 제한을 자동 확대하지 않는다.

**그룹의 경계**: 중첩은 허용하되 한 뷰·그룹은 한 상위 그룹에 배치하고 자기 자신·하위 그룹
안으로 이동하는 경로는 선택할 수 없게 하는 안이다. `임시`는 별도 업무·권한 단위가 아니라는
뜻이며 앱을 다시 켤 때 반드시 없어지는 뜻이 아니다. 여러 Agenda가 섞인 그룹의 저장 미리보기는
선택한 Agenda의 뷰·배치만 포함하고 다른 Agenda의 구성원을 함께 저장하지 않는다.

**실패·취소·복귀**: Library의 원본이 offline이거나 권한이 없으면 그 상태와 `[다른 원본 연결]`·
`[목록으로 돌아가기]`를 제공한다. 실제로 보존했고 열람 가능한 Snapshot만 별도로 열 수 있다.
이름·URL이 같아도 계정·PC가 다르면 같은 live 자원으로 합치지 않는다. 등록·공유 선택 취소는
원 자료와 초안을 유지한다. `[Library에서 제거]`는 등록만 해제하고, `[그룹 해제]`는 배치 관계만
푼다. 원 자료·실행을 삭제하거나 종료하지 않는다. 한 Agenda를 닫으면 그 뷰만 그룹에서 빠지고
다른 Agenda의 참조 뷰는 남을 수 있지만 실행 소유를 공유하지 않았다면 live 실행 유지까지
보장하지 않는다. 종료된 연결은 `실행 종료`로 표시한다. 등록 실패는 `등록되지 않음`, 그룹 기록
실패는 `배치 저장 안 됨`으로 표시하고 현재 화면·초안을 유지한다. `[다시 저장]`은 실패한 기록만
재시도하며 `Esc`로 목록을 닫으면 원 Agenda·뷰로 돌아간다.
**완료 근거**: Library에서 다시 연 대상의 출처·권한·live 공유 여부와 실행 소유가 일치한다.
앱을 다시 열면 세션 그룹을 복원하고, Saved Agenda에는 명시적으로 저장한 배치만 나타난다.
**대안·손실**: 독립 Library 없이 검색·Saved Agenda만 쓰면 별도 등록 관리가 줄지만 선별한
재사용 자료를 모으기 어렵다. 그룹을 매번 풀거나 중첩을 막으면 단순하지만 반복 정리와 큰 배치의
표현 제약이 생긴다. live 자원을 항상 독립적으로 열면 변경 간섭은 줄지만 실행 중복·자원 사용과
계정 연결이 늘어난다. 이 값들은 [Agenda 정책](#decision-agenda)의 독립된 선택이다.

**배치·조작 세부**: 대상 Agenda가 선택된 Desk에서 Sidebar `[Library]` 1 + 항목 선택 1 +
`[이 Agenda에 참조 추가]` 1 = 3클릭이다. 선택 상세의 상단에 대상 Agenda·원본 PC/계정·실행
소유를 남기고 출처 이력만 접는다. 등록은 자료 bar `[⋯]` 1 + `[Library에 추가]` 1 + `[등록]` 1
= 3클릭이며 포함 대상을 바꾸면 추가된다. 두 뷰의 bar를 `Shift`를 누른 채 각각 선택하는 2클릭
뒤 선택 영역 바로 위의 `[그룹으로 묶기]` 1 = 3클릭이다. 그룹 경계는 선택한 그룹만 강조하며
모든 중첩 테두리를 같은 강도로 쌓지 않는다. `[실행 함께 사용]`은 선택 상세의 별도 행동으로,
해당 실행·대상 Agenda·유지 범위를 같은 영역에서 고르고 `[적용]`한다.

**동시에 같은 원본을 고칠 때**: 두 Agenda의 뷰가 같은 파일을 가리킨다는 사실을 표시한다.
독립적인 편집·분석은 계속하지만, 저장 전에 다른 변경이 확인되면 해당 저장만
`원본이 변경됨`으로 남기고 `[변경 비교]`에서 원본·각 수정 내용을 연다. 위임된 Agent가
기존 범위 안에서 병합·검증할 수 있으면 계속한다. 해결되지 않은 의미 충돌만 사용자에게
선택을 요청하며 어느 사본도 조용히 덮어쓰지 않는다.
**원격 종료를 확인할 수 없을 때**: PC B가 끊기면 `PC B·종료 확인 안 됨`과 마지막 확인
시각·해당 작업이 Canvas에 남는다. `[상태 다시 확인]` 또는 다른 작업으로 이동할 수 있다.
PC A에서 확인된 종료와 저장한 내용은 유지하고, PC B 재접속 시 종료 요청·실제 결과를
대조한다. `닫기 요청됨`과 `닫힘`을 구별하며 재접속만으로 그 작업·예약을 재개하지 않는다.
**취소·복귀**: 6–7단계 취소는 열린 Agenda와 실행을 유지한다. 저장 실패면 `저장되지 않음`과
편집 내용을 남기고 `[다시 저장]`·`[복구용 초안으로 닫기]`·`[취소]` 중 가능한 경로를 제공한다.
보존하지 못하는 form은 닫기 전에 그 범위를 알린다. 종료 요청 이후에는 이미 끝낸 process를
되돌렸다고 표시하지 않는다. 다시 열기는 화면·자료 복원이며 Terminal의 새 시작과 구별한다.
이미 외부로 전송된 요청의 취소 여부도 별도다.
**확인 기준**: 단순 자료 참조가 남았다는 이유만으로 `자료 검토`의 작업을 `문서 수정`으로 넘기지 않는다.
Agenda 이름과 PC 이름은 각각 구별해 표시한다. 닫힌 Agenda의 전용 실행은 종료가 확인되고,
공유 실행은 이를 소유하는 열린 Agenda에서 계속 보인다. 다시 열었을 때 저장 구성·초안·
재개 전 상태를 확인할 수 있다. 공유·미저장·실행 영향이 없는 닫기에는 매번 확인 창을 요구하지 않는다.
**대안**: 예약을 함께 삭제하면 의미가 단순하지만 재설정이 필요하다. 계속 실행하는 대안은
닫기 전에 다른 Canvas 소유 표현을 명시적으로 남겨야 한다.

<a id="agenda-delete-recover"></a>

**저장한 Agenda를 삭제하고 복구하는 분기 — 제안**: `[닫기]`는 화면과 전용 실행을 닫고
저장본을 남긴다. Sidebar의 `[저장한 Agenda 삭제]`는 저장본을 휴지통으로 옮기는 별도 조작으로
추천한다. 열려 있다면 먼저 같은 닫기 처리를 거치며, 종료를 확인하지 못한 작업을 화면에서
숨기지 않는다. 휴지통은 보관 위치이지 실행 장소가 아니다.

|---:|---|---|---|---|
| 1 | Sidebar의 Agenda 행 `[⋯]` → `[저장한 Agenda 삭제]` | 이름·저장 revision·포함 자료, 닫힐 전용 실행·예약과 다른 Agenda에 남는 공유 실행이 보인다 | 삭제 권한·현재 저장본·참조·열림 상태를 조회; 외부 원본 파일은 삭제 대상에서 제외 | 요청받으면 영향 설명만 수행 |
| 2 | `[닫고 휴지통으로 이동]`을 누른다. 이미 닫혀 있으면 `[휴지통으로 이동]` | 미저장 편집은 위의 저장/초안 선택으로 이어지고, 이후 PC별 종료 상태가 보인다 | 전용 실행과 자동 재개를 막고 종료 확인 후 저장본·복구 가능한 구성과 참조를 휴지통으로 이동 | 중지 대상의 새 행동 없음; 다른 업무 계속 |
| 3 | 완료 안내의 `[휴지통에서 보기]` | 삭제 시각·보관 중인 구성·복구 가능한 내용과 더 이상 접근할 수 없는 자료가 보인다 | 일반 Sidebar 목록에서는 제외; 휴지통 참조에 필요한 허용된 자료는 보존 | 없음 |
| 4 | 휴지통에서 해당 Agenda 선택 → `[복구]` | 원 이름과 복구 위치가 보인다. 이름이 겹치면 새 표시 이름을 입력할 수 있다 | 같은 Agenda의 보존된 저장 이력을 Sidebar로 복구; 이름이 같은 다른 Agenda를 덮지 않음 | 없음 |
| 5 | `[복구한 Agenda 열기]` | 구성·허용된 과거 자료가 열리고 live 재연결·중지된 업무가 구별된다 | 권한을 다시 검사; 과거 권한·Engine 인증·실행·예약은 자동 복원하지 않음 | `[계속]` 등 실제 실행 지시 전에는 없음 |
| 6 | 필요할 때 휴지통의 해당 항목 → `[영구 삭제 영향]` → 범위 확인 → `[영구 삭제]` | 복구할 수 없게 되는 저장 이력, 다른 Answer·Agenda에서 계속 쓰는 자료, 보존 제약과 외부 사본이 보인다 | 선택 저장본과 전용 참조를 제거; 공유 중인 원문·대화·Snapshot은 삭제하지 않으며 미참조 자료 정리는 별도 결과로 확인 | 별도 삭제 범위를 추정하지 않음 |

**실패·취소·복귀**: 확인 전 `[취소]`는 원 행·Canvas·초안을 그대로 둔다. 종료 응답이 없으면
`삭제 대기·종료 확인 안 됨`인 Agenda를 Canvas에 남기고 `[상태 다시 확인]`·`[삭제 중단]`을
제공한다. 삭제 중단은 저장본을 유지하지만 이미 끝낸 실행을 되살리지 않는다. 저장본이 그사이
바뀌면 `[변경 내용 보기]`로 현재 삭제 범위를 다시 보여 주고, 확인하지 않은 새 내용을 함께 지우지
않는다. 휴지통 이동 실패는 저장본·확보한 초안을 유지하고 해당 이동만 재시도한다. 영구 삭제의
일부가 실패하면 `삭제됨·남음·확인 안 됨`을 구별하며 성공한 삭제를 되돌릴 수 있다고 표시하지 않는다.
복구 화면의 `[취소]`는 휴지통으로, 상세의 `Esc`는 시작한 목록 행으로 돌아간다.
저장 이력의 복구 적용에 실패하면 휴지통 항목을 유지하고 완료로 표시하지 않는다.
`[복구 다시 시도]`·`[휴지통으로 돌아가기]`로 해당 복구만 이어 가거나 목록으로 돌아간다.
**완료 근거**: 휴지통 이동이 저장됐고 전용 실행의 종료가 확인된 때만 `삭제됨·복구 가능`으로
표시한다. 복구 뒤 같은 저장 이력을 열 수 있고 자동 실행은 없다. 영구 삭제 후에는 복구 가능
표시를 없애며, 참조 제거·실제 데이터 정리·외부 사본 회수 여부를 한 가지 완료로 합치지 않는다.
공유 Agent 방 전체나 원본 폴더는 Agenda 하나를 지웠다는 이유로 사라지지 않는다.
계정 연결·공유 인증 정보도 해제하거나 삭제하지 않는다. 연결 해제는 [초기화 화면](#data-reset)에서 별도로 선택한다.
**추천·대안·손실**: 휴지통은 사용자가 비울 때까지 유지하는 안을 추천한다. 복구 가능성이 높지만
저장량이 남으며 별도 권한 철회·보존 제한을 우회하지 못한다. 기간 후 자동 비우기는 공간을 줄이는
대신 복구 기한이 생기고, 즉시 영구 삭제는 단순하지만 오삭제 복구가 어렵다. 이 보관 정책은
예약의 pause/삭제와 다른 선택이며 [HUM-AGENDA-001](../../codex/egdesk-product-interaction-trace-atlas-editorial-ledger.md#hum-agenda-001)에 연결한다.

**배치·진입 비용**: `Sidebar: 저장본 목록 │ Canvas: Agenda A + Agenda B │ 행 옆: 선택 메뉴`.
보이는 Saved Agenda 행 열기는 1클릭이다. 이미 닫힌 저장본의 삭제는 행 `[⋯]` 1 +
`[저장한 Agenda 삭제]` 1 + `[휴지통으로 이동]` 1 = 3클릭이다. 열린 실행·미저장 내용이
있으면 앞의 종료/저장 분기가 추가되므로 3클릭이라고 요약하지 않는다. 휴지통 진입 1 + 항목
선택 1 + `[복구]` 1 = 복구 3클릭이며 열기는 별도 1클릭이다. 삭제 확인은 선택 Agenda의
영향만 보여 주며 30개 Agenda의 전체 실행 목록을 한 확인창에 늘어놓지 않는다.

### 다른 탭에서 일하며 Agent 활동을 보고 돌아온다

**상황**: 사용자는 탭 A를 편집하고 Agent는 화면 밖 탭 B를 조작한다.
**연결**: 후보 4·8–10, ECS-03, CAP-05/06/08,
[Atlas V-02](../../../ideas/confirmed/EGDESK_PRODUCT_INTERACTION_TRACE_ATLAS.md#atlas-v-02),
[입력·관찰 계약](../../../ideas/confirmed/EGDESK_INTERACTION_AND_ORCHESTRATION_CONTRACT.md#tech-collaboration-computer-use).

**추천안**: 단일 live 활동은 활동 표시에서 현재 조작면을 열고, 완료된 읽기·명령은 당시
Snapshot을 연다. 동시에 여러 활동이면 Chat 안에서 대상·담당자를 고른다. 기본 탐색은
한 번 이동이며 지속 따라보기는 사용자가 별도로 켠다. 집중 보기는 우선 카메라 확대만
사용하고 Browser viewport는 유지하는 안을 제안한다. 내부 viewport를 넓히려면 명시적인
resize를 사용한다.

```text
Chat: 검토 Agent · 자료 비교
      ··· 2개 활동  [Browser B · 입력 중] [Reader · 읽는 중]

Canvas: Browser B                          [Chat으로 돌아가기]
        Live · Agent 작업 중              [당시 관찰] [따라보기: 꺼짐]
```

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | 탭 A에서 입력하거나 Canvas를 pan한다 | A의 입력과 카메라 이동이 유지된다 | B의 안정적인 대상·내부 좌표·관찰 시점을 유지 | 위임된 B 작업 계속 |
| 2 | Chat의 `[··· 2개 활동]` → `[Browser B]` | Canvas가 B를 보여주며 `Live·Agent 작업 중`과 복귀 컨트롤을 표시 | 원 카메라·Chat 위치·초안을 보존하고 B를 연결 | 관찰 열기 때문에 재시작하지 않음 |
| 3 | `[당시 관찰]`을 누른다 | Agent가 받은 screenshot/DOM/추출 자료의 읽기 전용 Snapshot이 별도로 열린다 | 정확한 전달 payload와 시각을 조회 | 추가 호출 없음 |
| 4 | `[현재 화면]`으로 돌아가거나 `[따라보기]`를 켠다 | 현재 대상의 변화와 Agent pointer가 보인다 | 선택한 활동에만 관찰 연결, 입력권은 주지 않음 | 기존 작업 계속 |
| 5 | 직접 pan·zoom하거나 다른 view를 선택한다 | 따라보기가 해제되고 사용자가 고른 화면에 머문다 | 카메라 추종만 종료, Agent 대상은 유지 | 기존 대상에서 계속 |
| 6 | view bar를 두 번 누르고 나중에 `[집중 보기 종료]` 또는 `Esc` | 비율을 유지한 확대 후 이전 시점으로 돌아온다 | 제안 정책에서는 camera만 변경; Browser layout을 재생성하지 않음 | 단순 확대만으로 재관찰 요구하지 않음 |
| 7 | 같은 Browser의 resize handle을 드래그하거나 `[크기]`에서 값을 입력한다. 또는 내용을 직접 바꾼다 | 새 크기·내용과 사용자 입력이 보인다 | 실제 layout·관찰 revision 변화에 걸린 미실행 조작을 재검증; 단순 pan은 제외 | 다음 호출에서 재관찰·행동 조정 |
| 8 | Agent가 업로드를 준비하는 동안 A에서 계속 작업한다 | 지원되는 파일 전달은 A를 이동시키거나 picker를 갑자기 띄우지 않는다 | 가능한 파일-input/지원 adapter 경로로 B에 전달; 외부 전송 권한은 별도 검사 | 허용된 업로드 수행 |
| 9 | 사용자 조치가 필요한 경우 관련 Chat의 `[권한 요청 보기]`를 누른다 | 필요한 권한·대상·이후 작업의 설명이 실제 권한 UI와 연결된다 | 플랫폼이 허용하면 설명과 native 요청을 함께 표시; 불가능하면 설명을 보존한 채 요청을 열고 복귀 | 해당 단계만 기다리며 독립 작업 계속 |
| 10 | `[Chat으로 돌아가기]` | 원 Chat 위치와 초안·Canvas 시점으로 돌아온다 | 저장한 탐색 위치를 복구; File의 active caret는 복원하지 않음 | 작업 상태 불변 |

**화면 밖 보존**: 폴더 확장·scroll·뷰 identity는 유지할 수 있고 무거운 renderer만 분리한다.
다시 보인다는 이유로 모든 데이터를 새로 읽는 정책을 요구하지 않는다. Browser DOM이
살아 있으면 일반 form 값은 그 상태로 남지만, reload나 runtime 종료 후 동일 form을
보장하지 않는다. 정확한 form 복구 범위는 [보존 선택](#decision-retention)에서 다룬다.
**예외·복귀**: native modal의 거부·취소는 해당 업무에 결과로 연결하고 원 화면으로 복귀한다.
사이트별 custom drop·파일시스템 API·popup·focus 격리는 지원 adapter와 실제 Firefox 검증으로
확인한다. 모든 사이트의 HTML을 다시 쓰는 방법을 기본 전제로 삼지 않는다.
파일 전달 지원이 없으면 해당 작업에 `[직접 파일 선택]`과 보낼 파일·업무 계정을 보여 주고,
사용자가 선택을 시작할 때만 picker를 연다. 취소하면 업로드 전 상태와 준비한 파일 참조가 남는다.
업로드 응답이 끊겼다면 `전송 결과 확인 중`으로 표시하고 접수 여부를 먼저 조회한다.
**현재 화면을 받지 못할 때**: 마지막으로 본 화면에 확인 시각과 `연결 끊김`을 표시한다.
이를 Live라고 계속 표시하거나 자동으로 다른 PC의 같은 제목 창에 붙이지 않는다.
자동 재연결 후 같은 대상·입력권이 확인되면 최신 화면으로 돌아가고, 확인되지 않으면
`[작업 위치 확인]`에서 원 대상을 다시 연결한다. 관찰 연결 해제나 `Esc`는 Agent 중지가 아니다.
**대상·입력 방식의 표시**: 활동 행과 Browser bar에 같은 짧은 탭 구분 표시를 남겨 비슷한
제목의 창도 연결해 찾을 수 있게 한다. bar의 `[작업 대상·입력 방식]` 1클릭은 그 View 안의
상단 상세를 펼쳐 PC·Browser instance·업무 profile/account·tab/frame·renderer·마지막 관찰을
보여 준다. 현재 보는 방식 `관찰`과 실제 입력 담당자 `Agent/사용자/없음`은 구별한다.
사용자 작업과 분리된 입력 경로가 확인된 때만 `다른 View에서 작업 계속 가능`으로 표시하며,
물리 입력을 쓰는 단계는 `공용 입력 사용 중`, 사용자 조치가 필요하면 `사용자 입력 필요`를
기본 상태에 표시한다. 포인터가 따로 보인다는 이유만으로 비간섭이 보장된다고 쓰지 않는다.
`[상세 접기]`는 같은 bar로 돌아가며 사이트 위에 설명을 덮지 않는다. 자료 A로 돌아온 뒤의
File 삽입점은 사용자가 다시 선택한다. 화면 복귀와 정확히 같은 편집 위치 재개는 구별한다.
**확인 기준**: A의 초안과 입력이 유지되고 B의 실제 작업 대상·계정·입력 담당자를 확인할 수
있다. 조작이 완료되면 사이트의 접수·저장 결과 또는 실패·미확인 범위가 활동에 연결된다.
관찰 화면이 열렸다는 사실만으로 업로드·외부 업무를 완료로 표시하지 않는다.
**대안**: 활동 진입을 항상 Snapshot으로 하면 당시 근거는 명확하지만 현재 조작면까지 한 단계
더 필요하다. 집중 보기에서 viewport도 넓히면 실제 내용이 더 보이지만 layout 재관찰이 필요하다.

**배치·진입 비용**: `Chat 활동 표시 → Canvas의 Browser B / B bar에 복귀·관찰 상태`.
기본 Chat에는 `··· 활동 2개`만 보이고 위 그림의 대상 목록은 누른 뒤 펼친 상태다. 단일 활동은
표시 1클릭으로 해당 조작면, 여러 활동은 표시 1 + 대상 1 = 2클릭이다. `[Chat으로 돌아가기]`
1클릭으로 복귀한다. 지속 따라보기·당시 관찰은 B의 bar 근처에 두고 원 사이트 HTML 위에
고정 툴바를 덧씌우지 않는다. 관찰 때문에 새 Browser 사본·새 전체 Chat을 반복 생성하지 않는다.

**추천안**: 기본 Chat에는 `자료 읽는 중` 정도를 표시하고 상세는 원할 때 연다. Reader 전환,
partition과 같은 원문의 재질문은 자동 진행한다. Child는 parent 한도 안에서 실행하며,
예산 수치·동시성은 estimator와 측정으로 정한다. 다른 Engine 계정이나 유료 경로로 조용히
넘기지 않는다.

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | 파일을 File view로 열거나 Chat에 드롭한다 | 파일명과 `보기·AI 읽기·편집`의 지원 여부가 구별된다 | 형식·권한·크기를 확인 | 없음 |
| 2 | `A의 납기 조건과 B의 같은 항목을 비교해줘` 입력 → `[전송]` | 요청·자료와 활동 표시가 보인다 | 입력과 자료 참조를 결합 | 조건에 맞는 검색·읽기 전략을 계획 |
| 3 | 별도 조작 없이 기다린다 | 큰 자료도 동일 업무 아래에서 읽힌다 | 담당 Agent의 여유·답변 reserve·자료형식·반환량을 평가한 뒤 direct/Reader 결정; 이후 Reader 분할 판단 | Reader는 읽기만 수행하고 담당 Agent가 비교·판단 소유 |

| 8 | 앱의 업무 한도에 도달하면 `[한도 조정]` 또는 `[이 업무 중지]`; Engine quota가 없으면 `[사용량 회복 대기]`, `[다른 Engine 선택]`, `[중지]` 중 가능한 행동을 선택 | 보존된 결과와 현재 막힌 이유가 구별된다 | 앱 한도와 provider 제한을 분리하고 parent·child 예약·취소에 적용; 불가능한 계속 행동은 활성화하지 않음 | 실제 사용 가능하고 허용된 범위만 진행하며 불충분 범위를 설명 |

**중단·부분 판독**: 원본 PC가 끊겨도 이미 허용 범위에서 확보한 Snapshot의 읽기·비교는
이어진다. 추가 자료만 `PC 연결 대기`로 표시하고 `[연결 상태 보기]`·`[다른 자료 연결]`을
제공한다. 권한이 철회된 자료는 연결 장애와 구별해 후속 열람·재사용 조건을 다시 확인한다.
`[이 업무 중지]`는 대기 중인 추가 읽기를 막고 종료가 확인된 Reader를 중지 상태로 남긴다.
이미 읽은 범위와 허용된 근거는 보존하되 늦게 도착한 packet이 취소한 분석을 다시 시작하지 않는다.
**확인 기준**: 결과에는 확인한 자료·범위, 읽지 못한 범위와 그 영향을 함께 표시한다.
`[읽지 못한 부분 보기]`에서 해당 자료만 다시 연결하거나 제외할 수 있다. 실제 측정값이 없는
사용량은 `추정` 또는 `확인 불가`로 남긴다. 일부 판독 성공을 전체 원문 검토 완료로 표시하지 않는다.

**원문과 설명을 함께 대조하는 배치**: 설명 메시지의 `[⋯]` → `[근거와 함께 보기]`는 선택한
설명 블록을 읽기 상세 상단에 남기고 그 아래에 실제 전달 자료·범위·미판독 사항을 보여 준다.
기간·대상처럼 그 설명을 한정하는 조건도 함께 남긴다. 긴 블록은 펼쳐 읽을 수 있고 전체
Chat을 복제하지 않는다. 상세가 Chat 본문을 바꿔도 대조 중인 문장과 작성기는 유지된다.
설명을 이미 고른 상태에서 이 메뉴 경로는 2클릭이며, 대화와 상세를 반복 왕복할 필요가 없다.
기존 비교 View에서는 원문·결과의 선택 행/영역을 유지한다. 폭이 부족하면 `[비교에 집중]`으로
사용자가 두 자료와 설명을 보는 배치로 전환하고 `[이전 배치로 돌아가기]`로 원 Canvas·Chat을
복구한다. 다른 Browser의 내부 크기를 바꾸거나 Agent의 작업 대상을 이동시키지 않는다.

**독립 검토를 별도로 요청하는 분기 — 제안**: 같은 Reader에 읽기 방향을 보정하는 것과,
기존 답을 보지 않은 실행 맥락에서 결과를 재현·검토하는 것은 다른 요청이다. 독립 검토는
읽기 도구의 옵션으로 업무를 몰래 넘기지 않고 대상 결과/자료 bar의 `[⋯]` → `[독립 검토 요청]`
에서 연다. 같은 Run 안의 분리된 검토 Task로도 구성할 수 있으며, 일반 교정에 새 Run을 강제하지 않는다.

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | `[독립 검토 요청]`에서 검토 목적·대상·적용 조건을 입력한다 | 별도의 검토 요청과 실제 전달할 자료 후보가 보인다 | 현재 답을 포함한 전체 대화를 자동 상속하지 않고 입력을 구성 | 요청받은 검토 목적에 맞는 방법 제안 |
| 2 | `[전달 자료]`·`[검토자에게 제외할 자료]`에서 범위를 고른다 | 원천·규칙 근거와 제외한 정답/기존 결과를 나눠 보여 준다 | 선택 식별자·시점·접근 범위 고정; 제외 자료가 자동 검색·도구 접근으로 새지 않게 검토 범위 제한 | 제외 내용을 힌트·요약으로 재주입하지 않음 |
| 3 | `[검토 시작]` | 별도 검토 활동과 `[이번 검토의 입력 보기]`가 보인다 | 분리된 context에 허용 입력만 전달; 과거 검토 이력과 구별 | 지정된 검토/재현을 수행. 단순 읽기 요약이면 Reader, 업무 판단이면 해당 검토 책임으로 구분 |
| 4 | 반환된 결과의 `[비교]` | 이전 결과·새 결과·사용한 근거·아직 검토하지 못한 범위가 보인다 | 입력·산출물·검사 근거를 연결 | 담당 Agent가 차이·실패·남은 확인을 통합 |

이 흐름의 `지시 반영`, `다시 계산됨`, `독립 검토에서 확인됨`은 다른 상태다. 숫자가 일치해도
원천·규칙·판정 조건을 만족하지 않으면 전체 재현 완료로 표시하지 않는다. 선택 취소는 원 업무·
결과를 유지하고, 검토 중지는 해당 검토만 멈춘다. 사용자 열람을 기다려 모든 통합을 막지는 않는다.

**형식별 출시 추천 범위 — 아직 지원 약속이 아님**

| 형식 | 사람용 보기 | AI 판독 | 직접 편집 추천 범위 | Snapshot·fallback |
|---|---|---|---|---|
| 텍스트·Markdown·코드·JSON | 텍스트/구조 보기 | 범위·검색·전체 읽기 | 원문 편집·diff | 원문 byte·범위; 잘못된 encoding 별도 처리 |
| PDF | 페이지 보기 | text·page image, 필요 시 OCR | 주석 우선, 문서 구조 재편집은 후속 | 원문·page/range·추출 관계 |
| 이미지 | 이미지·확대 | vision 판독 | annotation 우선 | 원 이미지·영역, 판독 불가를 표시 |
| CSV/TSV | 표 | 행·열·범위 | 값 편집 | 원문·table range |
| XLSX·문서·슬라이드 | preview + 원본 연결 | 지원 parser의 구조·내용 | 첫 단계는 외부 편집/연결과 변경 확인 | 원본·preview·추출 범위; 복잡한 서식 보존은 별도 검증 |
| HTML | inert preview 또는 source | DOM/text·원문 | source 편집을 별도 제공 | snapshot에서 script/network를 자동 실행하지 않음 |
| 기타 binary | 형식·크기·경로 | 지원 adapter 없으면 사용 불가 | 외부 앱 연결 | 지원하지 않는 기능을 별도로 표시 |

**대안**: 모든 office 형식의 완전한 내장 편집을 첫 출시 범위로 잡으면 사용은 통일되지만
서식·수식·재저장 검증 범위가 커진다. 필요한 형식부터 기본 보기·판독·변경 확인을 완성하는
안을 추천한다. Reader estimator·parser·viewer 선택은 외부 구현을 조사해 정할 수 있으며
매번 사용자에게 기술 제품 선택을 묻지 않는다.

**배치·진입 비용**: `Canvas: 첨부 자료 │ Chat: 읽는 중 → 같은 본문의 읽기 상세`.
해당 업무가 보이면 `[읽기 상세]` 1클릭이다. 그 상세에서 `[읽기 방향 수정]` 1 + `[적용]` 1 =
방향 수정 2클릭이며 문장 입력은 별도다. 기본 표시에는 자료 개수·진행/막힘만, 펼친 상세에는
선택 자료·읽은 범위·실패 이유를 우선 배치한다. 개별 partition·호출·사용량 이력은 그 아래
접어서 두며 Agent마다 큰 카드를 나란히 추가하지 않는다. 원문 열기는 실제 Canvas 자료로 연결한다.

### 당시 근거를 확인하고 수정 결과를 새 설명에 연결한다

**상황**: Agent의 비교표·Chat 설명·Briefing이 있고, 사용자는 원문 근거를 본 뒤 표를
고치고 특정 단계에 의견을 남긴다. **연결**: 후보 4·11·16, ECS-06, CAP-08/13,
[Snapshot 계약](../../../ideas/confirmed/EGDESK_INTERACTION_AND_ORCHESTRATION_CONTRACT.md#tech-observation-fidelity),
[Briefing 계약](../../../ideas/confirmed/EGDESK_INTERACTION_AND_ORCHESTRATION_CONTRACT.md#tech-answer-briefing).

**추천안**: 당시 근거와 Answer는 보존하고 편집 가능한 결과를 별도 사본으로 만든다.
Briefing은 설명한 결과 revision에 고정하며 새 설명을 요청할 때 새 결과에 연결한다.
주석을 무조건 새 결과로 옮기지 않는다. 원문을 지울 때는 관련 근거·파생물·알려진 사본의
영향을 보여 주고 범위를 선택한다.

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | Chat 결과의 `[당시 근거]` | 읽기 전용 Snapshot과 캡처 시각·Agent 전달 범위가 보인다 | 허용된 과거 payload를 열고 원 대화 위치 보존 | 현재 원문을 다시 읽어 과거처럼 대체하지 않음 |
| 2 | `[현재 원본]` 또는 `[비교]` | 현재 Live와 당시 내용이 구별된다 | 새 live 참조·관찰을 연결 | 열람만이면 없음 |
| 3 | `[결과로 돌아가기]` → 원 Answer의 비교표 선택 → `[사본으로 편집]` | 수정할 비교표 revision과 별도 편집 사본이 보인다 | 선택한 비교표 artifact의 사본을 만들고 원 결과·근거 Snapshot에 연결; 방금 본 원문을 편집 대상으로 바꾸지 않음 | 필요할 때만 편집 가능한 파생 결과 생성 |
| 4 | 값을 수정하고 `[사본 저장]` | 저장한 결과와 기존 Answer가 참조하는 결과가 구별된다 | 새 결과 revision을 저장; 과거 snapshot은 유지 | 명시적으로 검토를 요청받은 경우만 비교 |
| 5 | `[이 결과로 설명 갱신 요청]` | 새 요청과 생성 중인 설명이 보인다 | 수정 결과·기존 Answer를 다음 요청 context로 연결 | 새 결과를 해석해 Chat·Canvas 설명을 구성 |
| 6 | 완료된 설명의 `[브리핑 보기]` → `[다음]` → `[이 단계에 의견]` → 의견 입력 | 해당 결과·단계에 연결된 주석 초안이 보인다 | 설명·target revision을 유지; 이동은 새 Run을 시작하지 않음 | 보기·단계 이동에는 없음 |
| 7 | `[다음 메시지에 첨부]` → Chat에서 문장 작성 → `[전송]` | 원 단계·의견이 요청에 포함된다 | 실제 전송 시 참조·권한·변경 여부 확인 | 후속 요청을 처리하며 원 주석을 임의 이사시키지 않음 |
| 8 | 원 Answer의 `[근거]` → 삭제할 원문 Snapshot 선택 → `[삭제 영향]` | 근거가 사라질 Answer·Briefing과 남는 파생물·알려진 export가 보인다 | 선택한 원문 Snapshot의 관련 객체와 실제 삭제 가능 범위를 조회 | 설명상 영향은 요약할 수 있으나 삭제 결정은 하지 않음 |
| 9 | 삭제할 범위 선택 → `[선택 항목 삭제]` 또는 `[취소]` | 삭제·접근 제한 상태 또는 원래 근거가 보인다 | 정책상 허용된 명시 대상을 처리; 다른 payload로 바꾸어 표시하지 않음 | 별도 요청이 없으면 없음 |
| 10 | `[Chat으로 돌아가기]` | 원 대화와 초안으로 복귀한다 | 탐색 위치만 복구 | 작업 상태 불변 |

**취소·복귀**: 사본 편집 취소는 원 Snapshot을 유지한다. 설명 생성 중지는 저장된 사본과
이전 설명을 지우지 않는다. 삭제 확인 전 취소는 무변경이며, 영구 삭제 뒤 복구 가능성을
보장하지 않는다. 자료를 받은 외부 사본은 로컬 삭제로 회수됐다고 표시하지 않는다.
저장하지 않은 사본을 닫을 때는 `[저장]`·`[초안 유지]`·`[편집 계속]`을 보여 주며,
저장 실패를 성공으로 바꾸지 않고 해당 내용을 유지한다. Briefing 도중 닫기는 원 대화·초안으로
복귀하고 새 설명이 생성 중이면 그 작업은 별도로 계속된다.
**근거 접근이 바뀔 때**: 원문 권한 철회가 확인되면 정책상 제한되는 payload를 열린 뷰와
다음 호출에서 다시 사용하지 못하게 한다. 해당 근거에는 `접근할 수 없음`과 설명에 남는
검증 한계를 표시하며 현재 원문으로 대체하지 않는다. `[허용된 다른 근거 연결]`은 새 결과에
연결하고 과거 Answer의 출처를 바꾸지 않는다. 삭제 일부만 성공했으면 삭제됨·남음·결과 미확인을
항목별로 구별하고 재확인은 미완료 대상에만 적용한다. 파생 설명·개인 사본의 보존 범위는
[보존 선택](#decision-retention)에 따른다.
**주석 재연결 제안**: `[새 결과에 다시 연결]`을 사용할 때 이전·새 대상과 차이를 보여 준다.
문장의 의미가 여전히 맞는지는 Agent가 제안할 수 있으나, 원 target이 바뀐 사실은 남긴다.
**원본을 바꾸기 전 시안을 비교하는 분기**: 사본 bar의 `[⋯]` → `[원본과 사본 비교]`는
원본 변경 알림이 없어도 기존 비교 View를 연다. 알려진 원본 연결을 사용하며 별도 시안이라
연결이 없으면 같은 상세의 `[비교할 원본 선택]`에서 지정한다. 제목·파일명만으로 정본을 추정하지 않는다.

```text
비교 View                                 [비교에 집중] [원 결과로]
검토할 설명: 선택한 설명 블록 · 적용 조건
원본 · 적용 대상 · revision · 미리보기 방식 │ 사본 · 미반영 · revision · 미리보기 방식
               선택 영역                  │                 대응 영역
선택 변경 n개                             [선택 변경 수락·적용]
```

양쪽에 `원본/사본·revision·미리보기 방식`을 계속 표시한다. 예를 들어 내장 preview와 외부 앱
렌더가 다르면 그 차이를 구별하며 동일한 렌더링 결과라고 가정하지 않는다. 지원하는 형식에서만
같은 행·슬라이드·페이지 영역을 맞춰 보고, 대응을 계산할 수 없으면 각각 선택하게 한다.
`[사본 저장]`·`[설명 갱신]`만으로는 `원본 미반영`이 바뀌지 않는다. 원본에 반영하려면
[변경 적용 흐름](#collaboration-changes)의 범위 선택·수락·실제 저장 확인을 거친다.
원본 연결이 있는 사본 bar가 보이면 비교 진입은 2클릭, 그 뒤 변경 한 범위 선택 1 + 적용 1 =
총 4클릭이다. 범위 추가·원본 연결·외부 편집·인증은 별도다. 비교 종료는 원 사본과 초안으로
돌아가며, 적용 실패는 두 자료를 보존한다. 선택하지 않은 시안은 공유 원본에 미리 반영하지 않는다.
**확인 기준**: 저장한 사본의 수정 내용과 새 설명이 가리키는 결과가 일치한다. Chat·Canvas는
같은 Answer를 각 매체로 표현하고, 별도 결과처럼 중복 생성하지 않는다. 예전 설명·주석은
원 대상에 남으며 새 연결·삭제·권한 제한의 실제 결과를 확인할 수 있다.
**대안**: 편집할 때마다 새 Briefing을 자동 생성하면 빠르지만 비용·알림이 늘어난다.
명시적인 설명 갱신 요청을 기본으로 제안한다.

**배치·진입 비용**: `Canvas: 비교표 + 선택 근거 │ Chat: 완결된 답변 / Briefing: 현재 단계`.
결과가 보이는 Chat에서 `[당시 근거]` 1클릭으로 근거 View를 연다. `[현재 원본]` 1클릭은
그 View의 현재/당시 전환이며, `[비교]`를 선택했을 때만 두 내용을 함께 놓는다. 브리핑 시작은
`[브리핑 보기]` 1클릭, 다음 단계는 `[다음]` 1클릭이다. 단계 설명·이전/다음은 현재 산출물
가까이에 두고 전체 근거·모든 단계·모든 주석을 동시에 펼치지 않는다. 전체 단계 목록은 필요할 때
열되 현재 단계와 `[Chat으로 돌아가기]`는 계속 찾을 수 있다.

<a id="flow-portable"></a>
### 여러 PC의 작업을 이어 가고 필요한 자료를 파일로 옮긴다

**상황**: 하나의 Agenda에서 PC A의 Browser와 PC B의 파일·실행을 사용한다. 사용자는
어느 PC의 작업인지 확인하고 연결이 끊겨도 가능한 일을 이어 간다. 자료만 다른 환경에
옮기려는 경우에는 별도로 내보내기를 사용한다. **연결**: 후보 12·18, ECS-01, CAP-09/10,
[내보내기 계약](../../../ideas/confirmed/EGDESK_INTERACTION_AND_ORCHESTRATION_CONTRACT.md#tech-portable-bundle),
[협업 계약](../../../ideas/confirmed/EGDESK_INTERACTION_AND_ORCHESTRATION_CONTRACT.md#tech-collaboration-computer-use).

여러 PC를 실행 자원으로 쓰는 능력은 최종 제품 방향이다. 아래 PC 선택·상태 표시·복구
control은 추천안이며 실제 연결·전송은 승인된 환경과 해당 자원 권한 안에서만 가능하다.
권한·인프라가 준비되지 않은 동안에도 로컬 화면·연결 끊김·중복 방지 시나리오는 검증할 수 있다.

#### 연결된 PC에서 live 작업을 이어 간다

**추천안**: 실행 위치·사용 계정을 활동과 함께 표시한다. 연결이 돌아오면 기존 실행의 상태를
먼저 확인하고 같은 업무를 이어 간다. 허용된 PC 선택은 Agent가 맡을 수 있고 사용자는 필요할
때 재지정한다. PC 변경 자체를 새 Agenda·Run·매번 승인으로 만들지 않는다.

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | Agenda에서 요청을 작성하고, 실행 위치를 지정하려면 `[사용할 PC]` → 연결된 PC 선택 | 요청에 사용할 PC·자료·계정과 연결되지 않은 항목이 보인다 | 실제 기기·자원·Engine·업무 계정의 권한과 가용성을 각각 확인 | 지정하지 않은 실행 위치는 기존 위임 범위 안에서 선택 가능 |
| 2 | `[전송]` 후 다른 자료에서 작업한다 | PC A·PC B 활동이 같은 Agenda의 Canvas에서 보인다 | PC별 실제 실행과 같은 업무의 관계·마지막 확인 상태 기록 | 각 자원에서 가능한 작업을 진행·통합 |
| 3 | PC B가 끊긴 동안 PC A의 결과를 연다 | B는 `연결 끊김·마지막 확인 시각`, A는 실제 진행 상태로 보인다 | B의 새 행동 전달·재실행을 제한; 마지막 결과를 현재 Live로 표시하지 않음 | 확보한 허용 자료와 다른 PC의 독립 작업 계속 |
| 4 | PC B가 다시 연결되면 활동을 확인한다 | `상태 확인 중` 뒤 기존 실행의 `진행 중`·`완료`·`중지됨` 또는 `결과 확인 안 됨`이 보인다 | 같은 기기·실행·자원인지 대조하고 늦은 결과와 취소·조정 이력을 합침 | 최신 지시를 가능한 다음 호출에 반영; 끝난 작업을 다시 수행하지 않음 |
| 5 | 실행을 옮기려면 해당 업무의 `[다른 PC에서 이어서]` → 연결된 PC 선택 | 옮길 수 있는 작업과 원 PC에 남는 실행·미확인 결과, 사용할 계정이 보인다 | 기존 실행의 상태·동시 쓰기·자료 접근을 검사; 파일 사본 import와 구별 | 기존 권한으로 옮길 수 있는 미완료 범위부터 계속 |
| 6 | 외부 요청이 미확인으로 남으면 `[처리 상태 보기]` 또는 `[결과 확인]`을 연다 | 요청 대상·시각·마지막 응답·보류된 중복 행동이 보인다 | 허용된 상태 조회로 접수·완료·미실행을 확인; 연결 시간 초과만으로 실패 단정하지 않음 | 불명확한 같은 외부 행동은 재전송하지 않고 독립 읽기·준비 계속 |
| 7 | 기기가 교체되었거나 자원 연결이 달라졌으면 `[작업 위치 다시 연결]`에서 PC·파일·계정을 선택한다 | 이전 연결과 새 연결의 차이, 여전히 연결되지 않은 자료가 보인다 | 기기 이름·파일명만으로 동일성 판단 안 함; 잘못된 계정은 해당 연결의 사용 전 차단 | 허용된 대응 후보를 제안하고 변경 영향에 맞춰 후속 작업 조정 |
| 8 | 해당 업무의 `[중지]`를 누른다 | PC별 중지 요청·확인 결과와 이미 완료한 결과가 남는다 | 후속 행동 차단; 원격 중지 응답이 없으면 Canvas 상태 유지 | 이미 한 일·미완료·결과 미확인을 설명; 다른 업무는 계속 |

**PC 선택 상세의 배치**: 위에는 `실행 PC·연결 확인 시각`, 그 아래에는 이번 행동별
`사용 서비스·실제 업무 계정·대상 revision/환경·가능한 행동·부족한 권한`을 둔다. AI Engine
계정은 별도 줄이다. 코드 작업이라면 `PR 작성 가능 / Production 배포 권한 없음`처럼 구별하며
branch·배포 대상도 해당 행동에만 표시한다. 다른 업무에 Git 전용 필드를 강제하지 않는다.
PC가 연결돼도 서비스 권한이 없을 수 있고, Profile 편집·Desk 소유권 복구가 그 자격을 만들지
않는다. 부족한 배포만 제한하고 허용된 준비·검토는 계속한다. 긴 계정명과 대상은 선택 상세에서
줄바꿈해 전부 읽을 수 있으며, 무관한 서비스 목록은 펼치기 전까지 숨긴다.

**재연결·취소**: 자동 재연결은 동일 실행이 검증된 경우에만 `재연결됨`으로 표시한다.
PC B에서 process가 사라졌다면 과거 출력은 남기고 `이전 실행 종료`와 `[새로 시작]`을 구별한다.
기기·계정 다시 연결을 취소해도 과거 결과·초안은 남는다. 이미 확인된 외부 효과는 PC 이동이나
중지로 되돌아가지 않는다. 미확인 외부 행동은 확인 근거가 생기기 전까지 반복 실행하지 않는다.
**확인 기준**: 같은 Agenda에서 여러 PC의 결과를 함께 확인하고 실제 실행 PC·계정을 추적할
수 있다. 재접속 후 한 요청이 두 번 실행되지 않으며, 결과 파일·서비스의 접수/완료 기록처럼
해당 행동의 증거가 연결된다. 일부만 확인되면 `일부 완료`와 미완료·미확인 항목을 구별한다.
**대안**: PC 변경을 모두 수동으로 지정하면 실행 위치 통제는 쉽지만 사용자의 선택이 늘어난다.
허용된 PC 사이의 자동 선택은 편하지만 위치·비용·데이터 이동 경계가 선명해야 한다.
자동 범위를 넓히거나 새로운 계정·전송 권한을 부여하는 선택은 이 흐름이 승인하지 않는다.

#### 자료 사본을 한 파일로 옮긴다

**추천안**: 선택한 Agenda 안의 이동 가능한 자료를 하나의 bundle로 만든다. 암호화와
새 Agenda 사본 import를 기본안으로 제안하고, 병합은 차이 검토 후 선택한다. import는
자료만 복원하며 live 연결·실행 인계를 대신하지 않는다. 권한·기억 활성화·Agent 실행·예약
재개를 자동으로 상속하지 않는다.

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | Agenda의 `[내보내기]` | 구성·선택 대화·결과·Snapshot의 포함 목록 | 선택 root와 참조 관계 계산 | 필요할 때만 포함 이유 설명 |
| 2 | `[포함 항목 검토]`에서 범위 조정 | 포함·제외·파생본·누락 연결이 구별된다 | 권한 없는 원본으로 범위를 확대하지 않음 | 공유용 요약이 필요하면 요청 범위에서 생성 |
| 3 | `[암호화]` 설정·암호 확인 → `[파일로 저장]` | `.egdesk` 파일 저장 완료가 보인다 | credential·기기 전용 경로·cache 제외, manifest·hash 검사 후 저장 | 원격 전송 없음 |
| 4 | 새 기기의 `[가져오기]` → 파일 선택·필요 암호 입력 | Agenda 이름·자료와 기존 항목 충돌이 보인다 | 형식·무결성·object·현재 권한을 검사 | 없음 |
| 5 | `[새 Agenda로 가져오기]` → `[적용]` | 같은 Desk에 새 사본과 과거 자료가 열린다 | 격리된 적용 범위에서 검증한 뒤 대표 Chat·Snapshot 연결 확인 | 자동 실행 없음 |
| 6 | `[필요한 자원 연결]` → 파일·업무 계정 선택 → `[연결]` | 과거 Snapshot과 새 live 원본, 연결 안 된 항목이 보인다 | 파일명 외 내용·revision·실제 계정을 비교 | 대응 후보는 제안할 수 있음 |
| 7 | 업무의 `[계속]` | 사용할 PC·Engine·업무 계정과 재개 가능한 범위가 보인다 | 과거 업무와 현재 환경의 입력을 연결; 원 기기의 상태를 확인할 수 없으면 중복 효과가 있는 범위는 보류 | 허용된 미완료 업무부터 진행 |
| 8 | `[나중에 연결]` 또는 `[취소]` | 읽을 수 있는 과거 자료는 그대로 남는다 | live 연결·실행만 보류하고 import 자료 보존 | 선택하지 않은 작업 실행 없음 |

**비공개 원본을 참조할 때**: 완전한 원본이 필요한 export와 공유용 파생 결과 export를
구별한다. 전송 권한 없는 원본은 자동 포함하지 않는다. 허용된 파생 root로 범위를 다시
구성하고 제외된 근거를 표시하는 안을 추천한다. 원본 없이는 의미·무결성을 지킬 수 없는
항목은 그 항목의 내보내기만 보류한다.
**이미 실행 중인 이전 기기**: offline bundle만으로 원 기기의 종료를 확인했다고 간주하지
않는다. 읽기·준비는 계속할 수 있고, 중복 외부 효과가 걸린 행동은 실행 주체·처리 결과를
확인한 뒤 진행한다. 새 기기라는 이유만으로 모든 업무에 새 Run·fork를 강제하지 않는다.
**실패·복귀**: 잘못된 암호·손상된 파일·지원하지 않는 형식이면 사유와 `[다른 파일 선택]`을
표시하고 기존 Agenda를 바꾸지 않는다. 적용 전에 취소하면 새 사본을 만들지 않는다.
자료 일부를 제외했다면 가져온 목록에 그 항목과 영향이 남고 읽을 수 있는 자료는 열린다.
잘못된 계정으로 자원을 연결하려 할 때는 `[계정 다시 선택]`으로 돌아가며 import한 자료를 지우지 않는다.
**확인 기준**: 내보낸 파일에서 대표 Chat·자료·Snapshot을 다시 열 수 있고 포함·제외 범위가
일치한다. `가져오기 완료`는 자료 검증·복원의 완료이며 `실행 재개`·`기기 연결 완료`와 구별된다.
**대안**: 비암호화는 전달이 간단하지만 파일을 가진 사람이 내용을 읽을 수 있다. 기본 병합은
이름 중복을 줄이지만 원래 Agenda의 상태를 바꿀 수 있으므로 새 사본을 우선 추천한다.

#### 앱 설정·계정 연결·업무 기록을 따로 초기화한다 — 제안

**상황**: 사용자는 화면 설정만 되돌리거나, PC를 넘기기 전에 자기 연결·기록을 정리하려 한다.
**추천안**: `[설정]` → `[데이터와 초기화]`에서 아래 범위를 각각 선택한다. 처음에는 삭제 범위를
미리 선택하지 않는다. `이 PC의 저장분`과 `Desk의 공유 원본`을 구별하며 이 PC 정리가 다른 PC의
자료·실행·계정을 지운다는 뜻은 아니다. 아직 준비되지 않은 원격 초기화는 제공 가능한 것처럼
표시하지 않는다.

| 선택 범위 | 초기화되는 것 | 그대로 남는 것·추가로 필요한 행동 |
|---|---|---|
| `[화면·입력 설정]` | 이 PC의 표시·단축키·알림 등 선택한 환경설정 | Desk 배치·Agenda·초안·Agent/Profile·계정 연결·기록은 유지. 배치까지 지우려면 업무 기록에서 별도 선택 |
| `[계정 연결 해제]` → Engine/업무 서비스/Browser 연결 중 선택 | 선택한 연결의 EG-Desk 인증 사용과 이 PC가 관리하는 해당 인증 정보 | 계정 자체·구독·원격 서비스 자료와 비밀이 아닌 Profile 정의는 남음. Browser 방문 기록·비밀번호 저장소 전체 삭제는 포함하지 않음 |
| `[Agent·Engine Profile 설정]` → 대상 선택 | 사용자 설정·모델·기본 연결·위임 설정의 선택된 정의. 기본 제공 Profile은 기본값으로, 사용자 정의는 제거하는 안 | 대화 작성자·과거 호출의 실제 설정 이력은 유지. credential은 연결 해제에서 별도 선택; 조직이 강제한 정책은 개인 초기화로 수정 불가 |
| `[업무 기록]` → Agenda/Chat·초안/결과·Snapshot/개인 기억 등 선택 | 권한과 보존 정책이 허용하는 선택 기록 및 그 기록에서만 쓰는 저장 데이터 | OS 원본 파일·웹 서비스 원본·다른 사람의 공유 기록·활성 조직 규칙은 별개. 남는 참조와 삭제할 수 없는 항목은 적용 전에 표시 |

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | `[데이터와 초기화]`에서 대상 PC·범위·항목을 선택한다 | 지워질 것·남을 것·영향받는 업무·다시 연결할 계정이 나뉘어 보인다 | 실제 소유·권한·참조·연결 위치를 계산; 캐시 정리와 공유 원본 삭제 구별 | 없음 |
| 2 | 필요하면 `[먼저 내보내기]` → 포함 내역 확인 → `[파일로 저장]` | 보존할 자료와 제외된 자료·credential이 보인다 | 위 bundle 절차로 검증; 지원하는 설정의 비밀 아닌 사본은 포함 여부를 표시 | 요청한 범위 설명만 수행 |
| 3 | `[초기화 내용 확인]`에서 최종 범위를 읽고 `[선택 범위 초기화]` | 중지할 업무와 계속되는 업무, 항목별 처리 진행이 보인다 | Profile 삭제·연결 해제·기록 삭제에 종속된 실행만 중지/회수 확인. 화면 설정만 변경하면 실행 유지 | 중지 대상의 새 행동 없음; 관련 없는 작업 계속 |
| 4 | 결과의 `[처리 내역]`을 연다 | `완료·남음·확인 안 됨`과 실제 처리 범위가 보인다 | 저장값·인증 사용 차단·참조 및 데이터 정리 결과를 구분. 삭제한 본문을 처리 내역에 다시 복제하지 않음 | 없음 |
| 5 | 필요하면 `[계정 다시 연결]`, `[설정 다시 만들기]` 또는 `[백업 가져오기]` | 무엇을 다시 준비할지 보이고 보존한 업무·초안으로 돌아갈 수 있다 | 가져오기·인증을 각각 확인; 사본 복원만으로 권한·기억·예약·실행 활성화 없음 | 초기화 대상이 아닌 기존 유효 위임 업무만 계속; 복구한 업무는 `[계속]` 등 실행 지시 전에는 진행하지 않음 |

**목록 밖 선택의 확인**: 범주 목록과 최종 확인 화면 상단에 `선택 N개·현재 목록 밖 M개`와
`[선택 대상만 보기]`를 둔다. 이 보기는 선택한 PC·서비스·전체 계정명·기록 범위를 보여 주며,
항목의 `[선택 해제]`는 선택 집합만 바꾼다. 범주 이동·스크롤·검색이 이미 고른 대상을 조용히
추가하거나 바꾸지 않는다. 최종 적용은 검토한 식별자 집합에 묶고 새로 보인 행·현재 필터
전체로 확대하지 않는다. 대상이나 삭제 의미가 바뀌면 그 항목의 차이를 다시 보여 주지만 같은
범위의 재시도에 매번 새 승인을 만들지 않는다. 이 선택 규칙은 삭제·반출·공유 범위의 다중
선택에도 적용한다. 새 컨트롤을 쓰지 않은 기본 경로의 클릭 수와 선택 검사에 든 클릭은 구별한다.

**실패·취소·복귀**: 적용 전 `[취소]`는 무변경이며 선택 화면을 닫고 원 설정 위치로 돌아간다.
내보내기에 실패하면 `[다시 저장]`·`[초기화로 돌아가기]`를 제공하며 초기화를 자동 진행하지
않는다. 사용자가 백업 없이 계속할 때는 다음 확인 화면에서 복구할 수 없는 범위를 보여 준다.
적용 뒤에는 처리하지 않은 항목을 중단할 수 있으나 이미 삭제된 기록·끝난 process·해제된
인증을 취소로 복구하지 않는다. 원격 종료나 인증 철회가 미확인이면 해당 Canvas 표시를 유지하고
`[미완료 항목 다시 확인]`으로 그 항목만 조회한다. 계정 재연결 취소는 보존한 대화·초안을 지우지 않는다.
**계정·복원 경계**: 로컬 인증 정보 제거, provider의 연결 철회, 다른 PC의 로그아웃은 별도 결과다.
provider 철회가 필요하고 제공되면 `[서비스 연결 철회]`의 대상·다른 연결 영향을 보여 주며, 실패하면
해당 서비스에서 직접 확인할 경로를 남긴다. 로컬 초기화만으로 모두 로그아웃됐다고 표시하지 않는다.
원격 종료·철회 확인을 기다리지 않고 이 PC의 인증 사용 차단·정보 제거를 처리하며, 확인되지
않은 원격 실행은 비밀 없는 최소 상태로 Canvas에 남긴다. 기록 삭제 뒤 이전 연결로 다시 동기화할 수 있다면 그 가능성과
`[이 PC의 동기화 해제]`를 먼저 보여 준다. 공유 원본까지 지우려면 별도 권한·범위 선택이 필요하다.
**완료 근거**: 선택한 설정값·Profile·인증 사용·기록의 실제 처리 결과와 남는 항목이 일치한다.
완료는 선택한 위치·범위의 저장분 제거에 한정한다. 제거된 로컬 기록은 검색·새 모델 입력에서
제외한다. 동기화를 유지하면 남아 있는 원격 원본이 다시 유입될 수 있으며 재유입 방지까지
완료됐다고 표시하지 않는다. 공유 원본 삭제를 선택한 경우에는 재유입 차단과 권한 집행을 별도로
확인한다. 남는 참조에는 삭제 사실만 표시한다. 과거 입력
보존은 정상 사용 중 변경하지 않는 원칙이지 명시적인 삭제를 무효화하는 영구 보존 약속이 아니다.
기록 초기화는 영구 삭제 영향 확인을 거치는 안이며 복구는 검증된 백업이 있을 때만 가능하다.
**대안·손실**: 모든 로컬 항목을 한 번에 비우는 방식은 PC 양도에 짧지만 계정·설정·업무 손실을
구별하기 어렵다. 별도 `[이 PC 전체 정리]` 바로가기를 두더라도 같은 범위 미리보기·종료 확인을
거치는 대안으로 비교한다. 추천안은 조작이 늘지만 화면 설정 복구가 대화 삭제로 이어지지 않는다.
보존 제한·초기화 범위·백업 기본값은 [HUM-EXPORT-001](../../codex/egdesk-product-interaction-trace-atlas-editorial-ledger.md#hum-export-001)의 선택으로 비교한다.

#### 원격 협업이 승인·설정된 뒤의 분기

현재 단계에서는 아래 흐름을 로컬 mock과 권한 설계로 검토한다. 실제 초대 전송·서버·
동기화는 `HUM-REMOTE-001` 승인 범위가 준비돼야 한다.

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | `[공유 범위]` → Agenda·자료·상대 선택 | 공유·제외 영역과 상대가 보게 될 화면 미리보기 | scope와 참여자 identity 확인 | 없음 |
| 2 | 관찰·댓글·업무 위임·리소스 실행·computer-use 제어를 따로 선택 | 어떤 권한이 열리는지와 사용할 실행 계정·quota가 보인다 | 권한별 실제 account와 범위를 결합 | 권한을 스스로 추가하지 않음 |
| 3 | 승인된 환경에서 `[초대 보내기]`, 상대는 `[참여]` | 전달·수락·접근 가능 상태가 구별된다 | 초대·수락·실제 접근 확인 | 허용된 공유 맥락만 사용 |
| 4 | 각자 탐색하거나 상대의 `[따라보기]`를 선택 | 독립 카메라 또는 명시적으로 선택한 보기 연결 | 직접 pan하면 따라보기 해제; 입력권은 별개 유지 | 사용자 카메라 이동 때문에 작업 대상 변경 없음 |
| 5 | `[권한 변경]` 또는 `[접근 회수]` | 적용한 권한과 회수 확인 중인 PC·참여자가 구별된다. 관찰 권한을 남기면 `보기만 가능`으로 보인다 | 활성 grant·후속 행동을 갱신하고 해당 분기 재검증; 통신 단절을 원격 회수 완료로 표시하지 않음 | 회수된 권한으로 새 행동하지 않음 |

**추천 권한 기본값**: 관찰 초대와 실행 위임을 구별하고, 실행은 그 업무에 명시적으로
선택한 계정·quota 주체로만 허용한다. 누가 비용을 부담하고 어떤 권한을 기본 제공할지는
[협업 선택](#decision-collaboration)에 남는다.
**취소·철회·완료**: 초대 작성 취소는 공유를 만들지 않는다. 발송 후 취소는 초대 철회 결과를
확인하고, 이미 참여했다면 접근 회수로 처리한다. 상대 계정이 지정한 계정과 다르면 접근을
열지 않고 `[다른 계정으로 참여]`를 안내한다. 연결이 끊긴 상대에게는 만료·철회된 권한으로
재접속을 허용하지 않는다. 관찰·제어·실행마다 실제 적용 결과를 보이며, 이미 완료한 변경·
허용된 과거 기록은 해당 정책대로 남긴다. 외부로 전달한 사본까지 회수됐다고 표시하지 않는다.

<a id="collaboration-changes"></a>

**동시 변경을 보존·수락·되돌리는 분기 — 제안**: 같은 자료를 고치는 사용자·협업자·Agent의
변경은 작성자와 범위를 유지한다. 충돌 없이 처리할 수 있는 변경·위임된 병합은 계속하고,
해결되지 않은 의도 충돌만 선택 대상으로 남긴다. 모든 변경마다 사람의 수락을 요구하지 않는다.

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | 자료의 `원본이 변경됨` → `[변경 비교]` | 기준본·현재 원본·각 변경의 작성자·범위가 보인다 | 각 초안과 기준 revision 보존; 지원 편집기의 비교 화면 연결 | 의미·충돌 영향 설명, 위임된 병합·검증 계속 |
| 2 | `[내 변경 보존]` 또는 지원되는 `[직접 합치기]` | 미적용 초안 또는 편집 가능한 병합 사본이 보인다 | 보존은 원본 적용과 구별; 직접 합치기 미지원이면 `[사본으로 열기]`와 `[편집 앱에서 열기]` 중 가능한 경로 제공 | 요청 범위 안에서 수정안 작성 |
| 3 | 편집 권한자가 변경 범위 선택 → `[선택 변경 수락·적용]` | 미리 본 범위의 적용 결과와 원본 저장 상태가 보인다 | 적용 직전 현재 원본·권한 재검사; 그사이 변경됐으면 초안을 보존하고 차이 갱신 | 의미 검증이 필요하면 기존 위임 안에서 수행 |
| 4 | 변경 내역에서 자기 변경 선택 → `[내 변경 되돌리기]` | 되돌릴 부분과 이후 다른 사람이 고친 부분·의존 결과가 보인다 | 현재 상태에 대한 역변경을 준비; 이후 타인 변경까지 과거 상태로 되감지 않음 | 영향 분석·가능한 수정 제안 |
| 5 | 영향 확인 후 `[되돌릴 변경 적용]` 또는 `[취소]` | 최신 revision의 저장 상태 또는 변경 전 비교 화면으로 돌아간다 | 권한·현재본을 다시 검사하여 선택한 역변경만 저장 | 유효한 후속 작업은 새 관찰을 반영 |

**실패·복귀·완료**: 적용 실패·취소는 각 초안을 보존한다. 응답이 유실되면 `[저장 상태 확인]`으로
결과를 대조하기 전 같은 변경을 다시 적용하지 않는다. `[비교 닫기]`·`Esc`는 원 자료·스크롤로
돌아간다. 되돌릴 수 없는 형식·충돌은 사본에서 검토하며 자동 원본 덮어쓰기로 대체하지 않는다.
완료는 최신 revision·작성자별 변경·저장 상태와 되돌린 뒤 남은 타인 변경으로 확인한다. 자료 수정의
되돌리기는 전송한 메시지·서비스 요청·그 변경으로 이미 수행한 외부 행동까지 취소하지 않는다.
**대안·손실**: 충돌 부분만 순차 편집하도록 잠그는 대안은 병합 부담이 줄지만 대기·인계가 늘어난다.
각 초안을 보존하며 병행하는 추천안은 작업을 이어가기 쉽지만 변경 비교와 의미 충돌 처리가 필요하다.

**배치·조작 세부**: 변경 안내가 보이는 자료에서 비교 1 + 변경 범위 하나 선택 1 + 수락·적용 1
= 3클릭이다. 변경 내역이 닫혀 있다면 자료 bar `[⋯]` 1 + `[변경 내역]` 1 + 자기 변경 선택 1 +
되돌리기 미리보기 1 + 적용 1 = 5클릭이다. 기준본 전체·전체 변경 이력은 접고 선택 변경·작성자·
현재 원본·저장 상태를 먼저 보인다. 비교 View를 재사용하되 편집 중인 사본을 교체하지 않는다.

<a id="desk-ownership"></a>

**Desk 소유·관리 권한을 이전하거나 복구하는 분기 — 제안**: Desk 생성자를 초기 소유자로
두고 범위가 제한된 관리자를 지정하는 안이다. 일반 관리자 지정에 소유권 이전·복구 권한을
자동 포함하지 않는다. 아래 원격 절차 역시 승인·설정된 협업 환경에서만 수행한다.

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | 소유자가 `[공유 관리]` → `[관리자 지정]` → 사람·항목·기간 선택 → `[적용]` | 관리 가능한 범위와 적용 상태가 보인다 | 지정 권한과 실제 상대 identity 검사; 소유자와 관리자 역할 분리 | 영향 설명만 수행 |
| 2 | 소유자가 `[소유권 이전]` → 대상·이전 후 자신의 역할 선택 → `[이전 요청]` | 바뀔 관리 권한·유지할 공유 범위·수락 대기가 보인다 | 현재 소유자 확인과 이전 요청 기록; 수락 전 소유권 유지 | 대신 수락하거나 자신을 승격하지 않음 |
| 3 | 대상자가 같은 요청의 `[이전 내용 보기]` → `[수락]` 또는 `[거절]` | 양쪽에 이전 완료·거절 또는 결과 확인 중이 보인다 | 양쪽 신원·최신 소유권·요청 유효성을 재검사 후 한 전환으로 기록 | 없음 |
| 4 | 소유자가 미리 `[복구 권한 설정]` → 수임자·대상·조건 선택 → `[저장]` | 평상시 관리와 다른 복구 가능 범위가 보인다 | 소유자의 명시적 복구 위임 보존; 수임자의 일반 권한 확대 없음 | 요청받은 조건 설명만 수행 |
| 5 | 해당 수임자가 `[관리 권한 복구]` → 근거·대상 확인 → `[복구 요청]` | 충족한 조건·추가 확인할 조건·복구 결과가 보인다 | 사전 위임과 신원·조건을 검증한 범위만 복구; 근거가 없으면 적용하지 않음 | 소유자 무응답을 권한 부여 근거로 해석하지 않음 |

**이전되지 않는 것**: Desk 관리 권한은 AI 계정·구독 quota·OS 파일 권한·웹 로그인 자격이
아니다. 개인 방·기억·비공개 자료도 자동 공유하지 않는다. 기존 실행의 계정·비용은 유효한
기존 위임에 귀속되며, 소유권 변경 때문에 해당 위임이 무효가 된 행동만 재검증한다. 관리 권한
복구는 잊어버린 계정 비밀번호나 원본 파일의 OS 접근권을 복구하는 기능이 아니다.
기존 복구 위임을 유지할지 끝낼지는 이전 미리보기와 대상자의 수락 범위에 포함한다. 이전 시
기존 위임을 끝내고 필요한 위임만 대상자가 수락해 유지하는 안을 추천한다. 복구할 때 최신 소유
관계와 현재 유효한 위임을 검사하며, 전 소유자가 예전에 위임했다는 사실만으로 현 소유권을
되돌리지 않는다. 이 검토는 기존 이전·수락 안에서 처리하며 별도 승인 단계를 추가하지 않는다.
**취소·실패·복귀**: 수락 전에 `[이전 요청 취소]`가 확정되거나 상대가 거절·요청이 만료되면
기존 소유권을 유지한다. 수락과 취소가 겹치거나 통신이 끊기면 `[이전 상태 확인]`으로 현재
결과를 확인한다. 이전 후 역이전은 현재 소유권으로 새 절차를 거친다. 근거 없는 복구는
`복구 권한 확인 필요`와 확인 경로를 남기고 기존에 허용된 열람·독립 업무는 계속한다.
`Esc`로 닫으면 공유 관리의 원 참여자로 돌아간다. 이전 결과를 받지 못한 PC는 따로 표시하고
재연결로 옛 권한이 되살아나지 않도록 현재 권한을 다시 확인한다.
**완료 근거·대안**: 소유자·관리자 목록의 저장과 실제 권한 적용·축소를 각각 확인한다.
공동 소유자는 부재 대응이 쉽지만 이전·철회 충돌 규칙이 추가로 필요하다. 복구 위임 없는
단일 소유자는 단순하지만 소유자 접근 상실 시 관리 복구가 제한된다. 소유자 수와 복구 위임
기본값은 [협업 정책](#decision-collaboration)·HUM-COLLAB-001의 제안이며 확정된 새 계정 체계가 아니다.

**배치·조작 세부**: 앱 `[설정]` 1 + `[공유 관리]` 1 + `[소유권 이전]` 1 + 대상 선택 1 +
이전 후 역할 선택 1 + `[이전 요청]` 1 = 요청까지 6클릭이다. 기존 복구 위임을 유지하려고
선택하거나 상세 권한을 바꾸면 추가된다. 수신자는 `[설정]` 1 + `[공유 관리]` 1 + `[받은 요청]` 1 +
해당 요청의 `[이전 내용 보기]` 1 + `[수락]` 1 = 5클릭이다. 알림 상세로 바로 들어오면 앞의
진입 경로는 줄어든다. 양쪽 신원·전후 역할·복구 위임 처리·이전되지 않는 계정/권한은 같은 확인
화면에 기본 노출하고, 권한 목록의 개별 항목만 펼친다. 수락/취소 뒤에도 같은 요청 결과 위치를 유지한다.

**배치·진입 비용**: `Canvas: PC별 실제 자료·활동 │ 선택 상세: 해당 연결/공유/초기화 범위`.
PC 이름·연결 끊김은 해당 자료 bar에 보이고 모든 기기의 전체 상태판을 항상 띄우지 않는다.
해당 업무가 선택된 Chat에서 `[업무 메뉴 ⋯]` 1 + `[다른 PC에서 이어서]` 1 + PC 선택 1 = 대상 지정 3클릭이며 새 권한·
계정 연결은 별도 경로다. 설정 진입점이 보이고 대상이 이 PC인 경우 `[설정]` 1 +
`[데이터와 초기화]` 1 + `[화면·입력 설정]` 선택 1 + `[초기화 내용 확인]` 1 +
`[선택 범위 초기화]` 1 = 5클릭이다. 세부 대상·백업·계정 재인증을 고르면 추가된다.
설정과 공유 상세는 각자의 한 화면 안에서 목록→선택 상세→확인→처리 결과로 바뀌며
이전 단계로 돌아갈 컨트롤을 같은 위치에 둔다. 초기화 전 4개 범주 전체의 항목을 한꺼번에 펼치지 않는다.

**상황**: 사용자가 업무 중 조건을 바로잡았고 다음에도 사용할 수 있는 규칙인지 검토한다.
**연결**: 후보 17, ECS-07, CAP-04/12,
[호출별 조정 계약](../../../ideas/confirmed/EGDESK_INTERACTION_AND_ORCHESTRATION_CONTRACT.md#tech-agent-run-binding),

**추천안**: 현재 업무의 교정은 바로 이어지는 호출에 반영한다. 장기 재사용은 출처·범위를
보여 주고 선택적으로 저장하며, 조직 규칙은 권한 있는 운영 흐름으로 승격한다. 일회성
교정마다 조직 승인이나 새 Run을 요구하지 않는다. 자동 기억의 기본 범위는 아직 제안이다.

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | 연결된 Chat에 교정 문장을 입력해 `[전송]` | 조정 수신·반영 상태 | 가능한 가장 이른 다음 호출에 전달; 추가 적용 버튼 불필요 | 같은 Run에서 해석·계획을 조정 |

| 3 | `[나의 업무]` 또는 `[이 Agent와의 업무]` 선택 → `[저장]` | 저장 범위와 향후 관련 요청에서 사용될 조건 | version·소유 범위 기록 | 일회성 사실을 무조건 일반 규칙으로 확대하지 않음 |

| 6 | 위임 정책 안의 검토는 기다리지 않고, 권한자가 실제 결정할 단계에서 `[검토]` | 남은 판단과 적용 범위·시점·근거가 한 화면에 보인다 | 정해진 review·promotion 권한과 조건 확인 | 일반 finding 수정·재검토는 위임 범위에서 진행 |
| 7 | 권한자가 `[이 범위에 활성화]` 또는 `[보류]` | 활성 범위·시점 또는 비활성 후보가 보인다 | 의미 수락·승격·활성화를 구별해 기록; 과거 입력은 유지 | 관련 진행 중 Run도 다음 모델 호출에서 새 내용을 반영 |
| 8 | 개인 기억의 `[재사용 중지]` 또는 조직 규칙의 `[이전 버전으로 적용]` | 향후 사용 범위의 변화와 보존된 과거 기록 | 권한·영향을 확인해 후속 binding 갱신 | 다음 호출에서 관련 변경에 적응 |

**기억 소유와 적용 조건의 배치**: `[다음에도 기억]` 상세에서 위에는 `소유: 나 / 이 Agent와의
업무`, 바로 아래에는 `사용할 조건: 조직·역할·업무 계정·기간/상황`을 구별해 보여 준다.
현재 업무의 알려진 조건만 채우고 빠진 값은 미지정으로 표시한다. 예를 들어 한 회사의 특정
역할에서 얻은 규칙을 개인 기억으로 저장해도 다른 회사의 업무에 무조건 적용하지 않는 안이다.
`[조건 편집]`에서 조건을 바꾸고 `[저장]`하면 그 조건에 맞는 후속 요청에만 사용한다. 조건을
넓히는 영향은 같은 화면에서 확인한다. 개인 기억의 조건을 `역할`로 좁히는 것과 그 역할의
모든 사람에게 공유하는 것은 다르다. 공유하려면 기존 `[조직 후보로 제안]`과 실제 편집·승격
권한을 따르며, 이번 업무 교정에는 이 저장 절차가 추가되지 않는다. 소유·조건 기본값은
HUM-RUN-001의 같은 선택으로 남긴다.

**취소·복귀**: 기억 저장 취소는 이번 Run의 교정을 취소하지 않는다. 후보 검토를 닫아도
현재 업무는 이어진다. 의미 수락·승격·활성화 책임은 같은 권한자가 맡을 수 있으며, 필요한
결정을 한 번에 범위와 함께 확인하는 안을 추천한다. 정책상 별도 검토가 필요한 경우만
단계를 나눈다. 자동 조직 승격 권한을 Agent에게 새로 부여하는 제안은 아니다.
**동시 변경·권한 철회**: 검토 도중 기존 규칙이 바뀌면 `검토 이후 변경됨`과 차이를 보여 주고
위임 범위에서 재검토한다. 활성화 권한이 사라졌으면 후보·검토 결과는 남기고 해당 활성화만
`권한 필요`로 표시한다. 개인 기억은 `[재사용 중지]` 뒤 새 입력에서 제외하되 이미 사용한
과거 호출을 지우거나 이번 업무의 교정을 원상복구했다고 표시하지 않는다.
**확인 기준**: `후보 저장`·`조직에 제안`·`활성화됨`이 구별된다. 관련 진행 업무에서는
어느 범위의 규칙이 실제 다음 호출에 반영됐는지 확인할 수 있고, 적용되지 않은 요청도
범위 밖인지·권한이 없는지 구별된다. 후보가 보류돼도 현재 업무의 결과는 계속 완성한다.
**대안**: 일정 조건의 개인 기억을 자동 저장하고 변경 목록을 제공하면 편리하지만 잘못된
일반화·누적·망각 범위의 관리가 필요하다. 이 선택은 [기억 정책](#decision-memory)에 남긴다.

<a id="policy-conflicts"></a>

**적용 기준이 다를 때 — 제안**: 사용자는 업무의 `[적용 기준]`에서 강제 제한, 변경 가능한
기본값, 이번 업무의 명시적 지시를 구별한다. 이 화면은 설정의 출처와 변경 가능한 범위를
보여 주며 시스템 프롬프트 원문을 모두 공개하는 화면을 뜻하지 않는다.

| # | 사용자 조작 | 보이는 결과 | System 처리 | Agent 처리 |
|---:|---|---|---|---|
| 1 | 업무의 `[적용 기준]`을 연다 | 현재 기준·출처·적용 조건·편집 가능 여부와 강제 상한이 보인다 | 현재 허용 권한과 적용 설정을 구별해 표시 | 관련 기준의 의미·충돌 영향 설명 |
| 2 | Chat에 이번 기준을 명확히 입력해 `[전송]` | 수신 후 실제 다음 호출에 `이번 업무에 반영됨`이 보인다 | 허용된 범위에서는 명시적 지시를 기본값보다 우선; 원설정은 수정하지 않음 | 같은 업무에 적용하며 지속 규칙으로 자동 일반화하지 않음 |
| 3 | 판단에 필요한 기준이 모호하다는 안내에서 `[이번 업무에 사용할 기준]` → 항목 선택 | 이번 선택의 영향과 유지할 기본값이 보인다 | 선택 지시를 해당 업무에만 연결; 강제 제한을 넘는 항목은 이유와 함께 사용 불가 표시 | 기존 위임의 판단 기준으로 해소할 수 있으면 직접 처리; 의도 확인이 필요한 부분만 질문 |
| 4 | 계속 사용할 값이면 편집 가능한 항목의 `[원설정 편집]`, 권한이 없으면 `[변경 제안]` | 수정할 Profile/Desk/조직 설정과 적용 범위 또는 미적용 제안이 보인다 | 원설정의 편집·활성화 권한과 최신본 검사 | 위임된 변경 유형만 수정·검토하고 그 밖에는 제안 |
| 5 | 권한자가 `[변경 저장]` 후 필요하면 해당 설정의 활성화 절차를 완료한다 | 저장·활성 상태와 적용될 업무 범위가 나뉘어 보인다 | 관련 다음 호출에 유효한 새 설정을 연결; 과거 입력 유지 | 영향받는 업무를 이어서 조정 |

**기준의 추천 순서**: 실제 권한·강제 상한을 먼저 만족하고, 그 안에서 이번 명시적 지시,
이번 업무에서 선택한 설정, 선택 Profile의 기본값, Desk 기본값, 조직의 수정 가능한 기본값
순으로 적용하는 안이다. 조직이 강제한 제한을 마지막 순위로 미루는 뜻은 아니다. 기본값의
적용 조건·우선순위는 해당 설정 권한자가 변경할 수 있고, Agent는 위임된 기준 안에서 선택한다.
조직 기본값을 모두 잠그는 대안은 관리가 단순하지만 현장 조정이 줄어든다. 넓은 자동 편집
위임은 반복 교정을 줄이는 대신 잘못 일반화된 변경이 퍼질 수 있다.
**실패·복귀·완료**: 읽기 권한은 편집 권한이 아니며 Profile 편집으로 자원 접근권·상위 한도를
늘리지 않는다. 편집 중 원설정이 바뀌면 초안과 차이를 보존한다. 제한과 충돌하는 행동만 막고
허용된 읽기·독립 업무는 계속한다. `[편집 취소]`는 이미 전송한 이번 지시를 취소하지 않는다.
`Esc`로 닫으면 원 메시지·초안으로 돌아간다. 완료는 원설정 저장·활성화·실제 후속 호출의 기준을
따로 확인한다. 우선순위·편집 위임은 [기억·규칙 정책](#decision-memory), Profile·모델 전환 시점은
[실행 설정](#execution-settings)과 같은 HUM-RUN-001 선택에 연결한다.

**배치·진입 비용**: `Chat: 교정 메시지 │ 본문 상세: 기억/정책 범위 │ Canvas: 비교할 근거`.
교정 메시지가 보이는 출발점에서 `[다음에도 기억]` 1 + 범위 선택 1 + `[저장]` 1 = 3클릭이다.
이번 업무의 지시 전송에는 이 저장 경로가 추가되지 않는다. 현재 기준은 `[업무 메뉴 ⋯]` 1 + `[적용 기준]` 1 = 2클릭으로
읽으며 강제 제한·기본값·이번 지시를 제목으로 구별한다. 기본 화면에는 이번에 충돌한 기준과
영향만, 출처 전체·이전 revision·세부 검토 이력은 접힌 상세로 둔다. 조직 후보의 의미 비교는
Canvas의 비교 View를 사용하되 활성화 버튼은 권한자가 검토하는 같은 상세에 남긴다.

### 4.2 비교할 정책 추천안 7묶음

아래 일곱 묶음은 비교할 절의 수이며 일곱 건의 포괄 승인을 뜻하지 않는다. 확정 경계를
제외한 기본값은 `PROPOSED`다. 각 절의 **남은 실제 선택**은 주요 비교 항목의 요약이다.
연결된 원장의 고유한 미결 선택은 함께 유지하며, 서로 독립된 값은 따로 고를 수 있다. 같은 계정·보존 질문을
여러 흐름에서 반복 결정하지 않으며, control과 복구의 구체화는 이 추천안으로 계속 검증한다.

<a id="decision-first-use"></a>
#### 첫 사용·실행 계정

- **추천**: 기본 Agent와 제품 기본 정책으로 개인 사용을 시작한다. 조직 지식은 선택 연결,
  Engine은 첫 AI 사용 때 연결한다. 방의 Engine 기본값과 요청별 override를 제공한다.
  Reader·Worker는 parent 한도를 공유하고 quota 소진은 해당 업무 대기로 처리한다.
- **대안**: 첫 전송 전에 Agent 역할·정책을 직접 설정한다. 다른 계정으로 계속하려면
  사용자가 연결·선택한다. 어느 안도 추가 과금·계정 이동을 자동 허가하지 않는다.
- **차이**: 추천안은 첫 사용이 짧지만 기본 역할의 맞춤성이 낮다. 대안은 설정 단계가 늘어난다.
  동시성·estimator의 숫자는 별도 측정으로 제안하며 토큰을 구독 quota로 환산하지 않는다.
- **실행 설정 비교**: 방의 기본값 저장과 이번 업무 적용을 분리하고, 명시한 Profile·모델·한도·
  기간 안에서 자동 조정을 사전 위임하는 안을 추천한다. Profile·모델은 가능한 가장 이른 다음
  호출부터 적용하며 강제 상한·새 계정·추가 비용·전송 권한을 넘지 않는다. 수동 선택만 하는
  대안은 예측이 쉽지만 반복 조작·가용성 대기가 늘어난다. 위임형은 실제 적용 이력·범위·철회를
  쉽게 확인할 수 있어야 한다. [실행 설정 흐름](#execution-settings)을 기준으로 비교한다.
- **남은 실제 선택**: 기본 Agent를 제공할지, 사용자가 선택한 기본 Engine을 어느 범위에
  기억할지다. 추천은 기본 Agent 제공과 방별 Engine·요청별 명시적 선택이다. 다른 Engine으로
  이어갈 때의 대상 업무·비용 범위는 한 번 명시하고 협업에서는 그 위임을 재사용한다.
- **구체화할 부분**: 연결된 실제 계정 표시, quota 대기·초안 복귀, Reader의 상세 펼침은
  prototype으로 비교한다. 기본 Engine을 바꿔도 진행 중 Run의 계정은 조용히 바뀌지 않는다.
  기존 상한 안의 Reader 배분·동시성·추정 방법은 기술 재량이며 새 예산 승인 항목이 아니다.
  [흐름](#flow-first-use), [HUM-AGENT-001](../../codex/egdesk-product-interaction-trace-atlas-editorial-ledger.md#hum-agent-001),
  [HUM-ENGINE-001](../../codex/egdesk-product-interaction-trace-atlas-editorial-ledger.md#hum-engine-001),
  [HUM-READ-001](../../codex/egdesk-product-interaction-trace-atlas-editorial-ledger.md#hum-read-001).

<a id="decision-chat"></a>
#### 담당자 방·Memo 응답

- **추천**: 작성기에 명시적으로 연결한 업무를 유지하고 연결이 없고 모호할 때만 확인한다.
  위임 교환은 필요한 부분을 펼친다. Memo는 명시적 질문이나 담당 범위에 연결된 경우
  응답하며, 필요한 방 후속 질문은 쟁점당 한 번 조용히 남긴다. 미응답 자동 재촉은 하지 않는다.
- **대안**: 매 전송마다 업무를 선택하고, Memo에서 사용자가 방으로 이어가기 전에는
  Agent가 후속 연락하지 않는 수동형.
- **차이**: 추천안은 반복 조작을 줄이지만 오래된 업무 연결을 놓칠 수 있어 전송 가까이에
  대상 표시가 필요하다. 수동형은 귀속이 선명하지만 추가 조작과 확인 누락이 늘어난다.
- **남은 실제 선택**: Memo가 응답을 시작하는 연결 범위·후속 연락 기본값, 참여자에게 기본
  공개할 대화·기여 범위다. 공개 권한과 단순 `[펼치기]`의 화면 깊이는 구별한다.
- **구체화할 부분**: 명시적 대상 유지·모호한 메시지만 확인·이전 초안 복귀는 반복 승인 없이
  비교한다. 매번 업무를 고르게 하는 수동형은 추가 조작의 비교안으로 남기며 새 승인 단계로 넣지 않는다.

<a id="decision-agenda"></a>
#### Agenda 저장·공유 실행·닫기

- **추천**: 구성·배치·live 참조와 선택한 메모·대화·결과를 저장한다. 업데이트는 같은
  Agenda의 새 revision, 다른 이름 저장은 새 Agenda다. 공유 실행은 소유 Agenda를
  명시한다. 닫으면 전용 실행은 종료, 예약·반복 조건은 pause로 보존하며 재열기만으로
  실행하지 않는다. 미저장 편집의 복구 초안은 Saved Agenda와 구별한다.
- **대안**: 허용된 원문을 저장 시점에 함께 고정하는 archive형. 예약을 계속하려면 닫기 전에
  다른 열린 Agenda로 실행 소유를 명시적으로 옮긴다. 예약을 삭제하는 정책도 별도 선택 가능하다.
- **차이**: 추천안은 당시 원본 전체를 재현하지 못할 수 있다. archive형은 저장량·민감 자료
  복제가 늘어난다. pause를 놓치면 예약 업무를 빠뜨릴 수 있어 닫기 영향과 재개 상태가 보여야 한다.
- **Library·그룹 비교**: 명시적으로 고른 Resource·Saved Agenda·결과·Snapshot의 참조를
  독립 Library에 등록하고, 중첩된 화면 그룹은 자동 Desk 복원에 보존하는 안을 추천한다.
  그룹 배치는 Agenda 저장에서 선택한 부분만 포함하며 구성원·권한·실행 소유를 바꾸지 않는다.
  대안은 독립 Library 없이 검색·Saved Agenda를 쓰거나 그룹을 세션마다 풀고 중첩을 제한하는
  방식이다. 관리 구조는 줄지만 재탐색·반복 배치가 늘어난다. live 재사용은 동일 instance·계정·
  권한을 확인할 수 있을 때만 기본으로 제안하며, 항상 독립 열기는 간섭을 줄이는 대신 자원을 더 쓴다.
- **저장본 삭제·복구 비교**: 별도의 `[저장한 Agenda 삭제]`로 전용 실행 종료 확인 후
  휴지통에 옮기고, 사용자가 비우기 전까지 허용된 저장본을 보존하는 안을 추천한다. 복구는
  같은 저장 이력을 되돌리되 자동 실행하지 않는다. 기간 후 삭제는 보관량 대신 복구 기한을,
  즉시 영구 삭제는 단순함 대신 오삭제 손실을 늘린다. 외부 원본과 다른 Agenda의 공유 자료는
  자동 삭제하지 않는다. [삭제·복구 흐름](#agenda-delete-recover)에서 영향·실패·완료를 확인한다.
- **남은 실제 선택**: 저장할 기본 내용과 미저장 복구 범위, 닫을 때 예약을 pause로 남길지
  삭제할지, Saved Agenda 자체의 휴지통·보관 기한·복구 범위다. 예약 삭제와 저장본 삭제는
  독립된 값이다. 같은 live 자원·실행의 기본 재사용과 소유 범위, Library·그룹의 지속·Agenda 관계도
  HUM-SURFACE의 같은 선택으로 유지한다. 원문·form 자동 보존은 [보존 정책](#decision-retention)과 함께 다룬다.
- **구체화할 부분**: 공유 실행의 소유 표시·저장 충돌 비교·종료 미확인 상태·PC별 재연결은
  기존 수명주기 안에서 검증한다. 종료 확인·일반 닫기·재연결마다 새 승인을 묻지 않는다.

#### 근거 보존·수정본·반출

- **추천**: 사용 중인 근거와 사용자가 고정한 snapshot을 우선 보존하고 미참조 임시 자료부터
  정리한다. 사용자 수정·Briefing 편집·주석 재연결은 새 revision으로 남긴다. 원문 권한
  철회가 확인된 관리 대상은 추가 열람·재사용·재공유를 제한하는 기본안을 제안한다.
  Export는 허용된 범위와 제외 참조를 설명하고 암호화 기본 켬, import는 새 사본·자동 실행 없음으로 둔다.
- **대안**: 기간 중심 보존, Briefing 읽기 전용, 필요한 원본을 모두 허용 범위에 넣을 수 있을 때만
  export하는 완전 묶음형. 권한이 허용하는 개인 과거 사본의 보존 여부는 조직 공유자료와 따로 정할 수 있다.
- **차이**: 참조 중심은 저장량 관리가 필요하고, 기간 중심은 과거 근거가 사라질 수 있다.
  부분 묶음은 빠르게 옮길 수 있지만 복원 한계 설명이 필요하다. 완전 묶음은 일부 자료 때문에
  이동이 막힌다. 이미 전달한 외부 사본의 회수는 어느 안도 보장하지 않는다.
- **form 별도 경계**: 살아 있는 Browser DOM의 일반 입력은 그대로 남길 수 있다. reload·
  runtime 종료 뒤 값을 복원할지는 별도 범위이며 비밀 필드 자동 저장을 기본안에 넣지 않는다.
- **초기화 비교**: 화면·입력 설정, 계정 연결·로컬 인증 정보, Agent·Engine Profile 정의,
  업무 기록을 따로 고르고 선택 범위를 미리 보여 주는 안을 추천한다. 내보내기는 선택적으로
  제공하고 검증된 백업 없는 기록 초기화는 되돌릴 수 없음을 확인한다. 한 번에 이 PC를 정리하는
  대안은 빠르지만 손실을 구별하기 어렵다. 어느 안도 원격 계정 삭제·다른 PC 로그아웃·외부 원본
  삭제를 로컬 초기화에 묶지 않는다. [초기화 흐름](#data-reset)의 적용·취소·복원 경로를 비교한다.
- **남은 실제 선택**: 보존·철회 후 열람 범위, Briefing 편집·공유 범위, 반출입 기본값은 서로
  독립적이다. 반출입은 `제외 내역이 있는 부분 묶음 허용 / 암호화 켬 / 새 사본`을 추천하되
  각 값을 따로 선택할 수 있다. 초기화의 범주·기록 복구 범위·백업 기본값도 별도 선택으로 남는다.

#### 이번 교정·지속 기억·조직 규칙

- **추천**: 현재 업무 조정은 바로 적용하고, 지속 기억은 명시적으로 저장한 개인 소유·선택
  Agent 범위에서 시작한다. 조직에는 권한상 허용된 후보만 제안하며 활성화는 owner나
  명시적인 수임자가 결정한다. 동일한 권한자가 의미 수락·승격·활성화를 함께 맡을 수 있다.
- **대안**: 사전 동의한 범위에서 개인 기억을 자동 축적하고 여러 Agent에 적용한다.
  조직도 미리 위임한 변경 유형에 한해 매번 사람이 응답하지 않고 검토·승격하도록 구성한다.
- **차이**: 추천안은 반복 설명·저장 조작이 늘어난다. 자동형은 잘못된 일반화가 전파될 수
  있어 변경 목록·적용 조건·망각·철회 관리가 필요하다.
- **정책 충돌 비교**: 강제 제한은 항상 지키되 변경 가능한 기본값보다 이번 명시적 지시를
  우선하고, 일회성 적용과 지속 설정 편집을 분리하는 안을 추천한다. 기본값 간 제안 순서와
  편집 주체는 [적용 기준 흐름](#policy-conflicts)에 있다. 조직 기본값을 모두 잠그는 대안은
  통제는 쉽지만 현장 조정이 줄고, 넓은 자동 편집 위임은 반복 작업 대신 오일반화의 전파 위험을 높인다.
- **남은 실제 선택**: 개인 기억을 자동으로 쌓을 범위와 조직의 편집·검토·승격 권한을 누구에게

- **남은 실제 선택**: 초대받은 사람이 처음 갖는 권한과 각자 Engine/명시적으로 위임한 공동

#### Office 파일의 첫 지원 범위

- **추천**: Office 파일은 preview·AI 판독·주석·외부 연결 편집과 변경 확인부터 제공하고,
  텍스트·코드 편집·diff는 기본 사람용 화면으로 둔다. 형식별 차이는 지원표에서 보여 준다.
- **대안**: 첫 출시부터 Office 원본의 풍부한 내부 편집을 필수로 포함한다.
- **차이**: 추천안은 편집 중 외부 앱을 오갈 수 있다. 대안은 서식·수식·변경 보존 검증이
  커진다. 첫 지원 범위를 좁히는 선택은 최종 내장 편집을 영구 비목표로 정하는 결정이 아니다.
- **남은 실제 선택**: 첫 출시에서 약속할 형식별 보기·판독·편집 수준과 우선 형식이다.
  위 출시 순서 제안으로 최종 제품 범위를 축소하거나 내장 편집을 비목표로 확정하지 않는다.
- **구체화할 부분**: parser·viewer 선택, 지원표, 외부 편집 후 변경 확인과 복원 충실도는
  조사·검증을 계속한다. 실제 확인하지 않은 형식에 `편집 지원`을 붙이지 않는다.
  [흐름·지원표](#flow-reading), [HUM-CODE-001](../../codex/egdesk-product-interaction-trace-atlas-editorial-ledger.md#hum-code-001),
  [HUM-SURFACE-001](../../codex/egdesk-product-interaction-trace-atlas-editorial-ledger.md#hum-surface-001).

**별도 승인 질문으로 늘리지 않고 비교할 UX**: 진행 중 Live·완료 Snapshot, 선택적 follow·
직접 pan 해제, 카메라 기반 집중 보기, OS 단계의 설명 배치는 기존 의미·권한 안에서
prototype으로 비교한다. 키보드·클릭 대안, 한글 조합 중 전송 방지, 모달/상세 닫기 후 초안·
focus 복귀도 같은 범위다. 최종 접근성 지원 수준은
[HUM-A11Y-001](../../codex/egdesk-product-interaction-trace-atlas-editorial-ledger.md#hum-a11y-001)에 남지만
이 기본 경로의 설계·검증은 기다리지 않는다.

### 4.3 각 화면을 성립시키는 기술 연결과 검증 과제

아래는 **검증 계획**이다. 각 시나리오의 화면·저장 상태·실제 호출/행동 기록을 대조해야
통과를 판단할 수 있으며, 문서 정제만으로 통과한 항목은 없다. PC·협업 분기는 로컬 mock으로
먼저 설계를 검사할 수 있지만 실제 기기·네트워크·권한 집행을 검증했다는 증거는 되지 않는다.

위 시나리오에는 [혼잡 배치](#ux-layout-review)의 긴 이름·여러 활동·좁은 비교 공간도 함께
적용한다. Agenda에서는 예약 하나의 일시정지와 현재 실행 중지를, 반출입·초기화에서는
목록 밖 선택과 실제 적용 식별자 집합을, 기억에서는 소유 범위와 회사/역할별 적용 조건을
대조한다. 조작면 관찰에서는 탭 구분 표시·실제 입력 방식·관찰자/제어자의 표시가 일치해야 한다.
각 경로의 진입·선택·확정·복귀 클릭을 실제 시작 상태별로 기록하고, 기본 정보·필요한 설명·
작성기를 함께 읽을 수 있는지 확인한다. 상세를 접거나 비교에 집중해도 과거/현재·원본/사본·
계정·대상 같은 판단 단서를 잃지 않아야 한다.

일반 복구·분할·검토에는 이 시나리오를 통과하기 위한 별도 owner 승인을 추가하지 않는다.
검증기법·renderer 연결·저장 크기 기준·Reader 동시성·model adapter의 정확한 hook은
공식 자료와 로컬 reference 구현을 대조해 선택한다. 미지원 플랫폼·도구 분기는 지원 범위와
fallback을 함께 표시한다. 저장 시간·복구 시간·정확한 quota 환산처럼 아직 측정하지 않은
숫자나 모든 외부 서비스의 중복 실행 방지 보장을 이 표에서 만들어 내지 않는다.
