## 1. Dev-Space 개요

EG-DESK-Dev-Space는 **연구/기획/도구 워크스페이스**이다. 애플리케이션 자체가 아니다. 비전 문서, 외부 레퍼런스(18개 이상 프로젝트), 기능 아이디어/PRD, 에이전트 정의, 스웜 오케스트레이션 문서를 포함한다. `src/` 디렉토리에는 현재 `CODEBASE_STRUCTURE.md`만 존재한다.

```
EG-DESK-Dev-Space     =/=     EG-DESK 애플리케이션
   (이 저장소)                 (미래: eg-desk/ 하위 디렉토리)

+----------------------------+     +-------------------------------+
| 기획 & 오케스트레이션       |     | 런타임 애플리케이션 코드       |
| - 에이전트 정의             |     | - Theia 확장 패키지           |
| - 비전 문서                 |     | - Electron 통합               |
| - 외부 레퍼런스             |     | - 커스텀 위젯                 |
| - 기능 PRD                  |     | - 빌드 시스템                 |
| - 스웜 워크플로우 문서       |     | - 테스트 인프라               |
+----------------------------+     +-------------------------------+
```

### 이 공간에 존재하는 것들

| 디렉토리 | 용도 | 수명 |
|-----------|------|------|
| `.claude/agents/` | 에이전트 정의 (YAML + 지시사항) | 영구, 버전 관리 |
| `.claude/docs/` | 모듈화된 CLAUDE.md 문서 | 영구, 버전 관리 |
| `.claude/commands/` | 슬래시 커맨드 / 스킬 | 영구, 핫 리로드 가능 |
| `references/` | 외부 저장소 + API 문서 (18개 이상) | 영구, `setup.sh`로 관리 |
| `ideas/confirmed/` | PM 승인된 PRD | 영구 |
| `ideas/brainstorming/` | 탐색적 기능 아이디어 | 준영구 |
| `docs/` | 프로젝트 문서, 비전, 프로덕션 문서 | 영구 |
| `subagent_reports/` | 임시 에이전트 커뮤니케이션 | **사용자 이슈 해결 시 삭제** |
| `setup.sh` / `setup.bat` | 레퍼런스 저장소 관리 | 영구 |

## 2. 개체 모델

스웜 시스템에서 상호작용하는 4가지 독립 개체. 각각 다른 권한, 도구, 책임을 가진다.

```
+============================================================+
|                     사용자 (USER, 인간)                      |
|  권한: 모든 전략적 선택의 최종 의사결정자                     |
|  행동: 요청, 승인, 거부, 보류                                |
|  시야: Main Thread 출력만 볼 수 있음 (내부 보고서 미노출)     |
+==============================|=============================+
                               |
                    요청 / 결정 / 피드백
                               |
                               v
+============================================================+
|              MAIN THREAD (메인 스레드, Claude Code)          |
|  권한: 오케스트레이터, 라우터, 종합자                         |
|  도구: 전부 (Read, Write, Edit, Bash, Glob, Grep 등)        |
|  행동: 요청 분류, 에이전트 호출, 보고서 읽기,                 |
|        결과 종합, 사용자에게 제시, 정리                       |
|  상태: 세션 동안 유지 (압축 가능)                             |
+==|====================|===================|================+
   |                    |                   |
   v                    v                   v
+===============+  +==============+  +==================+
| PM 에이전트   |  | 프레임워크    |  | 실행 에이전트     |
| (전략)        |  | 에이전트      |  | (구현)            |
|               |  | (분석)        |  |                   |
| - 비전 정합성 |  | - Theia       |  | - coding-agent    |
| - PRD 생성    |  | - Electron    |  | - ux-flow-sim     |
| - 기술 스택   |  |               |  | - test-strategy*  |
|   관리        |  | 읽기 중심,    |  | - runtime-test*   |
|               |  | 코드 분석     |  |                   |
| Read + Write  |  | Read + Bash   |  | Write/실행 역량   |
+===============+  +==============+  +==================+

  * = 제안됨 (아직 미생성)
```

### 개체 분리 규칙

| 개체 | 파일 생성 | 파일 읽기 | 코드 수정 | 의사결정 |
|------|:---:|:---:|:---:|:---:|
| **사용자** | - | - | - | 전략적: 승인/거부/보류 |
| **Main Thread** | 보고서 (내장 에이전트용) | 전부 | coding-agent 통해서 | 분류, 에이전트 선택 |
| **PM 에이전트** | PRD, 보고서, 브레인스토밍 | 비전 문서, 기술 스택 | technology-stack.md | 전략적 권고만 |
| **프레임워크 에이전트** | 보고서 (Bash 경유*) | 프레임워크 소스 코드 | 절대 안 함 | 기술 분석만 |
| **Coding 에이전트** | 소스 코드, 보고서 | 대상 + 연관 파일 | 직접 Write/Edit | 없음 (지시 따름) |

\* [치명적 버그](#8-치명적-버그) 참조 -- Write 도구 불일치

```
+-------------------+     파일 기반 프로토콜     +------------------+
|   MAIN THREAD     |<===========================>|    SUBAGENT      |
|                   |                              |                  |
| 1. Task(agent,    |  ---- 호출 (prompt) ------>  | 1. 작업 읽기     |
|    prompt)        |                              | 2. 작업 수행     |
|                   |  <-- 보고서 파일 생성 ------  | 3. 보고서 작성   |
| 2. 보고서 읽기    |                              |                  |
|                   |  ---- Edit (코멘트 추가) ->   | 4. (다회전)      |
```

### Subagent vs Agent Teams (하이브리드 모델)

```
+================================================================+
|                     MAIN THREAD (리더)                           |
|                                                                 |
|  +-- SUBAGENT (집중적, 반복 가능) -----+                         |
|  |   - 정밀한 도구 제어 (YAML)         |                         |
|  |   - 버전 관리되는 정의              |                         |
|  |   - 파일 기반 통신                  |   +-- AGENT TEAMS --+   |
|  |   - 영구 메모리 가능               |   | (협업적)          |   |
|  |   - 호출마다 새 컨텍스트            |   | - 실시간 메시징  |   |
|  |   - 보고서로 세션 복구 가능         |   | - 공유 태스크    |   |
|  |   - MCP: 불안정 (알려진 버그)       |   | - MCP: 더 안정   |   |
|  |                                     |   | - 세션 한정      |   |
|  |  사용 대상:                         |   | - 사전설정 불가  |   |
|  |  - 프레임워크 분석                  |   |                  |   |
|  |  - PM 자문                          |   | 사용 대상:       |   |
|  |  - 코드 생성                        |   | - 리서치+토론    |   |
|  |  - UX 검증                          |   | - 아키텍처 설계  |   |
|  |  - 빠른 리서치                      |   | - 코드 리뷰      |   |
|  +-------------------------------------+   | - 디버깅         |   |
|                                             +-----------------+   |
+================================================================+

판단: 정밀한 도구 필요?     --> Subagent
      에이전트끼리 대화?    --> Agent Team
      MCP 안정적으로?       --> Agent Team (우선)
      감사 추적 필요?       --> Subagent + 파일 보고서
```

## 5. 7가지 워크플로우 분기

### 마스터 흐름도

```
                          사용자 요청
                              |
                              v
                +---------------------------+
                |   MAIN THREAD 분류기       |
                |   (자동, 규칙 기반)         |
                +--+--+--+--+--+--+--------+
                   |  |  |  |  |  |
      +------------+  |  |  |  |  +----------+
      |     +---------+  |  |  +------+       |
      v     v            v  v         v       v
  Branch1 Branch2    Branch3      Branch4   Branch5
  단순    프레임워크  PM 주도      리서치    에이전트
  Q&A     분석       워크플로우    기술      생성
                       |  |         |  |
                      3a  3b       4A  4B
                    자문  구현    통합  학습
                       |    |       |
                       v    v       v
                     [사용자 결정]  [사용자 결정]
                       |    |       |
                       +----+---->--+ (전환 가능)
```

---

### Branch 1: 단순 질의응답

```
사용자: "src에 어떤 파일이 있어?"
         |
         v
  Main Thread가 직접 답변
  도구: Read, Glob, Grep, Bash
         |
         v
  사용자에게 응답 (인라인)

  생성 아티팩트: 0
  서브에이전트 세션: 0
  보고서: 0
```

**갭**: 분류 검증 없음, "단순"이 "복잡"으로 넘어가는 경계 없음

---

### Branch 2: 프레임워크 질문

```
사용자: "Theia는 파일 와처를 어떻게 처리해?"
         |
         v
  Main Thread 선택: theia-analyzer-agent 또는 electron-analyzer-agent
         |
         v
  Task(agent: "[프레임워크]-analyzer-agent",
       prompt: "[주제] 분석.
                CREATE REPORT FILE:
                subagent_reports/YYYYMMDD_[주제]-[fw]-analysis.md")
         |
         v
  에이전트가 프레임워크 소스 코드 읽기 (5-30개 파일)
  에이전트가 보고서 작성
         |
         v
  Main Thread가 보고서 읽기 -> 사용자에게 제시
         |
    +----+----+
    |         |
    v         v
  만족?     후속 질문?
    |         |
    v         v
  보고서    MT가 <!-- MT: [질문] --> 코멘트 추가
  삭제      에이전트 재호출 (UPDATE 지시)
            재읽기 -> 제시 -> 반복
```

**아티팩트**: 임시 보고서 1개, 영구 0개
**갭**: Write 도구 불일치 (버그 참조), 병렬 위임 분기 미문서화

## 7. 플랫폼 제약사항

아키텍처를 결정짓는 7가지 검증된 제약. 각각 공식 문서와 GitHub 이슈에서 확인됨.

### 제약사항 요약

```
+---+----------------------------------+-----------+----------------------------+
| # | 제약사항                          | 심각도     | 우회 방법                   |
+---+----------------------------------+-----------+----------------------------+
| 1 | Subagent .md 핫 리로드 안 됨      | 높음      | 세션 재시작, Skills 리로드   |
| 2 | Agent Teams: 사전 설정 불가        | 보통      | 스폰 프롬프트, CLAUDE.md   |
| 3 | Subagent 무상태                    | 높음      | 파일 기반 보고서, 메모리    |
| 4 | 파일 기반 통신 오버헤드            | 보통      | 내구성 위해 유지            |
| 5 | 컨텍스트 윈도우/압축               | 높음      | 단기 팀, 새 subagent 컨텍스트 |

+---+----------------------------------+-----------+----------------------------+
```

### 제약사항 상세

**C1: Subagent .md 핫 리로드 안 됨** (GitHub #6497 OPEN)
- `.claude/agents/*.md` 편집 시 세션 재시작까지 반영 안 됨
- `/agents` 명령: 목록 표시만, 리로드 안 됨 (실증 검증 2026-02-06)
- `/compact` 명령: 리로드 안 됨 (실증 검증 2026-02-07)
- Skills (`.claude/commands/*.md`)는 핫 리로드 됨 -- 동적 행동에 활용
- **유일한 방법: 세션 재시작**

**C2: Agent Teams 사전 설정 불가**
- 팀원은 순수 자연어 스폰 프롬프트로만 정의
- YAML 프론트매터 없음, 버전 관리 안 됨
- 우회: `.claude/prompts/team-roles/`에 역할 설명 저장

**C3: Subagent 무상태**
- 매 호출 = 새 컨텍스트 (대화 이력 없음)
- 신기능: `memory: project` 필드로 MEMORY.md를 통한 교차 세션 학습 가능
- 파일 기반 보고서가 호출 간 영구 상태 역할

**C4: 파일 기반 통신 오버헤드**
- 상호작용당 최소 3회 파일 I/O (쓰기 + 읽기 + 삭제)
- 하지만: 세션 복구, 감사 추적, 디버깅 가능성 제공
- Agent Teams 메시징은 실시간이지만 일회성 (재시작 시 소실)

**C5: 컨텍스트 윈도우 압박**
- Subagent: 메인 컨텍스트 압축에 면역 (매 호출 새 컨텍스트)
- Agent Teams: 각 팀원이 컨텍스트 누적, 압축 대상
- 리더의 컨텍스트는 팀원 메시지마다 증가

**C6: 커스텀 Subagent에서 MCP 불안정** (다수 GitHub 이슈 오픈)
- #13605, #13898, #19526, #14496, #7296
- 커스텀 subagent가 MCP 도구 호출을 환각(hallucinate)함
- 백그라운드 subagent: MCP 명시적으로 사용 불가
- Agent Teams: 더 나음 (풀 Claude 인스턴스) 하지만 신기능/미검증

**C7: 도구 권한**
- Subagent: YAML `tools` 허용 목록으로 정밀 제어
- Agent Teams: 리더의 권한 상속, 조악한 제어
- 스폰 후 팀원별 모드 변경 가능하나 스폰 시점에는 불가

### 9.1 테스팅 레이어 설계

테스팅 갭을 메우기 위한 신규 에이전트 2개:

```
현재 상태:
  ux-flow-simulator-agent -> 코드 경로를 정신적으로 추적 (실행 없음)
  (그 외 없음)            -> 테스트 생성 없음, 테스트 실행 없음

제안 상태:

  ux-flow-simulator-agent   -> 정적 코드 검증 (유지)
          |
          v
  test-strategy-agent (신규) -> 테스트 계획 + .spec.ts 스켈레톤 생성
  도구: Read, Write, Edit, Glob, Grep, WebSearch
  Bash 없음 (코드 분석만, 실행 없음)
          |
          v
  runtime-test-agent (신규)  -> Electron 앱 실행, Playwright 테스트
  도구: Bash, BashOutput, KillShell, Read, Write, Glob, Grep
  사용: npx playwright test (Bash 기반, 불안정한 MCP 대신)
  타임아웃: 300000ms (5분) / 테스트 배치

  Phase 2 진화: MCP 안정화 시 runtime-test-agent를 Agent Teams로 마이그레이션
```

**워크플로우 통합 (Branch 3b의 Step 9.5와 9.7)**:
```
coding-agent 완료
    |
    v
test-strategy-agent가 테스트 계획 + 스켈레톤 생성
    |

Main Thread가 앱 빌드 (Bash: yarn build)
    |
    v
runtime-test-agent가 테스트 실행 (Bash: npx playwright test)
```

### 9.2 모듈 구조 철학

앱 코드 존재 시 적용할 Theia 기반 분해 규칙:

```
PM에서 기능 요청 도착
         |

  패키지 결정: 새 패키지 or 기존 확장?
         |

  플랫폼 레이어 (Theia 필수 분리):
  +-- common/          공유 IPC 인터페이스

  +-- electron-main/    Electron 메인 프로세스 (선택)
         |
         v
  파일 명명:
  +-- *-frontend-module.ts   ContainerModule (DI 와이어링)
  +-- *-contribution.ts      커맨드, 메뉴, 키바인딩
  +-- *-widget.tsx            React UI 컴포넌트

         |
         v
  조직화 원칙:
  1. 기능 기반 패키지 (레이어 기반 아님)
  2. 플랫폼 분리는 구조적 (Theia 요구사항)
```

### 9.3 동적 에이전트 생명주기

에이전트는 6-상태 생명주기를 거친다:

```
[아이디어] --> [초안] --> [테스트] --> [활성] --> [보관]
               |           |          |  |
               |           |          |  +--> [포크] --> 새 [초안]
               |           +--> [거부됨]
               +--> [폐기됨]

디렉토리:
  .claude/agents/staging/    초안 + 테스트 에이전트
  .claude/agents/            활성 에이전트 (프로덕션)
  .claude/agents/archive/    은퇴 에이전트
  .claude/agents/templates/  에이전트 스캐폴드 (호출 불가)

승격 기준:
  초안 -> 테스트:  YAML 유효, 지시사항 일관, 도구 적절
  테스트 -> 활성: 2회 이상 성공적 작업 완료, 일관된 품질
  활성 -> 보관: 30일 이상 미사용 또는 대체됨

레지스트리:
  .claude/agents/registry.yaml  기계 판독 가능한 에이전트 인덱스
  /refresh-agent-registry        재생성 슬래시 커맨드
```

**4가지 에이전트 템플릿** (제안된 스캐폴드):
1. **프레임워크 분석기**: 읽기 중심, 코드베이스 우선 분석
2. **리서치 에이전트**: WebSearch + 종합
3. **코드 실행기**: Write/Edit 중심, 지시 따르기
4. **검증기/체커**: 읽기 전용 검증
