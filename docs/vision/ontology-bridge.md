# 온톨로지 브릿지: 현실 세계와 디지털 세계 사이의 간극

**버전**: v1.1
**작성일**: 2026년 3월 25일
**위치**: EG-DESK Vision

---

## 요약

현실 세계에는 두 가지 축의 풍부함이 있다: **객체**(사물)와 **장소**(공간). 책은 두껍고 영수증은 얇다. 서재는 크고 조용하며 서랍은 작고 개인적이다. 인간은 이 물리적 속성을 무의식적으로 인식하여 "무엇을 어디에 둘지" 즉시 판단한다.

디지털 세계에서는 이 두 축 모두가 평탄화된다. 책과 영수증은 똑같은 `.pdf`가 되고, 서재와 서랍은 똑같은 "폴더"가 된다. 현재 파일시스템이 이 차이를 표현하는 유일한 수단은 **폴더명과 위치**뿐이며, 이 분류를 사용자가 수동으로 설계하고 유지해야 한다.

EG-DESK는 이 간극에 **LLM 기반 Operation Layer**를 놓는다. 현실 세계의 온톨로지(존재론적 분류)를 디지털에 자동으로 매핑하여, 사용자가 "이 파일을 어디에 넣지?"라는 질문에서 해방되는 것이 목표다.

## 1. 문제: 두 축의 평탄화

### 1.1. 객체의 평탄화 -- "무엇"이 사라진다

현실 세계에서 인간은 사물의 물리적 속성으로 즉시 분류한다:

| 물리적 속성 | 현실의 분류 | 디지털 표현 |
|---|---|---|
| 두꺼운 제본, 목차, ISBN | 책 → 서재에 꽂는다 | `.pdf` |
| 얇은 종이, 날짜, 금액 | 영수증 → 장부에 끼운다 | `.pdf` |
| A4 용지, 서명란, 직인 | 계약서 → 금고에 보관한다 | `.pdf` |
| 사진, 색감, 프레임 | 가족사진 → 앨범에 넣는다 | `.jpg` |
| 사진, 수치, 축 | 데이터 차트 → 보고서에 첨부한다 | `.jpg` |

디지털화 과정에서 이 풍부함이 사라진다:

```
현실 세계                    디지털 세계
─────────                    ─────────
책 (두꺼움, 목차, ISBN)  →   book_2026.pdf
영수증 (얇음, 날짜, 금액) →   receipt_march.pdf
계약서 (서명란, 직인)     →   contract_v2.pdf

전부 같은 .pdf → 같은 폴더 아이콘 → 같은 조작 방식
```

### 1.2. 장소의 평탄화 -- "어디"가 사라진다

객체만 평탄화되는 것이 아니다. 객체를 담는 **장소** 역시 현실에서는 고유한 물리적 속성을 가진다:

| 현실의 장소 | 물리적 속성 | 디지털 구현 |
|---|---|---|
| 서재 | 큰 방, 문 있음, 여러 사람 출입 | git-managed TSV 파일 |
| 선반 | 책상 옆 가구, 내 것, 손 닿는 곳 | 로컬 폴더 (git clone) |
| 금고 | 잠금장치, 두꺼운 벽, 제한된 접근 | 암호화 폴더 + ACL |
| 게시판 | 복도에 걸림, 누구나 열람 | Slack 채널 |
| 회의실 | 예약제, 시간 제한, 물리적 격리 | Zoom 링크 |
| 서랍 | 개인 공간, 작고 잠금 가능 | 로컬 스토리지 |
| 우편함 | 수신 전용, 외부→내부 단방향 | 이메일 inbox |
| 접견실 | 외부인 전용, 격식, 제한된 구역 | 고객 포털 |
| 창고 | 대용량, 비활성, 접근 빈도 낮음 | cold storage / archive |

현실의 장소는 다섯 가지 암묵적 속성을 가진다:

| 속성 | 현실의 작동 | 디지털의 표현 |
|---|---|---|
| **규모** | 서재 > 선반 > 서랍 (보면 안다) | 전부 "폴더" (구분 불가) |
| **접근 제어** | 금고 > 사무실 > 게시판 (물리적 장벽) | 전부 "권한 설정" (숫자/체크박스) |
| **가시성** | 게시판 = 공개, 서랍 = 비공개 (위치가 곧 공개 범위) | 전부 "공유 설정" |
| **영속성** | 서재 = 영구 보관, 책상 = 임시 작업 | 전부 "파일" (삭제 전까지 영구) |
| **공유 모델** | 회의실 = 예약제, 게시판 = 자유 | 전부 "링크 공유" |

디지털에서 이 다섯 가지 속성은 모두 **"폴더 + 권한 설정"**으로 평탄화된다. 금고와 게시판의 차이가 ACL 체크박스 하나로 축소되는 것이다.

### 1.3. 두 축이 결합할 때 -- 복합 평탄화

현실에서는 객체와 장소가 자연스럽게 결합한다:
- 책은 서재에 꽂는다 (객체의 속성이 장소를 결정)
- 영수증은 장부에 끼운다 (객체의 속성이 장소를 결정)
- 기밀 문서는 금고에 넣는다 (객체의 중요도가 장소의 보안 수준을 결정)

이 결합이 디지털에서는 완전히 끊어진다:
- 책이든 영수증이든 `.pdf` → 같은 폴더에 들어갈 수 있다
- 기밀이든 공개든 파일 → 같은 드라이브에 존재한다
- 객체가 장소를 결정하지 않는다 → **사용자가 매번 수동으로 결정**해야 한다

이것이 디지털 관리 부채(Digital Management Debt)의 첫 번째 원인이다.

### 1.4. 매핑의 비대칭 -- 1:1이 아니다

평탄화에 더해, 현실과 디지털 사이의 매핑 자체가 비대칭이다. 현실의 하나가 디지털의 하나에 대응하지 않는다:

**1:N -- 하나의 디지털 객체가 여러 현실 객체에 대응**

```
report_q4.pdf (디지털: 파일 1개)
    │
    ├── 경영진용 보고서  → 임원실에 비치
    ├── 팀 회의 자료    → 회의실에서 발표
    └── 감사 증빙       → 금고에 보관
```

같은 파일이지만 현실에서는 세 가지 다른 객체이고, 각각 다른 장소에 속한다. 파일시스템에서는 하나의 경로에만 존재할 수 있으므로, 나머지 두 맥락은 사용자의 기억에만 의존한다.

**N:1 -- 여러 디지털 객체가 하나의 현실 객체에 대응**

```
cover.jpg + chapter1.md + chapter2.md + index.json + styles.css
    │
    └── 현실: "한 권의 책"
```

현실에서는 하나의 물리적 객체(책)를 손에 들 수 있지만, 디지털에서는 5개의 파일로 흩어져 있다. 사용자는 이 5개를 "하나의 책"으로 인식해야 하지만, 파일시스템은 이 관계를 표현하지 못한다.

**N:M -- 현실과 디지털이 다대다로 얽힌다**

```
프로젝트 폴더 (수백 파일)
    │
    ├── "하나의 사업"       ← 사업계획서, 예산, 일정
    ├── "여러 산출물"       ← 각각 독립된 결과물
    ├── "관련 계약들"       ← 법적 문서 묶음
    └── "회의 기록들"       ← 시간순 아카이브

각 현실 객체가 여러 파일을 포함하고,
각 파일이 여러 현실 객체에 속한다.
```

이 비대칭이 관리 부채를 기하급수적으로 증가시킨다. 1:1 매핑만 존재했다면 폴더 구조로 충분했겠지만, 현실은 1:N, N:1, N:M이 혼재한다. 기존 파일시스템은 이 복잡성을 사용자에게 전가하고 있으며, 이것이 디지털 관리 부채의 두 번째 원인이다.

EG-DESK의 LLM Operation Layer는 이 비대칭 매핑을 자동으로 추적한다:
- 하나의 파일이 여러 공간에 동시 존재할 수 있다 (1:N 해소)
- 여러 파일을 하나의 현실 객체로 묶어 표현할 수 있다 (N:1 해소)
- 이 관계를 LLM이 내용 기반으로 자동 추론한다 (N:M 해소)

### 1.5. 관리 부채의 현실

사용자들이 디지털 세계를 어려워하는 이유는 기술 자체가 아니라 **현실 세계의 직관이 작동하지 않기 때문**이다:

- "이 파일 어디에 저장하지?" -- 현실에서는 고민할 필요 없는 질문
- "다운로드 폴더에 1,247개 파일" -- 현실의 책상에 1,247권의 책을 쌓아두는 사람은 없다
- "같은 파일이 3군데에 복사" -- 현실에서 같은 책을 3권 사는 사람은 없다
- "이름이 `최종_최종_진짜최종.pdf`" -- 현실에서 책 표지를 매번 다시 쓰지 않는다
- "이 채널이 회의실인지 게시판인지" -- 현실에서는 문을 열면 바로 안다

이 모든 문제는 **파일시스템이 현실의 온톨로지를 반영하지 못하기 때문**에 발생한다. 객체도, 장소도.

### 1.6. 기업 환경에서의 증폭

개인 수준의 관리 부채는 기업 환경에서 기하급수적으로 증폭된다:

| 현실의 기업 공간 | 암묵적 속성 | 디지털 평탄화 |
|---|---|---|
| 부서별 사무실 | 물리적 분리, 소속감, 벽 | Teams/Slack 채널 하나 |
| 임원실 | 격리, 기밀, 의사결정 공간 | 같은 Slack에 private 채널 |
| 보안 서버실 | 출입 카드, CCTV, 항온항습 | 네트워크 세그먼트 설정값 |
| 접수처 | 외부인 최초 접점, 안내 | 웹 폼 하나 |
| 자료실 | 부서 공유, 열람 기록 관리 | SharePoint 폴더 |
| 우편실 | 수발신 중앙 허브, 분류 담당자 | 메일 서버 + 규칙 |

기업에서는 수십 개의 물리적 공간이 각각 고유한 보안 등급, 접근 패턴, 업무 흐름을 가진다. 이것이 디지털에서는 "폴더 + 권한 + 링크"로 획일화되면서, IT 관리자가 수천 개의 ACL 규칙으로 현실의 공간 속성을 수동 재현해야 한다.

## 2. 해결: LLM Operation Layer

### 2.1. 개념

EG-DESK는 현실 세계의 온톨로지와 디지털 세계 사이에 **LLM 기반 Operation Layer**를 놓는다. 이 레이어는 객체와 장소 두 축 모두를 다룬다:

```
┌──────────────────────────────────────────────────────────┐
│                  현실 세계 (Physical)                      │
│                                                           │
│  객체: 책, 영수증, 계약서, 사진, 메모, 도면, 편지...       │
│     → 물리적 속성으로 즉시 식별                            │
│                                                           │
│  장소: 서재, 금고, 게시판, 회의실, 서랍, 창고...            │
│     → 규모/접근/가시성/영속성/공유 모델로 즉시 구분         │
│                                                           │
│  결합: 객체의 속성 → 장소를 자동 결정                      │
│     "기밀 계약서는 당연히 금고에"                           │
└────────────────────────┬─────────────────────────────────┘
                         │
           ┌─────────────▼─────────────┐
           │   LLM Operation Layer      │
           │                            │
           │  객체 인식:                 │
           │    "이 .pdf는 영수증이다"   │
           │    "이 .jpg는 가족사진이다" │
           │                            │
           │  장소 매핑:                 │
           │    "영수증 → 장부 공간"     │
           │    "기밀 → 보안 공간"       │
           │                            │
           │  결합 추론:                 │
           │    객체 속성 → 적절한 장소  │
           │    장소 속성 → 적절한 접근  │
           └─────────────┬─────────────┘
                         │
┌────────────────────────▼─────────────────────────────────┐
│                  디지털 세계 (Digital)                      │
│                                                           │
│  객체: .pdf, .jpg, .md, .ts, .json (확장자로만 구분)       │
│  장소: 폴더, 드라이브, 채널, 링크 (권한 설정으로만 구분)    │
│  결합: 없음 (사용자가 매번 수동 결정)                      │
└──────────────────────────────────────────────────────────┘
```

LLM이 하는 일:
1. **객체 인식**: 파일의 실제 내용을 이해하여 현실 세계의 카테고리를 추론
2. **장소 매핑**: 디지털 공간의 속성(규모, 접근, 가시성, 영속성, 공유)을 현실의 장소와 대응
3. **결합 추론**: 객체의 속성으로부터 적절한 장소를 자동 결정
4. **관계 매핑**: 객체 간, 장소 간, 객체-장소 간의 관계를 추적

### 2.2. 현실 메타포의 디지털 구현 -- 객체와 장소

EG-DESK는 현실 세계의 정보 관리 메타포를 디지털로 충실히 옮긴다. 객체와 장소 모두:

**장소 (공간의 구현)**:

| 현실 메타포 | 암묵적 속성 | EG-DESK 구현 | 기술적 실체 |
|---|---|---|---|
| **서재** (Library) | 큰 방, 공유, 영구 보관 | 글로벌 레퍼런스 등록부 | `reference-registry.tsv` (user level, git-managed) |
| **선반** (Shelf) | 내 가구, 손 닿는 곳 | 프로젝트별 로컬 참고자료 | `references/[name]/` (project level, git clone) |
| **책상** (Desk) | 작업면, 임시, 시각적 | 작업 캔버스 | HTML Infinite Canvas (Electron + WebContentsView) |
| **서랍** (Drawer) | 개인, 숨겨진, 도구 | 설정/도구 보관 | `.claude/`, config files |

**객체 (사물의 구현)**:

| 현실 메타포 | 물리적 속성 | EG-DESK 구현 | 기술적 실체 |
|---|---|---|---|
| **창** (Window) | 열린 문서, 활성 상태 | 개별 작업 영역 | WebContentsView instances on Canvas |
| **메모** (Note) | 작은 종이, 부착 가능 | 인라인 기록 | Canvas 위의 텍스트 노드 |
| **참고서** (Reference) | 두꺼운 책, 펼쳐둠 | 선반에서 꺼낸 자료 | git clone된 소스코드/문서 |

핵심 원리: **사용자가 디지털 구현을 의식하지 않는다.** "tsv 파일을 편집한다"가 아니라 "서재에 책을 꽂는다"로 인식한다. "ACL을 설정한다"가 아니라 "금고에 넣는다"로 인식한다.

### 2.3. 서재-선반-책상 시스템 상세

현재 구현된 레퍼런스 관리 시스템이 이 철학의 첫 번째 실현이다. 세 장소가 각각 고유한 속성을 가지며, 이 속성이 기술적 구현을 결정한다:

```
서재 (EG-Library)                          ← 글로벌, 모든 프로젝트가 공유
│  현실 속성: 큰 방, 영구 보관, 목록 열람
│  디지털 대응: git-managed (버전 관리 = 영구), TSV (목록 = 열람)
│  구현: ~/.claude/reference-registry.tsv
│  특성: 가볍다 (메타데이터만, 실제 코드 없음)
│
├── 선반 A (Project Alpha)                 ← 프로젝트별, 실제 자료
│   현실 속성: 내 가구, 손 닿는 곳, 실물
│   디지털 대응: 로컬 (내 것), clone (실물), 프로젝트 디렉토리 (손 닿는 곳)
│   구현: references/ (git clone)
│   특성: 무겁다 (실제 소스코드)
│   명령: setup.sh → 서재에서 골라 선반에 꽂기
│
├── 선반 B (Project Beta)
│   다른 프로젝트, 다른 참고자료 조합
│
└── 책상 (EG-DESK Canvas)                  ← 실시간 작업 공간
    현실 속성: 작업면, 임시, 시각적 배치, 동시에 여러 개
    디지털 대응: Canvas (시각적), WebContentsView (동시 다수), 세션 (임시)
    구현: Infinite Canvas + WebContentsView
    특성: 시각적, 공간적, 동시에 여러 개
```

이 흐름이 현실과 정확히 대응한다:
- 서재에서 책을 고른다 (registry 조회)
- 선반에 꽂는다 (git clone)
- 필요할 때 책상에 펼친다 (canvas에 window 배치)

사용자는 이 과정에서 "tsv", "git clone", "WebContentsView"를 알 필요가 없다. 서재가 git인 이유는 서재의 현실 속성(영구 보관, 버전 관리, 공유)이 git의 특성과 일치하기 때문이지, 사용자에게 git을 노출하기 위함이 아니다.

## 3. 왜 기존 시스템은 실패하는가

### 3.1. 폴더 기반 파일시스템의 한계

객체 축:

| 현실의 직관 | 파일시스템의 제약 |
|---|---|
| 하나의 책이 여러 맥락에 속한다 | 하나의 파일은 하나의 폴더에만 존재 |
| 책의 크기, 색상, 질감으로 분류한다 | 파일의 내용은 아이콘에 반영 안 됨 |
| 자주 보는 책은 가까이 둔다 | 최근 사용은 별도 메뉴 (직관적이지 않음) |

장소 축:

| 현실의 직관 | 파일시스템의 제약 |
|---|---|
| 금고와 게시판은 보면 바로 구분된다 | 폴더는 전부 같은 아이콘 |
| 회의실은 들어가야 쓸 수 있다 | 폴더는 경로만 알면 접근 (물리적 장벽 없음) |
| 창고는 멀고, 서랍은 가깝다 | 모든 폴더가 같은 클릭 거리 |
| 공간의 크기가 수용량을 암시한다 | 폴더 크기는 속성에서 확인해야 |

### 3.2. 태그/검색 기반 시스템의 한계 (Notion, Obsidian 등)

태그 시스템은 객체 축의 "단일 위치" 제약을 부분적으로 풀지만:
- **태그 관리가 새로운 부채**가 됨 (태그 설계, 일관성 유지, 태그 폭발)
- **장소 축은 전혀 해결하지 못함** -- 모든 것이 리스트/테이블로 평탄화
- **공간감 부재** -- 서재의 웅장함도, 서랍의 아늑함도 없다
- **사용자가 분류 체계를 설계해야 함** -- 현실에서는 불필요한 인지 부하

### 3.3. AI 보조 도구의 한계 (현재 세대)

ChatGPT, Claude, Copilot 등:
- 파일을 "이해"할 수 있지만 **배치하지 않는다** (객체 인식 O, 장소 매핑 X)
- 대화 안에서만 맥락이 살아있고 **파일시스템에 반영 안 됨**
- 공간의 개념 자체가 없다 -- 모든 것이 대화 스레드라는 단일 공간

### 3.4. 기업 도구의 한계 (현재 세대)

SharePoint, Google Workspace, Confluence 등:
- 현실의 공간 속성을 **ACL 규칙**으로 수동 재현 (규모 → 폴더 계층, 접근 → 권한 매트릭스)
- IT 관리자가 수천 개의 권한 규칙으로 "금고"와 "게시판"의 차이를 표현
- 사용자는 이 구조를 이해하지 못하고 "공유 드라이브 어디에 올려야 하지?" 반복
- **권한 실수 = 보안 사고** -- 현실에서는 기밀 문서를 게시판에 붙이는 실수가 물리적으로 어렵지만, 디지털에서는 클릭 한 번

## 4. EG-DESK의 접근: Operation Layer 설계 원칙

### 4.1. 현실 세계의 직관을 존중한다

사용자가 "이건 참고자료야"라고 인식하면, 시스템이 자동으로:
- **객체 인식**: 이것이 어떤 종류의 자료인지 파악
- **장소 매핑**: 서재에 등록하고, 관련 프로젝트 선반에 배치하고
- **장소 속성 적용**: 접근 제어, 가시성, 영속성을 장소의 특성에 맞게 설정
- **표면화**: 필요 시 책상에 띄운다

사용자가 결정하는 것: **"이건 뭐다"** (what)
시스템이 처리하는 것: **"어디에, 어떻게, 누구에게"** (where, how, who)

### 4.2. 메타포는 구현과 분리한다

| 사용자가 보는 것 | 시스템이 실행하는 것 |
|---|---|
| "서재에 등록" | `reference-registry.tsv`에 행 추가 |
| "선반에 꽂기" | `project-refs.txt` 추가 + `git clone` |
| "책상에 펼치기" | Canvas에 WebContentsView 생성 |
| "금고에 넣어" | 암호화 + 접근 제한 ACL 설정 |
| "게시판에 올려" | 공개 채널/공간에 배치 + 열람 로그 활성화 |
| "이 파일은 계약서야" | 메타데이터 태깅 + 보안 공간 자동 배치 |

구현 기술이 바뀌어도 (tsv → DB, git clone → symlink, ACL → ABAC 등) 사용자 경험은 동일하다. 서재는 영원히 서재이고, 금고는 영원히 금고다.

### 4.3. LLM은 번역기다

LLM의 역할은 "현실의 의도 → 디지털 조작"을 번역하는 것이다. 객체와 장소 두 축 모두에서:

```
사용자: "아까 그 논문 좀 다시 볼래"
                │
    LLM 번역:  │
    객체 인식:  "논문" → .pdf 중 학술 논문 형식
    시간 추론:  "아까" → 최근 세션에서 열었던 파일
    장소 결정:  "다시 볼래" → 책상(Canvas)에 표시
                │
    실행: 해당 PDF를 Canvas 위에 표시
```

```
사용자: "이 계약서 안전하게 보관해줘"
                │
    LLM 번역:  │
    객체 인식:  "계약서" → 법적 문서, 서명 포함
    속성 추론:  "안전하게" → 높은 보안 등급
    장소 결정:  금고(보안 공간) + 접근 제한 + 암호화
                │
    실행: 보안 스토리지에 저장 + ACL 설정
```

사용자는 파일 경로, 확장자, 뷰어 선택, 권한 설정을 신경 쓰지 않는다.

### 4.4. 관리 부채를 시스템이 흡수한다

현재: 사용자가 폴더 구조 설계 → 파일 분류 → 권한 설정 → 정리 → 유지보수
목표: LLM이 분류 체계 + 공간 속성 추론 → 자동 배치 → 사용자는 "쓰기"에만 집중

```
관리 부채 이동:
  개인 사용자 ───→ LLM Operation Layer
  (폴더 관리)       (객체 분류 + 장소 배치)

  기업 IT 관리 ───→ LLM Operation Layer
  (ACL 수천 개)     (장소 속성 자동 매핑)
```

## 5. 로드맵: 온톨로지 브릿지 확장

### Phase 1: 레퍼런스 관리 (현재)
- 서재/선반/책상 메타포 -- 장소 3계층 구현 ✅
- LLM이 서재 등록/선반 배치 보조 ✅
- WM Agent가 파일 구조 인텔리전스 제공 ✅
- 장소 속성: 규모(서재>선반>책상), 영속성(서재=영구, 책상=세션) ✅

### Phase 2: 범용 파일 분류 + 장소 확장
- 사용자의 모든 파일에 대해 LLM이 객체 온톨로지 추론
- "이 PDF는 영수증이다" → 자동으로 장부 공간에 배치
- 장소 메타포 확장: 금고(보안), 게시판(공개), 창고(아카이브)
- 멀티-컨텍스트: 하나의 파일이 여러 공간에 동시 존재

### Phase 3: 관계 그래프 + 기업 공간
- 파일 간 관계를 LLM이 자동 추론 (참조, 의존, 버전, 파생)
- Canvas 위에서 관계를 시각적으로 탐색
- 기업 공간 메타포: 부서 사무실, 임원실, 접수처, 자료실
- 장소 속성의 조직적 적용: 부서별 접근, 보안 등급, 감사 추적

### Phase 4: 앰비언트 분류
- 파일 생성/수정 시 실시간으로 객체 분류 + 장소 배치 업데이트
- 사용자 행동 패턴에서 분류 규칙 학습
- "이 사람은 월말에 영수증을 정리한다" → 선제적 장부 배치
- 장소의 동적 생성: 프로젝트가 시작되면 자동으로 작업 공간 구성

## 6. 철학적 배경

### 6.1. 온톨로지(Ontology)와의 연결

철학에서 온톨로지는 "존재하는 것들의 분류 체계"다. 현실 세계에는 수천 년간 발전한 암묵적 온톨로지가 있다:
- 도서관학: 듀이십진분류법, LC 분류법 (객체의 분류)
- 건축학: 공간 프로그래밍, 동선 설계 (장소의 분류)
- 회계학: 계정 과목 체계 (객체 + 장소의 결합)
- 법학: 법률 문서 분류 체계 + 보안 등급 (객체 + 장소의 결합)
- 일상: "이건 주방에, 저건 서재에" (직관적 결합)

디지털 세계는 이 온톨로지를 **파일 확장자 + 폴더 구조 + 권한 설정**으로 극도로 단순화했다. EG-DESK는 LLM을 통해 이 잃어버린 풍부함을 객체와 장소 두 축 모두에서 복원한다.

### 6.2. 메타버스와의 차이

메타버스 접근: 현실 세계를 3D로 시뮬레이션 (시각적 복제 -- 객체와 장소의 외형을 복제)
EG-DESK 접근: 현실 세계의 **분류 체계/인지 모델**을 디지털에 이식 (개념적 복제 -- 객체와 장소의 속성을 복제)

메타버스가 "현실을 눈에 보이게 만들겠다"라면, EG-DESK는 "현실의 직관이 디지털에서도 작동하게 만들겠다"이다. 3D 서재를 렌더링하는 것이 아니라, "서재에 꽂는다"는 행위의 본질(분류 + 보관 + 검색 가능성)을 디지털로 구현한다. 3D 금고를 만드는 것이 아니라, "금고에 넣는다"는 행위의 본질(접근 제한 + 암호화 + 감사 추적)을 디지털로 구현한다.

## 7. 자기 참조: 이 문서 자체가 증명

이 문서의 저장 위치를 결정하는 과정 자체가 이 문서가 설명하는 문제를 증명했다:

> "이거 문서화 하려면 어디에 넣어야 하지? (이거봐 나도 힘들어 하잖아)"

이 문서는:
- **비전**이기도 하고 (→ `docs/vision/`)
- **아키텍처 철학**이기도 하고 (→ `docs/references/`)
- **UX 원칙**이기도 하고 (→ `ideas/confirmed/`)
- **현재 시스템 설계 근거**이기도 하다 (→ `.claude/docs/`)

하나의 객체(이 문서)가 여러 장소에 동시에 속해야 하지만, 기존 파일시스템에서는 하나만 골라야 한다. EG-DESK가 완성되면, 이 문서는 네 공간 모두에 존재하면서 각 맥락에서 적절한 모습으로 나타날 것이다.

지금은 `docs/vision/`에 넣었다. 이것이 최선의 선택인지는, 아직 인간이 판단해야 하기 때문이다. EG-DESK가 이 판단을 대신하는 날이 이 프로젝트의 완성이다.
